# Blitzdrache0

Blitz（稲妻）+ Drache（竜）。Rust + Vulkan による自作ゲームエンジン。

デバイスの理論値性能を志向し、汎用エンジン（Unity/Unreal）が払う汎用性の税金を避けるため、
Vulkan を生バインディング（ash）で直接扱う。安全性は「あらゆる使い方を安全にする汎用ラッパー」
ではなく「このエンジンの使い方だけを露出する狭い型安全層」で担保する。

## アーキテクチャ

```
ゲームロジック（安全なRust）
   ↓
blitz_engine: シーン・アセット・マテリアル（安全なRust）
   ↓
blitz_render: レンダーグラフ + リソースシステム ← 自作の型安全層 = エンジン中核
   ↓
ash（unsafe は blitz_render の実装内部に封じ込め）
```

層 = クレートとして分割し、依存方向を Cargo でコンパイル時に強制する。
`blitz_engine` / `blitz_app` は `#![forbid(unsafe_code)]` を宣言しており、
unsafe が blitz_render の外に書かれることも機械的に禁止される。

| クレート | 役割 | 制約 |
|---|---|---|
| `crates/blitz_app` | 起動バイナリ 兼 コンポジションルート。ウィンドウ生成と依存の配線のみ | unsafe禁止。ロジックを書かない |
| `crates/blitz_engine` | シーン・アセット・マテリアル。描画内容をレンダーグラフへ翻訳 | unsafe禁止。ash に依存しない |
| `crates/blitz_render` | レンダーグラフ + リソースシステム。Vulkan の unsafe をここに封じ込め | 公開APIに ash の型を露出しない |

## ライブラリ採用方針

コードに責任を持つため、ライブラリの採用は抑制的に行う（React を使わず SengenUI を
自作したのと同じスタンス）。

1. **迷ったら借りない。** エンジンの存在意義（レンダラー・リソース管理・同期・
   シミュレーション・シーン表現）は自作する。借りてよいのは「枯れた公開仕様の実装」と
   「基盤数学」だけ
2. **説明責任テスト。** 中身がどう動いているか説明できないライブラリは採用しない。
   採用時は本README に メリット・デメリット・採用理由・置換可能性 を書いてから使う
3. **境界に隔離。** 各ライブラリは特定クレートに閉じ、公開APIに型を漏らさない
   （ash の封じ込めと同じ扱い）。常に差し替え可能に保つ
4. **推移的依存も監視。** `cargo tree` で依存の連鎖を確認する。現在の依存総数は
   自前3クレート含め33（外部約30。ゲームエンジンとして極小）。肥大したら再考する
5. **「AIで再構築して超えられるか」の判定原理。** ライブラリの価値の源泉で分かれる:
   (a) 導出可能な数学（glam・レイアウト算法等）——AIは差分テスト（既存実装をオラクルに
   ランダム入力で突き合わせ）を武器に再構築できる。やらない理由は能力でなく経済性で、
   計測が特化カーネル等の利益を示した時に置き換えでなく追加から始める
   (b) 蓄積された経験的知識（winitのOSの癖10年分等）——第一原理から導出不能で、
   実機での再発見でしか再獲得できない。最も置き換えにくい
   (c) 仕様の機械生成（ash）——再構築という概念自体が空（再生成するだけ）。
   AIの知能はライブラリが存在しない層（レンダーグラフ・シミュレーション・介入モデル）に使う

## 利用ライブラリ（採用済み）

### ash — Vulkan 生バインディング
- 何か: Khronos の公式仕様レジストリ（vk.xml）から機械生成される、C API とほぼ 1:1 の薄い層
- メリット: Vulkan 仕様書・既存チュートリアルの知識がそのまま使える。機械生成の薄いバインディング
  なので「ライブラリ独自のバグ・独自の設計判断」がほぼ存在せず、責任の所在が Vulkan 仕様と
  自分のコードに限定される。コミュニティ（ash-rs）で長期保守され、Rust の本格 Vulkan 開発の標準
- デメリット: 全面 unsafe（安全網なし）。ドキュメントは実質 Vulkan 仕様書を読むことになる
- 採用理由: wgpu は WebGPU の共通部分集合に縛られ（バインドレス・メッシュシェーダー・
  マルチキュー等が制約）、vulkano は汎用安全化の実行時追跡コストと保守体制で不採用。
  安全性は自前の狭い型安全層で担保する方針のため、最薄の ash が最適
- 置換可能性: blitz_render 内部に封じ込め済み。置換対象があるとすれば自前生成だが、
  同じ vk.xml から生成する以上ほぼ同じものになるため実益がない

### ash-window — サーフェス生成の橋渡し
- 何か: raw-window-handle → VkSurfaceKHR 変換の数百行の小さなクレート（ash-rs 同一組織）
- メリット: OS別のサーフェス生成拡張（Win32/X11/Wayland/Metal）の定型コードを省く
- デメリット: 実質なし（小さすぎて壊れる場所がない）
- 採用理由と置換可能性: 自作しても同じコードを書くだけ。必要なら数百行で内製化できる

### winit — ウィンドウとイベントループ
- 何か: Win32 の RegisterClass / CreateWindowEx / メッセージループ / WndProc 一式を
  OS 差異ごと抽象化した純 Rust ライブラリ。描画機能は持たない。rust-windowing 組織が保守し、
  Bevy 等の主要プロジェクトが依存する事実上の標準
- メリット: 生 Win32 自作で発生する unsafe FFI を回避（封じ込め設計の維持）。
  クロスプラットフォームが無償で付く。Raw Input も露出
- デメリット: コールバック型イベントループ（ApplicationHandler）の流儀を強制される。
  バージョン間の API 変更が歴史的に多い（0.28→0.30 で大改変）。日本語 IME まわりに
  プラットフォーム差の癖がある（ゲーム内チャット等を作る段で要検証）
- 採用理由: ウィンドウ処理は性能と無関係で理論値志向の対象外。実績ある標準を使い、
  エンジン本体を `raw-window-handle` 境界で絶縁する
- 置換可能性: 触るのは blitz_app のみ。生 Win32 実装への差し替えでもエンジン本体は不変

### raw-window-handle — ウィンドウハンドルの共通インターフェース
- 何か: ウィンドウハンドル（HWND等）の受け渡し規約を定めた、ほぼトレイト定義のみのクレート。
  Rust グラフィックス生態系全体の共通規格
- メリット/デメリット: コードがほぼ無いため品質リスクも無い。規格そのもの
- 採用理由: winit と blitz_render の結合をこの規格だけにし、双方を差し替え可能に保つ要石

### glam — ゲーム数学（採用条件つき: 計算基盤としてのみ）
- 何か: Vec3 / Mat4 / Quat 等のゲーム向け線形代数。SIMD 最適化済み。Bevy 採用で
  Rust ゲーム開発の事実上の標準。f64 版の型（DVec3等）もあり大座標の扉とも整合
- メリット: 枯れた数学の高品質実装。API が小さく学習も検証も容易
- デメリット: **単位も座標系フレームも型で区別しない**（Unity の Vector3 と同じ欠陥。
  「この Vec3 の単位は何か・どの座標系か」が型から分からない）。
  汎用線形代数ライブラリではない（大行列・任意次元は対象外。意図的な設計）
- 採用理由と条件: SIMD計算の下請け（ALU）としてのみ採用する。**ドメイン語彙としては禁止**——
  ドメイン層は座標系フレームと単位を幻影型で付けた自作の値オブジェクト
  （`#[repr(transparent)]` でゼロコスト、コンパイル後はglam直書きと同一の機械語）で包み、
  生型に戻すのはGPU境界のみ。`参照: CLAUDE.md 数学DDD`。先行実例はServoのeuclid
  （幻影型で単位・空間を区別したジオメトリ型）。完全な次元代数が要る場合は
  uom（型レベル次元解析）を審査するが、当面はフレーム型 + 長さ・時間・角度の部分集合を自作する
- 置換可能性: ドメイン層が自作値オブジェクト越しに触るため、露出は包装の内側に限定され
  差し替え可能性は高い

### thiserror — 型付きエラー定義
- 何か: エラー enum に Display / Error 実装を導出する proc-macro。作者は dtolnay
  （serde / syn の作者。Rust で最も信頼される保守者の一人）
- メリット: 定型実装の削減。実行時コストゼロ（コンパイル時のコード生成のみ）
- デメリット: proc-macro のためコンパイル時間に寄与（syn 依存）
- 採用理由: 層ごとの判別可能なエラー型という規約（CLAUDE.md）の記述コストを下げる
- 置換可能性: 生成コードを手書きすれば依存を外せる（いつでも脱着可能）

## 候補ライブラリ（未採用。採用時に上記方針の審査を通す）

以下は計画上の候補であり、**まだ採用していない**。各マイルストーン着手時に
説明責任テストを通し、本節へ移してから使う。

- gltf（M3、glTF 2.0 パーサ）/ image（M3、画像デコード。重い依存のため
  個別デコーダ採用も比較する）/ egui（M5、開発用UIのみ）/
  cosmic-text（文字組版）/ taffy（UIレイアウト）/ rapier（剛体物理）/ kira（オーディオ）
- Slang はライブラリではなくシェーダーコンパイラ（Khronos 管轄のツールチェーン）。
  ビルド時にコンパイラとして呼び出す外部ツールの扱い

## ビルド

```
cargo build        # 全クレート
cargo run -p blitz_app
```

開発時は Vulkan validation layer（VK_LAYER_KHRONOS_validation、同期検証含む）を常時有効にする。
