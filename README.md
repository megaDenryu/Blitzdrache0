# Blitzdrache0

Blitz（稲妻）+ Drache（竜）。Rust + Vulkan による自作ゲームエンジン。

デバイスの理論値性能を志向し、汎用エンジン（Unity/Unreal）が払う汎用性の税金を避けるため、Vulkan を生バインディング（ash）で直接扱う。
安全性は「あらゆる使い方を安全にする汎用ラッパー」ではなく「このエンジンの使い方だけを露出する狭い型安全層」で担保する。

## アーキテクチャ

```
ゲームロジック: blitz_game（安全なRust）
   ↓
blitz_engine: シーン・アセット・マテリアル（安全なRust）
   ↓
blitz_render: レンダーグラフ + リソースシステム ← 自作の型安全層 = エンジン中核
   ↓
ash（unsafe は blitz_render の実装内部に封じ込め）

glTF・画像 → blitz_asset_compiler → アセット実行時形式 → blitz_engine
部品のglTF → blitz_asset_compiler（接合点の読み） → blitz_assembly（カタログと組み立て） → 配置列
```

層 = クレートとして分割し、依存方向を Cargo でコンパイル時に強制する。
`blitz_render` 以外の全クレート（`blitz_app` / `blitz_assembly` / `blitz_asset_compiler` / `blitz_collision` / `blitz_engine` / `blitz_game` / `blitz_math` / `blitz_sim`）は `#![forbid(unsafe_code)]` を宣言しており、unsafe が blitz_render の外に書かれることも機械的に禁止される。

| クレート | 役割 | 制約 |
|---|---|---|
| `crates/blitz_app` | 起動バイナリ 兼 コンポジションルート。ウィンドウ生成と依存の配線のみ | unsafe禁止。ロジックを書かない |
| `crates/blitz_assembly` | 部品の接合点・カタログ・接合の計算・展開。glTFもファイルシステムも知らない純粋計算 | unsafe禁止。gltfとimageに依存しない |
| `crates/blitz_asset_compiler` | glTFと画像を検証してアセット実行時形式へ変換する開発時層 | unsafe禁止。gltf/image型を公開APIへ露出しない |
| `crates/blitz_collision` | 形状の表現・幾何問い合わせ・詳細衝突計算・形状内の空間探索の数学 | unsafe禁止。blitz_mathとthiserror以外に依存しない |
| `crates/blitz_engine` | シーン・アセット・マテリアル。描画内容をレンダーグラフへ翻訳 | unsafe禁止。ash に依存しない |
| `crates/blitz_game` | ゲームロジック層。クソゲー1本目「キツネの場所巡り」の状態・進行・操作の意味付け | unsafe禁止。blitz_math以外に依存しない |
| `crates/blitz_math` | 座標系フレームと単位を区別する数学型 | unsafe禁止。glam型を公開APIへ露出しない |
| `crates/blitz_render` | レンダーグラフ + リソースシステム。Vulkan の unsafe をここに封じ込め | 公開APIに ash の型を露出しない |
| `crates/blitz_sim` | 布・介入・表面流・SPHの数学とGPUバッファレイアウト | unsafe禁止。ashとblitz_renderに依存しない |

## ライブラリ採用方針

コードに責任を持つため、ライブラリの採用は抑制的に行う（React を使わず SengenUI を自作したのと同じスタンス）。

1. **迷ったら借りない。** エンジンの存在意義（レンダラー・リソース管理・同期・シミュレーション・シーン表現）は自作する。借りてよいのは「枯れた公開仕様の実装」と「基盤数学」だけ
2. **説明責任テスト。** 中身がどう動いているか説明できないライブラリは採用しない。採用時は本README に メリット・デメリット・採用理由・置換可能性 を書いてから使う
3. **境界に隔離。** 各ライブラリは特定クレートに閉じ、公開APIに型を漏らさない（ash の封じ込めと同じ扱い）。常に差し替え可能に保つ
4. **推移的依存も監視。** `cargo tree --workspace --edges normal` で依存の連鎖を確認する。2026-07-23時点のWindows向け通常依存グラフは85パッケージ版（自前7、外部78）である。外部依存が増える変更では増加理由と境界を再審査する
5. **「AIで再構築して超えられるか」の判定原理。** ライブラリの価値の源泉で分かれる:
   (a) 導出可能な数学（glam・レイアウト算法等）——AIは差分テスト（既存実装をオラクルにランダム入力で突き合わせ）を武器に再構築できる。やらない理由は能力でなく経済性で、計測が特化カーネル等の利益を示した時に置き換えでなく追加から始める
   (b) 蓄積された経験的知識（winitのOSの癖10年分等）——第一原理から導出不能で、実機での再発見でしか再獲得できない。最も置き換えにくい
   (c) 仕様の機械生成（ash）——再構築という概念自体が空（再生成するだけ）
   (d) エコシステムの合意（raw-window-handle等の規格クレート）——価値が技術でなく合意そのものにあるため、技術では超えられない（自作すると独自規格になり接続を失うだけ）。AIの知能はライブラリが存在しない層（レンダーグラフ・シミュレーション・介入モデル）に使う

## 利用ライブラリ（採用済み）

### ash — Vulkan 生バインディング
- 何か: Khronos の公式仕様レジストリ（vk.xml）から機械生成される、C API とほぼ 1:1 の薄い層
- メリット: Vulkan 仕様書・既存チュートリアルの知識がそのまま使える。機械生成の薄いバインディングなので「ライブラリ独自のバグ・独自の設計判断」がほぼ存在せず、責任の所在が Vulkan 仕様と自分のコードに限定される。コミュニティ（ash-rs）で長期保守され、Rust の本格 Vulkan 開発の標準
- デメリット: 全面 unsafe（安全網なし）。ドキュメントは実質 Vulkan 仕様書を読むことになる
- 採用理由: wgpu は WebGPU の共通部分集合に縛られ（バインドレス・メッシュシェーダー・マルチキュー等が制約）、vulkano は汎用安全化の実行時追跡コストと保守体制で不採用。安全性は自前の狭い型安全層で担保する方針のため、最薄の ash が最適
- 再構築判定: (c) 仕様の機械生成。vk.xml からの再生成にすぎず「超える」対象が存在しない。自作生成器で使う拡張だけに絞る余地はあるが、利益はコンパイル時間程度
- 差し替えコスト: 低〜中。unsafe 呼び出しは blitz_render 内部に封じ込め済みで上位層は不変。内部実装の機械的置換（数千行規模）にはなるが、差し替え先も同じ vk.xml から生成する以上実質同型になるため、差し替えの動機自体が発生しにくい

### ash-window — サーフェス生成の橋渡し
- 何か: raw-window-handle → VkSurfaceKHR 変換の数百行の小さなクレート（ash-rs 同一組織）
- メリット: OS別のサーフェス生成拡張（Win32/X11/Wayland/Metal）の定型コードを省く
- デメリット: 実質なし（小さすぎて壊れる場所がない）
- 採用理由: 自作しても同じコードを書くだけの定型のため借りる
- 再構築判定: (a) 寄りの定型実装。数時間で再現可能で、超える余地がそもそも無い
- 差し替えコスト: ほぼゼロ。呼び出しは初期化時の1箇所のみ。保守が止まったら即日内製化する

### winit — ウィンドウとイベントループ
- 何か: Win32 の RegisterClass / CreateWindowEx / メッセージループ / WndProc 一式を OS 差異ごと抽象化した純 Rust ライブラリ。描画機能は持たない。rust-windowing 組織が保守し、Bevy 等の主要プロジェクトが依存する事実上の標準
- メリット: 生 Win32 自作で発生する unsafe FFI を回避（封じ込め設計の維持）。クロスプラットフォームが無償で付く。Raw Input も露出
- デメリット: コールバック型イベントループ（ApplicationHandler）の流儀を強制される。バージョン間の API 変更が歴史的に多い（0.28→0.30 で大改変）。日本語 IME まわりにプラットフォーム差の癖がある（ゲーム内チャット等を作る段で要検証）
- 採用理由: ウィンドウ処理は性能と無関係で理論値志向の対象外。実績ある標準を使い、エンジン本体を `raw-window-handle` 境界で絶縁する
- 再構築判定: (b) 経験的知識。価値の本体は10年分のOSの癖（IME・DPI・マルチモニタ・メッセージポンプの版差）で、第一原理から導出不能。コードは書けても正しさは実機での再発見でしか再獲得できず、採用ライブラリ中で最も置き換えにくい
- 差し替えコスト: 中。触るのは blitz_app のみでエンジン本体は raw-window-handle 境界により不変（設計済み）。ただし生 Win32 への差し替えは Windows 限定化と、経験的知識の再獲得（実機で癖を踏み直す検証）のコストを伴う

### raw-window-handle — ウィンドウハンドルの共通インターフェース
- 何か: ウィンドウハンドル（HWND等）の受け渡し規約を定めた、ほぼトレイト定義のみのクレート。Rust グラフィックス生態系全体の共通規格
- メリット/デメリット: コードがほぼ無いため品質リスクも無い。規格そのもの
- 採用理由: winit と blitz_render の結合をこの規格だけにし、双方を差し替え可能に保つ要石
- 再構築判定: (d) エコシステムの合意。価値は技術でなく合意そのものにあり、自作すると独自規格になって生態系との接続を失うだけ。技術では超えられない
- 差し替えコスト: 差し替えの動機が定義上発生しない（これ自体が他を差し替え可能にする要石）。外すなら winit と ash-window を自前で直結する改修になるが、実コードはトレイト数個分

### glam — ゲーム数学（採用条件つき: 計算基盤としてのみ）
- 何か: Vec3 / Mat4 / Quat 等のゲーム向け線形代数。SIMD 最適化済み。Bevy 採用で Rust ゲーム開発の事実上の標準。f64 版の型（DVec3等）もあり大座標の扉とも整合
- メリット: 枯れた数学の高品質実装。API が小さく学習も検証も容易
- デメリット: **単位も座標系フレームも型で区別しない**（Unity の Vector3 と同じ欠陥。「この Vec3 の単位は何か・どの座標系か」が型から分からない）。汎用線形代数ライブラリではない（大行列・任意次元は対象外。意図的な設計）
- 採用理由と条件: SIMD計算の下請け（ALU）としてのみ採用する。**ドメイン語彙としては禁止**——ドメイン層は座標系フレームと単位を幻影型で付けた自作の値オブジェクト（`#[repr(transparent)]` でゼロコスト、コンパイル後はglam直書きと同一の機械語）で包み、生型に戻すのはGPU境界のみ。`参照: CLAUDE.md 数学DDD`。先行実例はServoのeuclid（幻影型で単位・空間を区別したジオメトリ型）。完全な次元代数が要る場合はuom（型レベル次元解析）を審査するが、当面はフレーム型 + 長さ・時間・角度の部分集合を自作する
- 再構築判定: (a) 導出可能な数学。差分テスト（glam をオラクルにランダム入力で突き合わせ）で数日級で再構築可能。ただし型設計の上位互換はラッパー層で奪取済み、特化カーネル（SoA・ワイド演算）は置き換えでなく追加のため、現時点の再実装利益はゼロ。引き金は計測
- 差し替えコスト: 低（数学DDD採用後）。ドメイン層は値オブジェクト越しにしか触れないため、差し替えは値オブジェクトの内部実装（数百行）に局所化される。GPU境界のメモリレイアウト互換（repr(transparent) の中身）のみ注意

### gltf — glTF 2.0 パーサ（M3で採用）
- 何か: Khronos の公開仕様 glTF 2.0 のパーサ。シーン階層・メッシュアクセサ・マテリアル参照を型付きで読める。rust-windowing 系と並ぶ gltf-rs 組織が保守
- メリット: 仕様準拠の検証込みパース。アクセサのバイト解釈（ストライド・型変換）という地味に間違えやすい部分を吸収する
- デメリット: json 等の推移的依存が付く。glTF 拡張の網羅は過剰装備
- 採用理由: 使う部分集合だけの自作パーサと比較し、M3時点では階層・アクセサ・マテリアル参照の正確な網羅コストが自作の利益を上回る。OW1でglTFパースを`blitz_asset_compiler`へ移し、実行時のアプリとエンジンから分離した
- 再構築判定: (a/c) 公開仕様の実装。差分テストで再構築可能だが経済性なし
- 差し替えコスト: 低。安定ID境界により`blitz_asset_compiler`へ局所化し、公開APIにgltfの型を露出しない
- 制約: `blitz_asset_compiler`だけが依存する
- 機能: 既定に加えて`extras`を有効にする（部品カタログの段1で追加）。この機能は**新しいクレートを1つも足さない**。`gltf/extras`は`gltf-json/extras`へ委譲するだけであり、`gltf-json`は`serde_json`を機能に関わらず無条件で依存している。機能が変えるのは型別名1つで、`Extras`が空の構造体から`Option<Box<RawValue>>`になる。有効にしないと接合点のextrasが読めない（参照: `_doc/設計/部品カタログと接合点.md`「実地で確かめた事実」）

### image — 画像デコード（M3で採用、機能を絞る）
- 何か: Rust 標準の画像デコードライブラリ。**default-features を無効化し png / jpeg のみ有効**
- メリット: 枯れたフォーマット仕様実装。エコシステム標準で説明責任テスト通過
- デメリット: 全機能有効だと依存が重い（採用条件の機能絞りで対処）
- 採用理由: glTF のテクスチャ実体は png / jpeg が大半。個別デコーダ（zune系）との比較は「依存2つ vs 1つ + 標準度」で image 側に軍配。デコード層に局所化されるため、重量が問題化したら個別デコーダへ置換する
- 再構築判定: (a) フォーマット仕様の実装 + SIMD蓄積。再構築の経済性なし
- 差し替えコスト: 低。`blitz_asset_compiler`のデコード関数1箇所に閉じる

### egui + egui-winit — 開発用UI（M5で採用。本番UIとは別系統）
- 何か: 即時モードUIライブラリ（egui）と winit イベント統合（egui-winit）
- メリット: 計測表示・デバッグ操作のUIを数行で作れる。Rustの開発用UIの事実上の標準
- デメリット: 見た目・レイアウトの自由度は低い（開発用途では問題にならない）
- 採用理由と条件: 開発用UI専用（本番ゲームUIはリテインドモードで別系統、長期フェーズ計画参照）。本番コードに入らないため責任基準を緩める。**依存は blitz_app のみに閉じ、blitz_render は egui を知らない**——レンダラーは自前のUI描画語彙（2D頂点・テクスチャID・シザー）を公開し、egui出力からの変換は blitz_app（配線層）が行う
- 再構築判定: (a)寄り。差し替え自由（開発用UIは書き捨て可能。レンダラー側のUI描画語彙は egui 非依存のため、UIライブラリを替えても blitz_render は不変）
- 差し替えコスト: 低。blitz_app の変換層のみ

### thiserror — 型付きエラー定義
- 何か: エラー enum に Display / Error 実装を導出する proc-macro。作者は dtolnay（serde / syn の作者。Rust で最も信頼される保守者の一人）
- メリット: 定型実装の削減。実行時コストゼロ（コンパイル時のコード生成のみ）
- デメリット: proc-macro のためコンパイル時間に寄与（syn 依存）
- 採用理由: 層ごとの判別可能なエラー型という規約（CLAUDE.md）の記述コストを下げる
- 再構築判定: (a) 定型コード生成。超える対象が無く、価値は記述コストの削減のみ
- 差し替えコスト: ほぼゼロ。derive を外して同等の impl を手書きするだけの機械的作業。proc-macro のコンパイル時間が問題化した時点で外してよい

### rayon — データ並列（大規模世界の生成で採用）

- 何か: 逐次のイテレータを並列イテレータへ置き換えるだけでスレッド分割を行うデータ並列ライブラリ。仕事の横取り(手の空いたスレッドが他のスレッドの仕事を取る)方式のスレッドプールを内側に持つ
- メリット: 逐次の`iter()`を`par_iter()`へ替えるだけで済み、呼び出し側の構造を変えない。実行の順序が結果へ影響しない工程では、並列化が生成物のバイト列を1バイトも変えない
- デメリット: 内部にスレッドプールを持つため、開発ツールの外(実行時のエンジン)へ持ち込むとフレームの進行と競合しうる。依存する先はアセットコンパイラの層だけに閉じる
- 採用理由: 8,000チャンクの世界の生成とコンパイルはチャンクごとに独立で、1つの結果が他の結果へ影響しない。自作のスレッド分割は仕事の横取りの実装がそのまま要件になり、得られるものが同じである
- 再構築判定: (a) 導出可能な並列化。仕事の横取りの待ち行列は書けるが、超える余地は無く、価値は実装と検査の手間の削減のみ
- 差し替えコスト: 低。使うのはblitz_asset_compilerの生成の工程だけであり、`par_iter()`を`iter()`へ戻せば逐次に戻る。実行時のエンジンとblitz_appは依存しない

### serde_json — 接合点のextrasの解読（部品カタログの段1で採用）

- 何か: JSONの読み書きを行うライブラリ。ここで使うのは、値を`Value`として読む口だけである
- メリット: **依存の木に増えるものが1つも無い。** `gltf-json`が機能`raw_value`つきで無条件に依存しているため、直接依存へ足しても新しい取得もビルド単位も発生しない
- デメリット: 導出マクロ(`derive`)を使うと、検証を通らない値がそのまま型の中へ座る形を誘う
- 採用理由: 部品の接合点はglTFの`extras`にJSONとして載っており、`gltf`が返すのは生のJSON文字列である。解くには解析器が要る。自作すると、UTF-8とエスケープと数値の解析を書き直すことになり、日本語のキーを使う設計と相性が悪い。**導出マクロは使わず、`Value`として受けて型ガードで絞る**（外部境界はunknownで受ける、のRust版）
- 再構築判定: (a/c) 公開仕様の実装。書けるが超える余地は無い
- 差し替えコスト: 低。使うのは`blitz_asset_compiler`の接合点の読みの1箇所だけである
- 制約: `blitz_asset_compiler`だけが依存する

### crossterm — 端末の生モード制御とキー入力読み取り（`cargo xtask menu`で採用）

- 何か: 端末の生モード（raw mode）切り替え・カーソル移動・画面消去・キー入力イベント読み取りをクロスプラットフォームに抽象化する純Rustライブラリ。Windows Console API と Unix の termios/VT100を両方吸収する
- メリット: 番号入力に加えて矢印キー・ページ送りでコマンドを選べる対話メニューは、端末の生モード制御なしには作れない。Windows/Unix双方のキー入力APIの差異を1つの`KeyEvent`型へ吸収する
- デメリット: xtaskはこれまで外部クレートへ依存しない設計だったが、対話メニューという新しい要求により初めて外部依存を持つ。依存はxtaskだけに閉じ、blitz_app等のエンジン側は知らない
- 採用理由: 生のWin32コンソールAPI直叩きはunsafe FFIを伴い、xtaskは`#![forbid(unsafe_code)]`相当の単純さを保ちたい。広く使われているクロスプラットフォーム端末制御ライブラリの中で、依存が薄く（ANSIエスケープシーケンスの組み立てが主体）、機能を必要な範囲（生モード・カーソル移動・画面消去・キー入力）だけ使える
- 再構築判定: (b)寄り。Windows Console APIとUnix termios双方の癖（ANSIエスケープの解釈違い・キー入力イベントの粒度差）を吸収した経験的知識であり、第一原理から導出はできるが実機での再発見コストが高い
- 差し替えコスト: 低。使うのは`xtask/src/command_ui/menu`配下の端末制御を持つ1つの型（`端末セッション`）だけに閉じており、他のxtaskコマンドはcrosstermを知らない
- 制約: `xtask`だけが依存する

### ctrlc — Ctrl+Cの捕捉（`cargo xtask editor`で採用）

- 何か: Ctrl+Cによる割り込みを捕らえ、指定した処理を走らせる小さなクロスプラットフォームライブラリ。WindowsではWin32の`SetConsoleCtrlHandler`を登録し、Unixでは`SIGINT`のハンドラを置く。どちらも受け取った合図を専用スレッドへ渡し、そのスレッドが利用側の処理を呼ぶ
- メリット: `cargo xtask editor`がCtrl+Cで止められたとき、起動した編集サーバーと開発サーバーの木を終わらせてから終われる。これが無いとxtaskだけが消え、開発サーバー(vite)が待ち受け口を掴んだまま残って次の起動が番号の衝突で落ちる
- デメリット: 割り込みの処理は別スレッドで走るため、終わらせる対象を`Child`でなくプロセス番号で共有する必要がある。またプロセスが強制終了(`TerminateProcess`)された場合はハンドラ自体が走らないため、この手段では守れない
- 採用理由: 標準ライブラリに割り込みを捕らえる口が無い。自作すると`SetConsoleCtrlHandler`へのunsafeなFFIを書くことになり、xtaskを`#![forbid(unsafe_code)]`相当の単純さに保つ方針と衝突する。crosstermを採用したときと同じ理由であり、同じ判断を引き継ぐ
- 再構築判定: (a/b) OSの割り込みAPIの薄い包み。書けるが超える余地は無く、Windows/Unix双方の合図の届き方の癖を再発見する費用だけがかかる
- 差し替えコスト: 低。使うのは`xtask/src/editor/interrupt.rs`の1箇所だけで、他のxtaskコマンドはctrlcを知らない
- 制約: `xtask`だけが依存する

### win32job — 親の強制終了で子孫を道連れにする（`cargo xtask editor`で採用）

- 何か: Windowsの仕事の束（Job Object。複数のプロセスを1つの束にまとめ、束に制限をかけるOSの仕組み）を安全に扱う小さなライブラリ。束を作る・制限を設定する・プロセスを束へ入れる、の3つのWin32呼び出しだけを包む
- メリット: 束に「取っ手が全て閉じたら中のプロセスを終わらせる」制限（`JOB_OBJECT_LIMIT_KILL_ON_JOB_CLOSE`）をかけると、後始末の処理をOSが肩代わりする。`cargo xtask editor`が強制終了（`TerminateProcess`）されても、OSが取っ手を閉じた時点で編集サーバーと開発サーバーが終わる。Ctrl+Cの捕捉も通常の終了もこの止め方には届かず、実測で両方が残ることを確かめている
- デメリット: 推移的依存が11パッケージ増える（`win32job`本体と`windows` 0.61系の10パッケージ。うち`windows-implement`と`windows-interface`は手続きマクロであり、コンパイル時間へ寄与する）。同じ役割の`process-wrap`も同じ`windows`系を引くうえに`tracing`・`nix`・`futures`まで引くため、依存の増加が最も小さい選択がこれである
- 採用理由: 自作すると`CreateJobObjectW`・`SetInformationJobObject`・`AssignProcessToJobObject`へのunsafeなFFIを書くことになり、unsafeを`blitz_render`の実装内部だけに限る規約（CLAUDE.md「unsafe の規律」）を道具の側で破る。crosstermとctrlcを採用したときと同じ理由であり、同じ判断を引き継ぐ
- 再構築判定: (a/c) OSのAPIの薄い包み。3つの呼び出しの直訳であり超える余地は無い
- 差し替えコスト: 低。使うのは`xtask/src/editor/kill_with_parent.rs`の1つの型だけで、他のxtaskコマンドはwin32jobを知らない
- 制約: `xtask`だけが、しかもWindows向けのビルドでだけ依存する（`[target.'cfg(windows)'.dependencies]`）

### serde + serde_json — 編集資源と生成カタログの直列化（ゲーム開発用エディター段1・第3段階で採用）

- 何か: Rustのデータ構造をJSON等へ直列化・逆直列化する事実上の標準ライブラリ一式
- メリット: 型からの導出（derive）で直列化コードを書かずに済む。ts-rsがserdeの型情報を読んでTypeScript契約を生成するため、この2つは不可分
- デメリット: derive proc-macroのぶんコンパイル時間へ寄与する
- 採用理由: `プロジェクト保管庫`（段2）とts-rs契約生成の両方がserdeの型情報を前提にする。第3段階ではblitz_asset_compilerが建物定義の正本から版付きの建物外形カタログを生成するため、同じ直列化契約を使う。JSONの利用はオフラインの生成と編集サーバーの境界に閉じ、実行時の描画経路へ持ち込まない
- 再構築判定: (a) 定型コード生成。超える対象が無く、価値は記述コストの削減のみ
- 差し替えコスト: 低。利用箇所は`editor_server`の編集資源境界と`blitz_asset_compiler`の生成カタログ境界に閉じている
- 制約: `editor_server`と`blitz_asset_compiler`だけが依存する

### axum + tower + tower-http — 編集サーバーのHTTP層（ゲーム開発用エディター段1で採用）

- 何か: tokio上のHTTPフレームワーク(axum)と、そのミドルウェア基盤(tower)、静的ファイル配信等の既製ミドルウェア(tower-http)。GameScriptingTheoryのeditor_serverで先行採用済み
- メリット: ルーティング・状態注入・静的配信という定型のHTTPサーバー実装を自作せずに済む。tower::Serviceトレイトの上に薄い独自層（経路正規化アプリ）を重ねられるため、非ASCII経路のパーセント符号化という実地の落とし穴だけを自前で解決すればよい
- デメリット: HTTP・非同期ランタイムという、このエンジンが本来関わらない関心事の依存が増える。ただし editor_server はエンジン本体から独立したブラウザ用ツールであり、blitz_*クレートはこれらを一切知らない
- 採用理由: ブラウザ向けの開発ツールサーバーを自作のHTTP実装で書く利益が無い（枯れた仕様の実装であり、このエンジンの存在意義に関わらない）。GameScriptingTheoryで既に同じ構成が動いており、実装形を引き写せる
- 再構築判定: (a) 導出可能な定型実装。HTTP/1.1というよく仕様化されたプロトコルの実装であり、自作の利益がない
- 差し替えコスト: 低〜中。依存は`editor_server`クレート1つに閉じ、公開APIは`ルーターを組み立てる`等のこのクレートの語彙だけを出す
- 制約: `editor_server`だけが依存する

### tokio — 非同期ランタイム（ゲーム開発用エディター段1で採用）

- 何か: axumが要求する非同期ランタイム。Rustの非同期エコシステムの事実上の標準
- メリット: axumの実行に必須。マルチスレッドランタイムが1リクエストごとの並行処理を素直に扱える
- デメリット: このエンジンの本体（blitz_app等）はフレームループを自前で持ちtokioを使わないため、editor_serverだけが持つ独立した実行モデルになる
- 採用理由: axumを使う以上必須
- 再構築判定: (b)寄り。非同期I/Oのスケジューリングという経験的知識の蓄積があるが、editor_serverの用途では自作する動機が無い
- 差し替えコスト: 低。`editor_server`だけが依存する
- 制約: `editor_server`だけが依存する

### ts-rs — Rust型からTypeScript型契約の生成（ゲーム開発用エディター段1で採用）

- 何か: Rustの型定義からTypeScriptの型宣言を生成するderiveマクロ
- メリット: 編集資源の型契約をRust側1箇所を正本にでき、TypeScript側の写しを手で書いて食い違わせる二重管理を防ぐ。GameScriptingTheoryの`sprite_cut`・`editor_server`で先行採用済みの「鮮度検査テスト」様式をそのまま引き写せる
- デメリット: 生成結果の型の書式（プロパティの並び順・オブジェクト型の綴り）がライブラリ任せになる
- 採用理由: 判断1（操作コマンドはTS側1実装）・判断2（永続化境界）を支える型契約の正本をRust側に置くという設計判断（`_doc/設計/ゲーム開発用エディター基盤.md`）に必須
- 再構築判定: (a) 導出可能な定型変換。型情報からの機械的な文字列生成であり、自作の動機が薄い
- 差し替えコスト: 低。`editor_server`の`typescript`フィーチャの中に閉じ、既定ビルドでは依存しない（`optional = true`）
- 制約: `editor_server`だけが依存する（`typescript`フィーチャのみ）

以下は計画上の候補であり、**まだ採用していない**。各マイルストーン着手時に説明責任テストを通し、本節へ移してから使う。

## 大容量資産の保管とclone

このリポジトリは大容量のバイナリ資産を Git LFS（Git Large File Storage。実体の代わりに参照情報をGitへ記録する仕組み）で扱い、実体は共通の保管基盤 [git-lfs-rclone-storage](https://github.com/megaDenryu/git-lfs-rclone-storage) が置く。追跡対象は `.gitattributes` が持つ（`.heightgrid` / `.f32raw` / `.png`）。コミットに入るのは参照情報だけであり、リポジトリは保管先を知らない（`.large-assets.toml` が論理プロファイル名だけを持つ）。

glTFの文書が `uri` で指す共有バッファ（`.bin`）は追跡しない。あれは `cargo xtask gen-source-assets` が書き出す生成物であり、生成物をGitへ入れると、生成の結果とコミットの中身が食い違ったときにどちらが正しいかを決められなくなるためである。cloneした直後の作業ツリーには共有バッファが1件も無いが、`cargo xtask verify` と `cargo xtask smoke` と `cargo xtask compile-assets` は読む前に `supply-source-assets` の工程を通り、欠けていれば生成器を起こして揃える。

**正本は生成器のコードと生成の入力である。** 追跡している文書（`.gltf`）は「追跡された生成のスナップショット」であり、追跡するのはレビューで差分を読むためであって、正本だからではない。正本を1つに定めるのは、生成物をGitへ入れるとどちらが正しいか決められなくなるという上の理由と同じ判断による。したがって、揃える工程が生成器を起こした後に文書の中身が変わっていれば、それは正本が変わったのにスナップショットが古いままの状態であり、工程は型付きエラーで止まって、書き直された文書をコミットするよう伝える。判定はGitの状態でなく生成の前後のバイトの一致で行うため、Gitの外に置いた木でも同じ結果になる。

揃える工程が見るのは共有バッファが在るかどうかではなく、**いまの生成器といまの入力に対して新しいか**である。在るかどうかだけを見ると、生成器のコードや生成規則を変えた後も古い共有バッファを読み続け、追跡に入っていないその食い違いは差分に現れない。判定には「生成の指紋」（生成器の実行ファイルの中身と場所巡りの世界の乱数の種を1つの値へ畳んだもの）を使い、最後に揃えたときの値を `assets/source_asset_fingerprint.txt`（Gitの無視の対象）へ書く。指紋の材料には、追跡している文書の中身も入る。人が手で文書を書き換えた場合、それだけで指紋が変わって生成器が起き、上の一致の検査がその食い違いを名指す。共有バッファが欠けているか、記録された指紋がいまの指紋と違うか、その台帳が無いかのいずれかで生成器を起こす。

指紋の材料である生成器の実行ファイルの中身を読むため、この工程は毎回 `cargo build --quiet -p blitz_asset_compiler --example generate_source_assets` を1回起こす。生成器に変更が無ければこれは数秒で終わる（cargoが組み直さない）。

**初回のcloneは通常の `git clone` では完結しない。** cloneした時点では基盤が登録されておらず、追跡対象のファイルの展開が失敗する。次の手順を使う。PCの初期設定（基盤の実行ファイルの配置とPC設定ファイル）は `C:\devs\git-lfs-rclone-storage\_doc\利用\PC初期設定.md` が持つ。

```powershell
# 実行場所: cloneしたい親ディレクトリ
$env:GIT_CLONE_PROTECTION_ACTIVE = "false"
$env:GIT_LFS_SKIP_SMUDGE = "1"
git clone git@github.com:megaDenryu/Blitzdrache0.git
Remove-Item Env:\GIT_CLONE_PROTECTION_ACTIVE, Env:\GIT_LFS_SKIP_SMUDGE

# 実行場所: cloneされたリポジトリのルート
git lfs install --local
git-lfs-rclone-storage install
git lfs pull
git-lfs-rclone-storage doctor   # 全項目が [OK] になれば導入は完了している
```

導入の日(2026-09-05)より前にコミットされたファイルは履歴の書き換えを避けるため移行しておらず、実体のままGitに入っている。導入後に追加・変更したものだけが参照情報になる。
