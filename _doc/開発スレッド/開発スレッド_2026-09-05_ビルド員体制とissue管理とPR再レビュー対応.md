## 葉: どの検査を並列にできるか

| 検査 | 並列化 | 理由 |
| --- | --- | --- |
| 命名 / 構造 / 行数と分割の質 | **コミットごとに走らせる** | 1コミットの差分だけで判定でき、後の段に依存しない |
| 文章(文書の差分) | コミットごと | 同上 |
| 契約整合 / 孤立実装 | 最後の段の後 | 「配線されていない」は全部が揃うまで判定できない |
| テスト実効性 / 設計正本整合 | 最後の段の後 | 試験の全体像と正本の対応表が要る |
| 検証再実行(verify) | 最後の段の後 | 実装員自身が回す |

#### 必須: 証明できない帰属は推測しない

いまの `定義の索引::実装ブロックの所在を引き当てる` は、同名の定義が複数あるとき、同じファイルか、ディレクトリの成分を先頭から何個共有するかで最も近い1件を選んでいる。Rustの inherent impl は対象型と同じクレートにあればよく、近いモジュールにある必要は無い。`impl crate::far::設定` が `near/` のファイルに置かれると、ファイルの近さで `near::設定` へ正常に見える形で誤加算する。同点なら落ちる設計では防げない。

**採る裁定(初版)**: 次の順で決め、ディレクトリの近さによる自動選択を使わない。

1. 同名の定義が1件しかない → その定義へ帰属
2. impl と定義が同じファイルで一意 → その定義へ帰属
3. 同名の定義が複数あり、構文から自己型の所在を確定できない → 曖昧として `conform` を落とす(既存の `実装ブロックの引き当て::定義の候補を1つに絞れない` の経路へ流す)

より良くするなら、impl のヘッダから自己型の経路(`crate::foo::設定`・`super::設定`・`self::設定`)を `実装ブロック` の観測へ保持し、モジュールの解決まで行って定義を確定してよい。ただし解決できない形(`use` で持ち込んだ短い名前など)は必ず曖昧へ落とす。どこまでやるかはあなたが決め、理由を報告に書く。

**必須の反証**: 走査の入力に次の形を与え、固定する。

```
a/src/near/def.rs   → struct 設定
a/src/far/def.rs    → struct 設定
a/src/near/impl.rs  → impl crate::far::設定 { ... }
```

構文から `far` を確定する方式なら `far::設定` へ帰属すること、確定しない方式なら曖昧として落ちること。いまの距離の規則なら `near::設定` へ誤帰属する形である。

**現状のリポジトリで曖昧になる impl が出た場合**は、黙って寄せず、その impl の定義ファイルへ自己型の経路を明示する(`impl crate::...::型`)か、台帳へ「曖昧」の行を作らずに `conform` の違反として出したままにして親へ報告する(親が裁定する)。

検証はビルド員へ依頼し、`conform` が違反0件で、落ちるのが `blitz_sim` の #59 の2件だけであること。
