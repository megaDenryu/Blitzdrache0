`cargo xtask type-metrics`はフィールド数・impl分散・メソッド数を測っています。しかしCLAUDE.mdに明記されているとおり違反判定をしません。理由は「現状の`レンダラー`が確実に閾値を超えるため、denyにすると検証列が全面的に止まる」。**既存の違反があるから検査を入れられず、検査が無いから違反が増える**という循環です。エディター制作スキル第3条の「強制の仕組みは起動経路を持たなければ存在しないのと同じ」が、ここでは「計測は起動経路を持つが、落とす力を持たない」という形で出ています。

## 「持つ場所と動かす場所を分ける」の中身

**いま起きていること。** `アプリ`が46フィールドを所有し、同時に**毎フレームの工程も`impl アプリ`のメソッドとして持っています**。

```rust
impl アプリ {

        // &mut self なので、46フィールドのどれにでも触れる
        self.入力状態 ... self.時間進行 ... self.ゲーム配線 ...
        self.カメラ ... self.天空 ... self.レンダラー ...
    }

```

`&mut self`である以上、**この関数が何に触るのかは署名のどこにも書かれていません**。触れるから触る。新しい工程を足すときは`self`へフィールドを1つ足すのが最も安く、それが46回積み重なりました。

**変えるのはどこか。** `アプリ`が物を所有すること自体は変えません(誰かが所有しないといけない)。変えるのは、**毎フレームの工程を`impl アプリ`のメソッドとして書くのをやめ、モジュールの関数にして、触る対象だけを引数で受け取らせること**です。

```rust
// 持つ側: アプリ(と束)が所有する
struct アプリ { 実行配線, 世界配線, 描画配線, 資源配線, ... }

// 動かす側: 工程は関数。触る対象が署名に現れる
mod 描画機会の工程 {
    pub(crate) fn 一回進める(
        時間: &mut 時間進行配線,
        世界: &mut 世界配線,
        描画: &mut 描画配線,
        入力: &入力状態,
    ) { ... }
}

impl アプリ {
    fn 描画機会を処理する(&mut self) {
        描画機会の工程::一回進める(&mut self.実行配線.時間, &mut self.世界配線, &mut self.描画配線, &self.実行配線.入力);
    }
}
```

**これで何が変わるか。**

1. その工程が触る対象が、関数の署名に全部書かれます。署名に無いものには触れません
2. 新しい工程が新しい対象を必要とするとき、**引数を足すことになり、レビューで見えます**。いまは`self`に紛れて見えません
3. `アプリ`のフィールドが増えるのは、新しい**所有**が生まれたときだけになります。工程が増えても増えません

**機械にどう守らせるか。** 工程の関数を、`アプリ`を定義したモジュールの**外**へ置きます。Rustの可視性は、フィールドを定義モジュールとその子孫からしか見せません。外に置けば`self.フィールド`へ触れないので、**引数で受けるしか書きようがなくなります**。文書の約束ではなく、コンパイラが強制します。

これはissue #56が言う「処理する対象を長い寿命の参照としてフィールドに持たず、呼び出しのたびに借りる」を、`アプリ`へ当てはめた形と同じです。

- **禁止側だけを書いた規約は、書かない方向へ倒れる。** 「束ねただけの段を作らない」があるために、束ねるべきものが平のフィールドとして並び続けた。積極形を足した
- **閾値を「分解が終わってから入れる」と書くと、分解が終わらない限り閾値が入らない循環になる。** その循環のあいだに46まで育った
- 検査員を作るときは、規約の正本を必読として渡す。渡さずに「規約の穴を探せ」と言うと、規約を読まないまま探すことになる(レビュー員の12件の指摘のうち最も重いものがこれだった)
- ユーザーの是正: 「fableは軽量ではない」「fableは強いけど高いから基本的にopusを使う。むずい時にfable」「単一責任原則の話なだけになってない?」「ルールじゃなくて精神も書くべきだろこれ」「持つ場所と動かす場所を分ける、て主語が抜けてて何言ってるか不明」
