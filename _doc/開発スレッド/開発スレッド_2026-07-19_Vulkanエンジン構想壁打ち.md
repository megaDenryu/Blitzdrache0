### ユーザー: RustでVulkanは可能か？現実的か？

> 今までのOpusだとC++で普通にVulkanを触らせても仕様書を理解していないみたいな感じでまともに取り扱うことができなかったと先輩から聞きましたが、Fableだと行けるようになったそうです。わたしはVulkanもC++も触ったことっがないですし、C++は触りたくないのでなんとかrustで触りたい

### AI: 可能かつ現実的。選択肢は3層

- **ash**: 生バインディング。Vulkan C APIと1:1で、仕様書・チュートリアル知識がそのまま使える。unsafe。vulkanalia（vulkan-tutorial.comの完全Rust移植）という教材あり
- **vulkano**: 安全ラッパー。ただし独自抽象の学習が混ざり中途半端になりがち
- **wgpu**: WebGPU抽象層。Firefox基盤・Bevy採用。記述量はVulkan直の1/3〜1/5

この時点の推奨は「まずwgpuで概念を掴み、必要になったらashに降りる」だった（後に覆る）。

### ユーザー: 動機はUnity/Unreal批判。自作エンジンを作りたい

> とにかくUnityやUnrealのグラフィックスパフォーマンスはデバイスの理論値からは大きくかけ離れて低く（中略）基本的に商業向けにちゃんとゲームを作るならエンジンは自分で書かなければいけないと言われています。
> UnityやUnrealの今までの利点はあくまでもEditorのUIにあったが、AIがもはやUIを一瞬で作れる以上Editorは強みではない

- 先輩が2年で人力でエンジンを達成しており、AI駆動なら可能と考えている
- vulkanoが型安全でコーディング憲法に適合しそうで魅力的だが、信頼性が気になる
- wgpuではなく生Vulkanを触るメリット（デバイスの自由度・高速化余地）を理解したい

### AI: vulkano非推奨。生Vulkanの優位点の具体化。前提への正直な評価

**vulkanoの信頼性**: 実質メンテナ1〜2名、メジャーバージョンごとにAPI破壊、商用実績ほぼ無し。
信頼性序列は wgpu（Mozilla/Firefox基盤）> ash（薄すぎて壊れる場所がない）> vulkano。

**生Vulkanがwgpuに勝る点**: バインドレスレンダリング、メッシュシェーダー/レイトレーシング拡張、
明示的マルチキュー（非同期コンピュート）、同期バリアの手動制御、CPUオーバーヘッド、新拡張への即時アクセス。
wgpuは「WebGPUというポータブルな共通部分集合」に縛られる。理論値志向なら最終的にashに行くのは正しい。

**前提の評価**: Unity/Unrealの汎用性の税金は事実。ただし「書いている奴らは素人」は事実に反する
（Nanite/Lumenは学術会議レベル）。問題は技術力でなく汎用性・互換性という設計目標。
特化エンジンが速いのは「作るゲームが決まっていて不要機能を捨てられる」から。

### ユーザー: 「本質的な抽象化コスト」と「負債・残骸」を混同するな

> 本当に理論上マルチプラットフォーム対応するための抽象化によるコストと、単に作ったやつが馬鹿で失敗してる残骸や負債の話は区別すべきです。（中略）負債や残骸はAI駆動であれば一瞬で返せる

- 外部エンジン依存の問題は利用規約・料金だけでなく、Unity社内部のワークフロー障害で負債が解消されないこと
- レイヤー認識の質問: 「まずエンジンが存在していて、それに対してプラットフォームごとにこの機能は使える使えないという抽象化が行われる」と考えているがどうか
- 最初はWindowsで動けばいいのでは？

### AI: 区別を受け入れ。レイヤーの上下は逆。Windows先行は正しい

- 負債の区別は正当。ただし負債の発生源は怠慢だけでなく「将来要求が不明な時点での設計判断」にもある。
  AI駆動の正確な効能は「間違った設計を捨てて書き直すコストが安いため、負債を抱え続ける理由が消える」
- **レイヤー構造の修正**: 「機能の使える/使えない」を表す層（RHI）はエンジンの上ではなく下に置く。
  エンジンはRHIに対して書かれる。ただしcapabilityフラグという直感は正しく、Vulkan自体が
  feature/extension/limits問い合わせの仕組みを内蔵している
- **Windows先行の追い風**: Vulkan自体がクロスプラットフォームAPI（Windows/Linux/Android、
  MoltenVK経由でmacOS/iOS）。プラットフォーム固有はウィンドウ生成・サーフェス接続だけでwinitが吸収済み
- **コンソールだけは別**: 独自API・SDKはNDA下。RHI切り出しはコンソール対応が現実になった時点の
  リファクタリングでよい（AI駆動なら書き直しコスト低）

**確定方針**: RHIは今作らない。ashで直接書く。シェーダー言語はSlang（Khronos管轄、
SPIR-V/DXIL/Metal出力可）を最初に固定。最初のマイルストーンは winit + ash でスワップチェーン → 三角形 → glTF → PBR。

### ユーザー: ashをRustで書く利点がないのでは？vulkanoフォーク案

> 私自身でvulkan apiをrustで型安全にするための層を自分であなたに作らせたとしてそれを使いまわすこともないような気がする
> 叩き台としてvulkanoを使い、フォークする形で改造して信頼性はこちらで自分で担保するという方法もあると思うのですがどうでしょうか

### AI: 「汎用の型安全層」は作らない。作るのは「エンジンの使い方だけを露出する狭い層」

- vulkano/wgpuが難しいのは「あらゆる使い方を安全にする」汎用問題を解いているから。汎用の安全性証明は
  型で表しきれず実行時追跡コストを払う——それは避けたいオーバーヘッドそのもの
- 自分のエンジンは使い方が有限。運用規約（テクスチャはロード時生成・描画中不変、バッファはフレームごと
  リング等）を型にすれば、安全性は狭い層に閉じ実行時コストゼロ
- その層は使い捨てラッパーではなく**エンジン中核（レンダーグラフ + リソースシステム）そのもの**。
  レンダーグラフは同期バリア配置（Vulkanバグの大半）を依存関係から自動導出する仕組みで、
  現代の自作エンジンはほぼ例外なく持つ。型安全化層の工数 = どのみち書くエンジン本体の工数
- **vulkanoフォークは却下**: 要らない汎用性を大量に相続してから削る作業になる。ユーザー自身の
  思想（汎用性は負債）に照らしても、狭い自作層をashに積む方が1桁小さい
- 開発時はvalidation layer（同期検証含む）常時有効、リリースで外すのが標準作法

**確定構造**:

```
ゲームロジック（安全なRust）
   ↓
エンジン: シーン・アセット・マテリアル（安全なRust）
   ↓
レンダーグラフ + リソースシステム ← 自作の型安全層 = エンジン中核
   ↓
ash（unsafeはこの層の実装内部に封じ込め）
```

### ユーザー: C:\devs\Blitzdrache0 でプロジェクト開始。リポジトリ戦略を決めたい

> Blitzdrache0（ブリッツドラッヘ）意味: 稲妻（Blitz）＋ 竜（Drache）

全構造を1プロジェクトに入れるか、層ごとにプロジェクトディレクトリを分けるか。

### AI: 単一リポジトリ + Cargoワークスペース（層 = クレート）で両取り

- リポジトリ分割は不採用: 初期は層をまたぐ変更が毎日発生し、バージョン整合コストだけ払う。
  AI駆動だと単一コンテキストで全層を見渡せる単一リポジトリの利点が大きい
- 1クレート全部入れも不採用: クレート分割は**依存方向のコンパイル時強制**。
  blitz_engineのCargo.tomlにashが無い → エンジン層がVulkanに触るコードはコンパイルエラー
- `#![forbid(unsafe_code)]` を blitz_engine / blitz_app に宣言し、unsafeがblitz_render外に
  書かれることも機械的に禁止

**実施**: `crates/blitz_render`（ash封じ込め・公開APIへのash型露出禁止）、
`crates/blitz_engine`（シーン・アセット・マテリアル）、`crates/blitz_app`（コンポジションルート・winit）。
依存: ash 0.38 / winit 0.30 / glam / thiserror（ワークスペースで一元管理）。
cargo build 成功、初期コミット `95aa9ec`。

### ユーザー: 記録はメモリでなくリポジトリの開発スレッドへ。winitとは？

> 今回は壁打ちなのでそのまま保存です。

→ 本ファイル作成。以後の経緯もここに追記していく。

winitの説明: Win32のRegisterClass/CreateWindowEx/メッセージループ/WndProc一式をOS差異ごと
抽象化する純Rustライブラリ。描画機能は持たない。Vulkanとの接点はraw-window-handle経由で
HWND等の生ハンドルを渡す1箇所だけ。

### ユーザー: C++時代は「GLFWを使わず自分でウィンドウを作れ」と言われた。Rustではどうか

> クロノスのチュートリアルでは謎のライブラリ（GLFW？）を使ってたがそこは使わないで自分でウインドウ使ったほうが良いと言われて、Cppだったのでやりましたが、rustだとそれはどうでしょうか？

### AI: Rustではwinit採用が正解。C++の助言は損得が逆転する

**判断**: winitを使う。生Win32自作（`windows` クレート）は却下。

- C++で「GLFW回避・Win32自作」が正しかったのは、GLFWが描画コンテキストまで抱える太い
  Cライブラリでメッセージポンプを隠蔽し、かつ同じ言語圏なので自作が安かったから
- Rustで生Win32をやると全部unsafeのFFIになり、`blitz_app` の `#![forbid(unsafe_code)]` と
  unsafe封じ込め設計を、性能に無関係なウィンドウ処理のために破ることになる
- ウィンドウ生成・イベント処理は理論値志向の対象外（フレームあたりμs級、削っても速くならない）
- winitはGLFWと違いウィンドウとイベントだけの薄いライブラリで、Raw Inputも `DeviceEvent` で露出
- 保険: winitに触るのはコンポジションルート(blitz_app)だけ。raw-window-handle経由の設計なので、
  将来winitのイベントループモデルが邪魔になったら生Win32実装に差し替えてもエンジン本体は不変

### ユーザー: winitのコールバック型イベントループが心配

> winitのイベントループモデルはコールバック型なんですね。それはちょっと心配ですね。

（補足: この直前にBlitzdrache用コーディングルール整備の話が出たが、誤ってBoomYackの
SengenUIルールを参照しかけたため中断。ルール整備はプロジェクト専用ディレクトリで
セッションを開いてから行うことになった。未着手の残タスク）

### AI: コールバック性はOS側の現実。定石と脱出口があり心配は封じ込め可能

- コールバック型はwinitの発明ではない。Win32のWndProc自体がOSから呼ばれるコールバックで、
  さらにWindowsはリサイズ・移動中にOSがモーダルループに入り自前のメッセージループが返らなくなる。
  生Win32でも起きる。macOS/Android/iOSのライフサイクル要求も同根
- 本当の論点は「ループの所有権」。ゲームは `loop { 入力; 更新; 描画 }` と書きたいが、
  winit 0.30はApplicationHandlerトレイトを渡してwinitがループを所有する
- **ゲームでの定石**(Bevyも同方式): `ControlFlow::Poll` + `about_to_wait`で`request_redraw()` +
  `RedrawRequested`で1フレーム分の更新+描画。リサイズ中も描画が止まらない利点あり
- **保険は二重**: (1) blitz_engineは「更新(入力, 経過時間)/描画()を外から呼ばれるだけ」の
  ループモデル非依存APIにする。winitの流儀に染まるのはblitz_appの数十行だけ
  (2) `pump_app_events`（デスクトップで利用可）で従来型の自前ループに移行できる

**判断**: 標準パターン（Poll + request_redraw）で開始し、ループ所有権が実際に必要になった
時点でpump_app_eventsへ移行。
