## 判別方法は変わりません

## 効果が薄い理由（ここが本題）

他の3つの束（ポスト処理一式・シーン描画資源・フレーム進行）で得られた効果は、**`破棄する(&device)` 1回の呼び出しになり、内部の順序が束の中へ移った**ことです。`destroy.rs` は束どうしの順序だけを持つようになりました。

提示一式ではこれが得られません。Vulkanの制約が原因です。

- `swapchain` は device レベルのオブジェクトなので `vkDestroyDevice` の**前**に破棄しなければならない
- `surface` は instance レベルのオブジェクトなので `vkDestroyDevice` の**後**に破棄しなければならない

現在の `destroy.rs` がそうなっています。

```
L54: swapchain.破棄する(&device, &swapchain_loader)   ← 束の一部
L55: device.全メモリ解放を確認する()
L57: destroy_device()
L59: destroy_surface(surface)                          ← 束の一部
L61: デバッグメッセンジャー.破棄する()
L64: destroy_instance()
```

## 私が実装した部分

**Vulkan の同期方針にあたる部分**なので直接書きました。

- `描画束ID` — レンダラーにとって**不透明な番号**です。`blitz_render` が `blitz_engine::チャンク座標` に依存すると、世界の分割方針が描画レイヤーへ流れ込むので、意味は呼び出し元だけが持ちます
- `レンダラー::描画束を追加する` / `描画束を解除する` — どちらも `device_wait_idle` を伴いません
- **遅延破棄**: 解除は即座の破棄ではなく破棄待ちへの移動です

遅延破棄の根拠を明示しておきます。解除予約は描画発行より前に行うので、予約時点でその束を使う**新しい**描画は発行されません。残るのは発行済みのものだけで、フレームインフライト数ぶんフレームが進めば必ず完了しています（同じスロットを再び使うときにフェンスを待つため）。

**数えるのは提示まで到達したフレームだけにしました。** 見送り（最小化中など）ではフェンス待機が起きないので、フレームを数えても完了の保証が得られません。ここを取り違えると、GPUが使用中の資源を破棄します。

同じIDの二重追加は `assert!` で停止させます。上書きを許すと旧い束のGPU資源を辿れなくなって漏れるので、回復可能な失敗ではなく破られた不変条件として扱いました。`error.rs` が既に100行だったことも、エラー型を増やさない判断を後押ししています。
