### 概念E: 粗マスに置くもの

**今どこに溶けているか**: `coarse_cell_paint.rs:14-19` の `粗マスの塗り{列, 行, 高さメートル: Option<f64>, 層: Option<地表材質層>}`、`command/plan_view_ops.rs:38` の「高さも層も無い項目は**その粗マスの塗りを消す**」、`plan_view_draft.rs:44` の `(塗り.列, 塗り.行)` のタプルへの剥がし。

**与える名前**: `粗マスの位置` と `粗マスに置くもの`

```rust

    高さだけを置く { 高さメートル: f64 },
    層だけを置く { 層: 地表材質層 },
    高さと層を置く { 高さメートル: f64, 層: 地表材質層 },

```

**外へ見せるメソッドの全列挙**: `粗マスの位置` は `生成する(列, 行)` / `列()` / `行()` / `粗マスの数の内側であることを確かめる(粗マスの数)`。`粗マスに置くもの` は `検証する()` / `高さを置くか()` / `層を置くか()` / `塗りを消すか()`。

**分解後の宣言数**: **+7件で増える。** 正直に書くと件数は増える。得るものは、起こり得ない組み合わせが型の上から消えることと、`塗りを消す` という今は文書にしか無い意味が型の名前になることである。**件数を減らすことがこの分解の目的ではない。**

**検査体系が止められなかった原因**: **規約の不在**。「同時に生まれて同時に消えるOptionを、別々のフィールドで持たない」は「同時に」を要件にしており、この2つは独立に省けるため射程外である。**独立に省ける2つの `Option` が、組み合わせで第3の意味(命令)を持つ形**を扱う条文が無い。

## 2. 階層の案

現在の `resource/mod.rs` は31個の `mod` を1階層に平置きし、`pub use` で約100個の名前を1つの平らな一覧として再輸出している(`mod.rs:33-81`)。上位(`lib.rs:48-49`)はこの100個を全部知っている。

### 切った後: 4階層

```
resource
├── 値 (position, plane_position, chunk_coordinate, building_definition_id,
│      numeric_check, text_check, validation_error)          … 7
├── 資源 (building, chunk_road, regional_road, scatter_settings,
│        scattered_individual, contour_line, coarse_cell_paint,
│        plan_view_draft, chunk_structure, world_structure, world_layout,
│        material_*, building_grid, building_outline_catalog, grid, music) … 16
├── 版 (chunk_structure_version, world_structure_version, music::version) … 3
└── 操作 (command, music::command)                            … 2
```

`resource` が直接知る相手: **31 → 4**。

**停止条件1**: `値` は誰も知らない(葉)。`資源` は `値` の7個のみ。`版` は `資源` と `値`。`操作` は `値` と `資源`。

**停止条件2**:

- `値`: **存在理由を共有** — どれも「1つの値の不変条件を型で閉じる」ためだけに在る
- `資源`: **寿命を共有** — どれも「保存されるJSONまたはバイナリの1本ぶんの内容」である
- `版`: **頻度を共有** — どれも「読み込みの1回だけ通り、書き込みでは通らない」片道である
- `操作`: **寿命を共有** — どれも「利用者の1回の操作」であり、資源より短い

**向き**: `操作 → 資源 → 値`、`版 → 資源 → 値`。**ただし1つだけ逆になっている。**

- `resource/coarse_cell_paint.rs:6` — 資源である `粗マスの塗り` が `use super::command::地表材質層;` で**操作の階層を参照している**

概念Rの分解でこの列挙を `資源` の階層へ移すと、この1本の逆向きが消え、一方向だけで書けるようになる。

**上位が下位の中身を操作している箇所**: `chunk_structure_version.rs:70-97`(概念G)と `building_outline_catalog/validation.rs:36,43-44,53`(概念L・M)。後者の `定義を検証する(定義: &建物外形定義, 識別子一覧: &mut HashSet<String>)` は親を丸ごと受け、親の欄を1つも減らしていない。

## 6. 規約への提案

### 提案1: 「常に揃って渡される引数の組」の条を、宣言の組へも及ぼす

**書き換え案**:

> 同じ2つ以上の値が、名前の無いまま**3つ以上の宣言箇所**(関数の引数の並び・構造体の欄の並び・列挙の枝の中身)へ繰り返し現れるなら、それらは1つの概念である。**判定は「揃って現れる回数が3以上か」で行い、「引数か欄か」では行わない。**

**止める実例**: 概念A(20枝)・概念C(3構造体)・概念J(3型)。

**止めてはならない正常例(3件)**: `位置3次元{x,y,z}`(既に名前の付いた型の内部)、`打ち込みの対象`(現れているのは1欄)、`升目の座標`(名前の付いた型であり、かつ2箇所で3未満)。**回数で切る理由は、2箇所での一致は偶然でありうるが、3箇所での一致は偶然でないためである。**

### 提案2: 委譲だけの型を作らない条を、型の粒度で置く

**書き換え案**:

> **委譲だけの型を作らない。** 他の型を1つ包む型は、外へ見せるメソッドのうち、**包んだ型のメソッドをそのまま呼んで結果を返すだけでないもの**を1つ以上持つこと。**書けないなら、包むのをやめるか、型が引き受けるべき判断が別の場所に置かれている。**

**止める実例**: 概念Dの3型。この規則は「3型を消せ」ではなく「`grid/chunk_heightmap.rs:4` が経路へ出したと自ら書いている突き合わせを、型の中へ戻せ」と読ませる。

**止めてはならない正常例(3件)**: `建物定義ID`(`生成する` が検査を持つ)、`チャンク座標`(`アンダースコア区切り表記` が新しい値を導く)、`コマンドの指し先の解決係`(外へ見せる5本すべてが判断)。

### 提案3: クレート内のモジュール間の依存の向きを機械で見る

**書き換え案**:

> **層を名乗ったモジュールは、その層に許さない参照を持たない。これを `cargo xtask conform` の表で機械的に見る。** 表は「モジュールのパス」と「そのモジュールとその子孫が参照してはならない綴りの一覧」の対で書く。型契約層は入出力(`std::fs`・`std::io`・`serde_json::from_reader`・`serde_json::from_slice`)を参照しない。現状を上限として登録し、増えたら落とす。

初期の1行: `crates/editor_server/src/resource` は `std::fs` `std::io` を参照しない。

**止める実例**: 概念S。**止めてはならない正常例(3件)**: `storage/file_repository/chunk.rs:33`(storage は型契約層ではない)、`resource/building_outline_catalog/validation.rs`(同じディレクトリにありながら `std::fs` に触れない)、`resource/chunk_coordinate.rs`。**ディレクトリ単位で罰するのではなく、参照した綴りで判定する。** この形なら `resource/` 配下40ファイル中39ファイルが無変更で通る。

### 提案4: 版の移行の変換は、版ごとの型のメソッドとして持つ

**書き換え案**(「不在・未設定・使用不可」の条へ1文を足す):

> **変換は版ごとの型のメソッドとして持つ。版を並べる列挙は、枝ごとにそのメソッドを呼ぶだけにする。**
