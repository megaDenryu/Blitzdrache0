## 0. 分母の食い違い(道具の欠陥。最優先で報告する)

`xtask/src/conform/type_metrics_ledger/ledger.rs:36` の登録行はこうである。

```rust
型ごとの上限::構造体("一つの箱と静的な直方体の場面", 14, 0, 29),
```

署名は `構造体(型名, 実装ファイル数, フィールド数, メソッド総数)` である(`xtask/src/conform/type_metrics_ledger/limit.rs:16`)。**実装ファイル数14とメソッド総数29は現物と一致するが、フィールド数0は現物16と食い違う。**

原因は `xtask/src/type_metrics/member_line.rs:11-20` である。

```rust
match 整形.split_once(':') {
    Some((名前部分, _)) => !名前部分.is_empty() && !名前部分.contains('('),
    None => false,
}
```

`pub(super) 箱の識別子: 剛体の識別子,` の名前部分は `pub(super) 箱の識別子` であり `(` を含むため、**`pub(super)` / `pub(crate)` / `pub(in path)` の可視性を書いたフィールドは1つも数えられない。** 括弧の除外はタプル構造体とメソッド行を落とすためのものだが、経路を書いた可視性を巻き込んでいる。

影響範囲: `crates/` 配下で `pub(crate)` または `pub(super)` を書いたフィールド宣言らしき行は **1583行**ある。全フィールドが経路付き可視性である型は、台帳へフィールド数0で登録されている。この道具は「増えたら落とす」ための正本であるため、**フィールドの増加を検出する機械検査は現在ほぼ機能していない。**

この欠陥は [Issue #62](https://github.com/megaDenryu/Blitzdrache0/issues/62) として起票した。

## 7. 規約への提案

### 提案1: 「切り出した先が親を丸ごと受け取る形」の禁止を `&self` へ広げる

**どの文言がこの形を合法にしたか**: CLAUDE.md「切り出しの根拠義務」の2026-09-04追記は**引数の位置に書かれた `&親型`** を対象にしている。`impl 親型` の中のメソッドが受け取る `&self` は、意味論的に完全に同じものでありながら、この文言の字面に当たらない。

**書き換え案**:

> この条は `impl 親型` として切り出したメソッドの `&self` にも適用する。**判定は「そのファイルのメソッドが親のどのフィールドを触るか」で行い、切り出したファイルの冒頭コメントへ触れるフィールドを名前で列挙する。列挙が空になる(1つも触らない)メソッドは、その型に属していない。**

**この規則が止める実例**: `substep_sticking_rows.rs:25`・`:41`、`substep_sliding_fallback.rs:32`、`record_line.rs:53`・`:68` の5本。

**止めてはならない正常例(2件)**:

1. `cone_breach_record/eigen_direction_readers.rs`。冒頭コメント3-4行目が既に触れるフィールドを名前で列挙している。**この規則が要求する形を、制定される前から満たしている**
2. `substep_velocity_stage.rs`。触れるのは5つであり、列挙は空でない

**この規則をフィールド数の閾値にしなかったのは、それが2を落とすためである**(5は16の半分未満だが、速度段階の切り出しは局面の分離として正しい)。空か否かという最も狭い線に留めることで、目の前の5件だけを落とす。

### 提案2: `type-metrics` のフィールド計数を直し、全台帳を再計測する

0節を見る。[Issue #62](https://github.com/megaDenryu/Blitzdrache0/issues/62) として起票済み。

**止めてはならない正常例(2件)**: `blitz_math` の `メートル`(本当にフィールドが少ない `#[repr(transparent)]` の newtype)、`剛体と静的世界の接触拘束`(フィールド5は現物と合っている)。**この提案は判定の線を1本も動かさず、数え漏らしを直すだけである。**

### 提案3: 同じクレートの中でファイルをまたいで複写された数値定数を見る

**書き換え案**(「機械的強制」の検査項目へ追記):

> 検査の対象を「同じ値を持つべき定数の対」全般へ広げる。**具体の判定は、`_doc/` の設計文書か規約が「正本」と名指しした値について、その値のリテラルが2つ以上のファイルに現れることを違反とする**(名指しの無い値は対象外である)。名指しは `xtask` の台帳へ「正本のファイルと定数名」の形で登録する。

**この規則が止める実例**: `細分の刻み幅` の正本を `slope_fixture.rs:29` と登録すると、`drop_tests.rs:48`・`normal_iteration_record.rs:35`・`normal_multiplier_sum_tests.rs:41` の3箇所が落ちる。

**止めてはならない正常例(2件)**: `slope_tests.rs:34` と `tolerance_boundary_tests.rs:22` の `保持を要求する変位の上限`(2つの試験が独立に同じ受入条件を引用している)、`slope_fixture.rs:26` と `drop_tests.rs:23` の `箱の半分の長さの値`(たまたま同じ大きさであるだけ)。**規則の発火条件を「値が同じであること」ではなく「正本として名指しされていること」に置いたためである。**
