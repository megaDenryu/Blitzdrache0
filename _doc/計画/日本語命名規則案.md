# 自然で直感的な日本語のための命名規則案

## 1. 背景と目的
これまでの開発において、規約への過剰適合（小学生基準の誤読、擬人化、機械翻訳的な直訳漢語）により、プログラミングやゲーム開発の実態から乖離した不自然な日本語が多発した。
本規則は、**「誰が読んでも一読してデータ構造と処理の意図が正しく伝わる、自然で実用的な日本語」**を確立することを目的とする。

---

## 2. 命名の基本原則

### 原則1: 業界の定着度と認知負荷を最優先にする（不適切な翻訳の排除）
- ゲーム開発・CG・物理シミュレーションにおいて一般的に定着している用語は、無理に直訳漢語や大和言葉へ置き換えず、そのまま自然な用語を採用する。
  - **推奨**: `サブステップ`、`カスケードシャドウ`、`ワールドオフセット`、`シーン`、`コンテキスト`、`ピクセルシェーダー`、`バッファ`、`トークン`
  - **禁止**: `細分`、`多段影`、`大域ずらし量`、`世界`、`取り出し口`、`画素段`
- ただし、漢字表記で十分に直感的かつ定着している基本用語は無理にカタカナ化しない。
  - **維持**: `点光源`（ポイントライトも可）、`平行光源`、`減衰`、`剛体`、`座標`、`法線`、`視錐台`

### 原則2: 概念やデータ構造の擬人化を禁止する
- データ構造、設定、シーンなどの概念を主語として喋らせない。
- プログラムを実行・評価・操作する主体（システム、関数、呼び出し元）の視点で主述を組み立てる。
  - **禁止**: `世界が設定を読む / 読まない`、`配線が時刻を知らない`
  - **推奨**: `シーンが設定に対応している / 非対応である`、`設定を適用する / 無視する`

### 原則3: バリデーション・検証関数の主述を明確にする
- 「〜であることを確かめる」という曖昧・主客転倒な文を廃止する。
- ガード関数（不正な入力を弾く処理）は、**「何を拒絶・禁止するか」**または**「何の不正を検証するか」**を名指しする。
  - **禁止**: `局所光の件数の上書きを読まない世界であることを確かめる(...)`
  - **推奨**: `非対応シーンへのローカルライト数上書きを禁止する(...)`
  - **推奨**: `ローカルライト数上書きの不正指定を検証する(...)`
- アサート関数（前提条件を確認する処理）は、**「何が保証・検証されるか」**を書く。
  - **推奨**: `入力値の範囲が有効か検証する(...)`

### 原則4: スコープに応じた情報量の規律（二極化の解消）
- **公開型名（外向け）**: 1行まるごとの動作説明ポエムにしない。実体と役割を表す名詞句とし、詳細な仕様はコメントに委ねる。
  - **禁止**: `GPU命令の積み先と宣言済み資源の取り出し口`
  - **推奨**: `レンダーパス実行コンテキスト`
- **モジュール内私有関数（内向け）**: かっこつけて動詞や目的語を削らない。「何をどうする関数か」を明記する。
  - **禁止**: `方針を作る`、`灯数を決める`、`確定値`、`可視性を決める`
  - **推奨**: `夜間ライティング設定を生成する`、`配置するライト数を決定する`、`不変定数を検証して取り出す`、`影の生成可否を判定する`

### 原則5: 文学的・哲学的メタファーの排除
- 小説の設定資料集のような文学的抽象語を、実体を表す技術用語へ戻す。
  - `世界` → `シーン` または `環境`
  - `名前で選ばれない世界` → `未定義シーン` または `汎用シーン`
  - `破れ` → `破損` または `フォーマット不整合`
  - `参加者` → `対象剛体` または `拘束対象`
  - `選別係` → `カリング選別器` または `LODセレクター`
  - `綴り` → `シーン名` または `識別文字列`

## 3. 品詞・助数詞の規律
1. **助数詞の自然さ**:
   - サブステップやステップの回数を「本数」と呼ばない（`サブステップ数`、`ステップ回数`）。
   - ライトやオブジェクトの個数を不必要に「件数」一辺倒にせず、指すものに応じて「数」「個数」とする。
2. **エラー型の命名**:
   - エラー種別は状況描写の文章ではなく、「何が起きたか（原因・不正内容）」を表す名詞句にする。
   - **禁止**: `局所光の件数の上書きを読まない世界`
   - **推奨**: `ローカルライト数上書き非対応シーン` または `未対応シーンへのライト数指定`
