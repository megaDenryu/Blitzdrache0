# 評価軸

この文書は、エンジンを評価するための判断軸・判断方法・判断フローを定義する。実装・計画と常に一致させて維持する。制定の経緯は開発スレッド2026-07-20を参照。

評価は「能力」「品質」「性能」「変更容易性」の4系統に分ける。品質系は機械検証が導入済みのため、この文書は残り3系統の制度化が中心になる。

## 1. 能力(何ができるか・その意義・できないことの重大さ)

能力は一般的な機能一覧に対する充足率ではなく、**対象ゲーム像(原神型オープンワールドRPG)への到達度**で測る。

- 能力の判定には代表シーンテストを使う。**代表シーンテスト**とは、対象ゲームの典型的な1シーンを構成要素に分解し(フィールド地形・植生・キャラクターと衣装物理・空と時間帯・戦闘エフェクト・UI・ストリーミング・オーディオ)、各要素を現在のエンジンで実行できるか判定する試験のことである。
- 実行できない要素の重大さは**出自分類**で判定する。出自分類とは、その要素が計画のどこに由来するかを次の3つに振り分けることである。
  - (a) 実装予定のマイルストーン(M0〜M11)にある → 予定どおりの未実装。
  - (b) 長期フェーズ計画にある → 意図して後回しにした未実装。
  - (c) どちらにも無い → **計画から漏れた真の欠落**。発見したら開発計画の改訂として扱う。
- 能力の意義は、その能力がこのエンジンの差別化の中心(キャラクターシミュレーション・性能・AI駆動開発への適合)に属するか、汎用エンジンを使えば追加コストなしに得られるものかで判定する。差別化の中心に属さない能力は先行して実装せず、計測または仕様が必要性を示してから実装する。
- 2026-07-23のM11分類結果: キャラクターと衣装物理はフェーズ1で実装済みである。地形、植生、空と時間帯、戦闘エフェクト、本番UI、ストリーミング、オーディオは長期フェーズ計画の(b)に存在し、計画から漏れた(c)は検出されなかった。詳細は `_doc/計画/エンジンフェーズ1完了報告とフェーズ2計画.md` を参照する。
- 2026-07-28のOW3完了時点で、代表シーンの構成要素のうち地形が(b)から実装済みへ移った。高さ地形をチャンク単位の詳細段で描き、境界の亀裂をスカートで塞ぎ、km級の大域座標でも描画が原点移動に対して不変であることを画素で判定できる。植生は未実装のままOW4に残り、空と時間帯、戦闘エフェクト、本番UI、オーディオは引き続き(b)である。計画から漏れた(c)はOW3でも現れなかった。
- 2026-07-29のOW4完了時点で、植生が(b)から実装済みへ移った。1つの原型を共有するインスタンス群を地形と同じチャンク束へ載せ、シーンパスとシャドウパスが別々の視錐台で群と個体の2段階の可視判定を行い、個体単位で距離別のメッシュLOD段を選び、群と非空LOD段の組ごとに1回の描画発行で描ける。空と時間帯、戦闘エフェクト、本番UI、オーディオは引き続き(b)である。計画から漏れた(c)はOW4でも現れなかった。

## 3. 性能

「速いか」という問いは比較先を決めないと判定できない。この文書では比較先を3つ定義する。

### 3.1 フレーム予算との比較(日常の計器)

60fps(16.6ms)をパス群に配分した予算表に対する消費率で判断する。計器はM5で導入したパス別GPU時間計測と開発用UI。

初期予算表(エンジンフェーズ1向け。パス追加時にこの表を改訂する):

| パス | 予算 |
|---|---|
| シーン描画(PBR) | 4.0ms |
| シャドウ(M6) | 2.0ms |
| ポストプロセス(M7) | 1.5ms |
| スキニング(M8、コンピュート) | 0.5ms |
| シミュレーション(M9、コンピュート) | 3.0ms |
| UI・その他 | 1.0ms |
| 予備(フェーズ2の地形・植生・ストリーミング用に温存) | 4.6ms |

M10固定条件のシミュレーション更新時間は、128×128表面流が1.9166msで予算の63.9%、全対全探索SPHが512粒子で3.8503ms（128.3%）、1024粒子で5.2107ms（173.7%）、2048粒子で9.6049ms（320.2%）だった。表面流は予算内であり、SPHは512粒子から超過するため、本実装の前提を空間ハッシュによる近傍探索へ更新する。

2026-07-25のOW2固定ベンチ5回では、シーン描画が0.1487〜0.1605msで予算の3.7〜4.0%、シャドウが0.0303〜0.0436msで1.5〜2.2%、ポストプロセス合計が0.1008〜0.1135msで6.7〜7.6%、粒子更新が0.0115〜0.0130msで0.4%だった。GPU合計は0.3105〜0.3329msで16.6msフレーム予算の1.9〜2.0%である。ただし4回目だけトーンマップが0.5303msとなり、ポストプロセス合計0.6594ms(44.0%)、GPU合計0.9017ms(5.4%)へ跳ねた。この1回の原因は特定しておらず、GPU側の変動要因として残す。詳細は `_doc/計測/OW2_2026-07-25.md` を参照する。

OW3(2026-07-28完了)はGPUパスを追加していない。地形チャンクは既存のシーンパスとシャドウパスで描かれ、1チャンクが1つの描画対象として、距離で選んだ詳細段の頂点とインデックスだけを積む。したがってパスの区分は変わらず、予算表も改訂しない。ただしOW3完了時点でのパス別GPU時間の再計測は行っていないため、消費率は3.4節に記録したOW2完了時計測が最新である。地形の物量を載せた消費率は、植生と可視判定を含む代表シーンを測るOW4で更新する。

OW4(2026-07-29完了)もGPUパスを追加していない。植生は地形と同じシーンパスとシャドウパスで描かれ、群と非空LOD段の組ごとに1回の描画発行を積むだけである。したがって予算表は改訂しない。OW4の物量計測は`--unlit --no-post`で行っており、ライティングとポスト処理を止めているため、消費率を更新できるのはシーン描画とシャドウの2行だけである。以下の値の一次記録は`_doc/計測/OW4_2026-07-29.md`にある。

シャドウは、可視判定で個体を絞らず全候補を描いていた第5段の実装で、常駐50,026個体のとき3.27〜3.85msとなり2.0ms予算の164〜193%を消費した。1,000,026個体では5.21〜5.31msで261〜266%である。第6段でライト視錐台による個体カリングを入れた後は、50,026個体で0.143〜0.155ms(予算の7〜8%)、1,000,026個体で0.0324〜0.0328ms(予算の2%)へ下がり、予算内へ戻った。

シーン描画は1,000,026個体で5.44〜5.46msとなり、4.0ms予算の136〜137%を消費した。第6段の後は同じ物量点で5.90〜5.99ms(148〜150%)である。**これがOW4完了時点で残る唯一の予算超過である。**ただし超過が確定するのはこの物量点だけである。10,026〜100,026個体ではGPUのクロックと電力状態の変動が絶対値を支配し、入力が1件も違わない前後の実行で3倍以上動いた実測があるため、この負荷帯のシーン描画の値は物量の関数として読めない。低・中負荷帯での予算判定には、GPU負荷を固定した別の計測が要る。

判定基準: 消費率50%未満は順調。50〜100%は注視し、物量スケーリング(3.3)を確認する。100%超過は最適化タスクとして札に登録する。**最適化は計測に基づくものだけを行う**(開発計画の判断基準4)。

### 3.2 理論性能との比較(判定精度は高いが算出コストも高い。予算超過したパスに絞って適用)

- 対象パスの支配資源(メモリ帯域・ピクセル処理レート・三角形処理レート・演算能力)を特定し、GPUの仕様値から求めた理論下限時間との乖離倍率を出す。
- 乖離が説明できない大きさ(目安: 数倍以上)のときに初めて最適化に着手する。手法はGPUプロファイラ(Nsight等)による支配資源の実測と、ボトルネックへの構造的対処。

### 3.3 物量スケーリング(オープンワールド方針の検証手段)

- 同一シーンの物量(インスタンス数・頂点数・テクスチャ量)を1倍・10倍・100倍に変えて所要時間の伸び方を記録し、線形から外れる点(折れ点)を特定する。
- 折れ点の原因(描画コマンド数・メモリ帯域・CPU律速のいずれか)が、フェーズ2の投資先(バインドレスディスクリプタ・GPU駆動カリング)の根拠データになる。
- OW0完了時点では、同じメッシュとマテリアルを持つ描画対象を固定カメラ内へ1・10・100個配置し、描画発行数、GPU時間、CPU時間、GPUメモリを`cargo xtask object-bench`で比較できる。2026-07-23の実測では、1→100対象でシーン描画が0.0506→0.0755ms、シャドウが0.0287→0.0353ms、CPUの記録・送信・提示平均が0.1482→0.1784msとなり、描画発行は予算内だった。GPUメモリ確保数は10→604件へ増え、対象ごとに6件増える線形構造を確認した。この固定quad計測は描画対象数だけの基礎特性を測るものであり、OW4では植生、可視判定、LODを含む代表シーンへ差し替えて折れ点を正式に判定する。2026-07-25のOW2時点で同じコマンドを再実行したところ、1→100対象でシーン描画は0.0060→0.0154ms、シャドウは0.0037→0.0090ms、CPUの記録・送信・提示平均は0.2041→0.1761msだった。GPUメモリ確保数は10→64→604件で対象ごとに6件増える線形構造が維持されている。GPU時間の絶対値は2026-07-23の計測より低いが、同一コミットでの反復計測を行っていないため、実行間変動と実装差のどちらが主因かは判定していない。
- OW3完了時点(2026-07-28)で、地形1チャンクの実物量を得た。実行時形式は5段の詳細段を含めて440,882バイトであり、最詳細1段だけを焼いていた時点の319,694バイトの1.379倍である。先読み半径2で25チャンクを常駐させた統合計測(`cargo xtask ow3-dod`)では、ディスク読込が25件・11,022,050バイト、GPU転送が25件・11,017,200バイトだった。地形は1チャンクにつき1つの描画対象であるため、この量は常駐チャンク数に比例する。1倍・10倍・100倍の折れ点判定は、同一メッシュを共有するインスタンス群が入るOW4で行う方針を変えない。
- OW4完了時点(2026-07-29)で、代表シーンによる1倍・10倍・100倍の折れ点判定を正式に行った。計測は地形と植生が同居する25チャンクの検証用地形世界で行い、原型・共有マテリアル・カメラ経路・LOD閾値・配置の種をすべて固定して**変えたのはチャンクあたりの個体数だけ**である。物量点は常駐10,026・20,026・50,026・100,026・1,000,026個体の5点であり、各3回反復した(入口は`cargo xtask ow4-bench`)。**折れ点は5倍の50,026個体であり、そこで最初に予算を超えたのはGPUのシャドウパスである。**1倍と10倍のあいだに折れがあったため、規則に従って2倍と5倍を足して局在化した。折れ点での支配要因はGPUのシャドウパスであり、観測範囲全体(1倍から100倍)の支配区間は群選択である(増分9.92msで、2番目のシャドウの5.03msの約2倍)。この2つは別の問いへの答えであり混同しない。CPU区間には観測範囲内に折れ点が無く、群選択の個体あたり費用は5点すべてで9.55〜10.25nsに収まる。**描画発行数は5点すべてでシーン40・シャドウ51、GPUメモリ確保数は687件であり、個体数が100倍になっても変わらない。**フェーズ2の投資先はこの結果で判定した。間接描画・バインドレスディスクリプタ・サブアロケーションはいずれもトリガーが立たず不採用であり、立ったのは個体判定とLOD分類の区間の改善だけである。詳細は `_doc/計測/OW4_2026-07-29.md` を参照する。

### 3.4 計測の再現性

- ベンチマークはリリースビルド、固定シーン、固定カメラ、固定600フレームで行い、`cargo xtask bench` として登録済み(繰り返す検証は使い捨てにせずコマンド化する方針)。GPU時間に加え、先頭120フレームを除外したCPU側フレーム間隔の平均・p50・p95・p99・最大値・25ms超過回数を出力する。
- 結果は追記専用の記録として `_doc/計測/` に残し、推移を見る。CPU側はフレーム時間分布(中央値p50・悪化側p99・突発的な遅延の検出)を併記する(M11の完了条件に接続)。
- 2026-07-23のM11初回計測では、GPU合計0.7276msに対してCPU側フレーム間隔はp50 16.7057ms、p95 33.2550ms、25ms超過率8.75%だった。GPU予算には余裕があるが60fps安定は未達であり、イベントループとFIFO提示待ちを次の調査対象とする。詳細は `_doc/計測/M11_2026-07-23.md` を参照する。
- レンダラー内部の区間計測では、p99 33.5772msの遅延がフェンス待機へ集中し、フレームデータ準備・画像取得・記録送信提示はいずれもp99 1.5ms未満だった。フレームインフライト数変更では改善が再現しなかった。
- 実表示時刻は`VK_KHR_present_id`と`VK_KHR_present_wait`で直接測る。提示に単調増加のIDを付け、次フレームの先頭でそのIDの表示完了を待ち、`--report-display-timing`指定時に実表示間隔と停止時間を出力する。対応可否は物理デバイスの拡張一覧と機能フラグの両方から判定し、非対応環境では拡張を有効化せず計測も行わない。2026-07-25のOW2の5回反復では、CPU側の25ms超過と実表示の25ms超過が最大1回差で一致し、CPU側フレーム開始間隔の33ms級の遅延が実表示の更新脱落を伴うことを確定させた。したがってCPU側間隔はFIFO供給の診断値であると同時に、この環境では更新脱落回数の指標としても使える。詳細は `_doc/計測/OW2_2026-07-25.md` を参照する。
- この計測は専用フラグ`--report-display-timing`で明示したときだけ動く。NVIDIAドライバー596.21では`vkWaitForPresentKHR`がtimeout=0でも表示まで停止するため、指定した実行は毎フレーム約16ms描画ループが止まる条件になる。指定が無ければ拡張自体を有効化しないので、`cargo xtask bench`は従来と同じ素の条件を保つ。実表示計測つきの実行は`cargo xtask bench-display-timing`で採る。
- 計測の有無を比べるときは交互に実行すること。この機材のフレーム間隔は時間帯で大きく変動し、同一コード・同一コマンドで25ms超過が0回から156回まで動いた実測がある。時間帯をまたいだ比較で摂動の有無を判断してはならない。計測なしの条件の脱落回数は、FIFOの提示1件がvblank1回でしか表示されないことを使った算術で求める。
- 単発実行の結果から実行間分散と実在する欠陥を区別できないため、再現性の判定には同一条件の反復実行を用いる。2026-07-25のOW2時点では `cargo xtask bench` を5回反復し、25ms超過が5回中5回(40〜57回 / 480標本)、p99が33.8084〜35.0483msだった。M11の値は再現し、OW1完了時の25ms超過0回は5回中1回も再現しなかった。ただしこれはその時間帯の性質であり、この環境の常態と断定してはならない（同日の後半に0回から156回までの変動を観測した。上の項を参照）。詳細は `_doc/計測/OW2_2026-07-25.md` を参照する。
- **計測は表示構成を記録してから行う（2026-07-27制定）。** デスクトップの有効表示を1画面へ切り替えた条件で同じ5回反復を行うと25ms超過は5回中4回で0回・1回で1回になり、33ms級遅延の主要因はWindowsの複数画面デスクトップ合成であると強く支持された。表示構成が違う計測値を同じ時系列として比較してはならない。単一画面のこの条件でp99は20ms以下に収まり、60fps安定の証明に使える計測環境が初めて成立した。詳細は `_doc/計測/OW2_2026-07-25.md` の追記を参照する。
- 2026-07-29のOW4物量計測も単一画面条件で行い、各物量点を3回ずつ採った。さらに既定の3点は、validation検査を足す前のコード状態でも同じ日に1回採ってある。個体あたり費用の帯と会計の6列は両方の実行で重なり、描画発行数も一致した。折れ点が2倍と5倍のあいだにあることは2つの実行で再現した。一方でGPU時間は、入力が1件も違わない前後の実行で絶対値が3倍以上動く点があり、原因はGPUのクロックと電力状態の変動である。GPU時間の比較は負荷帯をそろえた条件でしか成立しない。詳細は `_doc/計測/OW4_2026-07-29.md` を参照する。
- 2026-07-28のOW2完了時計測(単一画面、リリースビルド、helmet+粒子): GPU合計0.3404msで16.6ms予算の2.1%。シーン描画0.1522ms(4.0ms予算の3.8%)、シャドウ0.0341ms(2.0ms予算の1.7%)、ポスト処理計0.1208ms(1.5ms予算の8.1%)、粒子計0.0333ms。CPU側フレーム間隔はp50 16.6308ms、p99 21.1073ms、25ms超過1回/480標本。OW2はGPUパスを追加しておらず、チャンクは既存のシーンパスで描かれる。能力の出自分類(c)は現れなかった。

### 3.5 容量予算(ストリーミングが保持してよいRAM・VRAM)

3.1がフレーム時間(16.6ms)の配分を扱うのに対し、この節は容量(バイト数)の上限を扱う。ストリーミングが保持してよいRAMとVRAMの上限は別々に持ち、超えた分は中心優先の順序で外周を縮退させる。

| 資源 | 上限(2026-07-26時点の既定値) | 位置づけ |
|---|---|---|
| ストリーミングRAM | 400バイト | 暫定。検証用世界で縮退を発動できる値 |
| ストリーミングVRAM | 4096バイト | 暫定。板の世界ではRAM上限が先に拘束するため、縮退の決め手にならない |

**この2つの値は暫定であり、実運用の値ではない。** 検証用世界は1チャンクが369バイト、25チャンク合計9,225バイトで、開発機のベースライン(専用VRAM 144.64MiB)に対して無視できる量である。現実的な上限を置くと縮退機構が一度も発動せず、機構が動くことを確かめられない。したがって既定値の根拠は「検証用世界で縮退を発動できること」だけに限る。

RAM上限を400バイトにしたのは、1チャンクの読込前見積が216バイト、読込完了後の実測が369バイトだからである。上限をこの2つの間に置くと、中心チャンク1件だけを収容して外周8件を縮退させ、なおかつ読込完了後の実測使用量が上限を超えない。上限を2チャンク分以上へ上げると、見積を根拠に収容した集合が読込完了後に上限を超えて現在使用量超過になる。この見積と実測の乖離(実測が見積の約1.71倍)は、見積がメッシュとテクスチャの生バイト数だけを数え、実測が版付きファイル全体の長さであることに由来する。

OW3で地形1チャンクの実測量が440,882バイトになり(3.3)、暫定既定値との差が確定した。既定のRAM上限400バイトは地形1チャンクの約1,102分の1、VRAM上限4096バイトは約108分の1であり、既定のままでは地形チャンクを1件も収容できない。これがOW3完了時点で検出した予算とのギャップである。地形世界を描く実行はこのギャップを`--streaming-ram-limit`と`--streaming-vram-limit`で16メビバイトを明示して迂回しており(参照: `_doc/設計/チャンクストリーミング.md`「検証用地形世界」)、実測の最大使用量はRAM 11,018,170バイト、VRAM 11,017,200バイトでこの上限に収まる。

このギャップを既定値の改定で埋めることはOW3完了時点では行わない。既定値の根拠が「検証用の板の世界で縮退を発動できること」だけであり、地形の物量へ引き上げると縮退機構が一度も動かず、機構が働くことを確かめられなくなるためである。実運用の値の制定には1チャンクの実測量に加えて、視界距離あたりの常駐チャンク数と対象機のVRAM配分が要る。この2つは植生と可視判定を載せた代表シーンを測るOW4で確定するため、それまでは板の世界と地形世界が別々の上限を使う状態を維持する。

OW2完了時(2026-07-28)に、この暫定予算が実行時に効くことを実測で確認した。縮退・上限超過の安全退避・中心優先の優先度退避がいずれも発動し、退避を無効化した対照実行では現在使用量超過で停止する(予算が判定に使われていることの直接証拠)。30分相当108,000フレームの反復で読込12,156回・解除12,150回を経てRAM・VRAMは横ばいだった。台帳のVRAMは実破棄の報告まで減らないため、解除予約は予算上の空きにならない。

**OW4完了時(2026-07-29)も既定値は400バイトと4096バイトのままであり、実運用の値は制定していない。**OW3完了時に制定をOW4の代表シーン計測へ委ねたが、OW4が確定させたのは検証用地形世界の側の値だけである。植生を同居させた1チャンクは446,212バイトになり、先読み半径2の25チャンクで最大使用量はRAM 11,152,980バイト・VRAM 11,274,000バイトだった(参照: `_doc/設計/チャンクストリーミング.md`「検証用地形世界」)。実運用の視界距離と対象機のVRAM配分は依然として未定であり、この2つが決まらないまま既定値を上げても、検証用の値が別の検証用の値へ変わるだけで縮退機構を確かめられなくなる副作用だけが残る。**したがって制定はOW5以降へ持ち越す。これがOW4完了時点で残るギャップである。**

物量計測は個体1件あたりの会計も確定させた。台帳RAMが44.0バイト(個体配置40 + 置換検査記録4)、台帳VRAMが120.0バイト(個体変換112 + 可視ID列8)であり、見積の定数と1バイトの誤差なく一致した。1,000,026個体では台帳RAMが55,082,000バイト、台帳VRAMが131,082,000バイトである。**ただし台帳が数えるRAMとプロセス実測のprivateの差は未閉塞である。**10,026個体から1,000,026個体でprivateが約150MiB増えたのに対し、台帳RAMの増分は41.5MiBで3.6倍の開きがある。差に含まれるのはホスト可視の可視ID列・群可視材料の個体境界球・個体別の段状態・可視選択の並べ替え作業域・ドライバー側の確保であり、いずれも入場制御が数えていない物量比例の常駐ホスト構造である。棚卸しと算入の判断は札#138へ起票した(参照: `_doc/計測/OW4_2026-07-29.md`「追記: RAM会計の記述の訂正」)。VRAM側は台帳の125.01MiBに対して専用VRAMの実測が213.62MiBだが、差の88.6MiBは10,026個体での差88.3MiBとほぼ同じであり、台帳の追跡対象外の量は物量で増えていない。

### 3.6 CPU区間予算(2026-07-29制定、暫定)

3.1がGPUパスへのフレーム時間の配分を扱い3.5が容量の上限を扱うのに対し、この節はメインスレッドのCPU区間が1フレームで占めてよい時間の上限を扱う。区間の切り方は `_doc/設計/植生インスタンスと物量計測.md`「CPU区間の切り方」の3区間に従う。

| CPU区間 | 予算(2026-07-29時点の暫定値) | 位置づけ |
|---|---|---|
| 群選択(群と個体の可視判定・個体別LODの段選択・可視ID列の並べ替えを1回に融合した走査) | 2.0ms | 暫定。約10ns/個体の実測に対して常駐200,000個体に相当する |

**この値は暫定であり、実運用の値ではない。**根拠は2つある。1つはOW4の実測であり、群選択の個体あたり費用は9.55〜10.25ns(シャドウのライト視錐台判定を足した第6段の後は11.14〜11.62ns)の帯に収まって物量で悪化しない。この単価のもとで2.0msは常駐約200,000個体にあたる。もう1つは他の予算との釣り合いであり、群選択はシーンの主描画そのものではなくそれに従属する区間であるから、主描画の4.0msではなくシャドウGPUと同じ2.0msの枠へそろえた。

この予算に対し、1,000,026個体での実測10.0174ms(第6段の後は11.3722ms)は5.0倍(5.7倍)の超過である。**したがってこの予算は、現在の単一スレッド走査で常駐させてよい個体数の上限を規定する予算として機能する。**同じ物量点では群選択だけで16.6msフレームの60.3%(第6段の後は68.5%)を1区間が占め、フェンス待機のp50が0.0075msへ落ちて律速がFIFO提示待ちからCPUの処理量へ移る。

**見直し条件**: OW5、または実運用の視界距離と常駐個体数が制定された時点で、この暫定値を実データで置き換える。それまでの200,000個体という含意は、検証用世界の密度と実測単価から逆算した値にすぎない。

## 4. 変更容易性(作り続けられるか)

エンジンは完成品ではなく継続開発される資産のため、変更のしやすさ自体を評価対象にする。

- **開発ループ速度**は、差分ビルド時間と、シェーダー・アセットのホットリロード反映時間で測る。目安は check 数秒・ホットリロード1秒未満である(`_doc/設計/開発ループとコンパイル時間.md` の段階定義に対応)。
- **AI駆動開発への適合**(このプロジェクト固有の軸)は、自律ループにおける検収指摘数の推移で測る。実績はM0で3件、M1で1件、M2で1件、M3で0件、M4で軽微1件である。増加に転じたら、コードではなく規約・分割粒度・機械検証の側の欠陥を疑って直す。
- **依存の隔離の健全度**(外販可能性・移植可能性の裏付け)は、公開APIへのash型の露出ゼロ、blitz_engine のash・winit非依存、外部依存クレート総数の推移で測る。層ごとの直接依存は `cargo xtask conform` の白リストで機械検査し、推移的依存は `cargo tree --workspace --edges normal` で確認する。2026-07-23時点のWindows向け通常依存グラフは85パッケージ版（自前7、外部78）である。
- **信頼性**は、長時間実行でのメモリ・VRAMリークの有無と、デバイスロスト時の型付きエラー伝播で測る。長時間実行の計測はM11で行う。
- M11の3600フレーム連続実行では、初期安定化後のワーキングセット、プライベートメモリ、専用VRAMは横ばいで、フレーム数に比例する増加を検出しなかった。`cargo xtask m11-soak`で同じテキスト計測を再実行できる。

## 判断フロー(いつ・何を判断するか)

1. **毎イテレーション**(自律ループ): 完了定義の充足 + validation + smoke + conform(現行の検証列)。M5以降はパス別GPU時間の確認を追加。
2. **マイルストーン完了時**: 予算表の消費率を更新する。超過があれば最適化タスクとして札に登録する。能力の出自分類で (c) が現れたら開発計画の改訂として扱い、非ゴールの変更に当たる場合はユーザーへ相談する。
3. **M11(エンジンフェーズ1完了検証)**: 4系統の総点検(代表シーンテスト・ベンチマーク総括・物量スケーリング計測・変更容易性の各指標)をレポートにまとめ、フェーズ2詳細計画の入力にする。
4. **対象ゲーム決定後**: 代表シーンを実仕様のシーンへ差し替え、予算表を実データで再配分する。

## 行わないこと

- 他エンジン(Unity・Unreal・Bevy)との相対ベンチマークはフェーズ1では行わない。等価なシーンを両側で用意するコストが高く、理論性能との比較(3.2)の方が同じ労力で得られる情報が多いため。外販の営業材料として必要になった時点で計画する。
- 合成的なマイクロベンチマーク(三角形数百万個の単純描画など)は、代表シーンテストの代替にしない。
