# 評価軸

エンジンを「どう評価するか」の判断軸・判断方法・判断フローの定義（生存型文書。
実装・計画と常に一致させる）。経緯は開発スレッド2026-07-20参照。

評価は4系統に分かれる。品質系は機械化済みで、他3系統をこの文書で制度化する。

## 1. 能力（何ができるか・意義・できないことの重大さ）

能力は絶対的な機能リストでなく**対象ゲーム像（原神型オープンワールドRPG）への距離**で測る。

- **判断方法: 代表シーンテスト**。対象ゲームの典型1シーンを要素分解し
  （フィールド地形・植生・キャラクター＋衣装物理・空と時間帯・戦闘エフェクト・UI・
  ストリーミング・オーディオ）、各要素を今日のエンジンで実行できるかを判定する
- **重大さの判定: 逆引きギャップ表**。各欠落能力に出自を張る:
  (a) 背骨マイルストーン（M0〜M11）にあり → 予定通り
  (b) 長期フェーズ計画にあり → 意図した棚上げ（無計画な欠落ではない）
  (c) どこにも無い → **これだけが真の欠落**。発見したら開発計画の改訂として扱う
- **意義の判定**: その能力が差別化の芯（キャラクターシミュレーション・理論値性能・
  AI駆動開発適性）に属するか、汎用エンジンでも無料で得られるものかを区別する。
  芯に属さない能力の先行実装は疑う
- 現状の逆引き結果（2026-07-20時点）: 代表シーン要素はすべて (a) または (b) に
  張り付いており、(c) は検出されていない。M11 で総点検する

## 2. 品質（正しく動くか）— 機械化済み

- validation layer（同期検証込み）エラーゼロ / `cargo xtask smoke` のピクセル判定 /
  検収5軸（設計遵守・規約遵守・孤立impl・検証実行・diff目視）
- 参照: 開発計画「自律ループの運用規約」。この文書では扱わない

## 3. 性能（理論値志向にどれだけ近いか）

「速いか?」は単体では判断不能。比較先を3つ持つ。

### 3.1 フレーム予算比（日常の計器）

60fps = 16.6ms をパス群に配分した予算表に対する消費率で判断する。
計器は M5 のパス別GPU時間計測 + 開発用UI。

初期予算表（フェーズ1の背骨向け。パス追加時にこの表を改訂する）:

| パス | 予算 |
|---|---|
| シーン描画（PBR） | 4.0ms |
| シャドウ（M6） | 2.0ms |
| ポストプロセス（M7） | 1.5ms |
| シミュレーション（M9、コンピュート） | 3.0ms |
| UI・その他 | 1.0ms |
| 予備（フェーズ2の地形・植生・ストリーミング用に温存） | 5.1ms |

- 判定: 消費率50%未満=順調 / 50〜100%=注視（物量スケーリングを確認）/
  超過=最適化タスクを札に登録（**計測に基づくものだけ。推測最適化は禁止**）

### 3.2 理論値比（本丸だが高コスト。予算超過パスに絞って適用）

- パスの支配資源（帯域・ピクセルレート・三角形レート・ALU）を特定し、
  GPU仕様値から導いた理論下限時間との乖離倍率を出す
- 乖離が説明できない（>数倍）とき初めて最適化に着手する。手法はGPUプロファイラ
  （Nsight等）による支配資源の実測 → ボトルネックの構造対処

### 3.3 物量スケーリング（オープンワールドの賭けの検証）

- 同一シーンの物量（インスタンス数・頂点数・テクスチャ量）を1x/10x/100xで振り、
  所要時間の伸び方（線形か・どこで折れるか）を記録する
- 折れ点の原因（描画コール数・帯域・CPU律速）がフェーズ2の投資先
  （バインドレス・GPU駆動カリング）の根拠データになる

### 3.4 計測の再現性（資産化）

- ベンチは**固定シーン + 固定カメラパス + 固定フレーム数**で行い、`cargo xtask bench`
  として登録する（M5波2で整備。スモークと同じ思想: 繰り返す検証は資産化）
- 結果はログ型で `_doc/計測/` に追記し、推移を見る。CPU側はフレーム時間分布
  （p50/p99、ヒッチ検出）を併記（M11のDoDに接続）

## 4. 進化容易性（作り続けられるか）

エンジンは完成品でなく継続開発される資産のため、変更のしやすさ自体を評価する。

- **開発ループ速度**: 差分ビルド時間 / シェーダー・アセットのホットリロード反映時間。
  目安: check数秒・ホットリロード1秒未満（開発ループ設計文書のTier定義に対応）
- **AI駆動開発適性**（本プロジェクト固有の軸）: 自律ループの検収指摘数の推移で測る。
  実績: M0=3件 → M1=1件 → M2=1件 → M3=0件 → M4=軽微1件。増加へ転じたら
  規約・分割粒度・機械検証の欠陥を疑い、ハーネス側を直す
- **封じ込めの健全度**（外販可能性・移植可能性の担保）: 公開APIへのash型露出ゼロ
  （grep検査）/ blitz_engine のash・winit非依存（Cargo.tomlで機械強制）/
  外部依存クレート総数の推移（README採用表と cargo tree の一致）
- **信頼性**: 長時間実行でのメモリ・VRAMリーク、デバイスロスト時の型付きエラー伝播。
  M11で長時間実行計測を行う

## 判断フロー（いつ・誰が・何を判断するか）

1. **毎イテレーション**（自律ループ）: DoD + validation + smoke（現行）。
   M5以降はパス別GPU時間の目視を追加
2. **マイルストーン完了時**: 予算表の消費率を更新し、超過は最適化タスクとして
   札#138系へ登録。能力ギャップ表に (c) が現れたら開発計画の改訂として扱い、
   非ゴール変更に当たる場合はユーザーへエスカレーション
3. **M11（フェーズ1完了検証）**: 4系統の総点検 — 代表シーンテスト・ベンチ総括・
   スケーリング計測・進化容易性指標 — をレポートにまとめ、フェーズ2詳細計画の入力にする
4. **対象ゲーム決定後**: 代表シーンを実仕様のシーンへ差し替え、予算表を実データで再配分する

## 非目標

- 他エンジン（Unity/Unreal/Bevy）との相対ベンチはフェーズ1では行わない
  （比較シーンの等価性担保が高コストで、理論値比の方が情報量が多い）。
  外販の営業材料として必要になった時点で計画する
- 合成マイクロベンチ（三角形数百万個の裸描画等）は代表シーンテストを代替しない
