# 命名規範(日本語識別子の受理条件)

日本語で書く識別子(型名・メソッド名・フィールド名・変数名)が満たすべき受理条件の正本である。CLAUDE.mdの「命名」「日本語命名の質」の細則であり(2026-08-09制定)、矛盾する既存条文は本規範を優先して、CLAUDE.md側を追って改訂する(改訂までの間も本規範が勝つ)。語の登録台帳は`_doc/計画/ユビキタス言語.md`である。

## この規範が作られた経緯(クレームの記録)

2026-08-09、オーナーが既存の命名を不合格と裁定した。規範の各条文はこのクレームへの対処であり、条文だけ読んで意図が取れないときはここへ戻る。

1. **`記録`(レンダーグラフのパスのフィールド)**: 実体はコールバック(処理)なのに名詞形で、「記録されたもの(データ)」と誤読される。さらに「記録」の語自体が日常語の「ログを残す」に読まれ、実際の動作(VulkanのコマンドバッファへGPU命令を積む)がまったく伝わらなかった。オーナーは他のAIに尋ねてはじめて意味を知った
2. **`記録文脈`**: 「ログを残すための文脈」と誤読された。実体はGPU命令の積み先(コマンドバッファ)と、宣言済み資源からVulkanの実物を取り出す口の束である
3. **`生成する()` / `作成する()`(staticなファクトリー関数)**: 何を作るのかが名前に無い。オーナーの裁定: 「crate名やファイル名が英語なのは別の理由があるからそれ自体は問題視しないが、**英語名は読まない。それと一緒に読まれることを前提にするな**」。クレームの対象はコンストラクタ(日本語の型名とセットで読まれ、型名が目的語を担うもの)ではなく、英語(ASCII)の文脈しか持たない位置に置かれたファクトリー関数の側である(例: `create.rs`のモジュール直下の自由関数`生成する()`。呼び出しは`create::生成する(...)`となり、補完に使えるのは読まれない英語名だけになる)
4. **総括のクレーム**: 名前が対象を一意に識別できていない。「これは何?」と聞かれたときに答えるものをそのまま名前に書くべきである。「**5W1Hは意識してほしい。でないと(規範を受け取る側への)指示が抽象的すぎて全く伝わらない**」——この経緯節自体が、そのクレーム(どういうクレームがあってこの規約が作成されたのかを明記しろ)への対処である
5. **長さについて**: 「長くなるのが問題」とは誰も言っていない。規範の起草中に親(AI)が短さとの妥協点をオーナーへ聞こうとして「誰が問題視したの?」と正された。条件8はこの経緯の固定である

根因の診断: AIの既定の命名は英語圏の慣習(役割の抽象名詞・短さ優先・レシーバ型による目的語の補完)の引き写しであり、それを日本語へ写すと、日本語で意味を担っている格助詞と項(何を・どこへ)が削られる。**日本語では助詞と項を削ることが意味を削ることである。**

## 受理条件

新しい名前はこの順で判定する。1つでも落ちたら不合格である。

1. **受理テスト**: その名前は「これは何?」と聞かれたときの答えとして**単独で**成立するか。「記録です」は答えになっていない(何の?されたもの?する処理?)。「GPU命令をコマンドバッファへ積む処理です」は答えになっている。動詞句の名前は「(それは)〜する処理です」への答えとして成立すればよい
2. **補完してよい文脈の限定**: 名前の意味の補完を前提にしてよいのは、読み手が実際に一緒に読む**日本語の識別子**だけである(呼び出しに現れる日本語の型名=`型名::関連関数()`の形、日本語のレシーバ変数=`変数.メソッド()`の形)。**ASCII識別子(crate名・モジュール名・ファイル名)は読まれないものとして扱い、それによる補完を前提にしない。** したがってASCIIモジュール直下の自由関数は、名前単独で条件1に答えなければならない
3. **5W1Hの必要格**: 動作の名前は、5W1H(誰が・何を・いつ・どこで/どこへ・なぜ・どうやって)のうち**一意識別に必要な格をすべて**名前自身に含める。一意識別の範囲はリポジトリ全体(ユビキタス言語の語彙空間)である。最低は「何を+どうする」であり、それで紛れるなら着点・材料・時点を足す。全格の機械的な列挙は求めない(不要な格は判定の雑音になる)。「紛れるか」の決着はユビキタス言語との照合で行う(登録済みの語・句と衝突しなければ一意とみなす)
   - 合格例: `視点を求める`(「誰の視点?」が無くても、このリポジトリで他の視点と紛れない)
   - 不合格例: `命令を積む`(何の命令? どこへ? が紛れる)→ `GPU命令をコマンドバッファへ積む`
4. **品詞の規律**: 品詞が実体を予告する。値=名詞句。処理(関数・メソッド)=動詞句「〜する」。処理を保持するフィールド=動詞句のまま(呼び出しが「(パス.GPU命令をコマンドバッファへ積む)(道具)」と読める)。真偽値・述語=「〜か」
5. **裸の動詞の禁止(日本語の補完が働かない位置)**: 条件2で補完が働かない位置(ASCIIモジュール直下の自由関数等)では、`生成する` `作成する` `実行する` `更新する`等の裸の動詞を名前にしない。目的語か材料を含める(`共有資源を確保する` / `画素から生成する`)。**型に属する関連関数の`生成する()`は、日本語の型名が目的語を担って「型名を生成する」と読めるため合格であり、値オブジェクト様式(private+static `生成する()`)はそのまま維持する。**同じ型に複数のファクトリー関数があるときは材料・条件の格で区別する(既存の良い例: `記録なしで生成する` `画素から生成する`)
6. **1語1義**: 判定の単位はユビキタス言語の登録句であり、1つの登録句はプロジェクト内で1つの意味だけを持つ(「積む」のような一般動詞が別の句に現れることは衝突ではない。「記録」のように語そのものが2つの意味で使われるのが衝突である)。衝突したら具体側が改名する。実例: 「記録」が計器の意味(太陽天頂区間の記録=数えて残す)とVulkanの意味(コマンド積み込み)で衝突していた
7. **直訳の検出質問**: 英語の対応語を知らない人が、この名前だけから動作・実体を復元できるか。復元できなければ実際の動作の日本語へ言い換える。過去の失敗例: record→記録、context→文脈、resolve→解決、lookup→引く。カタカナ専門語(コマンドバッファ等)の可否はCLAUDE.md「日本語命名の質」の基準(非専門家が読めるか+ユビキタス言語への登録)に従う
8. **長さは結果であって制約ではない**: 短さのために格・助詞を削るのは条件1〜7への違反である。長い名前は欠点ではない(この項が要るのは、AIが英語圏の短さ優先を無意識に持ち込むためである)

## クレーム対象の対訳(是正の見本)

| 旧 | 何が欠けていたか | 新 |
|---|---|---|
| `記録`(フィールド) | 品詞の偽装(処理なのに名詞)・目的語・着点・多義 | `GPU命令をコマンドバッファへ積む` |
| `記録文脈`(型) | 目的語・着点・「文脈」がcontextの直訳 | `GPU命令の積み先と宣言済み資源の取り出し口`(「解決」はresolveの直訳なので使わない) |
| `create::生成する()`(ASCIIモジュール直下の自由関数) | 目的語(補完できるのは英語の`create`だけ) | `共有資源を確保する`等、作る対象を名前へ |

## 運用

- 新規の命名はすべて本規範で書く。サブエージェントへの委譲プロンプトには本規範のパスを必読として渡す
- 既存違反は、その領域を触る実装のついでに是正する(リネームは機能変更と別コミット。CLAUDE.md「日本語命名の質」の運用と同じ)
- 本規範の制定を受けた一括の棚卸し(リネームタスク)は別途起票して段階実施する。起点はクレームの発生したレンダーグラフ層である。リネームでは設計正本・ユビキタス言語に現れる同じ名前も同時に動かす
- 条件5のうち機械検査できる形(ASCIIモジュール直下の自由関数の裸の動詞)は、棚卸しの実施時に`cargo xtask conform`への検査追加を審査する(機械検査可能な負債は常時強制、の方針に従う)
- ユビキタス言語へ新語を登録するときは、受理条件1〜7を通してから登録する
