# 裁定待ちユビキタス言語

裁定待ちユビキタス言語とは、実装の途中でAIが新しく作り、オーナーの裁定をまだ受けていない語のことである。

実装員は、既存の語では表せない概念に出会ったとき、その場で名前を決めてよい。ただし決めた名前は案であり、合意済みの語彙ではない。このファイルはその案を置く場所である。

`_doc/計画/ユビキタス言語.md` は、対話で合意した語彙を記録する正本である。親と実装員は、裁定を受けていない語をそちらへ書いてはならない。
グローバルCLAUDE.md「専門用語の表記」が求める「定義なしで新語を使い始めるのは禁止」は、このファイルへの登録で満たす。

手順の全文はプロジェクトのCLAUDE.md「新しいドメイン概念と語彙の導入」にある。

## 書き方

1件につき次の5つを書く。語を見出しにし、残りの4つを箇条書きにする。

- **区切られたドメイン**: 共通・描画・物理・ゲーム実行・ECS・資産ストリーミング・エディター・開発基盤のどれか。1語1義はこの範囲の中で成り立つ規律であり、区切られたドメインが違えば同じ表記が別の語でありうる。詳細はCLAUDE.md「区切られたドメイン」にある
- **暫定の定義**: 「Xとは〜のことである」の形で書く
- **使っている場所**: その語を識別子または文書で使っているファイルのパス
- **既存語で表せないと考えた理由**: どの既存語を検討し、なぜ足りないと判断したか

裁定が済んだら、親はこの節から項目を消す。親は、採用ならユビキタス言語へ定義を移し、必要なリネームを別のコミットで行う。親は、却下なら既存語へ戻すか、概念そのものを畳む。

## 裁定待ちの語(2026-09-20時点で8件。PR #138 の実装員と親が作った語)

### 設計マーカー

- **区切られたドメイン**: 共通
- **暫定の定義**: 設計マーカーとは、Rust上の型が設計上何として解釈されるか(純粋な所有データ・状態・コマンド・イベント・規則・入力・設定・工程)を、メソッドを持たないトレイトの実装で宣言する印のことである。正本は依存ゼロの共通設計語彙クレート`crates/blitz_design`であり、`blitz_sim`と`blitz_esca`がこれを使う。データの役割(`M状態`・`Mコマンド`・`Mイベント`・`M規則`・`M入力`・`M設定`)はすべて`M不変データ`を上位トレイトに持つ(2026-09-19 PR #138 第4回レビュー対応)。マーカーが課す法則のうち上位トレイトで書けるもの(`M不変データ`の`Clone`、データの役割の`M不変データ`実装)と関数の役割の型引数の境界(関数の役割は境界付きのnewtypeであり、型を使った時点でコンパイラが強制する。迂回できる書き方は無い)はコンパイラが強制し、残り(`M不変データ`または役割を実装する型の定義に参照・内部可変性が無いこと(`Mコマンド: M不変データ`等のsupertraitの関係はコンパイラが保証し、conformは役割の実装から型の定義をたどってその定義に純粋データ規約を当てる。`impl M不変データ for`の置き場所は法則にしない)、`Mコマンド`が列挙で`M規則`が構造体であること、`M不変データ`を実装する型(データの役割を実装する型をすべて含む)の固有の`impl`に`&mut self`が無いこと)は`cargo xtask conform`の設計オントロジーの検査が見る。`M規則`の「不変」とは、1回の遷移の評価のあいだ読み取り専用の入力であることであり、プログラムの全期間で同じ値であることは意味しない(速度の強化や難易度の変更で規則の値が変わることを妨げない)。正本の表は`_doc/設計/設計オントロジー.md`第2節。基底のマーカーの名前は 2026-09-20 のオーナー裁定で `MDTO` から `M不変データ` に決まった(裁定待ちなのは「設計マーカー」という語そのものである)
- **使っている場所**: `crates/blitz_design/src/marker.rs`(定義)・`crates/blitz_esca/src/*.rs`・`crates/blitz_sim/src/contact/non_penetration/substep_state.rs`・`crates/blitz_sim/src/contact/static_friction/substep_state.rs`・`crates/blitz_sim/src/rigid_xpbd/reference/substep_body.rs`・`xtask/src/conform/design_ontology.rs`・`_doc/設計/設計オントロジー.md`・`_doc/設計/Esca/設計正本.md`・`README.md`
- **既存語で表せないと考えた理由**: 「トレイト」「役割」を検討した。トレイトは Rust の機構の名前であり、メソッドを持たず設計上の解釈だけを宣言するという用途を言い当てない。役割は宣言される中身(状態・コマンド等)の側の語であり、宣言する印そのものを指す語が無かった

### 遷移結果

- **区切られたドメイン**: 共通
- **暫定の定義**: 遷移結果とは、遷移関数が返す、次の状態と、その遷移で生じた出来事の一覧の名前付きの組のことである。生のタプルで2つの値を返さないために置く。型引数で状態とイベントの型を受け(`M状態`・`Mイベント`の境界を持つ)、`M遷移関数`の戻り値`Result<遷移結果, 失敗>`の成功側がこれである(遷移は数値の表現範囲を超えたときなどに失敗しうる。2026-09-20 PR #138 第5回レビュー対応)
- **使っている場所**: `crates/blitz_esca/src/ontology.rs`(定義)・`crates/blitz_esca/src/traveler_movement.rs`・`crates/blitz_esca/src/tests/*.rs`・`_doc/設計/設計オントロジー.md`・`_doc/設計/Esca/設計正本.md`
- **既存語で表せないと考えた理由**: 「次の状態」「出来事一覧」を検討した。遷移関数が返すのはその2つの組であり、生のタプルで返さないための名前付きの型が要った。組そのものを指す既存語が無かった

### 歩行方向

- **区切られたドメイン**: ゲーム実行
- **暫定の定義**: 歩行方向とは、旅行者が歩く向きを表す、東の比率と北の比率の二乗和が1である値オブジェクトのことである。生成の口はキーボード歩行入力からの導出`キー入力から導く`だけであり、相反するキーが相殺して零になれば向きは無い(`None`)。斜めの入力は長さを1へ正規化する。同型の`f32`を2つ並べる生成の口を置かないのは、東と北を取り違えても型が通るためである
- **使っている場所**: `crates/blitz_esca/src/walking_direction.rs`(定義)・`crates/blitz_esca/src/traveler.rs`・`crates/blitz_esca/src/traveler_movement.rs`・`crates/blitz_esca/src/tests/walking_direction_tests.rs`・`_doc/設計/Esca/設計正本.md` 4.4
- **既存語で表せないと考えた理由**: 「方向」「向き」を検討した。長さが1であることを不変条件に持ち、生成の口をキーボードの入力からの導出だけに限る値オブジェクトであることを、裸の方向では言えなかった

### 移動可能範囲の指定

- **区切られたドメイン**: ゲーム実行
- **暫定の定義**: 移動可能範囲の指定とは、移動可能範囲を作るための、東の最小・最大と北の最小・最大を公開フィールドで持つ指定のことである。`検証する()`が各軸の最小が最大以下であることと端が数値であることを確かめ、通れば移動可能範囲になり、破れは`移動可能範囲の生成の失敗`(最小が最大を超えている軸と値、数値でない軸)で返る。移動可能範囲そのものはフィールドを私有にし、この検証を通らずには作れない
- **使っている場所**: `crates/blitz_esca/src/traveler_boundary.rs`(定義)・`crates/blitz_esca/src/tests/traveler_boundary_tests.rs`・`_doc/設計/Esca/設計正本.md` 4.2・4.4
- **既存語で表せないと考えた理由**: 「移動可能範囲」を検討した。移動可能範囲は検証済みの値であり、検証の前の公開フィールドの入力とは別の型である。検証の前後を同じ語で呼ぶと、検証を通らずに作れないという不変条件が名前から読めなかった

### 経過時間

- **区切られたドメイン**: ゲーム実行
- **暫定の定義**: 経過時間とは、遷移関数へ渡す、有限かつ0以上の時間のことである。`blitz_math::秒`を`経過時間::生成する`で検証して包んだ値オブジェクトであり、負・NaN・無限大は`経過時間の生成の失敗`で拒む。遷移関数が負の時間で逆向きに動いたり、数値でない時間で現在地を汚したりしないために置く。Esca第1段階の遷移文脈である
- **使っている場所**: `crates/blitz_esca/src/elapsed_time.rs`(定義)・`crates/blitz_esca/src/ontology.rs`・`crates/blitz_esca/src/traveler_movement.rs`・`crates/blitz_esca/src/tests/elapsed_time_tests.rs`・`_doc/設計/設計オントロジー.md` 3.5.1・4.5・`_doc/設計/Esca/設計正本.md` 4.1・4.4
- **既存語で表せないと考えた理由**: 「秒」「刻み幅」を検討した。`blitz_math::秒` は符号も有限性も持たない生の量であり、遷移に渡してよい(有限かつ0以上)ことを型で言う語が要った。刻み幅は固定刻みの語であり、可変の経過を指さない

### 旅行者の現在地の生成の失敗

- **区切られたドメイン**: ゲーム実行
- **暫定の定義**: 旅行者の現在地の生成の失敗とは、旅行者の現在地の東または北が有限な数値でない(NaN・無限大)ときに`旅行者の現在地::生成する`が返す失敗のことである。NaN は比較がすべて偽になり移動可能範囲の制限で捕まらないため、生成の口で閉じる
- **使っている場所**: `crates/blitz_esca/src/traveler_error.rs`(定義)・`crates/blitz_esca/src/traveler.rs`・`crates/blitz_esca/src/traveler_movement.rs`・`crates/blitz_esca/src/tests/traveler_invariant_tests.rs`・`_doc/設計/設計オントロジー.md` 3.5.9・`_doc/設計/Esca/設計正本.md` 4.1・4.4
- **既存語で表せないと考えた理由**: 既存の失敗の型の名前の様式(`移動可能範囲の生成の失敗`・`歩行の規則の生成の失敗`)に揃えた。現在地の座標が有限でないことを表す型付きエラーを指す語が無かった

### 遷移の失敗

- **区切られたドメイン**: 共通
- **暫定の定義**: 遷移の失敗とは、与えられた状態・コマンド・規則・遷移文脈から、有効な次の状態を構築できなかったことである。遷移の評価は成功(遷移結果)と失敗の2つの選択肢を持つ。失敗のとき次の状態は採用されず(呼び出し側は元の状態を維持する)、出来事は1件も生じない。「遷移に失敗した」は`Mイベント`ではない。法則E1からE8は成功した遷移だけを対象とする。Esca第1段階では`旅行者の現在地の生成の失敗`がこれである。正本は `_doc/設計/設計オントロジー.md` 3.5.9
- **使っている場所**: `_doc/設計/設計オントロジー.md` 3.5.1・3.5.9・4.5・`_doc/設計/Esca/設計正本.md` 4.1(`M遷移関数`の戻り値`Result<遷移結果, 失敗>`の失敗側)・`crates/blitz_esca/src/ontology.rs`(`M遷移関数`の型引数`失敗`)
- **既存語で表せないと考えた理由**: オーナーの第6回レビューが「遷移の失敗時の意味を決める必要がある」と述べたことを受けて、親が概念を定義して名付けた語である。オーナーが裁定したのは意味を決める必要があることまでであり、「遷移の失敗」という語そのものの裁定は受けていない。「エラー」「失敗」を検討したが、遷移の評価の成功と対になる側であることと、`Mイベント`ではないことを言うには、遷移に限定した語が要った

### 遷移文脈

- **区切られたドメイン**: 共通
- **暫定の定義**: 遷移文脈とは、状態でもコマンドでも規則でもない、遷移を成立させる追加の入力(経過時間・乱数源から確定した値・世界時刻・刻みの情報など)のことである。遷移の一般形は「状態 × コマンド × 規則 × 遷移文脈 → 遷移結果」であり、Esca第1段階では遷移文脈 = 経過時間である。一般形が未確定であることが、`M遷移関数`を`blitz_design`へ上げない理由の1つである。正本は `_doc/設計/設計オントロジー.md` 3.5.1
- **使っている場所**: `_doc/設計/設計オントロジー.md` 3.5.1・3.5.9・4.5・`crates/blitz_esca/src/ontology.rs`(モジュールの説明)・`_doc/計画/裁定待ちユビキタス言語.md`「経過時間」
- **既存語で表せないと考えた理由**: (a) オーナーが第4回レビューで「遷移を成立させる追加の文脈/入力」と書いた語を、親がそのまま採った。(b) ただし `_doc/計画/非推奨語.csv` の共通の行に「文脈」が `context` の直訳として非推奨で登録されており(その語が正しくなる場面は「無し」)、この語はその裁定と衝突する。代案として「遷移の追加入力」を挙げる。「遷移文脈」と「遷移の追加入力」のどちらを採るかの裁定を求める
