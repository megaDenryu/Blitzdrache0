# Blitzdrache0 開発計画

自律ループ実行（AIが単独で判断しながら開発を進める運用）の拠り所となる計画書。
各セッション・各イテレーションの冒頭でこのファイルを読み、現在地と次のタスクを特定する。

語彙は `ユビキタス言語.md` の定義に従う。
本計画に新しい概念語が現れたら、先にユビキタス言語へ定義を追加してから使う。

## プロダクトビジョン（2026-07-20 壁打ちで確定した部分）

- **最終成果物**: まず商業ゲーム。基盤（エンジン + エディタ）の外販は二段目として視野に入れる。帰結: 特化最適化を優先しつつ、モジュール境界の清潔さと文書化を外販可能性の担保として維持する
- **対象ゲーム像**: フルコースのオープンワールドRPG（原神が確立した水準）。
  賭けの構造: アセット物量という従来の参入障壁をAIによる量産で突破できるはずであり、その物量を受け止められる基盤（取り込み・検証・予算管理のパイプラインと、物量を描き切る性能）を先に整えておく。
  ゲームシステム（進行・ガチャ等）はただのプログラムであり後からどうとでもなる部分と位置づける。
  解決すべきボトルネックはアートとパフォーマンスの2つ
- **エディタ**: 作ることは確定（経営判断済み。需要検証は不要）。操作者はAIと人間の両対応。設計方針は操作コマンド層を核とし、AIもGUI（人間用の薄い皮）も同一のコマンドを発行する。undo/redo・操作ログ再生も同じ仕組みから導く。詳細仕様の策定はエディタフェーズ
- **絵の方向性**: 未決定（白紙）。分岐が効くのは主にエンジン側（マテリアルモデル・ライティング・輪郭線・AA戦略）で、エディタへの影響はエンジンのマテリアル語彙を映すだけの従属的なもの。**リアル調を先行させ、トゥーン調は後から追加する方針を採用する**。成立条件は次の3つの扉を閉めないこと:
  (1) マテリアルは判別共用体で設計し単一シェーディングモデルを型に焼き付けない
  (2) 様式決定までTAAを採用しない（AAはMSAAか無し）
  (3) 当面forward系で進めdeferredのG-bufferレイアウトを確定させない。
  この運用下では絵の最終決定はゲーム内容の壁打ちが熟すまで遅延できる。M3完了時に「3つの扉が開いたままか」を確認する。分岐の詳細は開発スレッド2026-07-20参照。
  対象ゲーム像（原神型）の確定により**有力仮説はアニメ調（セル）キャラ + 様式化された世界**に更新された。原神型はまさにPBR基盤の上にセル表現を載せる構成のため、リアル調基盤を先行させる方針はこの仮説とも整合する。最終確定は変わらずM3までに行う
- **大座標の扉（オープンワールド固有の第4の扉）**: f32の精度は原点から数kmで崩れるため、オープンワールドはカメラ相対レンダリング（描画時にカメラ原点へ座標を移す）が必須になる。今から閉めないでおく: ワールド座標の型とGPUへ渡す座標の型を最初から区別し、「ワールド座標をそのままシェーダーへ送る」設計を固定しない
- **VRの扉（第5の扉）**: VR対応はロードマップ上の能力であり、残る問いは実装時期の優先順位だけ（判断ゲートは2026-07-20の「可能性を閉じない」原則制定で廃止）。
  VR対応は (1) 視点数を1とハードコードしない（マルチビュー前提の型設計。レンダーグラフの各パスが視点数を引数に取る）(2) 入力インテント抽象化（ゲームロジックはインテントのみ消費、デバイス→インテント写像は入力層に隔離）(3) UIをワールド空間に置ける前提で設計する、の3点を守れば開いたままになる。
  なお既決定の forward系・MSAA・TAA保留・ループ所有権A→B移行路はすべてVR適合（VRのペーシングはOpenXRの xrWaitFrame が支配し、late-latchが標準技法のため）。
  至近距離検分への耐性はアセット取り込みパイプラインの検証項目（テクセル密度・近接ジオメトリ品質の予算）として扱う。
  昇格が確定したらOpenXR統合をエンジンフェーズ2の柱に加え、マイルストーンを改訂する
- **現在の主題**: 経営者（ユーザー）が「仕様を切れ」と言えば開発者（AI）が仕様を切れる水準まで、プロジェクトの方向性を壁打ちで詰めること

## ゴール

**最終ゴール**: デバイスの理論値性能を志向する自作ゲームエンジン。
構造は2段構え: **汎用かつ最高性能の基盤層**（blitz_render、シミュレーション基盤層等。手法の数学とGPU実行だけを持ち、特定の絵やゲームを知らない）と、**ドメインを達成する特別な仕組みの層**（キャラクターシミュレーションの表現群等）。
「特化」とは投資の優先順位と上位ドメイン層の話であり、基盤を狭めることではない。
汎用性の税金の正体は「使わない機能の実行時・保守時コストと互換性の足枷」であって能力を持つこと自体ではなく、クレート分離により「能力は持つが、使わないゲームは1バイトも払わない」を成立させる。

**エンジンフェーズ1の到達点（M0〜M11、本計画の背骨）**: glTFで読み込んだシーンをPBR + シャドウ + HDRポストプロセスで描画し、アニメーション付きキャラクターが動き、XPBD布のMVPと介入モデルが実証され、流体の実現可能性スパイクが完了し、GPU計測基盤で性能を定量把握できる「素のエンジン」。
Windows + Vulkan。
60fps（FIFO同期）で安定動作。

**その先（本計画のスコープ外）**: 対象ゲームの決定 → ゲーム特化の最適化（バインドレス、GPU駆動描画、非同期コンピュート）→ 必要になった時点でのRHI切り出し。
対象ゲームの決定はユーザーの仕様判断であり、AIが勝手に決めない。

## 非ゴール（エンジンフェーズ中は作らないもの）

作りたくなっても作らない。
ただし各項目の長期ゴールは「長期フェーズ計画」節で先に定義してあり、無計画な棚上げではない。
着手条件が満たされた時点で計画を改訂してから作る。

- エディタ（AI駆動開発ではエディタは強みにならないという本プロジェクトの前提）
- RHI / マルチグラフィックスAPI抽象層（コンソール対応が現実になるまで）
- 汎用シーングラフ・汎用ECS（対象ゲーム決定前の汎用化は負債）
- シェーダーグラフ（シェーダーはSlangを直接書く）
- 剛体物理・オーディオ・ネットワーク（ゲームフェーズで必要になってから。注意: キャラクターシミュレーションは非ゴールではなくエンジン中核。下記参照）
- スクリプト言語組み込み（ゲームロジックはRustで書く）

## 全体アーキテクチャ（確定事項）

```
ゲームロジック（安全なRust、将来 blitz_game として分離）
   ↓
blitz_engine: シーン・アセット・マテリアル（安全なRust、#![forbid(unsafe_code)]）
   ↓
blitz_render: レンダーグラフ + リソースシステム（エンジン中核の型安全層）
   ↓
ash（unsafe は blitz_render 実装内部に封じ込め。公開APIに ash 型を露出しない）
```

- 依存方向はCargoワークスペースのクレート分割でコンパイル時強制
- コンポジションルートは blitz_app。フレーム内の実行順序はここが一元支配（入力確定 → 世界更新 → 描画内容抽出 → 描画）
- イベントループはwinit所有パターンA（`参照: _doc/設計/イベントループとフレームペーシング.md`）
- シェーダー言語はSlang。SPIR-Vへコンパイルして使う
- 安全化の方針: 汎用のVulkanラッパーは作らない。「このエンジンの使い方」だけを露出する狭い型で安全性を担保し、実行時追跡コストをゼロに保つ

## マイルストーン

各マイルストーンは「完了定義（DoD）」を満たしたらコミット + 開発スレッド追記で完了。
番号順に依存しており、飛ばさない。

### M0: ウィンドウとクリアカラー
- winitでウィンドウ表示。blitz_renderがVulkanインスタンス・物理/論理デバイス・スワップチェーン・コマンドバッファ・同期プリミティブを構築し、クリアカラーを毎フレーム提示
- DoD: validation layer（同期検証含む）エラーゼロ / リサイズ・最小化で落ちない / ウィンドウを閉じたとき全Vulkanリソースが正しく破棄される（validation警告ゼロ）

### M1: 三角形とシェーダービルド基盤
- Slangツールチェーン導入。ビルド時にSlang→SPIR-Vコンパイルが走る仕組み（build.rs）
- グラフィックスパイプライン構築。頂点バッファなしのハードコード三角形を描画
- シェーダーホットリロード: ファイル監視 → Slang再コンパイル → パイプライン再生成（`参照: _doc/設計/開発ループとコンパイル時間.md` Tier 0）
- DoD: 三角形が表示される / シェーダーファイルの変更が実行中のアプリに自動反映される

### M2: メッシュ・カメラ・フレームインフライト
- 頂点/インデックスバッファ、深度バッファ、ユニフォーム、複数フレームインフライト（CPU/GPU並行）の確立
- 立方体をカメラ制御（マウス/キーボード）で眺められる
- 数学DDDの最小セットをここで導入: 座標系フレーム型（ワールド/ローカル/ビュー/クリップの幻影型パラメータを持つ位置・変換型）と単位型（長さ・時間・角度）。glamはこの値オブジェクト群の内部実装とし、生型はGPU境界のみ（第4の扉=大座標の型区別はこの一般化に統合）
- DoD: 深度が正しい / フレームインフライトの同期がvalidationクリーン / 入力→カメラの配線がコンポジションルート経由 / ドメインAPIに生のglam型が露出していない

### M3: glTF読込とテクスチャ
- gltfクレートでシーン読込（メッシュ階層・マテリアル参照）。imageクレートでテクスチャデコード、ミップマップ生成、サンプラー
- アセット参照は最初から安定ID経由にする（パス直接参照を禁止）。将来のアセット取り込みパイプライン後付けを可能にする唯一の先行手当て
- アセットホットリロード: ファイル監視による実行中差し替え（Tier 0開発ループ。安定ID参照が差し替えを容易にする）
- DoD: 標準サンプル（DamagedHelmet等）のジオメトリとベースカラーが表示される / アセットが安定IDで参照されている / アセットファイルの変更が実行中に反映される

### M4: PBRマテリアルとライティング
- metallic-roughnessモデル。方向光 + 点光源。法線マップ
- DoD: DamagedHelmetがPBRで正しく見える（金属・粗さ・法線の応答が妥当）

### M5: レンダーグラフ形式化とGPU計測
- ここまでに手書きしてきたバリア・レンダーパス管理を、パス宣言から同期を自動導出するレンダーグラフに置き換える（早すぎる抽象化を避けるため、実物経験を積んだこの段階で行う)
- **コンピュートパスを第一級で扱う**（シミュレーション層の先行要求）。検証として簡単なGPU粒子トイをコンピュートパスで動かし、描画パスとのバッファ共有を実証する
- GPUタイムスタンプクエリでパス別時間計測。フレーム統計の表示のため開発用UI（egui等の即時モードUI）をここで統合する（本番ゲームUIとは別系統。長期フェーズ計画参照）
- DoD: 既存機能がレンダーグラフ上で同一動作 / 手書きバリアが残っていない / パス別GPU時間が画面上の開発用UIに出る / コンピュートパスがグラフ上で描画と同期して動く

### M6: シャドウマッピング
- 方向光のシャドウマップ（カスケードは1枚から）。レンダーグラフに複数パスが乗る初のケース
- DoD: 影が出る / シャドウパスとメインパスの依存がグラフで表現されている

### M7: HDRポストプロセスとACESトーンマッピング
- HDR中間バッファ → トーンマップ → スワップチェーン。ブルーム1種
- DoD: 露出調整が効く / ポストプロセスチェーンがグラフのパスとして追加・削除可能

### M8: キャラクター基盤（2026-07-20改訂でフェーズ2から背骨へ前倒し）
- glTFのスキン・アニメーション読込、GPUスキニング、アニメーション再生とブレンド
- キャラクターシミュレーションとキャラクタークリエイトの前提。RPG必須要素であり、最大リスク領域（シミュレーション）を早期に検証可能にするための布石
- DoD: アニメーション付きglTF標準サンプルが再生・ブレンドできる / スキニングはGPUで行われ、シミュレーションが結果バッファへ介入できる設計になっている

### M9: キャラクターシミュレーションMVP
- シミュレーション基盤層の最小実装: XPBD布（セルフコリジョン初版）をコンピュートパスで動かし、スキン済みキャラクターに着せる
- 介入モデルの配線を実証: 入力 → ゲームロジック → 介入キュー → GPU → 描画。「掴む」（拘束の着脱）が効くこと
- DoD: キャラの動きに布が追従し、床に落ちてくちゃっとなる / 掴んで引っ張れる / validationクリーン / パス別GPU時間で予算を把握している

### M10: 流体の実現可能性スパイク（時間箱付き）
- 表面流（テクスチャ空間）のプロトタイプと、SPH/MPM系少量粘性流体の技術検証。達成可能な品質と性能の限界を計測する
- DoD: 検証レポート（達成可能品質・コスト・推奨方式・本実装可否）をユーザーへ提出。製品品質は要求しない。プロジェクト最大の不確実性をここで潰す
- 2026-07-23完了: 薄い液膜には表面流を採用し、空間内の少量流体には空間ハッシュ付きSPHを採用する。全対全探索SPHは性能比較用試作に限定し、MPMは雪・塑性・強い粘弾性が必要になった時点で再評価する

### M11: エンジンフェーズ1完了検証
- 60fps安定確認、フレーム時間分布計測、`_doc/` の全設計文書を実装と突き合わせて更新
- DoD: 全マイルストーンのDoD再確認 / READMEとドキュメントが現状を正しく記述 / ユーザーへエンジンフェーズ2（オープンワールドの柱）の詳細計画を提起する報告書
- 2026-07-23着工: `cargo xtask bench`へCPU側フレーム間隔分布を追加した。先頭120フレームを除外し、平均・p50・p95・p99・最大値・25ms超過回数をGPU時間と同じ固定条件で出力する
- 2026-07-23初回実測: GPU合計0.7276msに対しCPU側p50は16.7057ms、p95は33.2550ms、25ms超過率は8.75%だった。60fps安定は未達のため、イベントループとFIFO提示待ちを調査してから長時間実行と総点検へ進む
- 2026-07-23区間診断: 33ms級遅延はフェンス待機へ集中し、CPU処理やGPU処理量は律速でなかった。フレームインフライト数変更の改善は再現せず2を維持する。3600フレーム連続実行ではRAM・VRAMの継続増加を検出しなかった
- 2026-07-23完了: 全DoD、能力・品質・性能・変更容易性、性能9軸、絵の様式に関する3条件を総点検した。PBR固定だったマテリアル型を判別共用体へ修正し、大座標・VR・GPUメモリ確保の未完成部分をフェーズ2先行依存として記録した。実表示時刻による60fps安定は未証明である。詳細は `_doc/計画/エンジンフェーズ1完了報告とフェーズ2計画.md` を参照する

## 長期フェーズ計画（非ゴール項目のゴール定義）

エンジンフェーズ1（M0〜M11）の先にあるフェーズと、非ゴール項目それぞれの到達点を先に定義しておく。
着手条件が満たされるまで実装しないが、エンジンフェーズ中の設計判断でこれらの将来像と矛盾する選択をしないための参照点とする。

### エンジンフェーズ2: オープンワールドの柱（着手順序: M11完了後。詳細計画化はM11時点）
対象ゲーム像（オープンワールドRPG）が要求する、背骨（M0〜M11）に含まれないエンジン機能群。
背骨は様式非依存としてそのまま有効であり、その上にこれらを積む。
依存関係、各マイルストーンの完了定義、並行可能な系統は `_doc/計画/エンジンフェーズ1完了報告とフェーズ2計画.md` を正典とする。

- **ストリーミング**: 世界をチャンク分割し、プレイヤー位置に応じて非同期ロード/アンロード。メモリ予算管理。オープンワールドエンジンの定義的機能
- **地形と植生**: 地形レンダリング、LOD、大量インスタンシング（草木）。描画コール物量との戦いの主戦場で、バインドレス・GPU駆動カリングの導入先
- **キャラクターシミュレーション本格化（本エンジンの存在意義の一角。2026-07-20昇格）**: Unityの既定APIでは達成不可能でエンジンレベルの統合が必須だった表現群を、GPUコンピュート上の統一XPBDソルバを基盤に解く。
  シミュレーションと描画が同じGPUバッファをゼロコピー共有できることが自作エンジンの構造的優位。
  非同期コンピュート（生Vulkan採用理由の一つ）の主戦場。
  基盤（キャラクター基盤・布MVP・流体スパイク）は背骨のM8〜M10へ前倒し済みで、本フェーズでは残りを本格化する:
  (1) 軟体（肌のぷにぷに）: XPBD軟体をスキニング結果とブレンド
  (2) 髪: ストランドヘア（ガイド毛物理 + 補間、専用描画）
  (3) 流体の本実装: M10スパイクの検証レポートで決めた方式を製品品質へ
  (4) 布の品質向上（セルフコリジョンの精度・多層衣装）。
  層の切り方と介入モデルは `_doc/設計/シミュレーション層.md` 参照（表現はドメイン・数学は基盤）
- **キャラクタークリエイト**: パーツ単位のメッシュ合成・骨共有・ブレンドシェイプ合成。エンジン内機能として素直に実装する（複数体同期のような回避策を不要にする）
- **空と時間帯**: 大気散乱スカイ、昼夜サイクル、時間帯で変わるライティング
- **カスケードシャドウの本格化**: 遠距離視界に耐える多段カスケード（M6の発展）
- **アセットコンパイラ（旧称: アセット取り込みパイプライン。2026-07-20に層を確定）**: エンジンでもエディタでもない第3の独立したオフラインCLIツール層。
  rustcとIDEの類比でrustcに相当し、ソースアセット（glTF・画像）を検証 → 変換 → カタログ登録してエンジン内バイナリ形式を出力する。
  エンジンは実行時に汎用パースをせず（理論値志向）、エディタは変換を自分で持たずコンパイラを呼ぶ（GUI癒着でヘッドレスビルドが死ぬUnityの失敗を避ける）。
  アセット制作（DCC・AI生成）自体はプロジェクト管轄外。実装時期はアセット量産が現実になった時点。先行手当てはM3の安定ID参照のみ
- **文字とゲームUI（2026-07-20方針確定）**: 文字は組版（フォント解析・シェーピング・改行・禁則処理）を成熟クレート（cosmic-text系）に任せ、グリフアトラスのGPU統合だけ自作する。
  本番ゲームUIはリテインドモード（ツリー + フレックスボックス + スタイルというWebのメンタルモデル）をtaffy系レイアウトエンジンでレンダラー上に実装する。
  UIはテクスチャに描いて合成する構造とし、ブラウザエンジン埋め込み（Gameface方式）への差し替えとワールド空間配置（VRの扉）の両方に対して扉を開けておく。
  開発用UI（egui、即時モード）はM5で先行統合し、本番UIとは別系統として扱う
- **戦闘支援能力（2026-07-20追加。判断ゲートなしの能力として登載）**: VFXパイプライン（シミュレーションとは別系統のGPUパーティクル基盤と量産手段）、アニメーションシステム深化（ステートマシン・キャンセル・ルートモーション・IK・ヒットストップ）、当たり判定と空間クエリ（外部剛体クレート連携）、戦闘カメラ（ロックオン・画面揺れ）、敵の群れの物量性能（スキン済みインスタンシング・アニメーションLOD）。
  ゲームが戦闘をどの水準で使うかはゲーム側の後決めであり、エンジンは能力を提供する。
  M8のアニメーションシステムはレイヤー合成・ブレンド前提で設計し戦闘級拡張を閉ざさない

### ゲームフェーズ（着手条件: エンジンフェーズ2の主要機能が立つこと。ゲーム像は確定済み）
- ゴール: blitz_game クレートにオープンワールドRPGのゲームロジックを実装し、実データの描画負荷特性に合わせた特化最適化で理論値に迫る
- ゲームシステム（進行・経済・ガチャ等）の設計はこの段階で詰める（後からどうとでもなる部分という位置づけを維持し、基盤を先行させる）

### エディタフェーズ（作ることは確定済み。着手順序: エンジンのデータ形式が安定するM3以降に仕様策定を開始）
- ゴール: エンジンとプロセス分離した別アプリケーションとして、シーン配置・アセットインポート・マテリアル調整を行うエディタを作る。操作者はAIと人間の両対応
- 設計骨格: 操作コマンド層を核とする。すべての編集操作をコマンドとして定義し、AIはコマンドを直接発行、人間用GUIは同じコマンドを発行する薄い皮にする。undo/redo・操作ログ再生も同じコマンド列から導く
- 不変の原則: 依存は一方向（エディタ→エンジン）。エンジンのコードにエディタへの参照・条件分岐を一切入れない。エディタはエンジンのデータ形式を読み書きし、プレビューはエンジンをライブラリとして埋め込んで行う

### RHI・マルチプラットフォームフェーズ（着手条件: コンソール開発契約、またはMetal対応の実需要）
- ゴール: blitz_render の下にバックエンド差し替え層（RHI）を切り出し、Vulkan以外のAPIを差せるようにする。Slangで書いたシェーダー資産は無傷で移行する
- それまでの担保: Vulkan自体のポータビリティ（Windows/Linux/Android、MoltenVK）で賄う。エンジンフェーズ中も「ash型を blitz_render から漏らさない」封じ込めを守ることが、この切り出しコストを最小に保つ布石になっている

### シーン表現・ECSの決定（着手条件: 対象ゲーム決定）
- ゴール: 対象ゲームのエンティティ数・動的性・クエリパターンに基づいて、素朴な構造体群 / 自作の最小ECS / 既存ECSクレートのいずれかを選定する。汎用ECSを先に作ることはしない
- エンジンフェーズ中のシーンは「M3のglTF階層をそのまま保持する最小表現」に留める

### 剛体物理・オーディオ（作ることは確定。着手順序: ゲーム仕様が要求する時点）
- ゴール: 自作しない。実績ある外部クレート（剛体物理: rapier系、オーディオ: kira系を第一候補にその時点で再評価）をエンジンの語彙で包んで統合する
- 剛体（壊れる物・投擲物・当たり判定）とオーディオはエンジンの存在意義の外であり、汎用性の税金を払ってよい領域
- **キャラクターシミュレーション（軟体・布・髪・流体）はこの分類から除外**（2026-07-20改訂）。外部クレートで賄えずエンジンレベル統合が必須なこと自体が本エンジンを作る理由の一つであるため、エンジンフェーズ2の柱として自作する。外部の剛体ソルバとの衝突情報連携は設計時に考慮する

### 判断基準（迷ったときの優先順位）

0. **可能性を閉じる決定を早期にしない**（最上位原則、2026-07-20制定）: 将来の選択肢を不可能にする設計・計画判断を早い段階で行わない（「変更を困難にする継承を早期に決めるな」と同型）。
   エンジン計画の問いは常に「どの能力を・どの順で・どの品質で作るか」であり、ゲーム内容の決定をエンジン計画の前提にしない。
   「これを不可能にするか」という形の問いをユーザーに投げない。各「扉」はこの原則の個別事例である
1. **正しさ**: validationエラー・未定義動作の疑いは他の全てに優先して潰す
2. **封じ込め**: unsafe と ash型は blitz_render から漏らさない。漏らすくらいなら設計を変える
3. **単純さ**: 現マイルストーンに必要な最小の実装を選ぶ。将来のための汎用化はしない
4. **性能**: 上3つを満たす範囲で理論値志向。ただし計測（M5以降）なしの推測最適化はしない
5. 設計が間違っていたと判明したら、継ぎ足しではなく書き直す。書き直しの理由は開発スレッドに記録
