# Blitzdrache0 開発計画

自律ループ実行（AIが単独で判断しながら開発を進める運用）の拠り所となる計画書。
各セッション・各イテレーションの冒頭でこのファイルを読み、現在地と次のタスクを特定する。

## ゴール

**最終ゴール**: デバイスの理論値性能を志向する自作ゲームエンジン。汎用エンジンの
汎用性の税金を払わず、対象ゲームに不要な機能を持たない。

**エンジンフェーズの到達点（本計画のスコープ）**: glTFで読み込んだシーンを
PBR + シャドウ + HDRポストプロセスで描画し、GPU計測基盤で性能を定量把握できる
「素のエンジン」。Windows + Vulkan。60fps（FIFO同期）で安定動作。

**その先（本計画のスコープ外）**: 対象ゲームの決定 → ゲーム特化の最適化
（バインドレス、GPU駆動描画、非同期コンピュート）→ 必要になった時点でのRHI切り出し。
対象ゲームの決定はユーザーの仕様判断であり、AIが勝手に決めない。

## 非ゴール（当面作らないもの）

作りたくなっても作らない。要求が実際に発生した時点で計画を改訂してから作る。

- エディタUI（AI駆動開発ではエディタは強みにならないという本プロジェクトの前提）
- RHI / マルチグラフィックスAPI抽象層（コンソール対応が現実になるまで）
- 汎用シーングラフ・汎用ECS（対象ゲーム決定前の汎用化は負債）
- シェーダーグラフ（シェーダーはSlangを直接書く）
- 物理・オーディオ・ネットワーク（ゲームフェーズで必要になってから）
- スクリプト言語組み込み（ゲームロジックはRustで書く）

## 全体アーキテクチャ（確定事項）

```
ゲームロジック（安全なRust、将来 blitz_game として分離）
   ↓
blitz_engine: シーン・アセット・マテリアル（安全なRust、#![forbid(unsafe_code)]）
   ↓
blitz_render: レンダーグラフ + リソースシステム（エンジン中核の型安全層）
   ↓
ash（unsafe は blitz_render 実装内部に封じ込め。公開APIに ash 型を露出しない）
```

- 依存方向はCargoワークスペースのクレート分割でコンパイル時強制
- コンポジションルートは blitz_app。フレーム内の実行順序はここが一元支配
  （入力確定 → 世界更新 → 描画内容抽出 → 描画）
- イベントループはwinit所有パターンA（`参照: _doc/設計/イベントループとフレームペーシング.md`）
- シェーダー言語はSlang。SPIR-Vへコンパイルして使う
- 安全化の方針: 汎用のVulkanラッパーは作らない。「このエンジンの使い方」だけを
  露出する狭い型で安全性を担保し、実行時追跡コストをゼロに保つ

## マイルストーン

各マイルストーンは「完了定義（DoD）」を満たしたらコミット + 開発スレッド追記で完了。
番号順に依存しており、飛ばさない。

### M0: ウィンドウとクリアカラー
- winitでウィンドウ表示。blitz_renderがVulkanインスタンス・物理/論理デバイス・
  スワップチェーン・コマンドバッファ・同期プリミティブを構築し、クリアカラーを毎フレーム提示
- DoD: validation layer（同期検証含む）エラーゼロ / リサイズ・最小化で落ちない /
  ウィンドウを閉じたとき全Vulkanリソースが正しく破棄される（validation警告ゼロ）

### M1: 三角形とシェーダービルド基盤
- Slangツールチェーン導入。ビルド時にSlang→SPIR-Vコンパイルが走る仕組み（build.rs）
- グラフィックスパイプライン構築。頂点バッファなしのハードコード三角形を描画
- DoD: 三角形が表示される / シェーダーを書き換えて再ビルドすると反映される

### M2: メッシュ・カメラ・フレームインフライト
- 頂点/インデックスバッファ、深度バッファ、ユニフォーム（glamの行列）、
  複数フレームインフライト（CPU/GPU並行）の確立
- 立方体をカメラ制御（マウス/キーボード）で眺められる
- DoD: 深度が正しい / フレームインフライトの同期がvalidationクリーン /
  入力→カメラの配線がコンポジションルート経由

### M3: glTF読込とテクスチャ
- gltfクレートでシーン読込（メッシュ階層・マテリアル参照）。imageクレートで
  テクスチャデコード、ミップマップ生成、サンプラー
- DoD: 標準サンプル（DamagedHelmet等）のジオメトリとベースカラーが表示される

### M4: PBRマテリアルとライティング
- metallic-roughnessモデル。方向光 + 点光源。法線マップ
- DoD: DamagedHelmetがPBRで正しく見える（金属・粗さ・法線の応答が妥当）

### M5: レンダーグラフ形式化とGPU計測
- ここまでに手書きしてきたバリア・レンダーパス管理を、パス宣言から同期を自動導出する
  レンダーグラフに置き換える（早すぎる抽象化を避けるため、実物経験を積んだこの段階で行う）
- GPUタイムスタンプクエリでパス別時間計測、フレーム統計表示
- DoD: 既存機能がレンダーグラフ上で同一動作 / 手書きバリアが残っていない /
  パス別GPU時間が出る

### M6: シャドウマッピング
- 方向光のシャドウマップ（カスケードは1枚から）。レンダーグラフに複数パスが乗る初のケース
- DoD: 影が出る / シャドウパスとメインパスの依存がグラフで表現されている

### M7: HDRポストプロセスとACESトーンマッピング
- HDR中間バッファ → トーンマップ → スワップチェーン。ブルーム1種
- DoD: 露出調整が効く / ポストプロセスチェーンがグラフのパスとして追加・削除可能

### M8: エンジンフェーズ完了検証
- 60fps安定確認、フレーム時間分布計測、`_doc/` の全設計文書を実装と突き合わせて更新
- DoD: 全マイルストーンのDoD再確認 / READMEとドキュメントが現状を正しく記述 /
  ユーザーへ「ゲーム仕様の決定」を提起する報告書

## 自律ループの運用規約

1イテレーションの手順:
1. 本計画と開発スレッド最新分を読み、未完了の最小マイルストーン内で次のタスクを1つ選ぶ
2. 実装（原則は実装員サブエージェントへ委譲、親は設計判断と検収）
3. 検証: `cargo check` → `cargo clippy -- -D warnings` → `cargo test` → 実行して
   validation layerエラーゼロ確認。描画結果の自動検証はオフスクリーンレンダリング +
   ピクセル読み戻しの単体テストで行う（GUI操作の自動化はしない）
4. 自己レビュー5軸 → コミット（論理単位1コミット、微修正はスカッシュ）
5. 開発スレッドに逐語追記（dev-thread-genスキルがあれば利用）

### 判断基準（迷ったときの優先順位）

1. **正しさ**: validationエラー・未定義動作の疑いは他の全てに優先して潰す
2. **封じ込め**: unsafe と ash型は blitz_render から漏らさない。漏らすくらいなら設計を変える
3. **単純さ**: 現マイルストーンに必要な最小の実装を選ぶ。将来のための汎用化はしない
4. **性能**: 上3つを満たす範囲で理論値志向。ただし計測（M5以降）なしの推測最適化はしない
5. 設計が間違っていたと判明したら、継ぎ足しではなく書き直す。書き直しの理由は開発スレッドに記録

### 依存クレート追加の基準

- 追加してよい: エンジンの中核でない基盤処理（画像デコード、glTFパース、数学、エラー定義）
- 自作する: レンダラー・リソース管理・同期・シーン表現（エンジンの存在意義そのもの）
- 迷ったら: そのクレートの汎用性の税金を自分が払うかで判断。README の利用ライブラリ表に追記

### ユーザーへエスカレーションする事項（それ以外は自分で判断して進める）

- ゲーム仕様・ターゲット（M8での提起、および途中でスコープに影響する場合）
- 非ゴールリストの変更（新カテゴリの機能を作り始める判断）
- 実画面のスクリーンショット確認が必要な場合（テスト方法選定ルールに従い事前許可）
- マイルストーンの完了報告（報告のみ。承認待ちで停止はしない）
