# Blitzdrache0 開発計画

自律ループ実行（AIが単独で判断しながら開発を進める運用）の拠り所となる計画書。
各セッション・各イテレーションの冒頭でこのファイルを読み、現在地と次のタスクを特定する。

語彙は `ユビキタス言語.md` の定義に従う。本計画に新しい概念語が現れたら、
先にユビキタス言語へ定義を追加してから使う。

## プロダクトビジョン（2026-07-20 壁打ちで確定した部分）

- **最終成果物**: まず商業ゲーム。基盤（エンジン + エディタ）の外販は二段目として視野に
  入れる。帰結: 特化最適化を優先しつつ、モジュール境界の清潔さと文書化を
  外販可能性の担保として維持する
- **対象ゲーム像**: フルコースのオープンワールドRPG（原神が確立した水準）。
  賭けの構造: アセット物量という従来の参入障壁をAIによる量産で突破できるはずであり、
  その物量を受け止められる基盤（取り込み・検証・予算管理のパイプラインと、
  物量を描き切る性能）を先に整えておく。ゲームシステム（進行・ガチャ等）は
  ただのプログラムであり後からどうとでもなる部分と位置づける。
  解決すべきボトルネックはアートとパフォーマンスの2つ
- **エディタ**: 作ることは確定（経営判断済み。需要検証は不要）。操作者はAIと人間の両対応。
  設計方針は操作コマンド層を核とし、AIもGUI（人間用の薄い皮）も同一のコマンドを発行する。
  undo/redo・操作ログ再生も同じ仕組みから導く。詳細仕様の策定はエディタフェーズ
- **絵の方向性**: 未決定（白紙）。分岐が効くのは主にエンジン側（マテリアルモデル・
  ライティング・輪郭線・AA戦略）で、エディタへの影響はエンジンのマテリアル語彙を映すだけの
  従属的なもの。**貪欲法（リアル調先行で進め、トゥーンは後から追加）を採用する**。
  成立条件は次の3つの扉を閉めないこと:
  (1) マテリアルは判別共用体で設計し単一シェーディングモデルを型に焼き付けない
  (2) 様式決定までTAAを採用しない（AAはMSAAか無し）
  (3) 当面forward系で進めdeferredのG-bufferレイアウトを確定させない。
  この運用下では絵の最終決定はゲーム内容の壁打ちが熟すまで遅延できる。
  M3完了時に「3つの扉が開いたままか」を確認する。分岐の詳細は開発スレッド2026-07-20参照。
  対象ゲーム像（原神型）の確定により**有力仮説はアニメ調（セル）キャラ + 様式化された世界**に
  更新された。原神型はまさにPBR基盤の上にセル表現を載せる構成のため、貪欲法
  （リアル調基盤先行）はこの仮説とも整合する。最終確定は変わらずM3までに行う
- **大座標の扉（オープンワールド固有の第4の扉）**: f32の精度は原点から数kmで崩れるため、
  オープンワールドはカメラ相対レンダリング（描画時にカメラ原点へ座標を移す）が必須になる。
  今から閉めないでおく: ワールド座標の型とGPUへ渡す座標の型を最初から区別し、
  「ワールド座標をそのままシェーダーへ送る」設計を固定しない
- **VRの扉（第5の扉。実要件への昇格はユーザーのビジネス判断待ち）**: VR対応は
  (1) 視点数を1とハードコードしない（マルチビュー前提の型設計。レンダーグラフの各パスが
  視点数を引数に取る）(2) 入力インテント抽象化（ゲームロジックはインテントのみ消費、
  デバイス→インテント写像は入力層に隔離）(3) UIをワールド空間に置ける前提で設計する、
  の3点を守れば開いたままになる。なお既決定の forward系・MSAA・TAA保留・
  ループ所有権A→B移行路はすべてVR適合（VRのペーシングはOpenXRの xrWaitFrame が支配し、
  late-latchが標準技法のため）。至近距離検分への耐性はアセット取り込みパイプラインの
  検証項目（テクセル密度・近接ジオメトリ品質の予算）として扱う。
  昇格が確定したらOpenXR統合をエンジンフェーズ2の柱に加え、マイルストーンを改訂する
- **現在の主題**: 経営者（ユーザー）が「仕様を切れ」と言えば開発者（AI）が仕様を切れる
  水準まで、プロジェクトの方向性を壁打ちで詰めること

## ゴール

**最終ゴール**: デバイスの理論値性能を志向する自作ゲームエンジン。汎用エンジンの
汎用性の税金を払わず、対象ゲームに不要な機能を持たない。

**エンジンフェーズの到達点（本計画のスコープ）**: glTFで読み込んだシーンを
PBR + シャドウ + HDRポストプロセスで描画し、GPU計測基盤で性能を定量把握できる
「素のエンジン」。Windows + Vulkan。60fps（FIFO同期）で安定動作。

**その先（本計画のスコープ外）**: 対象ゲームの決定 → ゲーム特化の最適化
（バインドレス、GPU駆動描画、非同期コンピュート）→ 必要になった時点でのRHI切り出し。
対象ゲームの決定はユーザーの仕様判断であり、AIが勝手に決めない。

## 非ゴール（エンジンフェーズ中は作らないもの）

作りたくなっても作らない。ただし各項目の長期ゴールは「長期フェーズ計画」節で先に
定義してあり、無計画な棚上げではない。着手条件が満たされた時点で計画を改訂してから作る。

- エディタ（AI駆動開発ではエディタは強みにならないという本プロジェクトの前提）
- RHI / マルチグラフィックスAPI抽象層（コンソール対応が現実になるまで）
- 汎用シーングラフ・汎用ECS（対象ゲーム決定前の汎用化は負債）
- シェーダーグラフ（シェーダーはSlangを直接書く）
- 物理・オーディオ・ネットワーク（ゲームフェーズで必要になってから）
- スクリプト言語組み込み（ゲームロジックはRustで書く）

## 全体アーキテクチャ（確定事項）

```
ゲームロジック（安全なRust、将来 blitz_game として分離）
   ↓
blitz_engine: シーン・アセット・マテリアル（安全なRust、#![forbid(unsafe_code)]）
   ↓
blitz_render: レンダーグラフ + リソースシステム（エンジン中核の型安全層）
   ↓
ash（unsafe は blitz_render 実装内部に封じ込め。公開APIに ash 型を露出しない）
```

- 依存方向はCargoワークスペースのクレート分割でコンパイル時強制
- コンポジションルートは blitz_app。フレーム内の実行順序はここが一元支配
  （入力確定 → 世界更新 → 描画内容抽出 → 描画）
- イベントループはwinit所有パターンA（`参照: _doc/設計/イベントループとフレームペーシング.md`）
- シェーダー言語はSlang。SPIR-Vへコンパイルして使う
- 安全化の方針: 汎用のVulkanラッパーは作らない。「このエンジンの使い方」だけを
  露出する狭い型で安全性を担保し、実行時追跡コストをゼロに保つ

## マイルストーン

各マイルストーンは「完了定義（DoD）」を満たしたらコミット + 開発スレッド追記で完了。
番号順に依存しており、飛ばさない。

### M0: ウィンドウとクリアカラー
- winitでウィンドウ表示。blitz_renderがVulkanインスタンス・物理/論理デバイス・
  スワップチェーン・コマンドバッファ・同期プリミティブを構築し、クリアカラーを毎フレーム提示
- DoD: validation layer（同期検証含む）エラーゼロ / リサイズ・最小化で落ちない /
  ウィンドウを閉じたとき全Vulkanリソースが正しく破棄される（validation警告ゼロ）

### M1: 三角形とシェーダービルド基盤
- Slangツールチェーン導入。ビルド時にSlang→SPIR-Vコンパイルが走る仕組み（build.rs）
- グラフィックスパイプライン構築。頂点バッファなしのハードコード三角形を描画
- DoD: 三角形が表示される / シェーダーを書き換えて再ビルドすると反映される

### M2: メッシュ・カメラ・フレームインフライト
- 頂点/インデックスバッファ、深度バッファ、ユニフォーム（glamの行列）、
  複数フレームインフライト（CPU/GPU並行）の確立
- 立方体をカメラ制御（マウス/キーボード）で眺められる
- DoD: 深度が正しい / フレームインフライトの同期がvalidationクリーン /
  入力→カメラの配線がコンポジションルート経由

### M3: glTF読込とテクスチャ
- gltfクレートでシーン読込（メッシュ階層・マテリアル参照）。imageクレートで
  テクスチャデコード、ミップマップ生成、サンプラー
- DoD: 標準サンプル（DamagedHelmet等）のジオメトリとベースカラーが表示される

### M4: PBRマテリアルとライティング
- metallic-roughnessモデル。方向光 + 点光源。法線マップ
- DoD: DamagedHelmetがPBRで正しく見える（金属・粗さ・法線の応答が妥当）

### M5: レンダーグラフ形式化とGPU計測
- ここまでに手書きしてきたバリア・レンダーパス管理を、パス宣言から同期を自動導出する
  レンダーグラフに置き換える（早すぎる抽象化を避けるため、実物経験を積んだこの段階で行う）
- GPUタイムスタンプクエリでパス別時間計測、フレーム統計表示
- DoD: 既存機能がレンダーグラフ上で同一動作 / 手書きバリアが残っていない /
  パス別GPU時間が出る

### M6: シャドウマッピング
- 方向光のシャドウマップ（カスケードは1枚から）。レンダーグラフに複数パスが乗る初のケース
- DoD: 影が出る / シャドウパスとメインパスの依存がグラフで表現されている

### M7: HDRポストプロセスとACESトーンマッピング
- HDR中間バッファ → トーンマップ → スワップチェーン。ブルーム1種
- DoD: 露出調整が効く / ポストプロセスチェーンがグラフのパスとして追加・削除可能

### M8: エンジンフェーズ完了検証
- 60fps安定確認、フレーム時間分布計測、`_doc/` の全設計文書を実装と突き合わせて更新
- DoD: 全マイルストーンのDoD再確認 / READMEとドキュメントが現状を正しく記述 /
  ユーザーへ「ゲーム仕様の決定」を提起する報告書

## 長期フェーズ計画（非ゴール項目のゴール定義）

エンジンフェーズ（M0〜M8）の先にあるフェーズと、非ゴール項目それぞれの到達点を
先に定義しておく。着手条件が満たされるまで実装しないが、エンジンフェーズ中の設計判断で
これらの将来像と矛盾する選択をしないための参照点とする。

### エンジンフェーズ2: オープンワールドの柱（着手順序: M8完了後。詳細計画化はM8時点）
対象ゲーム像（オープンワールドRPG）が要求する、M0〜M8に含まれないエンジン機能群。
M0〜M8は様式非依存の背骨としてそのまま有効であり、その上にこれらを積む。

- **ストリーミング**: 世界をチャンク分割し、プレイヤー位置に応じて非同期ロード/アンロード。
  メモリ予算管理。オープンワールドエンジンの定義的機能
- **地形と植生**: 地形レンダリング、LOD、大量インスタンシング（草木）。
  描画コール物量との戦いの主戦場で、バインドレス・GPU駆動カリングの導入先
- **キャラクター**: スキニング・スケルタルアニメーション・アニメーションブレンド。
  RPGの必須要素でありM0〜M8に無い最大の欠落。エンジンフェーズ2の最優先候補
- **空と時間帯**: 大気散乱スカイ、昼夜サイクル、時間帯で変わるライティング
- **カスケードシャドウの本格化**: 遠距離視界に耐える多段カスケード（M6の発展）
- **アセット取り込みパイプライン**: AI量産アセットの自動取り込み・検証（規格・予算超過の
  機械的検出）・変換。アート物量の賭けを受け止める側の基盤で、エディタと共有する

### ゲームフェーズ（着手条件: エンジンフェーズ2の主要機能が立つこと。ゲーム像は確定済み）
- ゴール: blitz_game クレートにオープンワールドRPGのゲームロジックを実装し、
  実データの描画負荷特性に合わせた特化最適化で理論値に迫る
- ゲームシステム（進行・経済・ガチャ等）の設計はこの段階で詰める（後からどうとでもなる部分
  という位置づけを維持し、基盤を先行させる）

### エディタフェーズ（作ることは確定済み。着手順序: エンジンのデータ形式が安定するM3以降に仕様策定を開始）
- ゴール: エンジンとプロセス分離した別アプリケーションとして、シーン配置・アセット
  インポート・マテリアル調整を行うエディタを作る。操作者はAIと人間の両対応
- 設計骨格: 操作コマンド層を核とする。すべての編集操作をコマンドとして定義し、
  AIはコマンドを直接発行、人間用GUIは同じコマンドを発行する薄い皮にする。
  undo/redo・操作ログ再生も同じコマンド列から導く
- 不変の原則: 依存は一方向（エディタ→エンジン）。エンジンのコードにエディタへの参照・
  条件分岐を一切入れない。エディタはエンジンのデータ形式を読み書きし、プレビューは
  エンジンをライブラリとして埋め込んで行う

### RHI・マルチプラットフォームフェーズ（着手条件: コンソール開発契約、またはMetal対応の実需要）
- ゴール: blitz_render の下にバックエンド差し替え層（RHI）を切り出し、Vulkan以外の
  APIを差せるようにする。Slangで書いたシェーダー資産は無傷で移行する
- それまでの担保: Vulkan自体のポータビリティ（Windows/Linux/Android、MoltenVK）で賄う。
  エンジンフェーズ中も「ash型を blitz_render から漏らさない」封じ込めを守ることが、
  この切り出しコストを最小に保つ布石になっている

### シーン表現・ECSの決定（着手条件: 対象ゲーム決定）
- ゴール: 対象ゲームのエンティティ数・動的性・クエリパターンに基づいて、素朴な構造体群 /
  自作の最小ECS / 既存ECSクレートのいずれかを選定する。汎用ECSを先に作ることはしない
- エンジンフェーズ中のシーンは「M3のglTF階層をそのまま保持する最小表現」に留める

### 物理・オーディオ（作ることは確定。着手順序: ゲーム決定後、ゲーム仕様が要求する時点）
- ゴール: 自作しない。実績ある外部クレート（物理: rapier系、オーディオ: kira系を第一候補に
  その時点で再評価）をエンジンの語彙で包んで統合する。決定論性の要否は対象ゲームで判断
- これらはエンジンの存在意義（理論値志向の描画）の外にあり、汎用性の税金を払ってよい領域

### シェーダーグラフ（恒久非ゴール候補）
- AI駆動開発ではシェーダーはSlangを直接書けば足りるため、視覚的ノードエディタは
  必要性が実証されない限り作らない。棚上げではなく「作らない」side に倒した判断

### ネットワーク・スクリプト言語（未計画）
- 対象ゲームが要求した時点でゴールを定義する。現時点では計画を持たないことを明示する

## 自律ループの運用規約

1イテレーションの手順:
1. 本計画と開発スレッド最新分を読み、未完了の最小マイルストーン内で次のタスクを1つ選ぶ
2. 実装（原則は実装員サブエージェントへ委譲、親は設計判断と検収）
3. 検証: `cargo check` → `cargo clippy -- -D warnings` → `cargo test` → 実行して
   validation layerエラーゼロ確認。描画結果の自動検証はオフスクリーンレンダリング +
   ピクセル読み戻しの単体テストで行う（GUI操作の自動化はしない）
4. 自己レビュー5軸 → コミット（論理単位1コミット、微修正はスカッシュ）
5. 開発スレッドに逐語追記（dev-thread-genスキルがあれば利用）

### 判断基準（迷ったときの優先順位）

1. **正しさ**: validationエラー・未定義動作の疑いは他の全てに優先して潰す
2. **封じ込め**: unsafe と ash型は blitz_render から漏らさない。漏らすくらいなら設計を変える
3. **単純さ**: 現マイルストーンに必要な最小の実装を選ぶ。将来のための汎用化はしない
4. **性能**: 上3つを満たす範囲で理論値志向。ただし計測（M5以降）なしの推測最適化はしない
5. 設計が間違っていたと判明したら、継ぎ足しではなく書き直す。書き直しの理由は開発スレッドに記録

### 依存クレート追加の基準

- 追加してよい: エンジンの中核でない基盤処理（画像デコード、glTFパース、数学、エラー定義）
- 自作する: レンダラー・リソース管理・同期・シーン表現（エンジンの存在意義そのもの）
- 迷ったら: そのクレートの汎用性の税金を自分が払うかで判断。README の利用ライブラリ表に追記

### ユーザーへエスカレーションする事項（それ以外は自分で判断して進める）

- ゲーム仕様・ターゲット（M8での提起、および途中でスコープに影響する場合）
- 非ゴールリストの変更（新カテゴリの機能を作り始める判断）
- 実画面のスクリーンショット確認が必要な場合（テスト方法選定ルールに従い事前許可）
- マイルストーンの完了報告（報告のみ。承認待ちで停止はしない）

## コーディングルール

リポジトリ直下の `CLAUDE.md`（Rust版細則）に従う。グローバル憲法のRust適用・
100行分割・unsafe規律・`安全性:` コメント・lint機械強制を含む。開発初日から適用し、
「雑に書いて後で綺麗にする」は禁止。一度の横着も許容しない。
