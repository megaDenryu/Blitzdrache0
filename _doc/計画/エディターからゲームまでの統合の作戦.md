# エディターからゲームまでの統合の作戦

4つの完成済みの系——ブラウザのエディター・アセットコンパイラ・エンジン・部品カタログ——を繋ぎ、「編集した世界をゲームとして歩いて確かめる」閉ループを作る工事の見取り図である。2026-08-21のオーナーとの考察で制定した。個々の系の設計はそれぞれの正本が持ち、この文書は系のあいだの依存の向きと、作る順序だけを持つ。

## 目的(ゴールの絵)

オーナーがブラウザのエディターで地形・道・建物の配置を編集し、保存すると数秒で実機のゲームの中をキャラクターで歩いて確かめられる。建物は部品カタログの骨格方式で組まれ、いずれはグリッド配置の建物エディターで自作できる。**プレビューという別の絵は作らない。実際にゲームを動作させることが最も正確なプレビューである。**

## 無いもの(この作戦で作るもの)

1. **エディター世界の種別**: 書き出された `assets/editor_world/` を `compile-assets` へ通す世界の登録(エディター計画の申し送りの完済)
2. **プレビューの閉ループ**: 焼いた実行時形式をゲームが開き、編集→保存→焼き→反映が回る配線
3. **建物配置の焼き込み**: エディターの建物配置を、部品カタログの組み立て(骨格方式)の個体としてチャンクへ焼く変換
4. **家の外形カタログ**: 部品カタログ側が建物定義ごとの外接箱・設置面積・出入口の向きを要約として書き出し、エディターがそれを読む口
5. **道の焼き込み**: 道スプラインの高さ場への変形(切土盛土)と地表材質は編集側に在るが、エンジンの実行時形式への反映の検証が無い
6. **散布の設定の接続**: エディターの散布の設定を散布の宣言へ写す変換
7. **建物エディター**: グリッド配置で部品を組み合わせて建物を自作する道具
8. **テクスチャの制作経路**: 現在どこにも無い。部品は代表色(ベースカラー係数)のみで、テクスチャを作る・収蔵する・部品へ割り当てる経路が存在しない
9. ~~**地形の地表材質の描画**~~ → 段Eで完了。エディターが塗った地表材質4層をエンジンの地形描画が読み、層のタイルを重みで混ぜて描く

## 層と依存の向き

```
[建物エディター]──建物の定義──→[地形エディター]──世界のソース──→[コンパイラ]──実行時形式──→[ゲーム=プレビュー]
      ↑                              ↑
      └──部品の外形カタログ──[部品カタログ]──部品glbと組み立て規則──→(コンパイラが読む)
```

- **建物の正本**は建物エディターの保存物(部品をどう組んだか)。**世界の正本**は地形エディターの保存物(高さ場・道・区画・どの建物をどこへ置くか)。エンジンは正本を持たず、焼かれた実行時形式を読むだけである
- 流れは一方向である。エディターがエンジンの型を知ることはなく、接点は「ソースアセットの書式」と「外形カタログの書式」の2つの契約に限る
- 世界の由来は2系統になる(ゲーム制作アーキテクチャの判断7のとおり): 手続き生成(乱数の種から)と、エディターの手作業。どちらも同じソース書式へ合流し、コンパイラ以降は区別しない

## 決定

### 決定1: プレビューは実ゲーム実行であり、経路は「保存→増分焼き→ホットリロード」で始める

エンジンにはアセットのホットリロードと増分の鍵(変わったチャンクだけ焼き直す)が既に在る。editor_server はこのリポジトリ内のRustクレートであり、コンパイラを直接呼べる。**新しい通信基盤を作らず、既存資産の配線だけで「保存すると数秒でゲームに出る」を成立させる。** スライダー追従のような真のリアルタイムは、この閉ループの遅さが実測で問題になってから投資する。

### 決定2: ゲームの器はキツネの場所巡りを「世界を差し替えられる歩行の器」へ一般化する

新しいゲームプロジェクトをエントリーポイントから立てる案は採らない。理由は3つある。(1)プレビューに要るのは「編集した世界を歩けること」であり、場所巡りの移動・カメラ・接地がそのまま使える (2)ゲームの実体の持ち方はエンジンが強制しない(判断2)ため、新しいゲームは内容の要求が立ったときにいつでも別の状態機械として立てられる——いま立てても中身が無い (3)場所巡りが「アセトが無く意味不明」だった原因はゲームの器ではなく世界の中身であり、この作戦の閉ループがまさにそれを埋める。**場所巡り固有の部分(目印と到達判定)と、歩行の器(移動・カメラ・接地・世界の読み込み)を分け、器が任意の世界を開ける形にする。** ゲームオブジェクトへの振る舞いの付与(カスタムスクリプティング、`_doc/ゲーム開発用エディター計画/tmp計画2.md` の思索)は、歩ける世界の上でゲーム内容の要求が立ってから別の作戦として設計する。

### 決定3: 建物エディターはNatori City Builder Coreの思想を引き継いだ独自設計にする

Natori City Builder Core仕様(`_doc/ゲーム開発用エディター計画/Natori City Builder Core仕様.md`)は外部からの持ち込み素材であり、そのまま実装する対象ではない。引き継ぐのは思想である——**アセットの構築は、離散的なパラメータ(グリッドのセル・階・規格化された部品)としての配置指定と、塗りの操作ができるエディターでなければ成立しない**。この思想の上で、保存形式はこのリポジトリの部品カタログの組み立て(接合点)にする。推奨の形は「セル=1ベイ(2.0メートル規格)とし、グリッド配置を保存時に接合点の組み立てへ変換して噛み合いの検査を通す」——操作感は離散配置のまま、突き合わせと噛み合いの網が裏で生きる。検査に乗らない自由配置(セルをはみ出す装飾)は検査対象外の装飾層として別枠で許し、思想の自由度を殺さない。**具体の設計は建物エディターの着手前にオーナーと議論して裁定する。**

### 決定4: テクスチャはAI画像生成を第一経路にし、既存のロード経路へ流す

品質の印象を決めるのはテクスチャとマテリアルであり、閉ループの絵が出た瞬間に「テクスチャが無いから微妙」という感想が出ることは確実である。経路を次のとおり定める。

- **作り方**: タイル化(シームレス)テクスチャの生成は二段構えとする(2026-08-22の段Dの裁定でAI生成第一の当初案を改めた)。第一段はBlender側の既存プロシージャルマテリアル(漆喰・木骨の木・赤瓦・石壁)をCyclesで平面へベイクして画像化する。正本がコードのまま残って調整が再現でき、環境が既にあるため管(生成→シームレス化→収蔵→UV→材質→エンジン確認)を先に通せる。第二段として、絵の印象が不足したらAI生成画像を同じ管で差し替える(収蔵形式・検査・UV・エンジン経路が共通なので差し替えはtextures/の中身の交換だけ)。要る種類は、部品用(漆喰・木骨の木・赤瓦・石壁)と地形の層用(草・土・岩肌・泥)と装飾で、どれも1024画素級のタイルで足りる。**タイル化の成立は、シームレス化の最終工程で向かい合う境界の画素列を厳密に一致させ、機械検査は完全一致(閾値なし)で行う**(検査はBlenderPython側quality_gatesの静的検査)
- **収蔵**: Blitzdrache0Assets へ `textures/` を新設し、来歴(生成の指示文・生成器・日付)とREADMEの収蔵表を部品と同じ運用で持つ
- **部品への接続**: BlenderPython側の材質の割り当てで行う(UV展開+テクスチャ参照。代表色からの置き換え)。部品カタログの契約は既にテクスチャつき材質を想定している(ベースカラー係数の検査がテクスチャの有無で条件を分ける形)ため、契約の変更は要らない。これが従来「質感の段まで先送り」としてきた質感の段の実体である
- **地形への接続**: エディターの地表材質4層のスプラットと、層ごとのタイルテクスチャを、エンジンの地形描画が読む(シェーダーの工事。新しいパスは足さず、シーン描画の地形の枝を広げる)
- **ロード**: 部品側は既存経路がそのまま使える——glTFのテクスチャ読み・ブロック圧縮と縮小段のオフライン生成・実行時形式への焼きは着手順4で完成済みである。新しく要るのは地形の層テクスチャの読みだけである

## 段割り(依存順)

- **段A: エディター世界の種別と焼きの通し(完了)。** `assets/editor_world/` を読む世界を `compile-assets` へ登録した。ソース目録の版2と実行時目録の版2は世界ごとのチャンク一辺を1つ持ち、版1のソース目録は100メートルとして最新版へ変換する。エディター世界の16チャンクは256メートルの原点へ配置し、全高さ格子の一辺との一致を焼く前に検査する。既存21世界の実行時アセット149本は変更前とバイト単位で一致し、目録だけが版1から版2へ変わることを検収した
- **段B: 閉ループの成立。** 歩行の器(決定2の分離)がエディター世界を開き、編集→保存→焼き→ホットリロードで反映されるまで。**この縦切りが全系の配線を一度に実証する**。以降の段は同じ管を太らせるだけである。8km級の世界へ広げる時点で、保存要求を待たせない裏側でのベイクと、その完了状態をエディターへ表示する仕組みを再検討する

段Bの手順は次のとおりである。

1. 作業ディレクトリ`C:\devs\Blitzdrache0`で`cargo xtask editor`を実行し、編集サーバーを起動する。
2. エディターで大域世界またはチャンクを編集する。
3. エディターの保存操作を行う。保存処理はソースアセットの書き出しと`target/editor_world_assets`へのベイクまでを同期して完了させる。
4. 作業ディレクトリ`C:\devs\Blitzdrache0`で`cargo xtask play-editor-world`を実行する。起動済みの実行は、次の保存で生成台帳の内容が変わった後に実行時アセット一式を読み直す。
- **段C: 家の外形カタログと建物配置の焼き込み。** 部品カタログが外形の要約を書き出し、エディターの建物配置が骨格方式の家の個体としてチャンクへ焼かれ、ゲームの中に建つ。建物エディターを待たずに家を置けるよう、建物定義は当面手書き(部品カタログの組み立ての宣言)でよい
- **段D: 質感1=部品のテクスチャ化。** テクスチャのAI生成と収蔵の運用(決定4)を立ち上げ、BlenderPython側で部品へUVと材質を割り当てて再収蔵する。エンジン側は既存経路のため工事なし。**Blender側の作業が主で、段A〜Cと並行できる**
- **段E(完了): 質感2=地形の地表材質の描画。** スプラットと層テクスチャを読む地形描画のシェーダー工事。**道の絵(泥・舗装)の検証はこれとセットである**(材質の塗り分けが描けないと道が絵に出ない)。裁定と段割りは`_doc/設計/マルチマテリアルと材質境界.md`「地表の層の重ね合わせ」が持つ。到達点は次のとおりである
  - **E-1(完了)**: 地表材質の重み格子のソース形式と、エディターチャンクソースの形式版2。編集サーバーが塗られていないチャンクにも重みの格子を書き出し、コンパイラが素材として読んで増分の鍵の依存一覧へ載せる。形式版1のチャンクソースは「先頭の層だけの重み」へ写して読める。生成器の版を6へ上げた
  - **E-2(完了)**: 地表層テクスチャ集(実行時アセット種別5・形式版1)。層がどのエンジン材質名を参照するかはエディターのマテリアル台帳が正本であり、名前から索引への解決は焼く側の1回で終える。検査用の純色タイル4枚を`assets/surface_layer_textures/`へ置いた
  - **E-3(完了)**: マテリアルデータの地表の層の重ね合わせの枝・シーン内容の版6・材質テクスチャ役割の追加(重み+層4で8つ)・材質レコードのバイト長の96への拡大。版5から版6への昇格は恒等であり、既存4世界の生成物80本のうちシーン68本は形式版の4バイトだけが変わり、目録4本とカタログ3本はバイト単位で一致した
  - **E-4(完了)**: シェーディングモデルの2枝目一式とシェーダー。`cargo xtask surface-layer-draw`が、照明を切った条件で4層の純色の世界を本番のストリーミング経路で描き、四隅の色が層のタイルの純色と一致すること・南北と東西の向きが正しいこと・チャンクの境目で混ざり物が出ないこと・validationが0件であることを機械判定する。半テクセル寄せと南北の入れ替えのどちらを外しても落ちることを実測で確かめた
  - **E-5(完了)**: 文書の実装一致(アセット実行時形式の版6・マルチマテリアルと材質境界の2枝目)
- **段F: 散布の設定の接続。** エディターの散布の設定→散布の宣言の変換
- **段G: 建物エディター。** 決定3の具体設計の裁定→設計→実装。editor_web の隣に立てる(編集UIの資産と配信の口を再利用する)
- **段H: 定点。** 文書の実装一致・各正本への到達点の追記・外部台帳の棚卸し

段A・段Cの外形カタログ・段D(Blender側)は互いに並行できる。段Bまでが最優先であり、段C以降の順序はオーナーが絵を見てから入れ替えてよい。

## この作戦がやらないこと

- カスタムスクリプティング(ゲームオブジェクトへの振る舞いの付与)の設計。別の作戦として、歩ける世界の上で要求が立ってから行う
- 8km大規模世界へのエディター編集の適用。エディターの現在の規模(1024メートル四方)で閉ループを作り、規模の拡張は別の判断にする
- シャドウ超過の是正(札#138のコメント359)。ただし段Bで実プレイ入口ができると着手条件が成立するため、絵で気になったときに独立作業として起こす
