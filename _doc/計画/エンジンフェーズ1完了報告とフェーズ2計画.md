# エンジンフェーズ1完了報告とフェーズ2計画

この文書は、M0〜M11の完了定義、能力・品質・性能・変更容易性、将来方式へ変更できる設計状態を総点検し、エンジンフェーズ2の実装順序と完了定義を管理する生存型文書である。

## 結論

M0〜M10で予定した描画、アセット、アニメーション、布、流体技術検証は実装済みである。M11では再現可能な固定ベンチ、CPU区間計測、RAM・VRAM連続計測、文書と実装の照合を完了した。

GPU処理は固定シーンで合計0.7276msであり、16.6ms予算の4.4%だった。CPU側フレーム開始間隔は中央値16.7057msだったが、p95は33.2550msだった。区間計測では遅延がフェンス待機に集中し、エンジンのフレームデータ準備、コマンド記録、GPU処理量は律速でなかった。したがって、フェーズ1の処理性能には余裕があるが、実表示時刻に基づく60fps安定は証明できていない。現在のGPUは提示時刻取得用の`VK_EXT_present_timing`を公開する一方、採用中のash 0.38は同拡張を型として提供しないため、対応するVulkan仕様とash更新を審査してから計測入口を追加する。

M11の設計監査では、PBR固定だったマテリアル型を判別共用体へ修正した。大座標、VR、GPUメモリ確保は従来文書の記述より未完成だったため、フェーズ2の先行依存へ移した。代表シーンの物量を1倍・10倍・100倍へ変える計測は、現行の1メッシュ・1マテリアル構造では実施できない。合成的な頂点複製では代替せず、シーン表現を複数描画対象へ拡張した直後に測る。

OW0では複数描画対象、非空の描画視点一覧、大域座標とカメラ相対座標の型境界、GPUメモリ台帳、ライト方針、フレーム構成を実装した。固定カメラで1・10・100対象を生成する計測入口も追加し、M11で未計測だった描画対象数に対する基礎特性を取得した。

### 品質

標準検証は`cargo xtask verify`で規約検査、型検査、Clippy、単体・境界テストを実行する。実機境界は`cargo xtask smoke`の7ステージがVulkan validationと読み戻し画素を判定する。フェーズ1の最終差分では両方が成功し、全7ステージでVulkan validationのエラー・警告は0件だった。

### 性能

固定ベンチの全値は `_doc/計測/M11_2026-07-23.md` に記録した。主要な判断値は次のとおりである。

- GPU合計は0.7276msで、16.6ms予算の4.4%だった。
- シーン描画は0.3574msで4.0ms予算の8.9%、シャドウは0.0770msで2.0ms予算の3.8%、ポストプロセスは0.2268msで1.5ms予算の15.1%だった。
- CPU側フレーム開始間隔はp50 16.7057ms、p95 33.2550ms、p99 34.8432ms、25ms超過率8.75%だった。
- フェンス待機はp99 33.5772msだった。フレームデータ準備、画像取得、記録・送信・提示はいずれもp99 1.5ms未満だった。
- 3600フレーム連続実行では、初期安定化後にRAMと専用VRAMのフレーム数比例増加を検出しなかった。

p50、p95、p99は、標本の50%、95%、99%がその値以下に収まる百分位点である。p99は悪化側1%の境界を表す。

表面流は128×128セルで1.9166ms、シミュレーション予算の63.9%だった。全対全探索SPHは512粒子で3.8503msとなり、予算を128.3%消費した。フェーズ2では非同期コンピュートより先に空間ハッシュで近傍候補数を抑える。

OW0完了時の固定quad計測では、1→100対象でシーンGPU時間が0.0506→0.0755ms、シャドウが0.0287→0.0353ms、CPUの記録・送信・提示平均が0.1482→0.1784msだった。GPUメモリ確保数は10→604件へ増え、対象ごとに6件増える線形構造だった。現在の描画発行は予算内であり、間接描画やバインドレスディスクリプタへ着手しない。OW4では植生、可視判定、LODを含む代表シーンで1・10・100倍を正式に記録する。

### 変更容易性

- Rustは539ファイル・25,305行、Slangは22ファイル・1,437行であり、全`.rs`と`.slang`が100行以下である。
- 単体・境界テストの`#[test]`は107件ある。
- Windows向け通常依存グラフは84パッケージ版で、自前6、外部78である。直接依存の層境界はconformが検査する。
- M11監査時のキャッシュ済み`cargo check --workspace`は0.22秒だった。ホットリロードの監視間隔は500msである。
- ashとunsafeはblitz_render内部に限定され、blitz_engine、blitz_math、blitz_sim、blitz_appはunsafeを禁止する。
- M11で既知だったフレーム構成とライト方針のblitz_render固定は解消した。OW0第1〜10段でVulkanメモリ台帳、複数描画対象、非空の描画視点一覧、大域座標の型境界、blitz_engineが宣言するライト方針とフレーム構成を実装した。

### 大座標とVR

大座標対応は部分的である。OW0第8段でf64の大域ワールド位置からカメラ原点を引き、f32のカメラ相対位置へ狭める型境界を実装した。アセット頂点、描画対象変換、スキニングデータは現在も局所f32座標であり、OW3でkm級の実データへ境界を適用する。

VR対応も部分的である。入力インテントはデバイスから分離済みで、OW0第7段では`フレーム描画入力`を非空の描画視点一覧へ変更した。現在のスワップチェーン提示先は単一視点だけを実行し、複数視点入力は型付きエラーにする。本番UIのワールド空間配置は未実装であり、UI0では画面空間とワールド空間を同じUI描画結果の配置方法として扱う。OpenXR統合自体は優先順位が決まった時点で別マイルストーンにする。

## フェーズ2の依存関係

オープンワールド系統が全系統の基礎になる。主要な依存関係は次のとおりである。

```text
OW0 シーン・描画契約
 ├─ OW1 アセットコンパイラ ─ OW2 ストリーミング ─ OW3 地形・大座標 ─ OW4 植生・物量性能 ─ OW5 空・遠距離影
 ├─ SIM0 シミュレーション実行基盤 ─ SIM1 流体・布・髪・軟体の品質向上
 └─ OW1完了後 ┬─ CHAR0 キャラクター構成
               └─ UI0 本番UIと文字

CHAR0 + UI0 + OW4 ─ COMBAT0 戦闘支援能力
```

OW0とは、後続機能が共有するシーン・描画・座標・メモリの契約を確定したマイルストーンである。OW0で方針をblitz_engineへ移し、単一描画対象の制約を除いたため、後続系統は同じ描画経路を拡張できる。

## フェーズ2の詳細マイルストーン

### OW0: シーン・描画契約

- 複数の描画対象、変換、マテリアル、ライトを保持する最小シーン表現をblitz_engineへ置く。エンティティと部品の汎用管理方式を先に一般化せず、オープンワールドに必要な識別子、所有チャンク、描画抽出だけを型にする。
- blitz_engineがフレームのパス構成とライト方針を宣言し、blitz_renderはレンダーグラフの実行能力だけを提供する。
- フレーム入力を非空の視点一覧にし、単一視点も要素数1として表現する。
- f64ワールド座標、f32カメラ相対座標、GPU境界の変換を別の型にする。
- Vulkanメモリ確保の窓口を一元化し、現在数、デバイス上限、用途別確保量を標準出力へ出せるようにする。
- 1倍・10倍・100倍の描画対象を同じカメラで生成できる`cargo xtask`のベンチ入口を登録する。
- DoD: フレーム構成とライト定数がblitz_renderから除かれ、2つ以上の描画対象を1フレームに描ける。視点数、座標変換、メモリ確保数がテキストで取得でき、既存7ステージのスモークが同じ判定で通る。

完了: OW0第1〜10段でGPUメモリ台帳、複数描画対象、非空の描画視点一覧、大域座標とカメラ相対座標の型境界、blitz_engineが所有するライト方針とフレーム構成を実装した。`cargo xtask object-bench`は二対象の左右分離、1・10・100対象の描画発行数、GPU時間、CPU時間、GPUメモリ、視点数1、座標変換、実際のフレーム段階列をテキストで判定する。完了定点ではDoDをすべて充足し、評価軸、性能9軸、生存型文書を実装へ合わせた。次の主経路はOW1のアセットコンパイラと実行時形式である。

### OW1: アセットコンパイラと実行時形式

- ソースglTFと画像を検証し、版付きのエンジン内バイナリ、安定ID、依存関係、メタデータをカタログへ出力する。
- テクセル密度、近接ジオメトリ品質、LODの有無、依存循環、予算超過を機械検査する。
- 実行時のblitz_engineは汎用glTF・画像デコードを行わず、カタログとエンジン内形式だけを読む。ホットリロードはソース変更から再コンパイルして同じ安定IDを差し替える。
- DoD: 同じ入力からバイト単位で同じ出力が得られ、壊れた入力は型付きエラーになる。DamagedHelmetとFoxが実行時形式から既存スモークを通り、glTFとimageの依存はアセットコンパイラ側だけに限定される。

### OW2: チャンクストリーミング

- 世界をチャンクIDで分割し、プレイヤー位置と先読み範囲から必要集合を計算する。
- 読込、デコード済みデータの準備、GPU転送を非同期化し、フレーム境界でシーンへ反映する。解除はGPU使用完了後に行う。
- RAM・VRAMの予算、優先度、退避順序を明示し、要求集合が予算を超えた場合は型付きの縮退結果を返す。
- DoD: 固定経路を移動する自動実行でチャンクの読込・解除順が再現し、30分相当の反復でもRAM・VRAMが予算内に収まる。メインスレッドのp99と転送量を標準出力へ記録できる。

### OW3: 地形LODとカメラ相対描画

- チャンク化した高さ地形を距離別LODで描き、境界の亀裂を防ぐ。洞窟や張り出しは通常メッシュとして同じシーンへ載せ、地形形式へ無理に統一しない。
- f64ワールド位置からカメラ原点を引き、f32カメラ相対座標だけをGPUへ渡す。
- DoD: 原点からkm級の固定地点でもカメラ近傍の頂点揺れが画素判定の許容範囲内で、LOD境界に亀裂がない。カメラ移動時のストリーミングと地形更新を同じ自動実行で検査できる。

### OW4: 植生、大量インスタンス、物量スケーリング

- 同一メッシュとマテリアルを共有するインスタンス群、可視判定、距離別LODを追加する。
- 1倍・10倍・100倍でCPU時間、GPUパス時間、描画発行数、RAM、VRAMを測る。CPU描画発行が律速なら間接描画を導入し、資源束縛が律速ならバインドレスディスクリプタを導入する。測定前に両方を同時導入しない。
- DoD: 物量3点の結果と最初の折れ点を追記専用記録へ残し、折れ点の支配要因を特定する。採用した最適化は、その支配要因の改善を同じ条件で示す。

### OW5: 空、時間帯、遠距離シャドウ

- 大気散乱による空、太陽方向と露出の時間変化、複数距離帯の方向光シャドウをシーン方針として追加する。
- DoD: 時刻入力から空・主光源・影が決定的に変化し、地形の近距離から遠距離まで影の解像度予算を維持する。パス追加後もGPU合計が更新済み予算内に収まる。

### SIM0: シミュレーション実行基盤

- 空間ハッシュとは、空間を固定寸法のセルへ分け、近傍セルだけを衝突・流体計算の候補にする索引である。blitz_simへCPU参照実装、blitz_renderへGPU構築・検索パスを追加する。
- シミュレーション結果と描画頂点のゼロコピー共有を維持し、描画と依存しない計算区間を測る。空間ハッシュ後も3.0msを超える場合だけ計算専用キューを追加する。
- DoD: SPHの512・1024・2048粒子で全対全探索より計算量の伸びが改善し、近傍集合をCPU参照計算と照合できる。キュー変更を行う場合は重なり時間をテキストで示す。

### SIM1: 流体・布・髪・軟体の品質向上

- 表面流は横方向を含む保存的な二次元流束、二重バッファ、UV継ぎ目処理、濡れシェーディングを実装する。
- SPHは空間ハッシュ、複数ワークグループ、表面再構成を実装する。MPMは雪、塑性、強い粘弾性が要求された場合だけ再評価する。
- 布はセルフコリジョンと多層衣装、髪はガイド毛の物理と補間描画、軟体はスキニング姿勢とXPBD変形の合成をそれぞれ独立した素材として追加する。
- DoD: 各方式は専用の固定条件、予算、品質判定を持つ。共通ソルバ抽象へ方式を押し込まず、使わない方式のGPU資源とパスを生成しない。

### CHAR0: キャラクター構成

- パーツメッシュ、共有骨格、ブレンドシェイプ、マテリアルを1体のキャラクターへ合成し、安定IDの組として保存する。
- DoD: パーツ交換後も骨格とアニメーションが1体として動き、不要な重複スキニングを行わない。保存した構成をアセットコンパイラ経由で再現できる。

### UI0: 本番UIと文字

- 文字のシェーピング、改行、禁則処理は採用審査を通した成熟実装へ委ね、グリフアトラスとGPU合成を自作する。
- リテインドモードの要素ツリー、レイアウト、スタイル、入力を開発用eguiと分離する。UI描画結果は画面空間とワールド空間の両方へ配置できる。
- DoD: 日本語と英語の混在文、折返し、禁則、入力焦点を自動検査でき、同じUIツリーを画面空間とワールド空間へ描画できる。

### COMBAT0: 戦闘支援能力

- VFX、アニメーション状態遷移、ルートモーション、IK（Inverse Kinematics。手足の目標位置から関節姿勢を逆算する方式）、ヒットストップ、空間クエリ、戦闘カメラ、敵集団のアニメーションLODを追加する。
- DoD: 代表戦闘シーンを固定入力で再生し、キャラクター数1倍・10倍・100倍のCPU・GPU時間と描画発行数を記録する。ゲーム固有の攻撃ルールはblitz_gameに置き、エンジンは再利用可能な能力だけを持つ。

## 推奨着手順序

主経路はOW0、OW1、OW2、OW3、OW4、OW5の順で進める。SIM0はOW0完了後、CHAR0とUI0はOW1完了後に主経路と並行できる。SIM1はSIM0の実測後、COMBAT0はCHAR0、UI0、OW4の完了後に着手する。

フェーズ2の完了時には、地形、植生、キャラクターと衣装物理、空と時間帯、本番UI、ストリーミングを1つの代表シーンへ載せる。固定カメラと固定移動経路でGPU・CPU時間、1倍・10倍・100倍の物量、RAM・VRAM、Vulkan validationをテキスト記録し、能力・品質・性能・変更容易性の4系統を再監査する。
