# ユビキタス言語

Blitzdrache0 の全ドキュメント・全コード・全会話で使う語彙の定義。DDDの原則に従い、
同じ概念には常に同じ語を使い、定義の変更はこのファイルの改訂として行う。
コード上の日本語命名もこの語彙に一致させる。

## 製品構造の語彙

- **エンジン**: ゲームの実行時に動く基盤ソフトウェア全体（blitz_render + blitz_engine）。
  シーン・アセット・マテリアルを保持し、毎フレーム描画する。エディタの存在を知らない
- **エディタ**: エンジンが読むデータ（シーン・アセット）を人間やAIが作成・編集するための
  別アプリケーション。エンジンに依存するが、エンジンはエディタに依存しない（一方向依存）
- **ゲームロジック**: 対象ゲーム固有のルール・進行・挙動を書く層。エンジンの利用者。
  将来 blitz_game クレートとして分離する
- **コンポジションルート**: 全レイヤーの依存を配線し、フレーム内の実行順序を一元支配する
  唯一の場所（blitz_app）。ロジックを書いてはならない
- **RHI** (Render Hardware Interface): 複数のグラフィックスAPI（Vulkan/Metal/D3D12/
  コンソール固有API）の差異を吸収する抽象層。本プロジェクトでは当面作らない（計画書参照）

## 描画の語彙

- **レンダラー**: blitz_render クレートの通称。レンダーグラフ + リソースシステムから成る
- **レンダーグラフ**: フレーム内のGPU処理を「パス」の依存グラフとして宣言し、
  同期バリアの配置を宣言から自動導出する仕組み。エンジン中核の型安全層
- **パス**: レンダーグラフの1ノード。入力リソースと出力リソースを宣言して
  GPU作業（描画・計算）を1まとまり実行する単位
- **リソースシステム**: GPUリソース（バッファ・テクスチャ・サンプラー）の生成・寿命・
  破棄を管理する仕組み。「このエンジンの使い方」だけを型として露出する
- **スワップチェーン**: 画面提示用の画像の連なり。ウィンドウとVulkanの接続点
- **提示（present）**: 完成したフレーム画像をスワップチェーンへ送り表示させること
- **提示モード**: 提示とディスプレイのリフレッシュの同期方式（FIFO/MAILBOX/IMMEDIATE）。
  フレーム時間の主たる供給源。`参照: _doc/設計/イベントループとフレームペーシング.md`
- **フレームインフライト**: CPUが次フレームを準備する間にGPUが前フレームを描く並行状態。
  同時進行フレーム数ぶんのリソース多重化と同期が必要になる
- **validation layer**: Khronos公式のVulkan誤用検出層。開発時は同期検証込みで常時有効、
  リリースで外す
- **AA（アンチエイリアシング）**: ポリゴン縁のギザギザ（エイリアシング）を消す技法の総称
- **MSAA** (Multisample Anti-Aliasing): ピクセル内を複数サンプル判定してギザギザを消す
  GPU標準装備のAA。1フレーム内で完結し、副作用が少ない
- **TAA** (Temporal Anti-Aliasing): 過去フレームの描画結果を混ぜ合わせてギザギザを消すAA。
  高品質だが導入するとレンダラー全域（投影・履歴バッファ・モーションベクタ）に波及し、
  動くものがにじむ。トゥーンの線とVRに不向き
- **forwardレンダリング**: 物体を描くその場でライティングまで計算する方式。
  構成が単純でMSAA・VRと相性が良い。本プロジェクトの当面の方式
- **deferredレンダリング**: 全物体の材質情報を一旦G-bufferへ書き出し、後からまとめて
  ライティングする方式。大量光源に強いが、G-bufferのレイアウトに
  シェーディングモデルが物理的に焼き付く
- **G-buffer**: deferredレンダリングで使う、画面全ピクセルの材質・法線・深度等を
  格納する中間バッファ群
- **深度バッファ**: ピクセルごとの奥行きを記録し、手前の面が奥の面を正しく隠す
  （深度テスト）ための画像。カラーと並ぶもう1枚の描画先
- **プッシュ定数** (push constant): コマンドバッファに直接埋め込む小容量（128バイト保証）の
  シェーダー入力。ディスクリプタセットが不要で、フレームインフライトの多重化対象にもならない
- **ディスクリプタセット**: シェーダーからバッファ・テクスチャを参照するための束。
  本プロジェクトではテクスチャが必要になるM3で導入する
- **ユニフォームバッファ**: シェーダーが読む定数データ（カメラ・ライト等）を置くバッファ。
  プッシュ定数（128バイト保証）に収まらない量はこちらに置き、
  フレームインフライトごとに多重化する
- **法線マップ**: 表面の細かな凹凸を、ジオメトリを増やさずピクセル単位の法線として
  テクスチャに焼いたもの。接線空間で表現される
- **接線（タンジェント）**: UVのU方向に沿った表面ベクトル。法線・従法線と組で
  接線空間（TBN）を作り、法線マップの値をワールドの向きへ変換するのに使う
- **オービットカメラ**: 注視点を中心に回り込む視点操作方式。マウスドラッグで回転、
  ホイールで距離を操作する

## 実行モデルの語彙

- **フレームループ**: 「1フレーム分の処理をいつ始めるか」を決めるループ。
- **ループ所有権**: 最外周の `loop` 文を誰が書くか（winit所有 / 自前所有）。
  フレームの「中」ではなく「間」（ペーシング・ホスト統合）だけに効く
- **フレーム内実行順序**: 1フレーム内で入力確定→世界更新→描画内容抽出→描画を
  どの順で行うか。コンポジションルートが明示的に支配し、ループ所有権とは独立
- **capability**: GPU・プラットフォームごとの機能の使える/使えない。Vulkanの
  feature/extension/limits 問い合わせで実行時に判別する
- **視点（ビュー）**: 1フレームで描画するカメラの1つ。通常は1、VRステレオでは2以上。
  視点数は型として第一級で扱い、1をハードコードしない
- **入力インテント**: 「移動したい」「決定した」等、デバイス非依存の操作意図。
  ゲームロジックはインテントのみを消費し、デバイス→インテント写像は入力層に隔離する
- **late-latch**: フレーム処理の可能な限り遅い時点で入力（VRでは頭部姿勢）を採取し、
  入力から表示までの遅延を縮める技法

## 数学DDDの語彙

- **フレーム型**: 位置・変換がどの座標系（ワールド/ローカル/ビュー/クリップ）に属するかを
  幻影型パラメータで区別した型。`変換<ローカル, ワールド>` の合成は型が合うときだけ通り、
  座標系の混同・行列の掛け順ミスをコンパイルエラーにする
- **単位型**: 長さ（メートル）・時間（秒）・角度（ラジアン/度）を型で区別した量。
  次元の合わない加算を禁じる。単位の集合は基底次元上の自由アーベル群をなす
- **幻影型（phantom type）**: 実行時表現を持たず型検査にだけ使われる型パラメータ。
  `#[repr(transparent)]` と併用すればゼロコスト
- **GPU境界（生型境界）**: フレーム型・単位型を外して生の数値（glam型・バイト列）に戻す
  唯一の場所。blitz_renderのリソース層に置く

## オープンワールドの語彙

- **ストリーミング**: 世界をチャンクに分割し、プレイヤー位置に応じて必要な部分だけを
  非同期にロード/アンロードする仕組み
- **LOD** (Level of Detail): 距離に応じてメッシュ・テクスチャ・処理の詳細度を落とし、
  物量と性能を両立させる技法
- **カメラ相対レンダリング**: f32精度の崩壊（原点から数km）を避けるため、描画時に
  座標をカメラ原点基準へ移してからGPUに渡す方式。オープンワールドの必須技法
- **アセットコンパイラ**: エンジンでもエディタでもない第3の独立したオフラインCLIツール層。
  ソースアセット（glTF・画像）を検証・変換・カタログ登録してエンジン内バイナリ形式を
  出力する。rustcとIDEの類比でrustcに相当し、エディタ・CI・AIエージェントの誰からでも
  同じものを呼べる。旧称: アセット取り込みパイプライン
- **カタログ**: アセットコンパイラが管理する、安定ID・メタデータ・依存関係・版の台帳。
  エンジンは実行時に安定IDでカタログを引いてアセットをロードする

## キャラクターシミュレーションの語彙

- **XPBD** (Extended Position-Based Dynamics): 位置を直接補正する方式の実時間物理手法。
  布・髪・軟体を1つのソルバで統一的に扱える現代の主流。GPUコンピュートで回す
- **セルフコリジョン**: 布などが自分自身と衝突する判定。これが無いと床に落ちた服が
  「くちゃっ」とならない。計算コストの主因
- **ストランドヘア**: 毛束や骨ではなく毛1本単位で物理と描画を行う髪表現。
  ガイド毛だけ物理で解き、残りは補間する
- **スプリングボーン**: 骨をバネで揺らす簡易の揺れ物近似。XPBDの下位互換で、
  本エンジンでは採用しない
- **表面流（テクスチャ空間流体）**: 肌や物体表面のUV上で液滴の流れを解く手法。
  体を伝う液体は3D流体でなくこれで解くのが現代の正解
- **SPH** (Smoothed Particle Hydrodynamics): 粒子法の流体シミュレーション。
  少量流体・粘性表現の候補手法
- **MPM** (Material Point Method): 粒子と格子を併用し、雪・粘体・弾性体を統一的に
  扱える手法。少量粘性流体の候補だが実時間化は研究隣接
- **非同期コンピュート**: 描画と並行してGPUの計算キューでシミュレーション等を走らせ、
  GPUを飽和させる技法。生Vulkanの明示的マルチキューで実現する
- **キャラクタークリエイト**: パーツ単位のメッシュ合成・骨共有・ブレンドシェイプ合成に
  よるキャラクターのカスタマイズ機能
- **シミュレーション基盤層**: XPBDソルバ・拘束・粒子系・空間ハッシュ等、手法の数学だけを
  持つ汎用層。特定の絵を知らない。将来の blitz_sim クレート
- **ドメイン表現層**: 「唾液」「この服」等、見せたい絵ごとに基盤層の部品を組み上げた
  ゲーム固有の1表現。汎用化せず、ゲームごとに書き捨ててよい
- **介入（intervention）**: プレイヤーイベントをシミュレーションへ流し込む型付きの値。
  インパルス / 拘束の着脱 / 放出 / パラメータ場の書き換え の4種。
  `参照: _doc/設計/シミュレーション層.md`

## 文字とUIの語彙

- **シェーピング**: 文字コード列を実際の字形（グリフ）の並びに変換する処理。
  合字・カーニング・多言語対応を含む。成熟クレートに任せる領域
- **禁則処理**: 行頭に句読点が来ない等の日本語組版規則。改行処理の一部
- **グリフアトラス**: 一度ラスタライズした字形をテクスチャに貯めて使い回すキャッシュ。
  文字描画のGPU統合部分で、ここは自作する
- **即時モードUI**: 毎フレームUIを描き直すコードを書く方式（egui等）。開発用UIに使う
- **リテインドモードUI**: 要素ツリーを保持しレイアウトを解決する方式。ブラウザのDOMと
  同じモデルで、本番ゲームUIはこの方式（ツリー + フレックスボックス + スタイル）を採る

## データの語彙

- **シーン**: 描画対象の世界の構造（何がどこにどの姿勢で存在するか）
- **アセット**: ディスク上の外部データ（glTF、テクスチャ画像、シェーダーソース）。
  読み込んでエンジン内表現に変換して使う
- **マテリアル**: 表面の見た目を決めるパラメータ（PBRならベースカラー・金属度・粗さ等）と
  シェーダーの組
- **安定ID（アセットID）**: アセットをファイルパスでなく論理名で参照するための識別子。
  パス直接参照を禁じることで、アセットの移動・変換・カタログ化を後付け可能に保つ
- **ステージングバッファ**: CPUから書けるホスト可視の中継バッファ。ここへ書いた内容を
  GPU専用（デバイスローカル）のバッファ・画像へ転送コマンドでコピーする
- **ミップマップ**: テクスチャの縮小版の連なり。遠くの面に縮小版を使うことで
  ちらつき（エイリアシング）と帯域を抑える
- **サンプラー**: シェーダーがテクスチャを読むときの補間・繰り返し・ミップ選択の設定
- **仮想リソース**: レンダーグラフ構築時に宣言する論理リソース。ハンドルで参照し、
  実体（Vulkanハンドル）はグラフ実行器だけが知る。外部持ち込みとグラフ管理の2種
- **ストレージバッファ**: シェーダー（特にコンピュート）から読み書きできる汎用バッファ。
  ユニフォームバッファと違い大容量・書き込み可
- **タイムスタンプクエリ**: GPUのコマンド列に時刻記録を差し込み、パス間の実行時間を
  計測する仕組み。クエリプールに結果が蓄積され、CPUから読み戻す
- **シェーダー**: GPU上で実行されるプログラム。本プロジェクトはSlangで書き、
  ビルド時にSPIR-Vへコンパイルする
- **SPIR-V**: Vulkanが受け取るシェーダーの中間バイナリ形式（Khronos標準）。
  Slangソースからslangcでコンパイルして得る。32bit語単位のバイト列
- **パイプライン（グラフィックスパイプライン）**: シェーダー・固定機能設定・出力形式を
  束ねたGPU描画のコンパイル済み実行単位。Vulkanでは描画前に構築しておく必要がある
- **ホットリロード**: 実行中のアプリを止めずに資産（シェーダー・アセット・パラメータ）を
  差し替える仕組み。`参照: _doc/設計/開発ループとコンパイル時間.md` Tier 0

## 開発思想の語彙

- **理論値志向**: デバイスの理論性能との乖離を最小化する方針。計測なしの推測最適化は含まない
- **汎用性の税金**: 使わない機能が払わせる実行時・保守時コストと、互換性維持の足枷。
  能力を持つこと自体は税金ではなく、クレート分離で「能力は持つが使わないゲームは
  払わない」が成立する。本プロジェクトが払わないと決めたのはこのコストの方
- **2段構え**: 汎用かつ最高性能の基盤層（手法の数学とGPU実行。特定の絵やゲームを
  知らない）+ ドメインを達成する特別な仕組みの層、というエンジンの基本構造
- **可能性を閉じない原則**: 将来の選択肢を不可能にする設計・計画判断を早期に行わない
  最上位原則。各「扉」はこの原則の個別事例。`参照: _doc/計画/開発計画.md` 判断基準0
- **扉**: 将来採用するかもしれない技術・方式について「後から採用可能な状態」を指す語。
  「扉が開いている」= その方式へ変更した場合の影響範囲が現在の構造で局所化されており、
  可逆であること。「扉を閉める」= 不可逆な決定によりその方式の採用を事実上不可能にすること。
  開発計画の絵の様式3条件・大座標・VRの各項目がこの語の適用例
- **負債・残骸**: 誤った設計判断や放置により残った修正されるべきコード。
  AI駆動では「抱え続ける理由が消える」ため、発見したら書き直す
- **封じ込め**: unsafe と ash型を blitz_render の実装内部に閉じ込め、上位層に漏らさない規律
- **狭い型安全層**: 汎用のVulkan安全化ではなく「このエンジンの使い方」だけを型にすることで、
  実行時追跡コストゼロで安全性を得る設計方針
