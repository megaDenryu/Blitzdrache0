# OW2計測記録 2026-07-25

この文書は追記専用の計測記録である。OW2第4段時点の固定ベンチ、長時間実行、描画対象数スケーリングの実測値と、M11で観測した33ms級遅延が再現するかどうかの判定を残す。

M11の記録では固定ベンチのp99が34.8432ms、25ms超過が480標本中42回だった。OW1完了時の同じコマンドではp99 18.5580ms、25ms超過0回であり、2つの記録が食い違っていた。単発の実行結果からは実行間分散と実在する欠陥を区別できないため、今回は同一条件の反復実行で再現率を測る。

- CPU: 12th Gen Intel Core i7-12700KF
- GPU: NVIDIA GeForce RTX 3080 Ti、ドライバー32.0.15.9621
- 主表示: 3840×2160、60Hz。ほかに Meta Virtual Monitor（1920×1080、60Hz）と Virtual Desktop Monitor の仮想ディスプレイドライバーが登録済みである
- OS: Windows 11 Home 10.0.26200
- ビルド: リリースビルド。5回の反復を始める前に `cargo build --release -p blitz_app` を完了させ、反復中は他のビルド・テスト・型検査を実行していない
- コード状態: OW2第4段完了時点。ワーキングツリーに未コミットのソース変更はない

## 33ms級遅延の再現性判定

- 25ms超過が発生した実行は5回中5回である。回数は40回から57回の範囲で、最小でも480標本の8.33%を占める
- p99の最小値は33.8084ms（1回目）、最大値は35.0483ms（4回目）で、実行間の振れ幅は1.2399msである
- M11時点の値（p99 34.8432ms、25ms超過42回）は再現した。p99は5回すべてが33.8ms以上であり、25ms超過回数もM11の42回を挟む40〜57回の範囲に収まる
- OW1完了時の値（p99 18.5580ms、25ms超過0回）は5回中1回も再現しなかった

したがって、この5回を採った時間帯では33ms級の遅延は例外ではなく、M11の記録を単発の実行間分散として片付けることはできない。

注意: 「常態である」とまでは言えない。同日の後半に採った実測では、同一コードの同一コマンドで25ms超過が0回から156回まで動いた。詳細は下の「計測条件の分離と、機材側の時間変動」節に記す。この機材のこの指標は時間帯をまたいだ比較に使えないため、本節の5回は「その時間帯の性質」として読むこと。OW1完了時の0回も、外れ値ではなく脱落0の時間帯を引いた結果である可能性がある。

暫定の許容値としてフレーム間隔p99 20ms以下を親から与えられている。5回ともこれを13.8ms以上超過した。ただしこの20msはどの設計文書にも定義されていない今回限りの判定値であり、恒久の予算としては未制定である。基準の制定は親が行う。

この節の計測時点では、CPU側フレーム開始間隔がFIFO提示待ちを含むため実表示時刻での更新脱落と同一ではない、という留保を付けていた。この留保は下の「実表示時刻の計測(VK_KHR_present_id + VK_KHR_present_wait)」節で解消した。同節の実測により、33ms級のフレーム間隔は実表示の更新脱落を伴うと確定した。

残る留保として、今回の環境には仮想ディスプレイドライバーが2つ登録されており、Windowsデスクトップ合成の提示スケジューリングへの影響を排除できていない。M11・OW1の計測時に同じ構成だったかは記録がなく確認できない。

## OW2のRAM・VRAM予算の観測可能性

OW2第4段で追加したRAM・VRAM予算は、今回の3つの計測のいずれにも現れない。理由は実装の接続状態にある。

- `crates/blitz_engine/src/streaming/memory_budget.rs` の予算型と縮退結果は `crates/blitz_engine/src/lib.rs` から再公開されているだけで、`crates/blitz_app` を含む他クレートに呼び出し側が存在しない
- `_doc/設計/チャンクストリーミング.md`「メモリ予算と縮退」のとおり、チャンクごとの見積量をカタログメタデータと実読込量から作る接続は次段の作業である。実GPU転送、フレーム境界反映、GPU使用完了後の解除も未接続である
- 検証は単体テストだけで行われている。ストリーミング関連の `#[test]` は17件、うち予算に関するものは4件である

したがって「予算に対する現在の消費が何%か」という問いに答えられる実行時の値は現時点では存在しない。今回記録できたのは、予算機構が追加されても既存経路のVulkanメモリ確保統計（21件・97.63MiB）と長時間実行のRAM・VRAM推移が変わっていないという事実だけである。予算の効果を測れるのは、見積量と台帳の接続が入り、固定経路を移動する自動実行が動く段以降である。

## 実表示時刻の計測(VK_KHR_present_id + VK_KHR_present_wait)

上の節の留保「CPU側フレーム開始間隔が実表示の脱落と同一ではない」を決着させるため、提示に単調増加のIDを付けて表示完了を待つ計測を実装し、実表示間隔を直接測った。

### 拡張と機能の対応可否

判定方法は2段階である。第1段は`vkEnumerateDeviceExtensionProperties`による拡張名の列挙、第2段は`VkPhysicalDeviceFeatures2`へ機能構造体を連結した機能フラグの読み取りである。実行時の判定は `crates/blitz_render/src/vulkan/present_timing/support.rs` が行い、独立確認としてVulkan SDK 1.4.321.1の`vulkaninfo`出力とも突き合わせた。

| 拡張 | 物理デバイスの拡張一覧 | 機能フラグ | 採否 |
|---|---|---|---|
| VK_KHR_present_id | あり(revision 1) | `presentId` = true | 採用した |
| VK_KHR_present_wait | あり(revision 1) | `presentWait` = true | 採用した |
| VK_GOOGLE_display_timing | 無し | 該当構造体なし | 使えない |
| VK_EXT_full_screen_exclusive | あり(revision 4) | 該当構造体なし | 今回は使っていない |
| VK_EXT_swapchain_maintenance1 | あり(revision 1) | 未確認 | 今回は使っていない |

`VK_EXT_present_timing`はドライバー側にはrevision 3で存在する。採用中のash 0.38.0+1.3.281がこの拡張の型を提供しないため今回は使っていない。ただし実表示時刻の計測自体は上表の2拡張で成立しており、「ash 0.38では実表示時刻を測れない」という従来の記述は誤りである。ashが型を持たないのは`VK_EXT_present_timing`という特定の1拡張だけである。

`VK_GOOGLE_display_timing`は当初の第1候補だったが、この環境のNVIDIAドライバー(596.21、Windows表記32.0.15.9621)が拡張自体を公開していないため使えない。列挙されるGOOGLE拡張は`VK_GOOGLE_hlsl_functionality1`と`VK_GOOGLE_user_type`の2つだけである。

### 計測方法とドライバーの実測挙動

各提示に1から始まる単調増加のIDを付け、次フレームの先頭で`vkWaitForPresentKHR`を呼ぶ。待機対象はこれから提示するIDの2つ前に固定し、まずtimeout=0で判定し、`VK_TIMEOUT`が返ったときだけ待機上限1秒で待ち直す。観測ごとに、前回観測からの間隔と、その観測のために描画ループを止めていた停止時間を記録する。

このドライバーでは`vkWaitForPresentKHR`にtimeout=0を渡しても即座には返らず、表示まで停止してから`VK_SUCCESS`を返した。5回の実行すべてで停止時間が1.0ms未満の観測は0件であり、停止時間のp50は16.06〜16.20msだった。待機対象を1つ古いIDへ変えても停止時間のp50は16.15msで変わらなかった。したがって、この環境ではこの拡張を使う限り計測は非停止にできない。観測時刻はすべて表示完了時刻であり、間隔は実表示間隔として読める。

### 計測が測定対象へ与えた影響

この計測は`vkWaitForPresentKHR`で表示まで描画ループを止める。停止時間のp50は16.06〜16.20msであり、レンダラーのフェンス待機は5回ともp99 0.0351ms以下へ下がった。停止が実在することと、律速点がフェンス待機から待機呼び出しへ移ることは直接観測できた事実である。

一方、この停止がフレーム間隔分布を悪化させるかどうかは確認できなかった。当初は計測ありの5回(25ms超過83〜99回)を上の「固定ベンチの5回反復」の記録(40〜57回)と比べて約2倍の悪化と判断したが、これは異なる時間帯に採った値どうしの比較であり誤りだった。条件を交互に入れ替えた3対の実測では、計測ありのほうがむしろ同等以下だった。

### 計測条件の分離と、機材側の時間変動

計測を`--report-frame-times`へ相乗りさせると、既存の性能時系列と同じ条件が二度と採れなくなる。そのため専用フラグ`--report-display-timing`へ分離し、指定が無いときは VK_KHR_present_id と VK_KHR_present_wait を論理デバイスで有効化しない。`cargo xtask bench`は素の条件、`cargo xtask bench-display-timing`は計測ありの条件である。

分離後の`cargo xtask bench`が記録済みの25ms超過40〜57回へ戻るかを確認したところ、戻らなかった。同一コード・同一コマンドで、時間帯によって次のように動いた。

| 実行の並び | 25ms超過 | 平均 |
|---|---:|---:|
| 分離直後の5回 | 6回、154回、4回、156回、142回 | 16.6325〜16.6668ms |
| 拡張を強制的に無効化した3回 | 0回、0回、0回 | 16.6717〜16.6742ms |
| 拡張の有効化を要求で切り替えた後の3回 | 81回、75回、85回 | 19.0690〜19.6293ms |
| 交互実行の素の条件3回 | 65回、76回、0回 | 16.6757〜19.2458ms |

同一コードで0回から156回まで動くため、この機材のこの指標は時間帯をまたいだ比較に使えない。記録済みの40〜57回へ戻るかどうかも判定できない。拡張の有効化そのものが提示ペーシングを変えるかどうかも、この変動から分離できなかった。当初は「拡張を有効化するだけで悪化する」と判断しかけたが、根拠は異なる時間帯の比較だけであり、確定した事実として扱わない。

平均値には手がかりがある。25ms超過が0回に近い実行の平均は16.63〜16.67msで、これは480フレームがちょうど480回のvblankで表示された状態、すなわち脱落0を意味する。平均が18.7〜19.6msの実行では、480提示に対して消費したvblankが480を大きく超えており、実際に脱落している。つまりこの機材は、脱落がまったく起きない時間帯と、毎秒4〜6回以上脱落する時間帯を行き来している。原因は特定していない。

### 脱落回数を計測なしで求める算術

計測に依存しない算術でも脱落回数を確かめられる。FIFOでは1つの提示は1つのvblankでしか表示されないため、480提示に要した実時間をvblank周期で割った数から480を引いた差が、新しい画像が届かなかったvblankの回数になる。vblank周期は各実行のp50を用いる。この計算は測定窓の端にある先読みの深さを無視するが、先読みはスワップチェーン画像数で数フレーム分に限られ、差の実測値0.6〜0.9秒に対して十分小さい。

上の「固定ベンチの5回反復」の記録では、この差は41.6回、54.4回、37.6回、42.6回、38.9回であり、記録されている25ms超過44回、57回、40回、40回、43回に対して差は最大4.1回である。実表示計測ありの5回では82.8回、97.6回、90.6回、82.0回、88.0回となり、実測の83回、99回、91回、83回、89回に対して差は最大1.4回である。この一致は、25ms超過回数がそのまま脱落vblank数として読めることを示す。

### 判定

CPU側フレーム開始間隔の33ms級の遅延は、実表示の更新脱落を伴う。計測を有効にした5回では、CPU側の25ms超過と実表示間隔の25ms超過が最大1回差で一致し、実表示間隔のp95・p99は33.35〜33.41msだった。これは60Hz表示の1更新をまるごと落としたことを意味する。「CPU側フレーム開始間隔は提示待ちの分布にすぎずコマ落ちではない」という可能性は、この実測により否定された。

この対応は片方向ではない。フラグ分離後の交互実行3対では、CPU側25ms超過35回・45回・0回に対して実表示25ms超過が34回・45回・0回であり、脱落が起きない時間帯(0回)でも両者が一致した。CPU側に超過が出れば実表示にも同数出て、CPU側が0なら実表示も0である。

計測を有効にしない条件では、上記の算術により脱落回数を求められる。「固定ベンチの5回反復」の記録では1回の実行あたり37.6〜54.4回であり、480フレームで8.63〜8.92秒の実行であるから毎秒4.4〜6.1回の脱落に相当する。ただしこの脱落率はこの機材の常態ではなく、脱落0の時間帯も存在する(「計測条件の分離と、機材側の時間変動」節)。

## この記録から確定した判断

- 33ms級のフレーム間隔遅延は、ある時間帯では5回中5回で再現する。ただしこの機材は脱落0の時間帯と毎秒4〜6回脱落する時間帯を行き来しており、同一コードで25ms超過が0回から156回まで動く。脱落率をこの機材の常態として扱ってはならない。原因は特定していない
- 遅延は5回ともフェンス待機に集中し、エンジンのCPU処理量とGPU処理量では説明できない。GPU合計は0.31msでフレーム予算16.6msの1.9%である
- 描画対象数を1から100へ増やしても25ms超過は増えず、遅延は描画負荷に依存しない
- 33ms級の遅延は実表示の更新脱落を伴う。提示待ちの分布ではない。根拠は「実表示時刻の計測(VK_KHR_present_id + VK_KHR_present_wait)」節の実測である
- 実表示時刻の計測はash 0.38のままで実装できる。従来「ash 0.38では測れない」としていた記述は誤りであり、型が無いのは`VK_EXT_present_timing`だけである
- 残る課題は脱落の原因である。GPU処理量でもエンジンのCPU処理量でも説明できないため、次はWindowsデスクトップ合成側の要因(仮想ディスプレイドライバー2つの登録を含む)と提示経路の設定を対象にする

## 追記: 単一画面条件での再計測(2026-07-27)

ユーザーがWindowsの表示設定を変更し、デスクトップの有効表示を1画面へ切り替えた。`Screen.AllScreens`の実測で有効表示が1件であることを確認している。ただしWMI上はiiyama PLX2783HとAcer VG280Kの両モニタが`Active=True`のまま見えており、ケーブルは接続されたまま表示だけが1画面化された状態である。仮想ディスプレイドライバー2つの登録も変わっていない。

エンジン開発の帰結: 単一画面のこの条件ではp99が20ms以下に収まり、60fps安定の証明に使える計測環境が初めて手に入った。以後の性能時系列の計測は表示構成を記録してから行う。複数画面での脱落はエンジンのコードでは制御できない合成側の挙動であり、対処するならフルスクリーン排他や提示モードの変更というゲーム側の提示戦略の話になる。これはOW3以降の性能計測の前提条件として扱う。
