# OW2計測記録 2026-07-25

この文書は追記専用の計測記録である。OW2第4段時点の固定ベンチ、長時間実行、描画対象数スケーリングの実測値と、M11で観測した33ms級遅延が再現するかどうかの判定を残す。

M11の記録では固定ベンチのp99が34.8432ms、25ms超過が480標本中42回だった。OW1完了時の同じコマンドではp99 18.5580ms、25ms超過0回であり、2つの記録が食い違っていた。単発の実行結果からは実行間分散と実在する欠陥を区別できないため、今回は同一条件の反復実行で再現率を測る。

## 共通の実行環境

- CPU: 12th Gen Intel Core i7-12700KF
- GPU: NVIDIA GeForce RTX 3080 Ti、ドライバー32.0.15.9621
- 主表示: 3840×2160、60Hz。ほかに Meta Virtual Monitor（1920×1080、60Hz）と Virtual Desktop Monitor の仮想ディスプレイドライバーが登録済みである
- OS: Windows 11 Home 10.0.26200
- ビルド: リリースビルド。5回の反復を始める前に `cargo build --release -p blitz_app` を完了させ、反復中は他のビルド・テスト・型検査を実行していない
- コード状態: OW2第4段完了時点。ワーキングツリーに未コミットのソース変更はない

## 33ms級遅延の再現性判定

- 25ms超過が発生した実行は5回中5回である。回数は40回から57回の範囲で、最小でも480標本の8.33%を占める
- p99の最小値は33.8084ms（1回目）、最大値は35.0483ms（4回目）で、実行間の振れ幅は1.2399msである
- M11時点の値（p99 34.8432ms、25ms超過42回）は再現した。p99は5回すべてが33.8ms以上であり、25ms超過回数もM11の42回を挟む40〜57回の範囲に収まる
- OW1完了時の値（p99 18.5580ms、25ms超過0回）は5回中1回も再現しなかった

したがって、この計測環境では33ms級の遅延は例外ではなく常態であり、OW1完了時の記録のほうが5回に0回の頻度で観測された外れ値である。M11の記録を実行間分散として扱うことはできない。

暫定の許容値としてフレーム間隔p99 20ms以下を親から与えられている。5回ともこれを13.8ms以上超過した。ただしこの20msはどの設計文書にも定義されていない今回限りの判定値であり、恒久の予算としては未制定である。基準の制定は親が行う。

留保として、CPU側フレーム開始間隔はFIFO提示待ちを含むため、実表示時刻での更新脱落と同一ではない。この値だけから「60Hz表示に対して毎秒約2.5回のコマ落ちがある」とは断定しない。実表示時刻の判定には提示時刻を取得する計測入口が必要であり、`_doc/計画/エンジンフェーズ1完了報告とフェーズ2計画.md`「結論」のとおり、採用中のash 0.38が対応拡張を型として提供しないため未着手である。また、今回の環境には仮想ディスプレイドライバーが2つ登録されており、Windowsデスクトップ合成の提示スケジューリングへの影響を排除できていない。M11・OW1の計測時に同じ構成だったかは記録がなく確認できない。

## GPU時間の水準変化

シーン描画はM11の0.3574ms、OW1完了時の0.4073msに対し、今回は0.1487〜0.1605msだった。M11比で2.2〜2.4倍、OW1比で2.5〜2.7倍速い。合計もM11の0.7276ms、OW1の0.8932msに対して0.3105〜0.3329msである（4回目を除く）。

同じ `cargo xtask bench` の同じシーンで測っているため、シーン内容と解像度は変わっていない。この差の原因は特定していない。GPUの電力状態やクロックの実行時変動も候補に含まれ、コード変更による改善だと断定しない。判定するには、同一コミットで複数回測る比較か、GPUクロックを固定した計測が要る。

## OW2のRAM・VRAM予算の観測可能性

OW2第4段で追加したRAM・VRAM予算は、今回の3つの計測のいずれにも現れない。理由は実装の接続状態にある。

- `crates/blitz_engine/src/streaming/memory_budget.rs` の予算型と縮退結果は `crates/blitz_engine/src/lib.rs` から再公開されているだけで、`crates/blitz_app` を含む他クレートに呼び出し側が存在しない
- `_doc/設計/チャンクストリーミング.md`「メモリ予算と縮退」のとおり、チャンクごとの見積量をカタログメタデータと実読込量から作る接続は次段の作業である。実GPU転送、フレーム境界反映、GPU使用完了後の解除も未接続である
- 検証は単体テストだけで行われている。ストリーミング関連の `#[test]` は17件、うち予算に関するものは4件である

したがって「予算に対する現在の消費が何%か」という問いに答えられる実行時の値は現時点では存在しない。今回記録できたのは、予算機構が追加されても既存経路のVulkanメモリ確保統計（21件・97.63MiB）と長時間実行のRAM・VRAM推移が変わっていないという事実だけである。予算の効果を測れるのは、見積量と台帳の接続が入り、固定経路を移動する自動実行が動く段以降である。

## この記録から確定した判断

- 33ms級のフレーム間隔遅延は5回中5回で再現する常態であり、実行間分散として片付けられない。OW1完了時の0回のほうが外れ値である
- 遅延は5回ともフェンス待機に集中し、エンジンのCPU処理量とGPU処理量では説明できない。GPU合計は0.31msでフレーム予算16.6msの1.9%である
- 描画対象数を1から100へ増やしても25ms超過は増えず、遅延は描画負荷に依存しない
- 次に必要なのは原因の推定ではなく、実表示時刻を取得する計測入口である。CPU側フレーム開始間隔だけでは、この遅延が実際のコマ落ちなのか提示待ちの分布なのかを区別できない
