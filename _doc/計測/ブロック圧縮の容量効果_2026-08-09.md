# ブロック圧縮の容量効果の計測(2026-08-09)

テクスチャをブロック圧縮で格納したときに実行時形式のバイト数がどれだけ減り、その代償として絵がどれだけ変わるかの公式記録である。着手順4のアセット形式整備が達成した効果の記録にあたる。方式の設計正本は`_doc/設計/テクスチャのブロック圧縮と縮小段生成.md`にある。本記録はログ型であり追記のみ。

## この計測が測るもの、測らないもの

**測るのは容量と絵の差の2つだけであり、GPU時間は1つも測っていない。** ブロック圧縮が動かすのはテクスチャが占めるバイト数と、GPUがテクスチャを標本するときに読む帯域である。パスの構成も画素あたりの計算も1つも変えないため、フレーム予算(`_doc/計画/評価軸.md`の3.1節)へ新しい行が立たない。予算の行が立たない変更にGPU費用の計測日を割り当てないのは、判定に使う枠が存在せず、測った値を突き合わせる先が無いためである。

帯域の側の効果が数字に出るのは、テクスチャの総量がGPUのキャッシュに収まらない物量になったときである。この記録の対照の素材は512画素の板2枚であり、その条件を満たさない。したがって帯域の計測は、実アセットが到着して容量予算(評価軸の3.5節)を制定する日と同じ日に行う。

## 条件と由来

- 2026-08-09、入口は`cargo xtask texture-compression`である。この入口が唯一、テクスチャ格納方針として`ベースカラーのブロック圧縮`を渡す
- 値の初出はコミット12bf0fc時点の実行であり、本記録を書くときにコミット11f8a51で再実行して、下の全ての値が1桁も違わずに再現することを確かめた。11f8a51と12bf0fcの差は文書だけである
- 再実行の時点で追跡済みの変更は無い。未追跡はリポジトリ直下のテキストと`architecture.html`等の6件であり、いずれも構築の入力でも実行の入力でもない
- 機材はNVIDIA GeForce RTX 3080 Tiである。**容量の値は機材に依存しない**(焼くのはCPUの整数演算だけであり、決定性の契約が同じ入力から同じバイト列を保証する)。**絵の差の値は機材固有でありうる**(BC1の復号の補間には実装ごとの差が許容されるためである。参照: `_doc/設計/アセット実行時形式.md`「シーン内容の版5」)

## 公式値1: 実行時形式の容量

同じ世界を`全てRGBA8`と`ベースカラーのブロック圧縮`の2つの方針で焼き、シーンの実行時形式のファイル長を比べた値である。

| 世界 | 非圧縮 | ブロック圧縮 | 倍率 |
|---|---:|---:|---|
| 対照の板(512画素のグラデーションと雑音の2枚) | 2,098,251バイト | 350,795バイト | 5.98分の1 |
| DamagedHelmet(2048画素のテクスチャ3枚) | 51,216,009バイト | 37,235,097バイト | 1.37分の1 |

### 対照の板が6分の1に近い値になる理由

**符号化そのものは8分の1であるが、ファイルの上では約6分の1になる。** BC1は4x4の画素16個を8バイトへ写すため、RGBA8の64バイトに対して8分の1である。一方ブロック圧縮の格納は縮小段の全段をファイルが持つ規約であり、段ごとに縦横が半分になる列の合計は原寸の約3分の4になる。8を3分の4で割った6が、この2つを合わせた倍率である。

対照の板の実測はこの算術と1バイトも食い違わない。512画素の1枚は非圧縮1,048,576バイトに対しブロック圧縮の全10段が174,776バイトであり、段の宣言長がu64で9段ぶん増える72バイトを差し引くと1枚あたりの節約は873,728バイト、2枚で1,747,456バイトになる。実測の差(2,098,251から350,795を引いた値)はちょうど1,747,456バイトである。

### DamagedHelmetが1.37分の1にとどまる理由

**初版のスコープがベースカラー1枚だけを圧縮するためである。** この世界のテクスチャは2048画素が3枚(ベースカラー・金属粗さ・法線マップ)であり、圧縮されるのはそのうち1枚だけである。残る2枚は非圧縮のRGBA8のまま各16,777,216バイトを占め続ける。

内訳も算術と一致する。ベースカラー1枚は16,777,216バイトから全12段の2,796,216バイトへ落ち、段の宣言長が11段ぶん増える88バイトを差し引くと節約は13,980,912バイトである。実測の差(51,216,009から37,235,097を引いた値)はちょうど13,980,912バイトであり、他の2枚が1バイトも減っていないことをこの一致が示す。

**したがって1.37という倍率は符号化の性能ではなくスコープの帰結である。** 3枚とも圧縮したときの倍率は、この記録では測っていない。法線をBC5で、金属粗さを別の形式で持つ設計は第2弾であり、着手条件は実アセットで品質かVRAMのどちらかが実際に問題になったときである(設計正本「第2弾の着手条件」)。

## 公式値2: 絵の差

同じ構図で2つの方針の絵を描き、読み戻し画像の成分差を採った値である。単位は8ビットの符号値であり、平均は全画素の全成分にわたる平均である。度数分布は画素ごとの3成分の差の最大を区分へ入れた画素数である。

| 素材 | 最大 | 平均 | 差のある画素 | 度数分布(0以上/1以上/2以上/4以上/8以上/16以上) |
|---|---:|---:|---|---|
| 滑らかなグラデーションの板 | 5 | 1.078 | 449,733 / 460,800 | 11,067 / 154,597 / 271,963 / 23,173 / 0 / 0 |
| 決定的な雑音の板 | 200 | 31.970 | 460,764 / 460,800 | 36 / 512 / 2,147 / 6,112 / 22,179 / 429,814 |
| DamagedHelmet(画面全体) | 47 | 0.055 | 59,802 / 921,600 | 861,798 / 46,817 / 10,938 / 1,843 / 186 / 18 |

- **グラデーションと雑音の値には判定値が課されている。** グラデーションは最大12符号値・平均3.000符号値を上界、雑音は平均60.000符号値を上界とし、さらに圧縮が効いていることの反証として下界も持つ(`xtask/src/texture_compression/judgment.rs`)。上の実測はいずれもその内側にある
- **DamagedHelmetの値には判定値が無い。** この絵の合否は目視で決める定義であり(設計正本「判断h」)、機械が見るのは2枚の絵が実際に食い違うことだけである。目視は2026-08-09に合格した
- **雑音の板の差が大きいのは、BC1が1ブロックのRGBを2つの端点が張る線分上の4点で表す形式だからである。** 隣り合う画素の色が無関係に散らばる素材は1本の線分へ載らず、端点の探索を改良しても解けない。この板を対照へ置いたのは、実アセットの見た目を代表させるためではなく、符号化器が壊れたときに真っ先に値が動く素材を用意するためである
- **グラデーションの板の差が小さいのは、同じ理由の裏返しである。** 滑らかに変化する色は線分へよく載るため、残る誤差は端点をRGB565へ丸めたときの段差だけになる
- **DamagedHelmetの平均が0.055符号値と小さいのは、画面の大半が背景でありヘルメットが画面の一部しか占めないためである。** 平均を絵の品質の指標として読んではならない。破綻の有無を見るのは目視の側であり、この平均は背景の画素で薄まった値である

## この計測が主張しない範囲

- **実アセットの容量予算は制定していない。** 容量予算(評価軸の3.5節)の暫定値の再制定は、Blenderの路線が供給する実アセットが到着した計測の日に一度で行う。暫定値の付け替えを2回やらないためである
- **VRAMの実測は採っていない。** 上の値はファイルのバイト数であり、GPUへ載った後の専用VRAMの実測ではない。ブロック圧縮の画像はGPU上でも圧縮されたままであるから両者は一致する見込みであるが、この記録は確かめていない
