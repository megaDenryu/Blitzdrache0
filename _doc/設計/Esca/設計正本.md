# ゲームEsca 設計正本

本書は、ゲーム『Esca（エスカ）』のコンセプト、テーマ、世界観、登場人物の役割、ゲーム性の核、およびコード上の型契約を定める設計正本である。

本書の記述は、トップダウンでゲームドメインから最下層のエンジン構造まで完全に開発者の理解とコントロールを取り戻すための指針として運用する。

---

## 1. 開発方針と制作スタイル

### 1.1 理解負債の解消と主客の回復
過去のAI駆動開発で生じた「動くが人間が中身を把握しきれていない」という理解負債を解消する。
AIに一度に大量のコードを書かせず、人間によるマイクロマネジメント（1ステップあたり最大3ファイル修正）のもと、1つ1つのドメイン概念、型、状態遷移を完全に理解・納得しながらトップダウンで組み上げる。

### 1.2 ゲームドメイン主導の垂直貫通
汎用的な仕組みを先行して作らない。まず「Escaというゲームを成立させるための具体的な型とルール」を定義し、それを表現するために必要な分だけエンジン機能（数学、物理、地形、描画）を順次接続していく。

---

## 2. コンセプトとテーマ

### 2.1 一行コンセプト
戦火または混乱に陥った国を、戦えない旅行者として脱出を目指す逃亡・旅行劇。

### 2.2 テーマ
「観察と判断による生存」と「旅路の記憶」。
暴力による問題解決を行えない非戦闘員が、世界の状況を観察し、限られた情報と移動手段をやりくりして危機をかいくぐる。

### 2.3 ゲーム性の核
1. **非戦闘の行動選択**:
   敵を倒すのではなく、観察、交渉、回避、逃走によって事態に対処する。
2. **状況の推移と経路の変動**:
   旅の進行や時間経過に伴い、安全だった道が封鎖され、あるいは新たな抜け道が開かれ、迂回や引き返しが発生する。
3. **旅路の記録**:
   単なる脱出作業にとどまらず、旅の中で見聞きした土地の風景や人々の営みを心と記録に残していく。

---

## 3. 登場人物の基本構図

### 3.1 主人公（プレイヤーの分身・観察対象）
- **属性**: 非戦闘員の旅行者。
- **能力**: 武器を扱って敵を制圧する力は持たない。周囲の状況を注意深く見極める観察力、地形を把握する移動の判断力を武器とする。
- **意志**: 恐怖に震えながらも、生き延びること、そしてこの旅の真実を見届ける意志を持つ。

### 3.2 相棒（旅路を共にする存在）
- **属性**: 旅の途中で合流する同行者。
- **関係性**: 一方的に守られるだけの存在でも、主人公の都合で動く道具でもない。互いの事情と意志を尊重し合いながら、同じ目的地を目指して協力する対等なパートナー。

## 4. プログラミング設計オントロジーと規約

### 4.1 役割マーカー（直交概念）

共通の設計マーカーと射影・解釈の役割の newtype は、依存ゼロの共通設計語彙クレート `crates/blitz_design` に在る。Esca はそれを使い、遷移関数と遷移結果だけを `crates/blitz_esca/src/ontology.rs` に持つ。

- **`MDTO`**: 参照や内部可変性を所有せず、値として複製・受け渡しできる純粋な所有データ。境界を越える転送にも状態の正本にも使う。参照・ポインタ・内部可変性を持たず、`Clone` を持つ（`blitz_design`）。
- **`M状態`**: 実在し保持・遷移されるゲーム状態。純粋な所有データでもあり、必ず `MDTO` を実装する（`M状態: MDTO`。`blitz_design`）。
- **`Mコマンド`**: 主体の意志・選択肢・命令。純粋な所有データでもあり、必ず `MDTO` を実装する（`Mコマンド: MDTO`）。必ず `enum` で定義し、`&mut self` を持たない（`blitz_design`）。
- **`Mイベント`**: ある状態遷移によって成立した過去の事実を表す値。状態の正本として次の遷移へ継続保持するものではなく、`遷移結果` 等を通じて消費者へ配送される（配送後にログ・リプレイ・ネットワーク・監査履歴等へ保存されることは妨げない）。イベントは、その遷移によって実際に成立した事実だけを生成しなければならない。`enum` を必須とせず、1件の事実を `struct` で表してもよい。純粋な所有データでもあり、必ず `MDTO` を実装する（`Mイベント: MDTO`。`Clone` はそこから継承する）。`&mut self` を持たない（`blitz_design`）。名前が過去形であることと1フレームで破棄されることは機械で判定しない。
- **`M規則`**: 遷移からは読み取り専用で与えられる規則値（内部可変性を持たず、型自身に可変メソッドを持たない純粋な所有データ。値の置き換えを型では禁じない）。純粋な所有データでもあり、必ず `MDTO` を実装する（`M規則: MDTO`）。必ず `struct` で定義し、`&mut self` を持たない（`blitz_design`）。
- **`M入力`**: デバイス境界の生シグナル（キー・マウス・ボタン）。ゲーム意味論を持たず、純粋な所有データでもあり、必ず `MDTO` を実装する（`M入力: MDTO`。`blitz_design`）。
- **`M設定`**: 起動時に決まり、工程からは読み取り専用で与えられる設定値（内部可変性を持たず、型自身に可変メソッドを持たない純粋な所有データ。値の置き換えを型では禁じない）。純粋な所有データでもあり、必ず `MDTO` を実装する（`M設定: MDTO`）。`&mut self` を持たない（`blitz_design`。Esca に利用例はまだ無い）。
- **`M射影関数<状態: M状態, 射影DTO: MDTO>`**: `&状態 -> 射影DTO` の一方向観測計算を包む境界付きの newtype（`blitz_design`）。
- **`M解釈関数<入力: M入力, コマンド: Mコマンド>`**: `&入力 -> コマンド` の純粋解釈計算を包む境界付きの newtype（`blitz_design`）。
- **`M遷移関数<状態: M状態, コマンド: Mコマンド, 規則: M規則, イベント: Mイベント, 失敗: std::error::Error>`**: `(&状態, &コマンド, &規則, 経過時間) -> Result<遷移結果<状態, イベント>, 失敗>` を導出する純粋計算を包む境界付きの newtype（`blitz_esca`）。時間は、`blitz_math::秒` を有限かつ0以上に検証して包んだ値オブジェクト `経過時間`（`crates/blitz_esca/src/elapsed_time.rs`）で受ける。遷移は数値の表現範囲を超えたとき失敗を返す。有限な入力の積和でも `f32` は ±∞ になりうるため、遷移の結果の有限性は検証で閉じる（前提で置かない）。Esca の遷移の失敗は `旅行者の現在地の生成の失敗` である。
- **`遷移結果<状態, イベント>`**: 遷移関数が返す、次の状態と出来事の一覧の名前付きの組（`blitz_esca`。4.4「多重戻り値の生タプル禁止」に合わせる）。型引数に `M状態`・`Mイベント` の境界を持つ意味型であり、境界は構造体の利用箇所でコンパイラが強制する。

`M遷移関数` と `遷移結果` を `blitz_design` へ上げないのは、オーナーの裁定「計算モデルまで固定しているため、まず Esca 側で直してから昇格を判断する」による。

法則の検査主体(コンパイラが強制する法則と `cargo xtask conform` の設計オントロジーの検査が見る法則の分担)と検査器の保証範囲は、`_doc/設計/設計オントロジー.md` が正本として持つ。`Mコマンド: MDTO` 等の supertrait の Relation はコンパイラが保証し、conform は役割の実装から型の定義を解決してその定義に純粋データ規約を当てる(`impl MDTO for` をどのファイルに書くかは法則ではない)。関数の役割は境界付きの newtype であり、型を使った時点でコンパイラが型引数の境界を強制する。迂回できる綴りは無い。Esca 側は `const _: M遷移関数<...> = M遷移関数::生成する(旅行者の現在地::歩行を遷移する);` の静的宣言で、遷移関数が役割を満たすことをコンパイラに確かめさせる。参照: `_doc/設計/設計オントロジー.md`。

### 4.2 引数DTOと名前付き引数様式（2026-09-18制定）
同型プリミティブが並ぶ引数は順序誤認の温床となるため禁止する。引数はDTO構造体に束ね、構造体リテラル直接呼び出し `(要求DTO { ... }).メソッド()` で呼び出す。

### 4.3 抽象度レイヤーの純化（シナリオ層とメカニズム層の混在禁止、2026-09-18制定）
シナリオ層（進行フロー、画面の流れ、テストケース等）に、それを支える道具・構文解析・計算・固有データ型等のメカニズム層を同居させてはならない。100行未満であっても抽象度レイヤーの異なるコードの同居を禁止し、メカニズムは独立モジュール（`syntax_checker.rs` 等）として分離してシナリオ層を純化する。

### 4.4 身体規則と空間制約の直交化と結果DTOの原則（2026-09-18制定）
1. **多重戻り値の生タプル禁止**: 計算結果は `(f32, f32, bool)` 等の生タプルで返さず、名前付きフィールドを持つ結果DTO（`境界制限結果` 等）として型定義する。
2. **身体規則と空間制約の直交化**: 主体の運動能力（`歩行の規則`）の中に世界の壁や障害物を埋め込まない。空間制約（`移動可能範囲`）は独立した環境の値として定義し、遷移時に `Option<移動可能範囲>` で合成する（無制限を表すマジックナンバーの全廃）。
3. **歩行方向の検証付き生成**: 歩く向きは長さ1を不変条件に持つ値オブジェクト `歩行方向` で表し、生成の口は `キーボード歩行入力` からの導出（相殺で零なら向き無し）だけにする。同型の `f32` を2つ並べる生成の口は置かない。
4. **移動可能範囲の検証付き生成**: `移動可能範囲` は公開フィールドの指定DTO `移動可能範囲の指定` を `検証する()` して初めて得る。最小が最大を超える軸と、有限な数値でない端（NaN または無限大）は型付きエラー `移動可能範囲の生成の失敗` で拒む。
5. **状態と出来事の分離と、事実でない出来事の禁止**: `遷移結果<状態, イベント>` で状態と出来事を分離する。`歩行を開始した`・`立ち止まった` のような状態変化のイベントは、前の状態と次の状態の差を判定できる場合だけ生成する。状態の差を表現できない段階では事実でないイベントを発行しない（2026-09-18 再レビュー）。語彙と法則E1〜E8の正本は `_doc/設計/設計オントロジー.md` である。
6. **歩行の規則の速さと経過時間の検証付き生成**: `歩行の規則::生成する` は速さが有限かつ0以上でなければ型付きエラー `歩行の規則の生成の失敗` で拒む（速さ0を許すのは、静止は `旅行者の意図::静止` で表すため速さ0の規則が矛盾を生まないことによる）。`歩行を遷移する` の経過時間は値オブジェクト `経過時間` で受け、`経過時間::生成する` が有限かつ0以上でない値（負・NaN・無限大）を型付きエラー `経過時間の生成の失敗` で拒む。遷移関数の側は経過時間を検査しない（型が保証する）。
7. **遷移の結果の有限性は検証で閉じる**: `旅行者の現在地` のフィールドは私有であり、`生成する` と `平行移動する`（変位 `移動の変位` を足して同じ検証を通す）だけが現在地を作る。遷移は数値の表現範囲を超えたとき失敗を返す。有限な入力の積和でも `f32` は ±∞ になりうるため、遷移の結果の有限性は検証で閉じる（前提で置かない）。`歩行を遷移する` の戻り値は `Result<遷移結果<旅行者の現在地, 旅行者の出来事>, 旅行者の現在地の生成の失敗>` である。

## 5. 今後の展開ステップ

1. **第1段階**: 主人公の基本移動と観察（歩行、移動可能境界との接触・衝突出来事、入力解釈、視界）。
   - 歩行移動（`旅行者の現在地::歩行を遷移する`）および描画位置射影（`旅行者の現在地::描画位置を射影する`）
   - キーボード生入力解釈（`キーボード歩行入力::歩行入力を解釈する`）
   - 世界法則としての移動可能限界（`移動可能範囲`）と衝突出来事（`障害物に遮られた`）。出来事は境界に当たったときと見回したとき（`周囲を観察した`）だけ生じ、歩き始めと立ち止まりは現在地だけの状態では差を判定できないため出来事にしない
2. **第2段階**: 地点と経路の表現（どこへ向かうか、どの道が通れるか）。
3. **第3段階**: 状況の進行とイベント（何が起き、どう選択肢を選ぶか）。
4. **第4段階**: エンジンへの接続（カメラ、高さ場地形、描画への配線）。
