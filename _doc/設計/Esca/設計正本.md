# ゲームEsca 設計正本

本書は、ゲーム『Esca（エスカ）』のコンセプト、テーマ、世界観、登場人物の役割、ゲーム性の核、およびコード上の型契約を定める設計正本である。

本書の記述は、トップダウンでゲームドメインから最下層のエンジン構造まで完全に開発者の理解とコントロールを取り戻すための指針として運用する。

---

## 1. 開発方針と制作スタイル

### 1.1 理解負債の解消と主客の回復
過去のAI駆動開発で生じた「動くが人間が中身を把握しきれていない」という理解負債を解消する。
AIに一度に大量のコードを書かせず、人間によるマイクロマネジメント（1ステップあたり最大3ファイル修正）のもと、1つ1つのドメイン概念、型、状態遷移を完全に理解・納得しながらトップダウンで組み上げる。

### 1.2 ゲームドメイン主導の垂直貫通
汎用的な仕組みを先行して作らない。まず「Escaというゲームを成立させるための具体的な型とルール」を定義し、それを表現するために必要な分だけエンジン機能（数学、物理、地形、描画）を順次接続していく。

---

## 2. コンセプトとテーマ

### 2.1 一行コンセプト
戦火または混乱に陥った国を、戦えない旅行者として脱出を目指す逃亡・旅行劇。

### 2.2 テーマ
「観察と判断による生存」と「旅路の記憶」。
暴力による問題解決を行えない非戦闘員が、世界の状況を観察し、限られた情報と移動手段をやりくりして危機をかいくぐる。

### 2.3 ゲーム性の核
1. **非戦闘の行動選択**:
   敵を倒すのではなく、観察、交渉、回避、逃走によって事態に対処する。
2. **状況の推移と経路の変動**:
   旅の進行や時間経過に伴い、安全だった道が封鎖され、あるいは新たな抜け道が開かれ、迂回や引き返しが発生する。
3. **旅路の記録**:
   単なる脱出作業にとどまらず、旅の中で見聞きした土地の風景や人々の営みを心と記録に残していく。

---

## 3. 登場人物の基本構図

### 3.1 主人公（プレイヤーの分身・観察対象）
- **属性**: 非戦闘員の旅行者。
- **能力**: 武器を扱って敵を制圧する力は持たない。周囲の状況を注意深く見極める観察力、地形を把握する移動の判断力を武器とする。
- **意志**: 恐怖に震えながらも、生き延びること、そしてこの旅の真実を見届ける意志を持つ。

### 3.2 相棒（旅路を共にする存在）
- **属性**: 旅の途中で合流する同行者。
- **関係性**: 一方的に守られるだけの存在でも、主人公の都合で動く道具でもない。互いの事情と意志を尊重し合いながら、同じ目的地を目指して協力する対等なパートナー。

## 4. プログラミング設計オントロジーと規約

### 4.1 役割マーカー（直交概念）

共通の設計解釈マーカーと射影・解釈の役割の newtype は、依存ゼロの共通設計語彙クレート `crates/blitz_design` に在る。Esca はそれを使い、遷移関数と遷移成功結果と遷移失敗結果を `crates/blitz_esca/src/ontology.rs` に、遷移パラメータを `crates/blitz_esca/src/transition_parameter.rs` に持つ。

- **`M不変データ`**: 参照や内部可変性を所有せず、値として複製・受け渡しできる純粋な所有データ。境界を越える転送にも状態の正本にも使う。参照・ポインタ・内部可変性を持たず、`Clone` を持つ（`blitz_design`）。
- **`M状態`**: 実在し保持・遷移されるゲーム状態。純粋な所有データでもあり、必ず `M不変データ` を実装する（`M状態: M不変データ`。`blitz_design`）。
- **`Mコマンド`**: 主体の意志・選択肢・命令。純粋な所有データでもあり、必ず `M不変データ` を実装する（`Mコマンド: M不変データ`）。必ず `enum` で定義し、`&mut self` を持たない（`blitz_design`）。
- **`Mイベント`**: ある状態遷移によって成立した過去の事実を表す値。状態の正本として次の遷移へ継続保持するものではなく、`遷移成功結果` 等を通じて消費者へ配送される（配送後にログ・リプレイ・ネットワーク・監査履歴等へ保存されることは妨げない）。イベントは、その遷移によって実際に成立した事実だけを生成しなければならない。`enum` を必須とせず、1件の事実を `struct` で表してもよい。純粋な所有データでもあり、必ず `M不変データ` を実装する（`Mイベント: M不変データ`。`Clone` はそこから継承する）。`&mut self` を持たない（`blitz_design`）。名前が過去形であることと1フレームで破棄されることは機械で判定しない。
- **`M規則`**: 遷移からは読み取り専用で与えられる規則値（内部可変性を持たず、型自身に可変メソッドを持たない純粋な所有データ。値の置き換えを型では禁じない）。純粋な所有データでもあり、必ず `M不変データ` を実装する（`M規則: M不変データ`）。必ず `struct` で定義し、`&mut self` を持たない（`blitz_design`）。
- **`M解釈前の入力`**: `M解釈関数` がゲームの意味（`Mコマンド`）へ読み替える前の、ゲーム意味論を持たない入力。純粋な所有データでもあり、必ず `M不変データ` を実装する（`M解釈前の入力: M不変データ`。`blitz_design`）。下位の `M生入力` か `M中間入力` のどちらか1つもあわせて名乗る（2026-09-27 のオーナー裁定。旧称は `Mデバイス生入力`）。
- **`M生入力`**: 入力の出どころに固有の形のままの、読み替え前の入力（キーの押下・パッドの軸の値など。`M生入力: M解釈前の入力`。`blitz_design`）。`M中間入力` と排他である。Esca の例はキーの押下状態 `キーボード歩行入力` である。
- **`M中間入力`**: 入力の出どころに依らない形へ整えた、まだゲーム意味論を持たない入力。誰が作ったかによらず、値の形で決まる（`M中間入力: M解釈前の入力`。`blitz_design`）。`M生入力` と排他である。Esca に利用例はまだ無い（`blitz_game` の `確定済みの操作入力` がこれを名乗る）。
- **`M観測`**: 状態・処理・評価について、その対象の正本や因果を構成せず、外部から観察するために導出された不変データ。必ず `M不変データ` を実装する（`M観測: M不変データ`。`blitz_design`。Esca に利用例はまだ無い）。
- **`M結果`**: ある処理・評価の出力の境界で、その処理が取り得る排他的な帰結を表す判別型。上位トレイトを持たず、標準の `Result<T, E>` は自動で `M結果` であり、独自の `enum` は `M結果` を実装したときだけ `M結果` であり、`struct` は `M結果` になれない（`blitz_design`）。Esca の遷移関数が返す `Result<遷移成功結果, 遷移失敗結果>` の外側の判別構造がこれであり、内側の2つの値は `M結果` ではない。
- **`M射影関数<状態: M状態, 射影DTO: M不変データ>`**: `&状態 -> 射影DTO` の一方向観測計算を包む境界付きの newtype（`blitz_design`）。
- **`M解釈関数<入力: M解釈前の入力, コマンド: Mコマンド>`**: `&入力 -> コマンド` の純粋解釈計算を包む境界付きの newtype（`blitz_design`）。
- **`M遷移関数<状態: M状態, コマンド: Mコマンド, 規則: M規則, イベント: Mイベント, 失敗: std::error::Error>`**: `(状態, &コマンド, &規則, 遷移パラメータ) -> Result<遷移成功結果<状態, イベント>, 遷移失敗結果<状態, 失敗>>` を導出する純粋計算を包む境界付きの newtype（`blitz_esca`）。状態は値で受け取る（所有権を移す）。参照で読んで組み直す形では、1か所しか変わらない遷移でも状態の大きさに比例した複製が毎回かかるためである（2026-09-26 のオーナー裁定。`_doc/設計/設計オントロジー.md` 第3節・2.5.3）。`遷移パラメータ`(`crates/blitz_esca/src/transition_parameter.rs`)は、状態でもコマンドでも規則でもない遷移の必須の入力を束ねた引数オブジェクト(`MParameter`。`_doc/設計/設計オントロジー.md` 2.6節・3.5.1)であり、Esca第1段階では `経過時間` だけを持ち、第2段階で刻みの始まりの時刻(`世界の時刻`。`crates/blitz_esca/src/時刻.rs`)を足した。時間は、`blitz_math::秒` を有限かつ0以上に検証して包んだ値オブジェクト `経過時間`(`crates/blitz_esca/src/elapsed_time.rs`)で受ける。遷移は数値の表現範囲を超えたとき失敗を返す。有限な入力の積和でも `f32` は ±∞ になりうるため、遷移の結果の有限性は検証で閉じる（前提で置かない）。Esca の遷移失敗結果の失敗の理由は、歩行の遷移では `歩行の失敗`(次の現在地を作れない・居場所がいる地点の区域の外にある)、経路の開閉の遷移では `経路の指定の失敗` である。
- **`遷移成功結果<状態, イベント>`**: 遷移関数が返す、次の状態と出来事の一覧の名前付きの組（`blitz_esca`。4.4「多重戻り値の生タプル禁止」に合わせる）。型引数に `M状態`・`Mイベント` の境界を持つ意味型であり、境界は構造体の利用箇所でコンパイラが強制する。
- **`遷移失敗結果<状態, 失敗>`**: 遷移関数が失敗のときに返す、受け取った状態(`元の状態`)と具体の失敗(`失敗の理由`)の名前付きの組（`blitz_esca`）。遷移は状態を値で受け取るため、失敗のときはこの値の中で状態を呼び出し側へ返し、呼び出し側は元の状態を維持する（`_doc/設計/設計オントロジー.md` 3.5.9）。型引数に `M状態`・`std::error::Error` の境界を持つ意味型である。

`M遷移関数` と `遷移成功結果` と `遷移失敗結果` を `blitz_design` へ上げないのは、これらが計算モデルまで固定しているためであり、まず Esca 側で確定してから昇格を判断する。

第2段階(Issue #187 の作業G2)の型が名乗るマーカーは次のとおりである(2026-09-27。PR #195 のレビューで付けた)。

- 状態: `旅行者の居場所`・`経路の開閉の状態` は `M状態`。区域の中の移動の作業の値 `移動の途中` は `M状態` を付けず、`M不変データ` だけを付ける。`移動の途中` は1回の呼び出しの中だけで生きる作業の値であり、保持され遷移されるゲームの今(`M状態`)に当たらないためである。`blitz_sim` のソルバ内部の作業状態は `M時間局所状態` で寿命を宣言しているが、`移動の途中` にはその宣言が無く、同じ扱いにはできない(2026-09-27 の親の判断)。
- 規則: `経路の開閉の規則`・`歩行遷移の規則` に加え、歩行の遷移へ読み取り専用で渡す空間制約 `区域の空間制約` と、その一部の `通れる通り口の集合` が `M規則` である。地図 `地点と経路のグラフ` は開閉と歩行の両方が読むため `M規則` を付けない。
- コマンドとイベント: `経路の開閉の命令` は `Mコマンド`、`経路の開閉の出来事` は `Mイベント` である。
- 関数へ渡す引数: 経路の開閉と旅行者の歩行の更新へ与える入力 `経路の開閉と旅行者の歩行の更新への入力`(開閉の命令と旅行者の意図の組)と、`区域の中の移動の指定`・`区域の指定`・`閉じている時間帯の指定`・`経路の開閉の状態の指定`・`経路の開閉と旅行者の歩行の進行の指定` は `MParameter` を付ける。同じ日に一度 `M関数への入力` もあわせて付けたが、2026-09-27 のオーナー裁定でそのマーカーを外し、意味の決まった入力を関数へ渡す1つの引数へまとめた型も `MParameter` に含めた(`_doc/設計/設計オントロジー.md` 第2節)。
- 処理: `経路の開閉と旅行者の歩行の進行` は `M工程`。一区切りの排他的な帰結 `移動の進み方` は `M結果` である。
- 失敗の列挙(`経路の開閉と旅行者の歩行の更新の失敗`・`区域の中の移動の失敗`・`地図の生成の失敗`・`経路の指定の失敗`・`閉じている時間帯の生成の失敗`・`地点を決められない理由`・`経路の開閉の予定の生成の失敗`・`世界の時刻の生成の失敗`・`旅行者の現在地の生成の失敗`・`歩行の失敗`・`歩行の規則の生成の失敗`・`経過時間の生成の失敗`)と、同一性を持たない値(識別子・地点・区域・通り口・経路の積み荷・開閉の予定・`経過時間`・`世界の時刻`・`移動の変位` など)は、`M不変データ` と `M値オブジェクト` を付ける。失敗の列挙はデータの役割を持たない。失敗は、`_doc/設計/設計オントロジー.md` 3.5.1 の因果モデルで、次の状態も出来事も無い帰結の理由であり、状態・コマンド・規則・イベント・入力・観測のどれにも当たらないためである。失敗を `Mイベント` にすると、成立していない事実を生成しないという法則E2(同 4.4)に反する。`移動の変位` は関数の必須入力をまとめた引数ではなく、どの関数から見ても同じ意味を持ち、値で等しさが決まる量であるため、`MParameter` を付けずに `M値オブジェクト` を付ける。
- 何も付けない型: `経路の開閉と旅行者の歩行の更新の結果`(`M結果` は判別型に限られ、この結果は常に次の進行と出来事と失敗の一覧を持つ構造体であり、`M工程` の `経路の開閉と旅行者の歩行の進行` を持つため `M不変データ` でもない)と、`未検証の地図`(Graphiteのグラフを検証の前に持つビルダーであり、`&mut` の口を持つグラフを包むため `M不変データ` になれない)、`平面の幾何` の型7つ(`平面の点`・`平面の線分`・`平面のベクトル`・`単純多角形`・`単純多角形の生成の失敗`・`多角形に対する位置`・`線分の区間`)である。7つすべてにマーカーを付けない理由は、`平面の幾何` が仕組みの層であり、その型が Esca のドメインの概念ではないことである。このうち `単純多角形` と `平面の線分` には、もう1つ理由がある。この2つは型ごとの工程を定義と別のファイルに分けており(CLAUDE.md「切り出しの根拠義務」の5号)、マーカーを付けると、設計解釈マーカーを実装した型の実装を定義のファイルに置くという規則とぶつかる。

法則の検査主体(コンパイラが強制する法則と `cargo xtask conform` の設計オントロジーの検査が見る法則の分担)と検査器の保証範囲は、`_doc/設計/設計オントロジー.md` が正本として持つ。`Mコマンド: M不変データ` 等の supertrait の Relation はコンパイラが保証し、conform は役割の実装から型の定義をたどってその定義に純粋データ規約を当てる(`impl M不変データ for` をどのファイルに書くかは法則ではない)。関数の役割は境界付きの newtype であり、型を使った時点でコンパイラが型引数の境界を強制する。迂回できる書き方は無い。Esca 側は `const _: M遷移関数<...> = M遷移関数::生成する(旅行者の居場所::歩行を遷移する);` の静的宣言で、遷移関数が役割を満たすことをコンパイラに確かめさせる。参照: `_doc/設計/設計オントロジー.md`。

### 4.2 引数DTOと名前付き引数様式（2026-09-18制定）
同型プリミティブが並ぶ引数は順序誤認の温床となるため禁止する。引数はDTO構造体に束ね、構造体リテラル直接呼び出し `(要求DTO { ... }).メソッド()` で呼び出す。ここでいうDTOは設計解釈マーカーの `M不変データ`(純粋な所有データ)であり、引数DTOも `impl M不変データ for` を書く(`区域の指定`・`区域の中の移動の指定` がその例である)。関数へ渡す必須入力をまとめた引数DTOは、意味の決まった値(`Mコマンド`・`M状態`・`M規則` など)をまとめたものも含めて `MParameter` を付ける(4.1)。関数の外でも意味を持つ量は、引数として渡すときも `MParameter` でなく `M値オブジェクト` を名乗る(例は東と北の2成分を持つ `移動の変位`)。

### 4.3 抽象度レイヤーの純化（シナリオ層とメカニズム層の混在禁止、2026-09-18制定）
シナリオ層（進行フロー、画面の流れ、テストケース等）に、それを支える道具・構文解析・計算・固有データ型等のメカニズム層を同居させてはならない。100行未満であっても抽象度レイヤーの異なるコードの同居を禁止し、メカニズムは独立モジュール（`syntax_checker.rs` 等）として分離してシナリオ層を純化する。

### 4.4 身体規則と空間制約の直交化と結果DTOの原則（2026-09-18制定）
1. **多重戻り値の生タプル禁止**: 計算結果は `(f32, f32, bool)` 等の生タプルで返さず、名前付きフィールドを持つ結果DTO（`区域の中の移動の結果` 等）として型定義する。
2. **身体規則と空間制約の直交化**: 主体の運動能力（`歩行の規則`）の中に世界の壁や障害物を埋め込まない。空間制約（`区域の空間制約`。地図の区域と、いま通れる通り口）は独立した環境の値として定義し、歩行の規則（`歩行遷移の規則`）が身体と合成して持つ。第1段階は長方形の `移動可能範囲` を `Option` で合成していたが、第2段階(Issue #187 の作業G2)で区域へ置き換えて消した。旅行者はいつもどこかの区域にいるため、空間制約の無い歩行の規則は無い。
3. **歩行方向の検証付き生成**: 歩く向きは長さ1を不変条件に持つ値オブジェクト `歩行方向` で表し、生成の口は `キーボード歩行入力` からの導出（相殺で零なら向き無し）だけにする。同型の `f32` を2つ並べる生成の口は置かない。
4. **区域の検証付き生成**: `区域` は公開フィールドの指定DTO `区域の指定`(頂点の並び)を `検証する()` して初めて得る。頂点が3つより少ない・有限な数値でない・長さ0の辺がある・反時計回りに並んでいない・自己交差する並びは型付きエラー `単純多角形の生成の失敗` で拒む。地図は区域どうしの重なりと通り口の食い違いを型付きエラー `地図の生成の失敗` で拒む(5節)。第1段階の `移動可能範囲の指定` と `移動可能範囲の生成の失敗` は区域へ置き換えて消した。
5. **状態と出来事の分離と、事実でない出来事の禁止**: `遷移成功結果<状態, イベント>` で状態と出来事を分離する。`歩行を開始した`・`立ち止まった` のような状態変化のイベントは、前の状態と次の状態の差を判定できる場合だけ生成する。状態の差を表現できない段階では事実でないイベントを発行しない。語彙と法則E1〜E8の正本は `_doc/設計/設計オントロジー.md` である。
6. **歩行の規則の速さと経過時間の検証付き生成**: `歩行の規則::生成する` は速さが有限かつ0以上でなければ型付きエラー `歩行の規則の生成の失敗` で拒む（速さ0を許すのは、静止は `旅行者の意図::静止` で表すため速さ0の規則が矛盾を生まないことによる）。`歩行を遷移する` の経過時間は値オブジェクト `経過時間` で受け、`経過時間::生成する` が有限かつ0以上でない値（負・NaN・無限大）を型付きエラー `経過時間の生成の失敗` で拒む。遷移関数の側は経過時間を検査しない（型が保証する）。
7. **遷移の結果の有限性は検証で閉じる**: `旅行者の現在地` のフィールドは私有であり、`生成する` と `平行移動する`（変位 `移動の変位` を足して同じ検証を通す）だけが現在地を作る。遷移は数値の表現範囲を超えたとき失敗を返す。有限な入力の積和でも `f32` は ±∞ になりうるため、遷移の結果の有限性は検証で閉じる（前提で置かない）。第2段階から、歩行の遷移の状態は居場所(`旅行者の居場所`。いる地点と現在地)である。`旅行者の居場所::歩行を遷移する` は居場所を値で受け取り、戻り値は `Result<遷移成功結果<旅行者の居場所, 旅行者の出来事>, 遷移失敗結果<旅行者の居場所, 歩行の失敗>>` である。失敗のときは受け取った居場所を `元の状態` に入れてそのまま返す。区域の計算は倍精度で行い、次の現在地へ戻す単精度への狭めも同じ検証を通す(`旅行者の現在地::平面の点から狭める`)。

## 5. 今後の展開ステップ

1. **第1段階**: 主人公の基本移動と観察（歩行、移動可能境界との接触・衝突出来事、入力解釈、視界）。
   - 歩行移動（第2段階から `旅行者の居場所::歩行を遷移する`）および描画位置射影（`旅行者の居場所::描画位置を射影する`）

2. **第2段階**: 地点と経路の表現（どこへ向かうか、どの道が通れるか）。
   - 通れる可能性のある経路は、ステージを作る時点ですべて置く。プレイヤーが自由に道を作ること（掘る・地図の自動生成など）はしない。「壁が壊れて新しい通り道ができる」のような仕様は、作る人がはじめは閉じた経路として置いておき、経路を開くことで表す（2026-09-26オーナー裁定）
   - 世界は切れ目のない1枚のオープンワールドとして持つ。進行の制限（ゲート・封鎖）はありうる（2026-09-26オーナー裁定）
   - 経路を閉じたり開けたりするきっかけは、出来事と時間の両方である（2026-09-26オーナー裁定）
   - 地点（`地点`）は、世界の中の範囲である区域（`区域`）を持つ。区域は地面を上から見た多角形であり、作る人が1つずつ描く（2026-09-26 オーナー裁定）。頂点は北を上に見て反時計回りに並べ、区域は自己交差しない（`crates/blitz_esca/src/地点と経路/区域の形.rs`）。多角形の計算は仕組みの層（`crates/blitz_esca/src/平面の幾何.rs`）に置く（4.3）
   - 区域の境目は、越えられない地形（川・崖・城壁・山並み）に沿って描く。開けた野原でつながる場所は同じ区域にする（2026-09-26 オーナー裁定）。区域どうしは境目だけを共有し、内部が重なってはならない。区域と区域のあいだの隙間（どの区域でもない帯）は拒まず、壁として扱う。通り口の無い境目のあいだの隙間が、作る人の描き間違いか意図した空白かを機械は見分けられず、隙間はどの区域でもないため旅行者が入れず、壁と同じ役を果たして歩行を壊さないためである（地図の組み立ては隙間を確かめない）
   - 経路（`経路`）は、隣り合う区域のあいだで通り抜けられる箇所として持つ。境目を越えられるのは経路だけである（2026-09-26 オーナー裁定）。経路の積み荷（`経路の積み荷`）は、経路の種類・通り口・開閉の予定を持つ
   - 経路の種類（`経路の種類`）は幹線道路・橋・門・脇道・山道の5つであり、幹線道路・橋・門は封鎖でき、脇道・山道は封鎖できない（2026-09-26 オーナー裁定。時間や危険などの種類ごとの性質は第3段階で決める）。はじめから閉じた予定と時刻の予定を持てるのは封鎖できる種類だけであり、地図の組み立てが拒む。壁が壊れて通れるようになる抜け道は、はじめは閉じた門として置く
   - 地図は、封鎖できる経路にだけ封鎖できる経路の識別子（`封鎖できる経路の識別子`）を発行する。経路の開閉の命令・状態・出来事はこの識別子で経路を指すため、封鎖できない経路を閉じる命令は型の上で作れない
   - 通り口は自由な座標で持たず、経路の両端の2つの区域が共有する辺で指す（`通り口の指定`。両方の区域の、辺の始まりの頂点の番号の組）。共有する辺とは、頂点の座標が完全に一致し、2つの区域で逆向きに張られた辺である。Graphiteの向きの無い辺は両端の順序を保たないため、地図の組み立てが2つの番号を両端の区域へ当てる向きを決める。地図の組み立て（`地点と経路のグラフ::検証して生成する`）は、区域どうしの内部が重ならないこと・共有する辺の頂点が完全に一致すること・同じ区域の同じ辺を2本の経路の通り口が使わないこと・通り口の辺が両端の区域に実在し共有されていることを確かめる
   - 地点と経路のつながり（`地点と経路のグラフ`。`crates/blitz_esca/src/地点と経路/地図.rs`）は、ゲームの開始時に組んだ後は変わらない`M不変データ`として持ち、Graphite（Rustの型で検査されるグラフ記述言語）の型付きのグラフで書く（図式の宣言は `crates/blitz_esca/src/地点と経路/図式.rs`）。図式に `#[derive(Clone)]` を付けて完成したグラフを複製できるようにし（Graphite PR #51）、完成したグラフを私有のフィールドに包んで読み取りの口だけを公開する。Graphiteの完成したグラフは節点の値と辺の積み荷を `&mut` で書き換える口を持ち、その口を持つ型は`M不変データ`（自己変更を行わない）になれないためである。これが、Graphiteのグラフと`M不変データ`・`M遷移関数`（次の状態を新しい値として返す）を両立させる書き方である（Issue #187 の確かめる事項）
   - 経路は向きの無い辺であり、積み荷（`経路の積み荷`）に種類・通り口と並べて経路の開閉の予定（`経路の開閉の予定`。はじめに開いているか閉じているかと、閉じている時間帯の並び）を持つ。予定を経路と別の表で持たないのは、予定が地図に無い経路を指す食い違いを型で起こせなくするためである
   - 地点と経路の識別子（`地点の識別子`・`経路の識別子`）は、地図が自分の中に在ることを確かめてから渡す型であり、Graphiteの生成する識別子（中身の文字列が公開されている）をそのまま状態や命令へ入れない
   - 封鎖と開通は、閉じている経路の識別子の集合（並びが決まる `BTreeSet`）を持つ別の`M状態`（`経路の開閉の状態`）として持ち、`M遷移関数`（`経路の開閉の状態::開閉を遷移する`）がその新しい値を返す。規則（`経路の開閉の規則`）は地図を持つ。状態は規則からだけ作る（`経路の開閉の規則::はじめの状態`・`経路の開閉の規則::指定を地図で確かめて状態を作る`）。後者は閉じている経路と出来事が触れた経路の両方を指定（`経路の開閉の状態の指定`）で受け取り、どちらも地図と照らす。保存からの復元のように途中の状態を作り直すとき、出来事が予定に勝つという裁定の効果を黙って消さないためである。状態の型は地図を外から受け取って状態を作る口を持たない。その口があると、別の地図で確かめた状態を作れるためである
   - 開閉のきっかけの1つ目は出来事である。出来事は開閉の命令（`経路の開閉の命令`。経路を閉じる・経路を開く・命令が無い）として遷移へ渡る。出来事から命令を作るのはイベント反応（`_doc/設計/設計オントロジー.md` 3.5.7）であり、第3段階で作る
   - 開閉のきっかけの2つ目は時間である。遷移パラメータが持つ刻みの始まりの時刻と経過時間が、1回の遷移が覆う時間の区間（始まりを含み、終わりを含まない）を決め、規則がその区間に来た閉じている時間帯の端を読む。時間帯の始まりが来れば経路を閉じ、終わりが来れば開く。予定の変化はその時刻を跨ぐ刻みで1回だけ当たる（区間の終わりを含めないため、隣り合う刻みが同じ時刻を2回数えない）。刻みの終わり（次の刻みの始まり）を作るのは遷移パラメータの `次の刻みへ進める` だけであり、区間の判定と同じ1つの足し算を読む。世界の時刻（`世界の時刻`）は永続世界の絶対時刻の単位型 `大域秒`（倍精度）で持つ。単精度の秒では約2^19秒（約6日）から先で1/60秒の刻みの区間が空になり、時刻の予定が来なくなるためである。時刻を出来事として扱う案（当初の予定）を採らなかったのは、時刻の到来は状態遷移で成立した事実ではなく、遷移の入力だからである。実装では、時刻の予定は地図の辺の積み荷として持ち、刻みの区間に来た予定の変化を規則（`経路の開閉の規則`）が求めて遷移へ渡す
   - 時刻の予定と出来事（開閉の命令）が同じ経路にぶつかったときは、出来事が勝つ（2026-09-26 オーナー裁定）。出来事が一度でも閉じたり開けたりした経路には、それ以降、時刻の予定を効かせない。その経路の開閉を変えられるのは別の出来事だけである。時刻の予定は、出来事が一度も触れていない経路にだけ効く。同じ刻みで時刻の予定と命令が重なったときも、命令が指す経路には予定を当てない。裁定の例: 峠道が10時から20時に閉まる予定のとき、5時に崖崩れ（出来事）で閉じた峠道は、20時になっても閉じたままである。予定が20時から翌6時に閉まる城門を22時に命令で開けると、翌朝6時の予定も次の夜の20時の予定も効かず開いたまま残る。実装では、経路の開閉の状態が、閉じている経路の集合と並べて、出来事が触れた経路の集合（`出来事が触れた経路`。並びの決まる `BTreeSet`）を持ち、遷移はその集合と命令が指す経路への時刻の予定の変化を捨ててから命令の変化を当て、命令が指した経路をその集合へ加える（`crates/blitz_esca/src/tests/経路の開閉の出来事と予定の試験.rs` が例を固定する）。すでに閉じている経路を閉じる命令でも、その経路を出来事が触れた経路に数える。予定で閉じていた峠道に崖崩れが起きたら、時間帯が終わっても閉じたままであるべきだからである
   - 開閉の遷移は、実際に開閉が成立したときだけ出来事（`経路の開閉の出来事`。経路が閉じた・経路が開いた）を生む。出来事は、変化が触れた経路ごとに遷移の前後の開閉の差から組む（法則E2）。すでに閉じている経路を閉じる命令と、同じ刻みで時刻が閉じて命令が開いた経路は、前後の開閉が同じであるため出来事を生まない
   - 命令が地図に無い経路を指すときと、受け取った状態の閉じている経路か出来事が触れた経路が地図に無いとき（別の規則から作った状態を渡されたとき）、遷移は失敗し（失敗の理由は `経路の指定の失敗`）、受け取った状態を遷移失敗結果に入れて返す。失敗しうる検査は、状態の集合を動かす前に済ませる。「閉じている経路は、いつも地図にある経路である」は、小さな地図（地点4つ・経路5本。そのうち封鎖できる経路4本）の全状態・全コマンドの有限全数の検証で確かめる（`crates/blitz_esca/src/tests/経路の開閉の数え上げの試験.rs`）
   - グラフの上で経路を閉じたら、歩行の側もその箇所を通さない。経路の開閉の状態が、旅行者が歩けるかどうかの正本である。歩行の遷移は、経路の開閉の状態から刻みごとに導いた、いま通れる通り口（`通れる通り口の集合`。`経路の開閉の状態::通れる通り口を導く`）を、地図の区域と一緒に歩行の規則（`歩行遷移の規則`）の空間制約（`区域の空間制約`）として受け取る。別の仕組みが持つ状態から刻みごとに作った読み取り専用の値は、その遷移の規則（`M規則`）の一部として渡してよく、`M観測` として渡してはならない（2026-09-26 オーナー裁定。`_doc/設計/設計オントロジー.md` 3.5.2）
   - 歩行の遷移の状態は旅行者の居場所（`旅行者の居場所`。いる地点と現在地）である。地点を現在地と一緒に持つのは、境目の上の点が2つの区域のどちらの閉包にも入り、点だけからはいる地点を決められないためである。閉じた通り口の上に立った旅行者は、来た側の地点にいるまま、向こう側へは閉じた境目として遮られる。受け取った居場所の現在地が、いる地点の区域の外（世界の外を含む）にあれば、遷移は型付きの失敗（`歩行の失敗`）を返す。最初の居場所を点から決める口（`区域の空間制約::点を含む地点を決める`）は、どの区域にも入らない点を世界の外として、2つ以上の区域の境目の上の点を決まらないとして拒む
   - 歩いていて越えられない境目に当たったら、境目に沿って滑る（2026-09-26 オーナー裁定。第1段階の`移動可能範囲`の端と同じ挙動）。動きが区域から初めて外へ出る位置（出口）が、いま開いている通り口の辺の上にあり、出口から先の動きが向こうの区域に入るなら、隣の区域へ入って残りの動きを続ける。そうでなければ境目に遮られ、出口が辺の途中なら残りの動きをその辺に沿わせて1回だけ滑る。滑った動きがさらに境目に当たるか、出口が区域の角（頂点）にあれば、そこで止まる。1刻みに開いた通り口を2つ以上続けて抜けることはある。境目に遮られた刻みには `障害物に遮られた` が生じる（`crates/blitz_esca/src/地点と経路/区域の中の移動.rs`）
   - 1刻みの順序は「開閉を遷移する → 通れる通り口を導く → 歩行を遷移する」であり、経路の開閉と旅行者の歩行の進行（`経路の開閉と旅行者の歩行の進行::経路の開閉と旅行者の歩行を1回更新する`。`crates/blitz_esca/src/経路の開閉と旅行者の歩行.rs`。工程が受け取り返す値は `crates/blitz_esca/src/経路の開閉と旅行者の歩行/経路の開閉と旅行者の歩行の更新の型.rs`）が型に書く。この順序により、門が閉じる刻みに門を通ろうとした旅行者は、閉じた門に遮られる。通れる通り口を導き直すのは、開閉の遷移が出来事を生んだ刻み（開閉が実際に変わった刻み）だけである。2つの遷移の失敗は互いに独立に扱う
   - 役割の分担（2026-09-26 オーナー裁定）: Esca のロジックは、どの門が閉じているか・いまどの区域にいるかを決める正本であり、命題を有限全数で検証できる。第4段階（エンジンへの接続）では、エンジンがこの正本に従って閉じた門にバリケードのコライダーと見た目を置き、旅行者の体はエンジンの移動の仕組みでコライダーに沿って滑る。いま作る歩行の判定（区域の境目で滑る・通り口を抜ける）は、第4段階でエンジンの移動に置き換わる前のロジックの模型であり、区域と門の正本と命題の検証にはそのまま使い続ける
   - 「閉じた門しか通り口の無い区域へは入れない」「旅行者はいつもどこかの区域にいる」は、小さな地図（軸に揃った一辺10メートルの正方形の区域4つ・経路3本。現在地は5メートルの格子の上、向きは軸方向の4つ）の旅行者と開閉を合わせた全状態の有限全数の検証で確かめる（`crates/blitz_esca/src/tests/旅の数え上げの試験.rs`）。全状態の主張が及ぶのはこの地図の上だけであり、歩行は斜めの壁・境界の許容幅・滑り・凹んだ頂点を通らない。それらの上で旅行者が区域の閉包に留まることは、単体の試験が決まった標本で確かめる（`crates/blitz_esca/src/tests/境目の許容幅の近くの歩行の試験.rs`・`crates/blitz_esca/src/tests/区域の閉包に留まる歩行の試験.rs`）。有限全数の検証は、この2つを命題の構文でなく遷移モデルを直接見て確かめる。振る舞いの原子命題（発生する・遷移する・到達可能である）に、状態の中身（いる地点・現在地が区域に入るか）を問うものも、遷移が失敗したかを問うものも無いためである
   - 境界の上かの判断は境界の許容幅（座標の大きさの2の20乗分の1）で行い、歩行の始点が閉包にあるかもこの幅で受け入れる。移動の終点が閉包に着いたかだけは、その半分の幅（着く点の許容幅）で判断し、着かなければ最後に境目に触れた位置で境目に遮られる。着いた点を単精度の現在地へ戻すと最大で許容幅の約11分の1動くため、同じ幅で判断すると壁の外の点に着き、次の刻みの始点が受け入れから外れて旅行者が動けなくなるためである（`crates/blitz_esca/src/平面の幾何/線分の区切り.rs`）
   - 地点が有限であるため、「出口へ至る経路がいつも1本以上ある」のような命題を、有限全数の検証で証明できる
3. **第3段階**: 状況の進行とイベント（何が起き、どう選択肢を選ぶか）。
4. **第4段階**: エンジンへの接続（カメラ、高さ場地形、描画への配線）。
