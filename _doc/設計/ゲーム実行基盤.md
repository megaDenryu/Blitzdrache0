# ゲーム実行基盤

Blitzdrache0のゲーム実行基盤は、ゲーム世界の状態、処理、時間意味、依存関係、正本所有を表現し、それぞれの処理を適切な実行方式へ接続するための最上位の設計正本である。この文書は生存型文書であり、実装や新しい知見と食い違った場合は、設計と実装のどちらを正すかを裁定したうえで内容を更新する。

この文書はECSの設計書ではない。ECS、通常のRustの型、物理世界、描画世界、非同期処理、CPU並列処理、GPU計算などを、ゲーム仕様に従って組み合わせるための上位契約を定める。

関連する既存Issueは #32、#44、#49、#50 である。これらのIssueで既に決めた「ECSをエンジン全体へ広げない」「状態の正本を複製しない」「時間意味を第一級にする」「実行順を万能なSchedulerへ隠さない」「Query中の構造変更を安全な境界まで遅延する」という判断は本設計へ引き継ぐ。

## 最上位原則

**ゲーム仕様が実装方式を決める。実装方式がゲーム仕様を決めてはならない。**

Blitzdrache0のゲーム実行基盤は、次の条件を同時に満たす。

- ゲーム仕様を最も自然なコード構造で表現できる。
- 独立した処理は自動または明示的に並列実行できる。
- 意味上ひとまとまりの処理を、並列化やECSの都合だけで分解しない。
- 大量同種データはデータ指向で効率良く処理できる。
- 単一個体や強く凝集した概念は通常のRustの型として記述できる。
- 物理、描画、AI、Animation、Audio、Navigation、通信などは、それぞれに適した専用基盤を持てる。
- 内部方式を後から差し替えられる。
- 内部方式の差し替えによってゲーム仕様を書き直さなくてよい。
- 実行順、データ依存、正本、同期点、時間意味を観測できる。
- AIがコードを書いても、設計意図を型、マーカー、属性、静的解析から読み取れる。
- 性能最適化のためにゲーム意味論を壊さない。
- ゲーム意味論を保ったまま、必要な箇所を専用方式へ最適化できる。

## 1. ゲーム実行基盤の中心

ゲーム実行基盤の中心概念をECS、Object、Schedulerのいずれにも固定しない。

```text
ゲーム仕様
  ↓
ゲーム状態
+ ゲーム処理
+ 時間意味
+ 読み書き依存
+ 正本所有
  ↓
ゲーム実行グラフ
  ↓
実行器
  ├─ 直列実行
  ├─ CPU並列実行
  ├─ 非同期実行
  ├─ GPU実行
  └─ 専用基盤
```

**ゲーム実行グラフ**とは、ゲームの処理をノード、処理間の意味上の前後関係と読み書き競合を依存関係として表した構造のことである。

ゲーム実行グラフの1ノードを**処理**と定義する。処理はECS Systemである必要がない。

```rust
fn 狐を考える(狐: &mut 狐, 世界観測: &世界観測);

fn 毒を進める(対象: 問い合わせ<(&mut 体力, &毒)>);

fn 物理を一刻み進める(物理世界: &mut 物理世界);

fn 経路を探索する(要求: 経路探索要求) -> 経路;
```

上の関数は実装方式が異なるが、ゲームライフサイクル上では同じ処理である。

## 2. ECSの位置づけ

ECSとは、状態の組成が動的であり、特定の状態を持つ個体集合へ横断処理を適用するときに使うゲーム世界の表現方式である。

ECSをゲーム実行基盤そのものとは定義しない。

狐の内部状態が意味上ひとまとまりであるなら、次の型を無理に細分化しない。

```rust
struct 狐の思考 {
    空腹: f32,
    警戒: f32,
    巣: Option<場所>,
    現在行動: 狐の行動,
}
```

`狐の思考`は1 Componentとして扱ってもよいし、ECS外の通常のRustの型として扱ってもよい。

状態をComponentへ独立させる判断には、少なくとも次の根拠のいずれかを必要とする。

1. その状態は独立して追加または削除される。
2. その状態は独立した寿命を持つ。
3. その状態は独立して横断問い合わせされる。
4. その状態は独立した処理から更新される。
5. その状態は独立した正本所有者を持つ。
6. その状態は独立した保存、同期、複製単位である。
7. その状態はデータ配置を独立して最適化する意味がある。

実装者は、「ECSだから」という理由だけで意味上ひとまとまりの状態を分解してはならない。

## 3. 専用基盤

次の仕組みはECSの内部へ押し込まない。

- WindowとOSイベント
- Renderer内部
- GPU資源管理
- 物理解法
- 衝突数学
- Asset管理
- Streaming基盤
- Audio Mixer
- 通信Transport
- Job Executor

これらの仕組みは専用基盤として存在する。

ゲームEntityは、必要に応じて外部基盤を指す型付きハンドルをComponentとして持てる。

```text
ゲームEntity ID
≠ 物理剛体ID
≠ 衝突形状ID
≠ 描画項目ID
≠ 保存用安定ID
```

実装者は異なるID体系を同一視してはならない。

## 4. 正本所有

すべての意味ある状態には正本所有者を1つだけ定める。

```text
動的剛体の位置・姿勢
  正本 = 物理世界

運動学的物体の目標配置
  正本 = ゲーム世界

GPUへ送った配置
  正本ではない
  描画用の派生値

保存データ
  Runtime ECS storageそのものではない
```

複製データを持つ場合は、正本から派生値へ向かう方向を明示する。

```text
正本
↓
抽出または同期
↓
派生値
```

同じ意味の値を複数箇所から自由に書き換えられる構造を禁止する。

## 5. 時間意味

**時間意味**とは、その処理がゲーム時間のどの契機と周期で実行されるかという契約のことである。

すべての処理は時間意味を持つ。

ゲーム実行基盤は、少なくとも次の時間意味を扱える。

- 起動時
- 固定刻み
- 可変刻み
- 低頻度刻み
- 描画機会
- 必要時
- 非同期
- 終了時

ゲーム側は、物理120Hz、ゲーム論理60Hz、近距離AI10Hz、遠距離AI2Hzなど、意味のある独自周期を定義できる。

各処理は `frame % N` のような場当たりの頻度管理を内部へ持たない。頻度は時間意味を所有する実行側が管理する。

## 6. ゲームライフサイクル

固定刻みの標準工程は、意味のある順序としてコードから読める形にする。

```text
前刻みからの構造変更確定
↓
ゲーム入力適用
↓
プレイヤーとAIの意図生成
↓
移動・作用要求生成
↓
物理入力確定
↓
物理Simulation
↓
接触・物理結果抽出
↓
ゲーム状態遷移
↓
破壊・生成・構成変更予約
↓
刻み確定
```

「ゲーム入力適用」と「ゲーム状態遷移」がそれぞれ何を含むかは `_doc/設計/ゲーム制作アーキテクチャ.md` 判断13が定める(前者は操作だけで決まる状態遷移を含み、後者は世界の結果で決まる状態遷移である)。

描画は別工程とする。

```text
確定Simulation状態
+ 必要なら前Simulation状態
↓
描画補間
↓
描画抽出
↓
Renderer
```

ゲームライフサイクルの意味上の順序をScheduler内部だけに置いてはならない。

## 7. 処理の実行契約

処理は必要な範囲で次を宣言できる。

- 時間意味
- 読む状態
- 書く状態
- 外部副作用
- 前提処理
- 後続処理
- 決定性要件
- 排他要件

例を次に示す。

```text
狐AI
  時間 = 10Hz
  READ = 周囲認識、時刻
  WRITE = 狐の思考
  AFTER = 認識更新

天候更新
  時間 = 10Hz
  WRITE = 天候状態

物理
  時間 = 120Hz
  EXCLUSIVE = 物理世界
```

ゲーム実行基盤は、この契約から実行依存グラフを構築できる。

## 8. 並列化

並列化はECSの特権ではない。ゲーム実行基盤は、ゲーム実行グラフ全体に対して並列化を適用する。

ECSを使う処理と通常のRustの型を使う処理が互いに独立している場合、ゲーム実行基盤は両者を並列に実行できる。

狐1体の内部処理が次の意味上の依存を持つ場合、実装者は並列化の都合だけで依存を壊してはならない。

```text
知覚
↓
判断
↓
行動決定
```

原則を次のように定める。

> 並列性はデータ依存から導出する。実装者は並列性を作るためにゲーム概念を壊してはならない。

ゲーム実行基盤は、少なくとも直列実行、決定的な並列実行、最大並列実行、デバッグ実行を交換可能にする。

ゲームロジックは特定の実行器へ依存してはならない。

## 9. Scheduler

**Scheduler**とは、ゲーム実行グラフに記録された依存を守りながら、実行可能な処理を実行器へ割り当てる仕組みのことである。

Schedulerはゲーム設計者ではない。

ゲーム側は意味上必要な順序を宣言する。Schedulerは、順序を変えても意味が同じ部分だけを並列化または並べ替える。

Blitzdrache0は、「万能Schedulerを持たない」ことを永久原則にはしない。Blitzdrache0は次の原則を採用する。

> Schedulerをゲーム意味論の所有者にしない。

## 10. ECS Storage

ゲーム実行基盤は、すべてのComponentへ1種類の保存方式を強制しない。

Storageの候補には次がある。

- Sparse Set
- ArchetypeまたはTable
- Packed Array
- Singleton
- Tag Storage
- Relationship Storage
- External Storage View

ComponentまたはComponent群は、要求に合う方式を選択できる。

ゲームコードのQuery APIは特定のStorage実装へ依存してはならない。

v1でSparse Setを採用することは、この契約と矛盾しない。

## 11. Query

**Query**とは、特定の状態集合への型安全な参照を提供する仕組みのことである。Queryを、毎回すべてのEntityを検索する処理とは定義しない。

```rust
問い合わせ<(&位置, &mut 速度)>
```

Storageは、必要な走査計画を選択し、再利用可能な探索情報をキャッシュできる。

ゲーム実行基盤は、将来少なくとも次の問い合わせを表現できる余地を持つ。

- Entity IDによる直接アクセス
- 1 Component走査
- 複数Componentの積集合
- Optional Component
- WithとWithout
- 変更済み
- 追加済み
- Relationship
- 空間問い合わせとの接続

Bevy風の巨大なgeneric DSLを唯一のQuery APIにしない。静的Query、Builder、事前構築Queryなど、複数の入口を共存できる設計にする。

## 12. Relationship

親子、所有、装備、標的、搭乗、所属などの関係を、各Componentが手製のIDフィールドとして無制限に持つ形へ固定しない。

ゲーム実行基盤は、関係を一級の概念として表現できる余地を持つ。

```text
子供Of(親)
装備中(剣, キャラクター)
所属(兵士, 軍隊)
標的(敵AI, プレイヤー)
```

ゲーム実行基盤は、すべての関係をECS Storageへ強制しない。木、グラフ、空間索引などの専用データ構造が適切な場合、実装者は専用構造を使う。

## 13. 構造変更

Entity生成、Entity破棄、Component追加、Component削除は、安全な工程境界で原子的に反映できるようにする。

```text
処理中
↓
変更Transactionへ記録
↓
工程境界
↓
原子的Commit
```

1つのゲーム操作が複数Componentの追加または削除を要求する場合、ゲーム実行基盤は中途半端な構成を他の処理から観測させない。

Componentの追加や削除に対する反応を必要とする場合、Component自身へUnityの `OnEnable` に相当する暗黙のライフサイクルメソッドを持たせることを既定にしない。構造変更の事実を明示された処理から観測する。

## 14. 通常のRustの型との共存

ECSを使わないゲームオブジェクトを第一級の実装方式として扱う。

```rust
struct 狐 {
    思考: 狐の思考,
    記憶: 狐の記憶,
}

impl 狐 {
    fn 更新する(&mut self, 世界: &世界観測) {
        // 狐という意味のまとまりに閉じた処理
    }
}
```

通常のRustの型もゲーム実行グラフへ参加できる。

ゲーム実行基盤は、ECS Entityへ変換しなければ時間管理、依存管理、並列実行へ参加できないという制約を設けない。

## 15. 専用World

**専用World**とは、1つの問題領域について状態の正本と専用データ構造を所有する実行時の領域のことである。

ゲーム実行基盤は、少なくとも次の専用Worldを許可する。

```text
ゲーム世界
物理世界
描画世界
Animation世界
Navigation世界
Audio世界
Replication世界
```

各Worldは独自のデータ構造を使用してよい。

World間は型付きハンドルと明示的な同期処理で接続する。

1つの巨大Worldがすべてを所有する構造を作らない。

## 16. イベントとメッセージ

ゲーム実行基盤は、永続状態とは別に「何が起きたか」を表すイベントを扱える。

例を次に示す。

- 被弾した
- 死亡した
- 扉が開いた
- 接触が始まった
- Animationが完了した

実装者はイベントを永続状態の代用品にしてはならない。永続的な事実は状態として保存し、一回性の通知だけをイベントにする。

ゲーム実行基盤は、同期イベント、遅延イベント、外部非同期メッセージを区別できるようにする。

## 17. 非同期処理

経路探索、Streaming準備、Asset処理などの時間がかかる処理を固定刻みの同期処理へ閉じ込めない。

```text
要求
↓
Task
↓
非同期計算
↓
結果
↓
安全な世界工程で反映
```

ゲーム実行基盤は、Taskの取消し、世代番号、古い結果の破棄を扱えるようにする。

## 18. 決定性

ゲーム実行基盤は、決定的なSimulationを第一級の能力として扱う。

同じ初期状態と入力列から同じ結果を再現できる実行方式を用意する。

ゲーム実行基盤は、少なくとも次を観測または固定できる。

- tick番号
- 乱数Stream
- 構造変更の反映順
- 意味上必要な処理順
- 非同期結果の反映順

ゲーム実行基盤は、最大性能の実行方式と決定的な実行方式を同じゲームロジックから選択できるようにする。

## 19. デバッグと観測

ゲーム実行基盤は、少なくとも次を観測できるようにする。

- 登録された処理一覧
- 実行依存グラフ
- 各処理の時間意味
- READとWRITEの集合
- 並列化された理由
- 直列化された理由
- Query実行計画
- Entity構成
- Component Storage
- 構造変更履歴
- World間同期
- 状態の正本所有者
- CPU時間
- 待機時間

開発者は、「なぜ遅いか」「なぜこの順で実行されたか」を実行器の内部コードを読まずに調査できる。

## 20. Editorと保存形式

Runtime Storageを保存形式の正本にしない。

```text
編集時の正本
↓
変換
↓
Runtime World
```

保存用安定IDとRuntime Entity IDを分離する。

保存形式は版を持ち、旧版から現行版への移行手続きを持てるようにする。

Editorからの変更も、Runtimeへ適用するときは明示的な変更境界を通す。

## 21. Reflection

ゲーム実行基盤は、Editor、保存、Debug Inspector、Hot Reload、AIによる構造理解、通信Schemaのために、実行時の型情報を取得できるReflection相当の能力を追加できる設計にする。

通常のゲームロジックは静的型を使用する。Reflectionのために通常コードを動的型へ変換しない。

## 22. 設計意図の静的表現

重要な設計意図をコメントだけに置かない。

ゲーム実行基盤は、将来、次のような意図をマーカー型、trait、属性、静的解析で表現できる構造を目指す。

```rust
#[正本(物理世界)]
struct 剛体位置;

#[時間意味(固定刻み)]
#[読む(入力)]
#[書く(移動要求)]
fn プレイヤー制御(...);

#[ゲーム領域(AI)]
struct 狐の思考;
```

静的解析は、少なくとも次の違反を検出できる方向へ拡張する。

- RendererがECSを直接参照する。
- 物理基盤がゲームEntity IDへ依存する。
- 正本ではないデータへ書き込む。
- 必須の時間意味が未宣言である。
- 禁止された層依存が発生する。

AIも同じ情報を設計契約として利用できる。

## 23. 差し替え可能性

主要な仕組みは、ゲーム意味論と実装方式の境界で交換できるようにする。

交換対象の候補は次である。

- Storage
- Query Planner
- Executor
- Job System
- Physics
- Renderer
- Navigation
- Serialization
- Networking
- Scripting
- Asset backend

実装者は、内部の細かな関数すべてへtraitを付ける方式を採らない。実装者は、意味論側と実装方式側の境界に交換点を置く。

## 24. 性能

性能は後付け機能ではない。

ゲーム実行基盤は、少なくとも次の費用を観測できるようにする。

- メモリ確保
- Cache locality
- 分岐
- Lock
- 同期
- False sharing
- Data movement
- GPU転送

実装者は高速化のためにゲーム意味論を壊してはならない。実装者は、意味構造と保存・実行方式を分離し、方式側を最適化する。

## 25. 専用実装への脱出

ゲーム実行基盤の共通抽象が適切でない問題では、専用実装を正規の選択肢として使える。

- 通常のRust関数
- 専用Vec
- 専用Arena
- 専用HashMap
- 専用Tree
- 専用Graph
- 専用SIMD loop
- 専用GPU Compute

ECSを採用したことを理由に、すべての問題をECSへ変換してはならない。

## 26. 公開API

公開APIはゲームの意味を表し、現在の内部実装を漏らさない。

`archetype_index`、`sparse_page`、`scheduler_node`のような内部方式の語彙を、ゲーム側の中心APIにしない。

ゲーム側には、個体、成分、問い合わせ、処理、時間領域、世界変更など、ゲーム世界の意味を表す語彙を公開する。

## 27. 基盤自身の変更可能性

現在最良と思われる設計が将来誤りだと判明しても、Blitzdrache0はエンジン全体を書き直さず、その部分だけを交換できることを最高位の要求とする。

主要能力を次の三層で管理する。

```text
意味論契約
↓
交換境界
↓
現在の実装
```

例を次に示す。

```text
特定Component集合を効率良く走査する
↓
Query契約
↓
Sparse Set v1
```

将来、ゲームコードを変えずに次へ移行できるようにする。

```text
同じQuery契約
↓
Archetype v2
```

## 28. 全体構造

ゲーム実行基盤の責務配置は次を基本形とする。

```text
Application
│
├─ OS / Window
├─ Asset / Streaming
│
└─ ゲーム実行基盤
     │
     ├─ 時間領域
     ├─ 実行グラフ
     ├─ Executor / Job System
     │
     ├─ ゲーム世界
     │    ├─ 通常のDomain Object
     │    ├─ ECS
     │    │   ├─ Entity
     │    │   ├─ Component
     │    │   ├─ Query
     │    │   └─ Relationship
     │    └─ Game Event
     │
     ├─ 物理世界
     ├─ Navigation世界
     ├─ Animation世界
     ├─ Audio世界
     └─ 描画抽出
            ↓
         Renderer
```

ECSを全体構造の根にしない。ゲーム実行基盤を全体構造の根にする。

## 29. 禁止する設計

Blitzdrache0は次の設計を既定にしない。

- すべてをEntityにする。
- すべてをComponentにする。
- すべてをSystemにする。
- すべてを毎刻み更新する。
- すべてを非同期処理にする。
- すべてを並列処理にする。
- すべてを1つのSchedulerへ登録する。
- すべてを1つのWorldへ置く。
- すべてを1種類のStorageへ置く。
- すべての個体に同じTransformを持たせる。
- Runtime Storageをそのまま保存形式にする。

## 30. 完成条件

ゲーム実行基盤が完成したと言えるためには、少なくとも次の条件を同時に満たす。

1. 通常のRustで書くべき処理を通常のRustとして書ける。
2. ECSが適切な問題ではECSを使える。
3. 大規模な横断処理を効率良く実行できる。
4. ECS System以外の処理も実行グラフへ参加できる。
5. 独立した処理を並列実行できる。
6. 意味上順序が必要な処理の順序を保証できる。
7. 固定刻み、描画、低頻度、必要時、非同期を区別して扱える。
8. すべての意味ある状態について正本所有者を説明できる。
9. 専用基盤へ責務を分離できる。
10. Storageや実行器を後から交換できる。
11. Runtime内部構造をEditorや保存形式へ漏らさない。
12. 実行状態と依存を観測できる。
13. 決定的Replayの土台を持つ。
14. 静的解析でアーキテクチャ違反を検出できる。
15. AIが設計意図を型、マーカー、実行契約から読み取れる。
16. より良い方式が見つかったとき、局所的に置換できる。

## 31. 既存Issueへの適用

Issue #32は、ゲーム世界の個体表現とECS採用の裁定を管理する。Issue #32のECSは、本設計のゲーム実行基盤の一部として扱う。

Issue #44は、現在のECS実装ロードマップを管理する。Issue #44は、本設計に従ってECS領域の進捗管理として読む。ゲーム実行基盤全体の進捗管理は、ECS領域と分離して管理できる形へ移行する。

Issue #49は、ECS内部のStorage、Query、遅延構造変更を実装する。Issue #49の実装者は、本設計のECS契約を具体化し、Bevy等の既存ECSのAPIを正解として模倣しない。

Issue #50は、System実行順と時間意味を管理する。Issue #50の最終形はECS Systemだけを対象にせず、本設計における一般の処理へ拡張できる形とする。

## 最終原則

Blitzdrache0はECSエンジンではない。

Blitzdrache0のゲーム実行基盤は、ゲームという時間発展する世界を、ゲーム仕様の意味を壊さずに、適切な表現方式、保存方式、実行方式へ写像する。

ECS、通常のRustの型、データ指向、Job System、GPU Compute、専用Simulationは、この目的を達成するための選択肢である。
