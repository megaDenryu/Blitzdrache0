# ゲーム制作アーキテクチャ

「このエンジンでゲームをどう作るか」を、人に渡して作れる水準で定義する設計正本である。語彙は `_doc/計画/ユビキタス言語.md` の定義に従う。

## 目的

オーナーの要求は3つである。第一に、ブレス オブ ザ ワイルド級のオープンワールドを作れる能力へ届く構造にすること。第二に、小さいゲーム(以下ではオーナーの語に従いクソゲーと呼ぶ。短期間で作り切る小規模なゲームのことである)を何本も作り、繰り返し現れる形を確かめてから共通化すること。第三に、AIと人間が同じエディタを別の口から操作できることである。

この文書はその3つを満たす層の切り方と、最初の1本を作るために決めた設計判断を定める。第1段階は実装済みであり、後続のゲームは本文書の層と契約を引き継ぐ。

## 現状の実態

2026-08-14時点でエンジンが持っているもの、持っていないものを棚卸しした結果を記す。

- 実行の入口はblitz_app 1本である。イベントループはwinitが所有するパターンA(`_doc/設計/イベントループとフレームペーシング.md`「パターンA: winit所有ループ（現行方針）」)であり、1フレームの手続き列は`crates/blitz_app/src/app/frame.rs:21`の`一フレーム実行する`が固定順で並べている。どの工程をどの工程の前後へ置くかの理由は同じファイルのコメントが固定しており、UIの組み立てを描画入力の作成より先に置く理由、必要チャンク集合の中心をカメラ更新の直後に置く理由、時刻を可視判定より先に確定させる理由、段差の走査を時計の進行の後に置く理由、自動露出の経過秒を時計の進行と別に確定させる理由の5つがそれにあたる
- blitz_gameがゲームの状態・振る舞い・確定済みの操作入力からゲームインテントへの写像を所有する。blitz_appの`world_execution/entity_ledger`はゲームの個体の識別子と描画対象を対応させ、動く個体の変換を毎フレームの描画入力へ渡す
- 世界の性格は、コマンド行の入口で`起動時シーン`へ解き、その内側の`世界の種別`を網羅分岐して決める。綴りの正本は`crates/blitz_app/src/cli/scene_selection/parse.rs`にあり、世界の方針を裸のシーン名の文字列で再解釈しない
- 共通入力層はデバイス入力を`確定済みの操作入力`へ確定し、blitz_gameが`ゲームインテント`へ写す。blitz_appの`input/game_intent_policy.rs`と`input/camera_intent_policy.rs`が、実行の種類に応じてゲームとカメラへの適用を遮断し、フレーム数の決まった実行の決定性を支えている
- 時間は3系統ある。世界時刻は実時間に追従して可変、アニメーション時刻は描画フレームごとに固定の1/60秒、露出の経過秒は実行の種類で分岐する
- パターンAからパターンB(アプリが最外周のループを所有する形)への移行手順は設計済みであり、変更はblitz_appのmain.rs周辺の数十行に収まる。移行の引き金は3つ記録されていた
- ホットリロードはシーンの差し替え(束0の再登録)とシェーダー3本に効く。コード自体のホットリロードは扉のままであり、適用先はblitz_gameだけ、開けるかどうかの判断はゲームフェーズである
- 高さ格子はアセットコンパイラの入力のままだが、その格子を貼り合わせた高さ場が種別番号4の実行時形式として焼けるようになった(第1段階の工程3)。実行中の高さの参照はblitz_engineの高さ場の読み口が答える。高さ場を宣言する世界は場所巡りの世界(`fox_tour_world`)の1つだけであり、既存の検収の世界のカタログは高さ場を持たない(工程4)
- スキンの制約はアセット形式(シーンデータ1個に高々1つ)より強く、**レンダラー全体でスキニング一式が高々1つである**(`crates/blitz_render/src/renderer/mod.rs:70`)。生成は起動時だけであり(`crates/blitz_render/src/renderer/replace_scene.rs:21-23`がスキン付きシーンの差し替えを型付きエラーで拒む)、布一式がスキニングの出力へ依存している(`crates/blitz_render/src/renderer/generate/generate_resources/cloth_resources.rs:24`)。スキンを描画束の単位へ分ける変更は、生成・差し替え・描画入力の平坦化・布の結合・アプリ側の再生状態を横断する独立した作り直しである

## 層の定義

依存は矢印の向きの一方向に限る。**エディタはゲームの上位ではなく、コンテンツの正本を編集する者としてゲームと並んで立つ。** どちらもエンジンに依存し、エンジンはどちらも知らない。

```
エディタ層(将来)            ゲームロジック層(blitz_game群)
  |                           |
  |                      ゲームサイクル基盤(複数本の後に抜き出す接続ライブラリ)
  |                           |
  +----------→ エンジン層(blitz_engine / blitz_render / blitz_sim / blitz_math) ←----------+
                              ↑
                コンポジションルート(blitz_app: 依存の配線・入出力・フレーム内実行順序)
```

Webのアプリケーションで使う依存の向きの設計(クリーンアーキテクチャ。依存を内側の層へ一方向に揃える設計の呼び名)との違いは3つある。第一に、フレームループという時間の軸が全ての層を貫く。第二に、「コンテンツの正本 → コンパイル → 実行時形式」という製造の流れが層と直交して存在する。第三に、エディタが編集するのはコンテンツの正本であって実行時形式ではない。

## 主要な設計判断

### 判断1: ゲーム更新は描画フレームごとの固定刻みで始め、ループはパターンAのままにする

クソゲー1本目のゲーム更新は、**描画フレーム1回につき固定1/60秒を1ステップ進める**形にする。アニメーション時刻と同じ刻みであるため足の滑りが出ず、累積器(描画の頻度と固定刻みの差を貯めて、貯まった分だけ更新を回す仕組み)も要らない。挿入位置は`一フレーム実行する`の列のうち、入力を確定した直後でカメラの更新より前である。プレイヤーの位置がカメラとストリーミングの導出元になるためである。

**時間源の決定性の分岐を最初から入れる。** フレーム数の決まった実行(スモーク・ベンチ等)は実時間を1度も読まず固定刻みだけで進む。露出の経過秒と同じ「実行の種類で1度だけ選ぶ」様式である。これを守らないと、画素の読み戻しで判定する検収の入口が全て壊れる。**1本目は無期限実行でも固定1/60秒のまま実時間を読まない**(垂直同期の60fpsでは実時間とほぼ同じであり、アニメーション時刻との一致と決定性を同時に保てる。フレームが落ちたときにゲームが実時間へ追従する要求が出たら、累積器とセットで再設計する——判断1の冒頭の矛盾を工程1の実装員が検出したため、この1文で決着を固定する。2026-08-09親裁定)。

**ループのパターンBへの移行はしない。** 移行の引き金は3つ記録されていた。垂直同期を待たないIMMEDIATEの提示モード、提示の直前に入力を採るlate-latch、別ホストへの埋め込みである。固定タイムステップのゲーム更新を描画の頻度から切り離す要求はこれに含まれていなかったため、第4の引き金として`_doc/設計/イベントループとフレームペーシング.md`「判断の記録」へ追記した。要求が実際に立った時点で、パターンBへの移行と累積器を同時に設計する。移行手順は設計済みであるため、今この決定を先送りする費用は小さい。

**2026-09-01のIssue #2裁定で実時間の蓄積への移行が確定した。** 時間の規律の正本は`_doc/設計/時間の規律.md`であり、通常プレイだけが実時間の蓄積器を持ち、検収・ベンチは従来どおり実時間を読まない。蓄積器はパターンAのままで成立するため、パターンBへの移行は伴わない。実装は#3(キャラクターコントローラーとカメラ)の完了後の作業であり、それまでは本判断の現行の形(1描画=1刻み・実時間を読まない)が実装の実態である。

### 判断2: ゲームの実体の持ち方はエンジンが強制しない

エンジンが提供するのはシーン・描画・時刻・入力の口だけである。実体をどう持つか(素朴な構造体の群れ、自作の最小ECS(エンティティ・コンポーネント・システム。ゲーム内の物を識別子と部品の表で持つ設計)、bevy_ecsの借用)はゲームごとに選ぶ。クソゲーを数本、素朴な構造体の群れで作り、同じ配線を繰り返し書く負担が実際に現れた時点でゲームサイクル基盤へ引き上げる。bevy_ecsの借用はそのときに審査する(`cargo xtask conform`の依存白リストの更新とREADMEの採用審査)。ロジックを持たない値だけのアセット(Unityの ScriptableObject に相当する役割)は型付きデータアセットで実現する。

**汎用ECSを先に作らない方針は変えない。** 変えたのは「対象ゲームが決まった時点で1度だけ選定する」という手順であり、選定をゲームごとの判断へ移し、共通化を複数本を作った後へ移した。`_doc/計画/開発計画.md`「シーン表現・ECSの決定」がこの方針の正本である。

**2026-09-18の追随**: 2026-09-02のオーナー裁定(Issue #44)で、Blitzdrache0のゲーム世界は自前の個体群の基盤`blitz_ecs`を採用した。この裁定は「汎用ECSを先に作らない」という前段の方針を覆すものではない。`blitz_ecs`はarchetype・万能Scheduler・巨大なマクロDSLを持たない自前実装であり、外部ECSクレート(bevy_ecs等)の導入は依然として非目標である。層と設計判断の正本は`_doc/設計/ゲーム世界の個体群の基盤.md`である。

### 判断3: 入力は2段構えにする

デバイスの生の入力を共通入力層(blitz_appが蓄積して確定する)が受け、そこからゲームインテントへの写像をゲーム側が持つ。クソゲー1本目に要るゲームインテントは移動2成分・決定・キャンセル(Escキーでメニューを開く)である。カメラの操作意図(旧称: カメラインテント)が持つ「実行の種類で適用を遮断する」規律をそのまま継承する。

**掴み操作(設計判断53)の形を統一する作業は1本目から切り離す。** 画面上の点から世界の対象を選ぶ処理を誰が担うかは、それ自体が独立した設計であるためである。

### 判断4: 世界の宣言をデータ駆動へ段階的に寄せる

シーン名の文字列分岐の現物は「現状の実態」に列挙した5箇所である。**ゲームの世界の宣言はゲーム側の表へ移し、検収のための世界の分岐(スモーク系)は検収装置としてblitz_appへ残す。** 検収はゲームではないためである。世界の宣言をアセットとして外へ出すかどうかは、エディタの設計時に改めて決める。

### 判断5: 動くオブジェクトはゲーム状態が正本であり、描画へは毎フレーム供給する

- エンティティIDと描画対象IDは別に持ち、その対応表はゲーム状態の台帳が所有する。同じ関心の所有者を2つ作らないため、`_doc/設計/機能配置の指針.md`「機能配置の第一原則: 仕組みと方針を分けて置く」の所有者表へこの台帳を新しい所有者として登録した
- 供給するのは大域位置と、読込時に焼かれた姿勢から天頂軸まわりに回す角の2つである。向きを世界の方角そのものでなく読込時からの差で運ぶのは、レンダラーが個体の姿勢の正本を持たず、モデルがどちらを向いて焼かれているかも知らないためである。世界での向きをこの差へ写すのはコンポジションルートの配線であり、その配線だけがアセットの焼かれた向きを知る
- GPU側には「動的な個体の変換を毎フレーム書き込む経路」を新設する。現行の静的な個体変換列と可視ID列とは別の、小さな動的枠として置き、静的側の設計を壊さない
- **1本目のFoxは起動シーン(束0)のスキン付き描画対象として読み、地形はチャンク束で合成する。** スキンが1つだけという現在の構造は変えない。スキンを描画束の単位へ分ける作り直しはレンダラーを横断する独立した作業であるため1本目から外し、複数のキャラクターが要るという要求が立った時点の節目とする。動的な更新は「束0の特定の個体の変換を毎フレーム上書きする経路」として作る。目的地の目印は静的な配置で足りる。個体の出し入れの一般化も、要求が立ってから行う

### 判断6: シーンの線引きをエンジンとゲームで分ける

エンジンが持つのは、シーンという読み込み・実行・破棄の単位と、その口である。ゲームが持つのは、遷移のグラフと遷移の条件、およびシーンをまたいで残る状態である。**クソゲー1本目のタイトル画面は「世界の切り替え」ではなく「ゲーム状態とUIの被せ」で表す。** プレイする世界を最初から読み込み、タイトル状態ではUIを被せて入力をメニューへ向ける。世界を実行中に切り替える口は、2本目以降で要求が立った時点で新設する。

### 判断7: 地図の正本を持ち、生成は2系統に分ける

- 地図の正本(高さ・道・領域・配置点を持つデータ構造)が正本であり、3Dの地形はそこからの導出物である。立体交差や建築物は地形の形ではなく、メッシュアセットの配置で表す(ブレス オブ ザ ワイルドが採った方式である)
- **クソゲー1本目のマップはオフライン生成で確定する。** xtaskへ乱数の種を受け取る生成コマンドを足し(器は examples の見本生成の拡張である)、そのコマンドがソースアセットを書き、既存の`cargo xtask compile-assets`が実行時形式へ焼く。実行中に生成する経路は作らない。決定性の契約を保てることと、大規模化した第2弾でも同じ器を使えることが理由である
- **地形の高さを実行中に参照する経路を新設する。** 実行時形式へ高さ場を運ぶ(アセット種別の追加として設計する。種別の番号は`crates/blitz_engine/src/asset/runtime_format.rs:57-71`が1から3までを使っており空きがある。シーン内容の版は上げない)。1本目は固定の安定IDを持つ単一の高さ場アセットをカタログ経由で参照する。**チャンク目録は1つの座標へ1つのアセットIDしか持てないため、チャンクごとに高さ場を運ぶ将来の形はこの目録に載らない。この壁は第2弾(8km四方級)の設計で解く。** カタログの容量メタデータがメッシュを前提にしており高さ場の容量が予算の会計から漏れる点も、同じ場面で扱う。高さの参照はFoxの接地と当たり判定の土台であり、ブレス オブ ザ ワイルド級でも必ず要る

### 判断8: エディタは操作コマンド層を核にし、UIはブラウザで作る

コマンドを人間用のUI(ブラウザ)とAI用のAPI(REST。ネットワーク越しにコマンドを呼ぶ口)の両方から積む。取り消しとやり直し(Ctrl+Zで戻す操作)はコマンドの列から導く。シーンを映す画面の表示方式(映像に圧縮して送る形、読み戻した画像を連続で送る形、ネイティブの窓を併用する形)は決めないまま残し、エディタの設計を詰めるときに決める。エンジンフェーズの間はエディタを作らない(非ゴールを維持する)。

### 判断9: コンパイルの分離は現状でほぼ足りている

依存の向き(blitz_game → blitz_engine)が正しく保たれていれば、ゲーム側の変更に対する増分ビルドは小さい(2026-08-09の実測で約6秒)。コード自体のホットリロード(動的読み込みライブラリ。dylibと呼ぶ)は既存の扉のままにする。シェーダー1本の変更で88本が再コンパイルされ約28秒かかる問題は、この設計とは独立した改善の課題として外部台帳の札#138へ起票する。

### 判断10: blitz_gameへのblitz_renderの型の漏れは当面受け入れる

blitz_engineがblitz_renderに依存する現在の構造では、ライティング入力のような型の露出を隠せない。隠すための写しの型をblitz_engine側へ先に作ることはせず、実際に不都合が出てから作る。

### 判断11: アプリの所有は据え付け・材料・配線の3種で表し、束は入れ物にしない(2026-09-18、Issue #45)

`アプリ`(`crates/blitz_app/src/app/mod.rs`)は2026-09-18時点で46のフィールドを直接所有していた。Issue #31(アプリ構造体の所有状態を責務別の配線構造体へ整理する)とIssue #45(アプリをApplicationHandlerと工程配線へ縮め、所有束と外向きAPIを確定する)の裁定に従い、本判断は`アプリ`の所有を次の3種で表す。据え付けとは、起動の途中(カタログを読んだ後)に同じ地点で揃って据わり、終了時に同じ地点で揃って消える状態の組のことである。材料とは、起動時に一度だけ読まれて以後使われない不変の値の組のことである。配線とは、責務・寿命・時間意味・生成破棄条件を共有し、取り出す口以外の命令を1つ以上持つ状態の組のことである(操作サービス)。

| 種 | 名前 | 中身 | 根拠 |
|---|---|---|---|
| 据え付け | `画面の据え付け` | `レンダラー`・`画面へ重ねるUI`・`window`(この宣言順でDropし、レンダラーの破棄をウィンドウの破棄より先にする) | 3つの`Option`が`resume`の同じ地点で`Some`になり、他の地点で個別に`None`へ戻らない。同時に生まれて同時に消える`Option`を別々に持つことを規約が禁じる。描画の入口が`None`を弾くため、下流の17箇所の`let Some(レンダラー) else`は到達しない防御であり、これを消す |
| 材料 | `起動時に一度だけ使う設定` | `シーン`・`アセットの置き場`・`空中遠近合成`・`粒子表示`・`開発UI初期有効`・`布モード` | `resume`が一度読んで`画面の作り方`と`読み込む世界の材料`へ写すだけの通過材料。`Option`で持ち`resume`で`take`して以後`None`(消費済みを型で言う)。詰め替えの綴りは`window_setup`の側に置く |
| 配線 | `布の配線` | `布プリセット`・`布の参照比較`・`掴みの介入` | 1つの機能の寿命を共有する。命令は`この描画の入力を作る`・`終了時に参照計算と突き合わせる` |
| 配線 | `描画束の台帳` | `可視判定`・`プリミティブ描画項目台帳`・`永続束`・`地表の層のタイル` | 束の登録と解除の3箇所(起動時・ホットリロード・ストリーミング)で必ず一体に動く。命令は`起動時に登録する`・`束を足す`・`束を外す`・`受け皿を預ける/戻す`。レンダラーと`大域ずらし量`は引数で受ける |

本判断は、`resumed`の1回性を「ゲーム世界の起動が1回であること」と同一視しない。1回性を決めているのは起動時に一度だけ使う設定の消費であり、winitの`resumed`というOSのライフサイクルの契機ではない。ゲーム世界の一回限りの初期化(時間意味は「起動時」)と、ウィンドウとサーフェスの据え付け(`resumed`の契機)を別の時間意味として扱えるようにする設計は、[Issue #145](https://github.com/megaDenryu/Blitzdrache0/issues/145)が持つ。

本判断は次を束ねない。`起動モード`と`大域ずらし量`は起動時に決まる写せる定数であり、どの束の私有にしても取り出す口が生えるため、`アプリ`が直に持ち値で渡す。`時間進行`と`入力状態`は「刻み数の決定」と「入力の蓄積」という別の時間意味を持ち、2つを包む階層は束ねただけの階層になるため、`アプリ`が直に持つ。`ゲーム配線`は、判断12(Issue #46)が定める`世界実行`(ゲーム世界を進める入口を時間意味ごとに限定してアプリへ貸す型)を実装する経路が現時点で1つしか無いため、本判断はこれを包まない。`ゲーム配線`は2つのゲームで共有される状態を`世界実行`へ渡し、ゲーム固有の振り分けだけを残す。`天空`と`世界の描画構成`は既に1つの概念へ畳まれた型であり、`アプリ`が直に持つ。このほか`アプリ`は、毎描画の描画入力が読む単独の値(`描画対象の並べ方`・`クリア色`・`計測つまみ`・`露出`・`ブレンド`・`アニメーション`・`アニメ時刻`)と、`ApplicationHandler`の責務そのものである`起動時エラー`を直に持つ。これらは互いに寿命も時間意味も共有せず、束ねると入れ物になるためである。

本判断は`現在フレーム`を`描画機会の番号`の値オブジェクト(`crates/blitz_app/src/app/time_step/draw_opportunity_number.rs`)にする。`時間進行配線`が番号を保持し、工程順を持つ`frame.rs`が1描画に1度読んで、既存の毎描画の材料(`この描画の時間の進み`・`フレーム視点`)へ載せて配る。どの束の私有にしても全束が共通して依存を取りに来る単一の窓口になるためである。本判断は、保持と終了判定を`時間進行`へ移す。名前に描画機会という時間領域を出すのは、固定刻みが1描画に0本・1本・複数本ありうるため、一般名の「フレーム番号」が固定刻みの番号と取り違えられる余地を残すためである(2026-09-18、PR #144のオーナーのレビュー)。固定刻みの番号は別の型であり、本判断は足さない(Issue #50が固定刻みの工程に番号を持たせるときに定める)。この型と対になる本数の名前も`描画機会の総数`(型のメソッドの引数)と`描画機会の数`(`起動モード`の枝のフィールド)へ揃え、1つの式の中に2つの時計の名前が並ぶ形を残さない。CLIの綴り(`--frames`等)と`cargo xtask`が数える報告の行の綴り(`ストリーミング進行(フレーム{...})`等)は外部との契約であり変えない。幅は64ビットであり、番号が上限に達しないことを型の不変条件とする。上限で同じ値に留める飽和加算は、奇偶・区切り・終了判定・固定経路を黙って壊すため採らない。番号を整数の算術で使う境界(自己操作の配線が渡すスモークの計画・ストリーミングの固定経路と計測・視点の画素内ずらしの列の添字)も64ビットで受けるため、番号を縮める境界は1つも無い。縮める境界を残すと、64ビットへ広げた番号がその境界の幅で頭打ちになり、幅を広げた意味が消える(2026-09-18、PR #144のオーナーの指摘)。

本判断は、外向きAPIを`main.rs`が呼ぶ5つ(`生成する`・`起動時エラーを取り出す`・`検証カウンタを取得する`・`終了時報告を出す`・据え付けの破棄)に留める。`queries.rs`と`queries/renderer_metrics.rs`の30の照会について、本判断は、`アプリ`が`終了時の観測一式`という材料を1つ組んで`reports`へ渡す形へ移す。これにより30の照会は`アプリ`の公開面から消える。

親はこの工事を3本のPRで進める。PR-Aが据え付けと起動時の材料と布の配線、PR-Bが描画束の台帳と資源の配線、PR-Cが検収の3分割と視点の配線と描画機会の番号の配り替えと外向きAPIの是正である。`&アプリ`または`&mut アプリ`を丸ごと受ける自由関数23件(`xtask/src/conform/free_function_whole_type/ledger/table/blitz_app_app.rs`)は、自分の触るものだけを受ける形か、束のメソッドへ移す形で各PRが減らす。束を丸ごと受ける自由関数は機械検査に掛からないため、親は構造チェック員へ検査を委譲する。

### 判断12: アプリは世界を時間意味ごとの入口だけで進め、共有される状態は世界実行が所有する(2026-09-18、Issue #46)

`世界実行`とは、ゲーム世界を進める入口を時間意味ごとに限定して`アプリ`へ貸し、2つのゲーム(キツネの場所巡り・歩くだけ)が共有する状態(`ゲーム状態の台帳`・`高さ場の読み口`・`プレイヤーカメラの配線`・`移動の観測の記録`・`ゲーム操作の適用方針`)を所有する型のことである(`crates/blitz_app/src/world_execution/`)。本判断は、判断11が示していた「`ゲーム配線`が共有される状態を`世界実行`へ渡してゲーム固有の振り分けだけを残す」という向きを採る。Issue #46の「現行の`ゲーム配線`の上か横に世界実行の境界を置き、現行ゲームを差し替えの間だけ置く振り分けの層として呼ぶ」という案は、段階移行の形として満たす。`ゲーム配線`を包むだけの型は、全メソッドが振り分けへ委譲するだけの束ねただけの階層になるためである。共有される状態を`世界実行`が持つと、`render_supply.rs`・`camera_supply.rs`・`tick.rs`で2つの枝が同じ本文を持っていた10のメソッドの振り分けが消え、`ゲーム配線`にはゲーム固有の状態(`場所巡りのゲームの状態`・`道順`・`ゲーム操作の出どころ`・`ゲーム更新の回数`・`歩くだけのゲームの状態`)と`一刻み進める`の振り分けだけが残る。各ゲームの`一刻み進める`は、共有される状態のうち触るもの(台帳・高さ場の読み口・移動の記録・操作の適用方針)を`一刻みが借りる共有の状態`という名前の付いた借用の束で受け、`世界実行`を丸ごと受けない。

遊ばない起動(`--game`の指定が無い起動)でも共有される状態は在る。台帳は動く個体を1体も持たず、高さ場は持たない世界、カメラはプレイヤー用の初期値、移動の記録はまだ刻んでいない記録である。遊ばない起動が刻みも操作の確定もカメラの操作も高さ場の読込も1つも行わないことは、`ゲーム配線`の`ゲームを遊ぶか`という1つの判定が各入口の先頭で決める。共有される状態を遊ばない起動で`Option`にしないのは、空の台帳と持たない世界の読み口が「何もしない」をそのまま表せる値であり、無い場合の分岐を入口ごとに書く形が判断11の指摘した「遊ばない枝を全メソッドへ書く」重複を`世界実行`へ持ち込むためである。

| 層 | 持つもの | 知ってよいもの | 知ってはならないもの |
|---|---|---|---|
| `アプリ`(`crates/blitz_app/src/app/`) | `世界実行`の所有と、描画機会・固定刻みの工程順 | `世界実行`の入口と、両側が読む値の型(`world_execution::contract`) | `ゲーム配線`・各ゲームの配線・`ゲーム状態の台帳`(`pub(in crate::world_execution)`で閉じる) |
| `世界実行`(`crates/blitz_app/src/world_execution/`) | 共有される状態、時間意味ごとの入口、`刻み入力`・`刻み結果`・`描画供給`の型 | `crate::world_execution::game`(旧`crate::game`)・`blitz_game`・`blitz_engine`・`blitz_render`の値の型 | レンダラーの資源の生成と破棄、ウィンドウ、ストリーミングの調停の内部 |
| `ゲーム配線`(`crates/blitz_app/src/world_execution/game/`) | ゲーム固有の状態と`一刻み進める`の振り分け | 従来どおり | 従来どおり |

本判断は、「値の型は共有し、配線の型は閉じる」という線を引く。`読込済みチャンクの形の出どころ`・`表示距離の指示`・`この描画のカメラの入力`・`ゲーム用高さ場`・計器と要約は`アプリ`の側が組み立てるか読むため`pub(crate)`のままとし、本判断はこれらを`world_execution::contract`へ置く(`刻み入力`・`刻み結果`・`描画供給`・`表示距離の指示`・`この描画のカメラの入力`・`ゲーム用高さ場`は`contract/`配下で定義し、計器・要約・出どころ・実装エラーはそれを作る型と同じ場所で定義して`contract`がそのまま見せる)。本判断は、`世界実行`が`blitz_render`の値の型(`描画シーン素材`・`描画束ID`)を受けることを許し、資源の生成と破棄を行わないことを「知ってはならない」の意味とする。`世界実行`を`blitz_app`に置くのは、`blitz_game`の依存の白リスト(`xtask/src/conform/dependency_whitelist/ledger.rs`)が`blitz_math`だけを許し、現行の`ゲーム配線`が`blitz_render`・`blitz_engine`・`crate::cli`・`crate::input`を使うためである。

入口は時間意味ごとに6つである。本判断は、`アプリ`から`ゲーム配線`へ触っていた13ファイル19箇所をこの6つへ写す。

| 時間意味 | 入口 | 中身 |
|---|---|---|
| 起動時 | `起動設定から作る(遊ぶゲーム, モード)`・`カタログから高さ場を読み込む`・`高さ場を据える`・`動く個体を描画束へ宣言する` | 起動時の据え付け |

| 低頻度 | (無し) | 2026-09-19時点で低頻度の処理は0件であり、周期は固定刻みの工程が持つ(判断13)。低頻度の型は置かない |
| 必要時(外から来たデータの反映) | `カタログから高さ場を読み込む`・`高さ場を据える`・`動く個体を描画束へ宣言する` | ホットリロードの反映が呼ぶ。反映の順序は判断11の`資源の配線`が持つ。構造変更の予約を積まず、自分で反映のセッションを閉じる(判断13) |

本判断は次を型でなく工程の並びと試験で守る。第1に、描画の値を固定刻みへ戻さないことは`刻み入力`の型が守る。本判断は、供給の型に`&mut 世界実行`の借用を持たせて縛る形を採らない(`frame.rs`の`描画機会を通す`は`&mut self`の工程を5つまたぐため、借用を持つ供給は書けない)。第2に、`刻み入力`の前へ進む向きの方位角は、`世界実行`がカメラの更新より前に読んだヨーから作る(`_doc/設計/時間の規律.md`「判断6」「入力の規律」)。この読む地点の順序は`app/frame.rs`と`app/frame/game_steps.rs`の工程の並びが守り、型も試験も守っていない。試験(`crates/blitz_app/src/world_execution/tick_input_tests.rs`)が固定するのは、`刻み入力`が生成の後にカメラが動いても生成時のヨーから作った向きを保つことまでである。順序を型で守る形(ヨーを読む口がカメラの更新より前にだけ開く形)は、固定刻みの工程を明示するIssue #50で扱う。#50で検討し、証の値(カメラの更新より前に読んだヨー)を刻みの入口とカメラの更新の両方が引数で受ける形は、証の値を2度発行できる(カメラの更新の後に読み直した値で刻みを回せる)ため型で守れないと判断し、工程の並びだけが守る形を裁定した(判断13)。ヨーは1描画に1度確定した`刻みごとの操作入力`が持ち、`刻み入力`はその器から生成するため、ヨーを読む地点は入力の確定の呼び出しに閉じる。第3に、指定一覧を預け出している最中に混ぜ直すことは実行時の検査(`draw_supply.rs`)のままであり、本判断は型で守らない。

低頻度の処理は0件であり、周期は固定刻みの工程が持つ。`アプリ`から見える口は`一刻み進める`のままであり、本判断は低頻度の型を置かない(判断13)。`blitz_ecs`は`blitz_app`の依存の白リストに無く、「アプリはECSの内部を知らない」はクレート単位で機械強制されている。親は、白リストへ入れる変更と`world_execution`配下以外での使用を禁じるファイル単位の検査の追加を、利用者が現れるIssue #55で同じPRとして行う。

### 判断13: 固定刻みの工程は段の並びを1箇所に持ち、規則の内部の順序は規則が持つ(2026-09-19、Issue #50)

固定刻みの工程とは、`世界実行`の`一刻み進める`が1刻みぶんの処理を段の並びの順に回す工程のことである。本判断は、Issue #50(ECSのSystem実行順と時間意味を明示し、万能Schedulerなしで世界更新工程を作る)の裁定として、段の並び・固定刻みの時間意味を持つ処理の一覧・番号の所有者・構造変更と物理の境界を定める。段の並びの正本はコードでは`world_execution/tick_stage.rs`の`固定刻みの段の並び`(11段の宣言的リテラル)であり、本判断の表はその写しである。

**工程の段の順序と、規則の内部の順序と条件を語として分ける。** 工程の段の順序とは、固定刻みの工程が段を回す順序のことであり、`世界実行`が所有する。規則の内部の順序と条件とは、ゲームの規則の1刻み(`blitz_game`の`一刻み進めた状態を返す`)の中で、進行段階の遷移・移動・到達判定がこの順で走り、遷移の結果で移動と到達判定を行うかどうかが決まることであり、`blitz_game`が所有する。本判断は、規則の1刻みを段ごとの処理へ分解しない。分解すると、規則の不変条件(メニューの裏で位置が動かない)の守り手が1箇所から複数箇所へ増えるためである。ゲームの規則の1刻みは1つの処理として、意図の生成からゲームの状態遷移までの段をまたぐ。

段の並びは次の11段である。Issue #50の本文の10段と`_doc/設計/ゲーム実行基盤.md`第6節の10段は「移動と作用の要求」と「アニメーション等のゲーム上必要な状態更新」の有無で食い違っており、本判断はどちらも落とさない和集合を採る。後から段を消す変更は足す変更より安全であるためである。処理を持たない段も名前のある位置として並びに残す。

| 順 | 段 | 2026-09-19時点でこの段に入る処理 |

**固定刻みの時間意味を持つ処理の一覧。** 本判断は、固定刻みで進む処理を`世界実行`の内側のものに限らず、`アプリ`の描画機会の工程が刻み数を受けて回すものも含めて1つの表に置く。走り方は2つある。「刻みごとに工程の中で走る」とは、上の段の並びの中で1刻みにつき1回走ることである。「まとめて走る」とは、固定刻みの処理が刻み数を受けて描画機会に1回で走ることである。

| 処理 | 段 | 走り方 | 遊ばない起動で走るか | 置き場 |
|---|---|---|---|---|
| ゲームの規則の1刻み | 第3段から第8段 | 刻みごとに工程の中で走る | 走らない | `world_execution/game/fox_tour.rs`・`walk_only.rs` |
| 刻みの確定(台帳への書き込み) | 第11段 | 刻みごとに工程の中で走る | 走らない(書く個体が無い) | `world_execution/tick.rs` |
| 布の入力(シミュレーションの工程の積み込み) | 第6段に相当 | まとめて走る(刻み数ぶんの工程を1描画で積む) | 走る | `app/frame.rs`の`この描画の布入力を作る` |
| アニメーション時刻と天空 | 第9段に相当 | まとめて走る(刻み数×基本刻みの秒を1回で足す) | 走る | `app/frame/clock_advance.rs` |

**まとめて走ることを許す条件。** 刻みごとの中間の状態が刻みの境界の外へ出ないことである。アニメーション時刻は秒の和であり、刻みごとの途中の値を誰も読まない。布の入力はGPUへ積む工程の列であり、CPU側の状態を刻みごとに公開しない。この条件を満たさない処理(ゲームの規則の1刻みのように、刻みの結果を次の刻みが読むもの)は、まとめて走らせてはならない。

**番号の所有者。** 固定刻みの番号とは、起動から数えた固定刻みの番号のことであり、最初の刻みが0である(`app/time_step/fixed_tick_number.rs`)。`時間進行配線`が所有し、刻みを回す工程(`app/frame/game_steps.rs`)が1本ごとに進めて`刻み入力`へ載せる。遊ばない起動でも番号は進む。布とアニメーション時刻が固定刻みで進むためである。様式は描画機会の番号と同じ(64ビット・飽和なし・上限に達しないことを不変条件とする)である。`キツネの場所巡りの配線`の`ゲーム更新の回数`(`u32`の飽和加算)は消し、台本は`刻み入力`の番号を読む。番号が最初の刻みで0であるのは、消した「回数」が0から始まり刻みの後に増えていたためであり、台本の各段階が当たる刻みが1つもずれないことを試験が固定する。**番号の型に剰余の演算(`Rem`)を実装しない。** 周期の判定(`何刻みごとか`)を処理の中に書けなくするためであり、最初の低頻度の処理が現れるPRが、工程だけが呼べる判定の口を足す。低頻度の処理は2026-09-19時点で0件であり、周期は工程が持つ。本判断は低頻度の型を置かない。

**構造変更の反映の境界。** 構造変更の反映は固定刻みの先頭の段(前刻みからの構造変更の確定)で行い、`blitz_ecs`の`構造変更の反映`(セッション型)をここで閉じる。予約は`blitz_ecs`の`構造変更の予約`へ積み、積むのは最後から2番目の段(構造変更の予約)と、ゲーム側の必要時の処理(経路探索等。2026-09-19時点で0件)である。描画機会の入口は反映も予約もしない。描画が破棄済みの個体を1描画描かないことは、刻みの確定の段が台帳へ書いた供給値だけを描画が読むことで守る(予約で破棄された個体の供給値は刻みの確定の段が書かない)。外から来たデータの反映(ホットリロード)は予約を積まず、自分で反映のセッションを閉じる。遊ばない起動は刻みを進めないため、予約を積むと永遠に反映されないからである。個体群の所有と処理の中身はIssue #55が足す。

**物理の境界。** 物理を一刻み進める段の処理は`blitz_sim`の1刻みの入口を1回呼ぶだけであり、処理が拘束の反復や細分を直接回すことを禁じる(`_doc/設計/時間の規律.md`「判断7」の内部細分は`blitz_sim`の内側である)。今のプレイヤーの移動は物理世界を通らない掃引であるため、移動と作用の要求の段に置く。接続はIssue #43が行う。

**引き金。** 本判断は、処理ごとの契約トレイトと、構築時に同じ段の書き衝突を検査する工程のビルダーを置かない。2026-09-19時点の処理は別の段に1つずつ入り、2つのゲームは同時に走らないため、検査は発火できない。処理は自分の状態を持たないため、処理側の型を作ることは「処理側に所有すべき状態が無いなら型を作らない」(CLAUDE.md「依存の設計」)に当たる。判断2の引き金に倣い、**同じ段に2つ目の処理が入るPRが、処理の契約(段・読む状態・書く状態)の型と、同じ段の書き衝突の検査を入れる。**

**守っていないこと。** 処理の契約(段・読む状態・書く状態)は、各処理のファイルの冒頭コメントの宣言であり、型で強制しない。段の並びを`match`で回す形は、11段すべてが使われることをコンパイラが見る点までを守る。

Issue #50の完了条件の読み替えは次のとおりである。「固定刻みのSystem順が1箇所から読める」は、段の並びが1箇所であることとする。処理の並びはゲームごとに違う(キツネの場所巡りは規則の1刻みと刻みの確定、歩くだけも同じ2つ)ため、段ごとに何が走るかは本判断の表と`ゲーム配線`が持つ。「必要時」は2つある。外から来たデータの反映(判断12の入口。実装済み)と、ゲーム側の必要時(経路探索等。0件)である。

## オーナー決定(2026-08-09)

### クソゲー1本目の仕様

- タイトル画面から始まり、Escキーで終了を選んで終わるまでの一連の流れを持つ
- マップは自動生成する(乱数の種を与えたオフライン生成。規模は小さく始める。生成の器は大規模化と同じものを使う)
- Fox(手元にある唯一のアニメーション付きアセット)で移動し、指定された場所を巡る
- 足りないアセットはBlenderで制作してよい

### ブレス オブ ザ ワイルド級の能力検証の方式

- 乱数の種を与えた手続き生成(規則と乱数から地形と配置を計算で作ること)で約8km×10kmのマップを事前に生成し、その中を移動して性能を測る。無限に生成し続ける仕組みは当面要らない
- 壁打ちで現物を確認した既知の壁が3つある。第一に、常駐の範囲の外にある遠景が描かれない(先読み半径の上限は16であり(`crates/blitz_app/src/cli/value_args.rs:79`)、一辺100メートルのチャンク(`crates/blitz_app/src/app/streaming.rs:18`)では3.3km四方までしか届かない。遠景の表現を新設しなければならない)。第二に、地形の全てのLOD段を常駐させるVRAMの費用が読めていない(現在の予算は先読み半径1を前提に組んである)。第三に、生成とコンパイルの物量である(現行の器は5×5チャンクの見本であり、8000チャンクは約320倍にあたる。増分コンパイルが無いままでは反復が詰まる)。加えてCPU側の可視選別の折れ点も同じ場面で測る
- LODの制御は小規模の世界に計器を付けてから実測に基づいて壁打ちする。実施はクソゲー1本目の後の第2弾である

## 第1段階の定義

クソゲー1本目の土台として作るものを10項目に確定する。壁打ちで挙がった不足9要素の裁定を含む。

1. **blitz_gameクレートの新設**(依存はblitz_mathのみ。blitz_engineへの依存は実際に必要になった時点で白リストの審査とセットで足す。ゲームの状態機械=タイトル・プレイ・終了確認、場所巡りの進行、素朴な構造体の群れで持つ個体を置く)
2. **ゲーム更新の挿入**(判断1の形。パターンAのまま固定刻みで進め、時間源の決定性の分岐を最初から入れる)
3. **ゲームインテント**(移動2成分・決定・キャンセル)と、その写像および適用方針の継承
4. **動的な個体の変換の供給**(判断5の形。ゲーム状態の台帳、GPUへの毎フレーム書き込み経路、動的な個体の束)
5. **カメラの追従モード**(オービットカメラへ追従を足す。ゲームからカメラへの接続を作る)
6. **地形の高さの実行時参照**(高さ場のアセット種別と読み口)
7. **スキン付き個体と地形世界の共存**(Foxを起動シーンの束0として読み、地形はチャンク束で合成する。スキンが1つだけという構造は変えない)

9. **タイトル画面とEscメニューのUIはeguiで代用する**(本番のUI系統は新設しない。1本目の役割は要求を記録することである)
10. **目的地の目印**(目印のメッシュの配置と距離の判定)

### 工程4で確定した実装の形

項目7から項目10までを1つの世界へ収めた結果、次の形が確定した。

- 世界は`fox_tour_world`という名前で焼き、起動時に読むキツネのシーンの安定IDを`terrain_fox_tour`にした。安定IDが`terrain`で始まることが空方針・間接照明方針・露出方式・拡散間接方式を地形の本番世界と同じものにする。時間再構成だけは外す。動く個体が前のフレームの変換を持たず、混ぜると歩くキツネが尾を引くためである
- キツネの標準サンプルは体長がおよそ120で書かれているため、寸法を合わせる一様倍率100分の1を掛けて焼く。倍率はローカルからワールドへの変換に載るため、平行移動と天頂軸まわりの向きを毎フレーム差し替える動く個体の経路をそのまま通る
- 目的地は水平の位置だけをゲーム側の表が決め、天頂成分は世界の高さ場を据えるときに地表へ置き直す。目印の柱はその場所のチャンクのシーンへ焼き込むため、チャンクと一緒に読み込まれてチャンクと一緒に解除される
- 目的地の水平の位置はゲームロジック層の道順とアセットコンパイラの宣言の2箇所にあり、どちらも整数のメートルで書いて目で突き合わせる。1箇所に畳めないのは、ゲームロジック層がblitz_mathだけに依存し、アセットコンパイラの型を知らないためである
- 遊ぶ世界の地面は草地に近い暗さを取る。検収の世界の白い地面のままでは、自動露出が画面のほとんどを占める地面へ合わせて地面が白く飛ぶ。検収の世界の地面は白のままであり、既存の判定値は動かない
- 遊ぶには世界を開く5つの起動指定(シーン名・アセットルート・ストリーミングの有効化と先読み半径と容量上限)が要る。手で並べると検収が通った条件と違う条件で遊ぶことになるため、`cargo xtask play-fox-tour`が同じ1箇所を読んで起動する

- `cargo xtask play-fox-tour`: 遊ぶ。起動の前に、これから遊ぶマップがどの乱数の種の生成物かを出す。操作はEnterではじめる・矢印キーで歩く・Escで終了確認である
- `cargo xtask gen-game-map --seed <32ビットの非負整数>`: 別の種でマップを作り直す。リポジトリへ収めた`assets/fox_tour_world/`は種20260810の生成物である
- `cargo xtask game-fox-tour`: 検収する。同じ種から同じマップが出ることと、決定的な台本がタイトルから終了まで1周することを機械で判定し、目視の材料として4枚の絵を書き出す。この入口は検収の種でマップを作り直すため、別の種で遊んでいたときは走らせた後に種の表示が変わる

### 現状の実態のうちこの完了で動いた項目

- 「ゲームの実体を置く場所、振る舞いを書く場所」が無いという記述は、blitz_gameの新設で解消した。オブジェクト単位の生成と破棄の口は依然として無く、動く個体は起動時に1体だけ登録する形のままである
- 「毎フレーム更新されるのは可視ID列だけ」という記述は、動く個体の位置と向きの毎フレーム書き込みが加わって変わった
- 高さ場を宣言する世界が場所巡りの世界の1つだけであることと、レンダラー全体でスキニング一式が高々1つであることは変わっていない

### 繰り返し書いた配線の記録

「進め方」の3が求める、ゲームサイクル基盤の抽出判断の材料である。コンポジションルートがゲームへ触れる面は9箇所ある(生成・高さ場を据える・起動時の動く個体の宣言・ホットリロード後の動く個体の宣言・1刻み進める・位置の列の預けと戻し・カメラの追従・画面へ重ねる表示内容・終了時の要約)。この9箇所と、その受け口であるゲーム配線の側を通して、同じ形を2度以上書いたのは次の2つである。

1. **束の読込より前に動く個体を宣言する配線を2箇所に書いた。** 起動時のシーン読込(`crates/blitz_app/src/app/window_setup.rs:65`)と、ホットリロードでシーンを差し替えた後の再登録(`crates/blitz_app/src/app/draw_bundle_ledger/installation.rs`)である。束を作り直す経路が2つあり、どちらも宣言をやり直さないと動く個体が静的な枝へ戻るためである
2. **「ゲームを遊ばない起動では何もしない」という枝を、ゲーム配線のほぼ全てのメソッドに書いた。** 1刻み進める・高さ場を据える・動く個体を宣言する・位置の列を預ける・位置の列を戻す・カメラが追従する位置・画面へ重ねる表示内容・進行の要約の8つがそれにあたる。2026-09-18の判断12で共有される状態を`世界実行`が持つ形にしたため、この枝は`ゲーム配線`の`ゲームを遊ぶか`という1つの判定と、ゲーム固有の状態を読む4つの口(プレイヤーのエンティティID・刻み境界の確定位置・移動状態・画面へ重ねる表示内容)に減った

**1本目ではゲームサイクル基盤を抽出する判断材料が揃っていない。** 上の2つはどちらもゲームが1本しか無いことに由来する重複であって、複数のゲームに共通する形の重複ではない。1は束を作り直す経路の数の問題であり、2はゲームを回さない起動が存在することの帰結である。2本目を同じ器で作り、同じ配線をゲームをまたいで書いたときに初めて、何を基盤へ引き上げるかを判定できる。

### 第2弾への申し送り

- **高さ場の縁の検査は共有する縁の一列しか突き合わせていない。** 貼り合わせが重複する縁を片側だけ採る根拠を値で確かめる工程(`crates/blitz_asset_compiler/src/height_field/edge_agreement.rs`)は、辺分割数+1点の共有線だけを比べる。高さ格子は法線の中央差分のために重なり幅1の帯を共有線の外側へ持っており、この帯と隣のチャンクの内側の点は同じ大域の点を指すが突き合わせていない。3×3では生成器が同じ関数から全点を作るため食い違わないが、チャンクを別々に作り直せる大規模の生成では検査の穴になる
- **遠景が描かれない壁は1本目では現れていない。** 3×3の世界は先読み半径2で全チャンクが常駐するためである。8km×10kmでは「現状の実態」と「ブレス オブ ザ ワイルド級の能力検証の方式」が挙げた既知の壁3つ(常駐の範囲の外の遠景・地形の全詳細段を常駐させるVRAMの費用・生成とコンパイルの物量)がそのまま立つ
- **チャンク目録が1つの座標へ1つのアセットIDしか持てない制約は解いていない。** 1本目は世界全体で1つの高さ場アセットを持つ形で回避した(判断7)。チャンクごとに高さ場を運ぶ形はこの目録に載らない
- **目的地の水平の位置がゲームロジック層とアセットコンパイラの2箇所にある。** 1本目は整数のメートルで書いて目で突き合わせている。目的地が増えるか座標が細かくなった時点で、どちらかを他方から導く経路が要る
