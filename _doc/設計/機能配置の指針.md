# 機能配置の指針(レイヤー責務)

この文書は、新しい機能をどのレイヤーへ置くかの判断基準と、後から機能を追加したときに「綺麗に入らない」状態を防ぐ運用を定義する。実装と常に一致させて維持する。制定の経緯は開発スレッド2026-07-20(M6の振り返り)を参照。

## レイヤーの責務

## クレート内のモジュール依存(2026-07-26 OW2第6段で判定)

レイヤー間の依存はクレート境界が一方向に強制する。クレート内部のモジュール間では、`blitz_engine` の `asset` と `streaming` が双方向に参照している。`asset::runtime_format::chunk_directory_v1` が `streaming::チャンク目録` を読み書きの対象として参照し、`streaming::directory_loader` が `asset` の読込関数を呼ぶ。

**この双方向は配置を変えても消えない。** チャンク目録は「チャンク座標からアセットIDへ」の対応であり、`chunk` の座標と `asset` のアセットIDを必然的に結びつける型である。目録を `chunk` へ移すと `chunk` から `asset` への参照が生まれ、`asset` から `chunk` への参照(描画対象データが所有チャンクを持つ)と合わせて同じ循環になる。消すには `アセットID` と `チャンク座標` の双方を最下層の共通モジュールへ移す必要があり、`アセットID` は `asset` の中心概念であるため不自然な再編になる。

したがって現状を許容する。ただし2つの制約を記録する。第1に、`blitz_engine` を `blitz_asset` と `blitz_streaming` のような別クレートへ分割する余地はこの循環が閉じている。分割が必要になった時点で、共通の最下層クレートを切り出す再編が前提になる。第2に、この許容はチャンク目録という1つの型に由来する循環に限る。他の関心で双方向参照を増やすときは、同じ必然性があるかを個別に判定する。

## 機能配置の第一原則: 仕組みと方針を分けて置く

機能は多くの場合、次の2つの部分に分解できる。

- **仕組み(mechanism)**とは、特定の用途を知らないGPU能力のことである。例: 深度のみの描画パス・比較サンプラー・テクスチャへの描画・ストレージバッファ・バリア導出。仕組みは blitz_render に置く。
- **方針(policy)**とは、仕組みを特定の絵のために組み合わせる決定のことである。例: どの光源に何枚のシャドウマップを割り当てるか・多段の分割距離・どのメッシュが影を落とすか。方針はシーンを知る側に置く(blitz_engine)。

シャドウマッピングを例にすると、深度のみパスと比較サンプラーは仕組み(render)、ライト行列の作り方と「シャドウパスを積む」という決定は方針である。M6ではどちらも render 内に実装したが、これは意図した足場であり、その後の方針部分の移管は下の「方針移管の現在状態」節が記録する。

## 方針移管の現在状態

- OW0第9段でライト方針をblitz_engineへ移し、blitz_renderは検証済みの`ライティング入力`をGPUへ書き込む実行能力だけを所有する。
- OW0第10段でフレーム構成をblitz_engineへ移した。blitz_engineは高水準なフレーム段階の依存順序を宣言し、blitz_renderは各段階をレンダーグラフの具体的なパスへ展開する。
- blitz_renderはフレーム構成の重複、依存順序、必須段階、素材との対応を検査する。これはVulkan資源を安全に実行するための能力側の制約であり、どの任意段階を採用するかという方針ではない。

## 「綺麗に入らない」の定義と対策

**「綺麗に入らない」とは、新機能が必要とする合流点(既存パイプラインへの接続点)が、既存機能の実装に占有されていて宣言的に共有できない状態のことである。** この状態で機能を追加すると、選択肢は2つしかない: 既存実装の侵襲的な書き換えか、並行インフラの複製である。後者が「同じ機能を持つものが2種類ある」現象(一般のアプリケーション開発でAIがサーバーを2つ作る現象と同型)の正体である。

デカールを例にする。デカールはシーン描画の「マテリアル決定とライティングの間」に割り込み、表面の材質パラメータを局所的に上書きする必要がある。もしマテリアル決定が単一シェーダーに焼き付いていて割り込む合流点が無ければ、デカール専用の第2の描画経路(第2の可視選別・第2のマテリアル適用)を作ることになり、以後すべてのマテリアル変更を2箇所へ適用し続ける負債が生まれる。

対策として本プロジェクトが備える合流点は次のとおり。

1. **パスの合流点 = レンダーグラフ**。新しい描画・計算の段はパス宣言の追加で入る(M6のシャドウパスが実例)。
2. **マテリアルの合流点 = 判別共用体の扉**(開発計画の絵の様式3条件)。単一シェーディングモデルを型・データ形式に焼き付けないことで、将来のマテリアル種別追加(トゥーン・デカール適用後の材質など)の割り込み位置を保つ。
3. **関心ごとの一意所有**。同じ関心に対する所有者は常に1つとする(下表)。2つ目の所有者を作る変更は、複製ではなく設計判断(開発スレッドの判断N)として明示し、理由なき並行インフラを禁止する。

**存在した合流点の不在(2026-07-25に測定して判明)は、OW5第2段(2026-07-30)で解消した。** レンダーグラフはパスを*宣言*する合流点として機能しており、M6のシャドウパスはパス宣言の追加だけで入った。しかしそのパスが読み書きする資源の*所有*には合流点が無く、`blitz_render` の `レンダラー` のフィールドになるしかなかった。この状態のまま、レンダラー直下のパイプライン群が増える見込み(空パスの追加)が実物になったOW5第2段で、`描画段階資源`という器を新設した。器はシーン段階・影段階・空段階・布専用シャドウ経路が使うパイプライン・パイプラインレイアウト・専用ディスクリプタ・専用画像を具体フィールドで持ち、段階の種類を鍵にした表では持たない。段階が増えるたびに`レンダラー`直下のフィールドが増える構造はこれで止まり、`レンダラー`直下には`描画段階資源`という1つのフィールドが増えるだけになった。生成は`create`、破棄は`レンダラー`の単一破棄元が担い、段階ごとの操作(大気のベイク済み画像・空段階)はそれぞれ専用の内部モジュールへ分けている。実装は`crates/blitz_render/src/renderer/draw_stage_resources/`、設計は`_doc/設計/空と時間帯と遠距離シャドウ.md`「描画段階資源の器と布専用シャドウ経路」を参照する。

測定した事実を残す。`レンダラー` のフィールド数はM0の16からM11の41へ単調増加した(平均+2.3/マイルストーン)。うち段階資源に帰属するのは+1.6程度で、残りは段階と無関係である。M6(影)・M7(ポスト処理)・M9(布)の3件はいずれも定義・生成・破棄・描画発行の4軸すべてを触った。段階の一覧は `blitz_render` 内で10箇所に列挙されており、そのうち4箇所(`レンダラー`・`フレーム資源`・`段別資源`・`フレーム画像一式`)は保管という同じ事実の複製である。

段階とフィールドは1対1ではない。影は2フィールド、シーンは2フィールドを持つ。逆に `深度バッファ`・`シャドウマップ`・`シェーダー定数`・`転送環境` は複数段階が共有し、うち `シャドウマップ` と `シェーダー定数` はシーンのディスクリプタセットに焼き込まれているため、影やシーンの資源として囲い込めない。

**注意: この合流点を「将来の段階が挿せるように」という予測で新設してはならない。** 判断基準3(将来のための汎用化はしない)が禁じる対象である。登録簿方式(トレイトオブジェクトまたは判別共用体で段階から資源への写像を持つ形)を検討して却下した。理由は、11個の段階資源のうち6個が非`Option`で「常に存在する」ことを型で表しており、容器へ入れると存在保証が実行時探索へ格下げされるためである(本文書の「無し・未設定は型に表す」の逆方向)。着手するなら、既存フィールドの再配置だけを行い拡張点を新設しない形で、フィールドが実際に増える見込みが実物になった時点とする。地形(OW3)は2026-07-28に完了したが、詳細段の幾何が既存の`シーン描画資源`の内側に収まったため`レンダラー`直下のフィールドは1つも増えなかった。着手条件が実際に成立したのは、空パスの追加でレンダラー直下のパイプライン群が増える見込みが実物になったOW5第2段である。既存フィールドの再配置(シーン・シャドウのパイプライン/レイアウトと、空・布専用シャドウの新設資源を`描画段階資源`という1つの器へ集める)だけで対応し、判別共用体や登録簿による拡張点の新設は行っていない。

| XPBDの距離拘束の正典式(CPUの参照計算。コンプライアンス・ラグランジュ乗数・刻み幅の型、一刻みの係数の導出、一回の射影と退化の枝)と、現在の布のGPU経路が実装している旧式(距離の誤差を逆質量の比で分配する)の写し | blitz_simのxpbd |

**ゲーム状態の台帳の置き場所は、宣言時のblitz_gameから実装時のblitz_appへ移した。** 台帳が持つ対応の片側(束ID・描画対象添字・個体添字)がblitz_renderの語彙であり、blitz_gameがそれを名指しすると、ゲームロジック層が描画レイヤーの型に依存する。写しのIDをblitz_game側へ作ると、写しと実物の対応を持つ2つ目の所有者が生まれる。どちらも避けるため、台帳はコンポジションルートのゲーム配線が持ち、ゲームの状態は位置の正本だけを持つ。

**高さ場の読み口が答えた高さをゲームロジック層の語彙へ写すのは、blitz_appのゲーム配線である。** blitz_gameがblitz_engineの高さ場の型を名指しすると、ゲームロジック層がアセット層へ依存する。写しは3つの枝の対応だけであり、2つ目の所有者を作らない。

新機能の設計判断では「どの合流点に入るか」「所有者表のどれを拡張するか(新しい所有者を作る場合はその理由)」を必ず書く。

## 判断フロー(新機能をどこに置くか)

1. 機能を仕組みと方針に分解する。
2. 仕組みは blitz_render の既存能力で足りるか確認する。足りなければ能力を render へ追加する(特定用途の名前を付けない。例: 「シャドウ用パス」でなく「深度のみパス」)。
3. 方針はシーンを知る側に置く(背骨期の足場として render に置く場合は、「方針移管の現在状態」節へ追記して移行対象にする)。
4. 上の所有者表と照合し、複製を作っていないか確認する。
