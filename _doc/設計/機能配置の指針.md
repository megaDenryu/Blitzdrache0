# 機能配置の指針(レイヤー責務)

この文書は、新しい機能をどのレイヤーへ置くかの判断基準と、後から機能を追加したときに「綺麗に入らない」状態を防ぐ運用を定義する。実装と常に一致させて維持する。制定の経緯は開発スレッド2026-07-20(M6の振り返り)を参照。

## レイヤーの責務

| レイヤー | 責務 | 知らないこと |
|---|---|---|
| blitz_math | 座標系・単位の数学 | 描画・シーン・GPU |
| blitz_asset_compiler(アセットコンパイラ) | glTFと画像の検証・デコード・実行時形式への変換 | GPU・ウィンドウ・毎フレーム実行 |
| blitz_render(描画レイヤー) | GPUで「どう実行するか」。パス・リソース・同期・パイプラインという能力の提供 | 特定の絵・特定のゲーム(理想。現状の逸脱は後述) |
| blitz_engine(エンジンレイヤー) | 「何を描くか」。シーン・アセット・マテリアルの表現と、それをレンダーグラフの語彙へ翻訳すること | Vulkan(ash)・ウィンドウ(winit)・glTF・画像デコード |
| blitz_app | 依存の配線・入出力(ウィンドウ・入力・CLI)・フレーム内実行順序の支配 | ロジック(書いてはならない) |
| shaders/ | GPU側のコード | CPU側の構造 |

## 機能配置の第一原則: 仕組みと方針を分けて置く

機能は多くの場合、次の2つの部分に分解できる。

- **仕組み(mechanism)**とは、特定の用途を知らないGPU能力のことである。例: 深度のみの描画パス・比較サンプラー・テクスチャへの描画・ストレージバッファ・バリア導出。仕組みは blitz_render に置く。
- **方針(policy)**とは、仕組みを特定の絵のために組み合わせる決定のことである。例: どの光源に何枚のシャドウマップを割り当てるか・カスケードの分割距離・どのメッシュが影を落とすか。方針はシーンを知る側に置く(現状は後述の足場、最終的には blitz_engine)。

シャドウマッピングを例にすると、深度のみパスと比較サンプラーは仕組み(render)、ライト行列の作り方と「シャドウパスを積む」という決定は方針である。M6ではどちらも render 内に実装したが、これは意図した足場であり、方針部分の所在は下の「既知の逸脱」で管理する。

## 方針移管の現在状態

- OW0第9段でライト方針をblitz_engineへ移し、blitz_renderは検証済みの`ライティング入力`をGPUへ書き込む実行能力だけを所有する。
- OW0第10段でフレーム構成をblitz_engineへ移した。blitz_engineは高水準なフレーム段階の依存順序を宣言し、blitz_renderは各段階をレンダーグラフの具体的なパスへ展開する。
- blitz_renderはフレーム構成の重複、依存順序、必須段階、素材との対応を検査する。これはVulkan資源を安全に実行するための能力側の制約であり、どの任意段階を採用するかという方針ではない。

## 「綺麗に入らない」の定義と対策

**「綺麗に入らない」とは、新機能が必要とする合流点(既存パイプラインへの接続点)が、既存機能の実装に占有されていて宣言的に共有できない状態のことである。** この状態で機能を追加すると、選択肢は2つしかない: 既存実装の侵襲的な書き換えか、並行インフラの複製である。後者が「同じ機能を持つものが2種類ある」現象(一般のアプリケーション開発でAIがサーバーを2つ作る現象と同型)の正体である。

デカールを例にする。デカールはシーン描画の「マテリアル決定とライティングの間」に割り込み、表面の材質パラメータを局所的に上書きする必要がある。もしマテリアル決定が単一シェーダーに焼き付いていて割り込む合流点が無ければ、デカール専用の第2の描画経路(第2のカリング・第2のマテリアル適用)を作ることになり、以後すべてのマテリアル変更を2箇所へ適用し続ける負債が生まれる。

対策として本プロジェクトが備える合流点は次のとおり。

1. **パスの合流点 = レンダーグラフ**。新しい描画・計算の段はパス宣言の追加で入る(M6のシャドウパスが実例)。
2. **マテリアルの合流点 = 判別共用体の扉**(開発計画の絵の様式3条件)。単一シェーディングモデルを型・データ形式に焼き付けないことで、将来のマテリアル種別追加(トゥーン・デカール適用後の材質など)の割り込み位置を保つ。
3. **関心ごとの一意所有**。同じ関心に対する所有者は常に1つとする(下表)。2つ目の所有者を作る変更は、複製ではなく設計判断(開発スレッドの判断N)として明示し、理由なき並行インフラを禁止する。

| 関心 | 唯一の所有者(現在) |
|---|---|
| フレーム構成(パスの列) | blitz_engine |
| メッシュ描画の経路 | ジオメトリバッファ+シーンパス |
| マテリアルの語彙 | マテリアルデータ(engine判別共用体)+マテリアル素材(render判別共用体)+scene.slang |
| 同期バリアの発行 | グラフ実行器 |
| 画面への出力 | スワップチェーン提示(1系統のみ) |
| 開発用UIの描画 | UIパス(本番UIは将来の別系統として計画済み) |
| アセットの参照 | 安定ID+カタログ |
| ソースアセットの読込 | blitz_asset_compiler |
| 実行時アセット生成のツール入口 | cargo xtask compile-assets |
| ソース依存の変更監視 | cargo xtask watch-assets |
| アセット実行時形式の読込 | blitz_engine |
| 必要チャンク集合と読込優先順 | blitz_engine |
| チャンクの必要性と非同期処理状態 | blitz_engineのチャンク台帳 |
| 実行時チャンクの非同期ファイル読込 | blitz_engineのチャンク読込器 |

新機能の設計判断では「どの合流点に入るか」「所有者表のどれを拡張するか(新しい所有者を作る場合はその理由)」を必ず書く。

## 判断フロー(新機能をどこに置くか)

1. 機能を仕組みと方針に分解する。
2. 仕組みは blitz_render の既存能力で足りるか確認する。足りなければ能力を render へ追加する(特定用途の名前を付けない。例: 「シャドウ用パス」でなく「深度のみパス」)。
3. 方針はシーンを知る側に置く(背骨期の足場として render に置く場合は、既知の逸脱の節へ追記して移行対象にする)。
4. 上の所有者表と照合し、複製を作っていないか確認する。
