# ゲーム世界の個体と個体構成要素

この文書は、Blitzdrache0のゲーム世界がどの種類の個体を持ち、それぞれの個体が持つ状態を誰が正本として所有するかを管理する設計正本である。あわせて、個体構成要素という型が自前ECS(エンティティ・コンポーネント・システム。ゲーム内の物を識別子と部品の表で持つ設計)の基盤との間で結ぶ契約の全集合を持つ。

正本の親はIssue #32(ゲーム世界の個体表現の列挙とECS採用の要否)であり、直接の親はIssue #44(アプリ境界と自前ECSの縦切り)である。本文書はIssue #48の成果物であり、個体構成要素の置き場と問い合わせの実装はIssue #49が担う。

## 目的

Blitzdrache0はこれまで、衝突・物理・描画・区域の出入り・アセット・時間進行・入力という、ゲーム世界の個体より下に置ける基盤を整備してきた。今後はキツネ・NPC・敵・箱・岩・扉・アイテム・発射物・破壊片・草・水・VRで触れる身体部位を、同じ世界モデルの上で扱う段階に入る。

そこで本文書は3つを確定する。第1に、どのゲーム上のものをゲーム世界の個体へ昇格させるかを決める。第2に、位置・姿勢・速度をはじめとする各状態の正本所有者を、ゲーム世界・物理・描画・アセットのいずれか1つへ確定する。第3に、個体構成要素という型が基盤と結ぶ契約を列挙し、その各契約をどこへ置くかを決める。

## この文書が管理しないこと

本文書は次を決めない。個体構成要素の置き場の実装方式(疎な集合か原型の表か)はIssue #49が決める。問い合わせの記述方式はIssue #49が決める。個体群に作用する処理の実行順と時間の割り当てはIssue #50が決める。物理との接続の配線はIssue #51が、描画供給の抽出はIssue #52が、区域の出入りと寿命の接続はIssue #53が、保存とエディターとの境界はIssue #54が決める。

具体ゲーム固有の状態の最終的な命名も本文書は決めない。本文書が決めるのは、その状態をゲーム世界の個体構成要素として置くかどうかと、その正本が誰かである。

## 語彙

一般的なECSの用語を、コードの主語としてそのまま持ち込まない。設計方式の名前としての`ECS`という略称は維持する。オーナーが2026-09-04にIssue #48で裁定した対応を次に写す。定義は `_doc/計画/ユビキタス言語.md` が正本として持つ。

| 一般的なECSの用語 | Blitzdrache0の語 |
|---|---|
| Entity | ゲーム世界の個体 |
| Entity ID | ゲーム世界の実行時個体ID |
| stable ID | 保存上の個体識別子 |
| Component | 個体構成要素 |
| Component storage | 個体構成要素の置き場 |
| World | ゲーム世界、およびその一部としてのゲーム世界の個体群 |
| Query | 個体群への問い合わせ |
| System | 個体群に作用する処理 |

名前を短くするために意味を落とさない。読み手が正本・寿命・役割・対象範囲を名前から読み取れることを、識別子の長さより優先する。

## 判定の原則

本文書が表を埋めるときに使った判定の原則を先に置く。表の各行はこの原則のどれかから説明できる。

### 原則1: ゲーム世界の個体はゲーム意味の粒度であり、基盤内部の計算の粒度ではない

草1本・布の頂点1個・XPBDの粒子1個・流体のセル1個・描画のインスタンス1個・三角形1枚を、機械的にゲーム世界の個体へ上げない。ゲーム世界の個体へ昇格させる条件は、次のどれかを持つことである。ゲーム上で独立に識別する必要がある。ゲーム上で独立した状態を持つ。個別に生まれて消える。保存の対象になる。相互作用の相手として個別に指される。持つ個体構成要素の組み合わせが実行中に変わる。

### 原則2: 個体構成要素は最小のフィールドではない

内部の不変条件を一緒に守る必要がある状態は、1つの個体構成要素として持ってよい。現物の `プレイヤーの状態`(`crates/blitz_game/src/player_state.rs`)は位置と向きの対と移動状態を1つの型で持ち、「移動で位置だけを更新して移動状態を置き去りにする」書き方を型で止めている。ECSへ移すことを理由にこの単位を粉砕しない。

個体構成要素を分ける理由は次のどれかである。個体ごとに有無が変わる。独立に付け外しされる。別の処理が横断して問い合わせる。寿命・保存・正本所有者が違う。

### 原則3: 配置は1種類ではない。正本所有者の違いを型の違いにする

万能の `Transform` を置かない。少なくとも次の5つを区別する。ゲーム規則が正本として持つ配置(非物理の個体)、キャラクター移動の確定状態(キャラクターの移動が決める)、運動学的物体の目標配置(ゲームが決めて物理へ渡す)、物理剛体への参照(位置と姿勢と速度の正本は物理世界)、変形体シミュレーションへの参照(頂点と自由度の正本は物理またはGPU)である。

動的な剛体の現在の配置をゲーム世界へ写した値を持つのは、写しが必要だと計測が示した場合だけである。そのときは `物理世界から写した確定配置` のように、派生した値であることを名前に含め、書き手を物理結果の反映の工程1つだけに限る。

### 原則4: 個体構成要素の名前は所有の意味を含む

外部の基盤への接続であること、または派生した値であることを名前が示す。`物理剛体への参照`・`描画する表現の指定`・`保存上の個体識別`・`物理世界から写した確定配置`がその形である。

### 原則5: 世界全体で1つしかない状態を個体へ偽装しない

ゲームの進行段階・場所巡りの進行・道順・世界の時計のように、その具体ゲームに1つしかない状態は、`〜のゲーム世界` にあたる構造体が直接所有してよい。現物の `場所巡りのゲームの状態`(`crates/blitz_game/src/game_state.rs`)が進行段階と場所巡りの進行を直接持つ形が、そのまま維持される形である。

### 原則6: 一時の値と作業領域を個体構成要素にしない

問い合わせの途中の接触の候補、1つの処理だけが使う作業領域、XPBDの内部の値、描画の補間のための一時の値を個体構成要素へ押し込まない。

### 原則7: 分類の標識を乱造しない

`プレイヤー`・`NPC`・`敵` を、中身を持たない個体構成要素として先に作らない。まず `操作入力を受け取る主体`・`陣営への所属`・具体の判断状態という実際の意味へ分解する。「プレイヤーであることそのもの」を横断して問い合わせるゲーム規則が実際に立ったときだけ、その要求を根拠に標識を足す。

## 現物の現在地

表を読む前に、2026-09-05時点でリポジトリに実在するものを列挙する。表の「現物」の欄はこの一覧を指す。

### ゲーム世界の側に実在するもの

- `プレイヤーの状態`(`crates/blitz_game/src/player_state.rs`)は `プレイヤーの位置と向き` と `移動状態` を持つ。`移動状態`(`crates/blitz_game/src/movement/movement_state.rs`)は接地中と空中の2枝であり、速度は空中の枝だけが持つ。
- `場所巡りのゲームの状態`(`crates/blitz_game/src/game_state.rs`)は進行段階・場所巡りの進行・プレイヤーの状態の3つを直接持つ。`歩くだけのゲームの状態` はプレイヤーの状態だけを持つ。
- `ゲームの進行段階`・`場所巡りの進行`・`場所巡りの道順`・`目的地` が実在する。道順は `キツネの場所巡りの配線`(`crates/blitz_app/src/game/fox_tour.rs`)が所有する。
- `エンティティID`(`crates/blitz_app/src/game/entity_id.rs`)は32ビットの番号を包む型であり、世代を持たない。採番する仕組みは無く、プレイヤーは0番の定数に固定されている。
- `ゲーム状態の台帳`(`crates/blitz_app/src/game/entity_ledger.rs`)はエンティティIDの列・前と現在の確定値の列・描画へ渡す指定の列の3本を同じ並びで持つ。これは描画へ供給する側の器であり、位置と向きの正本はゲームの状態の側にある。
- `動く個体の描画先`(`crates/blitz_app/src/game/entity_ledger/registration.rs`)は束のIDと描画対象の添字と個体の添字を持つ。

### 物理と衝突の側に実在するもの

- `剛体の識別子`(`crates/blitz_sim/src/rigid_body/body_id.rs`)は32ビットの番号を包む型であり、世代を持たない。`剛体の台帳`(`crates/blitz_sim/src/rigid_body/ledger.rs`)は登録と参照と書き戻しを持ち、破棄の口をまだ持たない。
- `剛体`(`crates/blitz_sim/src/rigid_body/body.rs`)は識別子・配置・質量特性・運動種別・実行状態を持つ。`運動種別` は静的と運動学的と動的の3枝であり、速度は静的でない枝だけが持つ。
- `材質の識別子`と`静的世界の接触相手の識別子`が `crates/blitz_sim/src/contact/` に実在する。
- `動く形の識別子`(`crates/blitz_collision/src/dynamic_index/identifier.rs`)は64ビットの番号を包む型である。この型は `blitz_collision` の外で1箇所も使われていない。
- 布は識別子を持たない。`布データ`と`布の参照計算`(`crates/blitz_sim/src/cloth/`)は1枚だけある前提で扱われ、粒子も拘束も並びの添字で指される。アプリは布を `Option` の1枚として持つ。
- 水は `crates/blitz_sim/src/sph/` の粒子と `crates/blitz_sim/src/surface_flow/` のセルであり、水域を指す識別子は実在しない。

### まだ無いもの

- ゲーム世界の実行時個体IDの採番と世代と失効の仕組みは実在しない。現物の `エンティティID` は定数で与えられ、破棄の口が無い。
- 個体構成要素の置き場と問い合わせは実在しない。個体の状態はゲームごとの専用の構造体が直接持つ。
- 保存上の個体識別子と、ゲームの状態を保存して読み戻す仕組みは実在しない。実在する `安定ID` はアセットを指す綴りであり、ゲーム世界の個体を指すものではない。
- ゲーム世界の個体を区域の出入りに合わせて生成し破棄する仕組みは実在しない。区域の出入りはチャンク単位であり、`チャンク状態`(`crates/blitz_engine/src/streaming/chunk_state.rs`)が読込待ちから解除待ちまでの7枝を持つ。
- `エンティティID`と`剛体の識別子`と`動く形の識別子`を結ぶ配線は実在しない。3つは幅も発行者も別であり、互いを写す口が無い。
- NPC・敵・動物・扉・アイテム・発射物・破壊片・VRで触れる身体部位に対応する型は実在しない。表のこれらの行は、要求から導いた設計であって現物の記述ではない。

### 描画と区域の側に実在するもの

- 描画の側に描画対象を指す1つの識別子の型は実在しない。描画は束のID(`描画束ID`)と束の中の描画対象の添字と個体の添字の3つ組で1体を指す。`描画対象ID`(`crates/blitz_engine/src/asset/render_object_id.rs`)はアセットの側の型であり、描画の側はこれを知らない。
- 束の読込のときにゲーム側が渡すのは `描画シーン素材`(`crates/blitz_render/src/render_scene_material/mod.rs`)であり、描画対象素材の列と `動く個体の宣言` の列を持つ。
- 描画機会ごとにゲーム側が渡すのは `フレーム描画入力`(`crates/blitz_render/src/frame_input.rs`)であり、その中の `動く個体の大域の位置と向きの指定` の列が動く個体1体ぶんの供給値を運ぶ。
- 区域を指す識別子は `チャンク座標`(`crates/blitz_engine/src/chunk/chunk_coordinate.rs`)であり、座標そのものが識別子である。区域から描画束のIDへは、座標の永続化した番号に固定の値を排他的論理和で掛けて写す(`crates/blitz_app/src/app/streaming/bundle_sync.rs`)。対応表を持たない。

## 表1: ゲーム世界の個体と状態の正本

この表は、題材にする16のものそれぞれについて、その状態と能力をどこへ置き、誰が正本として所有するかを決める。1つのものにつき1つの小表を持ち、小表の1行が1つの状態または能力である。列の意味は次のとおりである。

- 状態・能力: その個体が持ちうる状態、またはその個体が備える能力である。
- 置き場: その状態をゲーム世界の個体構成要素として置くか、ECSの外の基盤へ置くか、そもそも持たないかである。
- 正本所有者: その状態の値を決める権限を持つ唯一の側である。ゲーム世界・物理世界・衝突基盤・描画・アセットとソース・保存のいずれかである。
- 個体構成要素の型候補: 置き場が個体構成要素であるときの型の名前の候補である。
- 外部基盤を指すハンドル: その個体構成要素が保持する、外部の基盤が発行した識別子である。
- 更新する工程: その状態を書き換える工程と、その工程が走る頻度である。頻度の呼び名は `_doc/設計/時間の規律.md` が定める時間意味の4区分に従う。
- 保存: 保存の対象かどうかである。丸は対象、バツは対象外、候補は保存の仕組みが立った時点で対象にするという意味である。
- 区域の出入り: その個体を区域から読み出すときと読み込むときの扱いである。

### プレイヤーキャラクター

プレイヤーは「プレイヤーという種類である」ことで特別なのではない。操作入力の宛先になり、キャラクターとして運動し、ゲーム固有の状態を持つ個体として構成する。

| 状態・能力 | 置き場 | 正本所有者 | 個体構成要素の型候補 | 外部基盤を指すハンドル | 更新する工程 | 保存 | 区域の出入り |
|---|---|---|---|---|---|---|---|
| 実行中の識別 | 個体群の内部 | ゲーム世界の個体群 | 置かない。実行時個体IDそのもの | なし | 生成と破棄の境界 | バツ | 読み出しで失効してよい |
| 保存をまたぐ識別 | 個体構成要素 | 保存 | `保存上の個体識別` | なし | 生成時と復元時 | 丸 | 読み出し後も残す |
| 操作入力の宛先 | 個体構成要素 | ゲーム世界 | `操作入力を受け取る主体` | 入力の席 | 入力の適用(固定刻み) | バツ | 常駐している間だけ持つ |
| 位置と向きと移動状態 | 個体構成要素 | ゲーム世界 | `キャラクター移動の確定状態` | 世界の形を尋ねる口 | キャラクター移動(固定刻み) | 候補 | 読み出し時に保存用の状態へ写す |
| 身体の形と移動の規則 | 個体構成要素 | アセットとソース | `キャラクター移動に使う身体形状と規則の指定` | 形状のアセットID | 生成時と装備の変更時 | ソース由来ならバツ | 読み込みで作り直す |
| 描く姿 | 個体構成要素 | ゲーム世界とソース | `描画する表現の指定` | 描画のアセットIDと動く個体の描画先 | 装備と変身のとき | 候補 | 読み込みで作り直す |
| 生命と負傷 | 個体構成要素 | ゲーム世界 | `生命と負傷の状態` | なし | 戦闘と環境(固定刻み) | 丸 | 保存して復元する |
| 陣営 | 個体構成要素 | ゲーム世界 | `陣営への所属` | 陣営の識別子 | ゲームの出来事 | 候補 | 保存して復元する |
| ゲーム固有の進行 | 個体構成要素 | ゲーム世界 | 具体ゲームごとの型 | なし | 固定刻みと出来事 | 丸 | 保存して復元する |
| 見た目だけのアニメーションの位相 | ECSの外(描画) | 描画 | 置かない | アニメーションの資源 | 描画機会ごと | バツ | 作り直す |

現物では `プレイヤーの状態` が位置と向きと移動状態を1つで持ち、`キツネの場所巡りの配線` がそれを直接所有している。`キャラクター移動の確定状態` は、この現物の単位をそのまま個体構成要素へ移した名前である。プレイヤーであることを表す標識を作らない。操作の宛先が1人だけであるうちは、`操作入力を受け取る主体` からプレイヤーを特定できる。

| 状態・能力 | 置き場 | 正本所有者 | 個体構成要素の型候補 | 外部基盤を指すハンドル | 更新する工程 | 保存 | 区域の出入り |

| 生命と負傷 | 個体構成要素 | ゲーム世界 | `生命と負傷の状態` | なし | 戦闘(固定刻み) | 丸 | 保存して復元する |

### 遠距離で休眠する個体

これは個体の種類ではなく実行の状態である。少なくとも4つを区別する。通常の活動、低い頻度での活動、ゲーム上は存在するが詳細な処理を休ませている状態、実行時の個体そのものを持たない状態である。

| 状態・能力 | 置き場 | 正本所有者 | 個体構成要素の型候補 | 外部基盤を指すハンドル | 更新する工程 | 保存 | 区域の出入り |
|---|---|---|---|---|---|---|---|
| 実行の活動段階 | 個体構成要素 | ゲーム世界の実行 | `個体の実行活動段階` | なし | 活動の判定(独自の低い頻度) | バツ | 読み出しで消してよい |
| 物理の休止 | ECSの外(物理世界) | 物理世界 | 置かない | なし | 物理の刻み(固定刻み) | バツ | 作り直す |

物理の休止とゲーム上の休眠は別の概念である。両者を1つの真偽値へ潰さない。現物の剛体は `実行状態` として起きているか休止しているかを物理側で持っており、これがゲーム側の活動段階と混ざらないことがこの行の要点である。休眠しているからといって実行時の個体を必ず消すわけでもない。実行時の個体を持たなくした場合、その実行時個体IDは失効してよい。

### 区域の出入りで生き死にする個体

これも個体の種類ではなく、個体の寿命の扱いである。次の4つは互いに別の事実であり、1つの真偽値へまとめない。ソースまたは保存の上で存在すること、実行時の個体として存在すること、その区域が常駐していること、通常の活動をしていることである。

| 状態・能力 | 置き場 | 正本所有者 | 個体構成要素の型候補 | 外部基盤を指すハンドル | 更新する工程 | 保存 | 区域の出入り |
|---|---|---|---|---|---|---|---|
| ソースと保存の上の記述 | ECSの外(アセットと保存) | ソースと保存 | 置かない | なし | 読み込みと書き出し | 丸 | 実行時の個体が無い状態を正常とする |
| 保存をまたぐ同一性 | 個体構成要素 | 保存 | `保存上の個体識別` | なし | 生成時と復元時 | 丸 | 読み出し後も残す |
| 区域の常駐 | ECSの外(区域の出入りの基盤) | 区域の出入りの基盤 | 置かない | `チャンク座標` | 区域の出入り(独自の低い頻度) | バツ | 基盤が持つ |

読み込みは、ソースまたは保存の記述から基盤が必要なデータを準備し、ゲーム世界へ生成を要求し、安全な構造変更の境界で実行時の個体を作り、物理と衝突へ登録する順で進む。読み出しは、保存が必要なゲーム状態を退避し、外部の基盤の登録を解除し、安全な構造変更の境界で実行時の個体を破棄する順で進む。読み込み済みかどうかを表す真偽値を全個体へ持たせない。

## 候補から落としたもの

Issue #48が挙げた初版の候補17件は、名前を2つ改めたうえで全件が表2に残った。`描画上の表現` を `描画する表現の指定` へ、`ゲーム上の寿命` を `ゲーム上の残り寿命` へ、`活動の段階` を `個体の実行活動段階` へ改めた。改めた理由は、どれも「これは何か」への答えが元の名前だけでは決まらないことである。表現が何を指すのか、寿命が経過した時間なのか残りの時間なのか、段階が何の段階なのかが、元の名前からは読み取れない。

検討したうえで表2へ入れなかったものと、その理由を次に置く。

| 落とした候補 | 落とした理由 |
|---|---|
| `プレイヤー`・`NPC`・`敵` の標識 | 実際の意味へ分解できる。プレイヤーは `操作入力を受け取る主体`、NPCは具体の判断状態、敵は `陣営への所属` と交戦の状態で表せる。横断して問い合わせるゲーム規則が実際に立つまで作らない |
| 万能の `配置` | 正本所有者の違う5種類の配置を1つの型へ押し込むことになり、動的な剛体の位置がゲーム世界と物理の二重の正本になる |
| `動く個体の描画先` | 実行時個体から描画先への対応は描画へ供給する側の関心である。Issue #52が描画供給の台帳として整理する。現物でも `ゲーム状態の台帳` が持っている |
| 前と現在の確定値の2枚 | 描画の補間のための値であり、ゲーム世界の正本ではない。`_doc/設計/時間の規律.md` の判断6のとおり、描画へ供給する側に残す |
| 感知の結果 | 1つの判断の工程の中で作って捨てる一時の値である。複数の工程が刻みをまたいで使う要求が立った場合だけ、意味を限定した状態へ上げる |
| ゲーム上の水位 | 水のシミュレーションが正本であり、写すと二重の正本になる。必要なときに読み口から取る |
| 読み込み済みかどうかの真偽値 | 実行時の個体が存在しないこと自体を正常な状態として扱うため、この真偽値を全個体へ持たせる必要が無い |
| ゲームの進行段階・場所巡りの進行・道順・世界の時計 | その具体ゲームに1つしかない状態であり、`〜のゲーム世界` にあたる構造体が直接所有する。現物の `場所巡りのゲームの状態` が既にこの形である |
| 実行時個体ID そのもの | 個体群が個体を指すための鍵であり、個体構成要素として重ねて持つと二重の正本になる |

## 個体構成要素にしないもの
