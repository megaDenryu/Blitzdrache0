# レンダーグラフ設計

M5で導入する、フレーム内のGPU処理を「パス」の宣言的な列として記述し、同期バリアの配置を宣言から自動導出する仕組み。エンジン中核の型安全層。
語彙は `../計画/ユビキタス言語.md`（レンダーグラフ・パス・仮想リソース）に従う。

## 位置づけ（幹）

M0〜M4では各パス（シーン描画・読み戻しコピー・提示遷移）のバリアを手書きしてきた。
パスが増えるたび（M6シャドウ・M7ポスト・M9シミュレーション）に手書きバリアは組み合わせ爆発するため、実物経験を積んだこの段階でグラフへ置き換える（早すぎる抽象化の回避。開発計画M5）。

設計の狙いは3つ:
1. **正しさの機械化**: 「リソースの前回用途 → 今回用途」からバリアを機械導出し、人手のstage/accessマスク選定ミス（M1・M3で実際に踏んだ種類のバグ）を構造的に消す
2. **コンピュート第一級**: 描画パスとコンピュートパスを同じ語彙で扱い、シミュレーション層（M9〜）のバッファ共有を最初から成立させる
3. **計測の足場**: パス境界が明示されるため、パス別GPU時間計測が自然に載る

## 語彙と型（葉）

### 仮想リソース

グラフ構築時に宣言する論理リソース。
ハンドル（`画像ハンドル` / `バッファハンドル`、世代付き添字のnewtype）で参照し、実体（vkハンドル）はグラフ実行器だけが知る。

- **外部持ち込み**: スワップチェーン画像・深度画像・メッシュ/テクスチャ/UBO等、レンダラーが所有する既存リソースをグラフへ登録したもの。寿命はグラフの外
- **グラフ管理**: グラフが生成・保持する一時リソース（M5では粒子ストレージバッファ）。M5では「初回構築時に確保し毎フレーム使い回す」最小実装とし、フレーム内エイリアシング（メモリ再利用）はやらない。M7のポストプロセス中間画像（HDR・光のにじみ2枚）はスワップチェーン再構築と連動して作り直す必要があるため、グラフ管理でなくレンダラー所有の外部持ち込みで実装した（判断38）

### 用途（usage）

バリア導出の入力となる、パスがリソースをどう使うかの列挙:

```
画像用途   = カラー出力 | 深度出力 | シェーダー読み画素段 | 深度シェーダー読み
           | コンピュート書き | コンピュート読み | 焼いた画像の画素段参照
           | 転送元 | 転送先 | 提示
バッファ用途 = 頂点読み | インデックス読み | シェーダー定数読み | 頂点段シェーダー読み
           | コンピュート読み | コンピュート書き | コンピュート読み書き | 転送元 | 転送先
```

各用途は (stage mask, access mask, image layout) の3つ組へ写像される（1関数に集約）。

### パス

```
パス宣言 {
    名前: &'static str,                 // 計測・デバッグ表示用
    読み: [(ハンドル, 用途)],
    書き: [(ハンドル, 用途)],
    種別: グラフィックス { カラー: ハンドル, 深度: Option<ハンドル>, クリア指定 }
        | コンピュート
        | 転送,
    記録: クロージャ(記録文脈)          // 実際のコマンド発行
}
```

- 記録クロージャが受ける `記録文脈` は、宣言済みハンドルの解決（vkハンドル取得）とコマンドバッファ操作だけを許す内部型。宣言していないリソースには触れない（触るには宣言に書くしかない）ことで「宣言=真実」を型で守る
- グラフィックスパスの begin/end rendering（アタッチメント設定・クリア）は実行器が種別宣言から行い、クロージャはバインド+ドローだけを書く

### 実行モデル

- **実行順序 = 宣言順**（M5の確定判断）。OW0第10段以降はblitz_engineの`フレーム構成`が高水準な段階列を宣言し、blitz_renderが各段階を具体的なパス列へ展開する。トポロジカルソートによる並べ替え・自動並列化・デッドコード除去はしない。依存宣言はバリア導出だけに使う。並べ替えが利益を持つのは非同期コンピュート（マルチキュー）導入時であり、その時点でスケジューラを足す
- 実行器はパス列を走査し、各リソースの「最後の用途」を状態として持ち、用途が変わる箇所に ImageMemoryBarrier2 / BufferMemoryBarrier2 を発行してからパスを記録する。フレーム先頭のスワップチェーン画像は UNDEFINED から開始
- 進行中フレーム（フェンス・取得/提示セマフォ・UBO多重化）はグラフの外で現行実装を維持する。グラフは「1フレームぶんのコマンドバッファ記録」だけを担う

### 同期導出の規則

- 書き→読み（RAW）、読み→書き（WAR）、書き→書き（WAW）: 前用途と今用途の(stage, access) を src/dst に持つバリアを発行。画像はレイアウト遷移を伴う
- 読み→読み: 画像レイアウトが同じなら省略。異なればレイアウト遷移のみ発行
- アタッチメント用途（カラー出力・深度出力）のアクセスマスクは書き込みと読みの両方を持つ。LOADするパスはレンダリング開始そのものが読みであり、固定機能ブレンドを有効にしたパスは宛先のカラーを読み、深度テストは既存の深度値を読む。書き込みだけを持たせると、同じアタッチメント用途が続く区間の依存が書き込みから書き込みへの向きだけになり、LOADとブレンドの読みが可視化の範囲から外れる。LOADするかどうかで用途の枝を分けないのは、その情報が`パス種別`の`クリア指定`と同じであり、2箇所が食い違うと絵にしか現れない同期の欠陥になるためである
- 導出はvalidation layer（同期検証）を審判として検証する。導出規則の単体テストは「パス列 → 発行されるバリア列」の純粋部分を切り出して書く

## GPU計測（M5で同時導入）

- パス前後に `vkCmdWriteTimestamp2`（前=TOP_OF_PIPE相当は使わずALL_COMMANDS基準）。クエリプールは進行中フレーム数ぶん持ち、そのフレームのフェンス待ち後に `vkGetQueryPoolResults` で読み、`timestampPeriod` でns換算する
- 表示は移動平均（例: 60フレーム）で開発用UIへ。`前提:` timestampComputeAndGraphics 対応キュー（非対応GPUでは計測無効を明示表示し、描画は続行）

## 開発用UI（egui。本番UIとは別系統）

- egui + egui-winit を採用（READMEの採用表参照）。描画はeguiの出力メッシュをVulkanで描く自作ペインタを blitz_render 内部に実装し、**UIパスもグラフ上の1パス**として載せる（グラフの実利用例を増やす）
- 開発用UIは書き捨て可能の位置づけ（README採用方針）。本番ゲームUIはリテインドモードで別系統（開発計画・長期フェーズ計画参照）

## M5のDoD対応

- 既存機能（シーン描画・読み戻し・提示）がグラフ上で同一動作 → スモークの厳密判定が変更なしで通ることが証明になる
- 手書きバリアが残っていない → `cmd_pipeline_barrier2` の呼び出しがグラフ実行器（とテクスチャアップロード等のセットアップ時転送。フレームループ外は対象外）に限られることをgrepで確認
- コンピュートパスの実証 → GPU粒子トイ（ストレージバッファをコンピュートで更新し頂点シェーダーが同バッファを読む）がグラフ上で描画と同期して動く
- パス別GPU時間が開発用UIに出る
