# マルチマテリアルと材質境界

この文書は、1メッシュ複数マテリアル(マルチマテリアル)への入力契約の拡張と、材質を表す型の境界(シェーディングモデル・材質特徴・固定機能状態の3軸)の設計を管理する。実装と常に一致させて維持する。本文書の大部分は設計先行の決定であり、「実装済み」と明記した節以外はまだ実装されていない。

設計の経緯は次のとおりである。オーナーが2026-07-30にマルチマテリアル対応と技術ビジョン第8章順1(方式境界の設計壁打ち)の開始を許可し、codexとの設計壁打ち(AgentRoom「ゲームエンジン開発室」連番205-206)で本設計を確定した。関連する技術ビジョンの節は `_doc/計画/技術ビジョン.html` の4.3節・第6章(a)(d)・第8章である。

## 決定の要約

3つの決定が背骨である。

1. **可視性の単位は個体のまま、描画の単位だけをプリミティブへ展開する。** 可視ID列の意味は今後も「可視な個体ID」であり、プリミティブIDを混ぜない
2. **材質はシェーディングモデル・材質特徴集合・表面描画状態の3軸へ型で分ける。** 材質変種キーはこの3分類から中央の1工程で導出し、パイプラインキーが材質変種キーへパス種別とジオメトリ変種を合成して実際のシェーダーとPSOを一意に選ぶ
3. **実行時形式のマルチマテリアル版(scene v4)はBC圧縮+ミップの版(将来v5)と分ける。** 1版に束ねると2つの独立な移行の不具合を分離できなくなるためである

## 入力契約と実行時形式(scene v4)

1つのLODメッシュを「頂点/インデックスの共有格納+非空のプリミティブ列」で表す。各プリミティブは、インデックス区間・頂点基準(vertex offset)・材質スロットIDを持つ。

- **材質スロットID**は原型ローカルな材質の置き場所の番号である。原型はLODごとのプリミティブ列とスロットの語彙を所有し、外側の描画対象が「材質スロットID→材質ID」の非空な材質集合を持つ。現行の「原型は形を、外側が材質を持つ」という責務分担を保ったまま、1材質を材質集合へ一般化する
- LOD間でプリミティブ数は一致させない。ただし参照する材質スロットIDは原型のスロット集合内に限る。未使用スロットは許容し、存在しないスロットへの参照はアセットコンパイル時のエラーにする
- glTFのmaterial indexは入力境界だけの番号であり、実行時には材質スロットIDへ正規化する
- 実行時形式は**scene v4**としてマルチマテリアルだけを追加する。v3→v4の変換は「既存メッシュ=プリミティブ1件・スロット0」「既存の単一材質=要素1件の材質集合」であり、後方互換は版ごとの型+最新への変換で表す(コーディング憲法のシリアライズ互換方針)。BC圧縮+ミップ生成はテクスチャ格納方式という別の移行軸のため、将来のv5へ分ける

棄却した案: 全プリミティブを連結して先頭材質を採る案(作者が分けた材質境界を消す)。プリミティブごとに独立メッシュ資源を作る案(頂点/インデックス格納とLOD境界の重複が増える)。マルチマテリアルとBC/ミップを1版に束ねる案(独立な変更を不可分にする)。

## 可視ID列の契約(第6段より先に確定する)

カリング(可視判定)は個体・原型・LODについて1回だけ行い、その結果の可視個体区間を、原型LODが持つ各プリミティブのdrawが再利用する。静的な描画片は「原型ID・LOD段・プリミティブ添字・材質スロットID」で識別し、フレームの描画束はそこへ「材質ID・パイプラインキー・可視個体区間」を結ぶ。材質別のまとめ(バッチング)は描画束をパイプラインキー→材質束縛→ジオメトリの順で並べ替えることで行い、同じ個体IDをプリミティブ数ぶん可視ID列へ複製しない。

OW5第6段(帯別カリングとID区間)との関係は次のとおりである。帯別区間は「群×シーン/4帯」の**個体**区間であり、マルチマテリアル展開は区間確定後の描画発行段で行う。この契約を先に確定すれば、第6段のバッファ形式をマルチマテリアル導入時に壊さない。第6段の実装自体は本設計の実装と並行できる。

棄却した案: (個体ID, プリミティブID)の組を可視ID列へ並べる案(カリング結果と帯別計数が材質都合でプリミティブ数倍に膨らむ)。材質ごとに再カリングする案(同じ境界判定の重複)。原型全体を1drawのままシェーダー内で材質を選ぶ案(材質境界を頂点データへ密輸し、固定機能状態と透明順序を扱えない)。

## 材質の3軸

材質に関わる可変性を3つの軸へ型で分ける。

1. **シェーディングモデル**は、照明式が相互排他的に変わる判別共用体である。初期は`標準金属粗さPBR`のみ。必要になったとき`非照明`を足し、後に表面下散乱・髪・水を追加する。モデル固有のパラメータは各腕の中に置く
2. **材質特徴集合**は、同じシェーディングモデル内で直交して有無が変わる機能のビット集合である。初期候補は法線テクスチャ・遮蔽テクスチャ・発光・頂点色。ビットと対応データ(テクスチャ等)の整合は材質の生成時に検証する。マルチマテリアルのスロットは材質IDだけを参照し、特徴ビットを複製して持たない
3. **表面描画状態**は、不透明/マスク/ブレンド・片面/両面・深度書込などの固定機能の軸である。材質特徴ビットへ入れず、パイプラインキーの型付き成分にする。スキニング・モーフ・頂点レイアウト・パス種別(シャドウ/シーン)も材質でなくジオメトリ/パスの軸である

キーは2段に分ける。**材質変種キー**は上の3分類だけから中央の1工程で導出するキーであり、材質能力の検証表(対応可能な組合せの閉じた一覧)の正本である。未対応の組合せはアセットコンパイル時に明示エラーにする。**パイプラインキー**は、材質変種キーへパス種別(シャドウ/シーン等)・ジオメトリ変種(頂点レイアウト・スキニング・モーフ)・必要な描画先状態を合成して導出するキーであり、実際のシェーダーとPSO(パイプライン状態オブジェクト)を一意に選ぶ。PSOの一覧・キャッシュの正本はパイプラインキーである。表面描画状態のうちシェーダーに影響しない部分はPSO選択だけに使う。2段に分けるのは、「材質にジオメトリ/パスの軸を混ぜない」と「パスでシェーダーが変わる」を両立させるためである。

コンパイル時のシェーダー分割は固定機能と大きく異なるモデル/パスだけに限定し、テクスチャの有無のような小さな特徴は材質データ+ビットで実行時に評価する(2^N本の事前生成をしない)。

棄却した案: 髪/肌/水を特徴ビットにする案(相互排他な照明式を同時ONにできてしまう)。全機能をモデルenumへ列挙する案(組合せ爆発)。全軸を1つのu64へ詰める案(不正な組合せを表現できる)。材質が任意シェーダー名を持つ案(検証・事前コンパイル不能)。

## 束縛バックエンドの移行境界

マルチマテリアルの型はGPUの記述子(ディスクリプタ)を知らない。描画束は不透明な材質IDだけを持ち、束縛の解決はレンダラー内部のバックエンドが行う。最初は既存の材質別ディスクリプタセットで材質IDを解決し、技術ビジョン第8章順1(c)のUBO分離+ディスクリプタインデクシング導入後に、同じ材質IDをstructured bufferの材質レコードとテクスチャ配列添字へ解決する形へ差し替える。この境界により、Blender段4(実アセット受入)を止めず、後の移行でアセット形式・実行時形式・可視ID列を変えずに済む。

UBO分離側の設計注記(順1(c)の壁打ちで詳細化する): frame constants・個体structured buffer・材質structured buffer・テクスチャ番号表を分ける。欠けたテクスチャをマジック番号で表さず、CPU側の`無し|有り(テクスチャID)`をGPU境界で特徴ビット+有効な添字へ変換する。

## Blender段4までの受理範囲

Blender実アセットの受理範囲は「1 glb内の1メッシュに複数の不透明な標準金属粗さPBR材質。プリミティブごとの材質。各LODでスロット集合内の任意プリミティブ列」までに限定する。透明・表面下散乱・髪・水・材質の動的差替え・個体ごとの材質上書き・GPU駆動間接描画は後段である。未対応のglTF機能は先頭材質へ縮退させず、glb契約検査器とアセットコンパイラで拒否する。

## 段階導入

各段は本番の呼び出し元を持って完了とする。

- **A. 契約・形式段**: scene v4(プリミティブ区間・材質スロット・材質集合)とv3→v4変換。アセットコンパイラが複数材質glbをv4へ焼き、実行時ローダーが往復することを検収する
- **B. CPU描画入力段**: ローダー→シーン構築→原型LOD+材質集合→描画束の本番配線。2材質アセットで2プリミティブ束が生成され可視個体区間を共有することを検収する。ディスクリプタは現行のまま
- **C. GPU描画段**: 同一個体を1回カリングし、2プリミティブ/2材質を実フレームで描く。プリミティブ境界の画素・draw数・可視ID数の不変を検収する
- **D. バッチ/計器段**: 変種キーと材質IDで描画束をまとめ、個体数・可視ID数・プリミティブdraw数・材質切替数・パイプライン切替数を別々に計測する。単一材質の既存シーンの画素/計数回帰も見る
- **E. Blender段4受入**: 実アセットを契約検査→コンパイル→実行時ロード→代表画素/計器まで通す。glb契約検査器の「複数材質の拒否」を「全プリミティブ保持」の検査へ置換する

実装順の推奨列(codex壁打ちの結論): 境界設計の確定(本文書)→scene v4+コンパイラ/ローダー→個体ID不変のプリミティブ描画縦切り→Blender段4の不透明標準PBR実アセット受入→UBO分離+ディスクリプタインデクシング→材質バッチ/PSO事前コンパイル→2つ目のシェーディングモデルで境界を反証→表面下散乱・髪・透明・水。
