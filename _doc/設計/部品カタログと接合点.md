# 部品カタログと接合点

この文書は、構造物と植物を無数のバリエーションとして作るための、部品の表し方・接合点の契約・展開の責務分割を管理する。実装と常に一致させて維持する。

**2026-08-15時点で実装は1行も無い。** この文書は着手前の設計であり、実装の到達点は「段の計画」節が持つ。文書が先行して実装したつもりになる事故を避けるため、段が進むたびにこの断り書きを更新する。

## 解こうとしている問題

オープンワールドの地図へ置く家と木に、個体ごとの違いを持たせたい。同じ家が並ぶ町も、同じ木が並ぶ森も、見た瞬間に作り物だと分かる。

素朴に解くと2つの道がある。どちらも行き止まりである。

**道1: 個体ごとに完成したメッシュを作る。** 家100軒なら100個のメッシュを作る。作る手間が軒数に比例し、メッシュ実体の数も軒数に比例する。描画発行数も軒数に比例し、`village_world` が実測した「1035体で発行11回」という性質が失われる。

**道2: 実行時にメッシュを変形する。** エンジンが頂点を動かして形を変える。エンジンがモデリング機能を持つことになり、`_doc/設計/機能配置の指針.md` の責務表が壊れる。メッシュ実体を個体ごとに持つことになるため、道1と同じ費用がかかる。

## 設計の核心

**バリエーションはメッシュの変形ではなく、部品の組み合わせで作る。**

**部品**とは、それ以上分けても組み合わせの自由度が増えない最小単位のメッシュのことである。家なら基礎・平壁・窓壁・扉壁・破風壁・屋根・煙突であり、木なら幹の一節・枝・葉房である。

家の形が軒ごとに違っても、使われる部品の**種類**は変わらない。壁Aと壁Bと屋根Cの組み合わせが違うだけである。したがって次が成り立つ。

```
描画対象1つ = 1部品 + その部品の個体配置の列
```

100軒分の壁が1つの配置列に入る。**描画発行数は部品の種類数に比例し、軒数には比例しない。** これは `village_world` が既に実測した性質と同じものであり、原型を部品へ置き換えるだけで得られる。

この設計が成り立つ根拠は、`blitz_engine` の `個体配置` が位置・回転・非一様の倍率を既に持つことにある。部品を任意の姿勢と大きさで置けるため、幹が上へ行くほど細くなる木も、既存の型の範囲で表せる。

```rust
個体配置::生成する([x, 0.0, z], 回転, [倍率; 3])?
```

## 責務の分割

| 決まる時点 | 担当 | 作るもの | 出力 |
| --- | --- | --- | --- |
| モデリング時 | Blender（外部リポジトリ） | 部品1つの形状と接合点 | glTF 1ファイル |
| 宣言時 | 本体の宣言表 | カタログに載る部品と、組み立て規則 | `examples/compile_assets/world/` の宣言 |
| ビルド時 | blitz_asset_compiler | 規則をシードで展開した部品ごとの配置列 | 実行時形式 |
| 実行時 | blitz_engine | 配置列を読んでインスタンス描画する | 絵 |

**エンジンが受け取るのは部品メッシュと接合点と配置列の3つだけである。** エンジンは組み立て方を知らない。展開済みの結果だけを受け取るため、`機能配置の指針.md` の責務表と衝突しない。

展開器はシードとカタログから配置列を作る純粋計算であり、bpy にも ash にも依存しない。Blenderもウィンドウも起動せずに単体テストできる。

## 接合点の契約

**接合点**とは、部品どうしを噛み合わせる位置・姿勢・接合面の寸法のことである。部品のローカル座標系で表す。

### 置き場所はglTFの`extras`である

部品ごとに変わる情報（位置・寸法）を本体の宣言表へ書くと、Blenderで部品を直したときに宣言表を直し忘れる形の二重管理になる。部品と接合点は同じファイルに置く。

一方、**どの種別とどの種別が対になるか**は部品を横断する知識であり、個々の部品のファイルには書けない。これは本体の型として1箇所に持つ。転記が発生しないため二重管理にならない。

### 形式

```json
{
  "接合点": [
    {
      "名前": "上面",
      "種別": "上面積層",
      "位置": [0.0, 0.0, 3.0],
      "向き": [0.0, 0.0, 1.0],
      "上方向": [0.0, -1.0, 0.0],
      "接合面": { "幅": 4.0, "高さ": 4.0 }
    }
  ]
}
```

キーと種別の値は日本語である。このデータを読むのは本エンジンだけであり、外部ツールとの相互運用を必要としない。グローバル規約が「英語名は読まないものとして扱う」と定めているため、読み手が意味を取れる日本語を使う。

**注意: glTFの仕様はJSONがUTF-8で符号化されていることを要求する。** テキストエディタでglTFファイルを直接編集する場合、Shift-JISなどで保存すると読み込みが壊れる。日本語のキーを使う以上、この事故は起こりうる。編集は原則としてBlender側の生成スクリプトから行い、手で開く必要があるときは文字符号化をUTF-8に固定する。

### 座標系は glTF に合わせる

**接合点の位置・向き・上方向、および接合面の幅と高さがどの軸に対応するかは、glTF の座標系（Y が上）で書く。** Blender の座標系（Z が上）で書いてはならない。

Blender の glTF 書き出しは頂点を Z が上から Y が上へ変換するが、**extras の値は変換しない。ただのデータとして素通りする。** そのため Blender の側で次を適用してから書き出す。

```
Blender(x, y, z) → glTF(x, z, -y)
```

**エンジンは変換を持たない。読んだ値をそのまま使う。** Blender という特定の道具の都合をエンジンの契約へ持ち込まないためである。

この条は 2026-08-15 の実測から定めた。Blender 側が最初に書き出した部品では、上面の接合点が `[0, 0, 3.0]`（Z が上のつもり）で出ており、glTF の座標系で読むと奥行方向の端を指していた。既存の収蔵アセットは全件が `export_yup=True` を明示して書き出されており、この条はその運用と一致する。

**注意: Blender で書き出して Blender で読み戻す検証では、この誤りを検出できない。** 読み戻すときに Y が上から Z が上へ戻るため、道具が持つ変換が相殺される。検証は glb のバイト列を直接読む形で行う。

### 向きだけでは姿勢が決まらない

`向き` は接合面の外向き法線である。**法線1本では、その軸まわりの回転が決まらない。** 壁へ出窓を嵌めるとき、出窓が横倒しでも法線の条件は満たされる。自由度が1つ残るため、`上方向` を併せて持つ。建築では窓の天地と屋根の勾配方向が常に意味を持つため、この自由度を残してはならない。

### 接合面の寸法を持つ理由

寸法が無いと、幅4メートルの壁の上へ幅3メートルの屋根を乗せても機械は何も言わない。位置だけ合って寸法が合わない接合が黙って通る。

寸法を持つと副次的な利点がある。**部品の規格を1つに固定しなくてよい。** 幅2メートル・3メートル・4メートルの壁が共存し、噛み合う組み合わせだけが成立する。規格を4メートル刻みに固定すると4メートル刻みの家しか建たず、不整形な敷地や折れ曲がる路地と衝突する。

## 実地で確かめた事実

2026-08-15にBlender 5.2.0で検証した。この2つを知らずに着手すると、症状が「接合点が無い」という同じ形で現れて切り分けができない。

**1. Blenderの日本語キーのネストしたデータは、1バイトも変わらず往復する。** 辞書の配列をカスタムプロパティへ代入でき、読み戻すと `IDPropertyGroup` になるが、キーも値も入れ子も保たれる。

**2. `export_extras=True` を明示しないと、Blenderは extras を黙って捨てる。** 既定は偽である。エラーも警告も出ない。

```python
bpy.ops.export_scene.gltf(filepath=..., export_extras=True, ...)
```

**3. `gltf` クレートの既定機能に `extras` は入っていない。** 1.4.1 の既定は `["import", "utils", "names"]` である。依存宣言を次へ変える必要がある。既存のローダーへの影響は未確認である。

```toml
gltf = { version = "1", features = ["extras"] }
```

## 型

グローバル規約の数学DDD（座標系と単位を型で区別する）と、本リポジトリの規約（プリミティブ執着禁止・条件分岐はenumと網羅的match）に従う。

```rust
/// 部品のローカル座標系での接合点。
pub struct 接合点 {
    名前: 接合点名,
    種別: 接合種別,
    位置: 部品ローカル座標,
    姿勢: 接合面の姿勢,
    接合面: 接合面寸法,
}

/// 接合面の姿勢。向きと上方向から作り、ここで回転の自由度を残さない。
pub struct 接合面の姿勢 { /* private */ }

impl 接合面の姿勢 {
    /// 零ベクトル・平行・非有限は型付きエラーで拒む。
    pub fn 生成する(向き: 部品ローカル方向, 上方向: 部品ローカル方向)
        -> Result<Self, 接合点エラー>;
}

/// 接合面の寸法。対になる接合点との噛み合いを判定する。
pub struct 接合面寸法 { 幅: メートル, 高さ: メートル }

impl 接合面寸法 {
    /// 許容差の内側で一致するかを答える。完全一致を要求しないのは、
    /// 部品を別々に作る以上、浮動小数の丸めが必ず入るためである。
    pub fn 噛み合うか(&self, 相手: &接合面寸法, 許容差: メートル) -> bool;
}
```

## 接合種別と対応表

```rust
pub enum 接合種別 {
    上面積層, 下面積層,
    壁面取付, 壁面差込,
    屋根の棟, 屋根の笠,
    枝の生え口, 枝の根元,
    頂芽, 葉房の根元,
}

impl 接合種別 {
    pub fn 対になる種別(self) -> 接合種別 {
        match self {
            Self::上面積層 => Self::下面積層,
            Self::下面積層 => Self::上面積層,
            // 以下、全種別を網羅する
        }
    }
}
```

**種別を1つ足すと、対応表を書き足すまでコンパイルが通らない。** 文書で「対応表を更新すること」と書いても守られないが、これは守られる。

extrasから読んだ文字列は、この enum へ変換する地点で検証する。未知の種別は型付きエラーで拒み、文字列のまま持ち回らない。

## 接合の定義

**接合とは、2つの接合点が向かい合うことである。** 具体的には次の2条件を同時に満たす配置のことである。

1. 子の接合点の位置が、親の接合点の指す面上の点に一致する
2. 子の接合点の向きが、親の接合点の向きの逆を向く

### 接合には2つの様式があり、検査すべきことが違う

**この区別を最初の版で見落とした。** 2026-08-15 に Blender 側が実際に部品を書き出した結果、壁の接合面が 6.4×2.6 で出窓の接合面が 1.8×1.4 になり、寸法の一致を要求する規則が成り立たないことが分かった。**大きな面のどこかへ小さなものを付ける関係は、面全体が一致する関係ではない。**

| 様式 | 対になる種別の例 | 検査すべきこと | 面上の位置 |
| --- | --- | --- | --- |
| **積層** | 上面積層 ↔ 下面積層 | 接合面の寸法が**一致する** | 常に面の中心 |
| **取付** | 壁面取付 ↔ 壁面差込 | 取付側の面が差込側の面を**包含できる** | **呼び出し側が指定する** |

```rust
pub enum 接合の様式 { 積層, 取付 }

impl 接合種別 {
    /// この種別がどちらの様式かを答える。網羅的matchで書く。
    pub fn 様式(self) -> 接合の様式;
}

/// 取付のとき、親の接合面のどこへ付けるか。面の中心を原点とする2次元の位置である。
/// 積層のときは常に中心であり、この型を渡す余地が無い。
pub struct 接合面上の位置 { 横: メートル, 縦: メートル }
```

**取付に面上の位置が要ることは、Blender 側の実装からも裏づけが取れている。** 建築の生成コードで`x_offset=1.5`（屋根のどこにドーマーを置くか）と書いていた数値が、まさにこの位置である。これは部品の寸法から導出できない意匠の決定であり、呼び出し側が与えるべき値である。

```rust
pub fn 向かい合わせる(
    親の配置: &個体配置,
    親の接合点: &接合点,
    子の接合点: &接合点,
    面上の位置: 接合面上の位置,
) -> Result<個体配置, 接合エラー>;
```

**戻り値が既存の `個体配置` であることが重要である。** 描画側は何も変わらない。

失敗するのは次の4つである。黙って繋がることはない。

1. 種別が対でない
2. 積層なのに接合面の寸法が一致しない
3. 取付なのに差込側の面が取付側の面より大きい
4. 取付で指定された面上の位置が、はみ出す（位置 + 差込側の面の半分が、取付側の面の外へ出る）

## 部品カタログと展開器

カタログは全部品を読み終えるまで不変条件を検査できない。対の相手がカタログに存在するかは、1件ずつ読んでいる途中では判定できないためである。したがって組み立て器を通してのみ完成させる。

```rust
pub struct 部品カタログ { /* private */ }
pub struct 部品カタログ組み立て器 { /* private */ }

impl 部品カタログ組み立て器 {
    pub fn 部品を1つ積む(&mut self, 部品ID: 部品ID, 定義: 部品定義);
    /// 対の相手がカタログに無い種別を型付きエラーで報告する。
    pub fn 組み上げる(self) -> Result<部品カタログ, カタログエラー>;
}

pub enum 組み立て規則 { 家(家の規則), 木(木の規則) }

pub struct 展開器 { カタログ: 部品カタログ }

impl 展開器 {
    pub fn 個体を展開する(&self, 規則: &組み立て規則, 種: 生成の種, 根の配置: 個体配置)
        -> Result<部品ごとの配置表, 展開エラー>;
}

/// 部品IDごとの配置列。そのまま描画対象の単位になる。
pub struct 部品ごとの配置表 { /* private */ }
```

規則をトレイトでなく判別共用体にするのは、本リポジトリが「条件分岐はenumと網羅的match」を規約にしているためである。規則の種類が増えるたびに枝を足し、網羅性を型で保つ。

展開の乱数には、`vegetation/placement.rs` が既に持つ決定的な混合関数（`零以上一未満(種, 添字, 用途)`）をそのまま使う。同じ種から同じ配置列が出る性質を、部品の選択にも広げる。

## 検査

`cargo xtask check-glb` へ次を足す。既存の検査器の拡張として入る。

| 検査項目 | 重大度 | 根拠 |
| --- | --- | --- |
| 接合点の宣言が1件以上ある | 警告 | 書き出し設定の `export_extras` を付け忘れると、接合点が無い部品が黙って作られる |
| 種別が既知のものである | 違反 | 未知の種別は enum へ変換できない |
| 向きと上方向が直交する | 違反 | 平行だと姿勢が決まらない |
| 位置が部品の境界箱の内側または面上にある | 違反 | 接合点が部品の外にあれば、宣言と実物が食い違っている |
| 接合面の寸法が正で有限である | 違反 | 噛み合いの判定が成り立たない |

**接合点が0件の部品を違反でなく警告にするのは、接合しない部品（単体で置く小物）が正当に成立するためである。**

## 外部リポジトリ連携

この設計は2つのリポジトリにまたがる。**接合点の契約が両者の唯一の接点であり、契約を変えるときは両方の文書を同じ変更で直す。**

| リポジトリ | 役割 | 文書 |
| --- | --- | --- |
| Blitzdrache0（本体） | 接合点の契約の正本。読み取り・型・展開・検査 | この文書 |
| BlenderPython | 契約を満たすglTFを作る側。部品の造形と接合点の埋め込み | `C:\Users\pokr301qup\python_dev\BlenderPython\_doc\設計\エンジン向け部品アセットの作り方.md` |
| Blitzdrache0Assets | 生成されたglbの置き場 | `_doc/設計/Blenderアセット運用.md`「本体からの参照の仕組み」 |

BlenderPython は Blender を bpy で操縦して建築と植物を作る実験の場である。そこで育てたモジュール（壁・屋根・出窓・幹・葉房）が、この設計の部品の供給元になる。**モデリングの技法そのものは向こうの管理であり、この文書は接合点の契約だけを持つ。**

契約が変わるのは次の場合である。いずれも両リポジトリの文書を同時に直す。

- 接合種別を足す、または意味を変える
- extrasのキーの名前や入れ子の形を変える
- 座標系の規約（原点の位置・軸の向き・単位）を変える

## 段の計画

着手前である。段の順序は、検査が空振りする状態を作らないことを基準に決めた。

- **段1（未着手）**: 部品2種（基礎と壁）をBlenderで作り、接合点をextrasへ埋め、`check-glb` が読めるところまで通す。**1種類でなく2種類から始めるのは、1種類では接合が起きず、接合の検査が動かないためである**
- **段2（未着手）**: 2部品を接合して1つの構造物にする。展開器は最小。**積層と取付の両方を通す。**
積層だけで通すと、取付の規則（包含の判定と面上の位置）が未検査のまま残る
- **段3（未着手）**: 規則を導入し、壁の面ごとに窓壁か扉壁かをシードから選ぶ
- **段4（未着手）**: 100軒を建て、**描画発行数が部品の種類数のままであることを計器で確かめる。** `village_world` と同じ計器で判定できる。ここが通れば設計が正しいことの実証になる
- **段5（未着手）**: 木へ広げる。幹の連鎖と倍率の変化。葉の物量は `_doc/設計/植生インスタンスと物量計測.md` の実測と合わせて決める

段4を実証の関門に置く。**発行数が軒数に比例し始めたら、この設計は前提から誤っている。**
