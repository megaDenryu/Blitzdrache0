# 部品カタログと接合点

この文書は、構造物と植物を無数のバリエーションとして作るための、部品の表し方・接合点の契約・展開の責務分割を管理する。実装と常に一致させて維持する。

**2026-08-16時点で段1に着手した。** 実装の到達点は「段の計画」節が持つ。文書が先行して実装したつもりになる事故を避けるため、段が進むたびにこの断り書きを更新する。

2026-08-16に、Blender側が書き出した部品7件のglbを直接読んで契約を検算した。その結果として契約の4箇所を直した。直した内容と根拠は「実データが暴いた契約の穴」節が持つ。

## 解こうとしている問題

オープンワールドの地図へ置く家と木に、個体ごとの違いを持たせたい。同じ家が並ぶ町も、同じ木が並ぶ森も、見た瞬間に作り物だと分かる。

素朴に解くと2つの道がある。どちらも行き止まりである。

**道1: 個体ごとに完成したメッシュを作る。** 家100軒なら100個のメッシュを作る。作る手間が軒数に比例し、メッシュ実体の数も軒数に比例する。描画発行数も軒数に比例し、`village_world` が実測した「1035体で発行11回」という性質が失われる。

**道2: 実行時にメッシュを変形する。** エンジンが頂点を動かして形を変える。エンジンがモデリング機能を持つことになり、`_doc/設計/機能配置の指針.md` の責務表が壊れる。メッシュ実体を個体ごとに持つことになるため、道1と同じ費用がかかる。

## 設計の核心

**バリエーションはメッシュの変形ではなく、部品の組み合わせで作る。**

**部品**とは、それ以上分けても組み合わせの自由度が増えない最小単位のメッシュのことである。家なら基礎・平壁・窓壁・扉壁・破風壁・屋根・煙突であり、木なら幹の一節・枝・葉房である。

家の形が軒ごとに違っても、使われる部品の**種類**は変わらない。壁Aと壁Bと屋根Cの組み合わせが違うだけである。したがって次が成り立つ。

```
描画対象1つ = 1部品 + その部品の個体配置の列
```

100軒分の壁が1つの配置列に入る。**描画発行数は部品ごとの材質スロット数の総和に比例し、軒数には比例しない。** これは `village_world` が既に実測した性質と同じものであり、原型を部品へ置き換えるだけで得られる。

総和が部品の種類数でないのは、描画発行がプリミティブ単位だからである。1つの部品が複数の材質を持つと、その部品は材質スロットの数だけ発行される。酒場の7部品は材質スロットを 1・4・1・2・2・4・3 と持つため、発行数は7ではなく17になる。**軒数に比例しないという設計の主張はこの数え方でもそのまま保たれる。** 17は軒数が1軒でも100軒でも17である。

この設計が成り立つ根拠は、`blitz_engine` の `個体配置` が位置・回転・非一様の倍率を既に持つことにある。部品を任意の姿勢と大きさで置けるため、幹が上へ行くほど細くなる木も、既存の型の範囲で表せる。

```rust
個体配置::生成する([x, 0.0, z], 回転, [倍率; 3])?
```

## 責務の分割

| 決まる時点 | 担当 | 作るもの | 出力 |
| --- | --- | --- | --- |
| モデリング時 | Blender（外部リポジトリ） | 部品1つの形状と接合点 | glTF 1ファイル |
| 宣言時 | 本体の宣言表 | カタログに載る部品と、組み立て規則 | `examples/compile_assets/world/` の宣言 |
| ビルド時 | blitz_asset_compiler | 規則をシードで展開した部品ごとの配置列 | 実行時形式 |
| 実行時 | blitz_engine | 配置列を読んでインスタンス描画する | 絵 |

**エンジンが受け取るのは部品メッシュと配置列の2つだけである。** エンジンは組み立て方を知らず、接合点も受け取らない。展開はビルド時に終わっており、実行時形式へ接合点を焼かない。エンジンは展開済みの結果だけを受け取るため、`機能配置の指針.md` の責務表と衝突しない。

実行時形式へ接合点を焼かないのは、実行時に組み立て直す用途が現時点で無く、焼くと実行時形式の版を上げることになるためである。**この決定は何も不可能にしない。** 将来プレイヤーが建て替える遊びを作るときは、そのときに版を上げれば足りる。

展開器はシードとカタログから配置列を作る純粋計算であり、bpy にも ash にも依存しない。Blenderもウィンドウも起動せずに単体テストできる。この「依存しない」を文書でなく機械で守るためにクレートを分ける。置き場は「層と依存の向き」節が持つ。

## 層と依存の向き

### 新しいクレート blitz_assembly

接合の語彙・部品カタログ・展開器は `blitz_assembly` が持つ。

| 項目 | 内容 |
| --- | --- |
| 知ってよい相手 | `blitz_engine`（`個体配置` のため）・`blitz_math`・`thiserror` |
| 知らないもの | `gltf`・`image`・`rayon`・ファイルシステム・実行時形式・カタログ・チャンク |

クレートを分ける理由は3つある。

第1に、**「展開器は glTF にも ash にも依存しない純粋計算である」を機械で守れるのはクレート境界だけである。** `blitz_asset_compiler` の中のモジュールとして置くと、同じクレートである以上 `use gltf::...` と書いた瞬間に通る。依存白リストへ登録すれば、gltf を足す変更は `cargo xtask conform` で落ちる。文書に書いただけの境界は境界ではない。

第2に、**将来の実行時組み立ての口を閉じない。** プレイヤーが建てる遊びを作るとき、展開器を実行時に呼ぶことになる。`blitz_asset_compiler` の中にあると、`blitz_app` がアセットコンパイラへ依存しなければ呼べない。別クレートなら `blitz_app` が `blitz_assembly` だけを引ける。

第3に、`blitz_asset_compiler` は構造是正の対象として名指しされたクレートであり（`_doc/計画/構造是正計画.md` の違反の地図）、是正が終わったばかりの領域へ同じ質の負債を積む余地を作らない。

### クレートの中の層

矢印は「知ってよい」向きである。

| モジュール | 持つもの | 知ってよい相手 |
| --- | --- | --- |
| `joint` | 接合点名・接合種別・接合の様式・接合面の姿勢・接合面寸法・接合面上の位置・接合点 | `blitz_math` |
| `part` | 部品ID・部品定義・部品カタログ・部品カタログ組み立て器 | `joint` |
| `mating` | 接合（検査済みの1つの噛み合わせ）。`個体配置` を返す | `joint`・`blitz_engine` |
| `expansion` | 組み立て規則・展開器・部品ごとの配置表 | `part`・`mating`・`blitz_engine` |

**`joint` が `part` を知らないことが重要である。** 接合点は部品に属するが、接合点の側から部品を参照する必要はない。逆向きの参照を許すと、接合面の姿勢を作るだけの計算がカタログを引きずる。

### 読みの置き場

glTFの `extras` から接合点を読む工程は `blitz_asset_compiler` の `loader` に置く。契約の正本がローダーの実装であるという既存の方針（`_doc/設計/Blenderアセット運用.md`「glTF入力契約の検査」）に従う。読みが作るのは `blitz_assembly` の `接合点` であり、gltf の型は境界を越えない。

### 機械強制の手段

| 境界 | 強制するもの | 破ったときに落ちるもの |
| --- | --- | --- |
| 展開器が glTF を知らない | 依存白リストへ `blitz_assembly` を登録 | `cargo xtask conform` の依存白リスト検査 |
| 接合種別の対応表の網羅 | `対になる種別` の網羅的match | `cargo check` |
| 接合の様式の網羅 | `様式` の網羅的match | `cargo check` |
| 検査する契約の枝の網羅 | `検査する契約` へ部品の枝を足す | `cargo check` |
| 外部依存の機能一覧 | `conform` の依存白リスト検査を機能まで拡張 | `cargo xtask conform` |

**最後の1行は、この設計に着手して見つかった既存の穴を塞ぐものである。** 依存白リスト検査は各クレートの依存の名前だけを読み、ワークスペース根の `Cargo.toml` を一度も開かない。そのため `gltf = { version = "1", features = ["extras"] }` のような機能の追加が、二重台帳を通らず無検査で入る。名前と同じく機能も台帳に持たせる。

## 接合点の契約

**接合点**とは、部品どうしを噛み合わせる位置・姿勢・接合面の寸法のことである。部品のローカル座標系で表す。

### 置き場所はglTFの`extras`である

部品ごとに変わる情報（位置・寸法）を本体の宣言表へ書くと、Blenderで部品を直したときに宣言表を直し忘れる形の二重管理になる。部品と接合点は同じファイルに置く。

一方、**どの種別とどの種別が対になるか**は部品を横断する知識であり、個々の部品のファイルには書けない。これは本体の型として1箇所に持つ。転記が発生しないため二重管理にならない。

### 形式

```json
{
  "接合点": [
    {
      "名前": "上面",
      "種別": "上面積層",
      "位置": [0.0, 0.0, 3.0],
      "向き": [0.0, 0.0, 1.0],
      "上方向": [0.0, -1.0, 0.0],
      "接合面": { "幅": 4.0, "高さ": 4.0 }
    }
  ]
}
```

キーと種別の値は日本語である。このデータを読むのは本エンジンだけであり、外部ツールとの相互運用を必要としない。グローバル規約が「英語名は読まないものとして扱う」と定めているため、読み手が意味を取れる日本語を使う。

**注意: glTFの仕様はJSONがUTF-8で符号化されていることを要求する。** テキストエディタでglTFファイルを直接編集する場合、Shift-JISなどで保存すると読み込みが壊れる。日本語のキーを使う以上、この事故は起こりうる。編集は原則としてBlender側の生成スクリプトから行い、手で開く必要があるときは文字符号化をUTF-8に固定する。

### 座標系は glTF に合わせる

**接合点の位置・向き・上方向、および接合面の幅と高さがどの軸に対応するかは、glTF の座標系（Y が上）で書く。** Blender の座標系（Z が上）で書いてはならない。

Blender の glTF 書き出しは頂点を Z が上から Y が上へ変換するが、**extras の値は変換しない。ただのデータとして素通りする。** そのため Blender の側で次を適用してから書き出す。

```
Blender(x, y, z) → glTF(x, z, -y)
```

**エンジンは変換を持たない。読んだ値をそのまま使う。** Blender という特定の道具の都合をエンジンの契約へ持ち込まないためである。

この条は 2026-08-15 の実測から定めた。Blender 側が最初に書き出した部品では、上面の接合点が `[0, 0, 3.0]`（Z が上のつもり）で出ており、glTF の座標系で読むと奥行方向の端を指していた。既存の収蔵アセットは全件が `export_yup=True` を明示して書き出されており、この条はその運用と一致する。

**注意: Blender で書き出して Blender で読み戻す検証では、この誤りを検出できない。** 読み戻すときに Y が上から Z が上へ戻るため、道具が持つ変換が相殺される。検証は glb のバイト列を直接読む形で行う。

### 向きだけでは姿勢が決まらない

`向き` は接合面の外向き法線である。**法線1本では、その軸まわりの回転が決まらない。** 壁へ出窓を嵌めるとき、出窓が横倒しでも法線の条件は満たされる。自由度が1つ残るため、`上方向` を併せて持つ。建築では窓の天地と屋根の勾配方向が常に意味を持つため、この自由度を残してはならない。

### 接合面の幅と高さがどの軸に対応するか

**縦軸は `上方向` であり、横軸は `上方向` と `向き` の外積である。** 3本は次の関係にある。

```
縦軸 = 上方向
横軸 = 上方向 × 向き
横軸 × 縦軸 = 向き（3本は右手系をなす）
```

`接合面` の `高さ` は縦軸に沿った長さ、`幅` は横軸に沿った長さである。

**この規約を書かないと、接合面上の位置の横成分の符号が決まらない。** 符号が逆だと出窓が壁の左右反転した位置へ付く。位置だけ合って向きが合わない接合は、機械では通って絵でだけ誤る。

この規約は2026-08-16に、Blender側が書き出した部品7件が持つ接合点15件の壁面すべてで検算して確定した。検算の例を3つ挙げる。`Mod_Tavern_F1_Base` の正面壁は 向きが (0, 0, 1)・上方向が (0, 1, 0) で 幅が 6.0 であり、横軸は (1, 0, 0) すなわちX軸で、部品のX方向の寸法 6.0 と一致する。同じ部品の左側面壁は 向きが (-1, 0, 0) で 幅が 5.0 であり、横軸は (0, 0, 1) すなわちZ軸で、奥行 5.0 と一致する。上面は 向きが (0, 1, 0)・上方向が (0, 0, 1) で 幅 6.0・高さ 5.0 であり、横軸は (-1, 0, 0) でXが 6.0、縦軸はZで 5.0 と一致する。

### 接合面の寸法を持つ理由

寸法が無いと、幅4メートルの壁の上へ幅3メートルの屋根を乗せても機械は何も言わない。位置だけ合って寸法が合わない接合が黙って通る。

寸法を持つと副次的な利点がある。**部品の規格を1つに固定しなくてよい。** 幅2メートル・3メートル・4メートルの壁が共存し、噛み合う組み合わせだけが成立する。規格を4メートル刻みに固定すると4メートル刻みの家しか建たず、不整形な敷地や折れ曲がる路地と衝突する。

## 実地で確かめた事実

2026-08-15にBlender 5.2.0で検証した。この2つを知らずに着手すると、症状が「接合点が無い」という同じ形で現れて切り分けができない。

**1. Blenderの日本語キーのネストしたデータは、1バイトも変わらず往復する。** 辞書の配列をカスタムプロパティへ代入でき、読み戻すと `IDPropertyGroup` になるが、キーも値も入れ子も保たれる。

**2. `export_extras=True` を明示しないと、Blenderは extras を黙って捨てる。** 既定は偽である。エラーも警告も出ない。

```python
bpy.ops.export_scene.gltf(filepath=..., export_extras=True, ...)
```

**3. `gltf` クレートの既定機能に `extras` は入っていない。** 1.4.1 の既定は `["import", "utils", "names"]` である。依存宣言を次へ変える必要がある。既存のローダーへの影響は未確認である。

```toml
gltf = { version = "1", features = ["extras"] }
```

## 型

グローバル規約の数学DDD（座標系と単位を型で区別する）と、本リポジトリの規約（プリミティブ執着禁止・条件分岐はenumと網羅的match）に従う。

```rust
/// 部品のローカル座標系での接合点。
pub struct 接合点 {
    名前: 接合点名,
    種別: 接合種別,
    位置: 部品ローカル座標,
    姿勢: 接合面の姿勢,
    接合面: 接合面寸法,
}

/// 接合面の姿勢。向きと上方向から作り、ここで回転の自由度を残さない。
pub struct 接合面の姿勢 { /* private */ }

impl 接合面の姿勢 {
    /// 零ベクトル・平行・非有限は型付きエラーで拒む。
    pub fn 生成する(向き: 方向<部品ローカル>, 上方向: 方向<部品ローカル>)
        -> Result<Self, 接合点エラー>;

    /// 接合面の幅が沿う軸。上方向と向きの外積である。
    pub fn 横軸(&self) -> 方向<部品ローカル>;
    /// 接合面の高さが沿う軸。上方向そのものである。
    pub fn 縦軸(&self) -> 方向<部品ローカル>;
    /// 接合面の外向き法線。向きそのものである。
    pub fn 法線(&self) -> 方向<部品ローカル>;
}

/// 接合面の寸法。対になる接合点との噛み合いを判定する。
pub struct 接合面寸法 { 幅: メートル, 高さ: メートル }

impl 接合面寸法 {
    /// 許容差の内側で一致するかを答える。完全一致を要求しないのは、
    /// 部品を別々に作る以上、浮動小数の丸めが必ず入るためである。
    pub fn 噛み合うか(&self, 相手: &接合面寸法, 許容差: メートル) -> bool;

    /// 配置の倍率を掛けた実寸を返す。宣言値どうしを比べてはならない理由は「倍率を掛けた実寸で判定する」節が持つ。
    pub fn 倍率を掛けた実寸(&self, 姿勢: &接合面の姿勢, 倍率: [f32; 3]) -> 接合面寸法;
}
```

### 位置は部品ローカル空間の型で持つ

`位置<部品ローカル>` は `位置<ローカル>`（群のローカル空間。`個体配置` が住む場所）と別の型である。同じ型にすると、**接合点の位置をそのまま `個体配置` の平行移動へ渡す誤りが型で落ちない。** この誤りは絵では「部品が群の原点へめり込む」として出るため、切り分けに時間がかかる。

`方向<空間種>` は正規化を不変条件に持つ単位ベクトルである。生の `[f32; 3]` で持つと、姿勢を作るたびに零ベクトルと非有限の検査を書き直すことになる。

### 倍率を掛けた実寸で判定する

`個体配置` は非一様の倍率を持ち、木の幹は上へ行くほど細くなる。**親の接合面の実寸は「宣言値 × 親の配置の倍率」であり、宣言値どうしを比べてはならない。** 宣言値で比べると、倍率の変わる幹の連鎖（段5）で噛み合いが必ず落ちる。

倍率は軸ごとに違うため、接合面の横軸と縦軸がどの軸を向いているかで掛かる倍率が変わる。`接合面の姿勢` が横軸と縦軸を答えるのはこのためである。`接合` は親の配置を受け取っているため、この計算に必要なものをすべて持っている。

## 接合種別と対応表

```rust
pub enum 接合種別 {
    上面積層, 下面積層,
    壁面取付, 壁面差込,
    屋根の棟, 屋根の笠,
    枝の生え口, 枝の根元,
    頂芽, 葉房の根元,
}

impl 接合種別 {
    pub fn 対になる種別(self) -> 接合種別 {
        match self {
            Self::上面積層 => Self::下面積層,
            Self::下面積層 => Self::上面積層,
            // 以下、全種別を網羅する
        }
    }
}
```

**種別を1つ足すと、対応表を書き足すまでコンパイルが通らない。** 文書で「対応表を更新すること」と書いても守られないが、これは守られる。

extrasから読んだ文字列は、この enum へ変換する地点で検証する。未知の種別は型付きエラーで拒み、文字列のまま持ち回らない。

## 接合の定義

**接合とは、2つの接合点が向かい合うことである。** 具体的には次の2条件を同時に満たす配置のことである。

1. 子の接合点の位置が、親の接合点の指す面上の点に一致する
2. 子の接合点の向きが、親の接合点の向きの逆を向く

### 接合には2つの様式があり、検査すべきことが違う

**この区別を最初の版で見落とした。** 2026-08-15 に Blender 側が実際に部品を書き出した結果、壁の接合面が 6.4×2.6 で出窓の接合面が 1.8×1.4 になり、寸法の一致を要求する規則が成り立たないことが分かった。**大きな面のどこかへ小さなものを付ける関係は、面全体が一致する関係ではない。**

| 様式 | 対になる種別の例 | 検査すべきこと | 面上の位置 |
| --- | --- | --- | --- |
| **積層** | 上面積層 ↔ 下面積層 | 接合面の寸法が**一致する** | 常に面の中心 |
| **取付** | 壁面取付 ↔ 壁面差込 | 取付側の面が差込側の面を**包含できる** | **呼び出し側が指定する** |

```rust
pub enum 接合の様式 { 積層, 取付, 未定 }

impl 接合種別 {
    /// この種別がどの様式かを答える。網羅的matchで書く。
    pub fn 様式(self) -> 接合の様式;
}

/// 取付のとき、親の接合面のどこへ付けるか。面の中心を原点とする2次元の位置である。
/// 積層のときは常に中心であり、この型を渡す余地が無い。
pub struct 接合面上の位置 { 横: メートル, 縦: メートル }
```

**`未定` の枝を持つのは、実データが2つの様式のどちらにも当てはまらない種別を含むためである。** `屋根の棟` と `屋根の笠` がそれであり、根拠は「実データが暴いた契約の穴」節が持つ。`未定` の種別で接合を組もうとすると型付きエラーで拒む。黙って積層か取付のどちらかへ倒すと、寸法の検査が意味を持たないまま通る。

`未定` は「この種別の様式をまだ決めていない」という状態であって、「様式を持たない」という意味ではない。**様式を決めるのは、それを要求する部品が実物になったときである。** 屋根板2枚を棟で合わせる形の部品が出てきた時点で、その部品の接合面の寸法を見てから枝を足す。寸法の合わない実データに合わせて先に規則を発明すると、規則が実装の都合の写しになる。

**取付に面上の位置が要ることは、Blender 側の実装からも裏づけが取れている。** 建築の生成コードで`x_offset=1.5`（屋根のどこにドーマーを置くか）と書いていた数値が、まさにこの位置である。これは部品の寸法から導出できない意匠の決定であり、呼び出し側が与えるべき値である。

```rust
/// 検査を通った1つの噛み合わせ。この値が在ることが、下の5条件を満たしていることの証拠である。
pub struct 接合 { /* private */ }

impl 接合 {
    pub fn 組む(
        親の配置: &個体配置,
        親の接合点: &接合点,
        子の接合点: &接合点,
        面上の位置: 接合面上の位置,
    ) -> Result<Self, 接合エラー>;

    /// 子の部品を置くべき配置。描画側はこの値をそのまま個体配置の列へ入れる。
    pub fn 子の配置(&self) -> 個体配置;
}
```

**`子の配置` が返すのが既存の `個体配置` であることが重要である。** 描画側は何も変わらない。

自由関数でなく値の型にするのは、失敗する条件を生成の1地点へ閉じるためである。`接合` という値が存在すること自体が、5条件を満たしていることの証拠になる。リポジトリの値オブジェクト様式（private フィールド + 検証付きの生成）と同じ形である。

失敗するのは次の5つである。黙って繋がることはない。

1. 種別が対でない
2. どちらかの種別の様式が `未定` である
3. 積層なのに接合面の実寸が一致しない
4. 取付なのに差込側の面が取付側の面より大きい
5. 取付で指定された面上の位置が、はみ出す（位置 + 差込側の面の半分が、取付側の面の外へ出る）

3から5の判定に使う取付側の寸法は、宣言値でなく親の配置の倍率を掛けた実寸である（「倍率を掛けた実寸で判定する」節）。

## 部品カタログと展開器

カタログは全部品を読み終えるまで不変条件を検査できない。対の相手がカタログに存在するかは、1件ずつ読んでいる途中では判定できないためである。したがって組み立て器を通してのみ完成させる。

```rust
pub struct 部品カタログ { /* private */ }
pub struct 部品カタログ組み立て器 { /* private */ }

impl 部品カタログ組み立て器 {
    pub fn 部品を1つ積む(&mut self, 部品ID: 部品ID, 定義: 部品定義);
    /// 対の相手がカタログに無い種別を型付きエラーで報告する。
    pub fn 組み上げる(self) -> Result<部品カタログ, カタログエラー>;
}

pub enum 組み立て規則 { 家(家の規則), 木(木の規則) }

pub struct 展開器 { カタログ: 部品カタログ }

impl 展開器 {
    pub fn 個体を展開する(&self, 規則: &組み立て規則, 種: 生成の種, 根の配置: 個体配置)
        -> Result<部品ごとの配置表, 展開エラー>;
}

/// 部品IDごとの配置列。そのまま描画対象の単位になる。
pub struct 部品ごとの配置表 { /* private */ }
```

規則をトレイトでなく判別共用体にするのは、本リポジトリが「条件分岐はenumと網羅的match」を規約にしているためである。規則の種類が増えるたびに枝を足し、網羅性を型で保つ。

展開の乱数には、`vegetation/placement.rs` が既に持つ決定的な混合関数（`零以上一未満(種, 添字, 用途)`）をそのまま使う。同じ種から同じ配置列が出る性質を、部品の選択にも広げる。

## 検査

### 部品の契約を第3の契約として足す

`cargo xtask check-glb` は検査する契約を旗で選ぶ。既存の2つ（静的シーンと群の原型）へ**部品の契約**を足し、`--part` で選ぶ。部品の契約は静的シーンの契約の全項目に、接合点の項目を足したものである。

**接合点があるときだけ検査する形にしてはならない。** その形だと、`export_extras` を付け忘れて接合点が1件も入らなかった部品で検査が丸ごと空振りし、合格が返る。これは「実地で確かめた事実」節が挙げた最も起こりやすい事故そのものである。旗で契約を選ぶ形なら、部品として検査せよと言われて接合点が0件であることが違反になる。

**部品の契約は「全段の原点が接地面の中央にある」を課さない。** これは群の原型だけの要求である。散布は個体を地表の点へ平行移動と天頂軸まわりの回転だけで置くため原点の位置が効くが、部品の配置は接合点が完全に決めるため、屋根や出窓の原点が底面中央にある必然性は無い。

### 接合点の検査項目

| 検査項目 | 重大度 | 根拠 |
| --- | --- | --- |
| 接合点の宣言が1件以上ある | 違反 | 書き出し設定の `export_extras` を付け忘れると、接合点が無い部品が黙って作られる。部品として検査せよと言われた以上、0件は付け忘れである |
| 種別が既知のものである | 違反 | 未知の種別は enum へ変換できない |
| 向きと上方向がどちらも単位長である | 違反 | 長さが0や2のベクトルは姿勢を壊すが、直交性の検査だけでは通ってしまう |
| 向きと上方向が直交する | 違反 | 平行だと姿勢が決まらない |
| 位置が部品の境界箱の内側または面上にある | 違反 | 接合点が部品の外にあれば、宣言と実物が食い違っている |
| 接合面の寸法が正で有限である | 違反 | 噛み合いの判定が成り立たない |
| 接合点の名前が部品の中で一意である | 違反 | 組み立て規則が接合点を名前で指すため、重複すると指す先が決まらない |

境界箱はアクセサが宣言する頂点位置の最小と最大から読み、バッファ実体は読まない。群の原型の原点の判定（`_doc/設計/Blenderアセット運用.md`「群の原型の契約と検査項目」）と同じ手法である。

### ベースカラー係数の欠落の検査

3つの契約すべてへ課す。**マテリアルを宣言していて、ベースカラーのテクスチャを持たず、ベースカラー係数も持たない材質を違反とする。**

glTFの既定のベースカラー係数は白（1, 1, 1, 1）である。テクスチャがあれば、この白はテクスチャへ掛かる中立の倍率として正しく働く。テクスチャが無いと白がそのまま色になり、作者が意図した色を持たない真っ白な面が焼ける。**焼けても作者の宣言と絵が食い違うことが確定するため、警告でなく違反である。**

テクスチャの有無で条件を分けるのは、`props/stone_hut.glb` の2つの材質がテクスチャだけを持ち係数を持たない形で正しく成立しているためである。条件を分けずに欠落を違反にすると、この既存アセットの検収が無関係に落ちる。

### カタログ横断の検査

`check-glb` はファイル1件を見るため、「対の相手がカタログに存在するか」を判定できない。`cargo xtask part-catalog <glbのパス...>` が全件を読んでカタログを組み上げ、次の3つを報告する。

- 組み上げの成否。失敗ならどの部品のどの接合点の種別が対の相手を持たないか
- 種別ごとの接合点の員数
- **未出現の種別と、様式が `未定` の種別の一覧。** 検査が空振りしている範囲を報告に出すことが目的である

## 外部リポジトリ連携

この設計は2つのリポジトリにまたがる。**接合点の契約が両者の唯一の接点であり、契約を変えるときは両方の文書を同じ変更で直す。**

| リポジトリ | 役割 | 文書 |
| --- | --- | --- |
| Blitzdrache0（本体） | 接合点の契約の正本。読み取り・型・展開・検査 | この文書 |
| BlenderPython | 契約を満たすglTFを作る側。部品の造形と接合点の埋め込み | `C:\Users\pokr301qup\python_dev\BlenderPython\_doc\設計\エンジン向け部品アセットの作り方.md` |
| Blitzdrache0Assets | 生成されたglbの置き場 | `_doc/設計/Blenderアセット運用.md`「本体からの参照の仕組み」 |

BlenderPython は Blender を bpy で操縦して建築と植物を作る実験の場である。そこで育てたモジュール（壁・屋根・出窓・幹・葉房）が、この設計の部品の供給元になる。**モデリングの技法そのものは向こうの管理であり、この文書は接合点の契約だけを持つ。**

契約が変わるのは次の場合である。いずれも両リポジトリの文書を同時に直す。

- 接合種別を足す、または意味を変える
- extrasのキーの名前や入れ子の形を変える
- 座標系の規約（原点の位置・軸の向き・単位）を変える

## 段の計画

着手前である。段の順序は、検査が空振りする状態を作らないことを基準に決めた。

- **段1（未着手）**: 部品2種（基礎と壁）をBlenderで作り、接合点をextrasへ埋め、`check-glb` が読めるところまで通す。**1種類でなく2種類から始めるのは、1種類では接合が起きず、接合の検査が動かないためである**
- **段2（未着手）**: 2部品を接合して1つの構造物にする。展開器は最小。**積層と取付の両方を通す。**
積層だけで通すと、取付の規則（包含の判定と面上の位置）が未検査のまま残る
- **段3（未着手）**: 規則を導入し、壁の面ごとに窓壁か扉壁かをシードから選ぶ
