# 部品カタログと接合点

この文書は、構造物と植物を無数のバリエーションとして作るための、部品の表し方・接合点の契約・展開の責務分割を管理する。実装と常に一致させて維持する。

**2026-08-20時点で段1から段8まで実装した。段7(一間四方の骨格へ壁をはめる)は絵の目視と正解表との突き合わせの両方で合格を確定し、段8(骨格の上下積層とベイの継ぎ口。屋根と床と壁の外面の飾りと煙突もこの段が収める)は絵の目視が残る。`cargo xtask part-assembly` は8組71件(酒場宿屋7件・木10件・壁をはめた骨格5件・2段積み10件・2ベイ8件・屋根つきの1ベイの家8件・屋根つきの2段の家13件・煙突を付けた1ベイの家10件)が全件一致し、**既知の不一致は0件である**。出窓の倍率の食い違いはBlender側が正解表を出し直して解消した(「正解表との突き合わせが1件食い違う(2026-08-19、既知の不一致)」節)。部品は煙突セグメントを加えて17件になり、`cargo xtask check-glb --part` は17件で違反0件である。壁の外面の飾りは接合種別を1つも増やさず、出窓は一体型のものを流用し、煙突は骨格の階高に合う新しい部品を1件だけ足して2段積む。** 実装の到達点は「段1の到達点」節が持ち、段の進みは「段の計画」節が持つ。文書が先行して実装したつもりになる事故を避けるため、段が進むたびにこの断り書きを更新する。

2026-08-16に、Blender側が書き出した部品7件のglbを直接読んで契約を検算した。その結果として契約の4箇所を直した。直した内容と根拠は「実データが暴いた契約の穴」節が持つ。

## 解こうとしている問題

オープンワールドの地図へ置く家と木に、個体ごとの違いを持たせたい。同じ家が並ぶ町も、同じ木が並ぶ森も、見た瞬間に作り物だと分かる。

素朴に解くと2つの道がある。どちらも行き止まりである。

**道1: 個体ごとに完成したメッシュを作る。** 家100軒なら100個のメッシュを作る。作る手間が軒数に比例し、メッシュ実体の数も軒数に比例する。描画発行数も軒数に比例し、`village_world` が実測した「1035体で発行11回」という性質が失われる。

**道2: 実行時にメッシュを変形する。** エンジンが頂点を動かして形を変える。エンジンがモデリング機能を持つことになり、`_doc/設計/機能配置の指針.md` の責務表が壊れる。メッシュ実体を個体ごとに持つことになるため、道1と同じ費用がかかる。

## 設計の核心

**バリエーションはメッシュの変形ではなく、部品の組み合わせで作る。**

**部品**とは、それ以上分けても組み合わせの自由度が増えない最小単位のメッシュのことである。家なら基礎・平壁・窓壁・扉壁・破風壁・屋根・煙突であり、木なら幹の一節・枝・葉房である。

家の形が軒ごとに違っても、使われる部品の**種類**は変わらない。壁Aと壁Bと屋根Cの組み合わせが違うだけである。したがって次が成り立つ。

```
描画対象1つ = 1部品 + その部品の個体配置の列
```

100軒分の壁が1つの配置列に入る。**描画発行数は部品ごとの材質スロット数の総和に比例し、軒数には比例しない。** これは `village_world` が既に実測した性質と同じものであり、原型を部品へ置き換えるだけで得られる。

総和が部品の種類数でないのは、描画発行がプリミティブ単位だからである。1つの部品が複数の材質を持つと、その部品は材質スロットの数だけ発行される。酒場の7部品は材質スロットを 1・4・1・2・2・4・3 と持つため、発行数は7ではなく17になる。**軒数に比例しないという設計の主張はこの数え方でもそのまま保たれる。** 17は軒数が1軒でも100軒でも17である。

この設計が成り立つ根拠は、`blitz_engine` の `個体配置` が位置・回転・非一様の倍率を既に持つことにある。部品を任意の姿勢と大きさで置けるため、幹が上へ行くほど細くなる木も、既存の型の範囲で表せる。

```rust
個体配置::生成する([x, 0.0, z], 回転, [倍率; 3])?
```

## 責務の分割

| 決まる時点 | 担当 | 作るもの | 出力 |
| --- | --- | --- | --- |
| モデリング時 | Blender（外部リポジトリ） | 部品1つの形状と接合点 | glTF 1ファイル |
| 宣言時 | 本体の宣言表 | カタログに載る部品と、組み立て規則 | `examples/compile_assets/world/` の宣言 |
| ビルド時 | blitz_asset_compiler | 規則をシードで展開した部品ごとの配置列 | 実行時形式 |
| 実行時 | blitz_engine | 配置列を読んでインスタンス描画する | 絵 |

**エンジンが受け取るのは部品メッシュと配置列の2つだけである。** エンジンは組み立て方を知らず、接合点も受け取らない。展開はビルド時に終わっており、実行時形式へ接合点を焼かない。エンジンは展開済みの結果だけを受け取るため、`機能配置の指針.md` の責務表と衝突しない。

実行時形式へ接合点を焼かないのは、実行時に組み立て直す用途が現時点で無く、焼くと実行時形式の版を上げることになるためである。**この決定は何も不可能にしない。** 将来プレイヤーが建て替える遊びを作るときは、そのときに版を上げれば足りる。

展開器はシードとカタログから配置列を作る純粋計算であり、bpy にも ash にも依存しない。Blenderもウィンドウも起動せずに単体テストできる。この「依存しない」を文書でなく機械で守るためにクレートを分ける。置き場は「層と依存の向き」節が持つ。

## 層と依存の向き

### 新しいクレート blitz_assembly

接合の語彙・部品カタログ・展開器は `blitz_assembly` が持つ。

| 項目 | 内容 |
| --- | --- |
| 知ってよい相手 | `blitz_engine`（`個体配置` のため）・`blitz_math`・`thiserror` |
| 知らないもの | `gltf`・`image`・`rayon`・ファイルシステム・実行時形式・カタログ・チャンク |

クレートを分ける理由は3つある。

第1に、**「展開器は glTF にも ash にも依存しない純粋計算である」を機械で守れるのはクレート境界だけである。** `blitz_asset_compiler` の中のモジュールとして置くと、同じクレートである以上 `use gltf::...` と書いた瞬間に通る。依存白リストへ登録すれば、gltf を足す変更は `cargo xtask conform` で落ちる。文書に書いただけの境界は境界ではない。

第2に、**将来の実行時組み立ての口を閉じない。** プレイヤーが建てる遊びを作るとき、展開器を実行時に呼ぶことになる。`blitz_asset_compiler` の中にあると、`blitz_app` がアセットコンパイラへ依存しなければ呼べない。別クレートなら `blitz_app` が `blitz_assembly` だけを引ける。

第3に、`blitz_asset_compiler` は構造是正の対象として名指しされたクレートであり（`_doc/計画/構造是正計画.md` の違反の地図）、是正が終わったばかりの領域へ同じ質の負債を積む余地を作らない。

### クレートの中の層

矢印は「知ってよい」向きである。

| モジュール | 持つもの | 知ってよい相手 |
| --- | --- | --- |
| `joint` | 接合点名・接合種別・接合の様式・接合面の姿勢・接合面寸法・接合面上の位置・接合点 | `blitz_math` |
| `part` | 部品ID・部品定義・部品カタログ・部品カタログ組み立て器 | `joint` |
| `mating` | 接合（検査済みの1つの噛み合わせ）。`個体配置` を返す | `joint`・`blitz_engine` |
| `expansion` | 組み立て規則・展開器・部品ごとの配置表 | `part`・`mating`・`blitz_engine` |

**`joint` が `part` を知らないことが重要である。** 接合点は部品に属するが、接合点の側から部品を参照する必要はない。逆向きの参照を許すと、接合面の姿勢を作るだけの計算がカタログを引きずる。

### 読みの置き場

glTFの `extras` から接合点を読む工程は `blitz_asset_compiler` の `loader` に置く。契約の正本がローダーの実装であるという既存の方針（`_doc/設計/Blenderアセット運用.md`「glTF入力契約の検査」）に従う。読みが作るのは `blitz_assembly` の `接合点` であり、gltf の型は境界を越えない。

### 機械強制の手段

| 境界 | 強制するもの | 破ったときに落ちるもの |
| --- | --- | --- |
| 展開器が glTF を知らない | 依存白リストへ `blitz_assembly` を登録 | `cargo xtask conform` の依存白リスト検査 |
| 接合種別の対応表の網羅 | `対になる種別` の網羅的match | `cargo check` |
| 接合の様式の網羅 | `様式` の網羅的match | `cargo check` |
| 検査する契約の枝の網羅 | `検査する契約` へ部品の枝を足す | `cargo check` |
| 外部依存の機能一覧 | `conform` の依存白リスト検査を機能まで拡張 | `cargo xtask conform` |

**最後の1行は、この設計に着手して見つかった既存の穴を塞ぐものである。** 依存白リスト検査は各クレートの依存の名前だけを読み、ワークスペース根の `Cargo.toml` を一度も開かない。そのため `gltf = { version = "1", features = ["extras"] }` のような機能の追加が、二重台帳を通らず無検査で入る。名前と同じく機能も台帳に持たせる。

## 接合点の契約

**接合点**とは、部品どうしを噛み合わせる位置・姿勢・接合面の寸法のことである。部品のローカル座標系で表す。

### 置き場所はglTFの`extras`である

部品ごとに変わる情報（位置・寸法）を本体の宣言表へ書くと、Blenderで部品を直したときに宣言表を直し忘れる形の二重管理になる。部品と接合点は同じファイルに置く。

一方、**どの種別とどの種別が対になるか**は部品を横断する知識であり、個々の部品のファイルには書けない。これは本体の型として1箇所に持つ。転記が発生しないため二重管理にならない。

### 形式

```json
{
  "接合点": [
    {
      "名前": "上面",
      "種別": "上面積層",
      "位置": [0.0, 0.0, 3.0],
      "向き": [0.0, 0.0, 1.0],
      "上方向": [0.0, -1.0, 0.0],
      "接合面": { "幅": 4.0, "高さ": 4.0 }
    }
  ]
}
```

**接合面の形は鍵の組で決まる。** 幅と高さがあれば矩形、直径があれば円である。木の幹の接合面は円であり、`{ "直径": 0.5 }` と綴る。両方の鍵を持つ宣言と、どちらの鍵も持たない宣言は型付きエラーで拒む。片方を優先して読むと、作者が2つの形を混ぜて書いた宣言が黙って一方の形として通り、噛み合いの判定が作者の意図と違う規則で走る。

キーと種別の値は日本語である。このデータを読むのは本エンジンだけであり、外部ツールとの相互運用を必要としない。グローバル規約が「英語名は読まないものとして扱う」と定めているため、読み手が意味を取れる日本語を使う。

**注意: glTFの仕様はJSONがUTF-8で符号化されていることを要求する。** テキストエディタでglTFファイルを直接編集する場合、Shift-JISなどで保存すると読み込みが壊れる。日本語のキーを使う以上、この事故は起こりうる。編集は原則としてBlender側の生成スクリプトから行い、手で開く必要があるときは文字符号化をUTF-8に固定する。

### 座標系は glTF に合わせる

**接合点の位置・向き・上方向、および接合面の幅と高さがどの軸に対応するかは、glTF の座標系（Y が上）で書く。** Blender の座標系（Z が上）で書いてはならない。

Blender の glTF 書き出しは頂点を Z が上から Y が上へ変換するが、**extras の値は変換しない。ただのデータとして素通りする。** そのため Blender の側で次を適用してから書き出す。

```
Blender(x, y, z) → glTF(x, z, -y)
```

**エンジンは変換を持たない。読んだ値をそのまま使う。** Blender という特定の道具の都合をエンジンの契約へ持ち込まないためである。

この条は 2026-08-15 の実測から定めた。Blender 側が最初に書き出した部品では、上面の接合点が `[0, 0, 3.0]`（Z が上のつもり）で出ており、glTF の座標系で読むと奥行方向の端を指していた。既存の収蔵アセットは全件が `export_yup=True` を明示して書き出されており、この条はその運用と一致する。

**注意: Blender で書き出して Blender で読み戻す検証では、この誤りを検出できない。** 読み戻すときに Y が上から Z が上へ戻るため、道具が持つ変換が相殺される。検証は glb のバイト列を直接読む形で行う。

### 向きだけでは姿勢が決まらない

`向き` は接合面の外向き法線である。**法線1本では、その軸まわりの回転が決まらない。** 壁へ出窓を嵌めるとき、出窓が横倒しでも法線の条件は満たされる。自由度が1つ残るため、`上方向` を併せて持つ。建築では窓の天地と屋根の勾配方向が常に意味を持つため、この自由度を残してはならない。

### 接合面の幅と高さがどの軸に対応するか

**縦軸は `上方向` であり、横軸は `上方向` と `向き` の外積である。** 3本は次の関係にある。

```
縦軸 = 上方向
横軸 = 上方向 × 向き
横軸 × 縦軸 = 向き（3本は右手系をなす）
```

`接合面` の `高さ` は縦軸に沿った長さ、`幅` は横軸に沿った長さである。

**この規約を書かないと、接合面上の位置の横成分の符号が決まらない。** 符号が逆だと出窓が壁の左右反転した位置へ付く。位置だけ合って向きが合わない接合は、機械では通って絵でだけ誤る。

この規約は2026-08-16に、Blender側が書き出した部品7件が持つ接合点15件の壁面すべてで検算して確定した。検算の例を3つ挙げる。`Mod_Tavern_F1_Base` の正面壁は 向きが (0, 0, 1)・上方向が (0, 1, 0) で 幅が 6.0 であり、横軸は (1, 0, 0) すなわちX軸で、部品のX方向の寸法 6.0 と一致する。同じ部品の左側面壁は 向きが (-1, 0, 0) で 幅が 5.0 であり、横軸は (0, 0, 1) すなわちZ軸で、奥行 5.0 と一致する。上面は 向きが (0, 1, 0)・上方向が (0, 0, 1) で 幅 6.0・高さ 5.0 であり、横軸は (-1, 0, 0) でXが 6.0、縦軸はZで 5.0 と一致する。

### 接合面の形を判別共用体で持つ

**円を「幅と高さが等しい矩形」で表さない。** 表すと、実物に無い組(矩形の面と円の面)が黙って通り、形ごとの判定の書き忘れも網羅matchが教えなくなる。噛み合いの判定は形の組ごとに定める。同じ形どうしは判定を定め、矩形の面と円の面のように形の違う組は型付きエラーで拒む。

円の面は面内のどの方向にも同じ長さを持つ。横軸と縦軸で伸び方の違う倍率が掛かると円が楕円になり、直径1つでは面を表せなくなるため、その配置を型付きエラーで拒む。

### 接合面の寸法を持つ理由

寸法が無いと、幅4メートルの壁の上へ幅3メートルの屋根を乗せても機械は何も言わない。位置だけ合って寸法が合わない接合が黙って通る。

寸法を持つと副次的な利点がある。**部品の規格を1つに固定しなくてよい。** 幅2メートル・3メートル・4メートルの壁が共存し、噛み合う組み合わせだけが成立する。規格を4メートル刻みに固定すると4メートル刻みの家しか建たず、不整形な敷地や折れ曲がる路地と衝突する。

## 実地で確かめた事実

2026-08-15にBlender 5.2.0で検証した。この2つを知らずに着手すると、症状が「接合点が無い」という同じ形で現れて切り分けができない。

**1. Blenderの日本語キーのネストしたデータは、1バイトも変わらず往復する。** 辞書の配列をカスタムプロパティへ代入でき、読み戻すと `IDPropertyGroup` になるが、キーも値も入れ子も保たれる。

**2. `export_extras=True` を明示しないと、Blenderは extras を黙って捨てる。** 既定は偽である。エラーも警告も出ない。

```python
bpy.ops.export_scene.gltf(filepath=..., export_extras=True, ...)
```

**3. `gltf` クレートの既定機能に `extras` は入っていない。** 1.4.1 の既定は `["import", "utils", "names"]` である。依存宣言を次へ変える必要がある。

```toml
gltf = { version = "1", features = ["extras"] }
```

この機能は**新しいクレートを1つも足さない**。`gltf/extras` は `gltf-json/extras` へ委譲するだけであり、`gltf-json` は `serde_json`（機能 `raw_value` つき）を機能に関わらず無条件で依存している。機能が変えるのは型別名1つだけで、`pub type Extras = Void`（空の構造体）が `Option<Box<RawValue>>` になる。既存のローダーは `gltf-json` の構造体を自分で構築しておらず `Extras` 型に触れる箇所も無いため、影響は無い。

## 実データが暴いた契約の穴

2026-08-16に、Blender側が書き出した部品7件のglbのJSONチャンクを直接読んで契約を検算した。4件の穴が出た。**いずれも実ファイルから読んだ値であり、推測ではない。**

### 穴1: 屋根の棟と屋根の笠は、2つの様式のどちらでも合格しない

`Mod_Tavern_Roof_Gable.glb` が宣言する対の2つは次のとおりである。

| 名前 | 種別 | 接合面 |
| --- | --- | --- |
| 屋根棟 | 屋根の棟 | 幅 0.2 × 高さ 6.2 |
| 破風頂点 | 屋根の笠 | 幅 6.8 × 高さ 2.6 |

一致の様式なら実寸がそろわないため落ちる。包含の様式なら高さ 6.2 が 2.6 を超えてはみ出すため落ちる。`様式` の網羅的matchをどう書いても、この2種別だけは実データで必ず失敗する。

**是正: `接合の様式` へ `未定` の枝を足し、この2種別をそこへ入れる。** 様式を発明するのは、屋根板2枚を棟で合わせる形の部品が実物になってからである。段1から段4までこの2種別は使わない。

### 穴2: 煙突は現状のカタログでは家へ取り付けられない

`Mod_Tavern_Chimney.glb` の3つの接合点は 下面（下面積層 0.7×0.7）・煙突頂部（上面積層 0.7×0.7）・壁面密着面（**壁面取付** 0.7×7.5）である。

**是正: Blender側へ、壁面密着面の種別を `壁面取付` から `壁面差込` へ変え、寸法を取り付く先に合わせる要求を出す。** あわせて、取付側と差込側のどちらを名乗るかの判定基準を1文で書かせる（受け入れる大きい面が取付、占める小さいものが差込）。この取り違えは種別の名前だけからは判別しにくく、同じ誤りが再発する。

**是正は済んだ（2026-08-16、Blitzdrache0Assets の 72c46b5）。** 壁面密着面は `壁面差込 0.7×3.0`・位置 `[0.35, 1.5, 0]` になった。高さ 3.0 は土台の側面壁の高さとちょうど同じであるため、収まる先は土台の正面壁・背面壁・左側面壁・右側面壁の4つだけである。2階の壁面は高さ 2.6、3階は 2.4 しかなく、包含の検査で落ちる。**煙突は7部品目として家並みへ入っている**（「段4の到達点」節）。

### 穴3: 発行数は部品の種類数でなく材質スロット数の総和である

7部品の材質スロット数は 1・4・1・2・2・4・3 であり、総和は17である。描画発行はプリミティブ単位であるため、発行数は部品の種類数7にならない。**是正の内容は「設計の核心」節が持つ。**

あわせて、**部品は既存のどちらの入力契約にも当てはまらない。** 静的シーンの契約（1メッシュ・複数材質）には形として合うが、群として描くには原型へ載せる必要があり、群の原型の契約は「メッシュが2個以上」「段ごとのプリミティブがちょうど1個」「全段が1つのマテリアルを共有」を要求するため落ちる。`blitz_engine` の `原型` は段1つを受け入れ、`メッシュデータ` はプリミティブ列と材質スロットを持つため、**受け皿の型は既にある。足りないのはローダーの経路だけである**（段4の作業）。

### 穴4: ベースカラー係数の欠落の検査は、テクスチャの有無で条件を分ける

アセットリポジトリ全件を走査すると、係数を持たない材質は `props/stone_hut.glb` の2件だけであり、**その2件はどちらもベースカラーのテクスチャを持つ。** 是正の内容は「ベースカラー係数の欠落の検査」節が持つ。

## 型

グローバル規約の数学DDD（座標系と単位を型で区別する）と、本リポジトリの規約（プリミティブ執着禁止・条件分岐はenumと網羅的match）に従う。

```rust
/// 部品のローカル座標系での接合点。
pub struct 接合点 {
    名前: 接合点名,
    種別: 接合種別,
    位置: 部品ローカル座標,
    姿勢: 接合面の姿勢,
    接合面: 接合面寸法,
}

/// 接合面の姿勢。向きと上方向から作り、ここで回転の自由度を残さない。
pub struct 接合面の姿勢 { /* private */ }

impl 接合面の姿勢 {
    /// 零ベクトル・平行・非有限は型付きエラーで拒む。
    pub fn 生成する(向き: 方向<部品ローカル>, 上方向: 方向<部品ローカル>)
        -> Result<Self, 接合点エラー>;

    /// 接合面の幅が沿う軸。上方向と向きの外積である。
    pub fn 横軸(&self) -> 方向<部品ローカル>;
    /// 接合面の高さが沿う軸。上方向そのものである。
    pub fn 縦軸(&self) -> 方向<部品ローカル>;
    /// 接合面の外向き法線。向きそのものである。
    pub fn 法線(&self) -> 方向<部品ローカル>;
}

/// 接合面の形と寸法。形ごとに噛み合いの判定が違うため判別共用体で持つ。
/// 中身が`正で有限な長さ`なのは、バリアントのフィールドを外から直に書いても不変条件が保たれるようにするためである。
pub enum 接合面の形と寸法 {
    矩形 { 幅: 正で有限な長さ, 高さ: 正で有限な長さ },
    円 { 直径: 正で有限な長さ },
}
```

### 位置は部品ローカル空間の型で持つ

`位置<部品ローカル>` は `位置<ローカル>`（群のローカル空間。`個体配置` が住む場所）と別の型である。同じ型にすると、**接合点の位置をそのまま `個体配置` の平行移動へ渡す誤りが型で落ちない。** この誤りは絵では「部品が群の原点へめり込む」として出るため、切り分けに時間がかかる。

`方向<空間種>` は正規化を不変条件に持つ単位ベクトルである。生の `[f32; 3]` で持つと、姿勢を作るたびに零ベクトルと非有限の検査を書き直すことになる。

### 倍率を掛けた実寸で判定する

`個体配置` は非一様の倍率を持ち、木の幹は上へ行くほど細くなる。**親の接合面の実寸は「宣言値 × 親の配置の倍率」であり、宣言値どうしを比べてはならない。** 宣言値で比べると、倍率の変わる幹の連鎖（段5）で噛み合いが必ず落ちる。

倍率は軸ごとに違うため、接合面の横軸と縦軸がどの軸を向いているかで掛かる倍率が変わる。`接合面の姿勢` が横軸と縦軸を答えるのはこのためである。`接合` は親の配置を受け取っているため、この計算に必要なものをすべて持っている。

### 一致の様式は子の倍率を導出する

**一致の様式は子の倍率を導出する（親の接合面の実寸 ÷ 子の接合面の宣言）。** 導出されるのは接合面に平行な軸の倍率であり、初手は一様倍率（導出値を3軸へ）とする。軸方向を別に選ぶ自由は要求が出てから作る。

**規則が倍率を自由に選ぶのではなく、接合が決める。** 木の幹が上へ行くほど細くなるのは、幹頂部の直径 0.4 へ幹基部の直径 0.5 を継ぐと 0.8 が導かれるからであって、規則が 0.8 と書くからではない。連鎖の2段目では親の実寸が 0.4 × 0.8 = 0.32 になり、そこから 0.64 が導かれる。**判定に使う親の面が宣言値でなく実寸であることが、この掛け合わせを生む。**

導出の結果として、一致の様式は「そろえるために子を伸縮させる」意味を持つ。落ちるのは伸縮ではそろえられない組だけである。矩形で幅と高さの比が食い違う組、形の違う組（矩形の面と円の面）、親の倍率が軸ごとに違う配置の3つである。**最後の1つを拒むのは、一様な比を子へ与える以上、親が非一様だと法線方向の倍率が親と子で食い違ったまま連鎖が進むためである。** 軸ごとの導出は、それを要求する部品が実物になってから設計する。

### 「一致は倍率の導出である」が正しい意味である理由

導出を入れる前の一致は「宣言した寸法がそろわなければ落ちる」であった。この変更を、検査が1つ緩んだ後退と読む余地があるため、2026-08-16のオーナー裁定で追認した理由をここへ残す。

1. **木の連鎖に必須の機構であり、建物にも表現力を開く。** 幹が上へ行くほど細くなる形は、子の倍率を接合が決めなければ表せない。同じ機構は建物でも「同じ部品を比で再利用する」ことを可能にし、部品ごとに大きさ違いを作らずに済む。これは町を作る仕事の本質であるパラメトリックなバリエーションと同じ向きである
2. **検査が1つ緩んだのではなく、検査の置き場が移った。** 意図しない伸縮（部品の宣言の誤り）を捕まえるのは、Blender側の正解表との突き合わせ・親との接触の検査・絵の目視という既にある網である。接合の計算の中で寸法の食い違いを弾いていたものが、組んだ結果を検証する側へ移ったのであって、どこにも網が無くなったわけではない
3. **比の値域に制限を作らない。** 「2倍までなら伸縮してよい」のような上限を置くと、その数の根拠を部品ごとに持てないまま1つの数へ畳むことになる。これは法線方向のずらしに値域を持たせない判断（「法線方向のずらしは配置の決定である」節）と同じ理由である

包含の様式では子が親の倍率をそのまま引き継ぐ。縮んだ親へ原寸の子を付けると宣言と絵が食い違うためである。子の倍率が親と違うのは一致のときだけであり、そのとき子の接合点の位置は親に対する比で伸ばしてから引く。組み立ての計算が親の座標系で進み、最後に親の変換が親の倍率を掛けるためである。**包含では比がちょうど1になり、掛けても値は1ビットも変わらない。** 家並みの実行時形式が導出の導入前後でバイト一致することを実測で確かめた。

## 接合種別と対応表

```rust
pub enum 接合種別 {
    上面積層, 下面積層,
    壁面取付, 壁面差込,
    屋根面取付, 屋根面差込,
    屋根の棟, 屋根の笠,
    壁のはめ口, 壁の外枠,
    ベイの継ぎ口,
    床のはめ口, 床の外枠,

    枝の生え口, 枝の根元,
    頂芽, 葉房の根元,

```

**屋根面の対を壁面の対と分けるのは、語と実体を合わせるためである。** ドーマーが噛み合う相手は屋根の傾斜面であって壁ではない。壁面差込と名乗ると1つの語が2つの実体を指すことになり、規則の読み手が名前からどちらの面へ付くのかを決められない。

**様式は新設していない。屋根面の対は壁面の対とまったく同じ包含である。** 包含の検査（面の大小と面上の位置のはみ出し）は接合面の中の2次元の判定であり、その面が水平か垂直か傾いているかに依らない。傾きは接合面の姿勢が表しており、様式は関知しない。

### 骨格と壁の対、扉の対（2026-08-16 追加）

Blender側が1間四方の骨格1件と壁3種（平壁・窓壁・扉枠付きの壁）を収蔵したことに合わせて4種別を足した。

| 種別 | 宣言する側 | 接合面 | 様式 |
| --- | --- | --- | --- |
| 壁のはめ口 | 骨格（1部品に4件） | 幅 2.00 × 高さ 2.60 | 一致 |
| 壁の外枠 | 壁3種（各1件） | 幅 2.00 × 高さ 2.60 | 一致 |
| 扉の吊り元 | 扉枠付きの壁（1件） | 幅 0.05 × 高さ 2.00 | 未定 |
| 扉板の吊り軸 | 扉板（未収蔵） | — | 未定 |
| 上面積層・下面積層 | 骨格（各1件、2026-08-19に追加） | 幅 2.00 × 高さ 2.00 | 一致 |
| ベイの継ぎ口 | 骨格（1部品に4件、2026-08-19に追加） | 幅 2.00 × 高さ 2.60 | 一致 |
| 床のはめ口 | 骨格（1件、2026-08-19に追加） | 幅 1.68 × 高さ 1.68 | 一致 |
| 床の外枠 | 床板（1件、2026-08-19に追加） | 幅 1.68 × 高さ 1.68 | 一致 |

**骨格を上下へ積む対は新設せず、既存の上面積層と下面積層を流用した。** 骨格の上面へ次の骨格の下面を向かい合わせる関係は、家の階を積む関係とまったく同じ「水平な面どうしを実寸をそろえて重ねる」ことであり、検査すべきことが1つも違わない。種別を分ける理由は語と実体が食い違うときにだけ生まれる（屋根面の対を壁面の対と分けたときがそれである）が、ここにはその食い違いが無い。

**横へ継ぐ対だけは新設した。** 骨格の側面は既に壁のはめ口を宣言しており、同じ物理面へ「壁を受ける口」と「隣のベイを継ぐ口」の2つの意味が重なる。壁のはめ口を流用すると、壁が隣のベイの口へはまる組み方と、隣のベイが壁の口へ継がる組み方が型を通る。別の種別にすれば、その2つはどちらも「種別が噛み合わない」で落ちる。

**壁の対を包含の流用にせず一致の新対にしたのは、寸法のずれが素通りするためである。** 骨格の枠 2.00×2.60 へ壁が同じ 2.00×2.60 でぴったりはまる。包含にすると、枠より小さい壁を差し込んでも合格し、隙間の空いた組み上げが検査を通る。

**床の対を積層の対の流用にせず新しい対にしたのは、「床のつもりで骨格を積む」誤結合を種別で弾けないためである。** 骨格の床のはめ口は水平な面を上へ向けており、実寸をそろえて重ねるという判定の中身は上面積層とまったく同じである。それでも流用すると、床のはめ口へ骨格の下面が噛み合い、床板を張るつもりの宣言が骨格を1つ余分に積む組み方になる。種別を分ける理由が語と実体の食い違いにあるという規準は、ここでは「階を重ねる口」と「1つの階の床を張る口」の食い違いとして満たされる。**寸法でも弾けない。** 床のはめ口が 1.68×1.68・積層の口が 2.00×2.00 であるため一致の様式は落とすが、それは寸法がたまたま違うことに頼った検査であり、同じ寸法の骨格が現れたら黙って通る。

**壁の対と壁面の対は互いに噛み合わない。** 壁面の対は「壁の面のどこかへ出窓や煙突を差し込む」関係であり、壁の対は「骨格の枠へ壁そのものをはめる」関係である。噛み合わせると壁が壁へ差し込まれる組み方が通る。

**扉の対の様式を未定にしたのは、扉板の部品がまだ実物になっていないためである。** 蝶番の回転を接合面の姿勢だけで表せるかを実データで確かめていない。屋根の棟・屋根の笠と同じく、決めるのは実物が出てきたときである。

```rust
impl 接合種別 {
    pub fn 噛み合う相手の種別一覧(self) -> &'static [接合種別] {
        match self {
            Self::上面積層 => &[Self::下面積層],
            Self::下面積層 => &[Self::上面積層],
            // 以下、全種別を網羅する
        }
    }
}
```

**相手が1つとは限らない。** 木では枝の根元が幹頂部と枝の生え口と頂芽の3つへ付き、頂芽は枝の根元と葉房の根元の2つを受ける。1対1の表では、同じ部品を幹の先にも枝の先にも継げる木を表せない。

**種別を1つ足すと、対応表を書き足すまでコンパイルが通らない。** 文書で「対応表を更新すること」と書いても守られないが、これは守られる。

extrasから読んだ文字列は、この enum へ変換する地点で検証する。未知の種別は型付きエラーで拒み、文字列のまま持ち回らない。

### 役割「相互」（2026-08-19 追加）

**相互とは、噛み合う相手が自分自身である接合の役割のことである。** 対応表がその種別自身を返し、様式は自分と自分のあいだで一致する。2026-08-19時点で相互なのは `ベイの継ぎ口` だけである。

役割を相互にするのは、**取り付ける側と取り付けられる側の区別が実体に無いとき**である。骨格の右面の継ぎ口へ隣の骨格の左面の継ぎ口が噛み合うが、どちらが受け入れる側でどちらが差し込む側かは決められない。区別の無いものへ2つの種別を立てると、部品を作るたびに「どちらを名乗るか」を判断することになり、その判断に根拠が無い。

相互の接合が課すもの・課さないものは次のとおりである。

- **様式は一致であり、実寸がそろうことを課す。** 相互であることは様式の決まり方を変えない。ベイの継ぎ口は 2.00×2.60 の面をまるごと突き合わせるため、面のどこかへ小さいものを付ける包含にはならない
- **取り付く先がカタログに在るかの検査は課さない。** その種別を宣言する部品が1件でも在れば相手も同時に在るため、カタログの組み上げの検査は自動的に満たされる。相互のための特別扱いは1行も要らない
- **同じ物理面に重ねて宣言された別の種別との排他は課さない。** 骨格の1つの側面は壁のはめ口とベイの継ぎ口を重ねて持つが、どちらを使うかを決めるのは規則であり、接合の契約ではない。契約が課すのは「噛み合う種別どうしであること」までである

**Rust側では、対の載せ忘れをenumの網羅的matchが防ぐ。** 相互の種別を足しても、対応表と様式の網羅的matchへ枝を書き足すまでコンパイルが通らない。自分を返す枝を書き忘れることはできない。Blender側は静的検査の自己除外を「同一接合点だけを除く」形にし、載せ忘れの検出を相互にも課すことで同じ穴を塞いでいる。

## 接合の定義

**接合とは、2つの接合点が向かい合うことである。** 具体的には次の2条件を同時に満たす配置のことである。

1. 子の接合点の位置が、親の接合点の指す面上の点に一致する
2. 子の接合点の向きが、親の接合点の向きの逆を向く

### 接合には2つの様式があり、検査すべきことが違う

**この区別を最初の版で見落とした。** 2026-08-15 に Blender 側が実際に部品を書き出した結果、壁の接合面が 6.4×2.6 で出窓の接合面が 1.8×1.4 になり、寸法の一致を要求する規則が成り立たないことが分かった。**大きな面のどこかへ小さなものを付ける関係は、面全体が一致する関係ではない。**

| 様式 | 対になる種別の例 | 検査すべきこと | 面上の位置 |
| --- | --- | --- | --- |
| **一致** | 上面積層 ↔ 下面積層 | 接合面の実寸が**そろう** | 常に面の中心 |
| **包含** | 壁面取付 ↔ 壁面差込 | 受け入れる側の面が差し込む側の面を**収められる** | **呼び出し側が指定する** |

**様式の名前は2026-08-16に `積層` から `一致` へ、`取付` から `包含` へ改めた。** 様式が決めるのは噛み合いの判定の本質だけであり、面が上下を向くか側面を向くかは接合点の宣言（向きと上方向）が持つ。旧名は判定でなく置き方を指しており、木の幹のように上下へ積みながら実寸の一致を課す接合と、水平な面へ包含で付ける接合の両方が現れたときに、名前が判定を誤って予告する。この節より前に書かれた記録の `積層` と `取付` は、それぞれ `一致` と `包含` を指す。**種別の名前（上面積層・壁面取付）は変えていない。** 種別は置き方の語彙であり、様式とは変わる理由が違う。

```rust
pub enum 接合の様式 { 一致, 包含 { 役割: 包含の役割 }, 未定 }

impl 接合種別 {
    /// この種別がどの様式かを答える。網羅的matchで書く。
    pub fn 様式(self) -> 接合の様式;
}

/// 包含のとき、親の接合面のどこへ付けるか。面の中心を原点とする2次元の位置である。
/// 一致のときは常に中心であり、この型を渡す余地が無い。
pub struct 接合面上の位置 { 横: メートル, 縦: メートル }

/// 向かい合わせた位置から親の接合面の法線方向へ子を寄せる量。正が離す側、負が食い込ませる側である。
pub struct 法線方向のずらし(メートル);
```

### 法線方向のずらしは配置の決定である

**部品は互いに食い込ませて組む。** 面をぴったり合わせると、重複した頂点の統合が非多様体を作るためである。これはBlender側の確立した運用であり、部品を組む限り必ず現れる。したがって接合の呼び出し側が与える値には、面上の2次元の位置に加えて法線方向の1次元が要る。

**接合点の宣言は部品の表面のままにし、食い込みは配置の決定として持つ。** 2つを混ぜて接合点を食い込んだ位置へ宣言すると、部品を単体で検査したときに宣言が実物の表面と食い違う。実際に、出窓とドーマーの差込口は最初この形で宣言されており、正解表との突き合わせが0.4メートルと0.7メートルの差として現れていた（「煙突を足した突き合わせ」節）。宣言を実面へ戻し、差を法線方向のずらしとして与えることで、7部品すべてが正解表と一致した。

**値域を型で持たない。** 離しすぎた配置は、組み上げた部品が親と接しているかの検査が、ずらしを適用した後の位置で落とす。型で幅を決めると、その幅の根拠を部品ごとに持てないまま1つの数へ畳むことになる。正のずらしで浮いた部品が接触の検査に必ず現れることは単体試験が固定する（`crates/blitz_assembly/src/mating/normal_offset_tests.rs`）。

面上の位置と別の値にしたのは、役割が違うためである。面上の位置は親の接合面へ収まることを求められ、はみ出しの判定を受ける。法線方向のずらしはどの判定も受けず、噛み合いを確かめた後の平行移動にだけ効く。1つの値へ畳むと、判定を受ける成分と受けない成分が同じ型に同居し、「接合面上の位置」という名前が面の外の量を含むことになる。

**`未定` の枝を持つのは、実データが2つの様式のどちらにも当てはまらない種別を含むためである。** `屋根の棟` と `屋根の笠` がそれであり、根拠は「実データが暴いた契約の穴」節が持つ。`未定` の種別で接合を組もうとすると型付きエラーで拒む。黙って一致か包含のどちらかへ倒すと、寸法の検査が意味を持たないまま通る。

`未定` へ入る2つ目の理由が2026-08-16に出た。**対の片側の部品がまだ実物になっていない場合である。** `扉の吊り元` と `扉板の吊り軸` がそれであり、根拠は「骨格と壁の対、扉の対」節が持つ。どちらの理由でも、決めるのは実物が出てきてからという扱いは同じである。

`未定` は「この種別の様式をまだ決めていない」という状態であって、「様式を持たない」という意味ではない。**様式を決めるのは、それを要求する部品が実物になったときである。** 屋根板2枚を棟で合わせる形の部品が出てきた時点で、その部品の接合面の寸法を見てから枝を足す。寸法の合わない実データに合わせて先に規則を発明すると、規則が実装の都合の写しになる。

**包含に面上の位置が要ることは、Blender 側の実装からも裏づけが取れている。** 建築の生成コードで`x_offset=1.5`（屋根のどこにドーマーを置くか）と書いていた数値が、まさにこの位置である。これは部品の寸法から導出できない意匠の決定であり、呼び出し側が与えるべき値である。

```rust
/// 検査を通った1つの噛み合わせ。この値が在ることが、下の5条件を満たしていることの証拠である。
pub struct 接合 { /* private */ }

impl 接合 {
    pub fn 組む(
        親の配置: &個体配置,
        親の接合点: &接合点,
        子の接合点: &接合点,
        面上の位置: 接合面上の位置,
        法線方向のずらし: 法線方向のずらし,
    ) -> Result<Self, 接合エラー>;

    /// 子の部品を置くべき配置。描画側はこの値をそのまま個体配置の列へ入れる。
    pub fn 子の配置(&self) -> 個体配置;
}
```

**`子の配置` が返すのが既存の `個体配置` であることが重要である。** 描画側は何も変わらない。

自由関数でなく値の型にするのは、失敗する条件を生成の1地点へ閉じるためである。`接合` という値が存在すること自体が、5条件を満たしていることの証拠になる。リポジトリの値オブジェクト様式（private フィールド + 検証付きの生成）と同じ形である。

失敗するのは次の5つである。黙って繋がることはない。

1. 種別が対でない
2. どちらかの種別の様式が `未定` である
3. 一致なのに接合面の実寸がそろわない
4. 包含なのに差し込む側の面が受け入れる側の面より大きい
5. 包含で指定された面上の位置が、はみ出す（位置 + 差し込む側の面の半分が、受け入れる側の面の外へ出る）

3から5の判定に使う受け入れる側の寸法は、宣言値でなく親の配置の倍率を掛けた実寸である（「倍率を掛けた実寸で判定する」節）。

## 部品カタログと展開器

カタログは全部品を読み終えるまで不変条件を検査できない。対の相手がカタログに存在するかは、1件ずつ読んでいる途中では判定できないためである。したがって組み立て器を通してのみ完成させる。

```rust
pub struct 部品カタログ { /* private */ }
pub struct 部品カタログ組み立て器 { /* private */ }

impl 部品カタログ組み立て器 {
    pub fn 部品を1つ積む(&mut self, 部品ID: 部品ID, 定義: 部品定義);
    /// 対の相手がカタログに無い種別を型付きエラーで報告する。
    pub fn 組み上げる(self) -> Result<部品カタログ, カタログエラー>;
}

pub enum 組み立て規則 { 家(家の規則), 木(木の規則) }

pub struct 展開器 { カタログ: 部品カタログ }

impl 展開器 {
    pub fn 個体を展開する(&self, 規則: &組み立て規則, 種: 生成の種, 根の配置: 個体配置)
        -> Result<部品ごとの配置表, 展開エラー>;
}

/// 部品IDごとの配置列。そのまま描画対象の単位になる。
pub struct 部品ごとの配置表 { /* private */ }
```

規則をトレイトでなく判別共用体にするのは、本リポジトリが「条件分岐はenumと網羅的match」を規約にしているためである。規則の種類が増えるたびに枝を足し、網羅性を型で保つ。

展開の乱数には、`vegetation/placement.rs` が既に持つ決定的な混合関数（`零以上一未満(種, 添字, 用途)`）をそのまま使う。同じ種から同じ配置列が出る性質を、部品の選択にも広げる。

## 検査

### 部品の契約を第3の契約として足す

`cargo xtask check-glb` は検査する契約を旗で選ぶ。既存の2つ（静的シーンと群の原型）へ**部品の契約**を足し、`--part` で選ぶ。部品の契約は静的シーンの契約の全項目に、接合点の項目を足したものである。

**接合点があるときだけ検査する形にしてはならない。** その形だと、`export_extras` を付け忘れて接合点が1件も入らなかった部品で検査が丸ごと空振りし、合格が返る。これは「実地で確かめた事実」節が挙げた最も起こりやすい事故そのものである。旗で契約を選ぶ形なら、部品として検査せよと言われて接合点が0件であることが違反になる。

**部品の契約は「全段の原点が接地面の中央にある」を課さない。** これは群の原型だけの要求である。散布は個体を地表の点へ平行移動と天頂軸まわりの回転だけで置くため原点の位置が効くが、部品の配置は接合点が完全に決めるため、屋根や出窓の原点が底面中央にある必然性は無い。

### 接合点の検査項目

| 検査項目 | 重大度 | 根拠 |
| --- | --- | --- |
| 接合点の宣言が1件以上ある | 違反 | 書き出し設定の `export_extras` を付け忘れると、接合点が無い部品が黙って作られる。部品として検査せよと言われた以上、0件は付け忘れである |
| 種別が既知のものである | 違反 | 未知の種別は enum へ変換できない |
| 向きと上方向がどちらも単位長である | 違反 | 長さが0や2のベクトルは姿勢を壊すが、直交性の検査だけでは通ってしまう |
| 向きと上方向が直交する | 違反 | 平行だと姿勢が決まらない |
| 位置が部品の境界箱の内側または面上にある | 違反 | 接合点が部品の外にあれば、宣言と実物が食い違っている |
| 接合面の寸法が正で有限である | 違反 | 噛み合いの判定が成り立たない |
| 接合面の形が鍵の組から決まる | 違反 | 幅と高さの組でも直径でもない宣言は、どの形として読むかが決まらない |
| 接合点の名前が部品の中で一意である | 違反 | 組み立て規則が接合点を名前で指すため、重複すると指す先が決まらない |

境界箱はアクセサが宣言する頂点位置の最小と最大から読み、バッファ実体は読まない。群の原型の原点の判定（`_doc/設計/Blenderアセット運用.md`「群の原型の契約と検査項目」）と同じ手法である。

### ベースカラー係数の欠落の検査

3つの契約すべてへ課す。**マテリアルを宣言していて、ベースカラーのテクスチャを持たず、ベースカラー係数も持たない材質を違反とする。**

glTFの既定のベースカラー係数は白（1, 1, 1, 1）である。テクスチャがあれば、この白はテクスチャへ掛かる中立の倍率として正しく働く。テクスチャが無いと白がそのまま色になり、作者が意図した色を持たない真っ白な面が焼ける。**焼けても作者の宣言と絵が食い違うことが確定するため、警告でなく違反である。**

テクスチャの有無で条件を分けるのは、`props/stone_hut.glb` の2つの材質がテクスチャだけを持ち係数を持たない形で正しく成立しているためである。条件を分けずに欠落を違反にすると、この既存アセットの検収が無関係に落ちる。

### カタログ横断の検査

`check-glb` はファイル1件を見るため、「対の相手がカタログに存在するか」を判定できない。`cargo xtask part-catalog <glbのパス...>` が全件を読んでカタログを組み上げ、次の3つを報告する。

- 組み上げの成否。失敗ならどの部品のどの接合点の種別が対の相手を持たないか
- 種別ごとの接合点の員数
- **未出現の種別と、様式が `未定` の種別の一覧。** 検査が空振りしている範囲を報告に出すことが目的である

**様式が `未定` の接合点は、対の相手の在否を問わない。** 未定の接合は組む地点で必ず拒まれるため、相手が揃っていても組めず、揃っていないことを不足として並べても直しようが無い。片側だけ先に収蔵された対（扉の吊り元は壁に在り、扉板の吊り軸を持つ部品は未収蔵）が、収蔵そのものを止めるのを避ける。片側が実データに現れていないことは、被覆の報告が未出現の行として受け持つ。

## 部品の追加の運び

新しい部品や接合の対を足すときの標準の手順である。段7から段8までの8回の往復（壁・積層・継ぎ口・屋根・床・飾り・煙突）で確立した。この運びは開発スレッド（ログ型）とAgentRoom「Blenderワークフロー開発室」の履歴に経緯が残るが、後続の作業者が読むべき規範はこの節が正本である。

1. **Blender側が着手宣言の前に論点を出す。** 論点とは、接合面の寸法・種別の語・様式（一致か包含か）・食い込ませる量など、契約に次元が欠けていると両側が別解釈で作って初めて食い違う事項のことである。実装してから食い違いを直すより、着手前に裁定するほうが安い（8往復で実装後の食い違いは1件だけであり、それも契約の穴でなく導出器の欠陥だった）
2. **エンジン側が裁定を返す。** 裁定には現物の確認を添える（例: 包含判定の等号の扱いを実装から確かめてから差込面の寸法を決める）。技術確認を添えた裁定は差し戻しを減らす
3. **Blender側が造形・接合点の宣言・正解表を収蔵し、宣言値を数値で報告する。** 正解表のキーは組み立てID・座標系はglTFで綴る。正解表の導出器は噛み合いの対応表から様式を引いて分岐する（包含は親の倍率を引き継ぎ、一致だけが倍率を導出する）
4. **エンジン側は、正解表を見る前に、宣言値だけから姿勢の予測値を導出して単体試験へ固定し、コミットする。** これが独立2実装の網である。予測値をBlender側へ渡してはならない（答えを先に渡すと一致が何も示さなくなる）。両側で事前に共有した契約の値（食い込ませる量など）は、この網が検証する対象ではない——その区別も記録に書く
5. **enum追加（新しい種別の対のときだけ）→ `check-glb --part` の緑 → `part-assembly` の手順の追加 → 突き合わせ。** 網羅的matchが対応表の載せ忘れをコンパイルで防ぐ
6. **食い違いが出たら、合格へ倒すために計算を変えず、差の値そのものから帰属を確定して止まる。** 帰属の根拠は、契約の条文・差の値が既知の式と一致するか・同じ部品の他の正解表での扱い、から組む。是正は帰属した側が行い、正解表の手直しでなく導出器の根治を選ぶ
7. **絵の目視の合否はエンジン側の親が確定する**（Blender側の絵は壁が透ける既知の表示問題があり参考に留まる）。機構の合否と意匠の所見を分けて返す
8. **到達点をこの文書へ追記する。** 契約が変わったときは「外部リポジトリ連携」のとおり両リポジトリの文書を同じ区切りで直す

### 食い違いの原因（穴5）

**差は両方とも、子の接合点の位置そのものである。** 出窓の壁面差込口は部品ローカルで [0, 0.7, 0] にあり、差は 0.7 である。ドーマーの屋根面差込口は [0, 0.6, -0.7] にあり、差は Y が −0.6・Z が +0.7 である。

接合の定義は「子の接合点の位置が、親の接合点の指す面上の点に一致する」であり、本体はこの定義どおりに子の原点を求めている。**正解表の取付2件は、子の接合点の位置を引かずに「親の接合点のワールド位置＋面上のずらし」をそのまま子の原点にしている。** 積層で食い違いが出ないのは、積層する部品の下面の接合点がどれも部品の原点 [0, 0, 0] にあり、引いても引かなくても同じになるためである。

裁定の候補は2つある。どちらを採るかで直す先が変わる。

1. **正解表の側が接合点の契約に従っていない。** Blender の建築コードが出窓とドーマーを配置するときに、差込口の接合点のオフセットを考慮していない。直すのは Blender 側の配置か正解表である
2. **接合点の宣言の側が実物とずれている。** 出窓の原点が差込面の中心にあるなら差込口の位置は [0, 0, 0] であるべきで、[0, 0.7, 0] という宣言が誤りである。直すのは Blender 側の接合点の登録である

**本体側の実装を変える案は無い。** 契約の文面（接合の定義）を満たしているのは本体の側だからである。

### 「貫入と包含」は実データで成り立たない（穴6）

設計案は段2の検収に「貫入の不在」と「接合面への包含」を挙げていたが、**どちらも実データで成り立たない。**

- **貫入は正常である。** 2階の張り出しは1階の上面より 0.6 メートル下へ出る。出窓は壁の内側へ差し込む。差し込むことがまさに `壁面差込` という種別の意味である。`Blenderアセット運用.md` も「部品は互いに食い込ませて組む」と書いている
- **接合面への包含も正常に破れる。** 出窓の境界箱は親の壁の接合面の矩形より 0.125 メートル外へ出る。出窓の屋根が壁面より張り出しているためである。ドーマーは 0.439 メートル外へ出る

残るのは「**子が親から離れていないこと**」である。接合点の宣言がメッシュの実物とずれていれば、組み上げた部品は親から離れた場所へ据わる。この形へ絞って実装し、実データの5件はすべて接している。

### 規則の形

```rust
pub enum 組み立て規則 { 家(家の規則) }
```

**枝は家だけである。** 木は段5で幹の連鎖と倍率の変化を扱うときに足す。呼ばれない枝を先に置かないためであり、枝を足す側は網羅的matchが漏れを教える。

`家の規則` は土台と、積む階の列と、壁面ごとの選択肢を持つ。**規則が手順を生み、展開器は生まれた手順をそのまま展開する。** 規則が増えても展開の側は変わらない。

### 「何も付けない」を候補の1つとして並べる

`壁面の飾り` は `付けない` と `付ける` の2つの枝を持ち、`壁面の指定` は候補の並びを持つ。**候補が空の指定は型付きエラーで拒む。** 選べない選択肢は「選んだ結果が無い」という半端な状態を作るためである。

**候補の数がそのまま選ばれる割合を決める。** 付けない側を厚くしたいなら同じ枝を複数並べる。割合を別の数で持つと、候補の並びと割合の2つを揃える手間が生まれる。

### 選択の添字は規則ぜんたいで通しにする

階ごとに数え直すと、階の数が違う家の同じ位置の壁が同じ値を引いてしまう。通しにすると壁面が1つ増えるだけで以降の選択がすべて変わる。据えた件数と選択の通し番号はどちらも「1つ足すと1つ増える」が増える契機が違うため、両方を `手順の組み手` が持ち、増やし忘れを1箇所へ閉じる。

### 積む相手は飾りでなく階である

**実装の途中で「直前に据えた部品の上へ積む」と書いて欠陥を作った。** 壁の飾りを先に足すと、直前に据えたのは飾りになり、次の階が出窓の上へ乗る。積む相手は飾りでなく階であるため、手順の組み手が直前に積んだ階の番号を別に持つ形へ直した。

**この欠陥は試験が積む階の一覧を空にしていたために一度も動かず、見つかったのは型の使われ方を数え上げたときである。** 積む道を通す試験を足し、欠陥版で落ちて修正版で通ることを確かめた。規則の分岐の網羅を数だけで確かめると、動いていない道が「網羅した」の中に紛れる。

### 煙突を足した突き合わせ

`cargo xtask part-assembly` の手順へ煙突を1件足し、7部品で走らせた。**最終の結果は全件一致であり、既知の不一致は0件になった。** そこへ至る途中で、煙突が食い違いの帰属を独立に裏づけた。

**煙突は取付でありながら、宣言が是正される前の正解表でも一致した。これが食い違いの帰属を裏づける積極的な証拠であった。** 煙突の壁面密着面は部品ローカルで [0.35, 1.5, 0] にあり、原点にない。本体は接合の定義どおりこの位置を引いて子の原点を [-3.0−0.35, 1.5−1.5, 0] + 面上のずらし = [-3.35, 0, -1.2] と求め、正解表と一致した。**同じ取付でも、子の接合点の位置を引いた側の宣言とは一致する。**

### 煙突が収まる先は土台の側面壁だけである

煙突の壁面差込は 0.7×3.0 であり、高さが土台の壁面の 3.0 とちょうど同じである。2階の壁面は 2.6、3階は 2.4 しかなく、包含の検査で落ちる。したがって規則は煙突を土台の壁面へ付ける。

**煙突は付ける付けないを選ばせず、壁に沿う位置を2つの候補で振り分ける。** 付ける付けないを選ばせると「たまたま全軒で煙突が選ばれない種」があり得て、部品の種類数が軒数で変わる。それは段4の実証の前提そのものを壊す。位置で振り分ければ、部品の種類数を動かさずに軒ごとの見た目を変えられる。同じ理由で3階の正面壁の出窓と屋根の破風正面壁のドーマーも必ず付ける。

### 軒ごとの向きが回転の合成を初めて動かした

段2の実データは回転をまったく持たず、正解表との突き合わせが確かめたのは平行移動だけであった。家並みは軒ごとに天頂軸まわりの4分の1回転を種から選ぶため、`接合`の回転の合成がここで初めて実行される。この道を単体試験で固定した（`crates/blitz_assembly/src/mating/rotated_root_tests.rs`）。回さない根で子が壁の正面へ出ること、4分の1回した根で同じ子が横へ出ること、子の姿勢にも親の回転が乗ることの3つである。期待値は回転行列を手で当てた値であり、実装の写しではない。

### 発行数の期待値を検収の側に持たない

`cargo xtask part-house-row-draw` は、焼く工程が数えた「部品ごとのプリミティブ数の総和」を報告の行から読み、それに地面の1を足した値をシーンパスの発行数の期待値にする。期待値を検収の側へ定数で書くと、部品を1つ足したときに検収だけが無言で通らなくなる。行の綴りは書き手と読み手の両方にあり、`cargo xtask conform` の綴りの契約の検査が片側だけの書き換えを拒む。

個体数の突き合わせには、シーンパスの個体数でなく可視個体の選別の候補数を使う。前者は視錐台に写った個体だけを数えるため構図に依存し、後者は可視判定へ登録された全個体を数えるため構図に依らない。焼く工程が据えた個体数と直に比べられるのは後者である。

### 規則が必ず付ける壁面を2つ持つ

3階の正面壁の出窓と、屋根の破風正面壁のドーマーは候補を1つだけにして必ず付ける。軒数を変えても部品の種類数が変わらないことが段4の実証の前提であり、付ける付けないを全壁面で選ばせると、たまたま全軒で出窓が選ばれない種があり得る。残りの4面(土台の左右側面壁と2階の正面壁と背面壁)は付けない枝を2つ・付ける枝を1つ並べてあり、同じ形の家が並ばない。

### 単体試験で固定したもの

- 幹の連鎖の倍率が接合面の比の掛け合わせになる(2段目が0.64)。**0.8という数を規則にも試験にも書かない**
- 円どうしの一致が直径の比で噛み合う
- 形の違う組(矩形の面と円の面)を型付きエラーで拒む
- 円の面へ面内で異なる倍率が掛かる配置を拒む(面が楕円になるため)
- 一致の様式で親の倍率が一様でない配置を拒む
- 矩形の一致で幅と高さの比が食い違う子を拒む
- 倍率を掛けた親の実寸と、宣言値のままの子の実寸がそろわない
- 一致の様式でも法線方向のずらしが子を動かす
- 同じ規則からの2回の展開が、配置表として完全に一致する
- 幹より高い節から枝を生やす規則を拒む

**「倍率を掛けた親へ宣言値のままの子を積むと落ちる」は、噛み合いの判定へ直に実寸を渡す形で固定した。** 導出を入れた後は、公開の口からこの状態を作れない。一致の様式が必ずそろう倍率を選ぶためである。判定が実寸を見ることの公開の口からの証拠は、連鎖の2段目が0.64になることである。宣言値で判定していれば2段目もまた0.8になる。

### 散布の原型の形は「1個体=部品の複数個体」を採る

候補は2つあった。**1本の木を1つのメッシュへ焼き固めて原型にする案は採らない。**

| | 焼き固める案 | 部品の複数個体にする案(採用) |
| --- | --- | --- |
| 1チャンクの原型の複製量 | 47.0KiB(枝1本)から208.6KiB(枝5本)×バリエーション数 | **88.3KiB(岩2種込み、枝の本数に依らず一定)** |
| チャンクあたりのプリミティブ | 2×バリエーション数 | 4(幹1・枝1・葉房2) |
| バリエーション | 焼いた本数だけ。増やすと複製量が乗る | 規則と種で無限。複製量は増えない |
| 段(詳細段) | 木を1つの単位として持てる | 部品ごとにしか持てない |

複製量は「群と段について頂点数×48とインデックス数×4を足し合わせた値」であり、群は原型を所有するためチャンクごとに複製される。針葉樹を残したまま樫を足したため、1チャンクあたりの内訳は次になった。

| 原型 | 複製量 |
| --- | --- |
| 小岩 | 16.45KiB |
| 大岩 | 29.25KiB |
| 針葉樹(2段) | 18.52KiB |
| 幹の一節 | 8.95KiB |
| 大枝 | 1.92KiB |
| 葉房(2段) | **44.44KiB**(段0が38.48、段1が5.95) |
| **合計** | **119.53KiB** |

世界全体では約934MB、先読み半径8の常駐289チャンクでは約33.7MiBになる。**葉房へ段1を足したことは複製量を1チャンクあたり5.95KiB増やし、描く三角形を遠距離で7.3分の1(876→120)にする。** 増減の向きが逆であることは「段(詳細段)は部品の側へ持たせる」節が述べたとおりであり、どちらが効くかは第7段階の公式の計測が決める。**焼き固める案は、個体ごとに完成したメッシュを作る道が行き止まりであるというこの文書の設計の核心が、チャンクという単位で再現された形である。**

**この選択が失うものを隠さずに書く。** 段の粒度が部品になり、「遠くで木を丸ごと簡略化する」ことができなくなる。群は原型を1つ持ち、個体はその原型の段の列からしか段を選べないため、近い木を5個体・遠い木を1メッシュへ切り替える道は実行時形式にも可視選別にも無い。あわせて、チャンクあたりのプリミティブが3(小岩・大岩・針葉樹)から6へ増える。**散布物はチャンクごとに独立した群として焼かれるため、発行数はチャンク数に比例する。** 家の並びが実証した「発行数は件数に比例しない」は1つのチャンクの内側の性質であり、部品の種類を増やすことはその比例係数を増やすことである。

### 段(詳細段)は部品の側へ持たせる(Rust側は実装済み、2026-08-16)

上の帰結として、詳細段を持たせられる場所は部品しか残らない。部品の入力契約を「1ファイル1メッシュ」から段の列へ広げ、接合点を宣言するのは段0のノードだけとする。**優先するのは葉房だけである。** 葉房が木の三角形の79パーセント(876/1108)と複製量の90パーセント(38.48/42.61KiB)を占め、幹と枝は60三角形と52三角形しかない。

**受け入れる側の実装は葉房の段1の到着より先に済ませた。** `部品の原型ソースを読み込む`が文書の並べたメッシュをそのまま段の列として読み、材質スロットの語彙を全段のプリミティブから作る。`cargo xtask check-glb --part`は段の列の項目を課し、段0以外が接合点を宣言していたら違反にする。項目の一覧は`_doc/設計/Blenderアセット運用.md`「部品の契約と検査項目」が持つ。

**群の原型と課すものが2つ違う。** 段ごとのプリミティブを1個に縛らないのは、部品が材質スロットの数だけプリミティブへ分かれるためである。段の間でマテリアルが揃うことを課さないのは、遠距離段が近距離段の材質の一部だけを使う形も、まとめた1つの材質へ置き換える形も、どちらも正当な簡略化だからである。後者は遠距離段で材質を1枚へまとめる典型の手法であり、そこでは近距離段に無い材質が現れる。部分集合を課すとこれを拒む。

**この拡張は絵を変えない。** 実データ10件は段を1つしか持たないため、拡張の前後で違反0件・警告0件のまま変わらない。家の並びと木の並びの実行時形式も、拡張の前後で全6ファイルがバイト一致する(`prop_part_house_row.blitzasset`894103バイト・`prop_part_tree_row.blitzasset`486084バイト・カタログ・チャンク目録)。

**段を足すと複製量は増え、描く三角形は減る。増減の向きが逆であることを記録しておく。** 常駐の量を減らしたいなら段を足してはならず、描く量を減らしたいなら足す。どちらが効くかは第7段階の公式の計測が決める。葉房の段1の物量はBlender側の造形判断に委ね、この文書は数を指定しない。

針葉樹を宣言から外すと、段の列を持つ原型が世界から消え、個体別の段の切替の実証が計数から消える。樹種の対比と観測点の維持の価値が、複製量18.52KiBの増分に勝る。**したがってこれは差し替えでなく追加である。**

### 決定性と生成器の版

差し替えは同じ乱数の種から出るチャンクの中身を変えるため、生成器の版を上げる。増分の鍵へ入る経路は3つあり、すべて塞ぐ。部品3件のglbの中身は対象1件の鍵のソース依存一式が捕まえ、散布と展開のコードは生成器の実行ファイルの内容ハッシュが捕まえる。**組み立て規則の値(幹の節数・枝を出す節・部品の安定ID)は、規則を宣言の型の中へ持たせることで焼き方の指定の綴りへ載る。** 規則を宣言の外の定数として置くと、規則を変えた実行が同じ鍵で前の生成物を据え置く。

### 絵の検収

**対照は「散布を焼かない実行」のままでよく、針葉樹の絵に置いてはならない。** 針葉樹と樫では輪郭が違うため、地面が背景へ変わる画素と背景が幾何へ変わる画素の両方が正当に出て、`distant-view --judge-scatter`の許可域が構造的に破れる。対照を散布なしに置けば、木が地面を隠しても地面は幾何のままであり、木は必ず手前に立つため、3つの条件はどれも成り立つ。**判定の入口は1行も変えずに使える。**

焼き方の指定の綴りが変わるため散布なしの側も焼き直されるが、絵は1画素も変わらないはずである。**対照を採り直して第6段階の検査点3の対照とバイト一致することを課す。** 一致しなければ木以外の何かが動いている。

**固定構図では木の姿を判定できない。** 視点高1.5メートルで地平線を画面上3分の1に置く構図では1本が数画素にしかならない。木の姿は「段6の順2」が作った近接の世界で確定する。

### Blender側への要求

現物の部品で組める木は「幹の途中から1方向へ枝が1本出て、幹の頂が切り口のまま残る形」が上限である。幹の一節が持つ枝の生え口は1つだけであり、接合面の姿勢が向きと上方向で完全に決まるため法線まわりに回す自由度が無く、3節積んでも枝は3本とも同じ方位を向く。幹頂部が噛み合う相手は幹基部だけであり、葉房の根元は直径0.14の別の種別であるため頂に葉が載らない。

**是正は部品の側で行い、接合の契約は変えなかった(2026-08-16に収蔵済み)。** 幹の一節へ生え口を黄金角137.5度ずつ回した3つ(高さ0.7・1.2・1.7メートル)にし、葉房へ幹基部(直径0.4)の接合点を1つ足して、同じ葉房の部品が幹の頂も冠として塞げるようにした。部品も種別も増えていない。接合の指示へ法線まわりの回しを足す案は、一致の様式が「向かい合わせて姿勢が決まる」ことを不変条件にしている場所へ自由度を戻すため採らなかった。

あわせて木の組み立ての正解表(`parts/tree_assembly_reference.json`、組み立てID `Tree_Oak_Standard`)が収蔵され、`cargo xtask part-assembly`の手順へ木を1件足した。**これが、組んだ木が意図どおりの姿かを機械で見る唯一の網である。**

### 順3の到達点

**規則が節を名指しするのをやめ、節ごとに候補を1件引く形にした。** 幹の1節から枝を生やすかどうかと、生やすならどの生え口からかを`節の枝`の候補として並べ、節ごとに種で1件引く。壁面の飾りと同じ様式であり、候補の数がそのまま割合を決める。この形にしたことで、旧い規則が持っていた「幹より高い節を指す」誤りが構造的に起きなくなり、その検査も要らなくなった。

**冠は幹の最上節の頂部へ必ず載せる。** 幹頂部が噛み合う相手は幹基部だけであり、葉房が幹基部の口を持つことでこの接合が成り立つ。載せない選択を候補で表さないのは、幹の切り口が絵に出る形を規則が選べるようにする理由が今は無いためである。

**葉房の指定は2つの接合点の名前を1つの型で持つ。** 枝の頂芽へ継ぐ根元(直径0.14)と、幹の頂部へ継ぐ幹基部(0.4)である。別々の指定に分けると、枝の先と冠に違う部品を書いた宣言が型を通る。

#### 正解表との突き合わせ

`cargo xtask part-assembly`が木を突き合わせられるようになった。**正解表の姿勢10件が全件一致し、宙に浮いた部品も無い。** 酒場宿屋の7件も全件一致のまま変わらない。実行はそれぞれ次の2つである(リポジトリの直下で走らせる)。

```
cargo xtask part-assembly <アセットリポジトリ>/parts/tree_assembly_reference.json <アセットリポジトリ>/parts/Mod_Tree_Oak_*.glb
cargo xtask part-assembly <BlenderPython>/exports/modular_parts/assembly_reference.json <アセットリポジトリ>/parts/Mod_Tavern_*.glb
```

突き合わせに2つの手当てが要った。**1つ目は、同じ部品が何度も現れる正解表への対応である。** 木は幹を3節・枝を3本・葉房を4つ据えるため、部品IDで先頭の1行を引く形では正しい組み立てが食い違いとして出る。据えた順と表の並び順で対応づけない。順は組み立ての手順とBlender側の書き出しの都合で決まり、どちらが変わっても絵は変わらないためである。代わりに平行移動が最も近い未使用の行を1対1で割り当て、割り当てた後に従来の許容差を課す。全件が1対1で許容差以内に収まって初めて合格になる。

**2つ目は、正解表が自分を名乗るキーの綴りが2つに割れていることである。** 酒場宿屋の表は`建物ID`、木の表は`組み立てID`を使う。読み取りの1箇所で両方を受け取り、読んだ先はどちらで書かれていたかを知らない。**正しい語は「組み立て」であり、木に「建物」は嘘である。** Blender側と揃えて`組み立てID`へ寄せるのが本筋であり、それまでの受け入れである。

手順は規則でなく宣言として書く。この突き合わせが確かめるのは接合の計算がBlender側の配置と一致することであり、節ごとにどの生え口を種で引くかは別の関心事だからである。手順は正解表が名乗る組み立ての識別子で引き当てる。旗で選ばせると、表と手順の取り違えが「全件が食い違う」という読み解きにくい結果になる。

### 一致の様式が面上の位置を検査していなかった(穴7)

**噛み合いの検査は一致の枝で面上の位置を1度も見ないが、子の原点を求める工程は様式に関わらず面上のずらしを足していた。** 中心以外を渡すと、どの検査も受けないまま子が面に沿って滑る。この状態を作る呼び出しは1つも無かった(家の階も木もすべて中心である)が、宣言から踏める穴である。面上の位置を渡す枝が包含にしかなかった頃は現れなかった破れであり、はめ口の規則を書く前に塞いだ。

判定は横と縦の両方を見る。横だけを見る形にすると縦のずらしが無検査で通る。許容差を持たせないのは、中心を作る口がどちらも丸めを経ずに零を置くためであり、許容すると意匠として与えた微小なずらしが中心として通る。

### 規則ははめ口ごとに候補を1件引く

`はめ口の指定`と`はめ口へ入れるもの`を新しい型にした。壁面の飾りと節の枝と同じ様式であり、候補の数がそのまま割合を決める。

**`壁面の指定`を流用しなかったのは、あちらが`横のずらし`を持つためである。** はめ口と外枠の対は一致の様式であり、面に沿って滑らせる自由度を持たない。流用すると宣言が横のずらしを書ける形になる。型で書けない形にするのが第一の防壁であり、上の穴7で足した判定は第二の防壁である。あわせて名前が実体と合わない。壁面の飾りは壁の面へ飾りを差し込むことであり、はめ口へ壁そのものをはめることではない。

**壁3種それぞれに必ず入れる面を割り当てる。** 正面へ扉枠付きの壁、背面へ平壁、左面へ窓壁を必ず入れ、右面だけを「入れない・平壁・窓壁」の3候補で振り分ける。全面を選ばせると、たまたま扉枠付きの壁が1棟も選ばれない種があり得て、部品の種類数が種で変わる。家の規則が3階の正面壁と屋根の破風正面壁を必ず付けているのと同じ理由である。

展開の用途の番号は103を新しく採った。壁面の飾りの選択が101、節の枝の選択が102であり、散布は1から7を使っている。

### 4方位の回転は新しい機構を要らず、壁は骨格の外側へ出る

4つのはめ口は向きだけが違い上方向がどれも天頂であるため、向かい合う枠(法線と横軸を反転して縦軸をそのままにする枠)から壁の回転が天頂軸まわりだけに決まる。**背面が恒等、正面が180度、左面が+90度、右面が−90度である。** 家並みの軒ごとの4分の1回転で既に動いている道であり、足した機構は無い。

**壁の本体は自分の外枠の面より奥にあるため、向かい合わせると骨格の面より外側へ0.20メートル出る。組んだベイの外寸は2.40×2.40×2.60になる。** 壁の仕上げ面(木骨と漆喰)が外を向くことも実データから確かめた。Blender側は木骨を厚み方向の前面へ置いており、glTFの座標系では外枠の面から最も遠い側になる。

**食い込ませる量は0.02メートルである。** 零にすると骨格の柱と梁の外面(±1.00)と壁の背面がちょうど同一平面になり、深度が競合する。骨格の柱は見付0.16で芯が±0.92にあるため、外面は正確に±1.00である。**この破れは親と接しているかの検査に掛からず絵にだけ出る。** 0.02は2026-08-18の裁定で置いた仮値だったが、**同日の親の目視で確定した**(下の「絵の目視で合格を確定した(2026-08-18)」)。

### 一致の倍率の導出はここでは何も動かさない

骨格のはめ口も壁の外枠も 2.00×2.60 であるため、幅から導かれる比はちょうど1.0になり、高さの照合も通る。子の倍率は `[1,1,1]`、親に対する比は 1÷根の倍率である。根の倍率が1なら比も1であり、子の接合点を伸ばす計算が値を1ビットも変えない。

### 骨格が宣言する接合点10件(床のはめ口を足す前)

glbのJSONチャンクを直接読んだ値である。

### 上下積層の裁定(2026-08-19、札#145のコメント367)

1. **種別は既存の上面積層と下面積層を流用する。** 新設しない。根拠は「骨格と壁の対、扉の対」節が持つ
2. **食い込ませる量は0である。** 積層は面が向かい合う隣接であり、柱の外面が上下へ連続するだけで重なる面をそもそも持たない。深度が競合する機構が無い。**壁の0.02メートルとは理由から違う**(あちらは骨格の柱の外面と壁の背面がちょうど同一平面になる)
3. **境目の梁の二重の帯0.32メートルは許容する。** 下の骨格の上端の梁と上の骨格の下端の梁が上下に並ぶため、境目に厚い帯が現れる。これは胴差しの意匠として受け入れる
4. **階高は当面1規格2.6メートルとする。** 骨格の上面の接合点の高さがそのまま階高になるため、規則も手順も高さを1つも書かない

### ベイの継ぎ口の裁定(2026-08-19、札#145のコメント368)

1. **新しい種別「ベイの継ぎ口」を足し、役割は相互とする。** 定義は「役割「相互」(2026-08-19 追加)」節が持つ
2. **接合面は 2.00 × 2.60 であり、4つの側面の中心に、壁のはめ口と重ねて宣言する。** 同じ物理面が2つの意味を持つ
3. **継いだ境目の柱の二重0.32メートルは許容する。** 左のベイの右端の柱と右のベイの左端の柱が横に並ぶ。積層の境目の梁と同じ扱いである
4. **食い込ませる量は0である。** 理由は積層と同じである
5. **どちらの口を使うかの排他は規則の責務であり、接合の契約は課さない。** 契約が課すのは「噛み合う種別どうしであること」までである

**Blender側の実装詳細2件も受理した。** 静的検査の自己除外は「同一接合点だけを除く」形にし、載せ忘れの検出を相互にも課す。**Rust側では載せ忘れをenumの網羅的matchが担う。** 対応表と様式の枝を書き忘れるとコンパイルが落ちる。

### 規則は骨格の継ぎ足しの連なりを持つ

`一間四方の骨格の規則` が根の骨格のはめ口の並びに加えて、`骨格の継ぎ足し` の連なりを持つ形にした。継ぎ足し1件は、直前に据えた骨格のどの接合点へ自分のどの接合点を向かい合わせるかと、その骨格が壁を受ける面の並びを持つ。

**繋ぐ相手を「直前に据えた骨格」に固定し、番号で指させない。** まだ据わっていない骨格を指す宣言を型で書けなくするためである。表せるのは連なりだけになるが、上へ積む骨組みも横へ継ぐ骨組みもどちらも連なりであり、枝分かれを要求する部品はまだ実物になっていない。

**上へ積むか横へ継ぐかを枝で分けない。** 渡す接合点の名前が違うだけで、接合の計算も指示の形も同じである。骨格の上面と下面を渡せば上へ積み、右面と左面の継ぎ口を渡せば横へ継ぐ。

**継いだ面のはめ口を並べないことが、壁と隣のベイが同じ面へ二重に入るのを防ぐ。** これが上の裁定5の「排他は規則の責務」の実装である。

#### 床を張るかどうかは骨格ごとの宣言であり、種で引かない

規則の側では、骨格1つへ床を張るかどうかを`骨格へ張る床`という骨格ごとの宣言として持つ。根の骨格の床は規則が、継いだ骨格の床は継ぎ足しの候補が持つ。**壁のように候補の並びから種で1件引く形にしていない。** 理由は2つある。

第1に、**床の有無は意匠の振れでなく、抜けが破れに見える。** 壁は面ごとに平壁か窓壁か何も入れないかを引いて軒ごとの姿を変えるが、床が引かれなかった骨格は「床の抜けた家」になる。1階が土間で2階が床板という違いは骨格が連なりのどこに在るかで決まり、種では決まらない。

第2に、**骨格を据えたら必ず1枚張るという形も採らない。** Blender側の正解表は床を持つ組み立てを屋根つきの家2件だけとし、2段積みと2ベイの見本には床を含めていない。骨格が床のはめ口を宣言していることは、床が必ず入ることを意味しない。必ず張る形にすると、骨格そのものの継ぎ方を見る見本の絵と、その見本の正解表が食い違う。

候補を引かないため展開の用途番号を1つも使わず、**床を宣言しない世界では指示が1件も増えない。** 既存の4世界の実行時形式が1バイトも変わらないことの根拠がこれである。

**骨格を読む世界とカタログには、床を張らなくても床板を載せる。** カタログの組み上げは接合種別の対の相手がカタログに在ることを課すため、骨格が床のはめ口を宣言した以上、床板を外したカタログは組み上げが落ちる。**据わらない部品は群を作らないため、据えた部品の種類数も材質スロットの総和も動かない。** 同じ理由で、`cargo xtask part-assembly` で骨格を読むどの実行にも床板のglbを渡す。

#### 飾りの選択は壁の候補に属する

規則の側では、壁1枚の外面へ何を差し込むかを`壁の外面の飾りの指定`として**壁の候補が持つ**。はめ口へ入れる候補が
「入れない」なら飾りの選択も無い。**壁の無い面へ飾りだけが浮く宣言を型で書けなくするためである。**

**一体型の家の`壁面の指定`を流用しないのは、あちらが横のずらしを持つためである。** 壁の外面の飾り取付は面の中心1つ
だけを使い、面に沿って滑らせる意匠の自由度を今は持たない。流用すると宣言が横のずらしを書ける形になる。
あわせて親が違う。あちらは一体の階の壁面へ差し込み、こちらは骨格へはめた壁1枚の外面へ差し込む。

**飾りの親は骨格でなく、いま据えたばかりの壁である。** 段7の時点では骨格が壁を受けるだけで壁は葉であった。
骨格から壁へ、壁から飾りへと組み立てが2段に伸びるのはこれが初めてである。展開の用途の番号は105を新しく採り、
既存の壁の選ばれ方を1つも動かさない。

### 規則の口は候補の三択を持つ

1. **骨格を継ぐ**(自分のどの口を向かい合わせるかと、その骨格が壁を受ける面の並びを持つ)
2. **屋根を載せる**(どの部品のどの口を向かい合わせるかを持つ)

1. **積層の連鎖の高さの検算。** 展開器が組んだ各部品の平行移動のY成分が、「下の部品の上面接合点のY − 自分の下面接合点のY」の累和と一致する。突き合わせる2つのうち片方は接合点の位置という独立な宣言であり、もう片方は展開の結果であるから、この検算は自己無矛盾の言い換えではない
2. **親との接触の検査。** 組み上げた子の境界箱が、親の境界箱と重なるか触れること。**接合点の宣言とメッシュの実物を突き合わせる**ため、宣言が実物とずれて部品が宙に浮けば必ず出る。**当初の案にあった「貫入の不在」と「接合面への包含」は実データで成り立たないため採らない**（理由は「段2の到達点」節の穴6）
3. **Blender側の組み立ての正解表との突き合わせ。** 分解前の建物での部品ごとのワールド姿勢を1つの表としてBlender側に書き出させ、接合点だけから展開した結果と比べる。判定は平行移動と倍率の差が許容差以下であることと、回転がクォータニオンとして同値であること（符号違いを同一視する）である。**倍率は2026-08-19に足した。****1と2では検出できない「向きが90度ずれている」を捉える唯一の手段である**
4. **絵の目視。** 機械が見るのはvalidationが0件であることだけであり、絵の合否は目視で確定する（`prop-draw`・`village-draw` と同じ様式）

**判定は2026-08-19に倍率を足して3つになった。** 平行移動と回転だけでは、大きさの違う部品を同じ位置へ据えた組み立てを捉えられない。木の幹が節ごとに細くなる比も、包含が親から引き継ぐ比も、それまで一度も突き合わされていなかった。

許容差は比べる値の大きさと `f32::EPSILON` の積を基にする。f32は仮数部の桁数が固定であるから、表せる刻みが値の大きさに比例するためである。

**注意: 実装はこの積をさらに1000倍している。** 接合の計算が平行移動・回転・倍率の合成を何段も重ね、丸めがその段数ぶん積み上がることを見込んだ係数である。**この係数には実測の裏づけが無い。** 2026-08-16の実測では積層4件の差が完全に0であり、係数が1でも1000でも判定は変わらなかった。**倍率が1でない接合や、回転を持つ接合が実データに現れた時点で測り直し、必要な大きさへ改める。** 数を発明した唯一の箇所であるため、ここへ明記して残す。
