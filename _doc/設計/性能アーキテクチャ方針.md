# 性能アーキテクチャ方針

マクロ性能（桁で効くアーキテクチャ選択）を軸ごとに「現在の決定 / 将来の大技 /
着手トリガ / 扉の状態」で棚卸しする生存型文書。微視的最適化（バリアの範囲最小化・
メモリレイアウト調整等）はこの文書の対象外で、評価軸.md の計測フローに従う。

## 方針（幹): マクロ最適化の3分類

- **(A) 片道ドア**: 後から変えると桁のコストになる選択。**今、意識的に決める**。
  開発計画の「扉」制度（判断基準0）がこれ
- **(B) 後付け可能な大技**: 後から足せるが桁で効く技法。**名指しで棚に置き、
  着手トリガ（計測・フェーズ）を決めておく**。今やらない理由は「対象ゲームの負荷特性が
  未確定のまま特化すると誤った方向へ最適化する」ため（開発計画: 特化最適化は
  対象ゲーム決定後）
- **(C) 微視的最適化**: 計測が要求した時のみ（判断基準4）。M5のパス別GPU時間計測が計器

## 軸ごとの棚卸し（葉）

### 1. グラフィックスAPIの深さ
- 決定済み(A): 生Vulkan（ash）直接。wgpu/vulkano の汎用性の税金を払わない。
  バインドレス・メッシュシェーダー・マルチキューの上限が存在しないことが全軸の前提
- これが本プロジェクト最大のマクロ決定（README採用理由参照）

### 2. 描画発行モデル（CPUがGPUへ仕事を渡す形）
- 現在: CPUが毎フレーム、メッシュ単位で draw を発行（現物量では律速でない）
- 大技(B): バインドレスディスクリプタ + 間接描画 + GPU駆動カリング。
  数万オブジェクト時にドローコールCPU律速を桁で解消する
- トリガ: フェーズ2「地形と植生」（計画済み）。または物量スケーリング計測（評価軸3.3）で
  CPU律速の折れ点が実測された時
- 扉の状態: 開。ディスクリプタは現在クラシック構成だが、リソースはハンドル参照で
  レンダーグラフに集約されており、移行は blitz_render 内部に局所化される

### 3. レンダリング経路
- 決定済み(A): forward + dynamic rendering。G-bufferレイアウトを確定させない
  （deferredの扉 = 絵の様式の扉。開発計画の3つの扉）
- 大技(B): deferred / visibility buffer（大量動的光源・シェーディングコスト分離）
- トリガ: 絵の様式確定（M3時点の扉確認は2026-07-20実施: 3枚とも開。
  マテリアルはシェーダー1本だが型・データ形式に焼き付けなし / AA未導入 / G-buffer不存在）

### 4. 同期・キュー構成
- 現在: 単一グラフィックスキュー + レンダーグラフ宣言順実行（M5）
- 大技(B): 非同期コンピュート（計算キューでシミュレーションを描画と重畳しGPUを飽和させる。
  生Vulkan採用理由の一つ・シミュレーション層の主戦場）
- トリガ: M9でXPBD布の実負荷をパス別GPU時間で計測し、重畳の利益が数字で見えた時。
  レンダーグラフの依存宣言が既にあるため、スケジューラとキュー割当の追加で対応できる
  （レンダーグラフ設計文書「実行モデル」に明記済み）
- 扉の状態: 開（グラフ導入自体が扉を開けるための布石）

### 5. GPUメモリ戦略
- 現在: リソースごとに個別 vkAllocateMemory（実装最小）
- 課題(B): Vulkanにはallocation数上限（維持4096程度）と断片化があり、アセット量が
  増えると専用アロケータ（サブアロケーション）が必須になる。自作 or VMA系の採用審査
- トリガ: M8（キャラクター基盤）前後でリソース数を計測し、上限の1/4に達したら。
  またはテクスチャ/バッファ生成のスパイクが計測された時
- 扉の状態: 開（確保箇所は vulkan/memory.rs 系に集約済みで差し替えは局所）

### 6. CPU並列性
- 現在: 単一スレッド（世界更新・コマンド記録とも。現物量で律速でない）
- 大技(B): コマンド記録の並列化（セカンダリコマンドバッファ/マルチプール）、
  更新のジョブシステム化
- トリガ: フレーム時間分布（評価軸3.4）でCPU側律速が実測された時（ゲームフェーズ想定）
- 扉の状態: 開（フレーム内実行順序はコンポジションルートの明示逐次コードに一元化
  されており、段階の並列化は構造変更が局所で済む。ループ所有権A→B移行と同型の設計）

### 7. パイプライン・シェーダー管理
- 現在: 数本を起動時生成（キャッシュ無し）
- 大技(B): VkPipelineCache永続化・事前ウォーム、マテリアルパーマテーション管理
- トリガ: マテリアル多様化（ゲームフェーズ）でヒッチ（評価軸のp99）が実測された時

### 8. 物量・ストリーミング
- 現在: 未着手（フェーズ2の定義的機能）。先行手当ては安定ID参照（M3導入済み）のみ
- 大技(B): チャンク分割・非同期ロード・メモリ予算管理・LOD
- トリガ: フェーズ2着工（M11完了後）

### 9. 座標精度（オープンワールド固有）
- 決定済み(A): ワールド座標とGPUへ渡す座標の型分離（第4の扉、blitz_mathの
  フレーム型で担保）。カメラ相対レンダリングを後付け可能に保つ
- トリガ: フェーズ2ストリーミングで世界がkm級になった時に実装

## 運用

- 各マイルストーンの設計判断（開発スレッドの判断N）でこの文書の軸に触れる決定をしたら、
  該当節を更新する（生存型文書の一致義務）
- トリガ条件は評価軸.md の計測（予算比・スケーリング・p99）を入力とする。
  トリガ未成立での大技着手は「計測なしの推測最適化」として禁止
- 扉確認の定点: M3完了時（実施済み・全開）/ M11（フェーズ1完了検証で全軸を総点検）
