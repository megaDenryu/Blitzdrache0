# 性能アーキテクチャ方針

この文書は、性能に大きな影響を与えるアーキテクチャ上の決定を軸ごとに一覧化し、各軸について「現在の決定」「将来の最適化手法」「着手条件」「可逆性」を管理する。実装と常に一致させて維持する。
細かな最適化(バリア範囲の縮小・メモリレイアウト調整など、影響が局所にとどまるもの)はこの文書の対象外で、`_doc/計画/評価軸.md` の計測フローに従う。

## 方針: 性能に関わる決定の3分類

1. **不可逆な決定**: 後から変更するとアーキテクチャの広範囲な書き直しを要する選択。この分類に該当する選択は、実装を始める前に決定して本文書と開発スレッドに記録する。管理原則は開発計画の判断基準0(可能性を閉じる決定を早期にしない)であり、絵の様式に関する個別項目は `_doc/計画/開発計画.md` のプロダクトビジョン節に列挙されている。
2. **後から導入可能な大規模最適化手法**: 導入すれば対象処理の性能が数倍から10倍以上改善しうるが、現時点では不要な手法。手法名と着手条件(どの計測値・どのフェーズで着手するか)を先に記録しておく。現時点で実装しない理由は、対象ゲームの負荷特性を計測できる前に特化すると誤った対象へ最適化するリスクがあるため(開発計画: 特化最適化は対象ゲーム決定後)。
3. **細かな最適化**: 計測が必要性を示した場合のみ行う(開発計画の判断基準4)。

## 軸ごとの一覧

各軸の「可逆性」は「その決定を将来変更した場合、影響範囲が現在の構造で局所化されているか」を意味する。

### 1. グラフィックスAPIの抽象度

- 決定(不可逆): ash による Vulkan の直接使用。wgpu / vulkano のような汎用抽象層を挟まない。
- 理由: バインドレスディスクリプタ・メッシュシェーダー・複数キューなどの機能上限が抽象層によって制限されないことが、以降の全軸の前提になる。採用理由の詳細は README「利用ライブラリ」。

### 2. 描画発行方式

- 現在: CPUがメッシュ単位で描画コマンドを毎フレーム発行する。現在の物量では律速でない。
- 将来の手法: バインドレスディスクリプタ + 間接描画 + GPU駆動カリング。数万オブジェクト規模で描画コマンド発行がCPU律速になる問題を解消する。
- 着手条件: フェーズ2「地形と植生」の着工、または物量スケーリング計測(評価軸3.3)で描画コマンド数起因のCPU律速が実測されたとき。
- 可逆性: 高い。ディスクリプタ構成の変更は blitz_render 内部に閉じる(リソースはハンドル参照でレンダーグラフに集約済み)。

### 3. レンダリング経路

- 現在の決定: forward + dynamic rendering。deferred が必要とする G-buffer レイアウトを確定させない(絵の様式が未決定のため。開発計画の3条件)。
- 将来の手法: deferred / visibility buffer。大量の動的光源、またはシェーディングコストとジオメトリコストの分離が必要になった場合の選択肢。
- 着手条件: 絵の様式の確定。M3時点の定点確認は2026-07-20に実施済みで、3条件(マテリアルの型・データ形式に単一シェーディングモデルを固定しない / TAA不採用 / G-buffer不存在)はすべて維持されている。

### 4. キュー構成と同期

- 現在: 単一グラフィックスキュー。レンダーグラフはパスを宣言順に実行する。
- 将来の手法: 非同期コンピュート(計算専用キューでシミュレーションを描画と並行実行し、GPU使用率を上げる)。Vulkan直接使用の採用理由の1つで、キャラクターシミュレーション(M9以降)が主対象。
- 着手条件: M9でXPBD布の負荷をパス別GPU時間で計測し、並行実行による短縮効果が数値で示されたとき。
- 可逆性: 高い。レンダーグラフに依存宣言が既にあるため、実行順スケジューラとキュー割り当ての追加で導入できる(参照: `_doc/設計/レンダーグラフ.md` 実行モデル)。

### 5. GPUメモリ確保

- 現在: リソースごとに vkAllocateMemory を個別に呼ぶ。
- 課題: Vulkan には総アロケーション数の上限(maxMemoryAllocationCount。多くの環境で4096)と断片化の問題があり、リソース数が増えた段階でサブアロケーション(大きく確保した領域を分割して使う方式)が必須になる。自作するかVMA系ライブラリを採用するかは、その時点で採用審査を行う。
- 着手条件: M8前後でアロケーション数を計測し上限の4分の1に達したとき、またはメモリ確保起因のフレーム時間スパイクが計測されたとき。
- 可逆性: 高い。確保箇所は vulkan/memory.rs 系に集約済み。

### 6. CPU並列性

- 現在: 単一スレッド(世界更新・コマンド記録とも)。現在の物量では律速でない。
- 将来の手法: コマンド記録の並列化(セカンダリコマンドバッファまたは複数コマンドプール)、更新処理のジョブシステム化。
- 着手条件: フレーム時間分布の計測(評価軸3.4)でCPU律速が実測されたとき。ゲームフェーズでの発生を想定。
- 可逆性: 高い。フレーム内の実行順序はコンポジションルートの逐次コードに一元化されており、段階単位の並列化は構造変更が局所で済む。

### 7. パイプライン管理

- 現在: 数本のパイプラインを起動時に生成する。キャッシュなし。
- 将来の手法: VkPipelineCache の永続化と事前生成、マテリアル別シェーダーバリアントの管理。
- 着手条件: マテリアルの多様化(ゲームフェーズ)で、パイプライン生成起因のフレーム時間の突発的悪化(p99の悪化)が計測されたとき。

### 8. 物量とストリーミング

- 現在: 未着手(フェーズ2の中心機能)。先行実装は安定ID参照(M3)のみ。
- 将来の手法: 世界のチャンク分割・非同期ロード・メモリ予算管理・LOD。
- 着手条件: フェーズ2着工(M11完了後)。

### 9. 座標精度

- 決定済みの布石: ワールド座標とGPUへ渡す座標を型で分離済み(blitz_math のフレーム型)。これによりカメラ相対レンダリング(f32の精度劣化を避けるため、描画時に座標をカメラ原点基準へ移す方式)を後から追加できる。
- 着手条件: フェーズ2のストリーミングで世界の広さがkm級になったとき。

## 運用

- マイルストーンの設計判断がこの文書の軸に触れたら、該当節を同じコミットで更新する(実装と文書の一致義務)。
- 着手条件の判定には評価軸.md の計測(フレーム予算比・物量スケーリング・フレーム時間p99)を使う。条件を満たさない段階での大規模最適化の実装は、計測に基づかない最適化として禁止する(開発計画の判断基準4)。
- 定点確認: M11(エンジンフェーズ1完了検証)で全軸を確認する。
