# 開発ループとコンパイル時間

コンパイル時間まわりの開発体験の方針。
結論: ホットリロードは対象別の3層で実現し、反復の9割（絵作り・調整）は再コンパイル不要の層でカバーする。
部分コンパイルはRust標準の差分コンパイル + クレート分割で成立している。

## 3層の開発ループ

### Tier 0: 再コンパイル不要（1秒未満）
- シェーダー: ファイル監視 → Slang再コンパイル → パイプライン再生成（M1で導入）
- アセット: `cargo xtask watch-assets`は版付きカタログのソース依存を250ms間隔で監視し、変更時に同じ安定IDの生成物を再コンパイルする。アプリは生成物の更新を500ms間隔で監視し、同じ安定IDのシーンを実行中に差し替える
- 調整パラメータ: 開発用UIの露出・アニメーションブレンド用スライダー（M5〜M8で導入）。設定ファイル監視は未実装
- ゲーム開発の反復の大半（絵作り・手触り調整）はこの層に属し、Rustのコンパイル時間と無関係

### Tier 1: 差分コンパイル（数秒）
- 通常のコード変更。内側ループは `cargo check`（rust-analyzerの診断は即時）、実行するときだけ `cargo run`
- クレート = 再コンパイルの単位。変更したクレートと依存側だけが再ビルドされる。エンジンが育ったら blitz_sim 等の分割で単位を細かく保つ
- 実測（2026-07-20、空のワークスペース）: クリーンビルド19秒 / check 0.35秒。成熟時の見込み: クリーン数分、末端クレート変更の差分は数秒

### Tier 2: コードホットリロード（扉として維持。導入判断はゲームフェーズ）
- 実行中にゲームロジックのdylibを差し替える方式。RustはABIが不安定なため、C ABI境界（#[no_mangle]）か同一コンパイラ保証が必要。先行実装に hot-lib-reloader、Bevy/Fyroxコミュニティに実用例
- 状態を保った差し替えには構造体レイアウト互換が必要 → 版付きシリアライズ（グローバル憲法の後方互換原則）で移行する
- **Functional DDD（状態とロジックの分離）が前提条件を既に満たす**ため扉は開いている。適用先は blitz_game のみ。エンジン本体は対象外（Vulkanリソースを跨ぐ再ロードは割に合わない）

## 部分コンパイルの仕組みと施策

- rustcの差分コンパイル（関数・モジュール粒度）は標準で有効
- 施策済み: devプロファイルでの依存クレート opt-level 2（初回のみ。以後キャッシュされる）/ rust-lld リンカ（.cargo/config.toml。リンクがボトルネックになりやすいため）
- 検討したが見送り: cranelift コード生成バックエンド（ビルド約3割高速だがnightly限定。安定版ツールチェーン運用を優先。差分が辛くなったら再評価）
- 規約: クレート境界の公開APIに重いジェネリクスを置かない。単相化が消費側クレートで行われるため、境界のジェネリクスは依存側の再コンパイルを太らせる。境界は具象型または dyn
