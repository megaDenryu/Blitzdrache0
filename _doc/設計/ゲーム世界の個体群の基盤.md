# ゲーム世界の個体群の基盤

この文書は、ゲーム世界の個体群(実行時個体IDと個体構成要素の組み合わせを保持する部分)を実装するクレート `blitz_ecs` の層と依存の向き、および主要な設計判断を定める設計正本である。親issueは Issue #44(アプリ境界と自前ECSの縦切り)であり、本文書は Issue #47(世代付きの実行時個体ID)と Issue #49(個体構成要素の置き場・問い合わせ・遅延構造変更の核)の成果物である。個体の種類と状態の正本所有者、および個体構成要素と基盤との契約26件は `_doc/設計/ゲーム世界の個体と個体構成要素.md` が正本として持ち、本文書は、その文書の表4(契約の置き場の裁定)を実装へ写す。用語は `_doc/計画/ユビキタス言語.md`「ゲーム世界の個体と個体構成要素の語彙」に従う。

## 目的

本文書は3つを成立させる。第1に、本文書は個体群の基盤が何を知ってよく、何を知ってはならないかをクレート境界で固定する。第2に、本文書は Issue #48 が Issue #49 へ渡した要求12件を、実装が推測せずに満たせる粒度の判断へ写す。第3に、本文書は「自前ECSを採用する」というオーナー裁定(Issue #44、2026-09-02)と、汎用ECSを先に作らないという以前の方針の線引きを明文化する。

## 層の定義

| 層 | 持つもの | 知ってよいもの | 知ってはならないもの |
|---|---|---|---|
| `blitz_ecs`(個体群の基盤) | 実行時個体ID・生存台帳・個体構成要素の標識となる`trait`・置き場・個体群・借りの型・構造変更の予約と反映 | `thiserror` だけ | blitz_math・blitz_game・blitz_engine・blitz_render・blitz_sim。具体ゲームの型も、物理・描画・アセットの型も知らない |
| `blitz_game`(ゲームロジック層) | 具体ゲームの個体構成要素の型と、個体群に作用する処理 | `blitz_ecs`・`blitz_math` | 従来どおり winit・ash・blitz_render |
| `blitz_app`(コンポジションルート) | 個体群の所有と、反映の境界の配線 | `blitz_ecs`・`blitz_game`・他の従来の依存 | 個体群の内部の走査(Issue #46 の原則「アプリはECS内部を知らない」) |
| `blitz_sim`・`blitz_engine`・`blitz_render` | 従来どおり | 従来どおり | `blitz_ecs`。物理APIは個体を受け取らず(Issue #44 の原則4)、描画は個体群を直接問い合わせない(原則3) |

この表の「持つもの」の列に並ぶ語は、下の判断2から判断7が順に定義する。`trait`とは、Rustが持つ、型に共通の振る舞いと境界を宣言する仕組みのことである。

依存の向きは `cargo xtask conform` の依存白リスト(`xtask/src/conform/dependency_whitelist/ledger.rs`)が機械で強制する。白リストは各クレートが持ってよい依存を列挙する形であるため、`blitz_sim`・`blitz_engine`・`blitz_render` の行に `blitz_ecs` を書かないことが、それらが個体群を知らないことの強制になる。`blitz_ecs` は `#![forbid(unsafe_code)]` を敷き、本文書の判断がすべて安全なRustで成立することを機械で保証する。

## 主要な設計判断

### 判断1: 個体群の基盤は独立したクレート `blitz_ecs` に置く

本文書は個体群の基盤を `blitz_game` の中のモジュールにしない。`blitz_game` は具体ゲーム(キツネの場所巡り・歩くだけ)のロジック層であり、基盤を同じクレートへ入れると、基盤が具体ゲームの型を参照しても何も落ちない。クレート境界だけが「基盤は具体ゲームを知らない」を強制できる。

クレート名の `ecs` は設計方式の名前としての略称であり、ユビキタス言語はこの用法を許している。クレート名はASCIIであることをプロジェクトの規約が求めており、日本語命名の受理条件の対象ではない。ただしクレート名にこの語を置くと、実装者が中の型名にも英語をそのまま使ってしまいやすくなる。本文書は、これを日本語命名の徹底と抽象名の禁止の2つで止める。第1に、`blitz_ecs` の公開する型名・メソッド名・フィールド名はすべて日本語にし、`ECS` という語はクレート名にだけ現れる。第2に、`cargo xtask conform` の検査へ、`blitz_ecs` の中で `World`・`Query`・`Component`・`Entity` の4語を識別子として使うことを違反にする項目を足す(実装は `xtask/src/conform/ecs_abstract_name.rs`)。

`blitz_engine` は `blitz_ecs` を知らない。`_doc/設計/ゲーム制作アーキテクチャ.md`「判断2」の「エンジンは実体の持ち方を強制しない」は、本文書の後も変わらない。変わるのは、同じ判断2の「汎用ECSを先に作らない」という後段であり、Issue #44 のオーナー裁定に従って「Blitzdrache0 のゲーム世界には自前の個体群の基盤を採用する。ただし archetype・万能Scheduler・巨大なマクロDSLは作らない」へ改める。

### 判断2: 実行時個体IDは添字と世代の組の値オブジェクトであり、生存台帳が発行する

`ゲーム世界の実行時個体ID` は `添字: u32` と `世代: u32` を私有フィールドに持つ値オブジェクトである。型名はユビキタス言語の登録語をそのまま使う。`ゲーム世界の実行時個体ID` が導出するのは `Debug, Clone, Copy, PartialEq, Eq, PartialOrd, Ord, Hash` であり、`剛体の識別子` と同じ組である。`Ord` は `(添字, 世代)` の辞書式順序になる。同じ添字に生きた個体が同時に2つ存在しないため、生きたIDの集合に対してこの順序は添字の昇順と一致し、契約25(走査の順序)と整合する。

`生存台帳` はスロットごとに世代と状態を持ち、破棄したスロットの世代を1つ進めて空き列へ戻す。生存確認は「添字の世代が一致し、かつ状態が生存である」を見るO(1)の判定である。**世代が上限に達したスロットは空き列へ戻さない。** 世代がu32で一周すると古いIDが新しい個体へ一致してしまうためであり、実用上は起きない(毎刻み10万個体を生成破棄しても一周に約700時間かかる)が、起きたときに黙って誤接続する形を規約が禁じている。10万個体の全スロットが一周するには42億かける10万回の再利用が要るため、この規則が枯渇を起こすことはない。

生存台帳の操作は、発行する・反映済みにする・破棄する・生存状態を答える、の4つである。失効した個体を反映済みにする要求と破棄する要求、および既に反映済みの個体をもう一度反映済みにする要求は、どれも呼び出し側の取り違えであり、黙って受理すると台帳が数える生存の件数と実体がずれるため、生存台帳は型付きエラーで拒む。

生存台帳が答える状態は3つである。`生存`(反映済みで問い合わせに現れる)・`反映待ち`(IDは発行済みだが、まだ反映の境界を通っていないため問い合わせに現れない)・`失効`(破棄済み、または世代が一致しない)。「生きているのに問い合わせに現れない」を `true` の1語で通すことを、本文書は無言の動作として禁じる。

現物の `エンティティID(u32)`(`crates/blitz_app/src/game/entity_id.rs`)は世代を持たない前身であり、描画供給側の台帳の鍵として本作業では触らない。置き換えは Issue #52 が行う。保存上の個体識別子の型は本作業で新設しない(契約20・22は Issue #54 の範囲)。実行時個体IDとの違いは、実行時個体IDが実行中だけ有効で区域の読み出しで失効してよいのに対し、保存上の個体識別子が保存と読み戻しをまたいで同じゲーム上の個体を指す点であり、定義はユビキタス言語が持つ。

### 判断3: 置き場は疎な集合であり、格納の方式は置き場の内部の選択である

`個体構成要素の置き場<T>` は、スロットの添字から密な列の位置を引く疎な配列と、IDの列と値の列を同じ並びで持つ密な列から成る(疎な集合)。個体構成要素の型は置き場の方式を知らない(契約10)。初版の方式はこの1つだけである。

置き場は、同じ個体へ同じ型の2つ目を書く操作を持たない(契約11)。追加は個体がその型を既に持っていれば型付きエラーを返す。2つ以上が要るなら、その複数を持つ1つの型を作る。

疎な配列は型ごとに全スロットぶんの長さを持つ。`_doc/設計/ゲーム世界の個体と個体構成要素.md` の表2(個体構成要素の候補)は37種類あり、10万個体で `Option<u32>` 相当の疎な配列を37種類持つと、実際には数十個体しか持たない型のぶんも含めて約30メガバイトが常時確保される。本文書はこの代償を承知で初版を1方式にし、数字を「計測の記録」の節へ残す。方式を増やす日には、型を消した置き場から具体の置き場を復元する対象の型を、方式を隠す型へ替える1段の工事が要る。

### 判断4: 個体構成要素の標識となる`trait`は1つであり、機能を持たない

`個体構成要素` は `Send + Sync + 'static` を上位境界に持つ、メソッドも関連型も関連定数も持たない、標識となる`trait`である。これは契約8(登録の認可)の中身であり、`_doc/設計/ゲーム世界の個体と個体構成要素.md` の表4の裁定どおり、契約2・3・4をその上位境界として束ねる。`'static` は契約2(借用を含まない)から来るとともに、型を消した置き場から具体の置き場を `std::any::Any` で復元するための要求でもある。全称の実装は書かない。書き手が実装を1行書くことが、その型を個体構成要素として登録してよいという意思表示である。

### 判断5: 個体群は型を消した置き場の列を持ち、型の復元は `std::any::Any` で行う

`ゲーム世界の個体群` は生存台帳と、`Vec<Box<dyn 型を消した置き場>>` と、型の識別から列の添字を引く索引を持つ。型を消した置き場の`trait`は、個体が消えるときに全個体構成要素を除く操作・件数と占有量を答える操作・型の復元のために `&mut dyn Any` を貸す操作を持つ。具体の置き場への復元は `downcast_mut::<個体構成要素の置き場<T>>()` で行う。

注意: 置き場の列の添字は、型を初めて登録したときに末尾へ足して以後変えない。索引がこれに依存する。置き場を削除する操作は持たない。

### 判断6: 問い合わせは借りの型を返し、個体群の可変参照そのものを処理へ渡さない

個体群の問い合わせは、反復子ではなく**借りの型**を返す。借りの型とは、1つまたは2つの置き場への参照を内部に持ち、IDの昇順の反復と個別の読み書きをメソッドで提供する型のことである。初版が持つのは、1型を読む借り・1型を可変に借りる借り・2型を読む借り・1型を読みもう1型を可変に借りる借り・2型を可変に借りる借り、の5つである。任意長のタプルへ広げるマクロは作らない。

`&mut ゲーム世界の個体群` が現れるのは借りを作る1箇所だけであり、個体群に作用する処理は借りの型を引数で受け、個体群そのものを受け取らない。Issue #55 の具体ゲームは、この借りを `キャラクター移動の対象を借りる` のように用途の名前で包む。基盤が借りの型を提供し、具体ゲームが用途の名前で包む、という2段の分担である。この向きは、サービスが自分の保持する依存を口から貸す形であり、呼び出し側が依存を持参する形ではない。

2つの置き場を同時に可変で借りる手段は `slice::get_disjoint_mut` である。同じ型を2度可変に借りる問い合わせは、`get_disjoint_mut` が返す誤りを受けて panic する。これは呼び出し側のコードの誤りであり実行時のデータに依存しないため、回復可能な失敗ではない。panic のメッセージに破られた不変条件と型の名前を書き、`#[should_panic]` の試験を1本置く。

### 判断7: 構造変更は予約の列へ積み、反映はセッション型で2段に分ける

処理の途中の生成・破棄・個体構成要素の追加と削除は、`構造変更の予約` へ積む(契約17)。予約の1件は名前を持つ命令の列挙(生成・破棄・追加・削除)であり、追加の値は型を消した箱で運ぶ。予約は個体群とは別の型であり、処理は `&ゲーム世界の個体群`(または借りの型)と `&mut 構造変更の予約` を同時に借りられる。

個体の生成は予約の時点でIDを発行する。生存台帳は置き場を触らないため即時でよい。発行した個体は反映まで `反映待ち` であり、問い合わせに現れない。同じ予約の列へその個体への追加を積めるため、生成と個体構成要素の追加は同じ反映の境界で一括で確定し、中途半端な組成を次の処理へ見せない。

予約の適用の順序は、積んだ順ではなく命令の種類で固定する。順序は「生成 → 個体構成要素の追加と削除 → 破棄」である。この順序なら、同じ境界で生成して個体構成要素を足して破棄することが矛盾なく書ける。積んだ順で適用する形は、複数の処理が同じ列へ積む設計と両立しない。

予約の矛盾は2つに分ける。同じ個体の同じ型への2つ目の追加は呼び出し側の誤りであり、**予約を積む時点で**型付きエラーを返す(予約は、置き場の現状と、同じ列に積まれた追加の両方を見る)。失効した個体への追加と削除は正常であり(契約21。発射元が先に消えた場合を通常として扱う)、反映が黙って捨てずに捨てた件数を数えて答える。検査を予約の時点へ前倒しすることで、反映は失敗しない操作だけになり、「一部だけ適用された置き場」という中途半端な組成は生まれない。

反映は1つのメソッドではなく、セッション型 `構造変更の反映` で2段に分ける。`個体群.構造変更の反映を始める(予約)` がセッションを返し、セッションは消える個体の一覧と、その個体が持つ個体構成要素を型ごとに読み出す口を持つ。外の工程(剛体の台帳・空間索引・変形体の基盤への口を持つ側)はここで登録を解除する(契約18の後始末は `trait` の外の工程が担うという、`_doc/設計/ゲーム世界の個体と個体構成要素.md` の表4の裁定)。`セッション.置き場への適用を終える()` が置き場を実際に書き換え、触った置き場の密な列を添字の昇順へ並べ直す(契約25)。セッションには `#[must_use]` を付け、個体群が未閉のセッションの件数を数えて破棄時に非0なら panic する。`Drop` には載せない。`Drop` は依存を受け取れない。

### 判断8: 計測は素朴な実装を先に測り、疎な集合の数字と並べる

Issue #49 の計測の目的は「型ごとに `HashMap` を引く素朴な実装より自作する意味があることを確認する」ことである。比較対象を先に測らなければこの確認はできない。したがって、疎な集合を書く前に、IDを鍵にした `HashMap` で置き場を持つ素朴な実装を計測専用に書き、1万と10万の個体について生成破棄・1型の走査・2型の問い合わせ・追加削除の4つを測る。この素朴な実装は本番の候補へ育てず、計測の役目が終わったら試験の中だけに残す。疎な集合を書いた後に同じ4つと占有量を測り、下の「計測の記録」へ表として書く。

## この段階でやらないこと

- archetype(個体構成要素の組み合わせごとに表を分ける方式)への移行と、格納の方式の2つ目。理由は、初版の問い合わせの集合が確定しておらず、方式の比較の基準が無いためである。契約10により方式は置き場の内部で後から替えられる
- 自動並列Scheduler・ジョブシステム。実行順は Issue #50 が直列で明示する
- Reflection・Serialization。保存の形は Issue #54 が版ごとの型で決める
- 任意タプル長の問い合わせのマクロDSL。初版は2型までで、3型が要る具体の要求が立った日にその要求から設計する
- 外部ECSクレートとの互換API
- 変更の検出(契約14)と個体の複製(契約19)。設計正本が初版で要求しないと裁定した
- 現行の `エンティティID(u32)` と `ゲーム状態の台帳` の置き換え(Issue #52)
- `blitz_engine` が個体群を知ること。「エンジンは実体の持ち方を強制しない」は変えない

| 要求 | 満たす判断 |

| 6. 生成と破棄と付け外しを安全な境界まで予約できる | 判断7 |

| 8. 外部基盤の識別子を持つ型とゲームの状態を持つ型を別扱いにしない | 判断4(標識は1つ) |
| 9. 万能の可変参照を各処理へ渡さず、用途の口へ狭められる | 判断6(借りの型) |

| 12. 型ごとの件数と占有量を数える口を持つ | 判断5(型を消した置き場の操作) |

## 計測の記録

本節は Issue #49 の完了時に埋める。素朴な `HashMap` の実装と疎な集合について、1万と10万の個体での生成破棄・1型の走査・2型の問い合わせ・追加削除の4つの所要時間と、10万個体・37型を仮定した占有量を表で書く。

## 決定性の保証

`blitz_ecs` はゲーム決定性(同じ初期状態と同じ入力系列から同じ結果になること)を、走査の順序をIDの昇順に固定し、予約の適用の順序を命令の種類で固定することで保証する。条件は、同じ順序で同じ予約を積むことである。失効する条件は、置き場の密な列を並べ直さずに反映を終えること(判断7がこれを禁じる)と、ハッシュの並びに依存した走査を足すことである。数値決定性は本クレートに数値計算が無いため対象外である。
