# Blenderアセット運用

この文書は、BlenderをAIエージェントに操縦させてエンジン用のアセットを作る運用の契約を管理する。管理する対象は、Blenderの実行形・成果物の扱い・glTF入力契約の検査手段の3つである。実装と常に一致させて維持する。

## 路線の目的

この路線の目的は、サンプルシーンを計測できる規模のアセットを供給することである。エンジンの性能と品質はアセットが無ければ測れず、アセットを人手で作ると供給が開発速度の律速になる。そこでBlenderをスクリプトで操縦し、アセットの生成を開発ループの中へ入れる。

段の計画は次のとおりである。オーナーが2026-07-30に開始を許可した。

- 段1(実装済み): glTF入力契約の検査器をxtaskへ新設し、Blender運用の契約をこの文書へ固定する
- 段2(実装済み): Blenderが生成したglbを実際に画面へ描き、絵として成立することを確かめる
- 段3(実装済み): 小物を10種そろえ、それらを散布した見本の集落を1つの世界として立て、実アセットの条件で絵と描画費用を見られるようにする
- 段4(実装済み): 1つのメッシュが複数の材質を持つ実アセットを受け入れ、契約検査からコンパイル・実行時ロード・絵の画素判定まで通す
- 段5以降: 未決定。段4の結果を見てオーナーが決める

## Blenderの実行形

Blenderの実体は `C:\Program Files\Blender Foundation\Blender 5.2\blender.exe` にあり、版は5.2.0である(2026-07-30にwingetの公式ソースから導入)。旧版4.0.2が `C:\Program Files\Blender Foundation\Blender 4.0\blender.exe` に併存しているが、新しい生成には5.2を使う。どちらの実行ファイルもPATHに登録されていないため、呼び出しは常に絶対パスで書く。

呼び出しの形は次の1つだけを使う。

```
"C:\Program Files\Blender Foundation\Blender 5.2\blender.exe" --background --factory-startup --python <スクリプト.py> -- <スクリプトへの引数>
```

3つの引数はいずれも省略できない。`--background` はウィンドウを開かずに終了させる。GUIを開くとプロセスが人の操作を待って戻らず、AIエージェントの実行が止まる。`--factory-startup` は利用者の設定とアドオンを読まずに起動する。設定を読むと、同じスクリプトの結果が実行環境の設定に依存して変わる。`--python` の後に置いたスクリプトを実行し、`--` の後の文字列はBlender自身が解釈せずスクリプトへ渡る。

スクリプト側は `sys.argv` から `--` の位置を探して引数を取り出す。引数が想定と違えば `SystemExit` で即座に落とす。無言で既定値を使うと、書き出し先を間違えたまま成功したように見える。

## 成果物の扱い

**Blenderのglb出力は、埋め込みテクスチャがあるとバイト列が実行ごとに変わる。** 同じスクリプトを同じBlenderで2回実行して比べると、glTFのJSONチャンクと幾何のバイナリ(頂点・インデックス)は完全に一致し、差分は埋め込みPNG画像の領域だけに現れる(2026-07-30の実測。4.0.2と5.2.0の両方で再現)。原因はPNGの符号化が出すバイト列が実行ごとに揺れることにあり、画素の絵としての内容は変わらない。テクスチャを埋め込まないglbはバイト列まで決定的である(単純な立方体で4.0.2は5回、5.2.0は5回の全一致を実測)。

この性質から、次の運用を採る。

**アセットの置き場は `C:\devs\Blitzdrache0Assets`(ローカル専用のgitリポジトリ、リモート無し)である。** 本体リポジトリへglbをコミットしない。GitHubとGit LFSへは上げない(オーナー方針、2026-07-30)。本体からの参照の仕組みは「本体からの参照の仕組み」節が管理する。

- **生成した.glbをリポジトリへ確定コミットする。** アセットの正本はコミットされたglbであり、スクリプトを再実行して同じものを得る運用は成立しない
- **生成に使った.pyを来歴として同じ変更に添える。** .pyの役割は、そのglbがどういう意図で作られたかを後から読めるようにすることと、似たアセットを作るときの出発点になることである。.pyから.glbを再現する契約は持たない
- .glbを更新するときは、.pyを直してから再生成し、両方を同じコミットへ入れる。テクスチャ埋め込みのglbは差分がバイト列として大きくなることを避けられない
- **テクスチャ画像を事前生成した固定ファイルとしてスクリプトへ与える形にすれば、埋め込みでも完全に決定化できる。** 2026-08-10に石積みの小屋(`props/stone_hut.glb`、2048画素四方のベースカラー2枚)で実測が立った。3回の生成がバイト一致し、埋め込まれたPNGは元のファイルと1バイトも違わなかった。Blenderの書き出し器は、画像が1枚のPNGファイルをそのまま使っているとき元のファイルを写すため、再符号化が起きないことが原因である。テクスチャの生成スクリプト(標準ライブラリのみのPNG符号化)もアセットリポジトリの`props/`に置き、規約はアセットリポジトリのREADME「テクスチャの扱い」の節が持つ

## 本体からの参照の仕組み

本体リポジトリのアセット宣言表が、外部のアセットリポジトリのglbを名指しで参照する。宣言の実体は `crates/blitz_asset_compiler/examples/compile_assets/world/asset_declaration.rs` にあり、置き場の解決は `crates/blitz_asset_compiler/examples/compile_assets/source_location.rs` が1箇所で持つ。

宣言1件は、安定IDと相対パスと**基準**の3つで書く。基準は2つあり、`本体のソースルート` は `assets/` からの相対、`外部ソースルート` は外部のアセットリポジトリからの相対である。宣言の1行1行は起点の実パスを持たないため、置き場を移しても宣言を書き換えない。

**外部ソースルートの場所は次の順で決める。**

1. 環境変数 `BLITZDRACHE0_ASSET_SOURCE_ROOT` があれば、その値をそのまま使う
2. 無ければ、本体リポジトリと同じ親ディレクトリに並ぶ `Blitzdrache0Assets` を使う

既定を隣接ディレクトリにするのは、絶対パスを本体リポジトリのコードへ焼くことを避けるためである。隣接の位置はコンパイル時の `CARGO_MANIFEST_DIR` から辿るため、実行時の作業ディレクトリに依存しない。この環境変数はソース側の置き場を指すものであり、実行時アセットルートを指す `--asset-root` とは別物である。

**ルートの不在は解決時の失敗にせず、値として運ぶ。** このアセットリポジトリはリモートを持たないため複製できず、存在しない環境が正当に成立する。そこで解決は必ず成功し、外部のソースを実際に引いた地点で初めて診断つきの失敗を返す。診断には見た場所と上書き用の環境変数名が入る。

失敗の扱いは2段に分かれる。

- **ルートそのものが無い**: その宣言を飛ばし、見た場所を添えて標準出力へ告げる。実行時形式は作られない
- **ルートはあるが宣言したファイルが無い**: 宣言の破れとして、探したパスを添えて失敗させる

飛ばす側にするのは、アセットリポジトリを持たない環境でも既存の検証が動き続ける必要があるためである。ただし飛ばしたままでは、そのアセットを使う検収が「カタログ未登録」という遠い場所の失敗に化ける。そのため検収の入口(`cargo xtask prop-draw`)が、実行時形式のファイルが作られたかを名指しで確かめてから描画へ進む。

## 絵に出すまでの経路

Blenderが生成した小物は、板の世界(`chunk_world`)の宣言に並ぶ。板の世界は `quad`・`shadow_scene`・`helmet`・`fox` という単体表示の検証シーンが集まる世界であり、小物1体を原点へ置く構図はこの流儀と同じである。専用の世界を足さないのは、1つの出力ルートが1つのチャンク目録を持つ制約から、世界を増やすと目録ソースと出力ルートが増えるだけで、得られる検証が変わらないためである。

シーン名の接頭辞 `prop_` が3つの方針を選ばせる。

- **カメラ**: `crates/blitz_app/src/app/scene_camera.rs` が、体積の中心を注視して3面が同時に見える斜めの姿勢を与える
- **空**: 空を持つのは `terrain` で始まる世界だけであるため、既定のまま空なしになる。背景がクリア色であることを前提にした画素判定が成り立つ
- **検収計画**: `crates/blitz_app/src/smoke/mod.rs` が、書き換えもピクセル判定も行わない読み戻しだけの計画へ振る。既定の計画は `quad` のホットリロード検証であり、監視対象のシェーダーと `quad` の実行時形式を書き換える

検収は `cargo xtask prop-draw` が行う。ポスト処理を外した条件で画素を判定し、本番の経路の絵をPNGへ書き出す。判定が弾くのは、何も描かれていない・画面全体が塗られている・物体が構図の中央に無い・面の明るさが一様で立体に見えない、の4つである。**絵としての見た目の合否は判定に含まれない。** 目視は親エージェントが書き出されたPNGで行う。

### 見本の集落の世界

見本の集落は `village_world` という独立した世界であり、出力ルートは `target/village_assets` である。世界を分けるのは、1つの出力ルートが1つのカタログと1つのチャンク目録しか持てず、原点チャンクを占める世界どうしが同居できないためである。

**世界はチャンクを1つだけ持ち、そのチャンクが集落そのものである。** シーンの安定IDは `prop_village` であり、地面の高さ格子は `assets/village_world/village_x0_z0.heightgrid` にある。チャンクを増やさないのは、この世界の目的が実アセットの絵と描画費用を見ることであり、チャンクの出入りは地形の世界と植生の世界がすでに検収しているためである。

シーンは描画対象を11個持つ。地面が1個で、小物の群が種ごとに1個ずつ10個である。地面は地形の世界と同じ経路で高さ格子から地形LODメッシュ群として焼き、小物の接地の高さは最詳細段が張る三角形の平面から引く。群の共有マテリアルは**原型のglTFが宣言したものをそのまま使う。** 小物は種ごとに色が違い、その色は生成した本人がベースカラー係数で与えているため、コンパイラが選び直すと作者の宣言と絵が食い違う。植生の同居がマテリアルを選び直すのは原型が既定の白のままで地形と画素で見分けられないからであり、こちらにその事情は無い。

配置は種ごとに様式を選ぶ。様式は3つあり、`輪に沿う`は中心を囲む輪へ等間隔に並べて個体を接線へ向け、`集まり`は指定した点のまわりの円板へ集め、`一様に散らす`は正方領域へ格子状に散らす。囲いを作る石垣・柵・杭は半径15.0・26.0・30.5メートルの3重の輪になり、荷と器は輪の内側の4箇所へ寄せ、岩と切り株は一辺84から88メートルの領域へ散る。合計は1035体である。配分の表は `crates/blitz_asset_compiler/examples/compile_assets/world/village_declaration.rs` が持つ。

**この世界は `cargo xtask compile-assets` の引数なし実行に入れていない。** 小物の原型が外部のアセットリポジトリにしか無く、それを持たない環境では焼けないためである。焼けない世界を一括生成へ入れると、アセットリポジトリを持たない環境で既存の検証が全部止まる。この世界を焼くのは `cargo xtask village-draw` と、世界名を明示した `cargo xtask compile-assets assets target/village_assets village_world` の2つである。

シーン名を `prop_` で始めるのは、書き換えもピクセル判定も行わない読み戻しだけの検収計画を選ばせるためである。初期カメラだけは名前そのもので分かれ、小物1体を斜めから見る姿勢ではなく集落を見下ろす姿勢になる(`crates/blitz_app/src/app/scene_camera/village_view.rs`)。空は世界の方針では付かない(方針が空ありになるのは名前が `terrain` で始まる世界だけである)ため、`village-draw` が `--sky` で明示する。

### 絵と描画費用を見る入口

`cargo xtask village-draw` が、ソースアセットの生成・集落の世界の実行時形式への変換・本番の描画経路での180フレーム実行・PNGへの変換までを行う。書き出し先は `target/village_draw/village.png` である。**画素の合否判定は置かない。** この入口の目的は絵として成立しているかの判断材料を出すことであり、その判断は目視が行う。機械が見るのはvalidationが0件であることだけである。

同じ実行が既存の終了時報告を有効にして、フレーム間隔・パス別GPU時間・描画発行内訳・Vulkanメモリ確保を標準出力へ出す。新しい計測基盤は作っていない。時刻は17時に固定してあり、太陽が低いため小物の影が地面を長く横切って、起伏と物の高さが影の形で読み取れる。

### 2026-07-31の実測

`cargo xtask village-draw` の1回の実行から採った値である。

- **描画発行数はパスごとに11である。** シーンも4つの距離区分のシャドウもすべて11であり、地面1つと群10個に対応する。個体数が1035であっても発行数が個体数に比例しないことがこの値で確かめられる
- **候補1036に対しシーン可視は982である。** 距離区分0のシャドウ可視は751、距離区分1から3は1036である。個体別LODの段切替は0回であり、小物の原型がどれも段を1つしか持たないためである
- **パス別GPU時間はシーン描画0.183ミリ秒、シャドウ合計0.396ミリ秒である。** 大気の多重散乱生成が0.547ミリ秒で最も大きい。この時点では小物の描画がフレーム時間の支配要因になっていない
- **CPU側フレーム間隔はp50が16.9ミリ秒である。** これはFIFO提示待ちを含む値であり、提示が支配する系列であるから描画費用の指標にしてはならない
- **Vulkan確保は現在127件・最大同時136件、validationは0件である**

**既知の見え方の限界**: 世界がチャンク1つであるため、集落を載せた一辺100メートルの地面が四角い島として見え、その外側には大気が作る地面色だけが広がる。チャンクを増やせば島の縁は消えるが、配置がチャンク中央を基準に決まるため、同じ集落が隣のチャンクにも現れる。地面を広げることと集落を1つに保つことの両立はこの段の範囲外である。

### 石積みの小屋を絵に出す経路

`props/stone_hut.glb`は屋内の多光源の検収世界(`stone_hut_world`、シーンの安定IDは`prop_stone_hut_interior`)が読む。据え方は群でなく**固定物の据え付け**である。群の原型は全段で1つのマテリアルを共有する形式契約を持ち、石と木の2材質を持つこの小屋を受け取れないためである(`crates/blitz_asset_compiler/src/loader/archetype_material.rs`)。地面へ固定物を据える経路は場所巡りの世界の目印の柱が持っていたものを一般化して共有している(`crates/blitz_asset_compiler/src/fixed_placement.rs`)。

据え付けは回転を持たないため、小屋は原型の姿勢のまま立つ。この原型の戸口は局所+Z軸を向いており、世界の+Z軸を向いて立つ。カメラは小屋より+Z側に立ち、戸口ごしに屋内を見る。テクスチャ格納方針は既定(全てRGBA8)のままであり、2048画素四方のベースカラー2枚を含む実行時形式は約34メガバイトになる。

検収は`cargo xtask cluster-lights`が行う。灯を3件点けた条件と0件の条件で同じ構図を撮り、屋内が点光源で照らされていることを画素で確かめる。**絵の合否は判定に含まれない。** 参照: `_doc/設計/クラスタ多光源と点光源の影.md`「第4段階の実装と検収の実測」

## 段4: 複数材質の実アセットの受入

この段の目的は、1つのメッシュが複数の材質を持つ実アセットを、契約検査からコンパイル・実行時ロード・絵の画素判定まで通すことである。エンジン側の受理範囲と段の計画は `_doc/設計/マルチマテリアルと材質境界.md` が管理し、この節はBlender側の作り方と検収の入口を管理する。

### 材質を3つ持つ小物

アセットリポジトリの `props/banded_chest.glb` が金具付きの木箱である。木の本体へ鉄の帯を2本巻き、4隅へ真鍮の角金具を立てた、幅0.88・奥行0.68・高さ0.80メートル・三角形84枚の箱である。材質は木・鉄・真鍮の3つであり、Blenderの書き出し器が材質スロットごとにプリミティブを分けるため、glbは1メッシュ3プリミティブ3マテリアルになる。

**3つの部品の外面をすべてずらす。** 木の本体が幅0.80・奥行0.60、鉄の帯がその外へ0.02ずつ、真鍮の角金具がさらに0.02ずつはみ出す。同じ面に2つの部品が乗ると同一平面の奥行き争いが縞として絵に出て、材質ごとの画素が混ざるためである。角金具の上端と下端を本体の上面と底面から離すのも同じ理由である。境界箱は最も外へ出る角金具で決まる。

**材質の割り当ては生成スクリプトが部品ごとに行い、書き出す前に検査する。** 検査するのは、全ての面が実在する材質を指すことと、宣言した材質がすべて1面以上に使われていることの2つである。面を1枚も持たない材質は書き出し器がプリミティブを作らないため、宣言した材質の数と絵に出る材質の数が食い違う。書き出した後は、マテリアル数とプリミティブ数が宣言と一致することと、全プリミティブが材質を宣言していることを確かめる。共通の工程は `props/prop_common.py` の `複数材質で生成する` にある。

テクスチャを持たないため、成果物は3回の生成でバイト列が完全に一致することを実測した。

### 絵と画素判定の入口

`cargo xtask prop-multi-material-draw` が、ソースアセットの生成・実行時形式への変換・本番の描画経路での実行・画素と計数の判定・PNGへの変換までを行う。書き出し先は `target/prop_multi_material_draw/` であり、`flat.png` が材質の色をそのまま読む条件、`post.png` が本番経路の絵である。

**画素の判定は領域でなく色の分布で行う。** 小物のどの面がどの材質かは構図とカメラ姿勢に依存するため、判定領域を画面の座標で決められない。ライティングとポスト処理を切ると1つの材質が塗る画素はすべて同じ色になるため、材質の本数は色の山の本数として現れる。判定は4つである。物体画素が画面の2パーセント以上あること、上位3色のどれもが物体画素の6パーセント以上を占めること、3色が互いにどれかの成分で30階調以上離れていること、3色が合わせて物体画素の80パーセント以上を覆うことである。材質が1つへ縮退すれば色の山は1本になり、2位と3位には輪郭のにじみしか残らないため、2つめの下限で必ず落ちる。

**アセットが宣言した色の写しを検収側へ持たない。** 写しを持つと、アセットの色を変えたときにこの検収だけが無言で通らなくなる。

計器の判定はシーンパスの発行数が材質の数と一致することと、validationが0件であることである。glbは材質スロットごとにプリミティブを分け、レンダラーはプリミティブごとに1回発行するため、プリミティブの脱落がこの数に出る。

### 2026-08-01の実測

`cargo xtask prop-multi-material-draw` の1回の実行から採った値である。読み戻し画像は1280×720である。

- **背景でない画素は147505であり、画面の16.0パーセントを占める**
- **上位3色は木が(153, 121, 85)で78181画素、真鍮が(221, 197, 118)で46957画素、鉄が(129, 132, 139)で22367画素である。** 割合はそれぞれ53.0・31.8・15.2パーセントであり、3色の合計は物体画素と完全に一致する。ライティングとポスト処理を切った条件では面の縁に中間色が出ないためである
- **色の隔たりは最も近い木と鉄で54階調である**(青の成分)。木と真鍮は赤で68、真鍮と鉄は赤で92である
- **シーンパスの発行数は3、シーン可視数は1、validationは0件である**

既存の検収入口(smoke・prop-draw・instance-cull・multi-material-draw)の判定値は不変である。

## glTF入力契約の検査

`cargo xtask check-glb [--archetype] <glbまたはgltfのパス...>` が、エンジンのアセットコンパイラが受け取れる形になっているかを検査する。複数のパスを一度に渡せる。

検査する契約は3つあり、どれで検査するかは呼び出し側が旗で選ぶ。旗を付けなければ静的シーンの契約(1ファイル1メッシュ)であり、`--archetype` を付けると群の原型の契約(複数のメッシュを詳細段の列として読む)、`--part` を付けると部品の契約(静的シーンと同じ形のメッシュに接合点の宣言を載せたもの)である。旗はその実行の全パスへ同じに効く。メッシュの個数から契約を推し量らないのは、静的シーンとして書き出した小物が誤って2メッシュになったとき、推し量る形だと原型の契約が無言で当たって合格が返るためである。契約を取り違えた合格は、検査していないことより悪い。

検査は最初の破れで止めず、見つけた指摘を全件並べる。指摘は重大度・位置・内容・是正方法の4つを持つ。重大度は2つある。

- **違反**: 焼けないか、焼けても作者の宣言と絵が食い違うことが確定するもの。1件でもあれば終了コードは1になる
- **警告**: 宣言がローダーに読まれず捨てられるが、作者がその宣言を諦めていれば絵は成立するもの。終了コードには影響しない

警告で落とさないのは、Blenderの書き出しには作者が気にしていない宣言が常に混ざるためである。それで落とすと運用者が終了コードを見なくなる。

検査は概要も出す。概要はメッシュ数・プリミティブ数・材質スロット数・頂点数・インデックス数・先頭のメッシュ(群の原型なら最詳細段)の境界箱である。境界箱を出すのは、絵に出ない事故の多くが位置と大きさの取り違えであり、数値を見れば切り分けが1回で済むためである。材質スロット数を出すのは、1メッシュが複数の材質を持てるようになり、作者が分けた材質の境界が何本残ったかを数で確かめられるようにするためである。

マテリアルに関する検査は材質スロットごとに1回ずつ行う。同じマテリアルを参照するプリミティブが何件あっても指摘は1件へ畳む。先頭の材質だけを見ないのは、2番目以降の材質へ書いた宣言の破れが黙って通ると、作者の宣言と絵が食い違うためである。

検査の実体は `crates/blitz_asset_compiler/src/loader/contract.rs` 以下にあり、xtaskはexampleを起動して終了コードを写すだけである。ローダーの隣に置いたのは、契約の正本がローダーの実装だからである。検査は文書を開く処理・メッシュを読む処理・マテリアルを読む処理をローダーからそのまま呼び、読み方の写しを持たない。

## エンジンのglTF入力契約

契約の正本は `crates/blitz_asset_compiler/src/loader/` の実装である。以下はその要約であり、実装と食い違ったときは実装を正とし、この節を直す。

- 1つのglTFファイルは1つのメッシュを持つ。ローダーは先頭のメッシュだけを読む
- 1つのメッシュは複数のマテリアルを持てる。ローダーは全プリミティブを連結しつつ、プリミティブごとのインデックス区間と材質スロットIDを残す。glTFのmaterial indexはプリミティブの出現順で0から振り直す
- ノードの変換は読まれない。配置はエンジン側のシーン定義が与える
- 座標系は glTF の規約（Y が上の右手系）である。Blender の書き出しが Z が上から変換するため、`export_yup=True` を明示する。**extras へ載せる値は書き出し器が変換しないため、Blender の側で同じ変換を適用してから載せる**（参照: `_doc/設計/部品カタログと接合点.md`「座標系は glTF に合わせる」）
- 面は三角形である。インデックス列は三角形リストとして扱われる
- 頂点位置(POSITION)は必須である。法線と接線とUV座標は欠けていても計算か既定値で充填される
- マテリアルはpbrMetallicRoughnessのベースカラー・金属粗さ・法線マップの3枚と、ベースカラー係数・金属度係数・粗さ係数だけが読まれる。係数は0以上1以下の有限値である
- テクスチャの画像はpngまたはjpegである。data URIは受け取らない
- 拡張機能は一切解釈されない

### 静的シーンの契約の検査項目とその根拠

| 検査項目 | 重大度 | 根拠 |
| --- | --- | --- |
| メッシュ数が1である | 違反 | `loader/mod.rs` が `document.meshes().next()` だけを読む |
| 読み込みに必須の拡張機能を宣言していない | 違反 | ローダーが拡張機能を参照する箇所が無い |
| 拡張機能の使用宣言が無い | 警告 | 同上 |
| カメラを含まない | 警告 | ローダーがカメラを読まず、視点はアプリ側がシーン名から決める |
| 先頭メッシュを参照するノードがちょうど1つである | 違反 | ローダーがメッシュを1回だけ読み、ノードごとの配置を作らない |
| 先頭メッシュに効くノード変換が単位行列である | 違反 | `loader/mod.rs` が配置変換に単位行列を直接与える。スキン付きメッシュは対象外(glTF仕様がノード変換の無視を要求する) |

| テクスチャがあるならUV座標(TEXCOORD_0)がある | 違反 | `loader/mesh/primitive.rs` がUV欠落を(0,0)で充填する |

| 頂点位置とインデックスが読める | 違反 | `loader/mesh/primitive.rs` がPOSITION欠落を型付きエラーで拒む |
| 頂点1個以上・インデックス1個以上である | 違反 | 実行時形式の書き出しが0件を拒む |
| インデックスが頂点数の範囲内である | 違反 | 同上 |
| インデックス数が3の倍数である | 違反 | 三角形リストとして扱うことから従う |
| 頂点属性に非有限の小数を含まない | 違反 | 実行時形式の書き出しが非有限の小数を拒む |

| テクスチャの幅と高さが1以上である | 違反 | 同上 |
| テクスチャの画像がデコードできる | 違反 | `loader/texture_decode.rs` のデコードを実際に走らせる |

| 画像がdata URIでない | 違反 | `loader/texture_decode.rs` がdata URIを型付きエラーで拒む |
| テクスチャがTEXCOORD_0を参照する | 違反 | `loader/mesh/primitive.rs` がUV座標を0番の組からしか読まない |

| doubleSidedが真である | 警告 | レンダラーが面の裏表を捨てない設定であり、片面表示の宣言は効かない |
| スキン付きならJOINTS_0とWEIGHTS_0が揃う | 違反 | `loader/mesh/skin_vertex.rs` が両方を要求する |
| スキンが無いならアニメーションを持たない | 違反 | `loader/mod.rs` がスキンの無いメッシュでアニメーション一覧を空にする |
| アニメーションの補間がCUBICSPLINEでない | 違反 | `loader/animation/` がCUBICSPLINEを型付きエラーで拒む |

### 群の原型の契約と検査項目

群の原型は、複数のメッシュを詳細段(LOD)の列として読む別の契約を持つ。`loader/archetype.rs` がglTFの並べたメッシュの順をそのまま段番号とし、先頭を最詳細段として読む。ノードは一度も読まれず、個体の配置は散布が与える。マテリアルは段ごとに持たず、外側の描画対象データが1つだけ持つ。

| 検査項目 | 重大度 | 根拠 |
| --- | --- | --- |
| メッシュが2個以上ある | 違反 | 段が1つの文書は段の列でなく、切り替える先の段が無い |
| ノードの数がメッシュの数と一致する | 違反 | 段とノードが1対1でなければ、どのノードがどの段なのかを読み手が対応付けられない |
| 段に効くノード変換が単位行列である | 違反 | `loader/archetype.rs` がノードを読まず、個体の配置は散布が与える |
| 段ごとのプリミティブがちょうど1個である | 違反 | 段の中の全プリミティブが1つの頂点列へ連結される。ある段だけ材質の境界が増えると、絵の分かれ方が段ごとに変わる |
| 段の描画の並び方が三角形である | 違反 | 静的シーンと同じくインデックス列を三角形リストとして渡す |
| 段の間でマテリアルとUV座標の有無が揃う | 違反 | `loader/archetype_material.rs` の判定をそのまま走らせ、型付きエラーを1件の指摘へ写す |
| 段ごとのプリミティブがインデックスを持つ | 違反 | 段の詳しさを三角形の数で比べられず、実行時形式もインデックス列を要求する |
| 三角形数が段の順に減る | 違反 | 先頭が最詳細段であることの機械の証拠である。後の段が前の段以上なら、遠景で軽くなるどころか重くなる |
| 全段の原点が接地面の中央にある | 違反 | 散布が個体を地表の点へ平行移動と天頂軸まわりの回転だけで置く。原点が外れると全個体が浮くか埋まり、向きを変えると立つ位置が動く |

原点の判定は、段ごとの境界箱について「Y成分の最小が0」「X成分の最小と最大の和が0」「Z成分の最小と最大の和が0」の3つを見る(glTFはY軸を上とする)。境界箱はアクセサが宣言する頂点位置の最小と最大から読み、バッファ実体は読まない。許容差はその段の境界箱の最大の辺の長さと `f32::EPSILON` の積である。f32は仮数部の桁数が固定であるから表せる刻みが値の大きさに比例し、この積より小さいずれは0と区別できない。

材質・テクスチャ・スキン・アニメーション・幾何の検査は、静的シーンと同じ項目をそのまま課す。原型は全段が1つのマテリアルを共有するため、先頭段から数え上げた材質スロットが原型ぜんたいの材質スロットと一致する。

### 部品の契約と検査項目

部品の契約は、**メッシュを詳細段(LOD)の列として読み、段ごとに複数の材質スロットを許し、接合点を段0のノードから読む**契約である。接合点の項目の一覧と根拠は `_doc/設計/部品カタログと接合点.md`「接合点の検査項目」が持つ。

| 検査項目 | 重大度 | 根拠 |
| --- | --- | --- |
| メッシュが1つ以上ある | 違反 | メッシュを段の列として読むため、最詳細段の1つが要る。0個は原型として焼けない |
| ノードの数がメッシュの数と一致する | 違反 | 段とノードが1対1でなければ、どのノードがどの段なのかを読み手が対応付けられない |
| 段に効くノード変換が単位行列である | 違反 | 部品の配置は接合点が決め、ノード変換は読まれない |
| 段ごとのプリミティブが1つ以上ある | 違反 | 面を持たない段は絵に何も出さない。**個数の上限は課さない**(下の理由) |
| 段の描画の並び方が三角形である | 違反 | インデックス列を三角形リストとして渡す |
| 三角形数が段の順に減る | 違反 | 先頭が最詳細段であることの機械の証拠である |
| 接合点を宣言するのは段0のノードだけである | 違反 | 読み取りが先頭メッシュのノードだけを見るため、段1以降の宣言は無言で捨てられる |

**群の原型と課すものが2つ違う。** 段ごとのプリミティブを1個に縛らないのは、部品が材質スロットの数だけプリミティブへ分かれるためである(酒場の屋根は3スロット、葉房は2スロットを持つ)。**段の間でマテリアルが揃うことも課さない。** 遠距離段が近距離段の材質の一部だけを使う形も、まとめた1つの材質へ置き換える形も、どちらも正当な簡略化だからである。材質スロットの語彙は全段のプリミティブから作られる。

**「全段の原点が接地面の中央にある」は課さない。** 部品の配置は接合点が完全に決めるため、屋根や出窓の原点が底面中央にある必然性が無いためである。

段を1つしか持たない部品はその1つが最詳細段になる。2026-08-16時点の実データ10件はすべてこの形であり、段の列への拡張の前後で違反0件・警告0件のまま変わらない。

ファイル1件では判定できない検査は `cargo xtask part-catalog <部品のglbのパス...>` が受け持つ。対の相手がカタログに存在するかは全件を読み終えて初めて答えが出るためである。この入口は種別ごとの接合点の員数と、実データに現れていない種別と、様式がまだ決まっていない種別も報告する。件数0の行が「まだ確かめていない」ことの記録になる。

### ベースカラーが白のまま焼ける材質の検査

3つの契約すべてへ課す。**マテリアルを宣言していて、ベースカラーのテクスチャを持たず、ベースカラー係数が白(1, 1, 1, 1)である材質を違反とする。**

glTFの既定のベースカラー係数は白である。テクスチャがあれば白はテクスチャへ掛かる中立の倍率として正しく働くが、テクスチャが無いと白がそのまま色になり、作者が意図した色を持たない真っ白な面が焼ける。**見るのは綴りの有無でなく焼ける結果である。** `gltf`クレートは宣言が無いときに既定の白を埋めるため綴りの有無を区別できず、区別できたとしても真っ白な面が焼ける点で欠陥は同じである。

マテリアルを1つも宣言しないプリミティブは対象から外す。群の原型が材質を持たない形で正当に成立し、色は `loader/archetype_material.rs` が後から与えるためである。ここを対象にすると植生の原型が全件落ちる。

### 検査していない契約

- **群の原型での拡張機能とカメラの宣言**。この2つは静的シーンの契約の文書の検査に入っており、原型の契約では走らない。原型でも拡張機能は解釈されず、カメラは読まれないため、宣言があれば同じように捨てられる
- **画素の中身**。デコードが通ることは見るが、色空間や画素値が意図どおりかは見ない

## 契約変更の履歴

マルチマテリアル対応が入り、1メッシュ1マテリアルの制約とプリミティブ間のマテリアル一致の検査項目は成り立たなくなった。「全プリミティブが同じマテリアルを参照する」の違反判定を廃し、「全プリミティブがマテリアルを宣言している」と「焼いた結果が入力の全プリミティブを保持する」の2項目へ置き換えた。あわせて、係数・テクスチャ・捨てられる宣言の検査を先頭の材質だけでなく全材質スロットへ広げた。受理範囲と段の計画は `_doc/設計/マルチマテリアルと材質境界.md` が管理する。

2026-08-16に群の原型の契約の枝を足した。それまで検査器は静的シーンの契約しか持たず、第6段階の散布のために作った針葉樹の原型(段2つ)を通すと「メッシュが2個ある」で必ず落ちた。原型として正しい形が静的シーンの契約に反しているだけであり、原型はこの検査器で受け入れを判定できなかった。契約を旗で選ぶ形にし、原型だけに課す9項目を足して穴を塞いだ。段の間の材質とUV座標の一致は規則の正本を2つにしないため `loader/archetype_material.rs` をそのまま呼ぶ。
