# ゲーム開発用エディター基盤

ブラウザで動くオープンワールド編集の道具(大域編集ツールとチャンク編集ツール)を、AIと人間が同じ口から操作できる形でこのリポジトリ内に立てるための設計正本である。生存型文書であり、実装とずれたら実装に合わせて直す。発端と段取りは `_doc/計画/ゲーム開発用エディター計画.md` が持つ。構成の手本は C:\devs\GameScriptingTheory(以下GST)であり、GSTの決定を引き写せる箇所は引き写し、引き写せない箇所だけをここで決める。

## 目的

この系が成立させるのは次の3つである。

1. **人がブラウザで地形・道路・地表材質・建物・散布を編集できる。** 編集の内容は2本のモックアップ(`_doc/ゲーム開発用エディター計画/`のHTML2本)が定義する
2. **AIが人と同じ意味の操作を、画面なしで実行できる。** 操作の意味が画面用とAI用で割れない
3. **編集の成果はゲームプロジェクトごとの保存先に永続化され、保存先の方式は境界1枚で差し替えられる。** このエディターはBlitzdrache0専用ではなく、今後の複数のゲームプロジェクトで使う

## 層の定義

### ブラウザ側(editor_web、TypeScript)

GSTの層の表(`GameScriptingTheory\_doc\設計\層と依存の向き.md`)をそのまま使う。矢印は「知ってよい」向きである。

| 層 | 持つもの | 知ってよい相手 |
| --- | --- | --- |
| 型契約(生成) | ts-rsがRustから生成した型。手編集禁止 | なし |
| 編集モデル | 高さ場・地表材質の重み・道路スプライン・建物配置・散布の値と純粋計算 | 型契約 |
| 操作コマンド | 直列化可能な編集操作(適用する・取り消す)。取り消しとやり直しはコマンドの列から導く | 編集モデル、型契約 |
| 境界 | サーバー通信・ブラウザ内保管の差し替え可能インターフェースと実装 | 型契約 |
| 三次元の視点操作 | 三次元を持つエディターが共有する視点の操作(判断13の割り当て)。特定のツールに属さない | 型契約 |
| 文書の表示名の編集 | 文書を編集するエディターが共有する、表示名の入力の規律(打っている間はコマンドを積まず、入力が決まったときに1つ積む)。特定のツールに属さない。参照: `_doc/設計/楽曲エディター.md`「判断13」 | なし |
| 画面 | SengenUIの部品とSengenThreeの三次元ビュー | 操作コマンド、編集モデル(読み)、境界、型契約、三次元の視点操作 |
| ツールルート | 1ツールの配線(編集モデル+コマンド+画面+境界の束ね) | 下の全部 |
| 入り口 | ツール登録簿・場所の断片ルーター・外殻 | ツールルート |
| main | コンポジションルート。実装の注入はここ1箇所 | 全部 |

強制はGSTと同じく eslint-plugin-boundaries + eslint-plugin-import(no-cycle) で行い、設定はGSTの `editor_web/eslint.config.js` を層名ごと引き写す。

### サーバー側(editor_serverクレート、Rust)

| 層 | 持つもの | 知ってよい相手 |
| --- | --- | --- |
| 型契約 | 編集資源の型と操作コマンドの型(ts-rsの生成元)。検証をメソッドで持つ | なし |
| プロジェクト保管庫(永続化境界) | trait `プロジェクト保管庫`: 資源種別ごとの読み・検証つき保存。実装はファイル保管庫 | 型契約 |
| 経路(routes) | axumのハンドラ。保管庫を通してのみ読み書きし、自分ではパスを持たない | 保管庫、型契約 |
| main | コンポジションルート。どのプロジェクトを開くかの解決と保管庫実装の注入 | 全部 |

強制はクレート内モジュール可視性と、GSTの `contract_freshness` 様式(生成し直したTS型と現ファイルの一致をテストが検査し、テストは書き換えない)で行う。

## 主要な設計判断

### 判断1: 操作コマンドはブラウザとヘッドレスの2つの入り口から、同じTS実装で適用する

`_doc/設計/ゲーム制作アーキテクチャ.md` 判断8(エディタは操作コマンド層を核にし、コマンドを人間用UIとAI用APIの両方から積む)を次の形で満たす。編集モデルと操作コマンドはDOMに依存しない純TSで書き、入り口を2つ持つ。

1. **ブラウザ**: 画面がコマンドを作って適用する。ブラシの1ストロークは1コマンド(筆致の径・強さ・通過点列を引数に持つ)であり、画素ごとにコマンドを作らない
2. **ヘッドレス**: コマンドJSONの列を受け取り、保管庫から資源を読み、同じ適用実装で適用し、検証して保存する入り口(Nodeで動く)。AIはこの口とRESTの読み書き口で人と同じ操作をする

サーバー側(Rust)にコマンド適用の実装を複製しない。適用の意味の正本はTSの1実装だけであり、Rust側が持つのは資源の型と検証である。理由: 適用実装を両言語に持つと、ブラシの数式のような細部が必ず割れ、「AIと人で同じ操作」が嘘になる。

### 判断2: 永続化は`プロジェクト保管庫`のtraitで差し替え、初期実装はプロジェクトルート配下のファイルにする

GSTの限界(通信インターフェースへデータ種別ごとのメソッドが直に生える・リポジトリが具体struct)をそのまま引き写さない。保管庫は「資源種別 × 読み/検証つき保存」を口にしたtraitとし、どのゲームプロジェクトのどのディレクトリへ保存するかは実装とmain(コンポジションルート)だけが知る。初期実装は `<プロジェクトルート>/editor_data/` 配下のファイル(RONまたはJSON+バイナリ)である。開くプロジェクトはサーバーの起動引数で選ぶ(`cargo xtask editor --project <ルート>`)。保存はGSTの規律を踏襲する(一時ファイルへ書いてから改名・検証に落ちたら正本を書き換えず`{種別, 説明}`+400番台・同時編集の競合検出は持たない)。

### 判断3: 三次元表示はSengenThree(新設submodule)で書き、Three.jsの生APIは画面層に露出しない

SengenThreeはSengenUIと同じ精神の薄い宣言層である(別リポジトリ megaDenryu/SengenThree、public、submodule)。APIは手順を組み立てるビルダーではなく**配置するものを並べる形**にする(グローバル規約「デザインパターンの既定」の第2の形。シーングラフは部品の並びが構造そのものであるため)。要点:

- `場面(...).childs([地形メッシュ(...), 道路メッシュ(...), 個体群(...)])` のように、式の入れ子がシーングラフの形を写す
- 事象(クリック・ドラッグ)はSengenUIの配線ポート様式で受ける
- **破棄を所有で管理する。** Three.jsのgeometry/material/textureはGC対象でなくdispose漏れがVRAMリークになるため、生成した資源は生成した部品が所有し、部品の破棄が配下の資源のdisposeまで責任を持つ。毎フレーム再生成せず、変更は既存バッファへの書き込み(needsUpdate)で行う
- Three.jsの型は `@types/three` を導入し、SengenThreeの公開APIには生のThree型をなるべく出さない(値オブジェクトで包む)。生型に触るのはSengenThree内部だけにする

### 判断4: 画面の外殻はVscodeShellLayoutにし、2つのエディターは1アプリの2ツールにする

app-standard-specスキルの標準に従い、外殻は `C:\devs\VscodeShellLayout` を使う。submoduleの配置は submodule-setup の標準(`submodules/SengenUI`・`submodules/VscodeShellLayout`・`submodules/SengenThree` の並び。VscodeShellLayoutの`package.json`が`file:../SengenUI`で隣を参照するため並び位置が契約)に従う。GSTの`editor_web/src/SengenUI`という独自配置は真似ない。大域編集ツールとチャンク編集ツールはツール登録簿への2項目であり、ツールの追加が登録簿の1配列追加で済むGSTの形を保つ。

### 判断5: エンジンへの引き渡しは明示の書き出しであり、エディターの正本と実行時形式を直結しない

エディターの正本(editor_data)はエディター自身の語彙(マザーハイトマップ・道路スプライン・POI・散布)で持つ。Blitzdrache0のソースアセット(チャンク世界・高さ場)への変換は「書き出す」という明示のコマンドで行い、モックアップのスライサー仕様(129×129の1px重複共有・RAW16・チャンクJSON・世界マニフェスト)はこの書き出しの中に実装する。理由: エディターは複数プロジェクトで使う道具であり、特定エンジンの実行時形式を正本にすると差し替え境界(判断2)が嘘になる。

### 判断6: 表示と正本の一致はエディター制作スキルの規律で機械検証する

エディター制作スキル第1条(表示は正本と一致・暗黙の変換禁止)を三次元へ翻訳して適用する。少なくとも次を機械で確かめる: RAW16量子化の往復(書き出して読み戻した高さが量子化誤差の内側で一致)・スプラット重みの正規化の恒等(合計が常に255に正規化されること)・ヘッドレス適用とブラウザ適用の同一コマンド列の結果一致(編集モデルが同じ実装なので、テストはヘッドレス側で書けばブラウザ側も同じ意味になる)。散布のような乱数を使う計算は種を型で持ち、同じ種で同じ結果を返すことを検査する。

### 判断7: 画面はエクスプローラーと文書タブの形にする(2026-08-19オーナー指示で追加)

編集対象を文書として開く。左サイドバーのエクスプローラーが対象を見せ、項目を開くと開いた対象ごとにエディタエリアのタブが開く(「大域世界」「チャンク (0,0)」…)。ツールとは対象の種類に応じた開き方のことであり、切替スイッチではない。初版の「アクティビティバーでツールを切り替え、1つのタブへ差し替える」形は、同じ編集対象に対するツールを切替スイッチとして見せる点が誤りだったため廃止する。

この判断は同時に、編集対象の階層(プロジェクト → 大域世界 → チャンク(x,z))をそのまま1本の木にして、すべての編集対象をその木へ並べる形も定めていた。**そのうち「対象を文書として開く」だけが今も生きており、「すべての編集対象を1本の木へ並べる」ほうは2026-08-28に廃止した。** 世界の階層に属さないもの(建物の格子・楽曲)を同じ木へ足すと、大域世界と並列に並んでしまうためである。いまエクスプローラーが見せるのは、一番左のサイドバーで選ばれている編集領域1つ分だけであり、領域の決め方と画面の構成は判断12が持つ。

描画資源の規律: WebGLコンテキストには実装上限があるため、描画ループは前面のタブだけ回す。非表示のタブは編集モデルを保持したままビューを停止し、閉じたタブはビューを破棄する(編集モデルと画面が分離しているため、ビューは捨てて再構築できる)。

アクティビティバーに連動する左サイドバーは、エディター固有の要求ではないためVscodeShellLayoutへ汎用機能として実装した(SengenThreeと同じ境界の判断: 汎用はライブラリへ、ドメインはエディターへ)。押しても左サイドバーを開かず、押されたことを伝えるだけの項目も同じ理由でライブラリ側が持つ(使い方のように、押すと中央へタブが1枚開くだけの項目のためである)。

### 判断8: 型契約層は素データ様式であり、数学DDDの幻影型は編集モデル側が担う(2026-08-19の段5で明文化)

型契約(Rustの資源型・コマンド型とts-rs生成のTS型)は、serdeとJSONの直列化境界に接するため、メートル・ラジアン等を素のf64+名前の格(`半径メートル`)で持つ**素データ様式**とする(GSTの素データの様式と同じ)。単位・値域を型で守る数学DDDは、境界の内側(編集モデル・エンジン側)の担当である。段2の申し送り「素データ様式の再検討」はこの明文化で決着とする。routesの私有関数が`&サーバー状態`を引数に受ける形は、axumのハンドラ署名の制約の内側で状態の保持者からメソッドで借りる形に留まっており、依存の持参には当たらない(構造チェック員の裁定を維持)。

### 判断9: 三次元表示は識別色で足り、絵の真実はエンジンが担う(2026-08-21オーナー指示で追加)

このエディターはマップの正本データを定義する道具であり、完全なプレビューは期待しない。本当のプレビューはエンジンで実際にゲームを動かす側に任せる。したがって: (1)地表の表示は地表の種類の違いが認識できる**識別色**で足りる (2)マテリアルについてエディターが持つのは**登録**(エンジン材質名との対応)と**識別用カラーの定義**のUIまでである (3)地表への実テクスチャの貼り付けはエディターの性能を優先して既定では行わない(性能上問題なければ付ける選択肢は残すが、要求ではない)。判断6の「表示と正本の一致」はこの前提で読む——一致させるのは値(高さ・重み・配置)であって、材質の見た目ではない。

**適用範囲(2026-08-28に限定した)**: この判断は**形ではなく分類を編集する対象**にだけ成立する。地表の材質は、形が高さ場で決まっていて材質は分類だから識別色で足りる。**建物は形そのものが編集の対象であるため、この判断を当てはめてはならない。** 建物の表示は判断13が別に定める。


### 判断10: 建物の外形と焼き上げは部品の組み立て規則を正本にし、エディターチャンクソースを境界にする

建物定義の正本はアセットコンパイラに置き、安定した建物定義ID・表示名・用途・組み立て規則・ベイ数・ローカルな入口方向を1件として持つ。建物の外接箱は手入力せず、同じ組み立て規則を実際に展開した部品の外接箱の和として求める。カタログが配る「使う部品の識別子一覧」も、規則が候補として宣言した部品ではなく実際に据わった部品から作る。高さは外接箱から引き算で導けるため、カタログは高さを別の値として持たない。初版は骨格見本2件と家屋3件の計5件を持ち、通常の配置操作には用途が家屋の3件だけを出す。

カタログの生成は、組み上げた定義1件ごとに2つの受理条件を機械で確かめてから通す。外接箱が据えた全部品の写した箱を包んでいることと、骨格見本の高さが階高2.60メートルと正本の階数の積に一致することである(横に二ベイ継いだ骨格は2.60メートル、二段に積んだ骨格は5.20メートル)。期待する高さは一間四方の骨格の宣言から手で当てた値であり、実装の写しではない。生産側の版と編集サーバーが受け入れる版の一致は`cargo xtask conform`が突き合わせ、ブラウザが持つ第3の写しは生成した型契約から取る。

入口のローカル方向と使う部品の識別子一覧は、まだ読む側が無い。カタログは編集画面とゲーム側の両方が読む台帳であり、建物の向きを問う操作と部品の差し替えの追跡がこの2つを消費する見込みであるため、契約として持ったままにする。

アセットコンパイラは建物定義から版付きの建物外形カタログを生成する。`cargo xtask building-outline-catalog`と`cargo xtask editor`は同じ生成入口を使い、`target/editor/building_outline_catalog.json`へ書く。編集サーバーは起動時にこのファイルを厳密に読み、欠落・未対応の版・不正な内容を明示の失敗にする。ブラウザは`GET /api/建物外形カタログ`から同じ値を読み、建物の選択肢と外形表示に使う。

現在の建物の配置は建物定義IDを必須で持つ。旧版の家屋は`frame_house_one_bay`へ移す。旧版の塔と宝箱は対応する建物定義が無いため、黙って別の建物へ変えず移行エラーにする。保存形式の後方互換は版ごとの型から現在の型への変換だけが担い、現在の型へ既定値を持たせない。

明示の書き出しは、各チャンクについて高さ格子と版付きのエディターチャンクソースを出力する。チャンク目録は高さ格子を直接指さず、エディターチャンクソースを指す。エディターチャンクソースの形式版1は参照する高さ格子と建物配置一覧を持つため、同名の隠れた付随ファイルへ依存しない。形式版2は地表材質の重み格子の参照を、形式版3は散布の群一覧を、形式版4はそのチャンクが使う建物の格子一覧を足した版であり、どれも欄を必須にして「無し」を欄の不在で表さない。旧版の読みは版ごとの型から現在の型への変換だけが担い、形式版1と形式版2は散布の群0件へ、形式版1から形式版3は建物の格子0件へ写す。

エディターが保存するチャンク内の水平位置はチャンク中心を原点とし、各軸の範囲を`-チャンク一辺/2`から`+チャンク一辺/2`までとする。実行時形式が使うチャンク内の水平位置は北西角を原点とし、各軸の範囲を0からチャンク一辺までとする。北西角を原点とするのは、この実装が東の増加をX、南の増加をZとしており、格子の添字(0,0)が北西の頂点に当たるためである。書き出し境界は型の異なる座標として前者から後者へ変換し、範囲外と単精度へ収まらない値を拒む。所有チャンクの内側かどうかは根の1点でなく、カタログの外接箱を配置の向きで回した4つの角すべてで見る。建物の高さは保存したY成分を使わず、変換後の水平位置で高さ格子を参照して焼く。

アセットコンパイラはエディターチャンクソースを読み、高さ格子の地形と建物の部品群を1つの実行時シーンへ焼く。建物は既存の展開器と部品ごとの配置の集約を使い、部品の種類ごとのインスタンス群へまとめる。配置ごとの種は建物定義の種と配置の安定した識別子から決め、同じ入力から同じ部品配置を得る。読み込む部品はそのチャンクに現れる建物定義が使うものだけに絞り、建物を1件も持たないチャンクでは部品を1つも開かない。

この経路が焼く地面のベースカラー係数は、検収の白い地面ではなく草地に近い暗さ(`[0.13, 0.19, 0.09, 1.0]`)を取る。白い地面のままでは、自動露出が画面のほとんどを占める地面へ合わせるため地面が白く飛び、起伏も建物の影も読み取れない絵になる。同じ値を遠景・固定物・エディターチャンクの3経路が使うため、正本は`crates/blitz_asset_compiler/src/terrain.rs`の1箇所に置く。

外部アセットの置き場(`Blitzdrache0Assets`)は複製できないため、存在しない環境が正当に成立する。置き場が無いときは建物定義0件の版付きカタログを書いて診断を印字し、編集サーバーは定義0件のまま起動する。建物パネルは配置できる定義が無い理由を画面へ出し、カタログの取得に失敗したときと、カタログにない建物定義IDが配置に残っているときも、無言で消さずに理由を出す。未解決の建物定義IDは三次元表示で赤いワイヤーフレームの箱として見せる。

### 判断11: 建物の格子は編集データの置き場が正本であり、カタログの組み直しが保存の検査である(2026-08-22 段Gで追加)

建物エディターが編集する格子1件の正本は`<プロジェクトルート>/editor_data/建物/<建物定義ID>/格子.json`に置く。建物1件ごとにディレクトリを掘り、その名前を建物定義IDにするため、置き場を数え上げるだけで台帳の見出しが揃う。ファイルの中の名乗りとディレクトリ名の食い違いは台帳の読みが拒む。

保存形式のトップレベルは「格子」と「装飾」の2区画である。装飾の区画は初版が欄を1つも持たない。検査に乗らない自由配置の飾り(決定3が言う装飾層)を後から足すときに、トップレベルの欄の並びを組み替えずに済ませるためである。

**保存の検査は、格子をベイ格子へ解いて組み立て手順へ写し、建物外形カタログを組み直すところまでを1続きで行う。** 組み直しが通ってから格子の正本を書き、そのあとカタログのファイルを差し替える。通らない格子で正本を書き換えないためであり、保存した直後にその建物をチャンクへ置けるようにするためでもある。編集サーバーは格子の置き場とカタログのファイルと組み立て係を1つの操作サービス(`建物の格子の保存係`)へ保持し、読みも書きも1つの錠で守る。

建物定義の由来は判別共用体で1段上に立てる。宣言の規則5件と、人が編集したベイ格子である。**外接箱とベイ構造と使う部品の識別子一覧は、どちらの由来でも展開結果から導く。** ベイ構造は据わった骨格の平行移動のうち相異なる値を軸ごとに数えて求めるため、この導出は升目の間隔も階高も知らない。宣言の規則の側は手で当てたベイ構造を持ち続け、導いた値との一致を受理条件が課す。

外部アセットの置き場が無い環境では、どんな格子を送っても組み立てが通らない。この失敗は送り手の破れではないため500番台で返し、格子の宣言そのものの破れ(到達不能・継いだ面へ壁・浮いた階・升目が空)だけを400番台で返す。

編集画面の側は平面図で編集する。升目の中央を触ると升目への筆が、周りの帯を触ると面への筆が効き、1回の触りが1つのコマンドとして積まれる。**升目を置いた時点で隣と真下の升目の継ぎ目を整える**(隣を継ぐ面の壁を外し、真下の升目の屋根を外す)。サーバーが拒む形を編集の途中で作れないようにするためである。三次元の識別色表示はまだ持たない(判断9のとおり、絵の確認はエンジンで実際に世界を歩いて行う)。

## この段階でやらないこと

- **同時編集・認可・外部公開。** GSTと同じく127.0.0.1固定の1人用の道具として作る。理由: 要求がなく、競合検出は保存規律を複雑にする
- **MCPサーバー化。** AIの口はRESTとヘッドレス適用で足りる。MCP化が要ると分かった時点で agent-tool-design スキルを読んで別途設計する
- **取り消し履歴の永続化。** 取り消しはブラウザのセッション内のコマンド列から導くだけにする。理由: 履歴の保存形式はコマンド型が安定してから決める方が安い
- **編集資源を実行時形式の正本にすること。** 明示の書き出しは判断10のエディターチャンクソースを作り、その直後に既存のアセットコンパイラを同期実行して実行時形式を公開する。実行時形式を直接組み立てる実装を編集サーバーへ複製しない

### 判断12: 一番左のサイドバーが切り替えるのは編集領域である(2026-08-28制定)

2026-08-28のオーナー試用で、エクスプローラーの1本の木に大域世界・チャンク・建物・楽曲・マテリアルが並列に並ぶ形が「だめ」と判定された。

判断7は「編集対象は階層(プロジェクト → 大域世界 → チャンク)であり、対象を文書として開く」を定めた。**この判断のうち「対象を文書として開く」は正しく、そのまま残す。誤っていたのは「すべての対象を1本の木へ入れる」ほうである。** 判断7を決めた時点で編集対象は世界だけであり、その後にマテリアル台帳・建物の格子・楽曲を足すとき、いずれも同じ木へ項目を1つ足して済ませた。世界の階層の中に無いものを階層の木へ並べたことになる。

判断7が廃止した初版(アクティビティバーでツールを切り替え、1つのタブへ差し替える)へ戻すのではない。**あの初版は、同じ編集対象に対するツールを切替スイッチとして見せていた点が誤りだった。** いま切り替えたいのはそれとは別で、**何の集合を探索して編集しているかという領域そのもの**である。

**編集領域とは、独立した探索と作業の文脈を持つ、編集対象の集合のことである。** 資源の種別ごとに1つずつ作るのではない。初版は3つとする。

| 編集領域 | 中身 |
| --- | --- |
| 世界 | 大域世界、チャンク、マテリアル台帳 |
| 建物 | 建物定義の一覧 |
| 楽曲 | 楽曲の一覧 |

マテリアル台帳を世界へ入れるのは、判断9のとおりそれが地表材質のためのものだからである。世界に属さない共有の編集対象(音色の一覧、会話の語彙など)が出たときに、そこで初めて第4の領域を作る。**いま「その他」の入れ物を作らない。** 何が入るか決まっていない入れ物には正しい名前が付けられず、既にGPU資源の意味で使っている「資源」のような多義の語を選ぶことになる。

画面の構成は次のとおりである。

- **一番左(アクティビティバー)**: 編集領域の切替。下部に設定と使い方を置く。この2つは編集対象ではないため木から外す
- **その右(サイドバー)**: いま選ばれている領域だけのエクスプローラー
- **中央**: 文書のタブ。**全領域で共有する**

タブを共有にするのは、領域を切り替えたときに開いている対象が隠れると状態が分からなくなること、そして建物を見ながらマテリアルを開くような横断の作業が自然に出るためである。ただし領域ごとに「最後に前面だったタブ」を覚え、領域を選び直したときそのタブへ戻す。これはタブの集合を分けずに、領域を切り替えた感じだけを出す。

外殻は**編集領域の登録**という単位を持つ。識別子・表示名・アイコン・その領域のエクスプローラーを1件とし、中央のタブの管理はこの単位から独立させる。領域ごとのコマンド(「建物を作る」等)は、いまはそれぞれのエクスプローラーの中の項目として持つ。サイドバーの見出しへボタンを並べる口が外殻のライブラリに無いためであり、必要になった時点でライブラリへ足して登録の欄にする。この情報の設計は、将来ネイティブ側の外殻を作るときにも持っていける。

### 判断13: 三次元を持つエディターは操作文法を共有し、形を編集する対象は形が見える表示にする(2026-08-28制定)

2026-08-28のオーナー試用で、建物エディターについて「三次元の識別色表示とか、ボタンを押さないと回したりできないのが意味不明」と判定された。

**視点の操作と編集の操作を分ける。**

| 層 | 割り当て |
| --- | --- |
| 視点の操作 | 右ドラッグ=回転、中ドラッグ=パン、ホイール=ズーム |
| 編集の操作 | 左クリックでの選択、左ドラッグでの配置と移動、操作つまみ |

2026-08-20のオーナー指示でチャンク編集と大域編集はこの割り当てへ揃えたが、その後(2026-08-22)に作った建物編集が揃っていない。**この割り当ては個々のツールのものではなく、三次元を持つエディター全体の既定である。** 共通の置き場へ寄せ、新しい三次元のエディターが増えても割れないようにする。

**視点を動かすためにモードのボタンを押させてはならない。** モードのボタンが切り替えてよいのは編集の操作(配置・選択・削除)だけであり、視点の操作は常に同じ手で使える。

**形そのものを編集する対象は、形が見える表示にする。** 判断9の識別色は分類を編集する対象のためのものである。建物の表示は次の3段階とし、識別色を「物体そのものの代わり」ではなく「意味を補う重ね表示」として使う。

1. 実際の部品のモデルが取れる → それを表示する
2. まだ資産が無い → 寸法と形が分かる忠実な簡易の形状を表示する
3. 識別色 → 部品の種別や選択の状態を示す補助として重ねる

### 判断14: 中央は編集対象そのものを置き、設定は右サイドバーへ置く。増えうるものだけがスクロールする(2026-08-28制定)

2026-08-28のオーナー試用で、楽曲エディターについて「パターンの変種とか曲構成とかミキサー設定とかトラック設定とかコード進行とかが全部縦に配置されてるので少し使いづらい。1個1個の部品自体は問題ない。配置の問題」と判定された。部品の出来ではなく、置き場の設計の問題である。

**中央のエディタ領域には、編集の対象そのものだけを置く。** 楽曲なら打ち込みの格子、建物なら三次元の形、チャンクなら地形である。**設定と一覧は右サイドバーへ置く。** 楽曲ならパターン・曲構成・ミキサー・トラックの設定・コード進行がこれに当たる。外殻は右サイドバーを持っており、`実行可能ツール` が `インスペクター` を返せばそこへ出る。

**中央のうち、いま何を編集しているかを示すものと、対象の全体に効く操作は固定する。** 楽曲なら曲の名前・演奏の操作・和音の帯である。これらが編集の対象と一緒にスクロールして消えると、いま何をしているかが分からなくなる。

**スクロールするのは、数が増えうるものだけである。** 楽曲ならトラックの並び、建物なら階の並びである。したがって「増えうるものの並び」は1つの部品として括り、その部品の中だけがスクロールする。

**下パネルは「これから何を使うか」の棚である(2026-08-28のオーナー指摘で追加)。** 一覧には2種類あり、置き場が違う。「いま選んでいるものの中の要素の一覧」(楽曲のパターン、建物の階)は右サイドバー、「これから使うものの棚」(建物の部品、世界の配置物とブラシと地表材質)は下パネルである。この2つを同じ区画へ置くと、選ぶ対象と使う道具が混ざる。下パネルは常設ではなく、横長の棚か時間軸を一時的に広げる必要があるときだけ開く。

区画の役割をまとめると次のとおりである。

| 区画 | 役割 |
| --- | --- |
| アクティビティバー | 何の編集領域を使うか(判断12) |
| 左サイドバー | 何を開くか |
| エディタ領域 | 何を編集するか |
| 右サイドバー | 選んだものをどう設定するか |
| 下パネル | 何を配置・利用するか / 時間の方向にどう変えるか(必要なエディターだけ) |

**外形を借りることと、用途まで借りることは別である。** VSCode風の外殻を使っても、Console・Problems・Log のようなプログラミングの用途を持ち込む理由は無い。左サイドバーについても同じで、ファイルの木を引き写した結果が判断12で直した形である。

この工事の4つのエディターのうち、**下パネルが要るのは建物・チャンク・大域の3つである**(部品の棚、配置物とブラシと地表材質の棚、ブラシと道の種類の棚)。楽曲は要らない。和音の帯は時間の方向の情報だが、打ち込みの格子と同じ時間の軸に揃っている必要があるため主編集面の一部である。

**縦の幅を、増えないものへ使わない。** 名前を表示するためだけの行を1本取るような形は、増えうるものの見える範囲をそのぶん狭める。名前は操作の帯と同じ行へ収めるか、右サイドバーへ移す。
