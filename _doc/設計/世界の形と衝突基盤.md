# 世界の形と衝突基盤

「この線分は何かに当たるか」「この形はどこまで動けるか」という問い合わせに答える基盤の設計正本である。物理エンジンの全分類(布・流体・剛体・弾性体・紐・破壊・爆発。目録は[Issue #5](https://github.com/megaDenryu/Blitzdrache0/issues/5))が共有する、形状表現・空間探索・衝突検出の土台を定める。裁定の経緯は[Issue #1](https://github.com/megaDenryu/Blitzdrache0/issues/1)にある(2026-08-23〜26のオーナー裁定と設計ノート)。

用語は `_doc/計画/ユビキタス言語.md`「世界の形と衝突の語彙」に従う。

## 目的

キャラクター操作(接地・めり込み防止)とカメラ(遮蔽物の手前で止める)が最初の利用者であり、剛体の動力学(#7)・布や紐の外部衝突・破壊片の飛散もすべてこの基盤の上に載る。基盤が答えるのは幾何学的事実までであり、「止まる・滑る・登る・壊れる」というゲーム上の意味は返さない。

## 層の定義

| 層 | 置き場所 | 持つもの | 知ってよいこと |
|---|---|---|---|
| 衝突数学層 | `blitz_collision`(新クレート) | 形状の表現・幾何問い合わせ・詳細衝突計算・形状内の空間探索の数学 | blitz_math と thiserror(型付きエラーの導出)。世界・チャンク・アセット・GPUを知らない |
| 世界側 | `blitz_engine` | 世界の形への問い合わせ口。高さ場・チャンクの読込状態と衝突数学の接続、問い合わせの完全性 | blitz_math・blitz_collision・自クレートのアセットとストリーミング |
| ゲーム側 | `blitz_game`(意味付け)と `blitz_app`(配線) | 地面・壁・登れる面・カメラを遮る物という意味付け。エンジンの結果をゲームの語彙へ写すのは blitz_app のゲーム配線(既存の高さ場の写しと同じ形) | ゲーム側は衝突数学層と世界側の結果型 |

依存の向きは `blitz_math ← blitz_collision ← { blitz_engine, blitz_sim, blitz_asset_compiler }` である。機械強制はクレート境界(依存を書かなければコンパイルできない)と `cargo xtask conform` のクレート依存の白リストで行う。

## 主要な設計判断

### 判断1: 物理は全部自前で作り、外部の衝突・物理ライブラリは採用しない

2026-08-23のオーナー裁定で確定した。物理シミュレーションはゲームの核となる仕組みそのものになるため、コードを完全に制御できなければならない。rapier3d・parry3dの採用審査はこの裁定で恒久に閉じた。開発時のテストの答え合わせにも外部実装を依存として持ち込まない(値の照合は教科書の解析解と手計算の期待値で行う)。

### 判断2: 共通のインターフェースを先に切らず、数学の部品を提供する

ゲームごとに必要な物理は異なり、そのAPIも異なる。エンジン側が提供するのは数学の部品(形状・判定・解法・拘束・介入)であり、ゲームごとの物理APIはゲームの側が部品を組んで定義する。先に固定するのは部品の層とゲームの層の依存の向きだけである。これは `_doc/設計/シミュレーション層.md` が布・流体について定めた「表現はゲームごと、数学は基盤」の一般化である。

### 判断3: 問い合わせの結果を数学層・世界側・ゲーム側の3層に分ける

- 数学層が返すもの: 当たった/当たらない・距離・最近接点・接触位置・接触面法線・貫通量・初回接触時刻
- 世界側が返すもの: その物理形状が存在するか・読込済みか未読込か・どの世界要素に属するか
- ゲーム側が与えるもの: 地面・壁・登れる面・壊せる物・カメラを遮る物という意味付け

「未読込の区域に触れたので分からない」は純粋な衝突数学の戻り値ではなく、世界のストリーミングを含む問い合わせ側の結果である(判断8)。

### 判断4: 衝突数学は新クレート blitz_collision に置く

候補は3つあった。(a)新クレート、(b)blitz_sim の内部モジュール、(c)blitz_math の内部モジュールである。(b)は blitz_engine が解法やGPUレイアウトを含む blitz_sim 全体へ依存することになり、「何を描くか」の層へシミュレーション解法の依存が混ざる。(c)は座標系・単位という blitz_math の責務へ、形状目録から空間探索までの大きな体系を積むことになる。(a)はクレート境界が「衝突数学は世界を知らない」を機械強制でき、blitz_engine・blitz_sim・blitz_asset_compiler のどれからも同じ数学を使えるため、(a)を採る。既存の blitz_sim の布の衝突計算(カプセル)は当面そのままとし、剛体(#7)の着工時に blitz_collision の形状型へ揃える移行対象として記録する。

### 判断5: 形状の目録を先に確定する(物理形状と描画形状は別物)

最終的に扱う形状は次のとおりである。点・線・半直線・線分 / 平面・球・カプセル・円柱 / 軸平行箱・任意姿勢の箱 / 三角形・凸多面体 / 複合形状 / 三角形網 / 高さ場 / 線状・面状・体積状の変形形状。実装は段階化する(実装順の節)が、目録は設計として今確定する。物理形状と描画形状は同一視しない。

### 判断6: 幾何問い合わせの能力一覧

内外判定・表面までの距離・最近接点と二形状間の最近接点対・重なり判定・貫通方向と貫通量・線分や形状を動かした場合の初回接触時刻・接触位置と接触面法線・複数接触点の生成・継続接触を追跡するための接触特徴の識別。単純形状同士は解析式を優先し、一般の凸形状は支持点(指定した方向に最も遠い表面の点)を使った最近接・重なり・貫通・接触点生成まで自前で持つ。三角形網は候補三角形の探索と形状対三角形の判定を分ける。

### 判断7: 高さ場の物理は最詳細段の三角形化と一致させる

見えている地形と物理地形がずれてはならないため、高さ場の地表位置・法線は、描画に使う地表の三角形化と一致する定義にする。三角形化の正本はアセットコンパイラの `crates/blitz_asset_compiler/src/terrain/surface.rs` が固定した規約(四角形の対角は常に(X,Z)から(X+1,Z+1)へ張る)である。

一致するのは最詳細段の三角形化とであり、描画は視点からの距離に応じて標本を間引いた粗い詳細段の三角形を使うため、段が粗くなる距離では見える面と物理の面に高さの差が出る。衝突が要る近傍を常に最詳細段で描く保証を置くかどうか(置くならその距離をどう決めるか)は、キャラクター操作(#3)の設計で扱う。

実行中の高さ問い合わせは当初は双一次補間であり、描画の三角形の面とずれていた。2026-08-28の実装順1で、この区分線形の計算を blitz_collision が一意に所有し、実行中(`crates/blitz_engine/src/height_field/cell_position.rs` が求めた升目の位置を衝突数学へ渡す経路)と焼き込み時(`crates/blitz_asset_compiler/src/terrain/ground_height.rs`)の両方が同じ式を呼ぶ形へ是正した。高さ場の問い合わせは、高さに加えて地表位置・地表法線・接線方向・該当格子・該当三角形を取得できるようにし、線分対高さ場・球対高さ場・カプセル対高さ場・凸形状対高さ場へ拡張する。

#### 升目をまたぐ地表の連続性には高さの絶対値の上限が要る

隣り合う2つの升目は共有辺の上で同じ高さを返さなければならない。返さなければ、辺のちょうど上を通る線分が両側の升目で地表より上と判定され、地表を突き抜ける。区分線形の式は共有辺の上で数学的には同じ値を与えるが、浮動小数点では一致しない。一致しない量に上界を与えるのが、四隅の高さの絶対値へ課した上限(`crates/blitz_collision/src/height_field/cell_corner_heights.rs` の `地表の高さの絶対値の上限メートル`、2の24乗メートル)である。2026-08-28のレビューで、上限が無ければ「共有辺の差は数ULP以内」という主張が一般には成り立たないことが指摘され、上限を課して主張を成り立たせる形にした。

**記号と前提。** 高さはすべて倍精度のメートルであり、丸めは最近接偶数丸めとする。倍精度の演算1回について fl(x∘y) = (x∘y)(1+δ)、|δ| ≤ u = 2^-53 が成り立つものとし(浮動小数点演算の標準模型)、fl(x) で丸めた結果を表す。桁あふれは起きないものとする。非正規化数への落ち込みは別項で扱う。関わる隅の高さの絶対値の最大を M と書く。共有辺を挟む2つの升目を西と東とし(東の縁を共有する場合。南の縁でも隅の名前が入れ替わるだけで形は同じである)、西の升目の隅を手前左 a・手前右 b・奥左 c0・奥右 c、東の升目の隅を手前左 b・手前右 e・奥左 c・奥右 f と書く。辺に沿った比を s ∈ [0, 1] とする。

**前提1: 辺を横切る軸の比が厳密に 0 と 1 であること。** 走査は、升目の境界を横断した軸の比を1次式の評価で求め直さず、正準値(升目へ入る側で 0、出る側で 1。添字が減る向きへ進む軸では逆)として持つ(`crates/blitz_collision/src/height_field/cell_interval_end.rs`)。高さだけの問い合わせ(`crates/blitz_engine/src/height_field/cell_position.rs`)では比を「実数添字から升目の添字を引いた値」として求めており、辺の上では実数添字が整数に一致するため、この減算が厳密に 0 または 1 を返す。この前提が要る理由は、区間の内側の比の誤差を扱う下の項に書く。

**前提2: 辺に沿った軸の比が両側で同じ倍精度の値であること。** 走査では、西の升目を出る時刻と東の升目に入る時刻が同じ倍精度の値であり、南の軸の1次式(始値・変化量・升目の添字)も両側で同じであるから、評価はまったく同じ演算列になりビット単位で一致する。高さだけの問い合わせでも、東の縁を共有する2つの升目は南の添字が同じであるから一致する。両側の比が δ だけ食い違う場合は、下の上界へ 2M·δ を足す。

**補題(隅の再構成の誤差)。** |x| ≤ M かつ |y| ≤ M のとき |fl(x + fl(y - x)) - y| ≤ 3Mu + 2Mu² である。fl(y - x) = (y - x)(1 + δ1) であるから x + fl(y - x) = y + (y - x)δ1 であり、これを丸めた値は y + (y - x)δ1 + (y + (y - x)δ1)δ2 である。|y - x| ≤ 2M より第2項は 2Mu 以下、第3項は (M + 2Mu)u 以下である。

**辺の内部(0 ≤ s < 1)。** 西の升目は東の比 1 で手前側の三角形を、東の升目は東の比 0 で奥側の三角形を選ぶ。評価する式はそれぞれ fl(fl(a + fl(fl(b - a)·1)) + fl(fl(c - b)·s)) と fl(fl(b + fl(fl(c - b)·s)) + fl(fl(f - c)·0)) である。1 を掛ける乗算、0 を掛ける乗算、0 を足す加算はどれも厳密であるから、前者は fl(A' + P)、後者は fl(b + P) になる。ここで A' = fl(a + fl(b - a))、P = fl(fl(c - b)·s) である。P は両側でまったく同じ演算列であるからビット単位で一致し、|P| ≤ 2M(1 + u)² が成り立つ。補題より |A' - b| ≤ 3Mu + 2Mu² である。よって差は (A' - b) + (A' + P)δ3 - (b + P)δ4 であり、|A' + P| ≤ 3M + 7Mu + 4Mu²、|b + P| ≤ 3M + 4Mu + 2Mu² を当てると **差は 9Mu + 13Mu² + 6Mu³ 以下** である。

**辺の端(s = 1。4つの升目が集まる格子点)。** 西の升目は東の比 1・南の比 1 で奥側の三角形を選び、fl(fl(a + fl(c0 - a)) + fl(c - c0)) を評価する。補題と同じ数え方でこの値は c から 8Mu + 8Mu² 以内であり、東の升目が評価する fl(b + fl(c - b)) は c から 3Mu + 2Mu² 以内であるから、**差は 11Mu + 10Mu² 以下** である。

**上界。** u ≤ 2^-53 では u の2次以上の項の合計は Mu の 10^-14 倍にも満たないため、それを整数の係数へ吸収して **共有辺の上のどの点でも、隣り合う2つの升目が返す高さの差は 12·M·u 以下** と書ける。これは2次の項を落とした近似ではなく上界である。実測はこれよりはるかに小さい。導出のときに隅の高さと比を無作為に選んで300万通りを調べたが、差は 2·M·u を越えなかった。上界を破らないことの反証は `crates/blitz_collision/src/height_field/shared_edge_tests.rs` が持ち、その探索で差が大きく出た組を検査する組へ入れてある。

**数値。** M の上限を 2^24 メートルとすると、差は 12·2^24·2^-53 ≒ 2.2×10^-8 メートル(0.03マイクロメートル未満)である。地形として現実に取る高さ(M ≒ 10^4 メートル)では 1.33×10^-11 メートルである。上限が無ければこの積は抑えられない。指摘された反例(手前左 = -3×10^38、手前右 = 1。どちらも単精度が表せる値である)では M ≒ 3×10^38 であり、上界は 4×10^23 メートルとなって何も保証しない。実際にこの2値を倍精度で計算すると、fl(手前右 - 手前左) は 3×10^38 へ丸められて 手前左 の符号を反転した値にちょうど一致し、手前左 にそれを足した値は 0 になる。共有辺の上で片側が 0、隣が 1 を返すため、差はちょうど1メートルである。

**非正規化数。** 上の標準模型は演算の結果が正規化数に収まることを前提にする。落ち込む場合は乗算1回につき絶対誤差 2^-1075 メートル以下が加わり(加減算は非正規化数の範囲でも厳密である)、片側2回で両側4回であるから、厳密には上界を 12·M·u + 4·2^-1075 メートル と書く。第2項は 10^-323 メートル未満であり、地形の高さとして意味を持つ範囲では存在しないに等しい。高さの型は絶対値の下限を課していないため、下限を型で保証する代わりにこの項を上界へ含める。

**指数差による細分。** a と b が単精度の標本を倍精度へ広げた値である場合(実行中の問い合わせがこれである)、2つの2進指数の差 e が 29 以下なら fl(b - a) は誤差なく求まる。単精度の値はどちらも 2^(min(e_a, e_b) - 23) の整数倍であり、差の絶対値は 2^(max(e_a, e_b) + 1) 未満であるから、差を表すのに要る仮数は高々 e + 24 ビットであって倍精度の53ビットに収まるためである。この場合は減算の丸めが消えて上界が下がる。減算の丸めが入るのは、隣り合う格子点の高さの2進指数が30以上離れる場合だけである。

**取り逃しの幅。** 差が0でない以上、地表とちょうど接する線分の当たりを取り逃すことは原理的にありうる。共有辺の上で取り逃しうるのは、線分と地表の隔たりがこの上界(上限の高さで0.03マイクロメートル、現実の高さで1.33×10^-11 メートル)に収まる場合だけである。「取り逃さない」ではなく「取り逃す幅がこの上界に収まる」が正しい主張である。升目の中の対角の上では取り逃しうる幅が別の量になる。次の項に書く。

**入口の一致。** 上限は値オブジェクト `升目の四隅の高さ::生成する` が課す。実行中の高さ場(`crates/blitz_engine/src/height_field/field.rs` の `高さ場::生成する`)は同じ定数を読んで標本の段階でも課し、焼き込み(`crates/blitz_asset_compiler/src/terrain/ground_height.rs`)は同じ値オブジェクトを通るため、入口が3つに割れない。

**区間の内側の比は、始点からの距離に比例して誤差が育つ。** 上の2つの前提が要る理由がここにある。走査が升目の中の比を正準値で渡すのは、升目に居る区間の両端(境界を横断した軸)だけである。区間の内側の時刻(対角を越える時刻、当たりの時刻)の比は1次式「(始点の実数添字 - 升目の添字) + 実数添字の速度 × 媒介変数」で求める。線分の始点から数えて k 個目の升目では、この2つの項はどちらも大きさが k+2 まで育つのに対し、和は0以上1以下である。標準模型で各段を数えると、2つの項の丸めがそれぞれ (k+2)u 以下、最後の加算の丸めが u 以下であるから、**比の絶対誤差は (2k+5)·u 以下** である。走査は供給元が答えられる升目しか辿らないため k は格子の広がり(格子点数の上限65535)に収まり、比の誤差は 1.5×10^-11 以下である。境界の比を1次式で求め直すとこの誤差がそのまま縁の 0 と 1 のずれになるため、前提1が成り立たなくなる。2026-08-28のレビューが挙げた反例(東の実数添字が 19704.200921507865 から 19615.889565334084 へ進み、添字19649の境界を越える線分)では、境界の比が 0 でなく 1 の32ULPにあたる 7.1×10^-15 と評価された。

**求解も端の正準値を捨てない。** 走査が正準値を持つだけでは足りない。升目の中の交差の求解(`crates/blitz_collision/src/height_field/cell_segment_intersection.rs`)は、対角を越える時刻で区間を2つに割り、区間ごとに1次方程式を解く。対角が升目の辺・角と重なると越える時刻は区間の端と一致し、そこで内側の時刻の端を新しく作ると境界の軸の 0 と 1 が失われる。当たりが区間の終わりの端に一致する場合(高さの差が終わりでちょうど 0 になる場合と、区間の幅が 0 の場合)も同じであり、面を1次式の比で求め直すと上の誤差が答えの高さと法線へ戻り、媒介変数も「始まりの時刻 + 区間の幅 × 1」の丸めで端からずれる。したがって求解は、時刻が区間の端と一致するなら元の端をそのまま使い、既に求めた端の面と端の時刻を答えに使う。内側の解のときだけ1次式で面を求める。反証は `crates/blitz_collision/src/height_field/canonical_end_tests.rs` が持ち、上の反例の線分で面の高さ・2方向の傾き・媒介変数まで見る。

**升目の中の対角の上の跳び。** 対角の上では奥側と手前側の2つの式が同じ比の組に対して (手前左 - 手前右 - 奥左 + 奥右)(東の比 - 南の比) だけ違い、係数の絶対値は 4M 以下である。数学的な対角ではこの差が0になるが、求解は東の比と南の比の差を1次で内挿して対角を越える時刻を求めるため、その時刻で計算した2つの比の差は0にならず、上の比の誤差の数倍だけ残る。したがって対角の上の高さの跳びは 4M × (2k+5)u の数倍の程度である。高さの上限(M = 2^24 メートル)と格子の端(k = 65534)を同時に取る最悪の組では2ミリメートル、地形として現実に取る高さ(M ≒ 10^4 メートル)では1マイクロメートル程度になる。これは升目をまたぐ連続性(上の上界)とは別の量であり、1つの升目の中の1本の対角の上でだけ現れる。線分の求解は1つの区間を1つの三角形で解くため、この跳びにさらされるのは区間の境目だけである。比の誤差を消すには升目ごとに比を積み上げる形へ変える必要があり、それは別の誤差(升目ごとの積み上げの累積)を持ち込むため、当面は誤差の性質を明示して受け入れる。

#### 掃引の係数が桁あふれしないための長さの上限

高さの絶対値の上限とは別に、問い合わせの入力である長さそのものにも上限が要る。カプセルの掃引は特徴ごとに2次方程式を組み、その係数は位置と変位と半径の4乗、判別式は8乗の大きさになるため、上限が無ければ係数か判別式が有限でなくなる。求解は有限でない判別式を根なしとして扱うため、明白に面を横切る掃引が「覆いをすべて調べて触れなかった」として返る。2026-08-28のレビューが挙げた反例は、軸の中心の高さが10の155乗メートル・半径1メートル・天頂の変位がマイナス10の155乗メートルの掃引である。

上限は `crates/blitz_collision/src/height_field/length_limit.rs` が持ち、値は高さの上限と同じ2の24乗メートルである。同じ値を選んだのは、格子点の位置の天頂の成分がその隅の高さそのものであり、2つの上限が食い違うと上限ちょうどの高さを持つ格子点が自分の位置を作れなくなるためである。上限を課すのは問い合わせの入力(格子原点からの位置の成分・高さ場の中の変位の成分・カプセルの半径)と、掃引が調べる升目の格子点の位置であり、求解が導いた点には課さない。三角形の平面へ落とした足は平面が立っているほど遠くへ出るため、そこへ上限を課すと、その候補が三角形の外だと分かる手前で問い合わせ全体が止まるからである。係数と判別式が倍精度の範囲を出ないことの算術は同じファイルにある。

高さ場を貫く線分の側に、答えを偽る同じ形の穴は無い。線分の求解は差と1つの割り算だけで書かれ、大きな2つの量の積を作らないためである。桁あふれしうるのは両端の天頂の差だけであり、そこから出る有限でない値は媒介変数と升目の中の比の検査が型付きエラーで止める。線分の端点も同じ位置の型を通るため、この上限がその入力を入口で拒む。

### 判断8: 問い合わせの値と完全性を別軸にする

単純な「当たった/当たらない/不明」の3値では、手前の確定ヒットと奥の未読込領域を同時に表せない。世界側の問い合わせ結果は値と完全性の2軸で返す。

```rust
struct 世界問い合わせ結果<値> {
    値: 値,
    完全性: 問い合わせ完全性, // 「対象範囲を完全に評価できた」「未読込領域を含む」を最低限表現する
}
```

地形の高さ場は世界に1枚だけで常にメモリへ載っており、チャンクの読込状態に関係なく答えられる。建物や散布物の形はチャンクが読み込まれている間しか答えられない。この非対称が完全性の軸の存在理由である。

**最初の当たりを求める問い合わせでの完全性の意味。** 完全性は「返した答えが確定的か」を表す。最初の当たりを求める問い合わせでは、評価できない領域に達した時点で走査を止めるため、当たりを見つけた答えはその当たりより手前をすべて評価し終えていることが構造上保証される。したがって**打ち切りは当たり無しの側にしか現れず、「確定した当たり」と「その手前の未評価」が同時に立つ状態は作れない**。評価できない領域が当たりの手前に在るなら、その時点で走査が止まっていて当たりに達しないからである。完全性が「評価できない領域を含む」と答えたときの読み方は「この範囲に当たりは無い」ではなく「打ち切りより先は分からない」である。

この節の冒頭が言う「手前の確定ヒットと奥の未読込領域を同時に表す」は、範囲そのものを列挙する問い合わせ(区域内の物体をすべて挙げる、線分が通る全部の当たりを挙げる等)で立つ状態である。そこでは当たりで走査が止まらないため、確定した値と奥の未評価が同時に立つ。2軸に分けた形はどちらの問い合わせでもそのまま使えるため、最初の当たりの問い合わせだけを見て軸を1つへ潰してはならない。

### 判断9: 複合形状は子形状を束ねて1つの衝突対象にする

複合形状とは、複数の単純形状(子形状)を1つの衝突対象として所有・配置する形状である(椅子=座面と脚4本と背もたれの箱)。子形状同士の重なりや微小な隙間を許容し、同一複合形状の子同士は通常の外部衝突判定の対象にしない。「束ねる」(子形状はそれぞれ残る)と「融合する」(幾何学的な和集合を計算して内部面を消した新しい一形状を生成する)は別能力とし、融合を複合形状の必須動作にはしない。問い合わせ結果は親の衝突対象識別子と子形状識別子の両方を返せる構造にする。

### 判断10: 衝突形状が宣言できる属性

一個の実行時衝突形状は、幾何形状そのものとは別に次を宣言・参照できる。

- **表裏性**: メッシュ・面状形状で、表側だけ衝突するか両側から衝突するか。閉じた立体では原則不要
- **衝突分類**: 問い合わせ側が見る形状群を型付きの分類と集合指定で絞る。ゲーム固有の語彙は物理側に持たせず、分類への意味付けはゲーム側が行う
- **センサー性**: 力学的接触を生成するか、重なり・侵入・退出の観測だけ行うか(水域・イベント領域・攻撃判定)
- **物性への参照**: 摩擦・反発は子形状単位で異なりうる。質量・重心・慣性・速度は剛体側(#7)の責務でありここへ混ぜない
- **親から見た局所姿勢**: 位置・回転は必須。拡縮は形状生成時に焼き込むことを基本とし、実行時の非一様拡縮を当然の機能にしない
- **可変性の分類**: 静止 / 剛体移動(親の位置・回転だけ変わる) / 頂点変形 / 構造変化(布の裂け・紐の切断・破壊)を区別できること。更新方式は各下位Issueで決める
- **用途の分類**: 一つの親物体が動力学用・通常問い合わせ用・詳細問い合わせ用・カメラ用という複数の物理表現を持てる。用途を形状の種類と混ぜず、問い合わせ側が見る形状集合を選ぶ
- **制作時のデータとゲームの意味情報へ繋がる識別**: 物理層はゲームの意味を知らず、子形状・面・領域を外部データから参照できる安定した識別手段だけを提供する

凹形状には単一の万能実行時型を要求しない。複合形状(凸の束)・衝突用メッシュ・制作時の凸分解のどれかで表現できることを要求する。接触余白(数値安定性やキャラクター移動のための小さな余白)は形状の幾何へ焼き込まず、衝突問い合わせ・接触生成の数値方針として明示的に扱う。

### 判断11: 静的衝突メッシュは階層を持ち、事前生成を基本とする

静的で複雑な世界形状(崖・洞窟・建物・大型岩)には簡略化した衝突用メッシュを使う。三角形一覧の平坦な総当たりにはせず、全体の粗い境界 → 中間領域の境界群 → 少数の三角形群の葉、という階層を持つ。不変条件: (1)各節点は配下の全三角形を包含する境界を持つ (2)葉は直接詳細判定できる小さな三角形集合へ到達できる (3)静的メッシュ向け階層は実行中の頻繁な再構築を要求しない (4)形状の局所座標と世界座標を混同せず、問い合わせ時に配置変換を適用する (5)階層構造をゲームの意味へ露出しない。階層は #19 の物理アセット変換で事前生成して実行時形式へ焼き込むことを基本とし、チャンク読込のたびの高価な構築を必須にしない。「静的用の不変構造」と将来の地形変形(#17)向けの「更新可能な構造」を同じ型へ無理に統一しない。具体的な階層アルゴリズムはここで固定せず、実装時に静的データへの強さ・メモリ局所性・直列化可能性・デバッグ可視化を満たす方式を選定する。実装時には「何に適し何に適さないか」(適する: 静的で複雑な形状。適さない: 通常の動的剛体・毎刻み大きく変形する形状)を実装箇所の近くの文書コメントへ必ず残す。

### 判断12: 空間探索は粗い候補選別と詳細判定を責務として分け、世界は二段構えで辿る

世界全体を1つの巨大メッシュ階層へ固定しない。上位ではチャンク等の読み込み単位を選別し、読み込み済み単位の内部で静的メッシュ階層を辿る。初版では既存のチャンク → 群 → 個体の絞り込みを流用できるが、描画の可視性と物理の近傍探索は別物であるため、将来は物理専用の索引を持てる構造にする。動く物体には動的な境界箱の木、粒子系には空間ハッシュ(空間を升目に切って近所だけ調べる索引)という別方式を見据える。

### 判断13: 連続衝突と接触点集合を能力として最初から見据える

高速の飛翔体・回転体が一刻みの間に薄い物体を通り抜けないため、初回接触時刻を返す連続衝突を能力の目録に置く。剛体の積み重なりの安定と摩擦計算のため、1接触点だけでなく箱が床へ面で乗る状態を複数の接触点で近似できることも目録に置く。どちらも実装は後段(実装順9・10)だが、結果型の設計はこれらを収容できる形にする。

### 判断14: 決定性の維持

ゲームの更新は1フレーム1/60秒の固定の刻みで進み、同じフレーム数を実行すると必ず同じ結果になる決まりが既にある(`crates/blitz_app/src/game/step_seconds.rs`)。衝突の実装はこの決まりを壊してはならない。同じ入力で同じ結果になることを自分のコードだけで保証する(判断1の帰結でもある)。
