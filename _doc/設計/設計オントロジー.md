# 設計オントロジー

この文書は、共通設計語彙クレート `crates/blitz_design` が持つ設計マーカーと関数の役割、およびUpdate型のEventの語彙とコード文法を定める設計正本である。Issue #137 のオーナーのコメント(2026-09-18)を骨格にする。マーカーの定義文は `_doc/計画/ユビキタス言語.md`「設計マーカー」「M状態はMDTOである」「Mイベント」と同じ内容であり、本書はそれと矛盾しない。

## 1. 位置づけ

`blitz_design` は、Rust上の型が設計上何として解釈されるか(純粋な所有データ・状態・コマンド・イベント・規則・入力・設定・工程)を宣言する設計マーカーと、射影・解釈という関数の役割を表す境界付きの newtype だけを持つ。このクレートはドメインの語彙を1つも持たない。

置き場の判定の基準は「その型が何について語るか」である。

- プログラムについて語る(型が設計上どの役割かを言う)ものは `blitz_design` に置く。
- シミュレーションについて語る(時間尺度・物理小刻み等)ものは `blitz_sim` に置く。
- Esca世界について語る(旅行者・移動可能範囲等)ものは `blitz_esca` に置く。

`blitz_design` は何にも依存しない最下層であり、`blitz_sim` と `blitz_esca` がこれを使う。実装は `crates/blitz_design/src/marker.rs`(マーカー)と `crates/blitz_design/src/function_role.rs`(関数の役割)にある。

## 2. 設計マーカーの一覧と共通契約

設計マーカーとは、Rust上の型が設計上何として解釈されるかを、メソッドを持たないトレイトの実装で宣言する印のことである。

| マーカー | 設計上の役割 | `MDTO` との関係(Relation) | `MDTO` から継承する法則 | 役割ごとに追加で課す法則 |
|---|---|---|---|---|
| `MDTO` | 参照や内部可変性を所有せず、値として複製・受け渡しできる純粋な所有データ。境界を越える転送にも状態の正本にも使う | (基底) | 参照・生ポインタ・内部可変性を持たない(`cargo xtask conform` が検査する)。`Clone` を持つ(上位トレイト) | 無し |
| `M状態` | 実在し、保持され、遷移されるゲームまたはシミュレーションの状態 | is-a(`M状態: MDTO`) | 同上 | `struct` に限定せず `enum` も状態として扱う。`&mut self` は禁じない(状態は遷移されるものであり、遷移の工程が別に在る) |
| `Mコマンド` | 主体が選択・発行する命令、意図 | is-a(`Mコマンド: MDTO`) | 同上 | 必ず `enum` で定義する。固有の `impl` に `&mut self` を持たない |
| `Mイベント` | ある状態遷移によって成立した過去の事実 | is-a(`Mイベント: MDTO`) | 同上 | 固有の `impl` に `&mut self` を持たない。`enum` を必須としない |
| `M規則` | 計算や遷移を律する不変の法則、方針 | is-a(`M規則: MDTO`) | 同上 | 必ず `struct` で定義する。固有の `impl` に `&mut self` を持たない |
| `M入力` | 外界(入力デバイス等)から届く、意味付けの前の生の信号 | is-a(`M入力: MDTO`) | 同上 | ゲームの意味論を持たない |
| `M設定` | 起動時に決まって実行の間は変わらない設定 | is-a(`M設定: MDTO`) | 同上 | 固有の `impl` に `&mut self` を持たない |
| `M工程` | 状態を読み書きして進める工程 | 無し(工程はデータでない) | 無し | 現時点で共通契約を課さない |

データの役割(`M状態`・`Mコマンド`・`Mイベント`・`M規則`・`M入力`・`M設定`)はすべて `MDTO` を上位トレイトに持つ。したがって純粋データ規約(参照・生ポインタ・内部可変性を持たない)の検査は `MDTO` を実装する型に対して1回行えば、上位トレイトにより役割の型を全部含む。`cargo xtask conform` は加えて、役割のマーカーを実装する型が同じファイルに `impl MDTO for` も書いていることを検査する(コンパイラも上位トレイトで落とすが、検査器が `MDTO` の実装の一覧から役割の型を見落とさないための検査である)。

`M状態: MDTO` は Blitzdrache 全体の共通契約である(2026-09-18 オーナー裁定)。既存コードが適合しない場合は、共通契約を弱めず既存コードの側を直す。`Mコマンド`・`Mイベント`・`M規則`・`M設定` を `MDTO` の上に積んだのは、PR #138 の第4回レビュー(2026-09-19)の必須3・高優先度6への対応である。`Mコマンド` だけが純粋データ契約から外れていると、`&コマンド` から外部状態を書き換えられ、`M遷移関数` が純粋計算であるという理論を型契約が支えられないためである。

`MDTO` の役割を「境界を越えて運ばれるデータ」から「純粋な所有データ」へ広げたのは、PR #138 の第3回レビュー(2026-09-19)の必須1に対して、`M状態: MDTO` の共通契約を保つ側(案A)を採ったためである。`blitz_sim` のソルバ内部の作業状態も `M状態` であり、それは境界を越えないが純粋な所有データではあるので、この定義なら矛盾しない。`MDTO` という名前をこの役割に対して保つかどうかの再検討は、オーナーの裁定待ちである。

## 3. 関数の役割

`blitz_design` は、関数の設計上の役割を表す境界付きの newtype を2つ持つ。

- `M射影関数<状態: M状態, 射影DTO: MDTO>` は `fn(&状態) -> 射影DTO` を包み、状態から外部向けの表示データを取り出す一方向の観測の計算である。
- `M解釈関数<入力: M入力, コマンド: Mコマンド>` は `fn(&入力) -> コマンド` を包み、生の入力から主体のコマンドを導く純粋な解釈の計算である。

型エイリアスに書いた境界は Rust の仕様上強制されない(rust-lang/rust#112792)。そのため関数の役割は型エイリアスでなく、関数ポインタを包む構造体(newtype)であり、型引数の境界を構造体の宣言に書く。構造体の境界は利用箇所でコンパイラが強制するため、型を使った時点で型引数の境界が掛かる。迂回できる綴りは無い(`blitz_design::M射影関数<...>` と修飾しても、`use ... as` で別名を付けても、`let` で受けても、型を使った時点で境界が掛かる)。各 newtype は `生成する(関数)` で関数を包み、`呼び出す(&引数)` で包んだ関数を適用する。利用側は `const _: M射影関数<A, B> = M射影関数::生成する(関数);` の静的宣言で、関数が役割を満たすことをコンパイラに確かめさせる。

`M遷移関数<状態: M状態, コマンド: Mコマンド, 規則: M規則, イベント: Mイベント>` と `遷移結果<状態, イベント>` は `crates/blitz_esca/src/ontology.rs` に残る。`M遷移関数` も同じ形の境界付きの newtype である。`遷移結果` は型引数に `M状態`・`Mイベント` の境界を持つ意味型であり、汎用の入れ物ではない。構造体に書いた境界は利用箇所でコンパイラが強制するため、`遷移結果<String, usize>` のような値は作れない。これらを `blitz_design` へ上げないのは、オーナーの裁定「計算モデルまで固定しているため、まず Esca 側で直してから昇格を判断する」による。遷移文脈(3.5.1)がまだ確定していないことも、`M遷移関数` を `blitz_design` へ上げない理由である。

## 3.5 状態遷移の理論(因果モデル)

本節は、Issue #137のPR #138へオーナーが2026-09-19に書いたコメントが示した状態遷移の理論を正本として記録する。この理論は、第2節の設計マーカーと第3節の関数の役割が、個別に便利なトレイトの集まりではなく、ゲーム世界の因果関係を記述するための一組の設計語彙であることの根拠である。

### 3.5.1 基本形

状態遷移の基本形は次の図で表す。

```text
                  規則
                   │
                   ▼
現在の状態 ──┐
             ├─ 状態遷移 ──→ 次の状態
コマンド ────┘                 │
                               └─→ 起きた出来事
                                      │
                                      ▼
                                   イベント
```

遷移の型は次である。

```text
遷移 : 状態 × コマンド × 規則
      -> 遷移結果
```

一般形は次である。

```text
遷移 : 状態 × コマンド × 規則 × 遷移文脈
      -> 遷移結果
```

遷移文脈とは、状態でもコマンドでも規則でもない、遷移を成立させる追加の入力(経過時間・乱数源から確定した値・世界時刻・刻みの情報など)のことである。Esca第1段階では遷移文脈 = 経過時間であり、実装の `M遷移関数` は `(&状態, &コマンド, &規則, 経過時間) -> 遷移結果` である。3.5の基本形の図は遷移文脈を省略した概念図である。遷移文脈の一般形(共通のマーカーにするか、どの入力を含めるか)はまだ確定していない。

図の「起きた出来事」は、この文書と実装では `出来事一覧` という綴りを使う。`遷移結果` は第4.1節が定義する `遷移結果<状態, イベント>` であり、フィールド名は `次の状態` と `出来事一覧` である。

### 3.5.2 4概念の意味

状態・コマンド・規則・イベントの4概念は、それぞれ次の意味と時制を持つ。

| 概念 | 何を表すか | 時制 |
|---|---|---|
| 状態 | 今どうなっているか | 現在 |
| コマンド | 何をしようとしているか | 未来への要求 |
| 規則 | 何が起きてよいか、どう変わるか | 不変の法則 |
| イベント | 実際に何が起きたか | 過去の事実 |

### 3.5.3 Escaの旅行者での例

Escaの旅行者の場合は、次の関係になる。

```text
状態
  現在地 = (10m, 20m)
  行動状態 = 静止中

コマンド
  東へ歩く

規則
  歩行速度 = 3m/s
  東側に壁がある

        ↓ 遷移

次の状態
  現在地 = (11m, 20m)
  行動状態 = 歩行中

イベント
  歩行を開始した
  壁に接触した
```

この例が持つ `行動状態` は、2026-09-19時点の `blitz_esca` の状態には無い。`歩行を開始した` や `立ち止まった` を出来事として持つには、前の状態と次の状態の行動の差を判定できる `行動状態` が状態側に要る。現状の `blitz_esca` はこの `行動状態` を持たないため、`歩行を開始した` や `立ち止まった` を出来事として生成していない(参照: `_doc/設計/Esca/設計正本.md` 4.4 条5)。

### 3.5.4 イベントは状態変更の命令ではない

イベントは状態変更の命令ではない。イベントは、遷移の評価で成立した事実である。向きは次である。

```text
前状態 + コマンド + 規則
        ↓
     遷移を評価
        ↓
次状態 + その評価で成立した事実
        ↓
   イベントとして公開する
```

成立する事実は、状態が変化したことを必要としない。現行の `blitz_esca` では `旅行者の意図::見回す` の遷移が次の状態を前の状態と同じまま返し、`旅行者の出来事::周囲を観察した` を出来事一覧へ入れる。状態は変わらないが、観察したという事実は遷移の評価で成立している。

そのうち、`歩行を開始した`・`立ち止まった`・HPが0になった・扉が開いた のような状態変化イベントだけが、前状態と次状態の差分を根拠にする。状態変化イベントは、前状態と次状態の差を表現できることが生成条件である(4.4 の法則E2)。

### 3.5.5 イベントシステムの定義

イベントシステムとは、ある状態遷移で成立した事実を、その事実を必要とする別の系へ伝播させる仕組みのことである。伝播先の例は次である。

```text
                     ┌→ 音響
                     │    「歩行を開始した」
                     │       → 足音開始
                     │
状態遷移 → イベント ├→ アニメーション
                     │       → 歩行アニメ開始
                     │
                     ├→ クエスト
                     │       → 「初めて歩いた」を記録
                     │
                     └→ AI
                             → 近くの敵が音に反応
```

### 3.5.6 状態遷移系とイベント伝播系の二層

この理論は、少なくとも次の二層を分ける。

```text
【状態遷移系】

M状態
Mコマンド
M規則
Mイベント
M遷移

        ↓ イベントを生成

【イベント伝播系】

Mイベント発行
Mイベント購読
Mイベント反応
Mイベント配送
```

状態遷移系とは、`M状態`・`Mコマンド`・`M規則`・`Mイベント`・遷移関数からなる、状態を遷移させて起きた事実を生成する側の層のことである。イベント伝播系とは、状態遷移系が生成したイベントを、それを必要とする別の系へ伝播させる側の層のことである。イベント伝播系が持つ発行・購読・反応・配送の4語は、オーナーのコメントに名前だけがあり、2026-09-19時点の `blitz_design` にはまだ無い候補である。

### 3.5.7 イベント反応

イベント反応とは、イベントを受けて、コマンド・外部作用・別のイベント・何もしない のいずれかを返す工程のことである。イベント反応は次の型を持つ。

```text
イベント反応:
    イベント
        -> コマンド
        | 外部作用
        | 別イベント
        | 何もしない
```

例は次の2つである。

```text
敵を倒した
   ↓
クエストシステムが観測
   ↓
「報酬を付与する」というコマンドを生成
```

```text
敵を倒した
   ↓
音響システムが観測
   ↓
SEを鳴らす
```

この整理は、`Mイベント` がイベントシステム全体を表す型ではなく、状態遷移系とイベント伝播系をつなぐ「起きた事実」を表すマーカーであることを示す。

### 3.5.8 全体の因果モデル

全体の因果関係は次のモデルで表す。

```text
意図
 ↓
コマンド
 ↓
状態 + 規則
 ↓
状態遷移
 ↓
新しい状態
 +
起きた事実
 ↓
イベント
 ↓
別の系の反応
 ↓
新しいコマンド / 外部作用 / 別イベント / 記録
```

`M状態`・`Mコマンド`・`M規則`・`Mイベント` は、個別の便利なトレイトではなく、ゲーム世界の因果関係を記述するための一組の設計語彙である。

## 4. Update型のEventの語彙とコード文法

第4節は、第3.5節の理論の、Event側の語彙とコード文法である。

Observer / callback 型の Event と、`Mイベント` は別概念として語彙を分離する。Observer 系の `Event`・`Subscriber`・`Listener`・`Handler`・`Subscribe`・`Unsubscribe`・`Invoke` は「呼び出し機構」の語彙である。`Mイベント` はそうではなく、Update / 遷移が生成する過去の事実データである。したがって本書は、こちらにも「何を何と呼び、コードをどう書くか」という独自の文法を定める。

### 4.1 基本語彙

**`Mイベント` / 出来事**とは、ある遷移によって実際に成立した過去の事実を表す値のことである。

```rust
pub trait Mイベント: MDTO {}
```

Event 自身は誰かを呼び出さない。Event はコールバック一覧、`invoke()`、購読者を持たない。`struct` と `enum` のどちらでもよい。次の2つはどちらも正当な `Mイベント` である。

```rust
pub enum 旅行者の出来事 {
    歩行を開始した,
    立ち止まった,
    障害物に遮られた,
}
```

```rust
pub struct ダメージを受けた {
    pub 対象: 個体ID,
    pub 量: ダメージ量,
}
```

**`遷移結果<状態, イベント>`**とは、Update / 遷移が返す、次の状態と、その遷移で成立した出来事の組のことである。この型は状態と出来事を混ぜない境界である。

```rust
pub struct 遷移結果<状態, イベント> {
    pub 次の状態: 状態,
    pub 出来事一覧: Vec<イベント>,
}
```

**出来事の生成**とは、遷移の計算中に、実際に成立した事実を `出来事一覧` へ追加することである。出来事の生成は Observer 系の `invoke` に相当する語ではない。

- 良い語: `出来事を生成する`、`出来事一覧へ加える`、`〜が成立した`
- 避ける語: `invoke`、`fire`、`通知を呼ぶ`

`emit` を日本語へ持ち込む場合も、書き手はそれを「コールバックを呼ぶ」意味ではなく「出来事値を出力する」の意味に限定する。

**出来事の配送**とは、既に生成済みの出来事値を、0個以上の消費側へ渡す工程のことである。配送は新しい事実を作らない。配送は既存の事実を読者へ渡すだけである。

```text
遷移結果.出来事一覧
        │
        ├─→ 音響への解釈
        ├─→ 演出への解釈
        ├─→ 進行への解釈
        └─→ ログ
```

**出来事の解釈**とは、出来事を、別のドメインや外部システムが理解する型へ純粋変換することである。

```text
旅行者の出来事
    → 音響要求
    → 演出要求
    → 別ドメインのコマンド
```

基本形は `fn (&イベント) -> 出力` であり、0件以上を返すなら `fn (&イベント) -> Vec<出力>` である。将来、共通の関数役割として必要になった場合は `Mイベント解釈関数<イベント, 出力>` のような型を検討できるが、利用例が固まる前に共通化しない。

**要求**とは、SE再生、パーティクル生成、画面演出など、外部システムへ「これを実行してほしい」と渡す値のことである。

```text
旅行者の出来事::障害物に遮られた
    ↓ 解釈
壁衝突音を再生する要求
```

ドメインの遷移関数自身は音響API等を呼ばない。イベントから要求へ変換した後、外部境界が要求を実行する。`M要求` を共通マーカーにするかは、複数の実例が出てから判断する。

### 4.2 標準データフロー

Update型のEventシステムの標準形を次とする。

```text
M入力
  ↓ 解釈
Mコマンド
  ↓
M状態 + Mコマンド + M規則
  ↓ 遷移
遷移結果<M状態, Mイベント>
  ├─ 次の状態 ─────────→ 次回の状態正本
  │
  └─ 出来事一覧
       ├─→ 出来事の解釈 → 音響要求 → 音響境界
       ├─→ 出来事の解釈 → 演出要求 → 描画/演出境界
       ├─→ 出来事の解釈 → 別ドメインのMコマンド → 別のUpdate
       └─→ ログ / リプレイ等
```

重要なのは、`Event -> callback` ではなく `Event -> data flow` である。

### 4.3 Observer系の語彙との対応

この方式では以下の語を原則として使わない。

| Observer / callback型 | Update型で対応する概念 |
|---|---|
| Event object with invoke | `Mイベント` という事実値 |
| Subscriber / Listener | 出来事の消費側 |
| Handler | 出来事の解釈、または要求を実行する工程 |
| Subscribe | コンポジションルートで消費側を明示配線する |
| Unsubscribe | 通常は存在しない。配線自体の寿命を変える |
| Invoke / Fire | 出来事値を生成して遷移結果へ入れる |
| EventArgs | `Mイベント` 自身のデータ |
| EventBus | 原則作らない。必要なら「出来事の配送工程」として役割を限定する |

特に `Handler` という語は曖昧なので避ける。書き手は責務ごとに語を分ける。

- Event を別の値へ変換するなら「解釈」
- Event を複数の読み手へ渡すなら「配送」
- 要求を外部APIで実行するなら「実行」
- 状態を更新するなら「遷移」

### 4.4 Event生成の法則(E1〜E8)

#### 法則E1: 過去の事実

`Mイベント` は、既に成立した事実だけを表す。

#### 法則E2: 成立していない事実を生成しない

イベントは、その遷移によって実際に成立した場合だけ生成する。

悪い例:

```text
コマンド = 歩く
→ 毎刻み「歩行を開始した」を生成
```

正しい判定:

```text
前状態 = 非歩行
次状態 = 歩行
→ 「歩行を開始した」
```

したがって「開始した」「終了した」「変化した」のような状態変化イベントは、前状態と次状態の差を表現できることが生成条件になる。

#### 法則E3: 状態正本へ混ぜない

イベントは次回Updateへ持ち越す状態正本ではない。

```rust
struct 状態 {
    歩行開始イベントが起きた: bool,
}
```

のように「一度起きた出来事」をリセット前提のフラグとして状態へ埋め込まない。継続して成立する事実なら、それはイベントではなく状態として表す。

#### 法則E4: 消費されても事実は変わらない

消費側はイベントを変更しない。複数の消費者が同じ事実を読める。

#### 法則E5: 配送は意味を作らない

配送工程はイベントの意味を決めない。意味は Event 型の定義と生成元の遷移が決める。

#### 法則E6: 副作用は遷移から分離する

純粋なドメイン遷移は音響・描画・ネットワーク等を直接実行しない。

```text
遷移
→ Mイベント
→ 解釈
→ 要求
→ 外部境界で実行
```

と分ける。

#### 法則E7: 隠れた購読表を作らない

どの Event を誰が読むかは、可能な限りコンポジションルートまたは明示された工程のコードから追える形にする。任意の場所から `subscribe(TypeId, callback)` して依存関係を隠す汎用 EventBus を基本形にしない。

#### 法則E8: Eventから同じ状態への暗黙フィードバックを作らない

その遷移自身が知っている事実によって同じ状態をさらに変える必要があるなら、原則として最初の遷移の中で状態を確定する。別ドメインへ影響するときは、

```text
Mイベント
→ 解釈
→ 相手ドメインのMコマンド
→ 相手のUpdate
```

と明示する。これにより Event の連鎖で同一tick内に何度状態が変わるか分からない構造を避ける。

### 4.5 型・関数の文法

Event 型は次の形で書く。`struct` / `enum` は意味に応じて選ぶ。

```rust
#[derive(Clone, ...)]
pub struct / enum 何かの出来事 { ... }

impl Mイベント for 何かの出来事 {}
```

遷移は次の形で書く。遷移は「次の状態」と「今回成立した出来事」を同時に確定する。

```rust
状態.〜を遷移する(
    &コマンド,
    &規則,
    経過時間,
) -> 遷移結果<状態, 出来事>
```

解釈は、主語が自然なら次のように書ける。

```rust
出来事.音響要求へ解釈する()
出来事.演出要求へ解釈する()
```

ただし1つの Event 型へ各サブシステム固有の知識を集めて依存を逆流させる場合は、消費側の型に次のように置く。配置は「どちらがどちらを知ってよいか」という依存方向で決める。

```rust
音響方針.出来事を音響要求へ解釈する(&出来事)
```

配送は、中央の汎用 EventBus ではなく、その局面で必要な配送を明示する。

```text
一刻みを進める
  → 遷移結果を得る
  → 出来事一覧を各解釈工程へ渡す
  → 要求を各外部境界へ渡す
  → 次の状態を正本へ採用する
```

順序に意味がある場合は「購読登録順」に依存させず、工程の順序として名前を与える。

### 4.6 機械判定すること・しないこと

現在の `cargo xtask conform` は、次を法則として維持する。

- `Mイベント: MDTO`(コンパイラが強制する。`Clone` は `MDTO` から継承する)
- 参照を持たない
- 生ポインタを持たない
- 内部可変性を持たない
- 固有 `impl` に `&mut self` を持たない

参照・生ポインタ・内部可変性の検査は `MDTO` を実装する型に対して行い、`Mイベント` は `MDTO` の上に積んだ役割としてそれを継承する。`M規則`・`Mコマンド`・`M設定` も同じである。`&mut self` が無いだけでは `RefCell` 等を通じて `&self` から書き換えられ、不変の法則や純粋計算という定義に反するためである。

さらに検査器で型を正確に同定できるようになった後は、次を候補にする。これらは「現在・未来・過去」の役割を同じ型へ重ねないための直交の法則である。

- 同じ具体型が `M状態` と `Mイベント` を同時に実装しない
- 同じ具体型が `Mコマンド` と `Mイベント` を同時に実装しない
- 同じ具体型が `M入力` と `Mイベント` を同時に実装しない

一方、次は一般の構文検査では判定しない。これらは意味論または具体ドメインの配線だからである。

- イベントが本当に成立した事実か
- 開始/終了イベントが状態差からだけ生成されているか
- 名前が日本語の過去形か
- 必ず1フレームで消えるか
- enumであるか
- Event がどの消費者へ配送されるべきか

### 4.7 コメント / rustdoc の文法

Event のコメントは「何の通知か」ではなく、どの事実が成立した値なのかを書く。

悪い例:

```rust
/// 歩行開始時に使うイベント。
歩行を開始した,
```

良い例:

```rust
/// 非歩行状態から歩行状態へ遷移した事実。歩行中の各刻みを表すものではない。
歩行を開始した,
```

```rust
/// 移動先が空間制約を越え、実際の移動位置が制限された事実。
障害物に遮られた,
```

特に状態変化イベントは、前に何であり、次に何になったとき、この事実が成立するかがコメントから分かるようにする。

消費先(SEを鳴らす、エフェクトを出す等)は Event 自身の意味ではないので、書き手は Event 型の定義コメントには原則書かない。書き手はそれを消費側の「解釈」に書く。

### 4.8 Marker / Relation / Law としての位置付け

```text
Marker
  Mイベント
    = 過去の事実として解釈する型

Relation
  M遷移関数
    produces -> 遷移結果<状態, イベント>

  出来事の解釈
    consumes -> Mイベント
    produces -> 要求 / 他ドメインのMコマンド / 記録

Law
  E1 過去の事実
  E2 成立した事実だけ生成
  E3 状態正本へ混ぜない
  E4 消費側は事実を変更しない
  E5 配送は意味を作らない
  E6 副作用を遷移から分離
  E7 隠れた購読表を基本形にしない
  E8 同一状態への暗黙Eventフィードバックを作らない
```

この形なら Observer パターンと同様に、読み手は `Mイベント` を見た時点で「この型が何であり、どこから生まれ、どう流れ、どう書いてはいけないか」までコード文法として共有できる。

## 5. 機械強制の手段

依存の向きは `xtask/src/conform/dependency_whitelist/ledger.rs` の白リストが機械で強制する。`blitz_design` の行は依存ゼロであり、`blitz_sim` と `blitz_esca` の行が `blitz_design` を許す。

法則の検査主体は2つに分かれる。

- コンパイラが強制する法則: データの役割(`M状態`・`Mコマンド`・`Mイベント`・`M規則`・`M入力`・`M設定`)の `MDTO` 実装(上位トレイト)、`MDTO` の `Clone`(上位トレイト)、関数の役割の型引数の境界、`遷移結果` の型引数の `M状態`・`Mイベント` の境界(構造体の境界)。型エイリアスの境界は Rust の仕様上強制されない(rust-lang/rust#112792)ため、関数の役割(`M射影関数`・`M解釈関数`・`M遷移関数`)は境界付きの newtype であり、型を使った時点でコンパイラが型引数の境界を強制する。迂回できる綴りは無い。利用側は `const _: M遷移関数<...> = M遷移関数::生成する(旅行者の現在地::歩行を遷移する);` の静的宣言でコンパイラに確かめさせる。
- `cargo xtask conform` の設計オントロジーの検査(`xtask/src/conform/design_ontology.rs`)が見る法則: `MDTO` の定義に参照・生ポインタ・内部可変性が無いこと(上位トレイトによりデータの役割の型を全部含む)、データの役割を実装する型が同じファイルに `impl MDTO for` も書いていること、`Mコマンド` が `enum` であること、`M規則` が `struct` であること、`Mコマンド`・`Mイベント`・`M規則`・`M設定` を実装する型の固有の `impl` に `&mut self` が無いこと(`M状態` と `M入力` と `MDTO` には課さない)。定義が見つからない型は違反として報告する。

検査器の保証範囲は次のとおりである。検査は Rust の型意味論でなく構文パターン(`impl トレイト for 型` の行と `struct`/`enum` の定義ブロック)に対して行う。型の同一性は「定義のモジュールパス + 型名」である(モジュールパスはファイルのパスから導く。`crates/<名前>/src/lib.rs` は `<名前>`、`src/a/b.rs` は `<名前>::a::b`、`src/a/mod.rs` は `<名前>::a`)。`impl トレイト for 型` の行がどの定義を指すかは、実装と同じファイルの定義、無ければそのファイルの `use` 行(`crate::`・`super::`・`self::` の置き換えと1段の波括弧の群)を解決して得たモジュールパスの定義で決める。`use` が無ければ全体で1つだけの同名の定義を採り、2つ以上あれば一意に決まらない違反にする。`use ... as` の別名は解決できない違反にする(黙って通さない)。固有の `impl` の `&mut self` の探索も同じ規則で定義に属するファイルだけを見るため、同じクレートの別のモジュールの同名の型の `impl` を誤って数えない(CLAUDE.md の切り出しの根拠義務が `impl` を別ファイルへ置くことを許すため、同じファイルだけに限定しない)。入れ子の波括弧の `use`、glob の取り込み、ジェネリックな `impl`、フィールドの型の中に間接的に含まれる内部可変性は保証範囲の外である。
