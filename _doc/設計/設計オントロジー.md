# 設計オントロジー

この文書は、共通設計語彙クレート `crates/blitz_design` が持つ設計解釈マーカーと関数の役割、Update型のEventの語彙とコード文法、および設計の検証が扱う関係の3つの高さ・命題・検証(第6節から第11節)を定める設計正本である。マーカーの定義文は `_doc/計画/ユビキタス言語.md`「設計解釈マーカー」「M状態はM不変データである」「Mイベント」と同じ内容であり、本書はそれと矛盾しない。

## 1. 位置づけ

`blitz_design` は、Rust上の型が設計上何として解釈されるか(純粋な所有データ(値を複製して渡す不変データと、1つの実体を共有して読む不変データ)・状態・遷移が受け取る命令(コマンドと命令の組)・イベント・規則・解釈前の入力(生入力と中間入力)・観測・工程と、存在の分類である値オブジェクト・エンティティ・エンティティ識別子・不変エンティティ・可変エンティティ)を宣言する設計解釈マーカーと、射影・解釈・遷移(と、問い合わせを伴う遷移と評価)と規則によらない書き換えという関数の役割を表す境界付きの newtype と、遷移の戻り値の形を固定する意味型(`遷移成功結果`・`遷移失敗結果`)だけを持つ。このクレートはドメインの語彙を1つも持たない。

置き場の判定の基準は「その型が何について語るか」である。

- 実装者は、プログラムについて語る(型が設計上どの役割かを言う)ものを `blitz_design` に置く。
- 実装者は、シミュレーションについて語る(時間尺度・物理小刻み等)ものを `blitz_sim` に置く。
- 実装者は、Esca世界について語る(旅行者・区域・経路等)ものを `blitz_esca` に置く。

`blitz_design` は何にも依存しない最下層であり、`blitz_sim` と `blitz_esca` と `blitz_game` がこれを使う。実装は `crates/blitz_design/src/設計解釈マーカー.rs`(マーカー)と、`crates/blitz_design/src/function_role.rs`(射影と解釈の役割)・`crates/blitz_design/src/遷移関数.rs`(遷移の役割と意味型)・`crates/blitz_design/src/出来事も失敗も無い遷移関数.rs`(形を縮めた遷移の役割)・`crates/blitz_design/src/問い合わせを伴う関数.rs`(問い合わせを伴う役割)・`crates/blitz_design/src/規則によらない書き換え関数.rs`(規則によらない書き換えの役割)にある。

## 2. 設計解釈マーカーの一覧と共通契約

設計解釈マーカーとは、Rust上の型が設計上何として解釈されるかを、メソッドを持たないトレイトの実装で宣言する印のことである。例外は `Mエンティティ`(2.5節)だけであり、`Mエンティティ` は識別子を返すメソッドを1つ持つ。どの値がそのエンティティの識別子なのかを機械的に取得できるようにするためである。

本節の表はデータの役割の軸と、処理の役割の軸のうちトレイトのマーカーである `M工程` を持つ。存在の分類(値オブジェクトとエンティティ)と変更可能性(不変と可変)の軸は 2.5 節が持ち、関数境界の役割(必須入力の束と任意の設定の束と評価の排他的な帰結)の軸は 2.6 節が持つ。表の中で `M不変データ` はデータの役割の一種ではなく、複数のデータの役割が共有する基底の契約であり、`M工程` はデータの役割に含めない(2.1節)。

### 2.1 オントロジーの層

基礎オントロジーは、次の6つの層に分ける。2.5.1 の軸の表は、このうち A から D をトレイトのマーカーの軸として写したものであり、E はマーカーの軸ではなく `blitz_sim` が持つ関係、F はまだ設計していない関係である。

```text
A. 値・存在の意味: M不変データ / M共有される不変データ / M値オブジェクト / Mエンティティ / Mエンティティ識別子 / M不変エンティティ / M可変エンティティ
B. 因果モデル上のデータの役割: M状態 / M解釈前の入力(M生入力 / M中間入力) / M遷移が受け取る命令(Mコマンド / M命令の組) / M規則 / Mイベント / M観測
C. 関数境界の役割: MParameter / MOptions / M結果
D. 処理の役割: M工程 / M射影関数 / M解釈関数 / M遷移関数 / M遷移が受け取る命令で決まる遷移関数 / M規則で決まる遷移関数 / M規則と遷移パラメータで決まる遷移関数 / M問い合わせを伴う遷移関数 / M規則で決まる問い合わせを伴う遷移関数 / M問い合わせを伴う評価関数 / M規則によらない書き換え関数
E. 時間と寿命の関係: M時間尺度 / M時間局所状態 / M更新工程(blitz_sim が持つ)
F. アーキテクチャの関係: 状態とデータの正本 / 参照実装への準拠 / 境界 / 依存の向き / 配線(今後の設計対象)
```

- `M不変データ` は B のデータの役割の一種ではなく、複数のデータの役割が共有する基底の契約として扱う。A に置くのはそのためである。B の10はいずれも `M不変データ` を上位トレイトに持つ(`M生入力` と `M中間入力` は `M解釈前の入力` を通して、`Mコマンド` と `M命令の組` は `M遷移が受け取る命令` を通して持つ)。
- `M共有される不変データ` は、`M不変データ` と渡し方で分かれる兄弟の基底の契約であり、A に置く(2026-09-28 のオーナー裁定)。どのデータの役割もこれを上位トレイトに持たない(データの役割はどれも値を複製して渡す `M不変データ` を上位に持つ)。
- この定義から、`M共有される不変データ` を名乗る型は、`M不変データ` を上位に持つ分類(B のデータの役割・`M値オブジェクト`・`Mエンティティ識別子`・`M不変エンティティ`・`MParameter`・`MOptions`)を名乗れない。上位トレイトを通して `M不変データ` も名乗ることになり、2つの基底の契約の排他に反するためである。共有して読む値をデータの役割で使うときは、その値を `Arc` で持つ `M不変データ` の型に包む(Esca の `経路の開閉の規則` が地図を `Arc<地点と経路のグラフ>` で持つ形)。この排他は機械が落とす。`M不変データ` を上位に持つ分類を名乗れば、rustc が上位トレイトの要求として `M不変データ` の実装を求め、`cargo xtask conform` が `M不変データ` と `M共有される不変データ` を同時に名乗ることを排他の組として違反にするためである。また、`M可変エンティティ` と同時に名乗らない。中身が変わらないことと、同一性を保ったまま内部の状態を更新することが衝突するためである。こちらは機械では検査しない。名乗る型が1件も無く、実際に起きている誤りを名指せないためである。
- `M工程` はデータの役割に含めない。工程はデータではなく処理であり、D の処理の役割に置く。`cargo xtask conform` の一覧(`xtask/src/conform/設計オントロジーの規約検査/設計解釈マーカーの一覧.rs`)も `M工程` をデータの役割の一覧から外し、処理の役割の一覧に持つ。正規形・別名・再公開・波括弧付きのモジュールの検査の対象からは外さない。
- D のうち `M工程` 以外の10は関数の役割であり、境界付きの newtype(第3節)である。トレイトのマーカーではない。
- 2.5.1 の軸の表が持つ存在の分類と変更可能性は、A を「同一性を持つか」と「自己変更を行うか」の2つの問いに分けたものである。

### 2.2 共通のマーカーへ昇格させる前の受理テスト

親と実装員は、ある語を共通のマーカーの候補にするとき、少なくとも次の2つを確かめる。

- **その語を型名として主語に置き、その型自身へ自然なメソッドを生やせるか。** `X.何かする()` と読んだとき、`X` がその振る舞いの自然な主体であるかを確かめる。主体として読めない語は、型の分類ではなくメタの語である。
- **一般的な設計用語が頻出することと、それが実行時の共通の型の分類になることは別である。** 曖昧な上位の語で異なる実体をまとめず、必要ならより具体的なドメインの語彙へ分解する。この受理テストの目的は概念を減らすことではない。

次の概念は共通のマーカーにしない。一般的な設計語をそのまま型の分類へ持ち込むと、上の2つの受理テストを通らないためである。それぞれの理由と、どう表すかは次のとおりである。

| 概念 | 共通のマーカーにしない理由 | どう表すか |
|---|---|---|
| 設定 | 「起動時に決まる」「外から与えられる」「長く保持される」はライフサイクルや利用方法の事情であり、型の本質ではない | 関数境界の役割なら `MParameter` か `MOptions`。起動設定やアプリケーション設定が要るなら具体のドメインの語彙として定義する |
| 仕様 | 仕様は実行時のデータの種類ではなく、対象に何が許され、何を満たさなければならないかを定めるメタの概念である | マーカー・関係・法則・型・試験・設計文書の組み合わせで表す。実行可能な述語(Specification Pattern)が要るなら、空のマーカーではなく振る舞いを持つ普通のトレイトにする |
| 方針 | 人間や設計が採用する「方針」はメタの語であり、実行時の構造体名を `〜方針` にするとその型自身を振る舞いの主体として読みにくい | 方式を表す列挙・振る舞いを持つトレイト・具体の規則の型のどれかにする |
| 仕組み | 「仕組み」という語だけでは機械の法則を導けず、共通のマーカーとしては抽象度が高すぎる | 共通のマーカーを置かない |
| 変換 | 単なる「変換」まで一般化すると意味が薄くなる | 関数の役割と関係で表す(射影・解釈・遷移と、必要に応じた他の変換の役割) |

既存の `〜仕様`・`〜方針` の型の再分類と、関係の最小語彙は 2.3 節の今後の設計対象である。

`cargo xtask conform` が機械で保証しているのはここまでであり、設計解釈マーカーの型契約は値の置き換え(`規則.身体 = 別の値`、`&mut 規則` を受ける自由関数)を禁じていない。

`M共有される不変データ` とは、中身が変わらず(内部可変性も自己変更の API も持たない)、渡すときに複製せず1つの実体を `Arc` で共有して読む値のことである(2026-09-28 のオーナー裁定。名前は仮であり、裁定待ちの語である)。それまでの `M不変データ` は、「中身が変わらない」ことに加え、法則(参照・ポインタを持たない、`Clone` を持つ)によって「渡すときは複製する」ことまで決めていた。C# でいえば readonly struct だけを表し、中身は不変で1つの実体を皆で共有して読む readonly class(地図・3Dモデルなど)を表せなかった。そのため Esca の歩行の規則は地図を持つと毎刻み地図を複製することになり、借りて読む別の口(`区域の空間制約の読み口`)と宣言の無い歩行の関数を置いていた。裁定は、渡し方で分かれる兄弟のマーカーを足してこれを解いた。

`M共有される不変データ` は上位トレイトを持たない。`M不変データ` を上位に持つと `Clone` が要り、複製の口を持たせないという目的に反する。`Send`・`Sync` を上位に置くかは並行性の設計の判断であり、「中身が変わらない・共有して読む」という定義から導けないため置かない。`M不変データ` と `M共有される不変データ` は排他である。`M不変データ` は渡すとき値を複製し、`M共有される不変データ` は渡すとき複製せず1つの実体を共有するため、同じ値が2つの渡し方を同時に名乗ることは定義から成り立たない。`cargo xtask conform` は、同じ型が両方を名乗ることを違反にする。

`M不変データ` を名乗る型(データの役割の型を含む)は、`M共有される不変データ` を名乗る型を `Arc<型>` のフィールドで共有して持てる。借りる参照 `&型` は認めない。規則が地図を借りると、規則が地図より長く生きられず、値として持ち運べなくなるためである。`Rc` と `Weak` も認めない。実例は Esca の地図 `地点と経路のグラフ`(`crates/blitz_esca/src/地点と経路/地図.rs`)であり、`Clone` を実装せず、`経路の開閉の規則` と `区域の空間制約` が `Arc<地点と経路のグラフ>` で共有して持つ。

`M設定` は共通の設計解釈マーカーとして定義しない。「起動時に決まる」「外から与えられる」「長く保持される」は型の本質ではなく、ライフサイクルや利用方法の性質だからである。関数境界の必須の入力は `MParameter`、任意の指定は `MOptions` で表す。起動設定やアプリケーション設定が要るなら、実装者はそれを具体のドメインの語彙として定義する。

`M解釈前の入力` は、`M解釈関数` がゲームの意味(`Mコマンド`)へ読み替える前の、ゲームの意味を持たない入力である(2026-09-27 のオーナー裁定。PR #195 のレビュー)。`M解釈関数` の入力側の境界は `M解釈前の入力` である(解釈は意味を持たない入力に意味を付ける計算であるため)。旧称は `Mデバイス生入力` であり、さらに前は `M入力` である。

`M解釈前の入力` は、値の形が入力の出どころに固有かどうかで、下位の `M生入力` と `M中間入力` に分かれる(同じ裁定)。実装者は、`M解釈前の入力` を名乗る型に、この2つのどちらか1つもあわせて名乗らせる。`M生入力` は、入力の出どころに固有の形のままの値(キーの押下・パッドの軸の値など)であり、例は Esca の `キーボード歩行入力` である。`M中間入力` は、入力の出どころに依らない形へ整えた、まだゲームの意味を持たない値であり、例は `blitz_game` の `確定済みの操作入力` と、将来の必殺技の入力(キーの並びを組み立てた値)である。

2つの分け方は、値がどこから来たか、誰が作ったかではなく、値の形で決まる(2026-09-27 のオーナー裁定)。判定の問いは、値の各成分が何を名指すかである。各成分が特定の種類の装置の部品(キー・軸・ボタン)を名指すなら `M生入力`、装置に依らない操作(前へ進む・決定する等)を名指すなら `M中間入力` である。Esca の `キーボード歩行入力` の成分(上・下・左・右)はキーを名指すため `M生入力` であり、`確定済みの操作入力` の成分(前へ進む操作を押しているか・決定の操作を押した瞬間か等)は操作を名指すため `M中間入力` である。`確定済みの操作入力` はデバイスの違いを消し、押した瞬間を判定した形の値である。この値は共通入力層がデバイスの入力を整えて作るほか、決まった手順の操作(`crates/blitz_app/src/world_execution/game/操作の台本.rs`)がデバイスを通らずに直接作る。出どころで分ける定義では、決まった手順の操作から直接作られたこの値が生入力に読めてしまうが、形で分ける定義ではどちらの作られ方でも `M中間入力` である。旧い名前 `Mデバイス生入力` はこの値を言い当てていなかった。

下位を2つに分けるのは、このマーカーが今後2つの向きで増えるためである。1つ目は入力の出どころが増える向き(パッド・マウス・タッチ・画面のボタン・ネットワーク越しの他のプレイヤーの操作・リプレイ・AIの操作)であり、2つ目は読み替えを何回かに分ける向き(キーの並びから必殺技の入力を経て技の指示へ、指の動きからスワイプの判定を経て操作の意図へ)である。名前が「出どころに固有の形の値か、出どころに依らない形へ整えた値か」を言えば、どちらの向きに増えても型の位置が決まる。`M生入力` と `M中間入力` は排他であり、同じ型が両方を名乗ることと、`M解釈前の入力` を名乗る型がどちらも名乗らないことを `cargo xtask conform` が違反にする(`xtask/src/conform/設計オントロジーの規約検査/分類の排他と網羅の検査.rs`)。

`M命令の組` とは、`Mコマンド` を名乗る型だけを名前付きのフィールドに並べた構造体のことである(2026-09-28 のオーナー裁定)。定義は構造で決まり、この形の型はどれも `M命令の組` を名乗る。この形が表すのは、同じ刻みに届いた独立な選択ごとの命令を1つの値にしたものである。それまでの `Mコマンド` は、「1つの選択(排他的な選択肢のどれか1つ)」と「同じ刻みに届いた命令の全体」の両方を1語で表そうとしていた。1つの遷移はコマンドの位置を1つしか持たないため、独立な2つの選択(水平にどう動くかと、ジャンプするか)を1つの遷移へ渡すには、2つを掛け合わせた選択肢の列挙(`ジャンプせずに動く(水平移動)`・`ジャンプして動く(水平移動)`)へ展開するしかなかった。展開した列挙は、選択が増えるたびに選択肢が掛け算で増え、各選択を確定済みの操作入力から導く解釈を `M解釈関数` と宣言できない。裁定はこの2つを別の概念に分けた。「1つの選択」は今までどおり `Mコマンド`(必ず `enum`)であり、定義は変えない。「同じ刻みに届いた命令の全体」は、`Mコマンド` だけを並べた構造体である `M命令の組` が表す。実例は `blitz_game` の `胴体の移動の命令の組`(フィールドは `水平移動の操作` と `ジャンプの操作`)と、Esca の `経路の開閉と旅行者の歩行の更新への入力`(フィールドは `経路の開閉の命令` と `旅行者の意図`。それまで `MParameter` を付けていた)である。

遷移の役割(`M遷移関数`・`M遷移が受け取る命令で決まる遷移関数`・`M問い合わせを伴う遷移関数`)のコマンドの位置は、`Mコマンド` と `M命令の組` のどちらも受け取る。境界は2つの上位の `M遷移が受け取る命令` であり、`Mコマンド` と `M命令の組` はこれを上位トレイトに持つ。型は自分が名乗る下位と一緒に `M遷移が受け取る命令` を明示して実装する。2つの全称の実装(`impl<T: Mコマンド> M遷移が受け取る命令 for T` と `impl<T: M命令の組> M遷移が受け取る命令 for T`)で書く形は、両方を満たしうる型について実装が重なるため、コンパイラが拒む。この形は `M解釈前の入力` と下位の `M生入力`・`M中間入力` と同じであり、`cargo xtask conform` は、`M遷移が受け取る命令` を名乗る型が下位のどちらか1つを名乗ること(網羅)と、両方を名乗らないこと(排他)を検査する。`M解釈関数` のコマンドの位置(出力)は `Mコマンド` のままである。解釈は1つの選択を導く計算であり、命令の組は解釈した命令を並べて作るためである。

意味付けの済んだ入力を表すデータの役割は置かない(2026-09-27 のオーナー裁定)。関数へ渡す意味の決まった値は、命令なら `Mコマンド`、状態なら `M状態`、規則なら `M規則` がすでに名前を持ち、それらを関数へ渡す1つの引数へまとめた型は `MParameter`(2.6節)が名乗る。同じ日に一度置いたマーカー `M関数への入力` は、この裁定で外した。`M関数への入力` を付けた6つの型はすべて `MParameter` も付けており、逆に `MParameter` だけを付けた型(`遷移パラメータ`・`遮蔽の判定の入力`・`胴体の移動の遷移パラメータ`)も意味の決まった入力であったため、2つの付け分けが成り立っていなかった。`M関数への入力` にしか当てはまらない型も、このマーカーに固有の法則も無かった。このマーカーを置いた目的(意味付けの前の入力と区別すること)は、`M解釈前の入力` の側の定義だけで成り立つ。

データの役割(`M状態`・`M遷移が受け取る命令`(下位の `Mコマンド`・`M命令の組` を含む)・`Mイベント`・`M規則`・`M解釈前の入力`(下位の `M生入力`・`M中間入力` を含む)・`M観測`)はすべて `M不変データ` を上位トレイトに持つ。`Mコマンド: M不変データ` 等の supertrait の Relation はコンパイラが保証し、`cargo xtask conform` は `M不変データ` と役割の実装から型の定義をたどって、その定義に純粋データ規約(参照・生ポインタ・内部可変性を持たない)を当てる。`impl M不変データ for` をどのファイルに書くかは法則ではない。`cargo xtask conform` は、同じ型が複数の役割を持っても違反を1回だけ報告する。

`M状態: M不変データ` は Blitzdrache 全体の共通契約である。既存コードが適合しない場合、実装者は共通契約を弱めず既存コードの側を直す。本書が `Mコマンド`・`Mイベント`・`M規則` を `M不変データ` の上に積むのは、`Mコマンド` だけが純粋データ契約から外れていると、`&コマンド` から外部状態を書き換えられ、`M遷移関数` が純粋計算であるという理論を型契約が支えられないためである。

`M不変データ` の役割は「境界を越えて運ばれるデータ」ではなく「純粋な所有データ」である。`blitz_sim` のソルバ内部の作業状態も `M状態` であり、それは境界を越えないが純粋な所有データではあるので、この定義なら `M状態: M不変データ` の共通契約と矛盾しない。

## 2.5 存在の分類(同一性・ライフサイクル・不変性)

本節は、DDD(ドメイン駆動設計)の基礎概念である同一性・ライフサイクル・不変性の軸を、第2節のデータの役割とは別の軸として持つ。

### 2.5.1 5つの軸

設計解釈マーカーは5つの軸を持ち、軸は互いに直交する。1つの型は各軸から独立に分類を選ぶ。例外は、データの役割の `M命令の組` と関数境界の役割の `MParameter` の排他の組(軸をまたぐ排他)の1つだけである。`MParameter` は遷移の役割のコマンドの位置へ入れない必須入力の束であり、`M命令の組` はそのコマンドの位置へ入れる命令(`M遷移が受け取る命令` の下位)であるため、2つは定義から同時には名乗れない(2.6節)。`M共有される不変データ` は軸の分類でなく基底の契約であり(2.1節)、`M不変データ` を上位に持つ分類(データの役割・`M値オブジェクト`・`Mエンティティ識別子`・`M不変エンティティ`・`MParameter`・`MOptions`)と `M可変エンティティ` を同時に名乗らない。前者は2つの基底の契約の排他から、後者は中身が変わらないことと内部の状態を更新することの衝突から導かれる。データの役割で使うときは、`Arc` で持つ `M不変データ` の型に包む。本節が扱うのは存在の分類と変更可能性の軸であり、関数境界の役割の軸は 2.6 節が持つ。軸とオントロジーの層(2.1節)の対応は、データの役割が B、処理の役割が D、存在の分類と変更可能性が A、関数境界の役割が C である。

| 軸 | 問い | 分類 |
|---|---|---|
| データの役割 | その型は因果モデルのどこに現れるか | 状態・遷移が受け取る命令(コマンドと命令の組)・イベント・規則・解釈前の入力(生入力と中間入力)・観測(第2節)。`M不変データ` はこれらが共有する基底の契約であり、分類の1つではない |
| 処理の役割 | その型は処理として何を担うか | 工程(`M工程`。第2節)。関数の役割の newtype(第3節)も同じ層に属する |
| 存在の分類 | その型は同一性を持つか | 値オブジェクト(`M値オブジェクト`)とエンティティ(`Mエンティティ`)と、エンティティの識別子(`Mエンティティ識別子`) |
| 変更可能性 | その型は自己変更を行うか | 不変(`M不変エンティティ`)と可変(`M可変エンティティ`)。この軸のマーカーはエンティティに付け、値オブジェクトは `M不変データ` により常に不変である |
| 関数境界の役割 | その型は関数の境界をどう渡るか | 必須入力の束(`MParameter`)と任意の設定の束(`MOptions`)と評価の排他的な帰結(`M結果`)(2.6節) |

`M不変エンティティ` と `M可変エンティティ` は同じ軸の排他の分類であり、同じ型が両方を名乗ることを `cargo xtask conform` が違反にする(2.5.3)。

値オブジェクトとエンティティの区別と、不変と可変の区別は別の軸である。値オブジェクトは常に不変であるが(`M値オブジェクト: M不変データ`)、エンティティは不変にも可変にもなりうる。`M不変エンティティ` は「不変エンティティ」という新しい哲学ではなく、同一性とライフサイクルを持つこと(`Mエンティティ`)と自己変更を禁じること(`M不変データ`)の2つの既存の概念の合成である。

### 2.5.2 マーカーの一覧と法則

| マーカー | 定義 | 上位トレイト | 課す法則 | コンパイラが強制するもの | `cargo xtask conform` が検査するもの |
|---|---|---|---|---|---|
| `M不変データ` | 参照や内部可変性を所有せず、値として複製・受け渡しできる純粋な所有データ(第2節) | `Clone` | 内部可変性を持たない。自己変更を行わない。値として複製・受け渡しできる。変更は既存の値の書き換えでなく新しい値の構築で表す。変数への再代入や別の値への置き換えは禁止しない | `Clone` | 定義に参照・生ポインタ・内部可変性が無いこと。共有の指し先が `M共有される不変データ` を指す `Arc` だけであること。`M共有される不変データ` と同時に名乗らないこと |
| `M共有される不変データ` | 中身が変わらず、渡すときに複製せず1つの実体を `Arc` で共有して読む値(第2節) | 無し | 内部可変性を持たない。自己変更を行わない。`Clone` を求めない | 無し | `M不変データ` と同じ純粋データ規約。`M不変データ` と同時に名乗らないこと |
| `M値オブジェクト` | 同一性を持たず、その値そのものによって意味と等価性が決まる型 | `M不変データ + PartialEq` | 自己同一性を持たない。内容が同じなら同じ値として扱う。自己変更せず、変更は新しい値の生成として表す | `Clone`・`PartialEq` | `M不変データ` を通して同上(このマーカーを直接には見ない) |
| `Mエンティティ` | ライフサイクルを通して維持される同一性を持ち、状態が変化しても同じものとして追跡される型 | 無し | 同一性は識別子の一致で決まる。識別子を機械的に取得できる | 関連型 `識別子: Mエンティティ識別子` と `fn 識別子(&self) -> &Self::識別子` の存在 | 無し |
| `Mエンティティ識別子` | エンティティの同一性を担う識別子。値オブジェクトとして扱う | `M値オブジェクト + Eq + Hash` | 完全な同値とハッシュで同定できる | `Clone`・`PartialEq`・`Eq`・`Hash` | `M不変データ` を通して同上 |
| `M不変エンティティ` | 同一性とライフサイクルを持ち、かつ自己変更を行わない型 | `Mエンティティ + M不変データ` | 両方の上位トレイトの法則 | 両方の上位トレイトの要求 | `M不変データ` を通して同上 |
| `M可変エンティティ` | 同一性を維持したまま内部の状態を更新する設計を意図している型 | `Mエンティティ` | 強い追加の法則を持たない。設計の分類の印である | `Mエンティティ` の要求 | 無し |

`M値オブジェクト` の基底を `Eq` でなく `PartialEq` にするのは、`f32` を含む値オブジェクトでは完全な同値(反射律)が成り立たないことがあるためである。`Eq` が成り立つ値オブジェクトと、浮動小数を含み完全な同値が成り立たない値オブジェクトを、将来別の分類として足してよい。

`Mエンティティ` には `PartialEq` を要求しない。エンティティの同一性は全フィールドの一致ではなく識別子の一致で決まるためである。安易な `derive(PartialEq)` とエンティティの同一性を混同してはならない。例として、`旅行者#42, hp=100` と `旅行者#42, hp=50` は値としては異なるが、同じエンティティである。

### 2.5.3 機械検証の範囲

コンパイラが強制するものは、上位トレイトの `Clone`・`PartialEq`・`Eq`・`Hash` と、`Mエンティティ` の関連型と識別子のメソッドの存在である。

`cargo xtask conform` の設計オントロジーの検査が見るものは、`M不変データ`・`M共有される不変データ` またはデータの役割を実装する型の定義に参照・生ポインタ・内部可変性が無く、共有の指し先(`Arc`・`Rc`・`Weak`)が `M共有される不変データ` を名乗る型を指す `Arc` だけであること(`xtask/src/conform/設計オントロジーの規約検査/共有の指し先の検査.rs`)、`Mコマンド` が列挙で `M規則` が構造体であること、`M命令の組` が構造体でありフィールドの型がどれも `Mコマンド` を名乗ること、`M結果` を実装する型が列挙であること(標準の `Result` は特例。2.6.1)である。存在の分類のマーカーについても、実装の正規形(`impl マーカー名 for 型` または `impl blitz_design::マーカー名 for 型`)・別名の取り込みの禁止・波括弧付きのモジュールの中の実装の禁止・再公開の禁止は検査する(第5節)。純粋データ規約は `M不変データ` を上位トレイトに持つもの(`M値オブジェクト`・`Mエンティティ識別子`・`M不変エンティティ`)だけが `impl M不変データ for` の行を通して対象になり、`Mエンティティ` と `M可変エンティティ` には課さない(`Mエンティティ` は `M不変データ` を要求せず、`M可変エンティティ` は自己変更を意図する分類であるため)。同じ型が `M不変エンティティ` と `M可変エンティティ` の両方を名乗ることは違反にする(型の同一性は定義の位置のモジュール + 型名で突き合わせる。定義の位置のモジュールは次の段落で定める)。

現在 `cargo xtask conform` が `M観測` について直接保証するのは、`M不変データ` に由来する構文の法則(純粋データ規約)である。正本の保持(`M状態` が `M観測` を正本として保持していないか)と因果への逆流(遷移の因果の入力へ観測を戻していないか)は、型と型の関係の解析の対象とする。

次のものは検査しない。エンティティが本当に同一性を持つか。識別子が本当に一意か。`M可変エンティティ` が同一性を保っているか(識別子を書き換えていないか)。private のフィールドを通した間接の変更(自由関数と工程が `&mut 型` を受けてフィールドへ代入する形や、値の置き換え)。これらは意味論または具体ドメインの配線であり、構文の検査では判定できない。

型の定義の探索は、純粋データ規約・`Mコマンド` と `M規則` と `M結果` の型種別・`MParameter` の `Option` の禁止のために行う。型の同一性は、定義の位置のモジュールと型名の組である。定義の位置のモジュールとは、定義のファイルから推定したモジュールパスの下へ、定義の行を囲む波括弧付きのモジュール(`mod 名 { … }`)の名前を外側から繋いだもののことである。検査器は、ファイルが同じことを同じ型の根拠にしない。検査器は、その定義として、実装の位置のモジュールの直下の定義を採り、無ければその位置の `use` の取り込み元のモジュールの直下の定義を採る。検査器は、同じファイルにあっても局所の定義と別の波括弧付きのモジュールの定義を採らない。そうした定義しか無く `use` も無い実装と、局所の位置の実装のファイルに同名の局所の定義がある実装と、実装の位置のモジュールの直下の定義と型名を名乗る `use` を同時に持つ実装は、検査器が定義を一意に決められない違反にする。実装対象の型の `use ... as` の別名も、取り込み元を求められない違反にする。2段以上の再公開の連鎖を通した定義の探索は、保証範囲の外である。入れ子の波括弧の `use`(`use a::{b::{c, d}};`)は、検査器が群を入れ子ごと展開して読む。読み切れない `use` の文(`;` に届かない文・展開しきれない群・別名かパスの最後の名前がマクロのメタ変数を含む文)は取り込み元の候補にしないため、その型名の定義が他に無ければ定義が見つからない違反になる。

**`cargo xtask conform` は、`M不変データ` の自己変更の禁止(受け手と引数に自分の型への可変参照を持たないこと)を検査しない。** 設計解釈マーカーの役目は、型を書く・直すAIに「この型は不変でなければならない」と気づかせることである。設計解釈マーカーを実装した型を書き換える間違いは、そのマーカーを見ている書き手(AIも人も)が犯さない。そのため、その違反を字面から完全に機械で見つける仕組みは要らない。2026-09 に PR #177 でこの検査を作ったが、字句と名前で型の意味を近似する限り言い換えで抜ける形が残り、検査は約100ファイル・約5,600行に膨れた。本書は検査を外し、法則そのもの(自己変更を行わない)は設計の法則として残す。参照: `.claude/skills/設計解釈マーカーの思想/SKILL.md`

**`cargo xtask conform` は、設計解釈マーカーを実装した型の実装を、その型の定義と同じファイルに置くことを警告として求める。** 警告とは、conform が表示するが終了コードを変えない報告のことである。現実に起きうる事故は、AIが設計解釈マーカーを実装した型の `impl` を別のファイルに書き、マーカーを見ないまま型を書き換えることだけである。この規則は、マーカーが目に入らない場所で実装を書こうとしているAIに気づかせるためにある。違反にしないのは、止めたい事故がこれから書かれる実装であり、既存の置き場を今直すことを求めないためである。

調べる範囲は、設計解釈マーカーを実装した型と同じクレートの `src` にある実装の見出しのすべてである。固有の `impl`・トレイトの実装・`unsafe impl`・設計解釈マーカーの実装そのものを含む。検査器は、設計解釈マーカーを実装した型を設計解釈マーカーの実装(`impl マーカー for 型` の1件。どのマーカーの実装かを持つ)の一覧から求め、定義のファイルは型の定義の探索で求める。見出しの対象の型のパスの最後の名前が設計解釈マーカーを実装した型の名前と一致し、見出しが定義のファイルの外にあれば、その見出しの行で、その型が実装した設計解釈マーカーを名指して警告する。名前が付いていない対象(全称の実装 `impl<T> トレイト for T`)は調べず、正本 `blitz_design` が持つ標準の `Result` への `M結果` の包括の実装は設計解釈マーカーを実装した型に数えない。

この規則は型の意味を解析せず、型の名前だけで判定する近似である。同じクレートに同じ名前の別の型があると、その型の実装にも警告が出る。その場合、書き手は警告を無視してよい。警告の文がそのことを書き手へ伝える。逆に、型の別名(`type`)や `use … as` の別名を対象に書いた実装は、名前が一致しないため警告の対象にしない。実装は `xtask/src/conform/設計オントロジーの規約検査/marker_impl_placement.rs` にある。

**`M不変データ` を実装した型は、構築した後に値が変わらない API として書く。** 実装者は、次の3つの区分で書き方の規約を守る。区分は、すべての `M不変データ` の実装が満たす共通の法則、struct の実装が満たす規約、enum の実装が満たす規約である。Rust の `enum` の選択肢が持つデータは言語仕様で公開になるため、フィールドを私有にする規約は struct にしか当てはまらない。

**共通の法則**(`M不変データ` を実装したすべての型が満たす)

1. 実装者は、既存の値をその場で書き換えない。実装者は、値の変更を新しい値を作ることで表す。呼び出し側は、`let mut` の変数へ新しい値を代入し直してよい。
   所有権を受け取って新しい値を返すこと(`fn(self) -> Self` や `M遷移関数` の `fn(状態, ...) -> ...` の形)は、自己変更ではない。関数が受け取るのは呼び出し側の値とは別の値であり、呼び出し側の手元に残る値(`Copy` の型なら呼び出し側が持ち続ける元の値)は書き換わらないためである(2026-09-26 のオーナー裁定)。受け取った値の中身を使って新しい値を組むとき、実装者は複製を作らなくてよい。
   失敗しうる遷移では、実装者は失敗しうる検査を、受け取った状態の中身を動かす前に全部済ませる。失敗のとき遷移は受け取った状態を書き換えずに `遷移失敗結果` へ入れて返す(3.5.9)ため、中身を動かした後で失敗すると、元の状態を返すための複製が要るからである。
2. 実装者は、自己変更を行う API を持たない。典型的には `&mut self` などを受けるメソッドを書かない。ほかにも自己変更を可能にする様々な書き方はあるが、それらも用いない。
3. 実装者は、参照・生ポインタ・内部可変性(`Cell`・`RefCell` 等)を持たない。これは純粋データ規約であり、`cargo xtask conform` が検査する。例外は1つだけであり、`M共有される不変データ` を名乗る型 `T` を指す `Arc<T>` は持ってよい(2026-09-28 のオーナー裁定)。1つの実体を皆で共有して読む大きい値を、複製せずに持つためである。借りる `&T` は認めない(規則が地図より長く生きられず、値として持ち運べなくなるため)。`Rc` と `Weak`、`M共有される不変データ` を名乗らない型を指す `Arc` も認めない。`cargo xtask conform` は `Arc` の中身の型を、その表記を書いた行から型の定義の探索でたどり、たどり着いた型が `M共有される不変データ` を名乗るかで判定する。中身を1つの名前として読めない表記(`Arc<Vec<T>>` など)は違反にする。`Arc` と読むのは修飾の無い `Arc` と `std::sync::Arc`・`alloc::sync::Arc` の3つの表記だけであり、ほかの修飾の `Arc`(`別の::Arc<T>`)は同じ名前の別の型でありうるため違反にする。この3つの表記は設計関係の抽出器が保持する関係を読むときの表記と同じ一覧である(`blitz_design_verification` の `標準の共有の包みの表記か`)。`M共有される不変データ` を名乗る型自身にも同じ規約を当てる。
   検査は定義の行に `Arc`・`Rc`・`Weak` の名前で書かれた指し先を探すため、別名を通した指し先は名前が見えない。そこで `cargo xtask conform` は、純粋データ規約の対象の型を持つクレートで、`Arc`・`Rc`・`Weak` を `use … as` で別名にすること(`use std::rc::Rc as 共有;`)と、それらを右辺に持つ `type` の別名(`type 共有の地図 = Rc<地図>;`)を置くことを違反にする(`xtask/src/conform/設計オントロジーの規約検査/共有の指し先の別名の検査.rs`)。短い名前を付けるつもりで別名を置くだけで、`Rc` を持つ定義が検査を外れるためである。検査が `use` と `type` の文を見分けるときは、頭の属性と可視性(`pub(in パス)`・`pub(self)` を含む)を読み飛ばしてから見分ける。また、検査と抽出器は修飾の無い `Arc` を標準の `Arc` と読むため、同じクレートで次の3つも違反にする(`xtask/src/conform/設計オントロジーの規約検査/標準の外の共有の指し先の名前の検査.rs`)。1つ目は、`Arc`・`Rc`・`Weak` の名前を標準の表記(`Arc` は上の3つ、`Rc` は `std::rc::Rc`・`alloc::rc::Rc`、`Weak` は `std::rc::Weak`・`std::sync::Weak`・`alloc::rc::Weak`・`alloc::sync::Weak`)以外のパスから持ち込む `use`(`use crate::自前::Arc;` と、別名でその名前を付ける `use crate::自前::共有 as Arc;`)である。この `use` の後に書いた修飾の無い `Arc<地図>` は標準でない型を指すのに、検査も抽出器も標準の `Arc` として受け取るためである。2つ目は、その名前を識別子として含むのに読み切れない `use` 文(展開しきれない波括弧の群・マクロのメタ変数を含む文)である。読めない文が持ち込む名前を黙って見逃さないためである。3つ目は、その名前で `struct`・`enum`・`union` を定義することである。一括取り込み(`use crate::自前::*;`)が持ち込む名前は保証範囲の外である。次の2つも検査しない(保証範囲の外)。1つ目は、マーカーの無い型を間に挟んだ指し先(`struct 箱 { 中: Rc<地図> }` を、純粋データの型がフィールドに持つ形)であり、フィールドの型の中に間接的に含まれる内部可変性を見ないのと同じ扱いである。2つ目は、純粋データ規約の対象の型を持たないクレートが置いた別名を、対象のクレートが取り込んで使う形である。
4. 実装者は、`impl` を型の定義と同じファイルに置く。`cargo xtask conform` が警告で検出する。

**struct の規約**(`M不変データ` を実装した struct が満たす)

1. 実装者は、フィールドを私有にする。実装者は、値の読み出しを `&self` を受けるメソッドで提供する。
2. 実装者は、フィールドへの可変参照を外へ返さない。

使い心地の目安は C# の `readonly struct`(構築後にフィールドを書き換えられない構造体)である。ただしこの対応は言語仕様として一致するものではない。C# の `readonly struct` は `readonly` を付けた公開フィールドを持てるが、Rust には公開フィールドを読み取り専用にする言語機能が無いため、実装者はフィールドを私有にすることで同じ使い心地を得る。

**enum の規約**(`M不変データ` を実装した enum が満たす)

1. 実装者は、選択肢で値の種類を表す。
2. 実装者は、データを持つ選択肢について、そのデータを `M不変データ` を満たす型で持つ。例は `旅行者の意図::歩く { 方向: 歩行方向 }` である。`歩行方向` は、私有フィールドを持つ `M不変データ` の型である。
3. 実装者は、enum の値を変えるとき、選択肢のデータをその場で書き換えず、enum の値全体を新しく作る。
4. 選択肢のデータがすでに `M不変データ` の型であれば、実装者はそのデータを別の struct へ切り出す必要は無い。

`cargo xtask conform` は、共通の法則の項目1・2と、struct の規約と、enum の規約を検査しない。共通の法則の項目3・4は検査する(それぞれ本節が既に述べた純粋データ規約と実装の置き場の警告と同じものである)。本書は、任意の Rust のコードを許したまま後からこの使われ方を完全に機械で検証する方式を採らないため、検査しない項目を書き方の規約として実装者に委ねる。実装者がより強い保証を必要とする場合は、属性マクロなどの専用の記法で記述形式そのものを制限し、その範囲を構築的に保証する設計へ切り替えられる。本書はこの案を将来の候補として、issue #180(自己変更の禁止の検査に残る型の意味の穴を、型が何を指すかを特定する層で閉じる。https://github.com/megaDenryu/Blitzdrache0/issues/180)の追記に残してある。

### 2.5.4 設計の方針

Rust では束縛が既定で不変だが、それは言語の性質である。本節が扱っているのは設計の上での変更可能性・同一性・ライフサイクルであり、言語の性質とは別の層として明示する。意味のあるドメインの制約はマーカーとして明示し、できる限り法則を構文の検査(`cargo xtask conform`)で確かめる。

## 2.6 関数境界の役割(必須入力の束と任意の設定の束と評価の排他的な帰結)

関数境界の役割は、入力側の `MParameter` と `MOptions`、出力側の `M結果` を扱う。関数の境界を渡る型を、必須入力の束(`MParameter`)と任意の設定の束(`MOptions`)、評価の排他的な帰結(`M結果`)に分類する。

本書はこの分類を、データの役割と処理の役割(第2節)とも存在の分類とも変更可能性(2.5節)とも別の軸として置く。データの役割は「その型は因果モデルのどこに現れるか」を問い、存在の分類は「その型は同一性を持つか」を問い、変更可能性は「その型は自己変更を行うか」を問うのに対し、関数境界の役割は「その型は関数の境界をどう渡るか」を問う。どの既存の軸の問いにも答えないため、既存の軸の中へ入れない。`MParameter` と `MOptions` はこの軸の排他の分類であり、同じ型が両方を名乗ることを `cargo xtask conform` が違反にする(2.6.1)。`M結果` は排他の組に入らない。

| マーカー | 定義 | 上位トレイト | 課す法則 | `cargo xtask conform` が検査するもの |
|---|---|---|---|---|
| `MParameter` | 関数の実行に必要な必須入力のうち、遷移の役割のコマンドの位置へ入れないものを、名前付きのプロパティとして1つの引数オブジェクトへ束ねた型 | `M不変データ` | 関数へ渡す必須入力の束である。各プロパティは必要だから存在する値である。`Option<T>` をフィールドとして持たない。不変性は `M不変データ` から継承する。`Mコマンド` だけを並べた構造体は `MParameter` でなく `M命令の組` を名乗る | 定義に `Option<` のフィールドが無いこと(2.6.1)。`M命令の組` と同時に名乗らないこと。`M不変データ` を通して純粋データ規約 |
| `MOptions` | 関数呼び出し時に、呼び出し側が任意に指定できる設定を束ねる引数オブジェクト | `M不変データ` | `Option<T>` をフィールドとして持つことを許す。全フィールドが `Option<T>` である必要は無い。`Option<T>` を持つこと自体は成立の条件でない。指定してもしなくても関数の呼び出しが成立する設定を束ねる | `M不変データ` を通して純粋データ規約 |
| `M結果` | ある処理・評価の出力の境界で、その処理が取り得る排他的な帰結を表す判別型。標準の `Result<T, E>` と、意味を持つ独自の `enum` が代表形である | 無し | 構文の法則: 結果は判別型(`Result` または `enum`)であり、`struct` は `M結果` になれない。意味の法則: 関数境界の役割であり、単なる状態の列挙ではない。各選択肢が運ぶ値(`遷移成功結果`・`遷移失敗結果`)そのものは `M結果` ではない | 実装の対象の型が `enum` であること(標準の `Result` は特例)と、実装の正規形・別名の取り込みの禁止・波括弧付きのモジュールの中の実装の禁止・再公開の禁止(2.6.1) |

`M結果` に上位トレイトを付けないのは、`Result<T, E>` の性質が `T` と `E` に依存し、一律に `M不変データ` を課せないためである。純粋データ規約と 自己変更の禁止も `M結果` には課さない。`blitz_design` は `impl<T, E> M結果 for Result<T, E> {}` を持ち、標準の `Result` が `M結果` であることを型で示す。例えば `Result<遷移成功結果, 遷移失敗結果>` で結果を表しているのは外側の判別構造であり、内側の2つの値ではない。

`M結果` の位置づけは、型の形ごとに次のとおりである。

```text
std::Result<T, E>  -> 型自体の標準の意味(成功と失敗の排他的な帰結)により自動で M結果 と解釈する
独自の enum        -> 設計者が M結果 を実装したときだけ M結果 である(enum であるだけでは結果とは限らない)
struct             -> M結果 にはなれない(結果の値を束ねた struct は排他的な帰結そのものではない)
```

`M結果` の構文の法則は「結果は判別型である」ことであり、`cargo xtask conform` が機械で閉じる(2.6.1)。

`M結果` の意味の法則は「`M結果` は関数境界の役割であり、単なる状態の列挙ではない」ことである。判別型であるだけでは `M結果` ではない。

```rust
enum 接地状態 { 接地, 空中 }              // 判別型だが処理の帰結ではないため M結果 ではない
enum 接地判定結果 { 接地(...), 非接地, 評価不能(...) }  // 評価の排他的な帰結であるため M結果 になり得る
```

意味の法則は `cargo xtask conform` で完全には判定しない。`enum` が処理の帰結を表しているかは意味論であり、構文の検査では判定できないためである。

値が無い状態がドメイン上の必須入力なら、実装者は `Option<T>` を置かずに、その意味を表す専用の型か列挙へ持ち上げる。`MOptions` はブラウザの DOM API などにある options object に近い概念として扱う。Esca第1段階では `遷移パラメータ`(3.5.1)が `MParameter` を実装し、`MOptions` を実装する型はまだ無い。

`MParameter` を名乗る型には、意味の決まった値(`Mコマンド`・`M状態`・`M規則` など)を関数へ渡す1つの引数へまとめた型も入る(2026-09-27 のオーナー裁定。第2節)。ただし、`Mコマンド` を名乗る型だけを並べた構造体は、`MParameter` でなく `M命令の組` を名乗る(第2節。2026-09-28 の命令の組の裁定)。付け分けは定義から決まる。`MParameter` は遷移の役割のコマンドの位置へ入れない引数であり、`M命令の組` はそのコマンドの位置へ入れる命令であるため、2つは排他である。フィールドがどれも `Mコマンド` なら `M命令の組` であり、`Mコマンド` でない値を1つでも含むなら `MParameter` である。`cargo xtask conform` は、同じ型が2つを同時に名乗ることを違反にする。Esca の例は `区域の指定`・`区域の中の移動の指定`・`閉じている時間帯の指定`・`経路の開閉の状態の指定` である。

### 2.6.1 機械検証の範囲

`cargo xtask conform` は、`MParameter` を実装する型の定義ブロック(コメントと文字列を落としたコードだけの行)に `Option<` の文字列があれば違反にする。検査は文字列の照合であり、型の別名を通した `Option`(`type 任意の値 = Option<u8>` を経由する形)と、フィールドの型である別の構造体に埋めた `Option` は見ない(`Vec<Option<u8>>` のように定義の行に `Option<` が現れる入れ子は見つかる)。`MOptions` には課さない。同じ型が `MParameter` と `MOptions` の両方を名乗ることと、`MParameter` と `M命令の組` の両方を名乗ることは違反にする(型の同一性は推定したモジュールパス + 型名で突き合わせる)。さらに、`MParameter` を名乗る構造体の名前付きのフィールドがどれも `Mコマンド` を名乗る型であれば違反にする(`xtask/src/conform/設計オントロジーの規約検査/コマンドだけを並べた引数オブジェクトの検査.rs`)。その形の型は定義により `M命令の組` であり、2026-09-28 に Esca の `経路の開閉と旅行者の歩行の更新への入力` がこの形のまま `MParameter` を名乗る取り違えが実際に起きたためである。フィールドの読み方は `M命令の組` の検査と同じもの(`構造体のフィールドの読み取り.rs`)を使い、フィールドを読めない型とフィールドを持たない型は違反にしない。`M命令の組` もあわせて名乗る型は、排他の検査だけが報告する。実装の正規形・別名の取り込みの禁止・波括弧付きのモジュールの中の実装の禁止・再公開の禁止(第5節)は、この2つのマーカーにも `M結果` にも `M工程` にも掛かる。

`M結果` については、実装の対象の型が `enum` であること(構文の法則)を検査する。`impl M結果 for X` の `X` の定義をたどり、たどり着いた定義が `enum` でなければ違反にする。標準の `Result` への `M結果` の実装は `crates/blitz_design/src/設計解釈マーカー.rs` の完全に修飾した包括の実装 `impl<T, E> M結果 for std::result::Result<T, E> {}` の1箇所だけであり(他のクレートが標準の `Result` へ改めて実装することは coherence 上もできない)、そこだけが定義をたどらない特例である(`xtask/src/conform/設計オントロジーの規約検査/trait_implementation.rs` の `設計解釈マーカーの実装::正本の標準resultへの包括の実装か`。実装の行が正本のファイルにあることと、対象の型の表記が `std::result::Result` で始まることで判定する)。他の `impl M結果 for X` は、`X` の名前に関わらず、また正本のファイルにあっても定義をたどるため、`Result` という名前の独自の `struct` は正本のファイルに置いても違反になり、`Result` という名前の独自の `enum` は明示的に `M結果` を実装すれば許される。`M結果` には純粋データ規約と 自己変更の禁止を課さない(`M不変データ` を上位トレイトに要求しないため。`純粋データの役割一覧` に入れない)。

## 3. 関数の役割

関数の役割とは、関数が設計上何の計算であるかを、その関数を包む境界付きの newtype で宣言したもののことである。`blitz_design` は10の関数の役割を持つ。

- `M射影関数<状態: M状態, 射影DTO: M不変データ>` は `fn(&状態) -> 射影DTO` を包み、状態から外部向けの表示データを取り出す一方向の観測の計算である。
- `M解釈関数<入力: M解釈前の入力, コマンド: Mコマンド>` は `fn(&入力) -> コマンド` を包み、ゲームの意味を持たない入力から主体のコマンドを導く純粋な解釈の計算である。
- `M遷移関数<状態: M状態, コマンド: M遷移が受け取る命令, 規則: M規則, パラメータ: MParameter, イベント: Mイベント, 失敗: std::error::Error>` は `fn(状態, &コマンド, &規則, パラメータ) -> Result<遷移成功結果<状態, イベント>, 遷移失敗結果<状態, 失敗>>` を包み、状態とコマンドと規則と遷移パラメータ(3.5.1)から次の状態と出来事を導く純粋計算である。失敗しない遷移は `失敗` へ `std::convert::Infallible` を置く。
- `M遷移が受け取る命令で決まる遷移関数<状態: M状態, コマンド: M遷移が受け取る命令>` は `fn(状態, &コマンド) -> 状態` を包み、次の状態が今の状態と遷移が受け取る命令(`Mコマンド` か `M命令の組`)だけで決まる遷移である。旧称は `Mコマンドで決まる遷移関数` であり、2026-09-28 にコマンドの位置の境界が `M遷移が受け取る命令` へ広がったため改めた。規則を読まず、出来事を出さず、失敗しない。
- `M規則で決まる遷移関数<状態: M状態, 規則: M規則>` は `fn(状態, &規則) -> 状態` を包み、次の状態が今の状態と規則だけで決まる遷移である。コマンドを受けず、出来事を出さず、失敗しない。
- `M規則と遷移パラメータで決まる遷移関数<状態: M状態, 規則: M規則, パラメータ: MParameter>` は `fn(状態, &規則, パラメータ) -> 状態` を包み、次の状態が今の状態と規則と遷移パラメータだけで決まる遷移である。コマンドを受けず、出来事を出さず、失敗しない(2026-09-28。状態を受けて返す処理の宣言の法則を足したときに、目的地への到達の判定を宣言するために足した)。
- `M問い合わせを伴う遷移関数<状態: M状態, コマンド: M遷移が受け取る命令, 規則: M規則, パラメータ: MParameter, 問い合わせ先: ?Sized, 観測: M観測, 失敗: std::error::Error>` は `fn(状態, &コマンド, &規則, パラメータ, &mut 問い合わせ先) -> Result<問い合わせを伴う遷移成功結果<状態, 観測>, 遷移失敗結果<状態, 失敗>>` を包み、問い合わせ先へ問いながら次の状態と観測を導く遷移である。
- `M規則で決まる問い合わせを伴う遷移関数<状態: M状態, 規則: M規則, パラメータ: MParameter, 問い合わせ先: ?Sized, 観測: M観測, 失敗: std::error::Error>` は `fn(状態, &規則, パラメータ, &mut 問い合わせ先) -> Result<問い合わせを伴う遷移成功結果<状態, 観測>, 遷移失敗結果<状態, 失敗>>` を包み、コマンドを受けずに問い合わせ先へ問いながら次の状態と観測を導く遷移である。
- `M問い合わせを伴う評価関数<規則: M規則, パラメータ: MParameter, 問い合わせ先: ?Sized, 結果: M不変データ, 失敗: std::error::Error>` は `fn(&規則, パラメータ, &mut 問い合わせ先) -> Result<結果, 失敗>` を包み、状態を持たずに、問い合わせ先へ問いながら1つの結果を導く評価である。いま使う箇所は無いが、状態を持たずに世界へ問い合わせて1つの結果を導く関数のために残す。
- `M規則によらない書き換え関数<状態: M状態, 材料>` は `fn(状態, 材料) -> 状態` を包み、ゲームの規則を通さずに、シミュレーションの外から来た材料で状態の一部を外から書き換える関数である(2026-09-28 のオーナー裁定)。出来事を出さず、失敗しない。材料は、`M遷移が受け取る命令`・`M規則`・`MParameter` を名乗らない、外から来た値である。材料の型に設計解釈マーカーの境界を置かないのは、材料が単位の型(`blitz_math` の `大域メートル` など)のように設計語彙に依存しないクレートの型で運ばれることがあり、孤児規則のためにその型へマーカーを実装できないためである。

コマンドの位置を持つ3つの遷移の役割は、コマンドの位置の型引数を `M遷移が受け取る命令` の境界で受け取り、1つの選択(`Mコマンド`)も、同じ刻みに届いた命令の全体(`M命令の組`)も入れられる(第2節。2026-09-28 のオーナー裁定)。Esca の歩行と経路の開閉のように命令を1つだけ受ける遷移は、`Mコマンド` の型をそのまま入れる。2つを1刻みに進める Esca の `経路の開閉と旅行者の歩行の状態::経路の開閉と旅行者の歩行を1回更新する` は、開閉の命令と旅行者の意図を並べた `M命令の組`(`経路の開閉と旅行者の歩行の更新への入力`)を入れる(`crates/blitz_esca/src/経路の開閉と旅行者の歩行/状態.rs`)。

**遷移の形と役割の対応。** 遷移を宣言するとき、書き手は、関数が何を受けて何を返すかの形から役割を1つ選ぶ。次の表がその対応の全部である。どの遷移も状態を値で受け取り、次の状態を返す。

| 遷移の形 | 役割 | 実例 |
|---|---|---|
| コマンドと規則と遷移パラメータを受け、出来事を出し、失敗しうる | `M遷移関数` | Esca の歩行・経路の開閉・経路の開閉と旅行者の歩行 |
| 遷移が受け取る命令(コマンドか命令の組)だけを受け、出来事を出さず、失敗しない | `M遷移が受け取る命令で決まる遷移関数` | 進行段階の遷移 |
| 規則だけを受け、出来事を出さず、失敗しない | `M規則で決まる遷移関数` | 目的地への到達を判定して場所巡りの進行を進めた場所巡りのゲームの状態 |
| 規則と遷移パラメータを受け(コマンドを受けない)、出来事を出さず、失敗しない | `M規則と遷移パラメータで決まる遷移関数` | 目的地への到達の判定(`場所巡りの進行`。道順が規則、プレイヤーの大域位置が遷移パラメータ) |
| コマンドと規則と遷移パラメータを受け、問い合わせ先へ問い、観測を返し、問い合わせ先の失敗で失敗しうる | `M問い合わせを伴う遷移関数` | プレイヤーの胴体の移動 |
| 規則と遷移パラメータを受け(コマンドを受けない)、問い合わせ先へ問い、観測を返し、問い合わせ先の失敗で失敗しうる | `M規則で決まる問い合わせを伴う遷移関数` | 前の描画の表示距離(カメラの遮蔽の判定) |

失敗しうる3つの遷移は、失敗のとき受け取った状態を `遷移失敗結果` の `元の状態` に入れて返し、呼び出し側はそれを受け取り直して維持する(3.5.9)。

**規則によらない書き換え。** 高さ場アセットを据えたり差し替えたりしたことによる状態の据え直しは、シミュレーションの外からの介入であり、ゲームの規則の遷移ではない。書き手は、この関数を `M規則によらない書き換え関数` で宣言する(2026-09-28 のオーナー裁定。それまでは関数の役割を宣言しないとしていた)。実例は `blitz_game` の `場所巡りのゲームの状態::足元の地面の高さを反映した状態を返す` と `歩くだけのゲームの状態::足元の地面の高さを反映した状態を返す`(材料は `M結果` の `足元の地面の高さ`)と、その内側で呼ぶ `プレイヤーの状態::天頂成分を据え直した状態を返す`(材料は `大域メートル`)である。遷移と別の役割に分けるのは、規則によらない書き換えが状態の存在理由(規則で進むこと)にならないためである。定義の式はこの役割から状態を `書き換える` 関係を導き、状態を `消費する`・`生成する` 関係を導かない(6.5節)。そのため書き換えだけを持つ状態は、状態の存在理由の公理 A3 を満たさない。状態を受けて同じ状態を返す関数は、遷移の役割か規則によらない書き換えの役割のどちらかを宣言する(第8節の法則 A7)。

型エイリアスに書いた境界は Rust の仕様上強制されない(rust-lang/rust#112792)。そのため関数の役割は型エイリアスでなく、関数ポインタを包む構造体(newtype)であり、型引数の境界を構造体の宣言に書く。構造体の境界は利用箇所でコンパイラが強制するため、型を使った時点で型引数の境界が掛かる。迂回できる書き方は無い(`blitz_design::M射影関数<...>` と修飾しても、`use ... as` で別名を付けても、`let` で受けても、型を使った時点で境界が掛かる)。各 newtype は `生成する(関数)` で関数を包み、`呼び出す(..)` で包んだ関数を適用する。利用側は `const _: M射影関数<A, B> = M射影関数::生成する(関数);` の静的宣言で、関数が役割を満たすことをコンパイラに確かめさせる。この1行を関数の役割の宣言と呼ぶ。

射影と解釈が状態や入力を参照で読むのと違い、遷移は状態を値で受け取る(所有権を移す)。遷移が古い状態を参照で読むことしかできないと、1か所しか変わらない遷移でも状態の大きさに比例した費用(状態が集まりを持てば、その丸ごとの複製)が毎回かかるためである(2026-09-26 のオーナー裁定)。所有権を受け取って新しい値を返すことは自己変更ではない(2.5.3)。`遷移成功結果` は型引数に `M状態`・`Mイベント` の境界を持つ意味型であり、`遷移失敗結果` は型引数に `M状態`・`std::error::Error` の境界を持つ意味型である(3.5.9)。どちらも汎用の入れ物ではない。構造体に書いた境界は利用箇所でコンパイラが強制するため、`遷移成功結果<String, usize>` のような値は作れない。

`M遷移関数` と2つの意味型は、はじめ計算モデルまで固定する型として Esca 側(`blitz_esca`)で形を確かめ、遷移パラメータを Esca の具体の型へ固定していた。2026-09-27 のオーナー裁定(Issue #175)で、遷移パラメータを型引数へ一般化して `blitz_design` へ移した。`blitz_game` の遷移も同じ語彙で宣言し、関数の役割の宣言の漏れを構造の法則(第8節の公理)で見つけるためである。

**形を縮めた遷移の3つの役割を別に置く理由。** `blitz_game` の遷移には、規則を読まない遷移(進行段階が進行の操作だけで決まる)と、コマンドを受けない遷移(目的地への到達を道順と位置で判定する)があり、どちらも出来事を出さず失敗しない。これを `M遷移関数` の形へ押し込むと、読まない規則・受けないパラメータ・起こりえない出来事を表す意味の無い型を関数の署名と設計関係グラフへ持ち込み、その型自身が公理(第8節)の対象になる。呼び出し側は起こりえない失敗を毎回ほどくことにもなる。そこで、次の状態がどの入力だけで決まるかを役割の名前で言い、関数は次の状態をそのまま返す。規則と遷移パラメータで決まる役割(`M規則と遷移パラメータで決まる遷移関数`)も置くのは、遷移パラメータを受けるだけの遷移を `M遷移関数` で宣言すると、受けないコマンドと起こりえない出来事を表す意味の無い型を持ち込むためである。出来事を出す遷移・失敗しうる遷移は `M遷移関数` で宣言する。

**問い合わせを伴う3つの役割を別に置く理由。** 問い合わせ先とは、関数が計算の途中で問いを渡して答えを受け取る相手(`blitz_game` の世界の形を尋ねる口など)のことである。問い合わせ先は純粋な所有データでなく、答えるたびに作業領域を使い回すため可変参照で借りる。そのため、入力を全部値で受け取る `M遷移関数` の純粋計算にならない。答えが問い合わせ先に依存することを役割の名前で言うため、別の役割として置く。問い合わせ先の型を `?Sized` にするのは、問い合わせ先を型引数に取るジェネリックな関数を関数ポインタへ写すとき具体の型が1つ要り、ドメインのクレートの中で名指せる具体の問い合わせ先がトレイトのオブジェクト(`dyn 世界の形を尋ねる口<問い合わせエラー = std::convert::Infallible>`)だけであるためである。`blitz_game` はこのオブジェクトに別名 `口の実装を代表する口` を、その失敗の型 `Infallible` に別名 `口の実装が決める失敗の代表` を付けて宣言に書く(`crates/blitz_game/src/世界の形.rs`)。宣言が実際の失敗の型を書けないのは、実際の失敗の型を口の実装が決め(コンポジションルートの口では `blitz_app` の `世界の形を尋ねる口の実装エラー`)、ゲームロジック層の中からは名指せないためである。`Infallible` のまま書くと、宣言を読む者が関数は失敗しないと読むため、代表であることを名前で言う。この代表の具体化は実際の問い合わせ先と失敗の型を名指さないため、定義の式は問い合わせ先と失敗の位置から関係を導かない(6.5節)。コマンドは遷移パラメータへ入れず、コマンドの位置で受け取る(3.5.1 の遷移パラメータの定義による)。`blitz_game` の胴体の移動は、水平移動の操作とジャンプの操作の2つの `Mコマンド` をフィールドに並べた `M命令の組`(`胴体の移動の命令の組`)をコマンドの位置で受け取る(`crates/blitz_game/src/操作意図の命令/胴体の移動.rs`。2026-09-28 のオーナー裁定。第2節)。

## 3.5 状態遷移の理論(因果モデル)

本節は、状態遷移の理論を定める。この理論は、第2節の設計解釈マーカーと第3節の関数の役割が、個別に便利なトレイトの集まりではなく、ゲーム世界の因果関係を記述するための一組の設計語彙であることの根拠である。

### 3.5.1 基本形

本書は、状態遷移の基本形を次の図で表す。

```text
                  規則
                   │
                   ▼
現在の状態 ──┐
             ├─ 状態遷移(遷移を評価) ─┬─ 成功 ──→ 次の状態
コマンド ────┘                        │            │
                                      │            └─→ 起きた出来事
                                      │                   │
                                      │                   ▼
                                      │                イベント
                                      └─ 失敗 ──→ 失敗(次の状態も出来事も無い)
```

遷移の型は次である。

```text
遷移 : 状態 × コマンド × 規則
      -> 成功(遷移成功結果) | 失敗
```

一般形は次である。

```text
遷移 : 状態 × コマンド × 規則 × 遷移パラメータ
      -> 成功(遷移成功結果) | 失敗(遷移失敗結果)
```

遷移パラメータとは、遷移関数の実行に必要な、状態でもコマンドでも規則でもない必須の入力(経過時間・乱数源から確定した値・世界時刻・刻みの情報など)を、名前付きのプロパティとして1つの引数オブジェクトへ束ねた型のことである。`MParameter`(2.6節)を実装する。この型は遷移関数の実行に必要な引数を1つのオブジェクトへ束ねたものであるため、名前を `遷移パラメータ` とする。Esca第1段階では遷移パラメータは `経過時間` だけを持ち、第2段階で刻みの始まりの世界の時刻を足した(`crates/blitz_esca/src/transition_parameter.rs`。1回の遷移は、刻みの始まりの時刻を含み経過時間だけ進んだ時点を含まない区間を覆う)。実装の `M遷移関数` は遷移パラメータの型を型引数 `パラメータ`(`MParameter` の境界)に取り、`(状態, &コマンド, &規則, パラメータ) -> Result<遷移成功結果, 遷移失敗結果>` であり、状態を値で受け取る(第3節)。どの入力を遷移パラメータに含めるかはドメインごとに決め、ドメインはその型を型引数へ入れる(Esca は `遷移パラメータ`)。3.5の基本形の図は遷移パラメータを省略した概念図である。

遷移は成功と失敗の2つの選択肢を持つ。成功は遷移成功結果(次の状態 + その評価で成立した事実)であり、失敗は有効な次の状態を構築できなかったことを、受け取った状態と組にした遷移失敗結果である(3.5.9)。失敗を型で返すかは各ドメインが決め、Esca は `Result` で返す。

この文書と実装は、図の「起きた出来事」を `出来事一覧` という名前で呼ぶ。`遷移成功結果` は第4.1節が定義する `遷移成功結果<状態, イベント>` であり、フィールド名は `次の状態` と `出来事一覧` である。

### 3.5.2 4概念の意味

状態・コマンド・規則・イベントの4概念は、それぞれ次の意味と時制を持つ。

| 概念 | 何を表すか | 時制 |
|---|---|---|
| 状態 | 今どうなっているか | 現在 |
| コマンド | 何をしようとしているか | 未来への要求 |
| 規則 | 何が起きてよいか、どう変わるか | 不変の法則 |
| イベント | 実際に何が起きたか | 過去の事実 |

規則の「不変」とは、1回の遷移の評価のあいだ読み取り専用の入力であることである。規則の「不変」は、プログラムの全期間で同じ値であることを意味しない(速度の強化や難易度の変更で規則の値が変わることを妨げない)。

別の仕組みが持つ状態から刻みごとに作った、読み取り専用の値は、その遷移の規則(`M規則`)の一部として渡してよい(2026-09-26 のオーナー裁定)。規則の「変わらない」は1回の遷移の評価のあいだ読み取り専用であることを指すため、刻みごとに作り直した値もこの条件を満たす。一方、この値を `M観測` として渡してはならない。`M観測` は観測の対象の因果の入力へ戻してはならないためである(第2節)。実例は Esca の歩行の規則(`歩行遷移の規則`)であり、どの通り口がいま通れるかを決める経路の開閉の状態を、地図の区域と一緒に空間制約(`区域の空間制約`)として持つ(`_doc/設計/Esca/設計正本.md` 5節)。経路の開閉と旅行者の歩行の遷移は、この規則を刻みごとに組み、関数の役割を宣言した歩行の遷移 `旅行者の居場所::歩行を遷移する` を呼ぶ。刻みごとに組んでも複製は増えない。地図は `M共有される不変データ` であり、規則は `Arc` で共有して持つため、組むとき `Arc` の数が1つ増えるだけである(第2節)。開閉の状態は規則へ値で移し、歩行の後に規則から取り出して(`歩行遷移の規則::開閉の状態を取り出す`)次の状態へ戻す。この形は、開閉の状態を複製せずに歩行の規則へ入れるためのものである。規則は歩行の遷移のあいだ読み取り専用で渡され(遷移は `&歩行遷移の規則` を受け取る)、遷移の外で所有権ごと移して取り戻すだけであるため、本節の「規則は1回の評価のあいだ読み取り専用」は守られている。規則が状態を運んで返しても、遷移の評価の中で規則を書き換える口は無い。

### 3.5.3 Escaの旅行者での例

Escaの旅行者の場合は、次の関係になる。

```text
状態
  現在地 = (10m, 20m)
  行動状態 = 静止中

コマンド
  東へ歩く

規則
  歩行速度 = 3m/s
  東側に壁がある

        ↓ 遷移

次の状態
  現在地 = (11m, 20m)
  行動状態 = 歩行中

イベント
  歩行を開始した
  壁に接触した
```

この例が持つ `行動状態` は、現在の `blitz_esca` の状態には無い。`歩行を開始した` や `立ち止まった` を出来事として持つには、前の状態と次の状態の行動の差を判定できる `行動状態` が状態側に要る。現状の `blitz_esca` はこの `行動状態` を持たないため、`歩行を開始した` や `立ち止まった` を出来事として生成していない(参照: `_doc/設計/Esca/設計正本.md` 4.4 条5)。

### 3.5.4 イベントは状態変更の命令ではない

イベントは状態変更の命令ではない。イベントは、遷移の評価で成立した事実である。向きは次である。

```text
前状態 + コマンド + 規則
        ↓
     遷移を評価
        ├─ 失敗 → 失敗の値だけ(次状態も事実も無い。3.5.9)
        ↓ 成功
次状態 + その評価で成立した事実
        ↓
   イベントとして公開する
```

成立する事実は、状態が変化したことを必要としない。現行の `blitz_esca` では `旅行者の意図::見回す` の遷移が次の状態を前の状態と同じまま返し、`旅行者の出来事::周囲を観察した` を出来事一覧へ入れる。状態は変わらないが、観察したという事実は遷移の評価で成立している。

そのうち、`歩行を開始した`・`立ち止まった`・HPが0になった・扉が開いた のような状態変化イベントだけが、前状態と次状態の差分を根拠にする。状態変化イベントは、前状態と次状態の差を表現できることが生成条件である(4.4 の法則E2)。

### 3.5.5 イベントシステムの定義

イベントシステムとは、ある状態遷移で成立した事実を、その事実を必要とする別の系へ伝播させる仕組みのことである。伝播先の例は次である。

```text
                     ┌→ 音響
                     │    「歩行を開始した」
                     │       → 足音開始
                     │
状態遷移 → イベント ├→ アニメーション
                     │       → 歩行アニメ開始
                     │
                     ├→ クエスト
                     │       → 「初めて歩いた」を記録
                     │
                     └→ AI
                             → 近くの敵が音に反応
```

### 3.5.6 状態遷移系とイベント伝播系の二層

この理論は、少なくとも次の二層を分ける。

```text
【状態遷移系】

M状態
Mコマンド
M規則
Mイベント
M遷移

        ↓ イベントを生成

【イベント伝播系】

Mイベント発行
Mイベント購読
Mイベント反応
Mイベント配送
```

状態遷移系とは、`M状態`・`Mコマンド`・`M規則`・`Mイベント`・遷移関数からなる、状態を遷移させて起きた事実を生成する側の層のことである。イベント伝播系とは、状態遷移系が生成したイベントを、それを必要とする別の系へ伝播させる側の層のことである。イベント伝播系が持つ発行・購読・反応・配送の4語は、現在の `blitz_design` にはまだ無い候補である。

### 3.5.7 イベント反応

イベント反応とは、イベントを受けて、コマンド・外部作用・別のイベント・何もしない のいずれかを返す工程のことである。イベント反応は次の型を持つ。

```text
イベント反応:
    イベント
        -> コマンド
        | 外部作用
        | 別イベント
        | 何もしない
```

例は次の2つである。

```text
敵を倒した
   ↓
クエストシステムが観測
   ↓
「報酬を付与する」というコマンドを生成
```

```text
敵を倒した
   ↓
音響システムが観測
   ↓
SEを鳴らす
```

この整理は、`Mイベント` がイベントシステム全体を表す型ではなく、状態遷移系とイベント伝播系をつなぐ「起きた事実」を表すマーカーであることを示す。

### 3.5.8 全体の因果モデル

全体の因果関係は次のモデルで表す。

```text
意図
 ↓
コマンド
 ↓
状態 + 規則
 ↓
状態遷移 ─ 失敗 → 失敗の値(新しい状態も起きた事実も無い。3.5.9)
 ↓ 成功
新しい状態
 +
起きた事実
 ↓
イベント
 ↓
別の系の反応
 ↓
新しいコマンド / 外部作用 / 別イベント / 出来事の保存(ログ・リプレイ・監査履歴など)
```

`M状態`・`Mコマンド`・`M規則`・`Mイベント` は、個別の便利なトレイトではなく、ゲーム世界の因果関係を記述するための一組の設計語彙である。

### 3.5.9 遷移失敗結果

遷移失敗結果とは、与えられた状態・コマンド・規則・遷移パラメータから、有効な次の状態を構築できなかったことを表す失敗側の値のことであり、遷移が受け取った状態(元の状態)と、具体の失敗(失敗の理由)の組である。遷移の評価は成功と失敗の2つの選択肢を持つ。成功側の値を遷移成功結果(次の状態 + その評価で成立した事実)と呼び、失敗側の値を遷移失敗結果と呼ぶ。外側の `Result` が成功と失敗の分岐そのものを表すため、内側の成功側だけを「遷移結果」と呼ぶと `Result` 全体と意味が競合する。そのため成功側と失敗側を対称に名付ける。

```text
遷移
├─ 成功 → 遷移成功結果
│          ├─ 次の状態
│          └─ 出来事一覧
└─ 失敗 → 遷移失敗結果
           ├─ 元の状態
           └─ 失敗の理由
```

実装は `遷移失敗結果<状態: M状態, 失敗: std::error::Error>` という構造体であり、フィールドは `元の状態` と `失敗の理由` である。問い合わせを伴う2つの遷移(`M問い合わせを伴う遷移関数`・`M規則で決まる問い合わせを伴う遷移関数`)も失敗側にこの型を使い、問い合わせ先の失敗を `失敗の理由` にする。実装の `M遷移関数` の型引数 `失敗` の名前は変えない。型引数は具体の失敗の型を各ドメインが決めるための穴であり、そこへ入る型が `失敗の理由` の型になる。

遷移は状態を値で受け取る(第3節)。そのため、失敗のとき状態を呼び出し側へ戻す口が要り、遷移失敗結果がその口である。遷移は受け取った状態を書き換えずに `元の状態` へ入れて返す。

- 失敗のとき、次の状態は採用されない。呼び出し側は元の状態を維持する。本書はこの法則を、呼び出し側が `遷移失敗結果.元の状態` を受け取り直す形で守る。状態の所有権は遷移へ移っており(`Copy` でない状態の場合)、失敗のとき呼び出し側の手元に状態を戻すのはこの値だけである。
- 型が保証するのは、`遷移失敗結果` の中に状態の型の値が1つあること(状態を返す口があること)までである。`元の状態` へ入れた値が遷移の受け取った値と等しいことは型では保証されない。遷移の実装が書き換えた状態を入れても型検査は通るため、この等しさは検証で確かめる。有限全数の検証(第10節)は、探索したすべての失敗した遷移について `元の状態` が受け取った状態と等しいことを確かめ、食い違えば検証の失敗として報告する。実装では、領域(有限に数え上げられる領域)は遷移失敗結果の `元の状態` をそのまま遷移の帰結の失敗へ入れ、等しさを自分では確かめない。探索(`領域から遷移モデルを組む`)が失敗した遷移ごとに帰結の元の状態と遷移の受け取った状態を比べ、1件でも食い違えば遷移モデルを返さず、食い違った遷移を並べた `遷移失敗結果の元の状態の食い違い` を返す。契約を破った遷移関数から組んだモデルで命題に答えると、答えの根拠が壊れるためである。食い違いを数え上げの網羅性へ混ぜないのは、網羅性が見た範囲の限りを言う語であり、遷移関数が契約を破ったことは見た範囲の問題ではないためである(`crates/blitz_design_verification/src/domain/exploration/元の状態の食い違い.rs`)。
- 失敗のとき、出来事は1件も生じない。遷移が成立していないため、成立した事実も無い。
- 「遷移に失敗した」は `Mイベント` ではない。`Mイベント` はその遷移によって実際に成立した事実であり、失敗は事実の不成立である。失敗を別の系へ伝えるなら、呼び出し側が失敗の値を見て自分の語彙で表す。
- **遷移失敗結果として値で返すのは、回復できる失敗だけである**(2026-09-28 のオーナー裁定)。回復できる失敗とは、正しく組んだ状態・命令・規則からもゲームの規則として起こりうる失敗のことである。壊れた状態や、別の地図の命令を渡したときのような、プログラムの誤りでしか起きない状態は、遷移失敗結果にせず `panic!` にし、メッセージに破られた不変条件を書く(CLAUDE.md「エラー・パニック」)。回復できる失敗を持たない遷移は、失敗の型へ `std::convert::Infallible` を置く(第3節)。外から来たデータ(ステージを作る人が書いた地図・時間帯・状態の指定など)を検証して値を作る口は、遷移ではなく、回復できる入力の誤りを型付きのエラーで返す。
- 法則E1からE8(4.4)は、成功した遷移だけを対象とする。
- Esca の3つの遷移(歩行・経路の開閉・経路の開閉と旅行者の歩行)は、回復できる失敗を持たないため失敗の型へ `std::convert::Infallible` を置く。次の現在地の座標が有限な数でなくなること、地図に無い経路を指す命令や状態、地図に無い地点や自分の区域の外にいる居場所は、プログラムの誤りとして遷移を停止させる(`crates/blitz_esca/src/居場所.rs`・`crates/blitz_esca/src/地点と経路/開閉の状態.rs`)。そのため、経路の開閉と旅行者の歩行の遷移は、片方の遷移が進まなかったことを出来事にしない。実装の `M遷移関数` は失敗の理由を `std::error::Error` の型引数で受け、`Result<遷移成功結果<状態, イベント>, 遷移失敗結果<状態, 失敗>>` で返す。
- 状態を値で受け取る遷移は、同じ状態から何度も遷移を試す側(有限全数の検証。第10節)に複製を求める。本書は、複製するのを検証の側だけにする。検証は、たどった状態を覚えておくため、遷移を呼ぶ前に複製を残す。本番の遷移の呼び出しは状態を複製しない。

## 4. Update型のEventの語彙とコード文法

第4節は、第3.5節の理論の、Event側の語彙とコード文法である。

Observer / callback 型の Event と、`Mイベント` は別概念として語彙を分離する。Observer 系の `Event`・`Subscriber`・`Listener`・`Handler`・`Subscribe`・`Unsubscribe`・`Invoke` は「呼び出し機構」の語彙である。`Mイベント` はそうではなく、Update / 遷移が生成する過去の事実データである。したがって本書は、こちらにも「何を何と呼び、コードをどう書くか」という独自の文法を定める。

### 4.1 基本語彙

**`Mイベント` / 出来事**とは、ある遷移によって実際に成立した過去の事実を表す値のことである。

```rust
pub trait Mイベント: M不変データ {}
```

Event 自身は誰かを呼び出さない。Event はコールバック一覧、`invoke()`、購読者を持たない。`struct` と `enum` のどちらでもよい。次の2つはどちらも正当な `Mイベント` である。

```rust
pub enum 旅行者の出来事 {
    歩行を開始した,
    立ち止まった,
    障害物に遮られた,
}
```

```rust
pub struct ダメージを受けた {
    pub 対象: 個体ID,
    pub 量: ダメージ量,
}
```

**`遷移成功結果<状態, イベント>`**とは、Update / 遷移が返す、次の状態と、その遷移で成立した出来事の組のことである。この型は状態と出来事を混ぜない境界である。

```rust
pub struct 遷移成功結果<状態, イベント> {
    pub 次の状態: 状態,
    pub 出来事一覧: Vec<イベント>,
}
```

**出来事の生成**とは、遷移の計算中に、実際に成立した事実を `出来事一覧` へ追加することである。出来事の生成は Observer 系の `invoke` に相当する語ではない。

- 良い語: `出来事を生成する`、`出来事一覧へ加える`、`〜が成立した`
- 避ける語: `invoke`、`fire`、`通知を呼ぶ`

`emit` を日本語へ持ち込む場合も、書き手はそれを「コールバックを呼ぶ」意味ではなく「出来事値を出力する」の意味に限定する。

**出来事の配送**とは、既に生成済みの出来事値を、0個以上の消費側へ渡す工程のことである。配送は新しい事実を作らない。配送は既存の事実を読者へ渡すだけである。

```text
遷移成功結果.出来事一覧
        │
        ├─→ 音響への解釈
        ├─→ 演出への解釈
        ├─→ 進行への解釈
        └─→ ログ
```

**出来事の解釈**とは、出来事を、別のドメインや外部システムが理解する型へ純粋変換することである。

```text
旅行者の出来事
    → 音響要求
    → 演出要求
    → 別ドメインのコマンド
```

基本形は `fn (&イベント) -> 出力` であり、0件以上を返すなら `fn (&イベント) -> Vec<出力>` である。将来、共通の関数役割として必要になった場合は `Mイベント解釈関数<イベント, 出力>` のような型を検討できるが、利用例が固まる前に共通化しない。

**要求**とは、SE再生、パーティクル生成、画面演出など、外部システムへ「これを実行してほしい」と渡す値のことである。

```text
旅行者の出来事::障害物に遮られた
    ↓ 解釈
壁衝突音を再生する要求
```

ドメインの遷移関数自身は音響API等を呼ばない。イベントから要求へ変換した後、外部境界が要求を実行する。`M要求` を共通の設計解釈マーカーにするかどうかの判断は4.2.1節が持つ。

### 4.2 標準データフロー

Update型のEventシステムの標準形を次とする。

```text
M解釈前の入力(M生入力、または整えた M中間入力)
  ↓ 解釈
Mコマンド
  ↓
M状態 + Mコマンド + M規則
  ↓ 遷移
遷移成功結果<M状態, Mイベント>
  ├─ 次の状態 ─────────→ 次回の状態正本
  │
  └─ 出来事一覧
       ├─→ 出来事の解釈 → 音響要求 → 音響境界
       ├─→ 出来事の解釈 → 演出要求 → 描画/演出境界
       ├─→ 出来事の解釈 → 別ドメインのMコマンド → 別のUpdate
       └─→ ログ / リプレイ等
```

重要なのは、`Event -> callback` ではなく `Event -> data flow` である。

### 4.2.1 `M要求` を共通の設計解釈マーカーにしない(2026-09-21。Issue #172)

本書は、2026-09-21時点で `M要求` を共通の設計解釈マーカーにしない。理由は次の3つである。

第一に、定義に合致する実例が0件である。`M要求` の定義は「音を鳴らしてほしい・演出を出してほしい・外部のAPIへこの操作を実行してほしい」であり、イベントを解釈して生まれることを前提にしている。しかしこのリポジトリには音響のクレートも依存も無く、`Mイベント` を実装する型は `crates/blitz_esca/src/旅行者.rs` の `旅行者の出来事` の1件だけであり、その出来事から要求へ解釈する工程は1つも実装されていない。`Mイベント → 解釈 → M要求 → 外部境界` という連なりは1本も存在しない。

第二に、`Mコマンド` との差が構文に現れず、機械で判定できない。`crates/editor_server/src/resource/command/mod.rs` の `編集コマンド` と `crates/editor_server/src/resource/music/command/mod.rs` の `楽曲編集コマンド` は、不変の判別共用体であり、作った側(ブラウザ)ではなくブラウザのTypeScriptの編集モデル(外部の境界)が実行し、Rust側は適用の実装を持たない。形の上では `crates/blitz_render/src/present_display/request.rs` の `実表示計測要求` と完全に同じでありながら、意味は `Mコマンド` の側である。逆に `実表示計測要求` も「計測してほしい」という主体の意図として読めば `Mコマンド` の定義に当てはまる。差は「誰が実行するか」という型と型の関係にあり、これは第6節の設計関係が機械検査へ接続されてからでないと表せない。

第三に、構文の法則が定まらない。実例は `enum`(`実表示計測要求`・`表示距離の指示`・`起動要求`・`検収の経路`)と `struct`(`報告要求`・`接合の指示`・`焼き上げの計画`・`プリミティブ描画発行`)に割れており、`Mコマンド` のような「必ず `enum`」の法則を課せない。また `M不変データ` を課すと、レンダラーへ渡す最大の要求である `crates/blitz_render/src/frame_input.rs` の `フレーム描画入力<'a>`(参照を4つ持つ)が排除される。課さないなら、`M要求` は役割の名札以上のものを何も保証しない。

一方で、記録する価値のある反復する形がある。「不変の判別共用体を作って外部の境界へ渡し、渡した側は実行しない」という形が少なくとも6件で反復しており、`crates/blitz_app/src/world_execution/contract/display_distance.rs` の `表示距離の指示`・`crates/blitz_app/src/cli/launch_request.rs` の `起動要求`・`crates/blitz_app/src/app/report_requests.rs` の `報告要求`・`crates/blitz_app/src/app/verification_launch_settings/route.rs` の `検収の経路` は、いずれもモジュールの冒頭コメントで「ここは値を保つだけである」「判定の材料も判定の順序も持たない」と明文で書いている。語彙としては存在するが、設計解釈マーカーとしては括れていない状態である。

判断を改める条件は次のとおりである。第6節の設計関係が機械検査へ接続され、かつ音響か演出の境界が1つでも実装されてイベントから要求を作る工程が現れたときに、実装者はこの判断を改めて検討する。

### 4.3 Observer系の語彙との対応

この方式では以下の語を原則として使わない。

| Observer / callback型 | Update型で対応する概念 |
|---|---|
| Event object with invoke | `Mイベント` という事実値 |
| Subscriber / Listener | 出来事の消費側 |
| Handler | 出来事の解釈、または要求を実行する工程 |
| Subscribe | コンポジションルートで消費側を明示配線する |
| Unsubscribe | 通常は存在しない。配線自体の寿命を変える |
| Invoke / Fire | 出来事値を生成して遷移成功結果へ入れる |
| EventArgs | `Mイベント` 自身のデータ |
| EventBus | 原則作らない。必要なら「出来事の配送工程」として役割を限定する |

特に `Handler` という語は曖昧なので避ける。書き手は責務ごとに語を分ける。

- Event を別の値へ変換するなら「解釈」
- Event を複数の読み手へ渡すなら「配送」
- 要求を外部APIで実行するなら「実行」
- 状態を更新するなら「遷移」

### 4.4 Event生成の法則(E1〜E8)

#### 法則E1: 過去の事実

`Mイベント` は、既に成立した事実だけを表す。

#### 法則E2: 成立していない事実を生成しない

イベントは、その遷移によって実際に成立した場合だけ生成する。

悪い例:

```text
コマンド = 歩く
→ 毎刻み「歩行を開始した」を生成
```

正しい判定:

```text
前状態 = 非歩行
次状態 = 歩行
→ 「歩行を開始した」
```

したがって「開始した」「終了した」「変化した」のような状態変化イベントは、前状態と次状態の差を表現できることが生成条件になる。

#### 法則E3: 状態正本へ混ぜない

イベントは次回Updateへ持ち越す状態正本ではない。

```rust
struct 状態 {
    歩行開始イベントが起きた: bool,
}
```

のように「一度起きた出来事」をリセット前提のフラグとして状態へ埋め込まない。継続して成立する事実なら、それはイベントではなく状態として表す。

#### 法則E4: 消費されても事実は変わらない

消費側はイベントを変更しない。複数の消費者が同じ事実を読める。

#### 法則E5: 配送は意味を作らない

配送工程はイベントの意味を決めない。意味は Event 型の定義と生成元の遷移が決める。

#### 法則E6: 副作用は遷移から分離する

純粋なドメイン遷移は音響・描画・ネットワーク等を直接実行しない。

```text
遷移
→ Mイベント
→ 解釈
→ 要求
→ 外部境界で実行
```

と分ける。

#### 法則E7: 隠れた購読表を作らない

どの Event を誰が読むかは、可能な限りコンポジションルートまたは明示された工程のコードから追える形にする。任意の場所から `subscribe(TypeId, callback)` して依存関係を隠す汎用 EventBus を基本形にしない。

#### 法則E8: Eventから同じ状態への暗黙フィードバックを作らない

その遷移自身が知っている事実によって同じ状態をさらに変える必要があるなら、原則として最初の遷移の中で状態を確定する。別ドメインへ影響するときは、

```text
Mイベント
→ 解釈
→ 相手ドメインのMコマンド
→ 相手のUpdate
```

と明示する。これにより Event の連鎖で同一tick内に何度状態が変わるか分からない構造を避ける。

### 4.5 型・関数の文法

Event 型は次の形で書く。`struct` / `enum` は意味に応じて選ぶ。

```rust
#[derive(Clone, ...)]
pub struct / enum 何かの出来事 { ... }

impl M不変データ for 何かの出来事 {}
impl Mイベント for 何かの出来事 {}
```

`Mイベント: M不変データ` であるため、`impl Mイベント for` だけではコンパイルできず、`impl M不変データ for` も要る(他のデータの役割 `M状態`・`Mコマンド`・`M規則`・`M解釈前の入力` も同じ)。

遷移は次の形で書く。遷移は成功のとき「次の状態」と「その評価で成立した出来事」を同時に確定し、失敗のとき受け取った状態と失敗の理由を返す(3.5.9)。

```rust
状態.〜を遷移する(          // 受け手は self(状態を値で受け取る)
    &コマンド,
    &規則,
    遷移パラメータ,
) -> Result<遷移成功結果<状態, 出来事>, 遷移失敗結果<状態, 失敗>>
```

失敗を持たない遷移は `Result` を使わなくてよい。失敗を型で返すかは各ドメインが決める。Esca の遷移パラメータは `経過時間` と刻みの始まりの時刻を持つ(3.5.1)。

解釈は、主語が自然なら次のように書ける。

```rust
出来事.音響要求へ解釈する()
出来事.演出要求へ解釈する()
```

ただし1つの Event 型へ各サブシステム固有の知識を集めて依存を逆流させる場合は、消費側の型に次のように置く。配置は「どちらがどちらを知ってよいか」という依存方向で決める。

```rust
音響方針.出来事を音響要求へ解釈する(&出来事)
```

配送は、中央の汎用 EventBus ではなく、その局面で必要な配送を明示する。

```text
一刻みを進める
  → 遷移成功結果を得る
  → 出来事一覧を各解釈工程へ渡す
  → 要求を各外部境界へ渡す
  → 次の状態を正本へ採用する
```

順序に意味がある場合は「購読登録順」に依存させず、工程の順序として名前を与える。

### 4.6 機械判定すること・しないこと

現在の `cargo xtask conform` は、次を法則として維持する。

- `Mイベント: M不変データ`(コンパイラが強制する。`Clone` は `M不変データ` から継承する)
- 参照を持たない
- 生ポインタを持たない
- 内部可変性を持たない
- 純粋データが持てる共有の指し先は、`M共有される不変データ` を指す `Arc` だけである(2.5.3 の共通の法則3)

受け手と引数に自分の型への可変参照を持たないこと(自己変更の禁止)は設計の法則として維持するが、機械では検査しない(2.5.3)。

参照・生ポインタ・内部可変性の検査は、`M不変データ` と役割(`Mイベント`・`M規則`・`Mコマンド` 等)の実装から型の定義をたどり、その定義に対して行う。`Mイベント: M不変データ` 等の supertrait の Relation はコンパイラが保証し、`impl M不変データ for` の置き場所は問わない。`&mut self` が無いだけでは `RefCell` 等を通じて `&self` から書き換えられ、読み取り専用で与えられる規則値や純粋計算という定義に反するためである。

さらに検査器で型を正確に同定できるようになった後は、次を候補にする。これらは「現在・未来・過去」の役割を同じ型へ重ねないための直交の法則である。

- 同じ具体型が `M状態` と `Mイベント` を同時に実装しない
- 同じ具体型が `Mコマンド` と `Mイベント` を同時に実装しない
- 同じ具体型が `M解釈前の入力` と `Mイベント` を同時に実装しない

一方、次は一般の構文検査では判定しない。これらは意味論または具体ドメインの配線だからである。

- イベントが本当に成立した事実か
- 開始/終了イベントが状態差からだけ生成されているか
- 名前が日本語の過去形か
- 必ず1フレームで消えるか
- enumであるか
- Event がどの消費者へ配送されるべきか

### 4.7 コメント / rustdoc の文法

Event のコメントは「何の通知か」ではなく、どの事実が成立した値なのかを書く。

悪い例:

```rust
/// 歩行開始時に使うイベント。
歩行を開始した,
```

良い例:

```rust
/// 非歩行状態から歩行状態へ遷移した事実。歩行中の各刻みを表すものではない。
歩行を開始した,
```

```rust
/// 移動先が空間制約を越え、実際の移動位置が制限された事実。
障害物に遮られた,
```

特に状態変化イベントは、前に何であり、次に何になったとき、この事実が成立するかがコメントから分かるようにする。

消費先(SEを鳴らす、エフェクトを出す等)は Event 自身の意味ではないので、書き手は Event 型の定義コメントには原則書かない。書き手はそれを消費側の「解釈」に書く。

### 4.8 Marker / Relation / Law としての位置付け

```text
Marker
  Mイベント
    = 過去の事実として解釈する型

Relation
  M遷移関数
    consumes -> 状態(値で受け取る)
    produces -> 遷移成功結果<状態, イベント> | 遷移失敗結果<状態, 失敗>

  出来事の解釈
    consumes -> Mイベント
    produces -> 要求 / 他ドメインのMコマンド / 出来事の保存(ログ・リプレイ・監査履歴など)

Law
  E1 過去の事実
  E2 成立した事実だけ生成
  E3 状態正本へ混ぜない
  E4 消費側は事実を変更しない
  E5 配送は意味を作らない
  E6 副作用を遷移から分離
  E7 隠れた購読表を基本形にしない
  E8 同一状態への暗黙Eventフィードバックを作らない
```

この形なら Observer パターンと同様に、読み手は `Mイベント` を見た時点で「この型が何であり、どこから生まれ、どう流れ、どう書いてはいけないか」までコード文法として共有できる。

## 5. 機械強制の手段

依存の向きは `xtask/src/conform/dependency_whitelist/ledger.rs` の白リストが機械で強制する。`blitz_design` の行は依存ゼロであり、`blitz_sim` と `blitz_esca` と `blitz_game` の行が `blitz_design` を許す。

法則の検査主体は2つに分かれる。

- コンパイラが強制する法則: データの役割(`M状態`・`M遷移が受け取る命令`・`Mイベント`・`M規則`・`M解釈前の入力`・`M観測`)の `M不変データ` 実装(上位トレイト)と、`M生入力`・`M中間入力` の `M解釈前の入力` 実装(上位トレイト)、`Mコマンド`・`M命令の組` の `M遷移が受け取る命令` 実装(上位トレイト)、`M不変データ` の `Clone`(上位トレイト)、存在の分類の上位トレイト(`M値オブジェクト` の `PartialEq`、`Mエンティティ識別子` の `Eq`・`Hash`)と `Mエンティティ` の関連型と識別子のメソッドの存在(2.5節)、関数の役割の型引数の境界、`遷移成功結果` の型引数の `M状態`・`Mイベント` の境界と `遷移失敗結果` の型引数の `M状態`・`std::error::Error` の境界(構造体の境界)、失敗のとき状態を呼び出し側へ返す口があること(`遷移失敗結果` が状態の型の値を1つ持つため)。返す値が遷移の受け取った値と等しいことは、コンパイラは強制せず、有限全数の検証で確かめる(3.5.9)。型エイリアスの境界は Rust の仕様上強制されない(rust-lang/rust#112792)ため、関数の役割(`M射影関数`・`M解釈関数`・`M遷移関数` と、形を縮めた遷移と問い合わせを伴う5つの役割)は境界付きの newtype であり、型を使った時点でコンパイラが型引数の境界を強制する。迂回できる書き方は無い。利用側は `const _: M遷移関数<...> = M遷移関数::生成する(旅行者の居場所::歩行を遷移する);` の静的宣言でコンパイラに確かめさせる。
- `cargo xtask conform` の設計オントロジーの検査(`xtask/src/conform/設計オントロジーの規約検査.rs`)が見る法則: `M不変データ`・`M共有される不変データ` またはデータの役割を実装する型の定義に参照・生ポインタ・内部可変性が無いこと(役割の実装から型の定義をたどってその定義に当てる。`Mコマンド: M不変データ` 等の supertrait の Relation はコンパイラが保証し、`impl M不変データ for` の置き場所は法則にしない)、`Mコマンド` が `enum` であること、`M規則` が `struct` であること、`M命令の組` が `struct` でありフィールドの型がどれも `Mコマンド` を名乗ること(`xtask/src/conform/設計オントロジーの規約検査/命令の組の検査.rs`)、`M結果` を実装する型が `enum` であること(正本の標準の `Result` への包括の実装だけが定義をたどらない特例。2.6.1)、`MParameter` を実装する型の定義に `Option<` のフィールドが無いこと(2.6.1)、同じ型が排他の分類(基底の契約の `M不変データ` と `M共有される不変データ`、`M不変エンティティ` と `M可変エンティティ`、`MParameter` と `MOptions`、`M生入力` と `M中間入力`、`Mコマンド` と `M命令の組`、軸をまたぐ `M命令の組` と `MParameter`)を同時に名乗っていないこと(2.5.1・2.6・第2節)、純粋データ規約の対象の型の共有の指し先が `M共有される不変データ` を指す標準の表記の `Arc` だけであることと、その型を持つクレートが `Arc`・`Rc`・`Weak` を `use … as` や `type` の別名にしていないこと(2.5.3)、`M解釈前の入力` を実装する型が `M生入力` か `M中間入力` のどちらかを名乗っていることと、`M遷移が受け取る命令` を実装する型が `Mコマンド` か `M命令の組` のどちらかを名乗っていること(第2節)。定義が見つからない型は違反として報告する。

検査器の保証範囲は次のとおりである。検査は Rust の型意味論でなく構文パターン(`impl トレイト for 型` の行と `struct`/`enum` の定義ブロック)に対して行う。型の同一性は「標準的なファイル配置から推定したモジュールパス + 型名」である(`crates/<名前>/src/lib.rs` は `<名前>`、`src/a/b.rs` は `<名前>::a::b`、`src/a/mod.rs` は `<名前>::a`)。`impl トレイト for 型` の行がどの定義を指すかは、実装と同じファイルの定義、無ければそのファイルの `use` 行(`crate::`・`super::`・`self::` の置き換えと1段の波括弧の群)から取り込み元のモジュールパスを求めて、そのモジュールパスの定義で決める。起点の予約語で始まらない `use` のパス(`use 子::型;`)は、最初の区切りが `use` を書いたモジュールの子のモジュールとして在ればそこからの相対として読み、無ければ外部クレートのパスとして読む。取り込み元のモジュールの直下に定義が無ければ、そのモジュールの直下の再公開(`pub use`)を段ごとにたどって定義のモジュールへ行き着く(`xtask/src/conform/設計オントロジーの規約検査/type_definition/再公開の追跡.rs`)。`use` が無ければ別モジュールの同名の定義を推測せず、定義が見つからない違反にする。同じファイルに同名の定義が複数あるとき(波括弧付きのモジュール `mod 名 { ... }` で分けた場合)も一意に決まらないとして違反にする(黙って最初の1つを選ばない)。実装対象の型を `use ... as` の別名で取り込んだ実装は取り込み元を求められない違反にする(黙って通さない)。入れ子の波括弧の `use`、一括取り込み、型引数の境界が入れ子の `<` を含むジェネリックな `impl`、フィールドの型の中に間接的に含まれる内部可変性は保証範囲の外である。共有の指し先も同じであり、マーカーの無い型を間に挟んだ指し先と、純粋データ規約の対象の型を持たないクレートが置いた別名を取り込んで使う形は保証範囲の外である(2.5.3)。`#[path = "..."] mod` については、conform が別に、`crates` 配下の `src` のすべての `mod` の宣言について、宣言から読める論理のモジュールパス(宣言元のファイルのモジュールパス + 宣言されたモジュール名)と、対象の物理ファイルから求める物理のモジュールパスが等しいことを確かめる(`xtask/src/conform/設計オントロジーの規約検査/module_declaration.rs` と `module_structure_assertion.rs`)。日本語のモジュールは rustc が既定のファイルの探索を E0754 で拒むためこの属性を必ず持ち、この一致の検査によって上の推定はそのまま成り立つ。

設計解釈マーカーの実装の形は正規形へ固定する。設計解釈マーカーの実装は `impl マーカー名 for 型` または `impl blitz_design::マーカー名 for 型` の形に固定する。`blitz_design` を別名で取り込むこと(`use blitz_design as 別名;`・`use blitz_design::M不変データ as 別名;`・`use blitz_design::{M不変データ as 別名};` のいずれも)は conform が違反にする。別名で取り込むと conform が実装を認識できず、法則を破れる合法な Rust を黙って通すためである。別名を使わずに正規形を迂回する書き方も conform が違反にする。迂回する書き方とは、再公開の経由(`mod design_alias { pub use blitz_design::M不変データ; }` と書いてから `impl design_alias::M不変データ for 型`)、絶対パス(`impl ::blitz_design::M不変データ for 型`)、パスの中の空白(`impl blitz_design :: M不変データ for 型`)の3つである。conform は、トレイトを書く位置に設計解釈マーカーの名前が識別子として現れる `impl ... for ...` の行のうち、その位置が正確に `マーカー名` または `blitz_design::マーカー名` でない行をすべて違反にし、あわせて `blitz_design` の外のファイルが `blitz_design` を公開の `use`(`pub use`・`pub(crate) use` など)で再公開することを違反にする(`blitz_design` 自身の `lib.rs` が自分のモジュールを再公開するのは対象でない)。マーカーの実装をファイルの中の `mod 名 { ... }` の中へ置くことも conform が違反にする(マーカーの実装を、ファイルのモジュールの直下という1つの置き場へ固定するためである。構文検査は実装の位置のモジュールの直下の定義を採るため、`mod 名 { ... }` の中の実装はファイルの直下の同名の型を指さず、どの型のマーカーかを読み手が取り違える)。試験の `mod tests { ... }` は、その中にマーカーの実装を書かない限り違反にならない。

## 6. 関係の3つの高さと設計関係(Relation)

本節は、設計の検証が扱う関係を、何について語るかで3つの高さに分けて定める。6.1節が高さの区別を、6.2節が仕様の関係の種類を、6.3節が分類と公理を、6.4節から6.6節がプリミティブな事実と定義の式と設計関係グラフ(定義は6.6節)を持つ。正本の考え方は [Issue #193](https://github.com/megaDenryu/Blitzdrache0/issues/193) の「合意した考え方」と「契約」である。

### 6.1 関係の3つの高さ

関係の高さとは、その関係が何について語るかの区別のことである。設計の検証は次の3つの高さを持つ。

| 高さ | 例 | 何について語るか |
|---|---|---|
| 仕様の関係 | 町Aと町Bはつながっている・北の橋は閉じている・どこからでも出口へ行ける | ゲームの世界の値 |
| 設計の関係 | 旅行者IDは旅行者を識別する・遷移は状態を消費する | コードの型の役割 |
| プリミティブな関係 | フィールドに持つ・引数に取る・呼ぶ・マーカーを実装する | コードの形 |

設計の検証が最終的に記述したいのは仕様の関係である。設計の関係は中間表現として必要だが、目的ではない。

**上の高さの関係は、下の高さの関係(と同じ高さの他の関係)を組み合わせた式で定義される。** 本書はこの式を定義の式と呼ぶ(6.5節)。この定義の仕方は、数学でいう定義による拡張である。定義による拡張とは、既にある述語の論理式で新しい述語を定義して体系へ足すことのことである。足した述語はいつでも元の述語の式へ書き戻せるため、体系で言えることは増えても、元の述語について示せることは変わらない。本書は設計の関係をこの形で定義する。そのため、定義の式の評価器(6.5節)は、設計の関係を抽出器が読んだプリミティブな事実からいつでも導き直せ、導いた1件ごとに、どの規則がどの事実から導いたかを答えられる。

仕様の関係はゲームの世界の値について語る。そのため、仕様の関係はソースの型を読むだけでは現れない。書き手は、仕様の関係を、実行とは別の入口の試験(有限全数の検証。第10節)がプリミティブ(実物の遷移関数・状態とコマンドの数え上げ・原子命題)を使って命題を検証する形で定義する。例として、`crates/blitz_esca/src/tests/経路の開閉の数え上げの試験.rs` は、仕様の関係「閉じている経路は、いつも地図にある経路である」を定義する。この試験は、実物の開閉の遷移を小さな地図の全状態・全コマンドについて呼び、地図の外の経路を閉じている状態がどれも到達可能でないことを連言の命題として検証する。

### 6.2 仕様の関係の3つの種類

仕様の関係は、その関係がどう決まるかで3つの種類に分かれる。書き手がコードで使う書き方は、種類ごとに違う。

| 種類 | 例 | 書き方 |
|---|---|---|
| 並べて決まる関係 | 町Aと町Bがつながっている | Graphite(Rustの型で検査されるグラフの記述言語)のグラフで事実を並べる |
| 規則で決まる関係 | チェスのナイトは縦2横1に動ける | 規則を型と関数で書く(`M規則`) |
| 遷移 | 経路が出来事と時間で開閉する | `M遷移関数` で書き、有限全数の検証で確かめる |

- 並べて決まる関係とは、関係に入る組を1つずつ名指して並べることでしか決まらない関係のことである。町と町のつながりは地図を作る人が決め、どの町どうしがつながるかを導く規則は無い。実例は Esca の地点と経路のグラフである。`crates/blitz_esca/src/地点と経路/図式.rs` が地点を節点、経路を辺とする図式を宣言し、`crates/blitz_esca/src/地点と経路/地図.rs` が完成したグラフを `M共有される不変データ` の地図として包む。試験の地図は `crates/blitz_esca/src/tests/地点と経路の試料.rs` が `graphite::graph!` で並べる。
- 規則で決まる関係とは、関係に入る組を少数の規則から導ける関係のことである。チェスのナイトがどのマスへ動けるかは盤の全マスについて並べられるが、「縦2横1」という規則から全部が導ける。書き手は、規則を `M規則` の型と関数(その型のメソッドを含む)で書く。
- 遷移とは、状態がコマンド・時間・規則によって次の状態へ移る関係のことである。書き手は、遷移を `M遷移関数` で書き、遷移が満たすべき性質を有限全数の検証(第10節)で確かめる。実例は経路の開閉の遷移(`crates/blitz_esca/src/地点と経路/開閉の状態.rs` の `経路の開閉の状態::開閉を遷移する`)と、6.1節の試験である。

どんな関係もグラフで表せる。2項の関係は辺の集合として表せる。3項以上の関係も、書き手が関係そのものを節点にして役割の名前を付けた辺を引けば表せる。ただし、書き手が規則で決まる関係を事実の一覧としてグラフへ並べると、規則そのものがコードから消える。**そのため、書き手がグラフで書くのは並べて決まる関係だけにする。**

### 6.3 分類と公理

分類とは、型が実装した設計解釈マーカーの集合を、設計解釈マーカーどうしの上位トレイトの宣言で閉じたもののことである。`M状態` を実装した型は、`M不変データ` を直に実装していなくても、分類に `M不変データ` を持つ。

**分類は関係ではなく、設計関係グラフの節点のラベルである。** 「型Aに `M状態` を実装している」は、型Aへ「設計上これである」という分類を与える宣言であり、2つの概念のあいだの関係ではない。そのため設計関係グラフ(6.6節)は、分類を辺にせず、節点ごとのラベル(`節点の分類`)として持つ。設計関係グラフは、分類を設計関係への参加に数えない(6.6節)。

**公理とは、分類どうしの一種であるという関係のことである。公理の正本は `blitz_design` の上位トレイトの宣言(`trait M状態: M不変データ` など。`crates/blitz_design/src/設計解釈マーカー.rs`)である。** コンパイラが上位トレイトの宣言を既に強制しているため、書き手は手書きの公理の表を別に作らない。検証器は、抽出器が読んだ上位トレイトの宣言の事実から、分類の閉包を計算する。

分類の閉包は、設計解釈マーカーだけを辿る。`M不変データ: Clone` の `Clone` のような標準のトレイトは、上位トレイトの宣言の事実に在っても分類へ入らない。分類を持つのは、マーカーの実装の事実の主語に立つ型だけであり、トレイトと処理は分類を持たない。どのトレイトが設計解釈マーカーかは抽出器が渡し、検証器は写しを持たない。正本は `crates/blitz_design_verification/src/分類.rs` と `crates/blitz_design_verification/src/分類/事実.rs` である。

### 6.4 プリミティブな事実

プリミティブな事実とは、抽出器がRustのソースから読む、コンパイラが知っている形の事実のことである。抽出器が出すのはプリミティブな事実だけであり、抽出器は、どの事実からどの関係を導くかを知らない。

| 事実 | 出どころのRustの構文 | 持つ型 |
|---|---|---|
| 型の定義 | `struct`・`enum` の宣言(型の名前と種類) | `型の定義の事実` |
| フィールドの型の表記 | `struct`・`enum` のフィールド。包みを剥がす前の表記のまま運ぶ | `フィールドの型の表記の事実` |
| マーカーの実装 | `impl マーカー for 型`(型と設計解釈マーカーの組) | `マーカーの実装の事実` |
| 上位トレイトの宣言 | `trait A: B`(トレイトと上位トレイトの組) | `上位トレイトの宣言の事実` |
| 関数の役割の宣言 | `const _: M遷移関数<..> = M遷移関数::生成する(..)`(役割・型引数の表記の並び・包んだ関数のパス) | `関数の役割の宣言の事実` |
| エンティティの識別子の関連型 | `impl Mエンティティ for A { type 識別子 = B; }` の右辺の表記 | `エンティティの識別子の関連型の事実` |
| 関数の署名 | 項目の位置(モジュールの直下と `impl`・`trait` の本体の直下)の `fn` の見出し(所有者・受け手の受け方・引数の型の表記の並び・戻り値の型の表記) | `関数の署名の事実` |

マーカーの実装と上位トレイトの宣言の2つは分類を決める事実であり、`分類の事実` が持つ(6.3節)。残る5つは `プリミティブな事実` が持つ(`crates/blitz_design_verification/src/導出/プリミティブな事実の定義.rs`)。5つのうち、フィールドの型の表記・関数の役割の宣言・エンティティの識別子の関連型・関数の署名の4つは、定義の式の規則の本体に現れて関係を導く。型の定義の事実は、型の節点を立てるだけであり、どの規則の本体にも現れない。関係に1本も参加しない型も、この事実によって節点として在る。抽出器の実装は `xtask/src/設計関係のモデル/設計関係の抽出/` にある。

抽出器は設計語彙のクレート(`blitz_design`)の関数の署名を読まず、`設計語彙のクレートの関数である` として件数を数えて明示して外す(設計概念でないため明示して除外した区分であり、関係を落とした抽出の欠落に数えない)。このクレートの関数は、関数の役割の型と意味型の自身の操作(包む・呼び出す)とマーカーの既定の操作だけであり、どれも役割の型引数か関数ポインタを扱う設計の語彙の定義である。このクレートは何にも依存しないため、その関数はドメインの型を名指さない。

抽出器は、標準ライブラリ(`std`・`core`・`alloc`)のトレイトの実装の関数(`impl Clone for 状態` の `clone`・`impl std::ops::Add for 状態` の `add`・`impl fmt::Display for 状態` の `fmt`)の署名も読まず、`標準ライブラリのトレイトの実装の関数である` として件数を数えて明示して外す。これらの関数は言語の決まりごとであってゲームの操作ではなく、状態を受けて返す処理の宣言の法則(第8節の A7)の前件に当てないためである。トレイトが標準ライブラリのものかは、定義の式が型の表記を読むのと同じ定義の探索の口で見分ける(修飾して書いたトレイト・`use` で取り込んだトレイト・同じクレートに同じ名前の定義が無いプレリュードのトレイト)。このクレートや外部のクレートで宣言したトレイトの実装の関数は、署名を読む(`xtask/src/設計関係のモデル/設計関係の抽出/関数の署名の抽出.rs`)。

関数の署名の事実(Issue #175 の第2段階)は、`fn` の項目1件について、処理の節点・所有者(`impl 型` と `impl トレイト for 型` の型の表記、`trait 名` のトレイトの節点、自由関数は無し)・受け手の受け方(無し・値・参照・可変参照)・受け手を除いた引数の型の表記の並び・戻り値の型の表記(無ければ無し)を持つ(`crates/blitz_design_verification/src/導出/関数の署名の事実の定義.rs`)。抽出器は、項目の位置の `fn` だけを読む。関数や構造体やマクロの本体の中に書いた `fn` は、黙って外さずに `項目の位置でない関数である` として数え、関数の署名の答えを弱める。処理の識別子は、`fn` を書いた位置のモジュール(波括弧付きの `mod` を含む)・所有者の名前・関数の名前で作る。関数の役割の宣言の事実は、処理の識別子をまず使用箇所のファイルのモジュールパスで組むが、抽出の入口が全ての規則を併せた後に、同じクレートで名前が同じで、所有者の型の定義が同じ署名の事実の処理へ揃える(`xtask/src/設計関係のモデル/設計関係の抽出/役割の宣言と関数の定義の突き合わせ.rs`)。関数を別のファイルの `impl` に置いても、同じ関数が2つの節点へ割れないためである。所有者の型は、役割の宣言の行と署名の行のそれぞれから型の名前の定義を探して照らし、名前では照らさない。名前で照らすと、同じクレートの別のモジュールの同じ名前の型のメソッドと取り違えるためである。候補は固有の実装の関数を先に探し、無ければトレイトの実装の関数を探す(Rust が `型::関数` の定義を探す順と同じである)。トレイトの実装の関数へ揃えると、役割の宣言の処理の所有者の並びもトレイトの表記を含む形に揃う。候補が2つ以上なら役割の宣言を抽出できなかった行に数えて落とし、候補が無ければ(マクロが作る関数や、所有者の型の定義をたどれないときなど)使用箇所で組んだ識別子のまま残す。所有者の名前は、固有の実装なら対象の型の名前、トレイトの実装なら対象の型の名前とトレイトを書いた位置の表記(型引数を含む)の2つ、トレイトの本体ならトレイトの名前である。トレイトの実装の関数は、同じ型の固有の実装の同じ名前の関数とも、同じトレイトを型引数だけ変えて実装した関数とも別の処理であるためである。`impl` の本体の型の表記は、`Self::関連型` をその実装の本体で宣言した関連型の右辺(`type Item = 地点;` の `地点`)へ置き換え、残る `Self` を実装の対象の型の表記へ置き換える。先に `Self` を置き換えると `型::関連型` になり、型の関連項目として読めない表記に数えるためである。実装の本体に宣言の無い関連型(上位トレイトの関連型・既定の関連型)と、本体を開く `{` と同じ行に書いた宣言は置き換えず、抽出器の保証範囲の外として読めない表記に数え、関係を落とした抽出の欠落に数える。`trait` の本体の `Self` は型引数として残す(`xtask/src/設計関係のモデル/設計関係の抽出/関数の署名の抽出.rs` と `xtask/src/設計関係のモデル/設計関係の抽出/関数を持つ位置/関数を囲む本体の定義.rs`)。

抽出器は、型の定義の事実を `struct` と `enum` の宣言だけから出す。Issue #193 の契約は型の定義の出どころを「struct・enum・trait」と書くが、抽出器はトレイトの宣言から型の定義の事実を出さない。トレイトの節点は、分類を決める側の2つが立てる。1つは設計解釈マーカーの一覧(`xtask/src/設計関係のモデル/設計関係の抽出/marker_concept.rs`)であり、全部の設計解釈マーカーを、関係に1本も現れなくてもトレイトの節点として立てる。もう1つは上位トレイトの宣言を読む抽出の規則(`xtask/src/設計関係のモデル/設計関係の抽出/上位トレイトの宣言の抽出.rs`)であり、設計解釈マーカーの正本のファイルの `trait` の宣言と、設計解釈マーカーを上位に持つ `trait` の宣言について、宣言したトレイトとその上位トレイトを節点として立てる。`M不変データ: Clone` の `Clone` のような標準のトレイトも、上位トレイトとして節点になる。上位トレイトの宣言を読む規則は、トレイトの見出しを本体を開く `{` まで複数の行にわたって読み(rustfmt が `where` 句を持つ見出しを次の行以降へ折るため)、`: A + B` の境界と、`where` 句のうち左辺が `Self` の述語の境界を上位トレイトとして出す。Rust で `trait A where Self: B` は `trait A: B` と同じ意味だからである。左辺が型引数の述語(`where T: B`)は型引数への境界であり上位トレイトではなく、寿命の境界はトレイトでないため、どちらも出さない(`xtask/src/設計関係のモデル/設計関係の抽出/トレイトの宣言の行.rs`)。

実装者は、型の表記を持つ事実(将来の「引数に取る」など)を、事実の一覧を1つと、事実の原子(6.5節)の選択肢を1つと、定義の式の規則を足すことで足せる。分類と組み合わせる定義は、本体の原子 `分類にマーカーを持つ` で書ける(6.5節。命令の組を通した消費の規則が使う)。両端が節点の事実(「呼ぶ」「コンポジションルートが組む」など)は、いまの定義の式の形では書けない。実装者がそれを足すには、束縛と評価器の拡張が要る。[Issue #175](https://github.com/megaDenryu/Blitzdrache0/issues/175) のアプリケーションモデルは、この拡張を伴って事実を足す。

### 6.5 定義の式

定義の式とは、設計の関係とプリミティブな関係(保持する・関連関数として持つ・受け手に取る・引数に取る・そのまま受け取る・返す・そのまま返す)を、プリミティブな事実の上の規則として値で並べたもののことである。正本は `crates/blitz_design_verification/src/導出/定義の式の規則一覧.rs` であり、関数の役割の型引数の位置ごとの規則は `crates/blitz_design_verification/src/導出/役割の型引数の規則表.rs` の表が持つ。

定義の式の規則(導出の規則)は、頭の関係と、本体の原子の連言でできている。本体の原子は2種類ある。事実の原子とは、プリミティブな事実を1件選び、主語か目的語の変数へ概念を1つ当て、型の表記を1つ当てる原子のことである。`表記が型を名指す` とは、当てた型の表記を定義の式の読み方で読み、名指す型をもう一方の変数へ当てる原子のことである。評価器(`crates/blitz_design_verification/src/導出/評価.rs`)は、規則ごとに本体の原子を左から当て、成り立った当て方ごとに頭の関係を1件導く。導いた1件は、出どころ(表記が在ったソースの行と、関係を導いた事実が書かれていたRustの構文。本書はこの構文を抽出元の構文と呼ぶ)と、導出の根拠(規則の名前と、使った事実の出どころの並び)を持つ。定義の式が規則を関数の中の場合分けでなく値で持つのは、報告が「この関係はどの規則がどの事実から導いたか」を示せるようにするためである。

関係の語は次の12である。5つが設計の関係であり、保持する・関連関数として持つ・受け手に取る・引数に取る・そのまま受け取る・返す・そのまま返すの7つがプリミティブな関係である。

| 関係 | 高さ | 意味 |
|---|---|---|
| `識別する` | 設計 | 主語がエンティティである目的語の同一性を担う識別子である |
| `消費する` | 設計 | 主語の処理が目的語を入力として受け取る |
| `生成する` | 設計 | 主語の処理が目的語を出力として作る |
| `参照する` | 設計 | 主語の処理が目的語を読み取り専用で読む |
| `書き換える` | 設計 | 主語の処理が、目的語の状態をゲームの規則によらず外からの材料で書き換えた値として返す(2026-09-28。規則によらない書き換えの役割から導く) |
| `保持する` | プリミティブ | 主語の型が目的語の型をフィールドとして持つ |
| `関連関数として持つ` | プリミティブ | 主語の型かトレイトが、目的語の処理を自分の関連関数(メソッドを含む)として持つ |
| `受け手に取る` | プリミティブ | 主語の処理が、目的語の型かトレイトの値を受け手(`self`・`&self`・`&mut self`)として受ける。目的語は実装の対象の型か、トレイトの本体の関数ならそのトレイトである |
| `引数に取る` | プリミティブ | 主語の処理が、目的語の型かトレイトを受け手でない引数の型に書いている |
| `そのまま受け取る` | プリミティブ | 主語の処理が、目的語の型の値そのものを受け手でない引数として受け取る。引数そのもの(参照を含む)か、`Result`・組・意味型の成分か、`Box`・`Arc` の中身として受け取る。`Vec`・`Option` 等の包み・スライス・`impl`・`dyn` のトレイト・関数の型の中は含まない |
| `返す` | プリミティブ | 主語の処理が、目的語の型かトレイトを戻り値の型に書いている(`Result`・組・意味型・包み・`impl` のトレイト・関数の型の中の型を含む) |
| `そのまま返す` | プリミティブ | 主語の処理が、目的語の型の値そのものを返す。戻り値そのものか、`Result`・組・意味型の成分か、値を1つだけ必ず持つ包み(`Box`・`Arc`)の中身として返す。`Vec`・`Option` 等の包み・スライス・`impl`・`dyn` のトレイト・関数の型の中は含まない |

定義の式は、次の50本の規則をこの順に当てる。37本の関数の役割の規則・3本の命令の組を通した消費の規則・2本の残りの規則・8本の関数の署名の規則である。関数の役割の規則と残りの規則は、本体が事実の原子1つと、そのあとの `表記が型を名指す` 1つである。37本の関数の役割の規則は、どれも関数の役割の宣言のその位置の型引数を事実の原子が選び、抽出元の構文は関数の役割の型引数である。

| 役割 | 位置と頭の関係 |
|---|---|
| `M解釈関数` | 第1(入力)を `消費する`・第2(コマンド)を `生成する` |
| `M射影関数` | 第1(状態)を `消費する`・第2(射影)を `生成する` |
| `M遷移関数` | 第1(状態)を `消費する`・第2(コマンド)を `消費する`・第3(規則)を `参照する`・第4(遷移パラメータ)を `消費する`・第5(イベント)を `生成する`・第6(失敗)を `生成する`・第1(状態)を次の状態として `生成する` |
| `M遷移が受け取る命令で決まる遷移関数` | 第1(状態)を `消費する`・第2(コマンド)を `消費する`・第1(状態)を次の状態として `生成する` |
| `M規則で決まる遷移関数` | 第1(状態)を `消費する`・第2(規則)を `参照する`・第1(状態)を次の状態として `生成する` |
| `M規則と遷移パラメータで決まる遷移関数` | 第1(状態)を `消費する`・第2(規則)を `参照する`・第3(遷移パラメータ)を `消費する`・第1(状態)を次の状態として `生成する` |
| `M問い合わせを伴う遷移関数` | 第1(状態)を `消費する`・第2(コマンド)を `消費する`・第3(規則)を `参照する`・第4(遷移パラメータ)を `消費する`・第6(観測)を `生成する`・第1(状態)を次の状態として `生成する`。第5(問い合わせ先)と第7(失敗)からは導かない |
| `M規則で決まる問い合わせを伴う遷移関数` | 第1(状態)を `消費する`・第2(規則)を `参照する`・第3(遷移パラメータ)を `消費する`・第5(観測)を `生成する`・第1(状態)を次の状態として `生成する`。第4(問い合わせ先)と第6(失敗)からは導かない |
| `M問い合わせを伴う評価関数` | 第1(規則)を `参照する`・第2(パラメータ)を `消費する`・第4(結果)を `生成する`。第3(問い合わせ先)と第5(失敗)からは導かない |
| `M規則によらない書き換え関数` | 第1(状態)を `書き換える`・第2(材料)を `消費する`。第1(状態)を `消費する`・`生成する` とは導かない(状態の存在理由の公理 A3 を満たさないため) |

**命令の組を通した消費の規則。** 3本の規則は、「`M命令の組` が保持する `Mコマンド` は、その組を受け取った処理に消費される」(2026-09-28 のオーナー裁定)を、コマンドの位置を持つ遷移の役割(`M遷移関数`・`M遷移が受け取る命令で決まる遷移関数`・`M問い合わせを伴う遷移関数`)ごとに1本ずつ書いたものである(`crates/blitz_design_verification/src/導出/命令の組を通した消費の規則.rs`)。頭の関係は `消費する` であり、本体は6つの原子の連言である。事実の原子が役割の宣言のコマンドの位置(第2の型引数)を選んで包んだ関数を主語へ当て、`表記が型を名指す` がその表記の型を経由する概念(頭に現れず、本体の2つの事実をつなぐ変数)へ当て、`分類にマーカーを持つ` がその型の分類に `M命令の組` があることを求め、事実の原子が経由する概念のフィールドの型の表記を選び、`表記が型を名指す` がその型を目的語へ当て、`分類にマーカーを持つ` が目的語の分類に `Mコマンド` があることを求める。`分類にマーカーを持つ` とは、変数に当たった概念の分類(6.3節。上位トレイトの宣言で閉じたもの)がその名前の設計解釈マーカーを含むときだけ束縛を残す原子のことである。評価器は、分類の事実を評価の前に節点の分類へ閉じて読む。分類を本体に書くのは、組でない値(コマンドの列挙が選択肢に持つ値オブジェクトなど)のフィールドから消費を導かないためである。導いた関係の出どころはフィールドの行であり(抽出元の構文は構造体のフィールド)、導出の根拠は役割の宣言とフィールドの2つの事実を並べる。組そのものの消費は、第2の型引数の位置の規則が別に導く。

残る2本は次のとおりである。

| 規則の名前 | 頭の関係 | 事実の原子が選ぶもの | 抽出元の構文 |
|---|---|---|---|
| 識別子の関連型が名指す型はそのエンティティを識別する | `識別する` | エンティティの識別子の関連型の事実。エンティティを目的語へ当て、名指す型を主語へ当てる | エンティティの識別子の関連型 |
| フィールドの型が名指す型を持ち主が保持する | `保持する` | フィールドの型の表記の事実。持ち主を主語へ当て、名指す型を目的語へ当てる | 構造体のフィールド |

**関数の署名の規則。** 8本の規則は、関数の署名の事実からプリミティブな関係だけを導き、設計の関係を導かない(`crates/blitz_design_verification/src/導出/関数の署名の規則.rs`)。抽出元の構文はどれも関数の署名であり、出どころは `fn` の行である。

| 規則の名前 | 頭の関係 | 本体 |
|---|---|---|
| 関数の所有者の型がその関数を関連関数として持つ | `関連関数として持つ` | 所有者が型の署名を選んで関数を目的語へ当て、実装の対象の型の表記を所有者の読み方で読んで主語へ当てる |

定義の式はこの表記から関係を導かず欠け(`関数の署名の型引数である`)を返し、抽出器はそれを設計概念でないため明示して除外した区分に数えて件数を残す(関係を落とした抽出の欠落に数えない)。これは「検査器は解析できなかった入力を黙って対象から外してはならない」の、外す条件を書き下せる入力に当たる。境界を持つ型引数は境界のトレイトへ読み替えるため、この条件に当たらない。署名の読み方の欠けは `cargo xtask conform` の違反にはしない(書き手に関数の署名の書き方を制限しないため)。**`そのまま返す` は、同じ戻り値の表記を値そのものと成分だけ読む。** 戻り値そのものと `Result`・組・意味型の成分と、値を1つだけ必ず持つ包み(`Box`・`Arc`)の中身だけを読み、0個か複数の値を持つ包み(`Vec`・`Option`・`BTreeSet`)とスライスと `impl`・`dyn` のトレイトと関数の型の中を読まない。候補を並べて返す関数(`Vec<状態>`)や次の値を順に渡す関数(`impl Iterator<Item = 状態>`)は状態の値そのものを返しておらず、状態を受けて返す処理の宣言の法則(第8節の A7)の前件に当てないためである。読まない位置の型は `返す` が同じ表記から読むため、関係は失われない。

役割の定義の知識は、事実の側でなく定義の式の側に在る。役割の定義の知識とは、型引数の位置ごとに何を消費し何を生成するかのことである。遷移の役割の第1の型引数(状態)は現在の状態として消費され次の状態として生成されるため、2本の規則に現れる。定義の式が `M遷移関数` の第6の型引数(失敗)を生成するとするのは、`Err(遷移失敗結果<状態, 失敗>)` が運ぶ失敗の理由がその処理の取りうる明白な出力であるためであり、毎回は生成されないことは除外の理由にならない(2026-09-22のオーナーの裁定)。遷移パラメータは、2026-09-27 に型引数へ一般化するまで、役割の定義が関数ポインタの第4引数として固定する入力であり、定義の式は使用箇所の表記に現れない固定の入力として別の規則で消費を導いていた。いまは第4の型引数として表記に現れ、位置の規則が導く。問い合わせを伴う3つの役割の問い合わせ先と失敗の位置から関係を導かないのは、宣言がジェネリックな関数を代表の問い合わせ先(失敗しない問い合わせ先のトレイトのオブジェクト)で具体化して書き、その2つの型引数が実際の問い合わせ先と失敗を名指さないためである(第3節)。

`消費する`・`生成する`・`参照する` の主語は、役割の値の右辺に包まれている具体の関数である(`const _: M解釈関数<...> = M解釈関数::生成する(キーボード歩行入力::歩行入力を解釈する);` なら `blitz_esca::キーボードの入力::キーボード歩行入力::歩行入力を解釈する`)。役割の値を持つ宣言の名前は主語にならない。その宣言は関数の役割の宣言であり、その関数が役割の型契約を満たすことをコンパイラに確かめさせるだけで、処理そのものではないためである。抽出器は、右辺の関数のパスを読めない使用箇所(戻り値の型・フィールドの型注釈)から事実を出さず、抽出できなかった行として数える。rustfmt が表示の幅を超えて複数の行へ折った `const` の宣言は、抽出器が `;` まで繋いだ1つの文として読み、出どころを書き出しの行にする(`xtask/src/設計関係のモデル/設計関係の抽出/折れた役割の宣言.rs`)。

**定義の式は、生の `fn f(a: A) -> B` から `A を消費する`・`B を生成する` を導く規則を持たない。** 定義の式がその規則を持つと、関数の引数と戻り値という言語の形がそのまま設計の意味になり、定義の式は、設計として説明可能かを問う力を失う。関数の署名から導くのは、コードの形を語るプリミティブな関係(`引数に取る`・`返す`)だけである。

定義の式は、関係の目的語を型の表記から読む。この読み方(型の表記の読み方)は、関数の署名が語る6つ(関連関数として持つ・受け手に取る・引数に取る・そのまま受け取る・返す・そのまま返す)を除く6つの関係に共通である。包みの剥がし方とフレーム型の一覧が「フィールドに持つことが何を保持することか」の定義の一部であるため、この読み方は事実の側でなく定義の式の側に在る(`crates/blitz_design_verification/src/導出/型の表記の読み方.rs`)。

- 読み方は、外側の包み(`Vec`・`Option`・`Box`・`BTreeSet`・`Arc`)を剥がして中身の型を目的語にし、プリミティブ(数値・真偽・文字列)と、値を1つも持たない標準の型 `std::convert::Infallible`(失敗しない遷移が失敗の位置に置く型。修飾まで一致する表記だけ)を目的語にしない。この3つが、黙って対象から外してよいと書き下せる条件である。`Arc` を剥がすのは、`M不変データ` の型が `M共有される不変データ` の型を共有して持つ形(2.5.3 の共通の法則3)も中身の型を保持することであるためであり、`Arc` だけは修飾した表記を標準の `std::sync::Arc` と `alloc::sync::Arc` に限る(同じ名前の別の型と取り違えないため)。
- 読み方は、剥がす包みでない総称の型のうち、座標系を型引数に取る `blitz_math` のフレーム型の一覧に載った型(`位置`・`変位`・`方向` など17件。正本は `crates/blitz_design_verification/src/導出/表記が名指す型の定義.rs`)だけを、型引数を含む表記の全体を1つの型として目的語にする。`変位<ワールド>` と `変位<ローカル>` はRust上で別の型であるため、読み方は節点の同一性の名前へ座標系を含め、定義は座標系を落とした名前で探す。`blitz_math` は適用範囲の外であるため、この節点は `メートル` と同じく、定義をたどれずモジュールパスが空になる。一覧が `blitz_math` の実物と過不足なく一致することは、実物を走査する試験(`xtask/src/設計関係のモデル/設計関係の抽出/フレーム型の一覧の実物との突き合わせの試験.rs`)が確かめる。
- 読み方は、受理するかどうかを型引数の形で決めない。型引数の形で決めると、`Handle<メッシュ>` のように型引数の側が関係の相手である型にも当たり、内側の型への関係を黙って捨てることになるためである。
- 読み方は、一覧に無い総称の型・フレーム型でありながら型引数が座標系の名前だけの並びでない表記・パスの修飾が付いた表記・配列やタプルや関数ポインタを、読めない表記として導出の欠けに数える。表記を書いた場所で有効な型引数の名前(`struct 包み<状態> { 中身: 状態 }` の `状態` や `変位<空間種>` の `空間種`)は設計概念でないため、読み方はそこから関係を導かず、導出の欠けに数える。
- 定義の式は、名指した型の定義の在り処を、抽出器が実装する定義の探索の口(`型の名前の定義の探索`)へ、型かトレイトかの種類を添えて問う。抽出器は、型なら `struct`・`enum` の宣言を、トレイトなら `trait` の宣言を、同じ探し方(同じファイルの定義・`use` の取り込み・再公開)で探す(`xtask/src/conform/設計オントロジーの規約検査/type_definition.rs` の `探す定義の宣言の種類`)。署名の読み方が `impl トレイト`・`dyn トレイト` から名指したトレイトは、こうしてトレイトの本体の関数の所有者と同じ節点になる。修飾の無い名前が、書いた位置の `use` で標準ライブラリ(`std`・`core`・`alloc`)から取り込んだ名前(`use std::fmt::Display;` の後の `Display`)か、同じクレートに定義も取り込みも無いプレリュードのトレイトの名前(`Clone`・`Iterator` など)なら、定義の探索の口は標準ライブラリの項目であると答え(`修飾の無い名前の定義を探した結果`)、定義の式は修飾して書いた名前と同じく関係を導かない。書き方によって同じ標準ライブラリの項目の扱いが変わらないためである。ただし、書いた位置から一括取り込み(`use a::*;`・`pub use a::*;`。取り込み元のモジュールの公開された名前を全部まとめて取り込むこと)が見えるときは、プレリュードの名前であることだけを理由に標準ライブラリの項目と答えない。一括取り込みはプレリュードの名前を隠す名前(自作の `trait From`)を持ち込みうるためである。抽出器は、標準ライブラリの外の取り込み先ごとに、その名前が持ち込まれるかを求める。取り込み先の直下に定義があるか、その名前を名乗る再公開の先に定義があれば定義がある、取り込み先の直下に定義もその名前を名乗る取り込みも一括取り込みも無ければ確かに無い、取り込み先がさらに一括取り込みを持つか走査したソースに無いモジュールなら先をたどれない、と答える(`xtask/src/conform/設計オントロジーの規約検査/type_definition/一括取り込み先の探索.rs`)。1つでも先をたどれなければ定義をたどれないと答え(黙って標準ライブラリにしない)、定義が1つだけ見つかればその定義を答える。どの取り込み先にもその名前が確かに無ければ、その一括取り込みからは来ないため、見える一括取り込みが標準ライブラリのモジュールだけのときと同じく、標準ライブラリの一括取り込みとプレリュードの名前から標準ライブラリの項目であると答える(`xtask/src/conform/設計オントロジーの規約検査/type_definition/標準ライブラリの名前.rs`)。取り込み先が `Clone` を定義していないのに定義をたどれないと答えると、`use super::*;` を書いたファイルの `impl Clone for 状態` の関数を除外できず、状態を受けて返す処理の宣言の法則の偽の反例になるためである。定義をたどれない型について、定義の式は節点を落とさずモジュールパスを空にした節点を当て、導出の欠けを1件数える。

抽出器は、導出の欠けを抽出できなかった行へ写して数える。そのうち設計関係そのものを組めなかった行が、検証器へ渡す関係を落とした抽出の欠落になる(第9節)。

この4語の設計の関係は最終語彙ではなく、実際の設計を記述・検査できるかを確かめるための最小の実験の集合である。実装者は、不足が実測で出た関係だけを足す。実装者は、関係を宣言する専用のトレイトを先に増やさない。既存のRustの構文と設計解釈マーカーと関数の役割から一意に定義できない関係が現れたときにだけ、実装者は明示の宣言を検討する。

抽出器と定義の式は検証系の信頼基盤である。どちらかが誤った設計関係グラフを作れば、その上で示した命題の成立は意味を持たない。そのため実装者は、事実の読み取りの規則1つごとに「このRustの構文からこの事実が出る」を固定する回帰試験(`xtask/src/設計関係のモデル/設計関係の抽出/` の試験)を置き、定義の式の規則1つごとに「この事実からこの関係が出る」を固定する回帰試験(`crates/blitz_design_verification/src/導出/導出の試験.rs`)を置く。

### 6.6 設計関係グラフ

設計関係グラフとは、設計概念を節点、設計関係とプリミティブな関係を有向の辺、分類を節点のラベルとして持つ、検証の対象になるグラフのことである。設計関係グラフは設計関係とプリミティブな関係を別の一覧として持ち、同じ種類の辺として混ぜない(`crates/blitz_design_verification/src/設計関係グラフの定義.rs`)。プリミティブな関係の辺とその問いは、グラフが保持する部分の型 `プリミティブな関係の一覧` が持つ(`crates/blitz_design_verification/src/設計関係グラフの定義/プリミティブな関係の問い.rs`)。

関係の主語と目的語は、設計概念そのものではなく`設計概念への参照`(設計概念の識別子と設計概念の種類の組)である。実装者は、種類を識別子(同一性)へ入れない。理由は2つある。第一に、実装者が種類を同一性へ入れると、同じ識別子へ種類の違う概念が現れるという事象が原理的に起こらなくなり、`設計関係グラフ`が検出すべき同一性の衝突の報告が1度も実行されない経路になる。第二に、定義の式は目的語の種類を推測しており(表記が名指す型を無条件に型として当てる)、実装者が種類を同一性へ入れると、推測で当てた節点と正しい種類の節点が別の節点へ割れて辺が散る。正本は`crates/blitz_design_verification/src/concept/reference.rs`と`crates/blitz_design_verification/src/concept.rs`の冒頭のコメントである。ただし識別子の名前空間は、Rustと同じく型の名前空間(構造体・列挙・トレイト)と値の名前空間(関数)に分ける。Rustは同じモジュールに同じ名前の型と自由関数を書けるため、1つの名前空間にまとめるとその2つが同じ識別子になり、同一性の衝突が全部の答えを弱める。型とトレイトは同じ型の名前空間に住むため、種類の推測を外した箇所は同一性の衝突として数え続ける(`crates/blitz_design_verification/src/concept/identifier.rs`)。

抽出器は、`blitz_design`と`blitz_esca`と`blitz_game`の本番のソースを同じ対象範囲とする。抽出器は各クレートの`src/lib.rs`と`src/main.rs`からモジュール宣言を辿り、参照されないファイルと`#[cfg(test)]`の項目・子孫モジュールを除く。試験専用のエンティティは、本番の対象集合を非空にしない。抽出器は`cfg(not(test))`を本番として受理し、その他の条件・辿れないモジュール・同一行の複数項目など除外の境界を判断できない構文を欠落として報告する。抽出器は範囲外のクレートの定義やマーカー実装を読まない。範囲内から参照する外部型のうち、標準の`Result`への正本の包括実装だけは特例であり、定義をたどれない外部型の同一性はモジュールパスが空のまま残る。

設計関係グラフは、各端点と識別子・種類が一致する節点の存在を組み立て時に確かめる。グラフは一致しない端点を報告し、その辺を証拠や経路に使わない。グラフは分類の事実の端点も同じに扱う。構造の検証器は、この欠落があるとき、関係の不在から証明済み・反証済みを導かない。量化は参照全体で重複を1つにまとめるため、同じ識別子の型とトレイトを別々の対象として残す。

**設計関係グラフは、設計関係への参加を設計関係の辺だけで数える。** ある概念が設計関係へ参加しているとは、その概念が1本以上の設計関係の主語か目的語であることである。プリミティブな関係(保持する・関連関数として持つ・受け手に取る・引数に取る・そのまま受け取る・返す・そのまま返す)は設計の意味を持たないため、設計関係グラフはプリミティブな関係の辺を参加に数えない。分類は辺でないため、設計関係グラフは分類も参加に数えない。したがって、フィールドに持つだけの型も、マーカーを実装しただけの型も、設計関係へ参加していない。

この数え方では、フィールドとして持たれるだけの型(`経過時間`・`移動の変位`・`歩行の規則` などの値オブジェクト)は、関数の役割の型引数に直接現れない限り、設計関係へ参加しない。Issue #175 の第2段階が関数の署名から導くのは `引数に取る`・`返す` などのプリミティブな関係だけであり、設計の関係を導かないため、この型の参加は署名の事実によっても増えない。2026-09-26 にオーナーは、「すべてのドメイン概念は、少なくとも1つの設計関係へ参加する」という全称の命題を検証へ接続することを見送った。型の存在理由は、全概念の参加でなく、設計解釈マーカーの分類ごとの公理(第8節の存在理由の公理)で問う。設計関係への参加の計測(`cargo xtask design-verify`。`xtask/src/設計の検証/設計関係への参加の計測.rs`)は、命題へ接続しない材料として表示を続ける。

## 7. ドメインモデルとアプリケーションモデル

ドメインモデルとは、設計概念を節点とし、設計関係とプリミティブな関係を辺とし、分類を節点のラベルとして組んだ、検証の対象になるモデルのことである。いまのドメインモデルの実体は設計関係グラフ(6.6節)である。

アプリケーションモデルとは、ドメインモデルに、`main` とコンポジションルートが実際に構成した配線と、そこから到達できる処理の経路を加えたモデルのことである。

型として存在することと、完成したアプリケーションでその経路が使われることは別である。最終の判定の対象はアプリケーションモデルである。

2026-09-21時点の実装は設計関係グラフ(層1と層2の前半)までである。アプリケーションモデルの構成は別issueへ切り出す。切り出しの形は「何を作るかは確定しており、どこで実行するかが未確定である」である。

### 7.1 層の置き場

層の置き場は3つに分かれる。

```text
blitz_design(設計解釈マーカー。依存ゼロ)
    ↑
blitz_design_verification(命題・原子命題・検証結果・証拠・反例・検証器の共通語彙の正本。通常依存は blitz_design だけ)
    ↑                                        ↑
  xtask(Rustのソースを読む抽出と構造の検証)   ドメイン側の試験(実物の遷移関数を呼ぶ振る舞いの検証)
```

命題の型を1つのクレートへ置くのは、構造の検証と振る舞いの検証が同じ `命題` の型を語らなければ、構造の原子と振る舞いの原子を1つの連言へ結べないためである。写しを置くと、`cargo xtask conform` 自身が持つ「正本と写しで同じ値を持つべき定数の一致」の検査の精神に反する二重の台帳になる。

`blitz_design_verification` はドメインのクレートも `xtask` も知らない。振る舞いの検証が実物の遷移関数を呼ぶために、ドメインの側が `有限に数え上げられる領域` を実装する。この向きであるため、検証の語彙がドメインを知る必要が無い。

`xtask` がこのクレートへ依存することは、依存の白リストの例外である。理由は台帳(`xtask/src/conform/dependency_whitelist/ledger.rs`)へ書いた。

2026-09-22のオーナー裁定。Issue #174。

## 8. 命題(Proposition)

命題とは、ドメインモデルまたはアプリケーションモデルについて真偽を問う式のことである。

設計関係と命題は別の概念である。設計関係はモデルの中の関係であり、命題はその関係について真偽を問うものである。

命題は次の3種類を持つ。

- **構造の命題**: モデルの静的な形について真偽を問う命題である。例は「すべての `Mコマンド` は `enum` である」「`M状態` を実装する型は `M観測` を実装する型を保持しない」の2件である。
- **振る舞いの命題**: 遷移モデル(第10節)の到達可能な状態と遷移について真偽を問う命題である。例は「到達可能な状態のうち、体力が0の状態から歩行のコマンドを受けても新しい歩行イベントは発生しない」「休止した接触島は、外力が加わらない限り再開しない」の2件である。
- **設計の受理の命題**: 第11節が定める設計の受理条件について真偽を問う命題である。例は「すべてのドメイン概念は、少なくとも1つの設計関係へ参加する」「新しい概念は、既存の概念と区別される設計関係または法則の上の差分を持つ」の2件である。前者は、2026-09-26 のオーナーの裁定で検証へ接続しないと決めた(6.6節)。

命題の最小の構文は、原子・否定・連言・選言・含意・全称・存在の7つとする。

実装者は、連言と選言の項の並びを1件以上とし、型で保証する。数学の上では空の連言は真であり空の選言は偽であるが、検証器のAPIが意図せず0件になった要求の集まりを受理してよいことはそれとは別である。0件の連言は要求を1件も見ないまま証明済みになり、0件の選言は否定の下で同じ偽の証明を作る。同じ理由で、実装者は推論規則の前提も1件以上とする。前提が0件の推論規則は、前提を全部証明したという条件が1回も確かめられずに成り立ち、任意の結論を証明済みにできる。

原子命題は次の9つとする。前の6つが構造の原子命題であり、構造の検証器が設計関係グラフへ問う。後の3つが振る舞いの原子命題であり、有限全数の検証器が遷移モデルへ問う(`crates/blitz_design_verification/src/原子命題の定義.rs`)。

| 原子命題 | 問うこと | 定義域と数え方 |
|---|---|---|
| `設計関係が在る` | 主語から目的語へ、その種類の設計関係の辺が1本でも在るか | 種類は設計の関係の4語のどれかである。プリミティブな関係の辺を拾わない |
| `設計関係の経路が在る` | 主語から目的語へ、その種類の設計関係の辺だけを辿って達する経路が在るか | 直接の辺1本も経路に数える。プリミティブな関係の辺を辿らない |
| `プリミティブな関係が在る` | 主語から目的語へ、その種類のプリミティブな関係の辺が1本でも在るか | 種類はプリミティブな関係の7語のどれかである。設計関係の辺を拾わない |
| `プリミティブな関係の経路が在る` | 主語から目的語へ、その種類のプリミティブな関係の辺だけを辿って達する経路が在るか | 種類が保持するなら間接の保持(`旅行者` が `現在地` を持ち、`現在地` が `東西の位置` を持つ)を問う |
| `マーカーを持つ` | その型の分類が、その名前の設計解釈マーカーを含むか | 辺でなく分類(6.3節)を問うため、上位トレイトの宣言で閉じたマーカーでも成り立つ。定義域は型の主語と設計解釈マーカーの名前である(第9節) |
| `設計関係へ1つも参加していない` | その概念が、主語としても目的語としても、設計関係に1本も参加していないか | 設計関係の辺だけを数え、プリミティブな関係の辺と分類を数えない(6.6節) |
| `発生する` | その遷移でその出来事が成立するか | 振る舞いの原子命題である |
| `遷移する` | 前状態へその入力を与えると後状態へ移るか | 振る舞いの原子命題である |
| `到達可能である` | その状態が初期状態から到達できるか | 振る舞いの原子命題である |

`設計関係が在る` と `設計関係の経路が在る` は別の問いである。前者はソースがその関係を直接宣言しているかを問い、後者はその関係が宣言の連なりで推移的に成り立つかを問う。書き手は法則ごとにどちらかを選ぶ。保持するの2つの原子命題も同じ関係にある。書き手が保持するを問う原子命題を設計関係の原子命題と別に置くのは、保持するがプリミティブな関係であり(6.1節)、`設計関係が在る` にコードの形まで問わせないためである。

実装者は、4つの設計の関係の語を原子命題の4つの選択肢へ展開しない。`設計関係が在る { 種類 }` の1つで足りる。展開すると、関係の語を1つ足すたびに原子命題の選択肢と検証の場合分けが1つずつ増える。

**存在理由の公理。** 存在理由の公理とは、ある設計解釈マーカーを名乗る型が、関数の役割の宣言を通して処理に使われていることを求める構造の命題のことである(2026-09-27 のオーナー裁定。Issue #175)。目的は、コマンド等の型にマーカーが付いているのに、それを使う関数に関数の役割の宣言が漏れている状態を見つけることである。例として、`進行の操作` を使う `ゲームの進行段階::次の段階を決める` は意味の上で遷移であり、宣言が無ければ `進行の操作` を消費する処理がグラフに現れず、公理の反例になる。`cargo xtask design-verify` は次の6つの公理と、その後に述べる状態を受けて返す処理の宣言の法則(A7)の7つを検証し、反証済み・未決定・命題の集合が問う答えを弱める抽出の欠落のどれかが1件でもあれば失敗する(2026-09-27。Issue #175 の第1段階の検収で親が採った指摘。未決定と欠落を合格へ写すと、抽出が関係を落としたときに公理が何も確かめないまま検証が通るため)。この入口は `cargo xtask verify` の検証の列に入っている。

| 公理 | 命題 |
|---|---|
| A1 | すべての `Mコマンド` は、いずれかの処理に消費されるか、処理に消費される `MParameter` に推移的に保持される |
| A2 | すべての `M規則` は、いずれかの処理に参照されるか、処理に参照される `M規則` か処理に消費される `MParameter` に推移的に保持される |
| A3 | すべての `M状態` は、ある1つの処理に消費されかつ次の状態として生成されるか、そういう処理に消費される `M状態` に推移的に保持される |
| A4 | すべての `M解釈前の入力` は、いずれかの処理に消費されるか、処理に消費される `M解釈前の入力` か `MParameter` に推移的に保持される |
| A5 | すべての `Mイベント` は、いずれかの処理に生成される |
| A6 | すべての `M命令の組` は、いずれかの処理に消費されるか、処理に消費される `MParameter` に推移的に保持される |
| A7 | すべての `M状態` s とすべての処理 p について、p が s を受け手に取るかそのまま受け取り、かつ s をそのまま返すなら、p は s を消費しかつ次の状態として生成するか、s を書き換える |

どの公理も、原子命題 `設計関係が在る` と `プリミティブな関係の経路が在る { 種類: 保持する }` と量化で書く(`xtask/src/設計の検証/構造の法則.rs`)。A3 だけは、同じ1つの処理が状態を消費しかつ次の状態として生成することを求め、`MParameter` を容器に数えない(2026-09-27。Issue #175 の第1段階の検収で親が採った指摘)。状態から値を取り出すだけの射影と、状態を引数の束が運ぶだけの形は、その状態を次の状態へ進める処理が無く、状態の存在理由にならないためである。A1・A2・A4 が処理に消費される `MParameter` を容器に数えるのは、意味の決まった値を関数へ渡す1つの引数へまとめた型を `MParameter` が名乗る(2.6節)ためであり、そうして渡された値も処理に使われているためである。`blitz_game` の胴体の移動の遷移は、`胴体の移動の命令の組` をコマンドの位置で受け取り、直に消費する(3.5.1。遷移パラメータにコマンドを入れない)。組が持つ `水平移動の操作` と `ジャンプの操作` は、命令の組を通した消費の規則(6.5節)によってその遷移に消費され、A1 を満たす。A6 は 2026-09-28 の命令の組の裁定で足した。組のコマンドが別の宣言でも直に消費されていると、組を受け取る関数に関数の役割の宣言が漏れていても A1 は通る。組そのものの消費を求めることで、その漏れを見つける。容器は A1 と同じく処理に消費される `MParameter` である。かつて置いていた法則「`Mエンティティ` を名乗る型は設計関係へ1つ以上参加している」は外した。`Mエンティティ` は識別子の関連型をコンパイラが要求し、定義の式が必ず識別するの関係を張るため、構造上つねに真であるためである。

**状態を受けて返す処理の宣言の法則(A7)。** A7 は、状態を受けて同じ状態を返す関数が、遷移の役割の宣言か規則によらない書き換えの役割の宣言に包まれていることを求める構造の命題である(2026-09-28 のオーナー裁定)。目的は、遷移の関数に関数の役割の宣言を付け忘れたことを見つけることである。A1 から A6 は型の側から「その型を使う処理があるか」を問うため、同じ状態を別の宣言済みの遷移が使っていると、付け忘れた関数を見つけられない。A7 は処理の側から問う(`xtask/src/設計の検証/構造の法則/状態を受けて返す処理の宣言の法則.rs`)。前件はプリミティブな関係 `受け手に取る`・`そのまま受け取る`・`そのまま返す` で書く。`そのまま受け取る` は `そのまま返す` と同じ範囲を引数の側で読み、状態を引数そのもの(参照を含む)か `Result`・組・意味型の成分か `Box`・`Arc` の中身として受け取ることであり、スライス・`Vec`・`Option` の中や `impl Fn(状態)` として受け取ることを含まない。`fn 選ぶ(候補: &[状態]) -> 状態` のように候補の中から1つを選ぶ関数と、状態を作る関数を受け取る関数は、状態を次の状態へ進めないためである。受ける側を `引数に取る`(包みとトレイトの中まで読む)で書くと、これらの関数にまで遷移の宣言を求める。`そのまま返す` は状態を戻り値そのものか `Result`・組・意味型の成分か `Box`・`Arc` の中身として返すことであり、`Vec`・`Option` の中や `impl Iterator<Item = 状態>` として返すことを含まない(6.5節)。候補を並べる関数や次の値を順に渡す関数は遷移でないためである。後件は設計の関係で書き、遷移の役割はその処理が状態を `消費する` かつ `生成する` こと(A3 と同じ見分け方)で、規則によらない書き換えの役割は状態を `書き換える` ことで見分ける。射影の型が入力の状態をそのまま、または包み(`Vec`・`Option`・`Box`・`Arc` など)の中に持つ射影関数の宣言(`M射影関数<状態, 状態>`・`M射影関数<状態, Vec<状態>>`)は、状態から別の値を取り出すという射影関数の定義(第3節)に反し、定義の式が包みを剥がして状態を消費しかつ生成すると導くため A3 と A7 の抜け道になる。そのため `cargo xtask conform` が違反にする(`xtask/src/conform/射影関数の宣言の検査.rs`)。**標準ライブラリ(`std`・`core`・`alloc`)のトレイトの実装の関数は、A7 の前件から外す。** 手で書いた `impl Clone for 状態 { fn clone(&self) -> Self }` や `impl Add for 状態` の関数は状態を受けて同じ状態を返すが、言語の決まりごとであってゲームの操作ではないためである。抽出器がこれらの関数の署名を読まず、明示して除外した区分に件数を数えるため(6.4節)、前件の関係が導かれない。このクレートや外部のクレートで宣言したトレイトの実装の関数は外さない。**A7 が見逃す形。** 状態を `Option` の中に入れて返す遷移(終わったら無しを返す遷移。`fn 進める(self) -> Option<Self>`)は、A7 の前件に当たらない。`そのまま返す` が `Option` の中を読まないためである(6.5節)。`Option` の中を読むと、候補の中から次の1つを探す関数(`fn 次(&self) -> Option<状態>`)も前件に当たり、遷移でない関数に宣言を求める。この形の遷移に関数の役割の宣言を付け忘れても A7 は反例を出さず、状態の存在理由の公理(A3)が型の側から問うだけである。**境界付きの総称で状態を受けて返す関数(`fn f<S: M状態>(s: S) -> S`)は、A7 の対象外である。** 署名の読み方が型引数を境界のトレイト `M状態` として読むため、その関数が受けて返すのはトレイトの節点であり、`M状態` を名乗る型ではなく、A7 の量化(`M状態` を分類に持つ型)に入らないためである。A7 は全ての処理を量化するため、どの種類の答えを弱める抽出の欠落も A7 の答えを弱め(9節)、設計の検証の合否に効く。

**反例の片付け方。** 公理の反例が出たとき、実装者は、型の側を直して反例を片付ける。直し方は3つある。型を使う関数へ関数の役割の宣言を足す。どの処理にも使われない型を消す。型の実体と合わないマーカーの付け違いを直す。実装者は、公理のほうを緩めて反例を消さない。

仕様とは、アプリケーションが満たすべき命題の集合のことである。仕様は実行時のデータの種類ではない。実装者は、Rustの型の名前を `仕様` にせず `命題の集合` とする(2026-09-20のオーナー裁定とIssue #171)。

本書は、法則(Law)を2種類に分ける。普遍命題としての法則とは、対象の全部について成り立つと主張する命題のことである。推論規則としての法則とは、前提の命題から結論の命題を導く規則のことである。後者の例は排他の推論規則である。2つの事象が排他であるとき、片方が発生するなら他方は発生しない。これにより、実装者は否定の仕様をコードへ直接埋め込まず、正の仕様と排他の法則から否定の命題を導ける。

## 9. 検証と証拠

検証器とは、1つの命題を受け取り、証明済み・反証済み・未決定のどれかで答える道具のことである。

検証器の一覧と、それぞれが証明する対象は次のとおりである。

- **コンパイラ**: 上位トレイトの実装関係、関連型の存在、関数の役割の型引数の境界を保証する。
- **構文の検査**: `Mコマンド` が `enum` であることのような、構文パターンに対する法則を保証する。
- **設計関係グラフ**: 第6節の設計関係とプリミティブな関係が在ることと無いこと、型の分類が設計解釈マーカーを含むことと含まないこと、概念が設計関係へ参加していることと参加していないことを保証する。
- **有限全数**: 有限の遷移モデルの全状態・全遷移を数え上げ、振る舞いの命題を証明する。
- **反例の探索**: 生成した入力の一部を試し、反例が見つかればその命題を反証する。
- **記号実行**: 実行経路を記号のまま辿り、条件を満たす反例または証明を導く。
- **SMT(充足可能性を判定する理論の集まり)**: 記号実行が導いた制約式の充足可能性を判定する。

記号実行とSMTは、作ることは確定しており、どう作るかが未確定である。実装者はこの2つを別issueで設計する。

推論規則が導いた結論の証拠は、検証器が結論を直に示した証拠と別の出自であるため、方式として `推論` を名乗る。実装者は、前提を示した方式のどれか1つを結論の証拠へ引き継がない。引き継ぐと、その結論がその方式で直に示されたものと読める。前提を示した方式の一覧は、証拠の説明の文が前提の並びの順で並べる。

実装者は、`bool` を返す検証器のメソッドを作らない。真偽の2値では、「全対象について成立を示せた」と「この検証器では成立も反例も確定できなかった」が同じ偽へ潰れる。

実装者は、「反例の探索で反例が出なかった」を「証明済み」と呼ばない。有限の対象を全部列挙できたときだけ証明済みとし、生成による一部の探索は「未決定。探索の範囲では反例が無い」とする。

実装者は、空の対象集合の全称を証明済みにしない。論理としては空集合上の全称は真だが、検査器としては誤りである。対象集合が0件のとき検証器は未決定で答える。これはグローバル規約「検査器は解析できなかった入力を黙って対象から外してはならない」(2026-09-05制定)の同型である。

実装者は、定義のモジュールパスを求められなかった型を、節点から落とさない。落とすと「関係が無い」と読まれ、偽の反証が出る。偽の反証は偽の証明より運用の被害が大きい。実装員が正しいコードを直しに行くためである。モジュールパスが空の節点に触れた評価は未決定で答える。さらに、問いの端点と同じ名前・同じ所有者の並び・同じ種類でモジュールパスが空の節点がグラフに在り、その空の節点がその問いの問う答えの種類の辺か分類を持つとき、定義をたどれた節点への問いの、不在から導いた結果も未決定で答える。抽出器がどこかの表記か実装の対象からその型の定義をたどれなかったなら、そこから導いた辺と分類は空の節点へ付き、定義をたどれた節点へは付かない。定義をたどれた節点への問いは空の節点に触れないまま辺か分類の不在を答えるため、この止めが要る。この取り違えは、表記が関係の頭の端点にあっても、規則の本体の途中にあっても、マーカーの実装や `Mエンティティ` の実装の対象であっても同じ形で起きるため、構造の検証器は不在に由来する結果を弱める1か所(`crates/blitz_design_verification/src/verifier/構造の検証/原子命題の問い.rs` の `不在に由来する結果を弱める`)で止める。止めは不在から導いた結果だけに掛け、辺が在ると答えた問いには掛けない。空の節点が問わない答えの辺しか持たないとき(関数の署名が引数から作った空の節点が引数に取るの辺だけを持つとき)にも掛けない。無条件に掛けると、証明できる問いと、署名と関係の無い設計関係・保持する・分類の問いまで未決定になるためである。規則の本体の途中の変数(頭に現れない経由する概念と、本体が分類を問う変数)へ当てた、モジュールパスが空の節点については、抽出器が重ねてこの欠け(`名指せなかった変数の位置` が本体の途中である欠け)を関係を落とした抽出の欠落へ数え、その規則の頭の関係の答えを弱める。本体の途中の変数の定義をたどれないときは、本体が成り立たずに頭の関係ごと落ちるため、問いの両端のどちらにも同じ名前の空の節点が無いことがある(命令の組の型をたどれず、組の中のコマンドへの消費を問うとき)。そのとき問いの側の止めは効かず、欠落の弱めだけが偽の反証を止める。

経路の問い(`設計関係の経路が在る`・`プリミティブな関係の経路が在る`)では、割れた節点が問いの両端でなく辿る途中に在ることがある。容器 A のフィールド `x: X` から X の定義をたどれないと、辺は A から空の X へ付き、X から T への辺は定義をたどれた X に付くため、A から T への探索は空の X で途切れる。そこで経路の探索(`crates/blitz_design_verification/src/設計関係グラフの定義/経路.rs`)は、達した節点と名前・所有者の並び・種類が同じで定義をたどれたかだけが違う節点が、辿る種類の出る辺を持つなら、その節点で先を辿れないと答え、構造の検証器はその答えを未決定(`型の定義のモジュールパスが求まっていない`)にする。探索は割れた2つの節点を1つへまとめて辿らない。空の節点が本当にその型かを抽出器が確かめていないためである。定義をたどれた相方を持たない空の節点(適用範囲の外の型)は先へ続く辺を持ちえないため、探索はそこで止めない。

実装者は、抽出器が設計関係そのものを組めなかった箇所(関係を落とした抽出の欠落)が在るとき、その欠落が弱める答えに当たる原子命題の、辺の不在に由来する結果を未決定で答える。対象は、反証済みを答える側の原子命題(`設計関係が在る`・`設計関係の経路が在る`・`プリミティブな関係が在る`・`プリミティブな関係の経路が在る`・`マーカーを持つ`)と、証明済みを答える側の原子命題(`設計関係へ1つも参加していない`)の両方である。この2つの側はどちらも、辺か分類の事実が見つからなかったことだけを根拠にした結果であり、抽出がその答えを導く事実を落としているなら、その不在は信用できないためである。

欠落が弱める答えとは、欠落した事実のために不在を根拠にできなくなった答えの種類のことであり、設計関係の種類ごとの在り方・プリミティブな関係の種類ごとの在り方・分類の3つに分かれる。欠落の1件は、それが弱める答えの並びを持つ。原子命題ごとに問う答えは決まっている。`設計関係が在る` と `設計関係の経路が在る` はその種類の設計関係を、`プリミティブな関係が在る` と `プリミティブな関係の経路が在る` はその種類のプリミティブな関係を、`マーカーを持つ` は分類を問う。`設計関係へ1つも参加していない` は全ての種類の設計関係を問い、プリミティブな関係と分類を問わない。プリミティブな関係の辺と分類は参加に数えないため(6.6節)、その欠落は参加の答えを変えない。検証器は、原子命題の問う答えを弱める欠落が1件でも在るときだけ、その原子命題の不在に由来する結果を未決定にする。別の答えを弱める欠落は、その原子命題の答えを変えない。絞る理由は、関数の署名の型の表記のように読めない表記が多く出る事実を足したとき、その欠けが無関係な保持する関係や別の種類の設計関係の答えまで未決定へ倒し、存在理由の公理が答えを失うためである。原子命題ごとの問う答えと対象集合ごとの列挙が依る答えの対応は、`crates/blitz_design_verification/src/命題が問う答え.rs` の1か所が持ち、検証器と設計の検証の合否の両方がそこを読む。

**設計の検証の合否は、命題の集合が問う答えを弱める欠落だけを不合格に数える**(Issue #175 の第2段階の親の判断。`xtask/src/設計の検証/設計の検証の合否.rs`)。命題の集合が問う答えとは、集合の全ての命題の原子の問う答えと、量化の対象集合の列挙が依る答えを、重ねずに並べたものである(`命題の集合::問う答え一覧`)。欠落で不合格にする目的は、欠落が命題の答えを黙って弱めることを止めることであり、どの命題も問わない答えだけを弱める欠落は、どの命題の答えも弱めないためである。いまの命題の集合では、状態を受けて返す処理の宣言の法則(第8節の A7)が全ての処理を量化し、処理の列挙はどの事実を落としても欠けうるため、命題の集合は全ての答えを問う。したがって、いまはどの種類の答えを弱める欠落も合否に効く(`xtask/src/設計の検証/構造の法則/構造の法則の試験/構造の法則が問う答えの試験.rs` が固定する)。絞る仕組みは、命題の集合が一部の答えしか問わなくなったときのために残す。`cargo xtask design-verify` は、欠落の全件と、そのうち命題の集合が問う答えを弱める件数と、合否に効かない残りの件数を表示する。未決定と反証済みで不合格にすることは変えない。

欠落の1件が弱める答えは、抽出器が欠落を検証器へ渡すとき(`xtask/src/設計関係のモデル/設計関係の抽出/抽出の成果と欠け.rs` の `関係を落とした抽出の欠落へ写す`)に決める。欠落の行は2つに分かれる。1つは、定義の式が規則の本体で型の表記を読めなかったか、規則の本体の途中の変数へ名指した型の定義をたどれなかった導出の欠けであり、この欠けはそれを本体に持つ規則の頭の関係を持つ。この行は、その頭の関係の答えだけを弱める。もう1つは、抽出器がソースの構文から事実を作れなかった行(抽出器の保証範囲の外の構文の行など)であり、この行では主語が分からないが、どの種類の事実を読めなかったかは分かる。どの理由がどの種類の事実を読めなかったかは、抽出できなかった理由の区分(`xtask/src/設計関係のモデル/設計関係の抽出/抽出できなかった理由の区分の定義.rs`)が答える。この行は、その種類の事実を本体で読む定義の式の規則の頭の答えを全部弱め、読めなかった事実が分類の事実なら分類の答えも弱める。規則から求める(`定義の式::落とした事実が弱める答え一覧`)のは、事実の種類と答えの対応を表で持つと、規則を足したときに表を直し忘れ、新しい規則が導く関係の答えがその事実を落としても弱まらないためである。命令の組を通した消費の規則はフィールドの事実と分類を本体で読むため、フィールドか分類を読めなかった行は消費するの答えも弱める。本番のモジュールを丸ごと読めなかった行は、全ての答えを弱める。

`マーカーを持つ` は辺でなく分類(6.3節)を問う。分類を持つのは型だけであるため、この原子命題の定義域は、型の主語と、設計解釈マーカーの名前である。検証器は、定義域の外(トレイトや処理の主語、`Clone` のような設計解釈マーカーでない名前)を問われたとき、偽でなく未決定(問いの定義域の外である)で答える。偽で答えると、トレイトや処理の主語について分類の不在を「持っていない」と断定し、否定の下で証明済みへ反転するためである。量化の対象集合「マーカーを持つ設計概念」も同じ定義域を持ち、設計解釈マーカーでない名前を名指したときは列挙せず未決定で答える。

実装者は、同一性の衝突(同じ識別子へ種類の違う概念が現れたこと)と、関係の端点が節点を持たないことが在るときは、全ての答えについて辺の不在に由来する結果を未決定にする。同一性が信用できない状態のまま節点が2つに割れると、辺は割れた両方へ散り、片方の節点だけを見て辺が無いと判定してしまう。信用できない同一性の上で、不在を根拠に証明済みまたは反証済みを答えてはならない。

実装者は、命題が否定の下に置かれているかという状態を、原子の評価へ運ばない。原子の解き手は、結合を解く規則から独立に、その原子命題1つの成立だけを答える。この分離を守らずに否定の状態を原子の評価へ運ぶと、原子の解き手と結合の規則を分けた設計が壊れ、含意の前件・二重否定・量化の入れ子で符号が反転するたびに弱める向きを判定し直す必要が生まれ、その判定に誤りが静かに入る。実装者は、原子の結果が反証済み側か証明済み側かという向きだけを見て弱め、否定・含意・量化の側には手を入れない。

実装(`crates/blitz_design_verification/src/verifier/構造の検証/原子命題の問い.rs` の `不在に由来する結果を弱める`)は、原子命題の問う答えを弱める`関係を落とした抽出の欠落`が在るとき、辺の不在から導いた結果を、未決定の理由の選択肢 `関係を落とした抽出の欠落が在る` へ差し替える。理由の説明には、その答えを弱めた欠落だけを並べる。

実装者は、抽出器の保証範囲の外にあるRustの構文を、関係も出さず欠落にも数えない第三の状態へ落とさない。実装者が許す形は2つだけである。そのRustの構文を抽出器が正しく解析するか、解析対象であることは判ったが保証範囲の外であるとして`抽出できなかった行`(`関係を落とした抽出の欠落`の一部)へ倒すかである。あわせて`cargo xtask conform`は、抽出器が受理する正規形のRustの構文をリポジトリ全体へ強制し、保証範囲の外の構文が書けないようにする。正本は`xtask/src/conform/抽出器が受理する正規形の検査.rs`(検査そのもの)と`xtask/src/設計関係のモデル/設計関係の抽出/保証範囲の外の構文の定義.rs`(保証範囲の外の構文の列挙)である。

機械で保証できる法則と、意味の上の法則は次の表のとおり分ける。

| 検証主体 | 対象 |
|---|---|
| 機械で保証できる法則 | 上位トレイトの関係(コンパイラ)・`Mコマンド` が `enum` であること(構文の検査)・設計関係と保持する関係が在ることと無いことと分類(設計関係グラフ)・有限のモデルの全遷移についての振る舞いの命題(有限全数) |
| 意味の上の法則(機械が判定しないもの) | `M結果` が単なる状態の列挙ではないこと・`M観測` が正本ではないこと・新しい概念の粒度が妥当であること・名前が「これは何?」に答えていること |

### 9.1 網羅性と証拠の非対称

数え上げの網羅性とは、検証器が対象を全部並べられたか、標本に限るかの区別のことである。

網羅していない領域では、証拠の出方が命題の形によって非対称である。

| 命題の形 | 網羅して全件を数え上げたとき | 標本に限るとき |
|---|---|---|
| 全称が全件で成立 | 証明済み | 未決定(探索の範囲では反例が無い) |
| 全称命題の反例が1件 | 反証済み | 反証済み |
| 存在命題の実例が1件 | 証明済み | 証明済み |
| 存在命題の実例が0件 | 反証済み | 未決定 |

全称命題の反例と、存在命題の実例は見た範囲から得られるが、全称の成立と存在の不在は見ていない範囲に依る。

構造の検証器は、関係の抽出に欠落が在るとき、グラフから列挙した対象集合を全件と呼ばない。端点の欠けた関係をグラフが除くと、その関係だけを持つ主語も対象集合から消えるためである。どの欠落が全件を損なうかは対象集合で違う。全ての設計概念と種類で絞った設計概念は、読めなかった事実がどれでも節点を欠きうるため、欠落が1件でも在れば全件と呼ばない。マーカーを持つ設計概念は分類を弱める欠落が在るときだけ、ある種類の設計関係の主語はその種類の設計関係を弱める欠落が在るときだけ、全件と呼ばない。検証器は、残った対象の反例と実例をそのまま答え、全件の成立または実例の不在だけを未決定にする。

この非対称が `検証結果` の3値が在る理由そのものである。真偽の2値だと4行目の未決定が偽へ潰れ、「見ていない範囲に実例が居ない」と断定することになる。

連続量を含む領域は標本に限る。有限個の標本を証明済みと偽装しない。例として、`blitz_esca` の `旅行者の意図::歩く { 方向: 歩行方向 }` は `歩行方向` が東の比率と北の比率を持つ単精度2成分の連続量であるため、軸に沿う4方向の標本に限られ、その領域についての全称の命題は未決定で答える。

2026-09-22のオーナー裁定。Issue #174。

## 10. 遷移モデルと到達可能性

遷移モデルとは、前状態・入力・適用した規則・後状態・生成イベント・失敗を1件として持つ、遷移の集まりのことである。

実装者は、「Rustの型として組める状態」と「実際に到達する状態」を区別する。振る舞いの命題の対象は到達可能な状態と遷移である。

失敗した遷移はイベントを1件も生成しない。3.5.9節の遷移失敗結果と同じ法則である。

代表ケースは実在の `blitz_esca` の旅行者の移動である。命題は「区域の端で区域の外へ歩くと `旅行者の出来事::障害物に遮られた` が生じる」であり、ドメイン側の試験が実物の `旅行者の居場所::歩行を遷移する` を呼んで検証する(第1段階の長方形の移動可能範囲は、第2段階で1つの区域へ表し直した)。

検証の側は遷移の意味を1行も書き写さない。書き写せば Issue #173 が禁じた「検証入口がゲームロジックを再実装しない」の違反になる。実物を呼ぶ形にすることで、再実装が原理的に起こらない。

小さな人工のモデルは、検証器自身の単体試験のfixtureとしてだけ許す。実ゲームの仕様の代表ケースにも、受理の根拠の代用品にもしない。2026-09-21に `xtask` へ置いた有限の対戦進行の題材は、`blitz_design_verification` の `#[cfg(test)]` の中のfixtureへ移した。

### 10.1 状態の同一性と状態の名指し

状態の同一性とは、探索が2つの状態を同じ1件として扱ってよいかを決める判断のことである。

実装者は、状態の同一性と状態の名指しを別のメソッドに分ける。名指しは人が読む表示と命題が名指す先であり、位置をマスの番号へ丸めるように粗くしてよい。同一性は探索の済みの集合の鍵であり、異なる状態を同じ値へ写してはならない。

実装者は、名指しを同一性に使わない。使うと、表示のために粗くした名前がそのまま済みの集合の鍵になり、別の状態が黙って同じ1件として捨てられる。捨てた先を1件も辿らないまま、その探索が「全件を数え上げた」を名乗れば、未探索の状態を残したまま有限全数で証明済みが作れる。

領域の契約は、同一性が単射である(異なる状態が同じ同一性へ写らない)ことを要求しない。要求しても、契約を実装する側がそれを守るとは限らないためである。かわりに探索の側が検出する。探索は同一性ごとに代表の状態を控え、すでに代表が居る同一性へ代表と等しくない状態が写ったとき、その事実を数え上げの網羅性へ残す。その網羅性は `異なる状態に同じ同一性を与えた` であり、`全件を数え上げた` ではない。

この形が守るのは、嘘をつける経路を残したまま、嘘をついた結果が全件を名乗れないという1点である。実装者は、契約の文言で単射を求めるかわりに、破れたときに証明済みが出ないことを機械で保証する。

連続量を持つ状態の同一性は、領域の側が型で選ぶ。`blitz_esca` の旅行者の居場所の現在地(`旅行者の現在地`)は単精度を2つ持ち `Eq` も `Hash` も導出できないため、その領域は単精度のビットの並びへ写した `現在地のビット表現` を同一性に選ぶ。ビットの並びは丸めないため、同じマスの名前を持つ2つの現在地も別の状態として辿る。

失敗した遷移を表す節点の名前は、人が読む説明の文だけで作らない。同じ文面で失敗する別の遷移が1つの節点へ1つにまとめられ、検証がその2件を同じ失敗として読むためである。探索は、遷移1件を名指す識別子を名前へ入れ、探索の側の名前の空間へ置く。

### 10.2 名指しの衝突の検出と網羅性の優先順位

識別子は識別しなければならない。実装者は、領域が答える名指し(`状態を名指す`・`コマンドを名指す`・`出来事を名指す`)が単射であることを要求せず、かわりに探索の側でその破れを検出する。名指しは人が読む粗い表記であり、探索が同じ1件として扱ってよいかを決める識別子とは別に持つ。

探索は、名指しの台帳(`crates/blitz_design_verification/src/domain/exploration/naming_ledger.rs`)を通して名指しを頼み、互いに等しくない2つの値が同じ名指しへ写った事実をそこで検出する。名指しの台帳を経ずに領域へ直に名指しを頼む経路が1つでも在ると、その経路で異なる値に同じ名指しを与えたことだけが数えられない。

数え上げの網羅性の優先順位は、異なる状態に同じ同一性を与えたこと・異なる値に同じ名指しを与えたこと・上限で打ち切った・連続量の標本・全件の順である。実装者は、異なる状態に同じ同一性を与えたことを最も優先する。そこでは辿らなかった状態が在ることを、件数からも上限からも読めないためである。実装者は、異なる値に同じ名指しを与えたことを次に優先する。そこでは辿りが足りていても、モデルの上で互いに等しくない2つの値が1件の節点へ重なり、命題の層がその2つを区別できないためである。実装者は、上限で打ち切ったことを連続量の標本より優先する。打ち切った先を1件も見ていないためである。正本は`crates/blitz_design_verification/src/domain/exploration/coverage_basis.rs`と`crates/blitz_design_verification/src/coverage.rs`である。

## 11. 設計の受理

設計の受理とは、コードが動くことに加えて、その設計が説明可能であることを求める受理条件のことである。

受理条件は次の4種類を持つ。

- **肯定的な欲望**: システムが達成すべき機能や性質を求める欲望のことである。例は「遷移関数は与えられた状態とコマンドから次の状態を計算する」である。
- **否定的な欲望**: システムが陥ってはならない状態を避けることを求める欲望のことである。例は「休止した接触島は、外力が加わらない限り再開しない」である。
- **構造的な欲望**: システムの構造そのものが持つべき形を求める欲望のことである。例は「すべての `Mコマンド` は `enum` である」である。
- **認知的な欲望**: 設計を読む人間がその意味を理解できることを求める欲望のことである。例は「新しいドメイン概念の名前は、それが何であるかを単独で答える」である。

新しいドメイン概念について、実装者は次の6つの問いに答えられる状態を受理条件とする。それは何か。設計解釈マーカーと関数の役割は何か。どの設計関係に参加するか。どの法則と命題に参加するか。既存のどの概念と何を区別するために存在するか。なぜその粒度なのか。

機械化できる部分は命題として書く。「すべてのドメイン概念は、少なくとも1つの設計関係へ参加する」「新しい概念は、既存の概念と区別される設計関係または法則の上の差分を持つ」の2件である。前者は、2026-09-26 のオーナーの裁定で検証へ接続しないと決めた。型の存在理由は、設計解釈マーカーの分類ごとの公理で問う(6.6節・第8節)。

実装者は、日本語の識別子であることを可読性の達成とみなさない。
