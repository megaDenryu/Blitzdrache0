# 設計オントロジー

この文書は、共通設計語彙クレート `crates/blitz_design` が持つ設計解釈マーカーと関数の役割、およびUpdate型のEventの語彙とコード文法を定める設計正本である。マーカーの定義文は `_doc/計画/ユビキタス言語.md`「設計解釈マーカー」「M状態はM不変データである」「Mイベント」と同じ内容であり、本書はそれと矛盾しない。

## 1. 位置づけ

`blitz_design` は、Rust上の型が設計上何として解釈されるか(純粋な所有データ・状態・コマンド・イベント・規則・入力・観測・工程と、存在の分類である値オブジェクト・エンティティ・エンティティ識別子・不変エンティティ・可変エンティティ)を宣言する設計解釈マーカーと、射影・解釈という関数の役割を表す境界付きの newtype だけを持つ。このクレートはドメインの語彙を1つも持たない。

置き場の判定の基準は「その型が何について語るか」である。

- 実装者は、プログラムについて語る(型が設計上どの役割かを言う)ものを `blitz_design` に置く。
- 実装者は、シミュレーションについて語る(時間尺度・物理小刻み等)ものを `blitz_sim` に置く。
- 実装者は、Esca世界について語る(旅行者・移動可能範囲等)ものを `blitz_esca` に置く。

`blitz_design` は何にも依存しない最下層であり、`blitz_sim` と `blitz_esca` がこれを使う。実装は `crates/blitz_design/src/marker.rs`(マーカー)と `crates/blitz_design/src/function_role.rs`(関数の役割)にある。

## 2. 設計解釈マーカーの一覧と共通契約

設計解釈マーカーとは、Rust上の型が設計上何として解釈されるかを、メソッドを持たないトレイトの実装で宣言する印のことである。例外は `Mエンティティ`(2.5節)だけであり、`Mエンティティ` は識別子を返すメソッドを1つ持つ。どの値がそのエンティティの識別子なのかを機械的に取得できるようにするためである。

本節の表はデータの役割の軸と、処理の役割の軸のうちトレイトのマーカーである `M工程` を持つ。存在の分類(値オブジェクトとエンティティ)と変更可能性(不変と可変)の軸は 2.5 節が持ち、関数境界の役割(必須入力の束と任意の設定の束と評価の排他的な帰結)の軸は 2.6 節が持つ。表の中で `M不変データ` はデータの役割の一種ではなく、複数のデータの役割が共有する基底の契約であり、`M工程` はデータの役割に含めない(2.1節)。

### 2.1 オントロジーの層

基礎オントロジーは、次の6つの層に分ける。2.5.1 の軸の表は、このうち A から D をトレイトのマーカーの軸として写したものであり、E はマーカーの軸ではなく `blitz_sim` が持つ関係、F はまだ設計していない関係である。

```text
A. 値・存在の意味: M不変データ / M値オブジェクト / Mエンティティ / Mエンティティ識別子 / M不変エンティティ / M可変エンティティ
B. 因果モデル上のデータの役割: M状態 / M入力 / Mコマンド / M規則 / Mイベント / M観測
C. 関数境界の役割: MParameter / MOptions / M結果
D. 処理の役割: M工程 / M射影関数 / M解釈関数 / M遷移関数
E. 時間と寿命の関係: M時間尺度 / M時間局所状態 / M更新工程(blitz_sim が持つ)
F. アーキテクチャの関係: 状態とデータの正本 / 参照実装への準拠 / 境界 / 依存の向き / 配線(今後の設計対象)
```

- `M不変データ` は B のデータの役割の一種ではなく、複数のデータの役割が共有する基底の契約として扱う。A に置くのはそのためである。B の6つはいずれも `M不変データ` を上位トレイトに持つ。
- `M工程` はデータの役割に含めない。工程はデータではなく処理であり、D の処理の役割に置く。`cargo xtask conform` の一覧(`xtask/src/conform/design_ontology/syntax_patterns.rs`)も `M工程` をデータの役割の一覧から外し、処理の役割の一覧に持つ。正規形・別名・再公開・波括弧付きのモジュールの検査の対象からは外さない。
- D のうち `M射影関数`・`M解釈関数`・`M遷移関数` は境界付きの newtype(第3節)であり、トレイトのマーカーではない。
- 2.5.1 の軸の表が持つ存在の分類と変更可能性は、A を「同一性を持つか」と「自己変更を行うか」の2つの問いに分けたものである。

### 2.2 共通のマーカーへ昇格させる前の受理テスト

親と実装員は、ある語を共通のマーカーの候補にするとき、少なくとも次の2つを確かめる。

- **その語を型名として主語に置き、その型自身へ自然なメソッドを生やせるか。** `X.何かする()` と読んだとき、`X` がその振る舞いの自然な主体であるかを確かめる。主体として読めない語は、型の分類ではなくメタの語である。
- **一般的な設計用語が頻出することと、それが実行時の共通の型の分類になることは別である。** 曖昧な上位の語で異なる実体をまとめず、必要ならより具体的なドメインの語彙へ分解する。この受理テストの目的は概念を減らすことではない。

次の概念は共通のマーカーにしない。一般的な設計語をそのまま型の分類へ持ち込むと、上の2つの受理テストを通らないためである。それぞれの理由と、どう表すかは次のとおりである。

| 概念 | 共通のマーカーにしない理由 | どう表すか |
|---|---|---|
| 設定 | 「起動時に決まる」「外から与えられる」「長く保持される」はライフサイクルや利用方法の事情であり、型の本質ではない | 関数境界の役割なら `MParameter` か `MOptions`。起動設定やアプリケーション設定が要るなら具体のドメインの語彙として定義する |
| 仕様 | 仕様は実行時のデータの種類ではなく、対象に何が許され、何を満たさなければならないかを定めるメタの概念である | マーカー・関係・法則・型・試験・設計文書の組み合わせで表す。実行可能な述語(Specification Pattern)が要るなら、空のマーカーではなく振る舞いを持つ普通のトレイトにする |
| 方針 | 人間や設計が採用する「方針」はメタの語であり、実行時の構造体名を `〜方針` にするとその型自身を振る舞いの主体として読みにくい | 方式を表す列挙・振る舞いを持つトレイト・具体の規則の型のどれかにする |
| 仕組み | 「仕組み」という語だけでは機械の法則を導けず、共通のマーカーとしては抽象度が高すぎる | 共通のマーカーを置かない |
| 変換 | 単なる「変換」まで一般化すると意味が薄くなる | 関数の役割と関係で表す(射影・解釈・遷移と、必要に応じた他の変換の役割) |

既存の `〜仕様`・`〜方針` の型の再分類と、関係の最小語彙は 2.3 節の今後の設計対象である。

### 2.3 今後の設計対象

本書はまだ次の3つの詳細を持たない。

```text
今後の設計対象:
- 関係の最小語彙(consumes・produces・identifies・observes・参照実装に準拠する) -> 第6節(2026-09-21に実装)
- 既存の「〜仕様」「〜方針」の再分類 -> #171
- M要求の成立条件の検証 -> 4.2.1節(2026-09-21に判断済み)
```

| マーカー | 設計上の役割 | `M不変データ` との関係(Relation) | `M不変データ` から継承する法則 | 役割ごとに追加で課す法則 |
|---|---|---|---|---|
| `M不変データ` | 参照や内部可変性を所有せず、値として複製・受け渡しできる純粋な所有データ。境界を越える転送にも状態の正本にも使う。意味は次の5つである。内部可変性を持たない。自己変更を行わない。値として複製・受け渡しできる。変更が必要な場合は既存の値を書き換えるのではなく新しい値を構築する。変数への再代入や別の値への置き換えそのものは禁止しない | (基底) | 参照・生ポインタ・内部可変性を持たない。受け手と引数に自分の型への可変参照を持たない(固有の `impl`・トレイトの実装・実装しているトレイトの宣言の既定の関数)(以上2つは `cargo xtask conform` が検査する。読む範囲は 2.5.3)。`Clone` を持つ(上位トレイト) | 無し |
| `M状態` | 実在し、保持され、遷移されるゲームまたはシミュレーションの状態 | is-a(`M状態: M不変データ`) | 同上 | `struct` に限定せず `enum` も状態として扱う。遷移は新しい状態を返す工程が担い、状態自身は自分の型への可変参照を受け手と引数に持たない(`M不変データ` から継承する法則) |
| `Mコマンド` | 主体が選択・発行する命令、意図 | is-a(`Mコマンド: M不変データ`) | 同上 | 必ず `enum` で定義する。受け手と引数に自分の型への可変参照を持たない(固有の `impl`・トレイトの実装・実装しているトレイトの宣言の既定の関数) |
| `Mイベント` | ある状態遷移によって成立した過去の事実 | is-a(`Mイベント: M不変データ`) | 同上 | 受け手と引数に自分の型への可変参照を持たない(固有の `impl`・トレイトの実装・実装しているトレイトの宣言の既定の関数)。`enum` を必須としない |
| `M規則` | 遷移からは読み取り専用で与えられる規則値(内部可変性を持たず、型自身に可変メソッドを持たない純粋な所有データ。値の置き換えを型では禁じない)。規則の「不変」とは、1回の遷移の評価のあいだ読み取り専用の入力であることであり、プログラムの全期間で同じ値であることは意味しない(速度の強化や難易度の変更で規則の値が変わることを妨げない) | is-a(`M規則: M不変データ`) | 同上 | 必ず `struct` で定義する。受け手と引数に自分の型への可変参照を持たない(固有の `impl`・トレイトの実装・実装しているトレイトの宣言の既定の関数) |
| `M入力` | 外界(入力デバイス等)から届く、意味付けの前の生の信号 | is-a(`M入力: M不変データ`) | 同上 | ゲームの意味論を持たない |
| `M観測` | 状態・処理・評価について、その対象の正本や因果を構成せず、外部から観察するために導出された不変データ | is-a(`M観測: M不変データ`) | 同上 | 法則は6つである。`M観測: M不変データ` である。正本ではない。観測の対象の因果の入力へ戻さない。`Mイベント` ではない(`Mイベント` はドメイン上で成立した過去の事実であり、`M観測` は対象を外から見るために導出した情報である)。`M結果` の部分型ではない。`struct` と `enum` の形は固定しない |
| `M工程` | 状態を読み書きして進める工程。データの役割ではなく処理の役割の軸に属する(2.1節) | 無し(工程はデータでない) | 無し | 現時点で共通契約を課さない |

`cargo xtask conform` が機械で保証しているのはここまでであり、設計解釈マーカーの型契約は値の置き換え(`規則.身体 = 別の値`、`&mut 規則` を受ける自由関数)を禁じていない。

`M設定` は共通の設計解釈マーカーとして定義しない。「起動時に決まる」「外から与えられる」「長く保持される」は型の本質ではなく、ライフサイクルや利用方法の性質だからである。関数境界の必須の入力は `MParameter`、任意の指定は `MOptions` で表す。起動設定やアプリケーション設定が要るなら、実装者はそれを具体のドメインの語彙として定義する。

データの役割(`M状態`・`Mコマンド`・`Mイベント`・`M規則`・`M入力`・`M観測`)はすべて `M不変データ` を上位トレイトに持つ。`Mコマンド: M不変データ` 等の supertrait の Relation はコンパイラが保証し、`cargo xtask conform` は `M不変データ` と役割の実装から型の定義をたどって、その定義に純粋データ規約(参照・生ポインタ・内部可変性を持たない)を当てる。`impl M不変データ for` をどのファイルに書くかは法則ではない。`cargo xtask conform` は、同じ型が複数の役割を持っても違反を1回だけ報告する。

`M状態: M不変データ` は Blitzdrache 全体の共通契約である。既存コードが適合しない場合、実装者は共通契約を弱めず既存コードの側を直す。本書が `Mコマンド`・`Mイベント`・`M規則` を `M不変データ` の上に積むのは、`Mコマンド` だけが純粋データ契約から外れていると、`&コマンド` から外部状態を書き換えられ、`M遷移関数` が純粋計算であるという理論を型契約が支えられないためである。

`M不変データ` の役割は「境界を越えて運ばれるデータ」ではなく「純粋な所有データ」である。`blitz_sim` のソルバ内部の作業状態も `M状態` であり、それは境界を越えないが純粋な所有データではあるので、この定義なら `M状態: M不変データ` の共通契約と矛盾しない。

## 2.5 存在の分類(同一性・ライフサイクル・不変性)

本節は、DDD(ドメイン駆動設計)の基礎概念である同一性・ライフサイクル・不変性の軸を、第2節のデータの役割とは別の軸として持つ。

### 2.5.1 5つの軸

設計解釈マーカーは、互いに直交する5つの軸を持つ。1つの型は各軸から独立に分類を選ぶ。本節が扱うのは存在の分類と変更可能性の軸であり、関数境界の役割の軸は 2.6 節が持つ。軸とオントロジーの層(2.1節)の対応は、データの役割が B、処理の役割が D、存在の分類と変更可能性が A、関数境界の役割が C である。

| 軸 | 問い | 分類 |
|---|---|---|
| データの役割 | その型は因果モデルのどこに現れるか | 状態・コマンド・イベント・規則・入力・観測(第2節)。`M不変データ` はこれらが共有する基底の契約であり、分類の1つではない |
| 処理の役割 | その型は処理として何を担うか | 工程(`M工程`。第2節)。関数の役割の newtype(第3節)も同じ層に属する |
| 存在の分類 | その型は同一性を持つか | 値オブジェクト(`M値オブジェクト`)とエンティティ(`Mエンティティ`)と、エンティティの識別子(`Mエンティティ識別子`) |
| 変更可能性 | その型は自己変更を行うか | 不変(`M不変エンティティ`)と可変(`M可変エンティティ`)。この軸のマーカーはエンティティに付け、値オブジェクトは `M不変データ` により常に不変である |
| 関数境界の役割 | その型は関数の境界をどう渡るか | 必須入力の束(`MParameter`)と任意の設定の束(`MOptions`)と評価の排他的な帰結(`M結果`)(2.6節) |

`M不変エンティティ` と `M可変エンティティ` は同じ軸の排他の分類であり、同じ型が両方を名乗ることを `cargo xtask conform` が違反にする(2.5.3)。

値オブジェクトとエンティティの区別と、不変と可変の区別は別の軸である。値オブジェクトは常に不変であるが(`M値オブジェクト: M不変データ`)、エンティティは不変にも可変にもなりうる。`M不変エンティティ` は「不変エンティティ」という新しい哲学ではなく、同一性とライフサイクルを持つこと(`Mエンティティ`)と自己変更を禁じること(`M不変データ`)の2つの既存の概念の合成である。

### 2.5.2 マーカーの一覧と法則

| マーカー | 定義 | 上位トレイト | 課す法則 | コンパイラが強制するもの | `cargo xtask conform` が検査するもの |
|---|---|---|---|---|---|
| `M不変データ` | 参照や内部可変性を所有せず、値として複製・受け渡しできる純粋な所有データ(第2節) | `Clone` | 内部可変性を持たない。自己変更を行わない。値として複製・受け渡しできる。変更は既存の値の書き換えでなく新しい値の構築で表す。変数への再代入や別の値への置き換えは禁止しない | `Clone` | 定義に参照・生ポインタ・内部可変性が無いこと。受け手と引数に自分の型への可変参照を持たない(固有の `impl`・トレイトの実装・実装しているトレイトの宣言の既定の関数) |
| `M値オブジェクト` | 同一性を持たず、その値そのものによって意味と等価性が決まる型 | `M不変データ + PartialEq` | 自己同一性を持たない。内容が同じなら同じ値として扱う。自己変更せず、変更は新しい値の生成として表す | `Clone`・`PartialEq` | `M不変データ` を通して同上(この印を直接には見ない) |
| `Mエンティティ` | ライフサイクルを通して維持される同一性を持ち、状態が変化しても同じものとして追跡される型 | 無し | 同一性は識別子の一致で決まる。識別子を機械的に取得できる | 関連型 `識別子: Mエンティティ識別子` と `fn 識別子(&self) -> &Self::識別子` の存在 | 無し |
| `Mエンティティ識別子` | エンティティの同一性を担う識別子。値オブジェクトとして扱う | `M値オブジェクト + Eq + Hash` | 完全な同値とハッシュで同定できる | `Clone`・`PartialEq`・`Eq`・`Hash` | `M不変データ` を通して同上 |
| `M不変エンティティ` | 同一性とライフサイクルを持ち、かつ自己変更を行わない型 | `Mエンティティ + M不変データ` | 両方の上位トレイトの法則 | 両方の上位トレイトの要求 | `M不変データ` を通して同上 |
| `M可変エンティティ` | 同一性を維持したまま内部の状態を更新する設計を意図している型 | `Mエンティティ` | 強い追加の法則を持たない。設計の分類の印である | `Mエンティティ` の要求 | 無し |

`M値オブジェクト` の基底を `Eq` でなく `PartialEq` にするのは、`f32` を含む値オブジェクトでは完全な同値(反射律)が成り立たないことがあるためである。`Eq` が成り立つ値オブジェクトと、浮動小数を含み完全な同値が成り立たない値オブジェクトを、将来別の分類として足してよい。

`Mエンティティ` には `PartialEq` を要求しない。エンティティの同一性は全フィールドの一致ではなく識別子の一致で決まるためである。安易な `derive(PartialEq)` とエンティティの同一性を混同してはならない。例として、`旅行者#42, hp=100` と `旅行者#42, hp=50` は値としては異なるが、同じエンティティである。

### 2.5.3 機械検証の範囲

コンパイラが強制するものは、上位トレイトの `Clone`・`PartialEq`・`Eq`・`Hash` と、`Mエンティティ` の関連型と識別子のメソッドの存在である。

`cargo xtask conform` の設計オントロジーの検査が見るものは、`M不変データ` またはデータの役割を実装する型の定義に参照・生ポインタ・内部可変性が無いこと、`Mコマンド` が列挙で `M規則` が構造体であること、`M結果` を実装する型が列挙であること(標準の `Result` は特例。2.6.1)、`M不変データ` を実装する型(データの役割を実装する型をすべて含む)が受け手と引数に自分の型への可変参照を持たない(固有の `impl`・トレイトの実装・実装しているトレイトの宣言の既定の関数)ことである。存在の分類のマーカーについても、実装の正規形(`impl マーカー名 for 型` または `impl blitz_design::マーカー名 for 型`)・別名の取り込みの禁止・波括弧付きのモジュールの中の実装の禁止・再公開の禁止は検査する(第5節)。純粋データ規約と 自己変更の禁止は `M不変データ` を上位トレイトに持つもの(`M値オブジェクト`・`Mエンティティ識別子`・`M不変エンティティ`)だけが `impl M不変データ for` の行を通して対象になり、`Mエンティティ` と `M可変エンティティ` には課さない(`Mエンティティ` は `M不変データ` を要求せず、`M可変エンティティ` は自己変更を意図する分類であるため)。同じ型が `M不変エンティティ` と `M可変エンティティ` の両方を名乗ることは違反にする(型の同一性は定義の位置のモジュール + 型名で突き合わせる。定義の位置のモジュールは後の段落で定める)。

現在 `cargo xtask conform` が `M観測` について直接保証するのは、`M不変データ` に由来する構文の法則(純粋データ規約と 自己変更の禁止)である。正本の保持(`M状態` が `M観測` を正本として保持していないか)と因果への逆流(遷移の因果の入力へ観測を戻していないか)は、型と型の関係の解析の対象とする。

次のものは検査しない。エンティティが本当に同一性を持つか。識別子が本当に一意か。`M可変エンティティ` が同一性を保っているか(識別子を書き換えていないか)。private のフィールドを通した間接の変更(自由関数と工程が `&mut 型` を受けてフィールドへ代入する形や、値の置き換え。型の固有の `impl` とトレイトの実装とトレイトの宣言の関連関数が `&mut 型` を受ける形は、型自身のAPIとして自己変更を与えるため、次の段落の自己変更の禁止として検査する)。これらは意味論または具体ドメインの配線であり、構文の検査では判定できない。

`cargo xtask conform` が自己変更の禁止(受け手と引数に自分の型への可変参照を持たない)として読む範囲は次のとおりである。検査器が読むのは、走査範囲(`crates` 配下の各クレートの `src`)の中のコードである。検査器はマクロを展開しない。検査器は、宣言の見出しの行の頭に同じ行で書いた属性(`#[allow(x)] impl 型 {`・`#[..] trait 名前 {`・`#[macro_export] macro_rules! 名前 {`)を剥がしてから読む。検査器は、見出しが `impl`・`trait`・`macro_rules!` で始まる1行から本体を開く括弧までを括弧の対応で読むため、見出しと本体を複数行へ分けた形も読む。検査器は、外部のクレートが定義したマクロ・`derive`・属性マクロが生やす実装を読まない。それらの実装は走査範囲のソースに現れないためである(`derive` が生やす std のトレイトの実装は、std の宣言が自己変更を与える関数を持たないことを言語が保証する)。 **検査器が宣言として読むのは、行の頭に書いた `impl`・`type`・`use`・`macro_rules!` だけである。** 行の頭とは、字下げと属性と可視性(`impl` では可視性の代わりに `unsafe`)を読み飛ばした位置のことである。検査器は行の頭でない宣言を読めず、その `impl` の本体の関数と、その `type` と `use` が作る名前の辺と、その `macro_rules!` の本体の中の実装を、違反にも件数にもせずに黙って落とす。**そのため検査器は、原文を字句の木へ変えて項目を始めうる予約語の現れを数え、行の頭で読み口の答えと双方向に完全に一致するかを突き合わせ、一致しない現れを違反にする。** 字句の木とは、1つのファイルの原文を、識別子・記号・リテラルと、括弧で囲んだ群へ分けた木のことである。

**検査器は、字句を proc-macro2 で読む。** 識別子の文字(Unicode の XID_Continue)・コメント・文字列・寿命・生の識別子・括弧の対応を、rustc と同じ規則で読むためである。自前の字句の走査は、識別子の文字を `is_alphanumeric` で数えて `通す·!(..)` をマクロの呼び出しと読まず、コメントを消した前後の字句を直結して `impl/**/丙` を1つの語にした。検査器は、字句の木へ変えられなかったファイルを違反にし、変えられなかった行と桁を説明に書く。**検査器は、シバンで始まるファイルを違反にする。** シバンとは、ファイルの先頭の `#!` で始まる行のうち、3文字目が `[` でないもののことである(先頭のバイト順マークは除いて数える)。rustc と検査器では、`#!` の行の読み方が分かれうる。rustc は `#!/usr/bin/env run` を読み飛ばし、`#! [..]` と、`#!` の後ろで改行した `[..]` を内側の属性と読むが、proc-macro2 は `#!` の行を読み飛ばさず、読み口はどちらの読み方もしない。そのため検査器は、読み飛ばす規則を真似て行を落とさず、`#!` の直後に空白や改行を置かず `#![` と書くことを求め、それ以外の `#!` で始まるファイルを違反にする。落とした行を2つの読みへ渡すと、`#!/*` で始まりブロックコメントが次の行へ続くファイルと、`#! [..] impl ..` の1行が、落とし方の違いで読み口と字句の木の読みを分けるためである。シバンを許していたとき、`#!/usr/bin/env run` の次の行の `use self::甲 as 乙; pub use self::甲 as 丙;` は、2つ目の `use` が読み口に読まれずに検査から落ちていた。正本は `xtask/src/conform/design_ontology/token_tree_gate/token_tree_scan.rs` であり、走査範囲の現状は0件である。字句の木の走査は、項目を始めうる予約語の現れを、次の2つの規則で数える。

**第一に、トークン木の外では、検査器は直前の字句が項目を始めうる字句の集合に入る現れだけを数える。** トークン木とは、字句の木のうち、マクロの呼び出しの引数(`名前 !` の直後の群)と `macro_rules! 名前` の本体の群のことである。直前の字句とは、字句の木の同じ並びの中の1つ前の字句のことであり、群の最初の字句の直前は群を開いた括弧である。項目を始めうる字句の集合は、`impl` では `{`・`}`・`;`・`]`・`unsafe`・`default` であり、`type` と `use` と `macro_rules!` では `{`・`}`・`;`・`]`・`pub`・`pub(..)` を閉じる `)` である。この集合は、Rust の文法が項目の直前に置くことを許す字句であるため、文法で閉じている。数えるのは、`pub struct A; impl A {`・`const _: () = { impl A { … } };`・`let x = 1 + { impl A { … } 2 };`・`{ use a as b; impl A { … } }` である。集合に入らない前置き(`->`・`:`・`&`・`'a`・`<`・`,`・`=`・`(`・`[`・`+`・`#`・`mut`)の後ろの現れは、項目を始められないため数えない。そのため、型の位置の `impl`(`&'a impl Display`・`Iterator<Item = impl Display>`・`Result<impl Display, impl Debug>`・`(impl Display, u8)`・`[impl Display; 2]`)と、精密な捕捉の `use<'a>`(`impl Sized + use<'a>`)と、属性の中の語(`#[cfg_attr(feature = "typescript", ts(type = "string"))]` の `type`)は数えない。生の識別子(`r#type`)と寿命(`'impl`)の識別子は、予約語として数えない。

**第二に、トークン木の中では、検査器は項目の予約語の現れをすべて数える。** マクロは引数の字句を並べ替えて展開できるため、`->`・`:`・`&`・`<`・`mut`・`#[..]`・`use <..>` の後ろに書いた `impl` と `use` も、項目として展開されうるからである。マクロのメタ変数の `$` の後ろの予約語も数える。`捨てる!($ impl 丙 { .. })` のように、`$` の後ろに書いた実装を展開できるためである。そのため、メタ変数を予約語の名前(`$type`)にすると違反になり、違反の説明が改名を求める。`if !(..)` の群もトークン木に数えるが、厳しくなる向きの誤りだけである。**この規則の費用は、マクロの本体とマクロの引数に書いた型の位置の予約語(`-> impl Iterator`)も違反になることである。** 型の位置の予約語を行の頭に置くように行を分けて書けば避けられる。走査範囲の現状は0件である。

**検査器は、数えた現れを、読み口の答えと行の頭で双方向に完全に一致するかで突き合わせる。** 読み口は、行の頭の宣言1つについて、「読めた」か「読めない」かを答え、`impl` と `type` の読めた答えは後の段落の見出しの中身を持つ。辺を作らない宣言とは、右辺の無い関連型の宣言(`type 状態: M状態;`)のように、読み切ったが名前の閉包の辺を作らない宣言のことであり、読み口はこれを読めた答えとして数え、見出しの中身に右辺が無いことを持たせる。字句の木の側は、現れごとに行の頭にあるかを持つ。検査器は、現れの前の字句を同じ並びの中で遡り、同じ行の字句が読み口と同じ前置き(属性と、`impl` では `unsafe`、それ以外では可視性)だけなら、その現れを行の頭にあるとする。突き合わせの規則は2つである。第一に、行の頭でない現れは、答えの数によらず違反にする。読み口は行の頭の宣言しか読まないため、同じ行の2つ目の宣言(`impl A {} impl B {}`)は必ず読まれずに落ちる。第二に、行の頭では、字句の木が項目を始めると見た現れの数と読み口の答えの数を、行と種類ごとに等しくする。字句の木だけにある現れは、読み口が読まなかった宣言である(行の頭の予約語の後ろに改行やコメントを挟んだ形。`impl` の直後の改行・`use` の直後の改行・`use::`・`use{`)。読み口だけにある答えは、字句の木が項目を始めないと見た位置の予約語を、読み口が宣言と読んだものである。**検査器はどちらの向きも違反にする。「読み口だけが読む向きは辺と実装を余分に集めるだけであり安全側に倒れる」という論証は成り立たない。** 数だけで突き合わせると、読み口の余分な答えが同じ行の読まれなかった現れを打ち消すからである。`pub fn 作る() ->` の次の行へ型の位置の `impl Sized { … impl 書き換え for 甲 { fn 変える(&mut self) { … } } }` を折った形は、行の頭の `impl Sized` を読み口だけが読み、同じ行の2つ目の `impl` の現れと数が釣り合って、`甲` の自己変更を検査から落としていた。項目でない位置の予約語を行の頭へ置く形は `->` の次の行の型の位置の `impl` だけであり、rustfmt はこの形を出さない。正本は `xtask/src/conform/design_ontology/token_tree_gate/item_keyword_reconciliation.rs` と `token_tree_gate/line_head.rs` であり、走査範囲の現状は0件である。

**検査器は、行の頭の `impl` と `type` の見出しの中身も、字句の木から取り出して読み口の読みと突き合わせる。** 予約語の数の突き合わせは、読み口が宣言を読んだかだけを見て、どう読んだかを見ないためである。読み口が識別子の文字や `for` や `where` の位置を読み違えると、実装の対象を取り違えたまま数だけが釣り合う。見出しの中身とは、行の頭の宣言の見出しについて、自己変更の検査が実装と名前の辺を集めるときに読み口から読む値そのもののことである。`impl` では、トレイトの実装か(山括弧の外に `for` の識別子があり、その後ろが高階の寿命の束縛の `<'a>` でないか)・対象の型の表記の全体・対象の型のパスの最後の名前・可変参照を対象にするか・型引数の名前の一覧であり、`type` では、別名・型引数の名前の一覧・右辺の全体・右辺のパスの最後の名前(右辺の無い宣言は右辺が無いこと)である。対象の型の表記は、1つの型を囲む丸括弧と、参照と、`Pin<&mut ..>` を外した後の表記である。可変参照を対象にするかは、外す前の表記のどの深さにでも可変参照(`&mut X`・`&'a mut X`)が現れるかであり、`Option<&mut 規則>`・`(&mut 規則, u8)`・`Box<&mut 規則>` も可変参照を対象にする。型引数の名前の一覧は、寿命を除いた型引数と定数の引数の名前である。名前は1つの識別子(マクロのメタ変数なら頭の `$` を含む)で書けるときだけ持ち、それ以外(`[規則]`・`dyn 変更`・`&'a 規則`)は名前で読めないとする。

**検査器は、対象の型の表記と型の別名の右辺を、名前だけでなく表記の全体で比べる。** 比べる形は正規化した字句の並びである。正規化した字句の並びとは、表記を字句へ分け、空白と改行とコメントの違いを消し、字句を1つの空白で区切った並びのことである。括弧の群は開き括弧と中の並びと閉じ括弧を並べ、文字列と文字のリテラルは並びに入れない(読み口が読むコードだけの行に無いためである)。読み口の側は、自己変更の検査が実際に読む値(`実装の見出しの構文` が返す対象の表記と、型の別名の宣言の右辺)をそのまま字句へ分ける。読み口の表記を字句へ分けられないのは、表記が括弧の途中で切れているときであり、字句の木の並びとは必ず食い違う。名前だけで比べると、型引数の定数式の中の `where` で対象の表記を切る読み(`包み<{ const fn 一() -> usize where u8: Copy { 1 } 一() }, 規則>` を `包み<{ const fn 一() -> usize` と読む)が、パスの最後の名前 `包み` で両側一致し、表記に現れる `規則` を自己変更の検査から落としていた。読み口は、`where` と本体を開く `{` を、どの括弧の中でもない位置でだけ探す。

**字句の木の側は、読み口と読み方の規則を共有しない。** 同じ規則で読むと、その規則の誤りが両側で同じ読み違いに揃い、突き合わせが違反を出さないためである。`impl<#[cfg(target_pointer_width = "64")] T: M不変データ> 変更 for T` は、両側が「各引数の先頭の識別子」を型引数の名前にしていたため、どちらも `T` を落とし、全称の実装の判定を抜けていた。字句の木の側は、見出しを `Ident`・`Punct`・`Group` の並びとして読む。型引数の名前は、外側の属性(`#` と角括弧の群)を読み飛ばした後が寿命なら無く、`const` なら次の識別子であり、それ以外なら最初の識別子である。見出しの終わりは、山括弧の外の本体の波括弧の群か `where` である。括弧の中は群として1つの字句になるため、型引数の定数式の中の `where` で止まらない。対象の型の丸括弧と参照と `Pin` も、群と記号で外す。読み口の側は、各引数の頭の外側の属性を読み飛ばしてから名前を読む。読み口と字句の木が同じ行の同じ予約語の見出しを読んだのに中身が違えば、検査器は違反にする。**字句の木は答え合わせの基準であり、検査器は構文の木を作らない。** 下流の読み口は文字列のまま読み、構文を syn の構文木へ移す作業は issue #179 が受け持つ。正本は `xtask/src/conform/design_ontology/token_tree_gate/header_content_reconciliation.rs` と `token_tree_gate/header_tokens.rs` と `token_tree_gate/normalized_token_sequence.rs` であり、走査範囲の現状は0件である。

**コードだけの行は、ブロックコメントを消した位置の前後がどちらも空白でないコードなら、その位置に半角空白を1つ置く。** rustc がコメントを字句の区切りとして読むのに合わせ、`impl/**/丙` を `impl丙` という1つの語にせず、`impl 初期化/* 注 */for 規則` を固有の実装と読み違えないためである。文字列の位置には置かない(`include_bytes!` の括弧の中が空であることを手がかりにする検査があるためである)。原文の先頭のバイト順マークは落とす。

**整形は偽陽性を減らすだけであり、この検査の健全性は字句の木と突き合わせが保証する。** rustfmt は項目を行の頭へ置くが、整形しきれない文(長い文字列を引数に持つ呼び出し・式の中のコメント)を元の1行のまま残し、そのときも `cargo fmt --check` は成功で終わる。そのため検査器は、ソースが整形済みであることを前提にしない。`h("…長い文字列…", || { impl A { … } })` と `1 + /* 注 */ { impl A { … } 2 }` は整形の後も1行のまま残り、突き合わせが違反にする。`#[rustfmt::skip]` を付けた項目も、同じ規則と突き合わせで読む。見出しを複数の行へ崩した実装(`impl 甲\nfor 乙 {`)は読み口が読み、予約語の直後で行を改めた形(`impl\n乙 {`・`type\n別名 = u8;`)は違反になる。

**検査器は、行の頭から読み始めた宣言を読み切れなかったときも、黙って飛ばさず違反にする。** `type` と `use` の読み口は、1つの宣言について「その宣言でない」「読めた」「辺を作らない宣言を読んだ」「読み切れない」の4つだけを返す。ファイルの `use` を読む工程は、それを読めた項目の一覧と読み切れない文の一覧の2つへ分けて返す。`impl` の見出しは、本体を開く `{` に届かないときに読み切れないとする。rustfmt は表示の幅(`max_width = 250`)を超える宣言を折る(`type` の別名を `=` の後ろで折る)ため、`type` と `use` の読み口は宣言を終える `;` まで行を繋いでから読む。日本語の識別子は表示の幅を2つ使うため、125文字でこの幅に届く。`type` はどの括弧の中でもない `;` で宣言を終え(`type 配列 = [規則; 2];`)、括弧は丸括弧・角括弧・波括弧だけで数えて山括弧を数えない(`type 表 = [u8; 1 << 4];` のシフトを山括弧と読まないためである。`;` は山括弧の中に直に書けない)。`use` は最初の `;` で文を終える(`use` の木は `;` を持てない)。読み切れない綴りは、入れ子ごと展開できない波括弧の群・ファイルの最後まで `;` に届かない宣言・1つのパスと別名に読めない取り込みの項目・`type` の後ろに別名の識別子が無い宣言・別名の型引数の山括弧が `;` までに閉じていない宣言・`=` の右辺が空である宣言・辺を作る名前にマクロのメタ変数を持つ宣言(次の段落)・本体を開く `{` に届かない `impl` の見出しである。正本は `xtask/src/conform/design_ontology/token_tree_gate/readable_form_assertion.rs` であり、走査範囲に現状0件である。根拠はグローバルCLAUDE.md「検査器は解析できなかった入力を黙って対象から外してはならない」である。

**検査器は、辺を作る名前にマクロのメタ変数を持つ `use` と `type` を読み切れないとする。** 辺を作る名前とは、名前の閉包の辺(後の段落)の端になる名前のことであり、`use` では別名とパスの最後の名前、`type` では別名と右辺の全体である(第2段の辺が右辺に現れる識別子を問うためである)。`use $パス as $別名;` と `pub type 別の法則 = $元;` は、展開した先の名前を検査器が知らず、その辺を黙って落とすため違反になる。`$crate` はメタ変数でなく、そのマクロを定義したクレートの根を指す決まったパスであるため数えない。`use $crate::a::規則 as 法則;` と `type 法則 = $crate::a::規則;` は読める。実装の本体の中の関連型(`impl … { type Output = $型; }`)も、名前の閉包の片方向の辺を作るため、同じく違反にする。正本は `xtask/src/conform/design_ontology/macro_metavariable.rs` であり、走査範囲の現状は0件である。

**検査器は、実装の対象がどの型を指すかを名前解決で求めない。検査器は、型の名前で過大に近似して実装を集める。** 検査器は、走査範囲の全ソースの本文から `impl [<..>] [blitz_design::]M不変データ for X` を集め、`X` のパスの最後の要素を名前の種にする。検査器は、見出しを `実装の見出しの構文` の1つの読みでトレイトと対象に分け、` for ` の空白の一致では探さない。`X` のパスの最後の名前を1つの識別子で読めない実装(`impl M不変データ for [規則]`)は、種にも定義の探索にも入らないため、黙って捨てずに違反にする(`xtask/src/conform/design_ontology/impl_syntax/target_form.rs`)。同じ工程は、設計解釈マーカーの実装の対象の表記のどの深さにでも参照か `Pin` が現れる形(`impl M不変データ for &規則`・`&mut 規則`・`Pin<&mut 規則>`・`包み<&mut 規則>`・`Box<&規則>`)も違反にする。対象の名前は包みを外した `規則` か包む型の `包み` で読めるため、この形を許すと、正規形の検査も純粋データ規約も参照を持たない定義を見て通り、可変参照を中に持つ型が `M不変データ` を名乗れる。一番外側だけで判定すると、型引数を1段かぶせた `包み<&mut 規則>` が抜ける。`[規則]`・`dyn 変更`・タプルを対象にしたマーカーの実装と同じ扱いである。種を集める位置は問わない。マクロの本体の中の実装も、関数の本体の中の実装も、`#[cfg(..)]` が付いた実装も同じく種になる。検査器は、種から後の段落の2段の閉包で閉じた名前の並びを作る。検査器は、走査範囲のすべての `impl` について、閉じた名前のどれかが実装の対象の型の表記か、型引数の並びの境界か、`where` 句に**識別子の境界**で現れれば、その実装の本体の直下の関数と、その実装が実装したトレイトの宣言の関数を検査する。見出しに名前が当たらない実装でも、本体の直下の関数か実装したトレイトの宣言の関数の署名の境界で、可変の借用を与えるトレイトの型引数に閉じた名前が現れれば、その関数を違反にする(後の段落)。トレイトの型引数(`impl IndexMut<地点> for 地図` の `地点`)は照らさない(後の段落)。識別子の境界とは、その現れの直前の文字と直後の文字がどちらも識別子の文字(英数字・下線・非ASCIIの文字)でない位置のことである。ただし生の識別子の接頭辞 `r#` の直後は境界に数えない(`impl 変更 for r#where` の `where` を `where` 句の始まりと読まないためである)。**検査器の読み口が識別子の文字を判定するのは、`xtask/src/conform/design_ontology/identifier_boundary.rs` の `識別子の文字か` の1つの関数だけである。** この述語(英数字・下線・非ASCIIの文字)は、Rust の識別子の文字(XID_Continue)の上位集合である。上位集合でも読み違えないのは、コードだけの行に残る非ASCIIの文字が識別子の中にしか現れないためである。rustc は全角の空白と全角の括弧を拒み、それ以外の非ASCIIの空白は後の段落の空白の正規形が禁じる。以前の12箇所の判定は英数字(`is_alphanumeric`)で数えたため、`·`(U+00B7)を含む `T·x`・`同じ·x`・`型·for` の名前を途中で切り、全称の実装と型引数の既定値と固有の実装を読み違えていた。`impl 変更 for crate::歩行::地点` の `地点` は当たり、`impl 変更 for 歩数を動かす領域` の `歩数` は当たらない。**検査器は実装の在り処を一切問わない。** 関数の本体の中の実装も、波括弧付きのモジュール(`mod 名 { … }`)の中の実装も、マクロの本体の中の具体の実装も、`#[cfg(..)]` が付いた実装も、同じく検査する。名前解決をやめたのは、`use`・glob・再公開・別名・cfg・局所の項目・波括弧付きのモジュール・波括弧を使って呼んだマクロの本体を解く解き方に、名前を取りこぼす穴が繰り返し見つかったためである。名前で過大近似すると、その種類の穴が原理的に存在しなくなる。

**名前の閉包は2段で求める。第1段は、種と同じ型を指す名前の集合である。** 辺は3つである。`use …::元 as 別名;` の別名と元の名前(双方向)、項目の `type 別名 = 右辺;` の別名と右辺のパスの最後の要素(双方向)、実装の本体の直下の関連型の宣言 `type 名前 = 右辺;` の右辺のパスの最後の要素から関連型の名前(片方向)である。双方向にするのは、マーカーを別名の側へ書く形(`type 別名 = 規則; impl M不変データ for 別名`)で本体の型名 `規則` が漏れるためである。**第2段は、第1段の集合の型を包む名前の集合である。** 辺は、右辺に第1段か第2段の集合の名前が識別子の境界で現れる型の別名(関連型を含む)への片方向と、`use` の別名と元の名前の双方向である。`type 配列 = [規則; 2];`・`type 包み = Vec<規則>;` の `配列` と `包み` がこれで入る。その別名を対象にした実装は、型を包む実装(後の段落)と同じく、包まれた型の値を書き換えうるためである。**検査器は、第2段の名前から右辺のパスの最後の要素(`Vec`・`fn`・`Result`)へ辿らない。** 辿ると、包む型の名前を通して、同じ包む型を使う無関係な別名が連鎖して閉包へ入る。2つの段は、どちらも辺を足しても減らない名前の集合の最小の不動点であるため、閉包は辺を辿る順序によらない。正本は `xtask/src/conform/design_ontology/marker_name_closure.rs` である。

**第2段で包む型の名前を辿らない代わりに、検査器は型引数の並びの境界と `where` 句を照らす。** 包む型(`Vec`)への実装のうち、中身を具体的に書いた実装(`impl ローカル for Vec<規則>`)は、対象の表記に閉じた名前を含むため、閉包の名前で検査に入る。型引数だけで包んだ実装(`impl<T> ローカル for Vec<T>`)は、本書の数え方では全称の実装ではない(全称の実装の基準は後の段落が定める)。境界の無い型引数の値を、同じ本体は書き換えられず、値を丸ごと動かすか捨てることしかできない。本書は値の丸ごとの置き換えを禁じていない。**型引数の境界を通すと、その本体はマーカーの型の値を書き換えられる。** `impl<T: DerefMut<Target = 規則>> 変更 for Vec<T> { fn 変える(&mut self) { self[0].0 = 1; } }` は、`Vec<&mut 規則>` の中の `規則` を書き換える。同じ境界の下では、値で受ける `mut self` でも書き換えられる(`fn 変える(mut self) { self[0].0 = 1; }`)。境界の `DerefMut` は走査範囲の外のトレイトであり、`規則` への `DerefMut` の実装は std の `impl DerefMut for &mut T` であるため、「境界のトレイトの可変の関数はマーカーの型への実装の側で捕まる」とは言えない。以前の本書はそう論じたが、この論証は誤りだった。そのため検査器は、閉じた名前が型引数の並びの境界か `where` 句に識別子の境界で現れるかを照らし、`impl<T: DerefMut<Target = 規則>> 変更 for Vec<T>`・`where T: DerefMut<Target = 規則>` と書いた同じ実装・`impl<T: BorrowMut<規則>> 変更 for Option<T>` を検査に入れる。**境界に閉じた名前が当たった実装は、可変参照を対象にする実装と同じ扱いにする。** すなわち、検査器は値で受ける `self` の関数も含め、関数を1つでも持てば違反にする。**全称の実装でも、境界か `where` 句に閉じた名前が当たれば、検査器は除かずに検査する。** `impl<T: DerefMut<Target = 規則>> 変更 for T { fn 変える(mut self) { self.0 = 1; } }` は、対象の型が型引数であるため全称の実装だが、境界が `規則` を指すため違反になる。型引数の並びから照らすのは、各引数の名前の後ろの `:` より後ろ(境界と定数の引数の型)だけであり、型引数の名前そのものは照らさない。実装自身の型引数と同じ名前は、修飾していない裸の現れだけがその実装の中で型引数を指すため、裸の現れは `where` 句でも当たらない(`impl<状態: M状態> 包み<状態> where 状態: Clone` の `状態`)。**直前が `::` の現れは、型引数と同じ名前でも当てる。** 型引数が隠すのは裸の名前だけであり、`self::規則`・`crate::a::規則`・`super::規則` はモジュールの型を指すためである。修飾した現れまで除いていたとき、`impl<T, 規則> 変更<規則> for Vec<T> where T: DerefMut<Target = self::規則>` と、同じ境界を型引数の並びに書いた実装と、同じ形の全称の実装の値で受ける `self`(`fn 変える(mut self) { self.0 = 1; }`)が、`規則` を書き換えるのに検査から落ちていた。**検査器は、トレイトの型引数を照らさない。** トレイトの型引数にマーカーの型を書いた実装(`impl IndexMut<地点> for 地図`・`impl Extend<地点> for 経路`・`impl AddAssign<距離> for 走行の合計`)は別の型のAPIであり、マーカーの型を引数に取る自由関数と同じ範囲にあるためである(後の段落の自由関数の扱い)。見出しの全体を照らしていたとき、この3つの実装はマーカーを名乗る値オブジェクトの `地点` と `距離` を書き換えないのに違反になっていた。これは名前による近似であり、境界を別のトレイトの宣言か走査範囲の外のトレイトで包んだ形は捕まえない(後の段落の保証範囲の外)。境界がマーカーの型を指すのに書き換えを与えない実装(`impl<T: Into<地点>> 記録器<T>`)が当たれば、台帳の区分 `境界で指した名前` で除く。正本は `xtask/src/conform/design_ontology/impl_syntax/bounds.rs` と `mutable_impl_scan.rs` であり、走査範囲の現状で境界か `where` 句に閉じた名前が当たる実装は0件である。

**検査器は、関数の署名の境界も照らす。** 関数の署名の境界とは、関数の型引数の並びの境界と、関数の `where` 句と、引数の `impl Trait`(`impl` から、その引数の型の中の要素の終わりまで)の3か所のことである。関数の境界を通すと、受け手と引数の型の字面に可変参照を持たずに、その関数が境界の型の値を書き換えられるためである。`impl 規則 { pub fn 変える(mut 相手: impl DerefMut<Target = Self>) { 相手.0 = 1; } }` と、同じものを `fn 変える<U: DerefMut<Target = Self>>(mut 相手: U)` と書いた形は、正本が名指しで禁じる `fn 変える(値: &mut Self)` と同じ働きをする。`impl<T> 変更<T> for Vec<T> { fn 変える(&mut self) where T: DerefMut<Target = 規則> { self[0].0 = 1; } }` は、実装の見出しに `規則` を持たない。**検査器は、閉じた名前も `Self` と対象の型の名前も、3か所のうち可変の借用を与えるトレイトの型引数の中だけで照らす。** 可変の借用を与えるトレイトとは、その境界を満たす値が型引数(`Target`・`Borrowed`・`T`・`Output`)の型への可変参照を与える std のトレイト `DerefMut`・`BorrowMut`・`AsMut`・`IndexMut` のことである。閉じた名前については、検査器は、見出しに名前が当たらない実装も含む走査範囲のすべての実装について、本体の直下の関数と、実装したトレイトの走査範囲の宣言の関数(既定の関数を含む)を照らし、当たった関数を違反にする。本体の直下のマクロの呼び出しは、見出しに名前が当たった実装だけを根拠にする。`Self` と対象の型の名前については、検査器は、見出しに名前が当たった実装と対象の型を決められない実装の関数を照らす。**境界の全体で照らさないのは、偽陽性の費用が大きいためである。** 閉じた名前を境界の全体で照らしていたとき、`impl Extend<地点> for 経路 { fn extend<I: IntoIterator<Item = 地点>>(&mut self, 列: I) }` が、`地点` を書き換えないのに違反になった。これは、トレイトの型引数を照らさないと定めた前の段落の偽陽性(`impl IndexMut<地点> for 地図`・`impl Extend<地点> for 経路`・`impl AddAssign<距離> for 走行の合計`)が、関数の署名の側から戻ったものである。std のトレイトの宣言がその関数の境界を決めるため、実装の書き手は境界を選べず、台帳で除くほかに手が無い。`Self` を境界の全体で照らすと、`fn 比べる<U: PartialEq<Self>>(&self, 相手: &U)`・`fn 集める<I: Iterator<Item = Self>>(列: I) -> Vec<Self>`・std の `Sum` と `Product` の実装の `fn sum<I: Iterator<Item = Self>>(列: I)`・既存の試験が違反にしないと固定した `fn 使う(処理: impl FnOnce(&mut Self))` がどれも違反になる。これらは値を比べるか作るか受け取る処理であり、境界の型の値への可変参照を与えない。実装の見出しの境界は、前の段落のとおり境界の全体で照らす。見出しの境界は実装の書き手が選ぶものであり、台帳の区分 `境界で指した名前` で除ける1件ごとの費用で済むためである。可変の借用の4つに限っても、この4つを上位トレイトに持つ別のトレイトの宣言を通した境界(`U: 取れる`)と、`Iterator<Item = &'a mut Self>` のように型引数へ可変参照を直に書いた境界は捕まえない(保証範囲の外の第四)。戻り値の型(`-> impl Iterator<Item = Self>`)は照らさない。戻り値は関数が作る値であり、呼び出し側の値を書き換える口を与えないためである。**対象の表記に可変の借用を与えるトレイトが識別子の境界で現れる実装(`impl 変更 for Box<dyn DerefMut<Target = 規則>>`)は、境界に当たった実装と同じく、値で受ける `self` の関数も数える。** その実装の `fn 変える(mut self) { self.0 = 1; を、空白の一致でなく識別子の境界で探す。`impl 初期化 for(規則)` と `impl 初期化 for&mut 規則` を固有の実装と読み違えないためである。高階の寿命の束縛の `for<'a>` は区切りに数えない。

型の定義の探索は、自己変更の禁止とは別の問い(純粋データ規約・`Mコマンド` と `M規則` と `M結果` の型種別・`MParameter` の `Option` の禁止)のために残る。型の同一性は、定義の位置のモジュールと型名の組である。定義の位置のモジュールとは、定義のファイルから推定したモジュールパスの下へ、定義の行を囲む波括弧付きのモジュール(`mod 名 { … }`)の名前を外側から繋いだもののことである。検査器は、ファイルが同じことを同じ型の根拠にしない。検査器は、その定義として、実装の位置のモジュールの直下の定義を採り、無ければその位置の `use` の取り込み元のモジュールの直下の定義を採る。検査器は、同じファイルにあっても局所の定義と別の波括弧付きのモジュールの定義を採らない。そうした定義しか無く `use` も無い実装と、局所の位置の実装のファイルに同名の局所の定義がある実装と、実装の位置のモジュールの直下の定義と型名を名乗る `use` を同時に持つ実装は、検査器が定義を一意に決められない違反にする。実装対象の型の `use ... as` の別名も、取り込み元を求められない違反にする。2段以上の再公開の連鎖を通した定義の探索は、保証範囲の外である。入れ子の波括弧の `use`(`use a::{b::{c, d}};`)は、検査器が群を入れ子ごと展開して読む。

検査器は、集めた実装の本体の直下の関数と、その実装が実装したトレイトの走査範囲の宣言の関数(既定の関数を含み、`where Self: Sized` も除外しない)の署名を読む。検査器は、引数の頭の属性(`#[allow(unused_mut)] &mut self`)を剥がしてから、受け手が `&mut self`・`&'a mut self`・`self: T`・`mut self: T`(`T` が可変参照を含む)である関数と、受け手でない引数の型のどこかに自分の型(`Self` か型名)への可変参照が現れる関数(`&mut Self`・`&'a mut 型名<..>`・`Option<&mut Self>`・`&mut [Self]`・`&mut &mut Self`・`(&mut Self, u8)`)を違反にする。`&mut Vec<Self>` を書き先に取る関連関数(`fn 足す(書き先: &mut Vec<Self>)`)も、`Self` の値を書き換えうるため違反にする。受け手でない引数の型は、最上位(丸括弧・波括弧・角括弧・山括弧の外)の単独の `:` より後ろであり、構造体のパターン(`規則 { 値: x }: &mut 規則`)の中の `:` では区切らない。値で受ける `self` と、型引数の境界(`F: FnOnce(&mut Self)`)と、引数の型の中の関数の型とトレイト境界(`fn(&mut Self)`・`impl FnMut(&mut Self)`・`Box<dyn Fn(&mut Self)>`)の中の可変参照は数えない。対象の型の表記のどの深さにでも可変参照が現れるトレイトの実装(`&mut 型`・`&'a mut 型`・`Pin<&mut 型>`・`Option<&mut 型>`・`(&mut 型, u8)`・`Box<&mut 型>`)は、値で受ける `self` でも型を書き換えられるため、関数を1つでも持てば違反にする。一番外側だけで判定していたとき、`impl 変更 for Option<&mut 規則> { fn 変える(self) { if let Some(中身) = self { 中身.0 = 1; } } }` が抜けていた。型引数の並びの境界か `where` 句に閉じた名前が当たった実装も、同じく関数を1つでも持てば違反にする(前の段落)。この字面の判定と受け手と引数の字面の判定が別名に隠れた可変参照を見落とさないことは、第十の正規形が保証する。**型を包む実装(`impl ローカル for Box<型>`・`Vec<型>`・`Option<型>`・`[型]`・`(型, u8)`)も、対象の表記に型名が識別子として現れるため同じく検査する。** その実装の可変の受け手(`&mut Vec<型>`)は包まれた型の値を書き換えることができるためである。

**トレイトの側も名前で引く。** 検査器は、実装が書いたトレイトの表記のパスの最後の要素の名前について、型と同じ閉包を作り、閉じた名前で走査範囲のトレイトの宣言を引く。検査器は、宣言の位置も問わない。関数の本体の中の宣言もマクロの本体の中の宣言も同じ名前として数える。同じ名前の宣言が複数あれば、検査器はそのすべてを見て、1つでも自己変更を与える関数を持てば違反にし、違反の説明に同名の宣言の件数を書く。上位トレイトは辿らない(`impl 下位 for 型` の成立に要る `型: 上位` は、明示の `impl 上位 for 型` か全称の実装でしか満たせず、どちらも別に読むためである)。**走査範囲にその名前の宣言が1件も無ければ、そのトレイトは走査範囲の外(std・core・alloc・外部の依存クレート)のものであり、検査器はその既定の関数を検査しない。** 名前で引くため、`use` の別名・glob・再公開・prelude の名前のすり替えは、どれも閉包か正規形が覆う。`pub use crate::t::可変化 as Default;` を取り込んだ `impl Default for 型` は、`Default` と `可変化` が閉包で繋がるため、`可変化` の宣言の関数で判定する。

検査器は、集めた実装のうち次の2つを、読めないため違反にする。第一に、本体の直下の項目の位置でマクロを呼ぶ実装(`名前!(...)`・`名前!{...}`・`名前![...]`)は、生える関数を読めない。項目の位置とは、本体の直下の直前の区切り(`;`・`{`・`}`)からマクロの名前までが空白と属性(外側の `#[..]` と、本体の先頭に書ける内側の `#![..]`)だけである位置のことである。式の位置のマクロ(`const X: bool = matches!(..);`・`#[doc = include_str!("..")] fn f(&self);`)は項目を生やさないため数えない。第二に、宣言の本体の直下(波括弧の深さ1)の項目の位置でマクロを呼ぶトレイト(`trait 変更可能 { 自己変更を生やす!(); }`)の実装は、マクロが既定の関数を生やせるのに、生える関数を読めない。宣言の関数の本体の中のマクロ(`println!` 等)と、第一と同じ式の位置のマクロは数えない。

全称の実装(`impl<T: 境界> トレイト for T`・`for &mut T`・`for &mut &mut T`・`for Pin<&mut T>`)と `macro_rules!` の本体の中の実装と関数は、検査器が境界を評価できず、生えた先の型も決められないため、`M不変データ` の型へ結び付けられない。検査器は、マクロの本体を `macro_rules!` の後ろで最初に開いた括弧の種類(`{`・`(`・`[`)の対応を数えて求め、開き括弧が名前の次の行にあってもよい。マクロの本体の中で、検査器は `impl` の中の関数をその実装の見出しから読み、`impl` の外の関数のうち受け手が可変のものと `&mut Self` を引数に持つものを数える(そのマクロを本体の直下で呼んだ実装の型へ生えるためである)。**全称の実装の基準は1つである。** 検査器は、実装の対象から参照と `Pin<..>` と囲みの丸括弧を外せなくなるまで繰り返し外し、外した後の名前が実装自身の型引数なら全称の実装とみなす。外しきれない形(`Pin<Box<T>>` のように `Pin` のまま残った表記)に型引数が識別子として現れるときも、見落とさない側へ倒して全称の実装とみなす。型引数を別の型で包んだ実装(`impl<T> ローカル for Vec<T>`・`for Option<T>`・`for &mut [T]`)は全称の実装に数えない。その実装は対象の型の名前(`Vec`)を具体の型として持ち、`T` の中身を書き換えられるのは境界を通したときだけであり、境界は型引数の並びの境界と `where` 句を照らす名前の近似が受け持つためである。同じ理由で、全称の実装の境界か `where` 句に閉じた名前が当たれば、自己変更の検査はその実装を除かずに検査する(前の段落)。1段だけ外していたとき、`impl<T: M不変データ + Default> 変更 for &mut &mut T` は全称の実装にも名前の当たる実装にもならず、`**self = T::default()` を検査から落としていた。検査器はこれらを黙って通さず、自分の型(型引数・メタ変数・`Self`)への可変参照を持つ関数を本体か実装しているトレイトの宣言に持てば違反にし(メタ変数は頭の `$` を含めて照らすため、`impl $型 { fn 足す(左: &mut $型) {} }` も違反になる)、`M不変データ` の型に当たらない理由を台帳(`xtask/src/conform/design_ontology/unbound_implementation_ledger.rs`)に書いた実装だけを除外する。台帳の行の鍵は、実装なら本体を開く `{` の手前までの見出しであり、マクロの本体の中の `impl` の外の関数なら `macro_rules! マクロ名 の fn 関数名` である。台帳に載っているのに該当しなくなった行も違反にする。

**保証範囲の外は次の5つである。** 第一に、外部のクレートの手続き型マクロと属性マクロが生やす実装である。走査範囲に手続き型マクロのクレートは無く、依存の白リストが追加を止める。第二に、走査範囲の外のトレイトの既定の関数である。検査器は std・core・alloc と外部の依存クレートのトレイトの宣言を読めない。**そのため検査器は、マーカーを名乗る型が明示の `impl` で実装する走査範囲の外のトレイトの名前を台帳(`xtask/src/conform/design_ontology/external_trait_ledger.rs`)と突き合わせ、台帳に無い名前が現れたら違反にする。** 台帳の行には、そのトレイトの既定の関数が値の丸ごとの置き換えだけであるという根拠を書く。設計解釈マーカーそのものは、対象を選ぶための印であるため台帳に数えない(判定に使う名前の一覧は `xtask/src/conform/design_ontology/syntax_patterns.rs` の `オントロジートレイト` が1つだけ持つ)。台帳に載っているのに現れなくなった行も違反にする。`derive` が生やす実装(`Debug`・`Clone`・`PartialEq`・`Eq`・`Hash`・`Copy`・`Default`)はソースの行に `impl` として現れないため台帳に載らず、2026-09-23 に走査範囲を調べた時点で台帳は空である。第三に、`unsafe` と内部可変性で私有のフィールドを書き換える形である。これは純粋データ規約(定義に内部可変性を持たないこと)が別に受け持つ。第四に、トレイトの境界を、別のトレイトの宣言か走査範囲の外のトレイトで包んだ間接の変更である。例は `trait 取れる: DerefMut<Target = 規則> {}` を経由した `impl<T: 取れる> 変更 for Vec<T>` と `fn 変える<U: 取れる>(mut 相手: U)` である。境界の名前を照らす近似は、境界に `規則` か `Self` を直接書いた実装と関数を捕まえる。捕まえる範囲は、実装の見出し(型引数の並びの境界と `where` 句)と関数の署名(型引数の並びの境界と `where` 句と引数の `impl Trait`)であり、関数の署名では名前と `Self` を可変の借用を与えるトレイトの型引数の中に限る。近似は、別のトレイトの宣言の上位トレイトに書いた `規則` と `Self` を辿らない。同じ理由で、`Self` を可変の借用の4つの外の境界に書いた形(`fn 変える<'a, I: Iterator<Item = &'a mut Self>>(列: I)`)も捕まえない。閉じるには型の解決が要る。第五に、可変参照を内部に持つ外部の型を対象にした実装である。例は `impl 変更 for std::slice::IterMut<'static, 規則> { fn 変える(mut self) { for 中身 in self { 中身.0 = 1; } } }` である。対象の表記に `規則` が現れるため検査器は実装を集めるが、`IterMut` が可変参照を持つことは字面に現れないため、値で受ける `self` を数えない。どの外部の型が可変参照を中に持つかを知るには、その型の定義を読む型の解決が要る。

走査範囲の外のトレイトについては、2つの別の事実がある。第一に、この法則は `Clone::clone_from(&mut self)` を禁じない。`clone_from` の意味は `*self = other.clone()` という値の置き換えであり、本書は値の置き換えを禁じないためである。同じことが `ToOwned::clone_into(&self, target: &mut T)` にも言える。**std が既定で与える可変の関数は、いずれも値の丸ごとの置き換えであり、本書はその置き換えを禁じていない。** 第二に、検査器はそれらの宣言を読めないため、既定の関数を検査しない。第二の事実は検査器の読む範囲の限界であり、第一の事実とは別の理由である。

自由関数(`impl` の外の `fn`)と工程が `&mut 型` を受ける形は、型自身のAPIではないため、この法則の対象ではなく、検査器も検査しない(第2節の「`&mut 規則` を受ける自由関数」の記述と同じ範囲である)。

### 2.5.4 設計の方針

Rust では束縛が既定で不変だが、それは言語の性質である。本節が扱っているのは設計の上での変更可能性・同一性・ライフサイクルであり、言語の性質とは別の層として明示する。意味のあるドメインの制約はマーカーとして明示し、できる限り法則を構文の検査(`cargo xtask conform`)で確かめる。

## 2.6 関数境界の役割(必須入力の束と任意の設定の束と評価の排他的な帰結)

関数境界の役割は、入力側の `MParameter` と `MOptions`、出力側の `M結果` を扱う。関数の境界を渡る型を、必須入力の束(`MParameter`)と任意の設定の束(`MOptions`)、評価の排他的な帰結(`M結果`)に分類する。

本書はこの分類を、データの役割と処理の役割(第2節)とも存在の分類とも変更可能性(2.5節)とも別の軸として置く。データの役割は「その型は因果モデルのどこに現れるか」を問い、存在の分類は「その型は同一性を持つか」を問い、変更可能性は「その型は自己変更を行うか」を問うのに対し、関数境界の役割は「その型は関数の境界をどう渡るか」を問う。どの既存の軸の問いにも答えないため、既存の軸の中へ入れない。`MParameter` と `MOptions` はこの軸の排他の分類であり、同じ型が両方を名乗ることを `cargo xtask conform` が違反にする(2.6.1)。`M結果` は排他の組に入らない。

| マーカー | 定義 | 上位トレイト | 課す法則 | `cargo xtask conform` が検査するもの |
|---|---|---|---|---|
| `MParameter` | 関数の実行に必要な必須入力を、名前付きのプロパティとして1つの引数オブジェクトへ束ねた型 | `M不変データ` | 関数へ渡す必須入力の束である。各プロパティは必要だから存在する値である。`Option<T>` をフィールドとして持たない。不変性は `M不変データ` から継承する | 定義に `Option<` のフィールドが無いこと(2.6.1)。`M不変データ` を通して純粋データ規約と 自己変更の禁止 |
| `MOptions` | 関数呼び出し時に、呼び出し側が任意に指定できる設定を束ねる引数オブジェクト | `M不変データ` | `Option<T>` をフィールドとして持つことを許す。全フィールドが `Option<T>` である必要は無い。`Option<T>` を持つこと自体は成立の条件でない。指定してもしなくても関数の呼び出しが成立する設定を束ねる | `M不変データ` を通して純粋データ規約と 自己変更の禁止 |
| `M結果` | ある処理・評価の出力の境界で、その処理が取り得る排他的な帰結を表す判別型。標準の `Result<T, E>` と、意味を持つ独自の `enum` が代表形である | 無し | 構文の法則: 結果は判別型(`Result` または `enum`)であり、`struct` は `M結果` になれない。意味の法則: 関数境界の役割であり、単なる状態の列挙ではない。各選択肢が運ぶ値(`遷移成功結果`・`遷移失敗結果`)そのものは `M結果` ではない | 実装の対象の型が `enum` であること(標準の `Result` は特例)と、実装の正規形・別名の取り込みの禁止・波括弧付きのモジュールの中の実装の禁止・再公開の禁止(2.6.1) |

`M結果` に上位トレイトを付けないのは、`Result<T, E>` の性質が `T` と `E` に依存し、一律に `M不変データ` を課せないためである。純粋データ規約と 自己変更の禁止も `M結果` には課さない。`blitz_design` は `impl<T, E> M結果 for Result<T, E> {}` を持ち、標準の `Result` が `M結果` であることを型で示す。例えば `Result<遷移成功結果, 遷移失敗結果>` で結果を表しているのは外側の判別構造であり、内側の2つの値ではない。

`M結果` の位置づけは、型の形ごとに次のとおりである。

```text
std::Result<T, E>  -> 型自体の標準の意味(成功と失敗の排他的な帰結)により自動で M結果 と解釈する
独自の enum        -> 設計者が M結果 を実装したときだけ M結果 である(enum であるだけでは結果とは限らない)
struct             -> M結果 にはなれない(結果の値を束ねた struct は排他的な帰結そのものではない)
```

`M結果` の構文の法則は「結果は判別型である」ことであり、`cargo xtask conform` が機械で閉じる(2.6.1)。

`M結果` の意味の法則は「`M結果` は関数境界の役割であり、単なる状態の列挙ではない」ことである。判別型であるだけでは `M結果` ではない。

```rust
enum 接地状態 { 接地, 空中 }              // 判別型だが処理の帰結ではないため M結果 ではない
enum 接地判定結果 { 接地(...), 非接地, 評価不能(...) }  // 評価の排他的な帰結であるため M結果 になり得る
```

意味の法則は `cargo xtask conform` で完全には判定しない。`enum` が処理の帰結を表しているかは意味論であり、構文の検査では判定できないためである。

値が無い状態がドメイン上の必須入力なら、実装者は `Option<T>` を置かずに、その意味を表す専用の型か列挙へ持ち上げる。`MOptions` はブラウザの DOM API などにある options object に近い概念として扱う。Esca第1段階では `遷移パラメータ`(3.5.1)が `MParameter` を実装し、`MOptions` を実装する型はまだ無い。

### 2.6.1 機械検証の範囲

`cargo xtask conform` は、`MParameter` を実装する型の定義ブロック(コメントと文字列を落としたコードだけの行)に `Option<` の文字列があれば違反にする。検査は文字列の照合であり、型の別名を通した `Option`(`type 任意の値 = Option<u8>` を経由する形)と、フィールドの型である別の構造体に埋めた `Option` は見ない(`Vec<Option<u8>>` のように定義の行に `Option<` が現れる入れ子は見つかる)。`MOptions` には課さない。同じ型が `MParameter` と `MOptions` の両方を名乗ることは違反にする(型の同一性は推定したモジュールパス + 型名で突き合わせる)。実装の正規形・別名の取り込みの禁止・波括弧付きのモジュールの中の実装の禁止・再公開の禁止(第5節)は、この2つのマーカーにも `M結果` にも `M工程` にも掛かる。

`M結果` については、実装の対象の型が `enum` であること(構文の法則)を検査する。`impl M結果 for X` の `X` の定義をたどり、たどり着いた定義が `enum` でなければ違反にする。標準の `Result` への `M結果` の実装は `crates/blitz_design/src/marker.rs` の完全に修飾した包括の実装 `impl<T, E> M結果 for std::result::Result<T, E> {}` の1箇所だけであり(他のクレートが標準の `Result` へ改めて実装することは coherence 上もできない)、そこだけが定義をたどらない特例である(`xtask/src/conform/design_ontology/trait_implementation.rs` の `トレイト実装型::正本の標準resultへの包括の実装か`。実装の行が正本のファイルにあることと、対象の型の表記が `std::result::Result` で始まることで判定する)。他の `impl M結果 for X` は、`X` の名前に関わらず、また正本のファイルにあっても定義をたどるため、`Result` という名前の独自の `struct` は正本のファイルに置いても違反になり、`Result` という名前の独自の `enum` は明示的に `M結果` を実装すれば許される。`M結果` には純粋データ規約と 自己変更の禁止を課さない(`M不変データ` を上位トレイトに要求しないため。`純粋データの役割一覧` に入れない)。

## 3. 関数の役割

`blitz_design` は、関数の設計上の役割を表す境界付きの newtype を2つ持つ。

- `M射影関数<状態: M状態, 射影DTO: M不変データ>` は `fn(&状態) -> 射影DTO` を包み、状態から外部向けの表示データを取り出す一方向の観測の計算である。
- `M解釈関数<入力: M入力, コマンド: Mコマンド>` は `fn(&入力) -> コマンド` を包み、生の入力から主体のコマンドを導く純粋な解釈の計算である。

型エイリアスに書いた境界は Rust の仕様上強制されない(rust-lang/rust#112792)。そのため関数の役割は型エイリアスでなく、関数ポインタを包む構造体(newtype)であり、型引数の境界を構造体の宣言に書く。構造体の境界は利用箇所でコンパイラが強制するため、型を使った時点で型引数の境界が掛かる。迂回できる書き方は無い(`blitz_design::M射影関数<...>` と修飾しても、`use ... as` で別名を付けても、`let` で受けても、型を使った時点で境界が掛かる)。各 newtype は `生成する(関数)` で関数を包み、`呼び出す(&引数)` で包んだ関数を適用する。利用側は `const _: M射影関数<A, B> = M射影関数::生成する(関数);` の静的宣言で、関数が役割を満たすことをコンパイラに確かめさせる。

`M遷移関数<状態: M状態, コマンド: Mコマンド, 規則: M規則, イベント: Mイベント, 失敗: std::error::Error>` と `遷移成功結果<状態, イベント>` は `crates/blitz_esca/src/ontology.rs` に残る。`M遷移関数` も同じ形の境界付きの newtype である。`遷移成功結果` は型引数に `M状態`・`Mイベント` の境界を持つ意味型であり、汎用の入れ物ではない。構造体に書いた境界は利用箇所でコンパイラが強制するため、`遷移成功結果<String, usize>` のような値は作れない。本書がこれらを `blitz_design` へ上げないのは、これらが計算モデルまで固定しているためであり、まず Esca 側で確定してから昇格を判断する。遷移パラメータ(3.5.1)の一般形がまだ確定していないことも、本書が `M遷移関数` を `blitz_design` へ上げない理由である。

## 3.5 状態遷移の理論(因果モデル)

本節は、状態遷移の理論を定める。この理論は、第2節の設計解釈マーカーと第3節の関数の役割が、個別に便利なトレイトの集まりではなく、ゲーム世界の因果関係を記述するための一組の設計語彙であることの根拠である。

### 3.5.1 基本形

本書は、状態遷移の基本形を次の図で表す。

```text
                  規則
                   │
                   ▼
現在の状態 ──┐
             ├─ 状態遷移(遷移を評価) ─┬─ 成功 ──→ 次の状態
コマンド ────┘                        │            │
                                      │            └─→ 起きた出来事
                                      │                   │
                                      │                   ▼
                                      │                イベント
                                      └─ 失敗 ──→ 失敗(次の状態も出来事も無い)
```

遷移の型は次である。

```text
遷移 : 状態 × コマンド × 規則
      -> 成功(遷移成功結果) | 失敗
```

一般形は次である。

```text
遷移 : 状態 × コマンド × 規則 × 遷移パラメータ
      -> 成功(遷移成功結果) | 失敗(遷移失敗結果)
```

遷移パラメータとは、遷移関数の実行に必要な、状態でもコマンドでも規則でもない必須の入力(経過時間・乱数源から確定した値・世界時刻・刻みの情報など)を、名前付きのプロパティとして1つの引数オブジェクトへ束ねた型のことである。`MParameter`(2.6節)を実装する。この型は遷移関数の実行に必要な引数を1つのオブジェクトへ束ねたものであるため、名前を `遷移パラメータ` とする。Esca第1段階では遷移パラメータは `経過時間` だけを持ち(`crates/blitz_esca/src/transition_parameter.rs`)、実装の `M遷移関数` は `(&状態, &コマンド, &規則, 遷移パラメータ) -> Result<遷移成功結果, 失敗>` である。3.5の基本形の図は遷移パラメータを省略した概念図である。遷移パラメータの一般形(どの入力を含めるか)はまだ確定していない。

遷移は成功と失敗の2つの選択肢を持つ。成功は遷移成功結果(次の状態 + その評価で成立した事実)であり、失敗は有効な次の状態を構築できなかったことである(3.5.9)。失敗を型で返すかは各ドメインが決め、Esca は `Result` で返す。

この文書と実装は、図の「起きた出来事」を `出来事一覧` という名前で呼ぶ。`遷移成功結果` は第4.1節が定義する `遷移成功結果<状態, イベント>` であり、フィールド名は `次の状態` と `出来事一覧` である。

### 3.5.2 4概念の意味

状態・コマンド・規則・イベントの4概念は、それぞれ次の意味と時制を持つ。

| 概念 | 何を表すか | 時制 |
|---|---|---|
| 状態 | 今どうなっているか | 現在 |
| コマンド | 何をしようとしているか | 未来への要求 |
| 規則 | 何が起きてよいか、どう変わるか | 不変の法則 |
| イベント | 実際に何が起きたか | 過去の事実 |

規則の「不変」とは、1回の遷移の評価のあいだ読み取り専用の入力であることである。規則の「不変」は、プログラムの全期間で同じ値であることを意味しない(速度の強化や難易度の変更で規則の値が変わることを妨げない)。

### 3.5.3 Escaの旅行者での例

Escaの旅行者の場合は、次の関係になる。

```text
状態
  現在地 = (10m, 20m)
  行動状態 = 静止中

コマンド
  東へ歩く

規則
  歩行速度 = 3m/s
  東側に壁がある

        ↓ 遷移

次の状態
  現在地 = (11m, 20m)
  行動状態 = 歩行中

イベント
  歩行を開始した
  壁に接触した
```

この例が持つ `行動状態` は、現在の `blitz_esca` の状態には無い。`歩行を開始した` や `立ち止まった` を出来事として持つには、前の状態と次の状態の行動の差を判定できる `行動状態` が状態側に要る。現状の `blitz_esca` はこの `行動状態` を持たないため、`歩行を開始した` や `立ち止まった` を出来事として生成していない(参照: `_doc/設計/Esca/設計正本.md` 4.4 条5)。

### 3.5.4 イベントは状態変更の命令ではない

イベントは状態変更の命令ではない。イベントは、遷移の評価で成立した事実である。向きは次である。

```text
前状態 + コマンド + 規則
        ↓
     遷移を評価
        ├─ 失敗 → 失敗の値だけ(次状態も事実も無い。3.5.9)
        ↓ 成功
次状態 + その評価で成立した事実
        ↓
   イベントとして公開する
```

成立する事実は、状態が変化したことを必要としない。現行の `blitz_esca` では `旅行者の意図::見回す` の遷移が次の状態を前の状態と同じまま返し、`旅行者の出来事::周囲を観察した` を出来事一覧へ入れる。状態は変わらないが、観察したという事実は遷移の評価で成立している。

そのうち、`歩行を開始した`・`立ち止まった`・HPが0になった・扉が開いた のような状態変化イベントだけが、前状態と次状態の差分を根拠にする。状態変化イベントは、前状態と次状態の差を表現できることが生成条件である(4.4 の法則E2)。

### 3.5.5 イベントシステムの定義

イベントシステムとは、ある状態遷移で成立した事実を、その事実を必要とする別の系へ伝播させる仕組みのことである。伝播先の例は次である。

```text
                     ┌→ 音響
                     │    「歩行を開始した」
                     │       → 足音開始
                     │
状態遷移 → イベント ├→ アニメーション
                     │       → 歩行アニメ開始
                     │
                     ├→ クエスト
                     │       → 「初めて歩いた」を記録
                     │
                     └→ AI
                             → 近くの敵が音に反応
```

### 3.5.6 状態遷移系とイベント伝播系の二層

この理論は、少なくとも次の二層を分ける。

```text
【状態遷移系】

M状態
Mコマンド
M規則
Mイベント
M遷移

        ↓ イベントを生成

【イベント伝播系】

Mイベント発行
Mイベント購読
Mイベント反応
Mイベント配送
```

状態遷移系とは、`M状態`・`Mコマンド`・`M規則`・`Mイベント`・遷移関数からなる、状態を遷移させて起きた事実を生成する側の層のことである。イベント伝播系とは、状態遷移系が生成したイベントを、それを必要とする別の系へ伝播させる側の層のことである。イベント伝播系が持つ発行・購読・反応・配送の4語は、現在の `blitz_design` にはまだ無い候補である。

### 3.5.7 イベント反応

イベント反応とは、イベントを受けて、コマンド・外部作用・別のイベント・何もしない のいずれかを返す工程のことである。イベント反応は次の型を持つ。

```text
イベント反応:
    イベント
        -> コマンド
        | 外部作用
        | 別イベント
        | 何もしない
```

例は次の2つである。

```text
敵を倒した
   ↓
クエストシステムが観測
   ↓
「報酬を付与する」というコマンドを生成
```

```text
敵を倒した
   ↓
音響システムが観測
   ↓
SEを鳴らす
```

この整理は、`Mイベント` がイベントシステム全体を表す型ではなく、状態遷移系とイベント伝播系をつなぐ「起きた事実」を表すマーカーであることを示す。

### 3.5.8 全体の因果モデル

全体の因果関係は次のモデルで表す。

```text
意図
 ↓
コマンド
 ↓
状態 + 規則
 ↓
状態遷移 ─ 失敗 → 失敗の値(新しい状態も起きた事実も無い。3.5.9)
 ↓ 成功
新しい状態
 +
起きた事実
 ↓
イベント
 ↓
別の系の反応
 ↓
新しいコマンド / 外部作用 / 別イベント / 出来事の保存(ログ・リプレイ・監査履歴など)
```

`M状態`・`Mコマンド`・`M規則`・`Mイベント` は、個別の便利なトレイトではなく、ゲーム世界の因果関係を記述するための一組の設計語彙である。

### 3.5.9 遷移失敗結果

遷移失敗結果とは、与えられた状態・コマンド・規則・遷移パラメータから、有効な次の状態を構築できなかったことを表す失敗側の値のことである。遷移の評価は成功と失敗の2つの選択肢を持つ。成功側の値を遷移成功結果(次の状態 + その評価で成立した事実)と呼び、失敗側の値を遷移失敗結果と呼ぶ。外側の `Result` が成功と失敗の分岐そのものを表すため、内側の成功側だけを「遷移結果」と呼ぶと `Result` 全体と意味が競合する。そのため成功側と失敗側を対称に名付ける。

```text
遷移
├─ 成功 → 遷移成功結果
│          ├─ 次の状態
│          └─ 出来事一覧
└─ 失敗 → 遷移失敗結果
```

実装の `M遷移関数` の型引数 `失敗` の名前は変えない。型引数は具体の失敗の型を各ドメインが決めるための穴であり、そこへ入る型を本書は遷移失敗結果と呼ぶ。

- 失敗のとき、次の状態は採用されない。呼び出し側は元の状態を維持する。
- 失敗のとき、出来事は1件も生じない。遷移が成立していないため、成立した事実も無い。
- 「遷移に失敗した」は `Mイベント` ではない。`Mイベント` はその遷移によって実際に成立した事実であり、失敗は事実の不成立である。失敗を別の系へ伝えるなら、呼び出し側が失敗の値を見て自分の語彙で表す。
- 法則E1からE8(4.4)は、成功した遷移だけを対象とする。
- Esca第1段階では、失敗は `旅行者の現在地の生成の失敗`(数値の表現の上で有効な次の状態を構築できなかったこと)である。実装の `M遷移関数` は失敗を `std::error::Error` の型引数で受け、`Result<遷移成功結果, 失敗>` で返す。

## 4. Update型のEventの語彙とコード文法

第4節は、第3.5節の理論の、Event側の語彙とコード文法である。

Observer / callback 型の Event と、`Mイベント` は別概念として語彙を分離する。Observer 系の `Event`・`Subscriber`・`Listener`・`Handler`・`Subscribe`・`Unsubscribe`・`Invoke` は「呼び出し機構」の語彙である。`Mイベント` はそうではなく、Update / 遷移が生成する過去の事実データである。したがって本書は、こちらにも「何を何と呼び、コードをどう書くか」という独自の文法を定める。

### 4.1 基本語彙

**`Mイベント` / 出来事**とは、ある遷移によって実際に成立した過去の事実を表す値のことである。

```rust
pub trait Mイベント: M不変データ {}
```

Event 自身は誰かを呼び出さない。Event はコールバック一覧、`invoke()`、購読者を持たない。`struct` と `enum` のどちらでもよい。次の2つはどちらも正当な `Mイベント` である。

```rust
pub enum 旅行者の出来事 {
    歩行を開始した,
    立ち止まった,
    障害物に遮られた,
}
```

```rust
pub struct ダメージを受けた {
    pub 対象: 個体ID,
    pub 量: ダメージ量,
}
```

**`遷移成功結果<状態, イベント>`**とは、Update / 遷移が返す、次の状態と、その遷移で成立した出来事の組のことである。この型は状態と出来事を混ぜない境界である。

```rust
pub struct 遷移成功結果<状態, イベント> {
    pub 次の状態: 状態,
    pub 出来事一覧: Vec<イベント>,
}
```

**出来事の生成**とは、遷移の計算中に、実際に成立した事実を `出来事一覧` へ追加することである。出来事の生成は Observer 系の `invoke` に相当する語ではない。

- 良い語: `出来事を生成する`、`出来事一覧へ加える`、`〜が成立した`
- 避ける語: `invoke`、`fire`、`通知を呼ぶ`

`emit` を日本語へ持ち込む場合も、書き手はそれを「コールバックを呼ぶ」意味ではなく「出来事値を出力する」の意味に限定する。

**出来事の配送**とは、既に生成済みの出来事値を、0個以上の消費側へ渡す工程のことである。配送は新しい事実を作らない。配送は既存の事実を読者へ渡すだけである。

```text
遷移成功結果.出来事一覧
        │
        ├─→ 音響への解釈
        ├─→ 演出への解釈
        ├─→ 進行への解釈
        └─→ ログ
```

**出来事の解釈**とは、出来事を、別のドメインや外部システムが理解する型へ純粋変換することである。

```text
旅行者の出来事
    → 音響要求
    → 演出要求
    → 別ドメインのコマンド
```

基本形は `fn (&イベント) -> 出力` であり、0件以上を返すなら `fn (&イベント) -> Vec<出力>` である。将来、共通の関数役割として必要になった場合は `Mイベント解釈関数<イベント, 出力>` のような型を検討できるが、利用例が固まる前に共通化しない。

**要求**とは、SE再生、パーティクル生成、画面演出など、外部システムへ「これを実行してほしい」と渡す値のことである。

```text
旅行者の出来事::障害物に遮られた
    ↓ 解釈
壁衝突音を再生する要求
```

ドメインの遷移関数自身は音響API等を呼ばない。イベントから要求へ変換した後、外部境界が要求を実行する。`M要求` を共通の設計解釈マーカーにするかどうかの判断は4.2.1節が持つ。

### 4.2 標準データフロー

Update型のEventシステムの標準形を次とする。

```text
M入力
  ↓ 解釈
Mコマンド
  ↓
M状態 + Mコマンド + M規則
  ↓ 遷移
遷移成功結果<M状態, Mイベント>
  ├─ 次の状態 ─────────→ 次回の状態正本
  │
  └─ 出来事一覧
       ├─→ 出来事の解釈 → 音響要求 → 音響境界
       ├─→ 出来事の解釈 → 演出要求 → 描画/演出境界
       ├─→ 出来事の解釈 → 別ドメインのMコマンド → 別のUpdate
       └─→ ログ / リプレイ等
```

重要なのは、`Event -> callback` ではなく `Event -> data flow` である。

### 4.2.1 `M要求` を共通の設計解釈マーカーにしない(2026-09-21。Issue #172)

本書は、2026-09-21時点で `M要求` を共通の設計解釈マーカーにしない。理由は次の3つである。

第一に、定義に合致する実例が0件である。`M要求` の定義は「音を鳴らしてほしい・演出を出してほしい・外部のAPIへこの操作を実行してほしい」であり、イベントを解釈して生まれることを前提にしている。しかしこのリポジトリには音響のクレートも依存も無く、`Mイベント` を実装する型は `crates/blitz_esca/src/traveler.rs` の `旅行者の出来事` の1件だけであり、その出来事から要求へ解釈する工程は1つも実装されていない。`Mイベント → 解釈 → M要求 → 外部境界` という連なりは1本も存在しない。

第二に、`Mコマンド` との差が構文に現れず、機械で判定できない。`crates/editor_server/src/resource/command/mod.rs` の `編集コマンド` と `crates/editor_server/src/resource/music/command/mod.rs` の `楽曲編集コマンド` は、不変の判別共用体であり、作った側(ブラウザ)ではなくブラウザのTypeScriptの編集モデル(外部の境界)が実行し、Rust側は適用の実装を持たない。形の上では `crates/blitz_render/src/present_display/request.rs` の `実表示計測要求` と完全に同じでありながら、意味は `Mコマンド` の側である。逆に `実表示計測要求` も「計測してほしい」という主体の意図として読めば `Mコマンド` の定義に当てはまる。差は「誰が実行するか」という型と型の関係にあり、これは第6節の設計関係が機械検査へ接続されてからでないと表せない。

第三に、構文の法則が定まらない。実例は `enum`(`実表示計測要求`・`表示距離の指示`・`起動要求`・`検収の経路`)と `struct`(`報告要求`・`接合の指示`・`焼き上げの計画`・`プリミティブ描画発行`)に割れており、`Mコマンド` のような「必ず `enum`」の法則を課せない。また `M不変データ` を課すと、レンダラーへ渡す最大の要求である `crates/blitz_render/src/frame_input.rs` の `フレーム描画入力<'a>`(参照を4つ持つ)が排除される。課さないなら、`M要求` は役割の名札以上のものを何も保証しない。

一方で、記録する価値のある反復する形がある。「不変の判別共用体を作って外部の境界へ渡し、渡した側は実行しない」という形が少なくとも6件で反復しており、`crates/blitz_app/src/world_execution/contract/display_distance.rs` の `表示距離の指示`・`crates/blitz_app/src/cli/launch_request.rs` の `起動要求`・`crates/blitz_app/src/app/report_requests.rs` の `報告要求`・`crates/blitz_app/src/app/verification_launch_settings/route.rs` の `検収の経路` は、いずれもモジュールの冒頭コメントで「ここは値を保つだけである」「判定の材料も判定の順序も持たない」と明文で書いている。語彙としては存在するが、設計解釈マーカーとしては括れていない状態である。

判断を改める条件は次のとおりである。第6節の設計関係が機械検査へ接続され、かつ音響か演出の境界が1つでも実装されてイベントから要求を作る工程が現れたときに、実装者はこの判断を改めて検討する。

### 4.3 Observer系の語彙との対応

この方式では以下の語を原則として使わない。

| Observer / callback型 | Update型で対応する概念 |
|---|---|
| Event object with invoke | `Mイベント` という事実値 |
| Subscriber / Listener | 出来事の消費側 |
| Handler | 出来事の解釈、または要求を実行する工程 |
| Subscribe | コンポジションルートで消費側を明示配線する |
| Unsubscribe | 通常は存在しない。配線自体の寿命を変える |
| Invoke / Fire | 出来事値を生成して遷移成功結果へ入れる |
| EventArgs | `Mイベント` 自身のデータ |
| EventBus | 原則作らない。必要なら「出来事の配送工程」として役割を限定する |

特に `Handler` という語は曖昧なので避ける。書き手は責務ごとに語を分ける。

- Event を別の値へ変換するなら「解釈」
- Event を複数の読み手へ渡すなら「配送」
- 要求を外部APIで実行するなら「実行」
- 状態を更新するなら「遷移」

### 4.4 Event生成の法則(E1〜E8)

#### 法則E1: 過去の事実

`Mイベント` は、既に成立した事実だけを表す。

#### 法則E2: 成立していない事実を生成しない

イベントは、その遷移によって実際に成立した場合だけ生成する。

悪い例:

```text
コマンド = 歩く
→ 毎刻み「歩行を開始した」を生成
```

正しい判定:

```text
前状態 = 非歩行
次状態 = 歩行
→ 「歩行を開始した」
```

したがって「開始した」「終了した」「変化した」のような状態変化イベントは、前状態と次状態の差を表現できることが生成条件になる。

#### 法則E3: 状態正本へ混ぜない

イベントは次回Updateへ持ち越す状態正本ではない。

```rust
struct 状態 {
    歩行開始イベントが起きた: bool,
}
```

のように「一度起きた出来事」をリセット前提のフラグとして状態へ埋め込まない。継続して成立する事実なら、それはイベントではなく状態として表す。

#### 法則E4: 消費されても事実は変わらない

消費側はイベントを変更しない。複数の消費者が同じ事実を読める。

#### 法則E5: 配送は意味を作らない

配送工程はイベントの意味を決めない。意味は Event 型の定義と生成元の遷移が決める。

#### 法則E6: 副作用は遷移から分離する

純粋なドメイン遷移は音響・描画・ネットワーク等を直接実行しない。

```text
遷移
→ Mイベント
→ 解釈
→ 要求
→ 外部境界で実行
```

と分ける。

#### 法則E7: 隠れた購読表を作らない

どの Event を誰が読むかは、可能な限りコンポジションルートまたは明示された工程のコードから追える形にする。任意の場所から `subscribe(TypeId, callback)` して依存関係を隠す汎用 EventBus を基本形にしない。

#### 法則E8: Eventから同じ状態への暗黙フィードバックを作らない

その遷移自身が知っている事実によって同じ状態をさらに変える必要があるなら、原則として最初の遷移の中で状態を確定する。別ドメインへ影響するときは、

```text
Mイベント
→ 解釈
→ 相手ドメインのMコマンド
→ 相手のUpdate
```

と明示する。これにより Event の連鎖で同一tick内に何度状態が変わるか分からない構造を避ける。

### 4.5 型・関数の文法

Event 型は次の形で書く。`struct` / `enum` は意味に応じて選ぶ。

```rust
#[derive(Clone, ...)]
pub struct / enum 何かの出来事 { ... }

impl M不変データ for 何かの出来事 {}
impl Mイベント for 何かの出来事 {}
```

`Mイベント: M不変データ` であるため、`impl Mイベント for` だけではコンパイルできず、`impl M不変データ for` も要る(他のデータの役割 `M状態`・`Mコマンド`・`M規則`・`M入力` も同じ)。

遷移は次の形で書く。遷移は成功のとき「次の状態」と「その評価で成立した出来事」を同時に確定し、失敗のとき失敗の値だけを返す(3.5.9)。

```rust
状態.〜を遷移する(
    &コマンド,
    &規則,
    遷移パラメータ,
) -> Result<遷移成功結果<状態, 出来事>, 失敗>
```

失敗を持たない遷移は `Result` を使わなくてよい。失敗を型で返すかは各ドメインが決める。Esca第1段階の遷移パラメータは `経過時間` だけを持つ。

解釈は、主語が自然なら次のように書ける。

```rust
出来事.音響要求へ解釈する()
出来事.演出要求へ解釈する()
```

ただし1つの Event 型へ各サブシステム固有の知識を集めて依存を逆流させる場合は、消費側の型に次のように置く。配置は「どちらがどちらを知ってよいか」という依存方向で決める。

```rust
音響方針.出来事を音響要求へ解釈する(&出来事)
```

配送は、中央の汎用 EventBus ではなく、その局面で必要な配送を明示する。

```text
一刻みを進める
  → 遷移成功結果を得る
  → 出来事一覧を各解釈工程へ渡す
  → 要求を各外部境界へ渡す
  → 次の状態を正本へ採用する
```

順序に意味がある場合は「購読登録順」に依存させず、工程の順序として名前を与える。

### 4.6 機械判定すること・しないこと

現在の `cargo xtask conform` は、次を法則として維持する。

- `Mイベント: M不変データ`(コンパイラが強制する。`Clone` は `M不変データ` から継承する)
- 参照を持たない
- 生ポインタを持たない
- 内部可変性を持たない
- 受け手と引数に自分の型への可変参照を持たない(固有の `impl`・トレイトの実装・実装しているトレイトの宣言の既定の関数)(`M不変データ` を実装する型すべてに課す)

参照・生ポインタ・内部可変性の検査は、`M不変データ` と役割(`Mイベント`・`M規則`・`Mコマンド` 等)の実装から型の定義をたどり、その定義に対して行う。`Mイベント: M不変データ` 等の supertrait の Relation はコンパイラが保証し、`impl M不変データ for` の置き場所は問わない。`&mut self` が無いだけでは `RefCell` 等を通じて `&self` から書き換えられ、読み取り専用で与えられる規則値や純粋計算という定義に反するためである。

さらに検査器で型を正確に同定できるようになった後は、次を候補にする。これらは「現在・未来・過去」の役割を同じ型へ重ねないための直交の法則である。

- 同じ具体型が `M状態` と `Mイベント` を同時に実装しない
- 同じ具体型が `Mコマンド` と `Mイベント` を同時に実装しない
- 同じ具体型が `M入力` と `Mイベント` を同時に実装しない

一方、次は一般の構文検査では判定しない。これらは意味論または具体ドメインの配線だからである。

- イベントが本当に成立した事実か
- 開始/終了イベントが状態差からだけ生成されているか
- 名前が日本語の過去形か
- 必ず1フレームで消えるか
- enumであるか
- Event がどの消費者へ配送されるべきか

### 4.7 コメント / rustdoc の文法

Event のコメントは「何の通知か」ではなく、どの事実が成立した値なのかを書く。

悪い例:

```rust
/// 歩行開始時に使うイベント。
歩行を開始した,
```

良い例:

```rust
/// 非歩行状態から歩行状態へ遷移した事実。歩行中の各刻みを表すものではない。
歩行を開始した,
```

```rust
/// 移動先が空間制約を越え、実際の移動位置が制限された事実。
障害物に遮られた,
```

特に状態変化イベントは、前に何であり、次に何になったとき、この事実が成立するかがコメントから分かるようにする。

消費先(SEを鳴らす、エフェクトを出す等)は Event 自身の意味ではないので、書き手は Event 型の定義コメントには原則書かない。書き手はそれを消費側の「解釈」に書く。

### 4.8 Marker / Relation / Law としての位置付け

```text
Marker
  Mイベント
    = 過去の事実として解釈する型

Relation
  M遷移関数
    produces -> 遷移成功結果<状態, イベント>

  出来事の解釈
    consumes -> Mイベント
    produces -> 要求 / 他ドメインのMコマンド / 出来事の保存(ログ・リプレイ・監査履歴など)

Law
  E1 過去の事実
  E2 成立した事実だけ生成
  E3 状態正本へ混ぜない
  E4 消費側は事実を変更しない
  E5 配送は意味を作らない
  E6 副作用を遷移から分離
  E7 隠れた購読表を基本形にしない
  E8 同一状態への暗黙Eventフィードバックを作らない
```

この形なら Observer パターンと同様に、読み手は `Mイベント` を見た時点で「この型が何であり、どこから生まれ、どう流れ、どう書いてはいけないか」までコード文法として共有できる。

## 5. 機械強制の手段

依存の向きは `xtask/src/conform/dependency_whitelist/ledger.rs` の白リストが機械で強制する。`blitz_design` の行は依存ゼロであり、`blitz_sim` と `blitz_esca` の行が `blitz_design` を許す。

法則の検査主体は2つに分かれる。

- コンパイラが強制する法則: データの役割(`M状態`・`Mコマンド`・`Mイベント`・`M規則`・`M入力`)の `M不変データ` 実装(上位トレイト)、`M不変データ` の `Clone`(上位トレイト)、存在の分類の上位トレイト(`M値オブジェクト` の `PartialEq`、`Mエンティティ識別子` の `Eq`・`Hash`)と `Mエンティティ` の関連型と識別子のメソッドの存在(2.5節)、関数の役割の型引数の境界、`遷移成功結果` の型引数の `M状態`・`Mイベント` の境界(構造体の境界)。型エイリアスの境界は Rust の仕様上強制されない(rust-lang/rust#112792)ため、関数の役割(`M射影関数`・`M解釈関数`・`M遷移関数`)は境界付きの newtype であり、型を使った時点でコンパイラが型引数の境界を強制する。迂回できる書き方は無い。利用側は `const _: M遷移関数<...> = M遷移関数::生成する(旅行者の現在地::歩行を遷移する);` の静的宣言でコンパイラに確かめさせる。
- `cargo xtask conform` の設計オントロジーの検査(`xtask/src/conform/design_ontology.rs`)が見る法則: `M不変データ` またはデータの役割を実装する型の定義に参照・生ポインタ・内部可変性が無いこと(役割の実装から型の定義をたどってその定義に当てる。`Mコマンド: M不変データ` 等の supertrait の Relation はコンパイラが保証し、`impl M不変データ for` の置き場所は法則にしない)、`Mコマンド` が `enum` であること、`M規則` が `struct` であること、`M結果` を実装する型が `enum` であること(正本の標準の `Result` への包括の実装だけが定義をたどらない特例。2.6.1)、`M不変データ` を実装する型(データの役割を実装する型をすべて含む)が受け手と引数に自分の型への可変参照を持たない(固有の `impl`・トレイトの実装・実装しているトレイトの宣言の既定の関数)こと(読む範囲は 2.5.3)、`MParameter` を実装する型の定義に `Option<` のフィールドが無いこと(2.6.1)、同じ型が同じ軸の排他の分類(`M不変エンティティ` と `M可変エンティティ`、`MParameter` と `MOptions`)を同時に名乗っていないこと(2.5.1・2.6)。定義が見つからない型は違反として報告する。

検査器の保証範囲は次のとおりである。検査は Rust の型意味論でなく構文パターン(`impl トレイト for 型` の行と `struct`/`enum` の定義ブロック)に対して行う。型の同一性は「標準的なファイル配置から推定したモジュールパス + 型名」である(`crates/<名前>/src/lib.rs` は `<名前>`、`src/a/b.rs` は `<名前>::a::b`、`src/a/mod.rs` は `<名前>::a`)。`impl トレイト for 型` の行がどの定義を指すかは、実装と同じファイルの定義、無ければそのファイルの `use` 行(`crate::`・`super::`・`self::` の置き換えと1段の波括弧の群)から取り込み元のモジュールパスを求めて、そのモジュールパスの定義で決める。`use` が無ければ別モジュールの同名の定義を推測せず、定義が見つからない違反にする。同じファイルに同名の定義が複数あるとき(波括弧付きのモジュール `mod 名 { ... }` で分けた場合)も一意に決まらないとして違反にする(黙って最初の1つを選ばない)。実装対象の型を `use ... as` の別名で取り込んだ実装は取り込み元を求められない違反にする(黙って通さない)。自己変更の禁止の探索も同じ規則で定義に属する実装だけを見るため、同じクレートの別のモジュールの同名の型の `impl` を誤って数えない(CLAUDE.md の切り出しの根拠義務が `impl` を別ファイルへ置くことを許すため、同じファイルだけに限定しない)。入れ子の波括弧の `use`、glob の取り込み、型引数の境界が入れ子の `<` を含むジェネリックな `impl`、フィールドの型の中に間接的に含まれる内部可変性は保証範囲の外である。`#[path = "..."] mod` については、conform が別に、`crates` 配下の `src` のすべての `mod` の宣言について、宣言から読める論理のモジュールパス(宣言元のファイルのモジュールパス + 宣言されたモジュール名)と、対象の物理ファイルから求める物理のモジュールパスが等しいことを確かめる(`xtask/src/conform/design_ontology/module_declaration.rs` と `module_structure_assertion.rs`)。日本語のモジュールは rustc が既定のファイルの探索を E0754 で拒むためこの属性を必ず持ち、この一致の検査によって上の推定はそのまま成り立つ。

設計解釈マーカーの実装の形は正規形へ固定する。設計解釈マーカーの実装は `impl マーカー名 for 型` または `impl blitz_design::マーカー名 for 型` の形に固定する。`blitz_design` を別名で取り込むこと(`use blitz_design as 別名;`・`use blitz_design::M不変データ as 別名;`・`use blitz_design::{M不変データ as 別名};` のいずれも)は conform が違反にする。別名で取り込むと conform が実装を認識できず、法則を破れる合法な Rust を黙って通すためである。別名を使わずに正規形を迂回する書き方も conform が違反にする。迂回する書き方とは、再公開の経由(`mod design_alias { pub use blitz_design::M不変データ; }` と書いてから `impl design_alias::M不変データ for 型`)、絶対パス(`impl ::blitz_design::M不変データ for 型`)、パスの中の空白(`impl blitz_design :: M不変データ for 型`)の3つである。conform は、トレイトを書く位置に設計解釈マーカーの名前が識別子として現れる `impl ... for ...` の行のうち、その位置が正確に `マーカー名` または `blitz_design::マーカー名` でない行をすべて違反にし、あわせて `blitz_design` の外のファイルが `blitz_design` を公開の `use`(`pub use`・`pub(crate) use` など)で再公開することを違反にする(`blitz_design` 自身の `lib.rs` が自分のモジュールを再公開するのは対象でない)。マーカーの実装をファイルの中の `mod 名 { ... }` の中へ置くことも conform が違反にする(マーカーの実装を、ファイルのモジュールの直下という1つの置き場へ固定するためである。構文検査は実装の位置のモジュールの直下の定義を採るため、`mod 名 { ... }` の中の実装はファイルの直下の同名の型を指さず、どの型のマーカーかを読み手が取り違える)。試験の `mod tests { ... }` は、その中にマーカーの実装を書かない限り違反にならない。

## 6. 設計関係(Relation)

設計関係とは、2つの設計概念の間に成り立つ、設計上の意味を持つ結び付きのことである。

設計関係の主語と目的語は、設計概念そのものではなく`設計概念への参照`(設計概念の識別子と設計概念の種類の組)である。実装者は、種類を識別子(同一性)へ入れない。理由は2つある。第一に、種類を同一性へ入れると、同じ識別子へ種類の違う概念が現れるという事象が原理的に起こらなくなり、`設計関係グラフ`が検出すべき同一性の衝突の報告が1度も実行されない経路になる。第二に、抽出器は目的語の種類を推測しており(関数の役割の規則は、役割の型引数から出した目的語を無条件に型として積む)、種類を同一性へ入れると、推測で積んだ節点と正しい種類の節点が別の節点へ割れて辺が散る。正本は`crates/blitz_design_verification/src/concept/reference.rs`と`crates/blitz_design_verification/src/concept.rs`の冒頭のコメントである。

本節は、第1実験として次の最小語彙6語を定める。各関係は、抽出元のRustの構文から機械的に抽出する。

抽出器の全規則は、`blitz_design`と`blitz_esca`の本番のソースを同じ対象範囲とする。抽出器は各クレートの`src/lib.rs`と`src/main.rs`からモジュール宣言を辿り、参照されないファイルと`#[cfg(test)]`の項目・子孫モジュールを除く。試験専用のエンティティは、本番の対象集合を非空にしない。抽出器は`cfg(not(test))`を本番として受理し、その他の条件・辿れないモジュール・同一行の複数項目など除外の境界を判断できない構文を欠落として報告する。範囲外のクレートの定義やマーカー実装は抽出しない。範囲内から参照する外部型のうち、標準の`Result`への正本の包括実装だけは既存の特例であり、解決できない外部型の同一性は未解決のまま残す。

設計関係グラフは、各端点と識別子・種類が一致する節点の存在を組み立て時に確かめる。グラフは一致しない端点を報告し、その辺を証拠や経路に使わない。構造の検証器は、この欠落があるとき、関係の不在から証明済み・反証済みを導かない。量化は参照全体で重複を畳むため、同じ識別子の型とトレイトを別々の対象として残す。

| 関係 | 抽出元のRustの構文 | 抽出の条件 | 例 |
|---|---|---|---|
| `下位型である` | `trait A: B {}` の上位トレイトの宣言 | 適用範囲のクレートのトレイトの宣言 | `trait M状態: M不変データ {}` から `M状態 下位型である M不変データ` |
| `下位型である` | `impl マーカー for 型` の行 | 設計解釈マーカーの実装 | `impl Mコマンド for 旅行者の意図 {}` から `旅行者の意図 下位型である Mコマンド` |
| `保持する` | `struct A { f: B }` のフィールドの型 | 適用範囲のクレートの全 `struct` と `enum` | `struct 旅行者の現在地 { 東: メートル }` から `旅行者の現在地 保持する メートル` |
| `識別する` | `impl Mエンティティ for A { type 識別子 = B; }` | エンティティの識別子の関連型 | `B 識別する A`(識別子が主語である) |
| `消費する` | 関数の役割の型引数の入力側 | `M解釈関数`・`M射影関数`・`M遷移関数` の使用箇所 | `M遷移関数<状態, コマンド, 規則, イベント, 失敗>` から `消費する 状態`・`消費する コマンド` |
| `生成する` | 関数の役割の型引数の出力側 | 同上 | 同じ役割から `生成する イベント`・`生成する 状態`(状態は入力でもあり出力でもあるため、状態の位置は `消費する` と `生成する` の2本を出す)・`生成する 失敗`(`Result` の `Err` はその処理が取りうる明白な出力であり、毎回生成されるとは限らないことは除外の理由にならない。2026-09-22のオーナーの裁定) |
| `参照する` | 関数の役割の型引数の規則側 | 同上 | 同じ役割から `参照する 規則` |
| `消費する` | 役割の定義が固定で持つ入力 | `M解釈関数`・`M射影関数`・`M遷移関数` が型引数によらず常に受け取る固定の入力 | `M遷移関数` の定義が固定で受け取る `遷移パラメータ` から `消費する 遷移パラメータ` |

役割の定義が固定で持つ入力から出す関係は、`関数の役割の型引数`とは別の抽出元の構文`関数の役割が固定で持つ入力`を持つ。この2つを分けるのは、表記の在り処が使用箇所の行にないことである。`遷移パラメータ`は使用箇所の`M遷移関数<状態, コマンド, 規則, イベント, 失敗>`のどこにも文字として現れず、その表記は役割の定義の側(`M遷移関数`が固定で受け取る入力の一覧)に在る。

`消費する`・`生成する`・`参照する` の主語は、役割の値の右辺に包まれている具体の関数のパスである(`const _: M解釈関数<...> = M解釈関数::生成する(キーボード歩行入力::歩行入力を解釈する);` なら `blitz_esca::traveler_input::キーボード歩行入力::歩行入力を解釈する`)。実装者は、役割の値を持つ宣言の名前を主語にしない。その宣言は、その関数が役割の型契約を満たすことをコンパイラに確かめさせる証人であって、処理そのものではないためである。実装者は、右辺の関数のパスを読めない使用箇所(戻り値の型・フィールドの型注釈)から関係を出さず、抽出できなかった行として数える。

実装者は、生の `fn f(a: A) -> B` から `A を消費する`・`B を生成する` を抽出しない。抽出すると、関数の引数と戻り値という言語の形がそのまま設計の意味になり、設計として説明可能かを問う力を失う。

この6語は最終語彙ではなく、実際の設計を記述・検査できるかを確かめるための最小の実験の集合である。実装者は、不足が実測で出た関係だけを足す。実装者は、関係を宣言する専用のトレイトを先に増やさない。既存のRustの構文と設計解釈マーカーと関数の役割から一意に抽出できない関係が現れたときにだけ、実装者は明示の宣言を検討する。

抽出器は検証系の信頼基盤である。抽出が誤った設計関係グラフを作れば、その上で示した命題の成立は意味を持たない。そのため実装者は、抽出の規則1つごとに「このRustの構文からこの関係が出る」を固定する回帰試験を置く。

## 7. ドメインモデルとアプリケーションモデル

ドメインモデルとは、設計概念と設計関係から組んだ、検証の対象になるモデルのことである。

アプリケーションモデルとは、ドメインモデルに、`main` とコンポジションルートが実際に構成した配線と、そこから到達できる処理の経路を加えたモデルのことである。

型として存在することと、完成したアプリケーションでその経路が使われることは別である。最終の判定の対象はアプリケーションモデルである。

2026-09-21時点の実装は設計関係グラフ(層1と層2の前半)までである。アプリケーションモデルの構成は別issueへ切り出す。切り出しの形は「何を作るかは確定しており、どこで実行するかが未確定である」である。

### 7.1 層の置き場

層の置き場は3つに分かれる。

```text
blitz_design(設計解釈マーカー。依存ゼロ)
    ↑
blitz_design_verification(命題・原子命題・検証結果・証拠・反例・検証器の共通語彙の正本。通常依存は blitz_design だけ)
    ↑                                        ↑
  xtask(Rustのソースを読む抽出と構造の検証)   ドメイン側の試験(実物の遷移関数を呼ぶ振る舞いの検証)
```

命題の型を1つのクレートへ置くのは、構造の検証と振る舞いの検証が同じ `命題` の型を語らなければ、構造の原子と振る舞いの原子を1つの連言へ結べないためである。写しを置くと、`cargo xtask conform` 自身が持つ「正本と写しで同じ値を持つべき定数の一致」の検査の精神に反する二重の台帳になる。

`blitz_design_verification` はドメインのクレートも `xtask` も知らない。振る舞いの検証が実物の遷移関数を呼ぶために、ドメインの側が `有限に数え上げられる領域` を実装する。この向きであるため、検証の語彙がドメインを知る必要が無い。

`xtask` がこのクレートへ依存することは、依存の白リストの例外である。理由は台帳(`xtask/src/conform/dependency_whitelist/ledger.rs`)へ書いた。

2026-09-22のオーナー裁定。Issue #174。

## 8. 命題(Proposition)

命題とは、ドメインモデルまたはアプリケーションモデルについて真偽を問う式のことである。

設計関係と命題は別の概念である。設計関係はモデルの中の関係であり、命題はその関係について真偽を問うものである。

命題は次の3種類を持つ。

- **構造の命題**: モデルの静的な形について真偽を問う命題である。例は「すべての `Mコマンド` は `enum` である」「`M状態` を実装する型は `M観測` を実装する型を保持しない」の2件である。
- **振る舞いの命題**: 遷移モデル(第10節)の到達可能な状態と遷移について真偽を問う命題である。例は「到達可能な状態のうち、体力が0の状態から歩行のコマンドを受けても新しい歩行イベントは発生しない」「休止した接触島は、外力が加わらない限り再開しない」の2件である。
- **設計の受理の命題**: 第11節が定める設計の受理条件について真偽を問う命題である。例は「すべてのドメイン概念は、少なくとも1つの設計関係へ参加する」「新しい概念は、既存の概念と区別される設計関係または法則の上の差分を持つ」の2件である。

命題の最小の構文は、原子・否定・連言・選言・含意・全称・存在の7つとする。

実装者は、連言と選言の項の並びを1件以上とし、型で保証する。数学の上では空の連言は真であり空の選言は偽であるが、検証器のAPIが意図せず0件になった要求の集まりを受理してよいことはそれとは別である。0件の連言は要求を1件も見ないまま証明済みになり、0件の選言は否定の下で同じ偽の証明を作る。同じ理由で、実装者は推論規則の前提も1件以上とする。前提が0件の推論規則は、前提を全部証明したという条件が1回も確かめられずに成り立ち、任意の結論を証明済みにできる。

原子命題は次の一覧とする: `設計関係が在る`・`マーカーを持つ`・`設計関係へ1つも参加していない`・`発生する`・`遷移する`・`到達可能である`。

実装者は、6つの設計関係の語を原子命題の6つの選択肢へ展開しない。`設計関係が在る { 種類 }` の1つで足りる。展開すると、関係の語を1つ足すたびに原子命題の選択肢と検証の場合分けが1つずつ増える。

仕様とは、アプリケーションが満たすべき命題の集合のことである。仕様は実行時のデータの種類ではない。実装者は、Rustの型の名前を `仕様` にせず `命題の集合` とする(2026-09-20のオーナー裁定とIssue #171)。

本書は、法則(Law)を2種類に分ける。普遍命題としての法則とは、対象の全部について成り立つと主張する命題のことである。推論規則としての法則とは、前提の命題から結論の命題を導く規則のことである。後者の例は排他の推論規則である。2つの事象が排他であるとき、片方が発生するなら他方は発生しない。これにより、実装者は否定の仕様をコードへ直接埋め込まず、正の仕様と排他の法則から否定の命題を導ける。

## 9. 検証と証拠

検証器とは、1つの命題を受け取り、証明済み・反証済み・未決定のどれかで答える道具のことである。

検証器の一覧と、それぞれが証明する対象は次のとおりである。

- **コンパイラ**: 上位トレイトの実装関係、関連型の存在、関数の役割の型引数の境界を保証する。
- **構文の検査**: `Mコマンド` が `enum` であることのような、構文パターンに対する法則を保証する。
- **設計関係グラフ**: 第6節の設計関係が在ることと無いことを保証する。
- **有限全数**: 有限の遷移モデルの全状態・全遷移を数え上げ、振る舞いの命題を証明する。
- **反例の探索**: 生成した入力の一部を試し、反例が見つかればその命題を反証する。
- **記号実行**: 実行経路を記号のまま辿り、条件を満たす反例または証明を導く。
- **SMT(充足可能性を判定する理論の集まり)**: 記号実行が導いた制約式の充足可能性を判定する。

記号実行とSMTは、作ることは確定しており、どう作るかが未確定である。実装者はこの2つを別issueで設計する。

推論規則が導いた結論の証拠は、検証器が結論を直に示した証拠と別の出自であるため、方式として `推論` を名乗る。実装者は、前提を示した方式のどれか1つを結論の証拠へ引き継がない。引き継ぐと、その結論がその方式で直に示されたものと読める。前提を示した方式の一覧は、証拠の説明の文が前提の並びの順で並べる。

実装者は、`bool` を返す検証器の口を作らない。真偽の2値では、「全対象について成立を示せた」と「この検証器では成立も反例も確定できなかった」が同じ偽へ潰れる。

実装者は、「反例の探索で反例が出なかった」を「証明済み」と呼ばない。有限の対象を全部列挙できたときだけ証明済みとし、生成による一部の探索は「未決定。探索の範囲では反例が無い」とする。

実装者は、空の対象集合の全称を証明済みにしない。論理としては空集合上の全称は真だが、検査器としては誤りである。対象集合が0件のとき検証器は未決定で答える。これはグローバル規約「検査器は解析できなかった入力を黙って対象から外してはならない」(2026-09-05制定)の同型である。

実装者は、定義のモジュールパスを解決できなかった型を、節点から落とさない。落とすと「関係が無い」と読まれ、偽の反証が出る。偽の反証は偽の証明より運用の被害が大きい。実装員が正しいコードを直しに行くためである。未解決の節点に触れた評価は未決定で答える。

実装者は、抽出器が設計関係そのものを組めなかった箇所が在るとき、辺の不在に由来する結末を未決定で答える。対象は、反証済みを答える側の原子命題(`設計関係が在る`・`設計関係の経路が在る`・`マーカーを持つ`)と、証明済みを答える側の原子命題(`設計関係へ1つも参加していない`)の両方である。この2つはどちらも、辺が見つからなかったことだけを根拠にした結末であり、抽出が関係そのものを落としているなら、その不在は信用できないためである。

実装者は、同一性の衝突(同じ識別子へ種類の違う概念が現れたこと)が在るときも、辺の不在に由来する結末を同じく未決定にする。同一性が信用できない状態のまま節点が2つに割れると、辺は割れた両方へ散り、片方の節点だけを見て辺が無いと判定してしまう。信用できない同一性の上で、不在を根拠に証明済みまたは反証済みを答えてはならない。

実装者は、命題が否定の下に置かれているかという状態を、原子の評価へ運ばない。原子の解き手は、結合を解く規則から独立に、その原子命題1つの成立だけを答える。この分離を守らずに否定の状態を原子の評価へ運ぶと、原子の解き手と結合の規則を分けた設計が壊れ、含意の前件・二重否定・量化の入れ子で符号が反転するたびに弱める向きを判定し直す必要が生まれ、その判定に誤りが静かに入る。実装者は、原子の結末が反証済み側か証明済み側かという向きだけを見て弱め、否定・含意・量化の側には手を入れない。

実装(`crates/blitz_design_verification/src/verifier/structural/atom.rs` の `不在に由来する結末を弱める`)は、`関係を落とした抽出の欠落`が在るとき、辺の不在から導いた結末を、未決定の理由の選択肢 `関係を落とした抽出の欠落が在る` へ差し替える。

実装者は、抽出器の保証範囲の外にあるRustの構文を、関係も出さず欠落にも数えない第三の状態へ落とさない。実装者が許す形は2つだけである。そのRustの構文を抽出器が正しく解析するか、解析対象であることは判ったが保証範囲の外であるとして`抽出できなかった行`(`関係を落とした抽出の欠落`の一部)へ倒すかである。あわせて`cargo xtask conform`は、抽出器が受理する正規形のRustの構文をリポジトリ全体へ強制し、保証範囲の外の構文が書けないようにする。正本は`xtask/src/conform/extractable_normal_form.rs`(検査そのもの)と`xtask/src/design_model/extract/out_of_range_syntax.rs`(保証範囲の外の構文の列挙)である。

機械で保証できる法則と、意味の上の法則は次の表のとおり分ける。

| 検証主体 | 対象 |
|---|---|
| 機械で保証できる法則 | 上位トレイトの関係(コンパイラ)・`Mコマンド` が `enum` であること(構文の検査)・`M不変データ` を実装する型が受け手と引数に自分の型への可変参照を持たないこと(構文の検査)・設計関係が在ることと無いこと(設計関係グラフ)・有限のモデルの全遷移についての振る舞いの命題(有限全数) |
| 意味の上の法則(機械が判定しないもの) | `M結果` が単なる状態の列挙ではないこと・`M観測` が正本ではないこと・新しい概念の粒度が妥当であること・名前が「これは何?」に答えていること |

### 9.1 網羅性と証拠の非対称

数え上げの網羅性とは、検証器が対象を全部並べられたか、標本に限るかの区別のことである。

網羅していない領域では、証拠の出方が命題の形によって非対称である。

| 命題の形 | 網羅して全件を数え上げたとき | 標本に限るとき |
|---|---|---|
| 全称が全件で成立 | 証明済み | 未決定(探索の範囲では反例が無い) |
| 全称に反例が1件 | 反証済み | 反証済み |
| 存在に証人が1件 | 証明済み | 証明済み |
| 存在に証人が0件 | 反証済み | 未決定 |

反例と存在の証人は見た範囲から得られるが、全称の成立と存在の不在は見ていない範囲に依る。

構造の検証器は、関係の抽出に欠落が在るとき、グラフから列挙した4種類の対象集合を全件と呼ばない。端点の欠けた関係をグラフが除くと、その関係だけを持つ主語も対象集合から消えるためである。検証器は、残った対象の反例と証人をそのまま答え、全件の成立または証人の不在だけを未決定にする。

この非対称が `検証結果` の3値が在る理由そのものである。真偽の2値だと4行目の未決定が偽へ潰れ、「見ていない範囲に証人が居ない」と断定することになる。

連続量を含む領域は標本に限る。有限個の標本を証明済みと偽装しない。例として、`blitz_esca` の `旅行者の意図::歩く { 方向: 歩行方向 }` は `歩行方向` が東の比率と北の比率を持つ単精度2成分の連続量であるため、軸に沿う4方向の標本に限られ、その領域についての全称の命題は未決定で答える。

## 10. 遷移モデルと到達可能性

遷移モデルとは、前状態・入力・適用した規則・後状態・生成イベント・失敗を1件として持つ、遷移の集まりのことである。

実装者は、「Rustの型として組める状態」と「実際に到達する状態」を区別する。振る舞いの命題の対象は到達可能な状態と遷移である。

失敗した遷移はイベントを1件も生成しない。3.5.9節の遷移失敗結果と同じ法則である。

代表ケースは実在の `blitz_esca` の旅行者の移動である。命題は「移動可能範囲の端で範囲外へ歩くと `旅行者の出来事::障害物に遮られた` が生じる」であり、ドメイン側の試験が実物の `旅行者の現在地::歩行を遷移する` を呼んで検証する。

検証の側は遷移の意味を1行も書き写さない。書き写せば Issue #173 が禁じた「検証入口がゲームロジックを再実装しない」の違反になる。実物を呼ぶ形にすることで、再実装が原理的に起こらない。

小さな人工のモデルは、検証器自身の単体試験のfixtureとしてだけ許す。実ゲームの仕様の代表ケースにも、受理の根拠の代用品にもしない。2026-09-21に `xtask` へ置いた有限の対戦進行の題材は、`blitz_design_verification` の `#[cfg(test)]` の中のfixtureへ移した。

2026-09-22のオーナー裁定。Issue #174。

### 10.1 状態の同一性と状態の名指し

状態の同一性とは、探索が2つの状態を同じ1件として扱ってよいかを決める判断のことである。

実装者は、状態の同一性と状態の名指しを別の口に分ける。名指しは人が読む表示と命題が名指す先であり、位置をマスの番号へ丸めるように粗くしてよい。同一性は探索の済みの集合の鍵であり、異なる状態を同じ値へ写してはならない。

実装者は、名指しを同一性に使わない。使うと、表示のために粗くした名前がそのまま済みの集合の鍵になり、別の状態が黙って同じ1件として捨てられる。捨てた先を1件も辿らないまま、その探索が「全件を数え上げた」を名乗れば、未探索の状態を残したまま有限全数で証明済みが作れる。

領域の契約は、同一性が単射である(異なる状態が同じ同一性へ写らない)ことを要求しない。要求しても、契約を実装する側がそれを守るとは限らないためである。かわりに探索の側が検出する。探索は同一性ごとに代表の状態を控え、すでに代表が居る同一性へ代表と等しくない状態が写ったとき、その事実を数え上げの網羅性へ残す。その網羅性は `異なる状態を同じ同一性へ畳んだ` であり、`全件を数え上げた` ではない。

この形が守るのは、嘘をつける口を残したまま、嘘をついた結果が全件を名乗れないという1点である。実装者は、契約の文言で単射を求めるかわりに、破れたときに証明済みが出ないことを機械で保証する。

連続量を持つ状態の同一性は、領域の側が型で選ぶ。`blitz_esca` の `旅行者の現在地` は単精度を2つ持ち `Eq` も `Hash` も導出できないため、その領域は単精度のビットの並びへ写した `現在地のビット表現` を同一性に選ぶ。ビットの並びは丸めないため、同じマスの名前を持つ2つの現在地も別の状態として辿る。

失敗した遷移を表す節点の名前は、人が読む説明の文だけで作らない。同じ文面で失敗する別の遷移が1つの節点へ畳まれ、検証がその2件を同じ失敗として読むためである。探索は、遷移1件を名指す識別子を名前へ入れ、探索の側の名前の空間へ置く。

2026-09-22。PR #177 のオーナーのレビューのBlocker 2。

### 10.2 名指しの衝突の検出と網羅性の優先順位

識別子は識別しなければならない。実装者は、領域が答える名指し(`状態を名指す`・`コマンドを名指す`・`出来事を名指す`)が単射であることを要求せず、かわりに探索の側でその破れを検出する。名指しは人が読む粗い表記であり、探索が同じ1件として扱ってよいかを決める識別子とは別に持つ。

探索は、名指しの台帳(`crates/blitz_design_verification/src/domain/exploration/naming_ledger.rs`)を通して名指しを頼み、互いに等しくない2つの値が同じ名指しへ写った事実をそこで検出する。名指しの台帳を経ずに領域へ直に名指しを頼む経路が1つでも在ると、その経路の畳みだけが数えられない。

数え上げの網羅性の優先順位は、同一性の畳み・名指しの畳み・上限で打ち切った・連続量の標本・全件の順である。実装者は、同一性の畳みを最も優先する。そこでは辿らなかった状態が在ることを、件数からも上限からも読めないためである。実装者は、名指しの畳みを次に優先する。そこでは辿りが足りていても、モデルの上で互いに等しくない2つの値が1件の節点へ重なり、命題の層がその2つを区別できないためである。実装者は、上限で打ち切ったことを連続量の標本より優先する。打ち切った先を1件も見ていないためである。正本は`crates/blitz_design_verification/src/domain/exploration/coverage_basis.rs`と`crates/blitz_design_verification/src/coverage.rs`である。

### 10.3 初期状態の数え上げ

## 11. 設計の受理

設計の受理とは、コードが動くことに加えて、その設計が説明可能であることを求める受理条件のことである。

受理条件は次の4種類を持つ。

- **肯定的な欲望**: システムが達成すべき機能や性質を求める欲望のことである。例は「遷移関数は与えられた状態とコマンドから次の状態を計算する」である。
- **否定的な欲望**: システムが陥ってはならない状態を避けることを求める欲望のことである。例は「休止した接触島は、外力が加わらない限り再開しない」である。
- **構造的な欲望**: システムの構造そのものが持つべき形を求める欲望のことである。例は「すべての `Mコマンド` は `enum` である」である。
- **認知的な欲望**: 設計を読む人間がその意味を理解できることを求める欲望のことである。例は「新しいドメイン概念の名前は、それが何であるかを単独で答える」である。

新しいドメイン概念について、実装者は次の6つの問いに答えられる状態を受理条件とする。それは何か。設計解釈マーカーと関数の役割は何か。どの設計関係に参加するか。どの法則と命題に参加するか。既存のどの概念と何を区別するために存在するか。なぜその粒度なのか。

機械化できる部分は命題として書く。「すべてのドメイン概念は、少なくとも1つの設計関係へ参加する」「新しい概念は、既存の概念と区別される設計関係または法則の上の差分を持つ」の2件である。

実装者は、日本語の識別子であることを可読性の達成とみなさない。
