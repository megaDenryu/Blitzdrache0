# チャンクストリーミング

この文書は、OW2で大域世界の必要部分だけを読み込み、不要部分を安全に解除する契約を管理する。実装と常に一致させて維持する。

## 所有境界

blitz_engineはプレイヤー位置から必要チャンク集合と優先順を決める。後続段でディスク読込とデコード済みデータの準備も所有する。blitz_renderはGPU転送とGPU使用完了後の資源解放だけを所有し、どのチャンクが必要かを判断しない。blitz_appは位置、予算、フレーム境界を配線するだけである。

## チャンク格子

世界はXZ平面を正方形へ分割する。一辺長は0より大きい有限の大域メートルであり、プレイヤーのXとZを一辺長で割って床を取ったi32整数2成分をチャンク座標とする。負座標をゼロ方向へ丸めないため、X=-0.1mは一辺100mならX=-1のチャンクに属する。

チャンク座標そのものがチャンクの識別子であり、座標から独立した識別番号は存在しない。描画対象の所有チャンクも同じ座標で表すため、シーン内の番号と世界の格子座標が別の識別空間へ分裂しない。

u64はこの識別子の永続化表現であり、実行時形式の読み書きだけがこの表現を使う。Xの32ビット表現を上位、Zの32ビット表現を下位へ格納し、座標とu64の変換は可逆である。負値を含む異なる座標は異なるu64になるため、識別はファイルパスや実行順に依存しない。

## チャンク目録

チャンク目録はチャンク座標からアセットIDを引く対応表であり、同時にその世界に存在するチャンクの集合を表す。ストリーミングは目録で座標をアセットIDへ解決し、カタログでアセットIDを生成物のパスへ解決する。この2段のうち前段だけが世界の形を知り、後段はアセットの所在だけを知る。

目録に無い座標は世界の端であってエラーではないため、引いた結果は値なしになりうる。必要集合は世界の外側の座標も含むため、不在は正常系である。1つの座標へ2つのアセットを登録する要求は、どちらを読むかが登録順に依存するため型付きエラーとして拒否する。

目録は種別番号3の版付き実行時アセットとして永続化する。内容は項目数と、チャンク座標順に整列した項目一覧である。各項目は座標のu64表現と長さ付きUTF-8のアセットIDを持つ（参照: `_doc/設計/アセット実行時形式.md`「チャンク目録内容の版1」）。座標の永続化表現はu64だけであり、生のi32を2つ書く形は持たない。

## 検証用チャンク世界

固定経路の移動でチャンクの読込順と解除順を再現するために、5×5の25チャンクからなる検証用世界を持つ。XとZはどちらも-2から2であり、負座標を含めることで符号の扱いを合成データではなく実データで検証する。一辺長は100メートルである。

各チャンクは独立したglTFファイル1つに対応し、チャンク中心（Xが`x * 100 + 50`、Zが`z * 100 + 50`、Yが0）へ板を1枚置く。ソース読込はノードの変換を捨てるため、チャンク中心への配置は頂点位置へ焼き込む。25チャンクは1つの共有バッファファイルを区間で分け合う。絵の内容は要件ではないため、マテリアルを持たず既定テクスチャで描かれる。

ソースは`cargo xtask gen-source-assets`が`assets/chunk_world/`へ決定的に生成し、`cargo xtask compile-assets`が25個の実行時シーンと版付きチャンク目録へ変換する。座標はソースの目録が宣言した値だけを根拠にし、ファイル名から逆算しない。ファイル名規約への暗黙の依存を作らないためである。

## 必要集合と優先順

先読み半径はu8のチェビシェフ距離で表す。半径0は所属チャンクだけ、半径1は中心と周囲8チャンクである。必要集合は中心を最初に置き、距離1、2の外周へ広げる。同じ外周ではZ差、次にX差の昇順とし、同じ入力から同じ読込要求順を得る。

一辺長の不正、非有限な大域位置、i32範囲を超える座標と先読み範囲は`チャンク格子エラー`として返す。必要集合計算はファイル、スレッド、GPUへ触れない。

## 状態台帳

チャンク台帳は必要性と処理段階をチャンク座標ごとに一意管理する。段階列は`読込待ち → 読込中 → 準備済み → GPU転送中 → フレーム反映待ち → 常駐 → 解除待ち`である。呼出し側が段階を飛ばすと型付きエラーになる。

新しい必要集合は、新規チャンクの読込要求を入力の中心優先順で返す。不要になった読込待ちと準備済みのCPUデータは即時削除し、読込中なら完了時にGPUへ送らず破棄する。GPU転送中なら転送完了後、フレーム反映待ちまたは常駐なら直ちに解除待ちへ進める。解除はGPU使用完了が通知された後にだけ台帳から削除する。

解除完了前に再び必要になった場合は新しく読み直さない。常駐由来なら常駐へ、まだシーンへ反映していないGPU資源ならフレーム反映待ちへ戻す。

必要なままでも、使用量が上限を超えたときは常駐から解除待ちへ進める(「メモリ予算と縮退」節の退避)。この遷移では再要求時の復帰先を残さない。退避したチャンクは必要集合に入ったままであるため、復帰先を残すと次のフレームで常駐へ戻り、退避が打ち消されるからである。

## フレームループへの配線

ストリーミング調停はチャンク格子、チャンク目録、ストリーミング予算、チャンク台帳、チャンク読込器を内部に持ち、プレイヤーの大域位置とカタログを受け取って1フレーム分を進める。5つを個別に配線しないのは、台帳の状態が格子・目録・予算を通った結果でなければならないという不変条件を共有するためである。個別に持たせると、この手続きを経ずに台帳だけを更新する経路が開く。また可変性の寿命が分かれており、格子・目録・予算は生成後不変で、台帳と読込器だけが可変である。

1フレームの手続きは、必要集合の計算、目録による座標からアセットIDへの解決、カタログの容量メタデータからの見積量算出、予算による縮退、台帳への反映、読込器への要求投入、不要になったCPUデータの破棄、完了の回収の順である。目録に無い座標は世界の端であるため候補から落とし、読込要求を出さない。目録が解決したアセットIDがカタログに無い場合は、世界の形とアセットの所在が食い違う不整合として型付きエラーにする。読込要求キューが満杯なら以降の投入を打ち切り、次フレームで再試行する。

予算へ渡す候補は台帳にまだ無い新規分だけである。既存記録が持つ資源は台帳が導出する現在使用量に既に入っており、候補にも入れると同じ資源を二度数えて必要集合が不当に縮む。

調停が返す進行は、そのフレームで読込を開始した座標、準備完了した座標、CPUデータを捨てた座標、GPU資源の解除待ちへ移した座標、台帳の登録数、導出した使用量、予算判定を持つ。いずれもそのフレームで観測できた事実だけである。

準備済みチャンクのCPUデータは調停が保持する。台帳は準備済みのRAMを保持量として数えるため、保持しないと数えている量と実際に持っている量が食い違う。保持する座標の集合は台帳が準備済みとしている座標の集合と常に一致させ、台帳が準備済みから外した記録は同じフレームのうちに捨てる。この保管と台帳の記録が「GPU転送と描画束」の入力になる。

blitz_appはCLIで有効化されたときだけ調停を組み立て、カメラ更新の直後にプレイヤーの大域位置を渡す。既定の位置はカメラの視点位置であり、必要集合の中心は確定した視点位置から決めるため、カメラより先に呼んではならない。`--streaming-route`を指定したときは位置が固定経路から決まり、カメラの姿勢に依存しなくなる（「固定経路の自動移動」節）。既定で有効にしないのは、既存のスモークとベンチがチャンク世界を使わず、既定で有効にすると性能の時系列とスモークの判定条件が変わるためである。有効化は`--streaming`、上限の指定は`--streaming-ram-limit`と`--streaming-vram-limit`、読込と解除の順の出力は`--report-streaming`、転送量と処理時間の出力は`--report-streaming-summary`である。順序と要約の出力を専用フラグにするのは、フレーム時間の時系列を変える既存の計測フラグへ相乗りさせないためである。

検証用世界では1チャンクの見積が216バイト、読込完了後の実測が369バイトであり、実測が見積の約1.71倍になる。見積はメッシュとテクスチャの生バイト数だけを数え、実測は版付きファイル全体の長さだからである。このため予算が縮退を起こす上限では、見積を根拠に収容した集合が読込完了後に上限を超えうる。超えたフレームの扱いは「メモリ予算と縮退」節の退避である。既定のRAM上限を1チャンクの実測以上かつ2チャンクの見積未満に置くのは、1件だけを収容して外周を縮退させる状態が安定して続き、縮退の観測が退避と混ざらないためである。見積と実測を近づけるかどうかは、地形1チャンクの物量が見えるOW3で決める。

## GPU転送と描画束

調停は1フレームを進める手続きとは別に、GPU層との受け渡しを3つの手続きで持つ。第1はGPU転送のためのシーンデータの取り出しであり、保管からの削除と台帳の`GPU転送中`への前進を同時に行う。片方だけを行うと、台帳が数える量と実際に保持している量が食い違うためである。準備済みでない座標には値なしを返す。第2は転送完了の報告であり、台帳を`フレーム反映待ち`を経て`常駐`まで進める。第3は資源解除の報告であり、`解除待ち`の記録を台帳から削除する。台帳に無い座標の解除報告はエラーにせず「台帳に無かった」を返す。リセットで台帳を空にした後に、リセット前に予約した実破棄が届く正常な後始末だからである。

解除の報告が指すのは実破棄の完了であって、解除の予約ではない。レンダラーの束の解除は破棄待ちへの移動であり、GPU資源は通常フレームインフライト数ぶんのフレーム、提示停止中はさらに長く残る。予約の時点で報告すると、台帳が数えるVRAMが実確保より先に減り、空いた分へ新しい束を収容して実VRAMが上限を超える。そこでレンダラーは実際に破棄し終えた束のIDを貯めて毎フレーム呼出し側へ引き渡し、blitz_appはそのIDから座標を復元して解除を報告する。台帳の`解除待ち`は実破棄の報告までVRAMを数え続けるため、解除予約は予算上の空きにならない。

段階の順序をblitz_appでなく調停が持つのは、blitz_appが配線だけを行い判断を持たないためである。順序を配線側に置くと、段階を飛ばす経路が調停の外に開く。

転送完了の報告は、呼出し側が1フレーム進めた直後に、そのフレームの準備完了一覧へ挙がった座標を報告することを前提にする。必要性は1フレーム進める手続きの中でしか変わらないため、この前提のもとで転送完了は常に`フレーム反映待ち`になる。前提が破れて不要へ変わっていた場合は、段階を無言で進めず型付きエラーにする。

blitz_appは1フレーム進めた結果の準備完了一覧について、シーンデータを取り出して描画シーン素材へ変換し、レンダラーへ描画束を追加してから転送完了を報告する。解除待ち一覧については描画束の解除を予約するだけにとどめ、解除の報告はレンダラーから実破棄済みの束IDを引き取った時点で行う。描画対象数の指定は渡さない。複製配置はベンチ専用の機能であり、チャンクの実体を歪めるためである。

描画束IDは座標から純粋に決め、座標と束IDの対応表を別に持たない。対応表を持つと同じ識別が2箇所で管理される。起動時のシーンは束ID0を占め続ける。レンダラーはシャドウ描画入力が1件以上であることを不変条件にしており、チャンクが1つも常駐しない期間にも描画対象が要るためである。したがって座標の永続化番号をそのまま束IDにはできない。原点チャンクの番号が0であり衝突するからである。XとZの符号ビットを反転して原点を識別空間の中央へ移すと、0へ写る座標は世界の隅である(x=i32::MIN, z=i32::MIN)だけになる。この座標だけを束IDへ変換できない座標として型付きエラーで拒否する。

## ホットリロードとの併用

アセットのホットリロードはレンダラーのシーンを差し替える。差し替えは描画資源を作り直すため、チャンクの描画束が全部消える。台帳をそのまま残すと、台帳が常駐としている座標に対応する描画束が存在しない状態になる。そこでblitz_appは、シーン差し替えが成功した直後に調停をリセットする。差し替えに失敗したときはリセットしない。従来の描画束がそのまま残っており、台帳と乖離しないためである。

リセットは台帳と準備済みCPUデータの保管を空にし、次のフレームから読み直させる。RAM実測の記憶と運んだ量の累計は残す。前者は読み直したときの見積精度に使い、後者は過ぎ去った事象の合計だからである。読込器も残す。ワーカースレッドを起動し直す理由がなく、進行中の読込は次の受信で処理できるためである。

リセット前に投入した読込の完了はリセット後に届く。同じ座標を読み直していれば、1つの座標へ2件の完了が届く。台帳がその座標を読込中としていない完了は、異常ではなくリセットの正常な後始末であるため、CPUデータ破棄として数えて破棄一覧へ載せる。段階の飛ばしとして型付きエラーにすると、ホットリロードのたびにストリーミングが停止する。

何を捨てて何を残すかの規則は調停のリセットが持ち、blitz_appは呼び出しだけを行う。この規則を配線側に置くと、台帳の不変条件を調停の外から壊す経路が開く。

## 固定経路の自動移動

読込順と解除順が実行のたびに再現するかを判定するには、プレイヤー位置が実行ごとに同じ列でなければならない。固定経路は始点と終点のあいだを一定速度で往復する直線であり、位置をフレーム番号だけから決める。実時間へ追従しないのはアニメーション時刻が固定歩進である理由と同じで、実行速度が変わっても同じフレーム番号から同じ位置を得るためである。

経路はXが-150メートルからXが250メートル、Zは0である。検証用世界はXとZがどちらも-2から2の5×5であり、一辺100メートルであるからXは-200から300メートルを占める。両端のチャンクの内側で折り返すため、往復のたびに世界の端で必要集合が縮み、読込と解除の両方が起きる。1フレームの移動量は5メートルであり、一辺100メートルの境界を20フレームに1回またぐ。これより速いと1件ずつしか収容しない予算では読込が境界の移動に追いつかず、遅いと同じ回数の入れ替わりを見るのに長い実行が要る。

経路は`--streaming-route`を指定したときだけ有効になり、指定が無ければプレイヤー位置は従来どおりカメラの視点位置である。位置の出どころは真偽値でなく選択肢の型で持つ。位置の出どころが変わると読込順の再現性が変わるためである。

## 計測の記録

DoDが求める観測は、メインスレッドのp99と転送量である。どちらも既存の計測フラグへ相乗りさせず、`--report-streaming-summary`で終了時にまとめて出す。毎フレームの順序を出す`--report-streaming`と別の指定にするのは、順序出力が事象のあるフレームごとに複数行を出し、長時間実行では標準出力量が桁違いになるためである。要約には見送りフレーム数(提示へ到達しなかったフレームの累計)も含める。提示停止中は破棄待ちが滞留しフレームループが空転するため、この値が大きい実行のRAM・VRAM推移は提示が続いた実行と比較できない(参照: `_doc/計測/OW2第10段_2026-07-26.md`)。

転送量は、起動から現在までにストリーミングが運んだ量の累計である。ディスクからCPUへ読んだ件数とバイト数、CPUからGPUへ載せた件数とバイト数、GPU資源を解除した件数の5つを持つ。読込バイト数は読込器が返した実測であり、GPU転送バイト数はVRAMの見積である。VRAMに実測が無いことは「見積量とRAM・VRAMの区別」節のとおりである。読込件数は必要でなくなって捨てた分も数える。ディスクを読んだ事実は捨てたかどうかで変わらないためである。この累計は状態から導出できない過ぎ去った事象の合計であるため、現在使用量と違って調停が値として保持する。加算は飽和も折り返しもせず、u64を超えたら型付きエラーにする。

メインスレッドの時間は2つの量を別々に記録する。1つはCPU側フレーム開始間隔であり、既存の`--report-frame-times`がそのまま使える。もう1つはストリーミングがメインスレッドを占めた時間であり、調停の1フレーム前進と描画束の追加解除を合わせた区間を測る。2つを分けるのは、フレーム間隔がFIFO提示待ちを含む合計であり、ストリーミングの寄与だけを取り出せないためである。区間の集計は先頭120フレームを除き、既存のフレーム間隔と同じ除外規則にそろえる。

`cargo xtask streaming-bench`は2つの条件を順に実行する。条件Aは縮退が起きない上限を置いた反復であり、読込と解除を繰り返してもRAMとVRAMがフレーム数に比例して増えないことを見る。条件Bは縮退が起きる上限で2回実行し、外周が落ちる順序が一致するかを突き合わせる。1つの条件では両方を確かめられない。縮退している状態では必要集合が常に縮んでおり増加の有無を見にくく、縮退しない状態では退避順序が観測できないためである。

順序の突き合わせはフレーム番号を含む行を除き、見出しごとの列で行う。読込完了のフレームはディスクの応答時間で前後するため、種類をまたいで混ぜた1本の列は順序の再現とは別の量になるからである。

条件Bの合否はCPUデータ破棄と解除待ちの列で決め、読込開始と準備完了の列は表示するが合否に使わない。縮退が起きる上限では読込が1件ずつ直列になり、次に読むチャンクが前の読込の完了時刻に依存する。プレイヤー位置はフレーム番号で決まるがディスクの応答時間は決まらないため、両者の相対関係が実行ごとに変わりうる。予算が拘束しない上限では読込順まで完全に一致することを実測で確かめてあり(`_doc/計測/OW2第10段_2026-07-26.md`)、読込順の非決定性は縮退による直列化に固有である。

## 段階導入

第1段は必要集合の純粋計算、第2段は集合差分と非同期処理の状態台帳までを実装した。第3段は版付きカタログで解決した生成物を専用ワーカースレッドから読み、形式検査済みシーン、読込バイト数、所要時間を完了通知として返す経路を実装した。第4段は予算計算と縮退結果までを実装した。第5段はシーン内番号として別に存在していた識別子を廃止し、識別をチャンク座標へ一本化してu64を永続化境界の表現へ限定した。第6段は座標をアセットIDへ解決する所有者としてチャンク目録を置き、その永続化形式と、25チャンクの検証用世界の実データを実装した。第7段は容量メタデータからチャンクごとの見積量を作り、台帳が状態から現在使用量を導出する経路を実装した。第8段は格子・目録・予算・台帳・読込器をストリーミング調停へ束ね、blitz_appのフレームループへ配線してRAM・VRAM上限の暫定値を置いた。第9段は描画束の追加と解除をレンダラーの公開APIとして置き、調停へGPU受け渡しの3手続きを足して、読み込んだチャンクが描画束として載り常駐まで進む経路を接続した。VRAM実測への置き換えは、常駐チャンクのGPU資源量をレンダラーが返す経路と同時に行う。第10段は固定経路と転送量の累計を足し、2つの条件でDoDを計測する`cargo xtask streaming-bench`を登録した。実測は `_doc/計測/OW2第10段_2026-07-26.md` にある。第9c段は第10段の計測のあとに戻り、上限を超えたフレームの退避とRAM実測の記憶、およびホットリロード併用時のリセットを足して、読込から解除までの経路が回復不能な停止を持たないようにした。

読込要求キューは64件、シーン実体を保持する完了キューは4件の有界キューであり、投入はメインスレッドを待たせない。要求が満杯なら型付きエラーを返し、呼出し側が次回再試行する。完了が未回収ならワーカー側で背圧を掛け、RAMの無制限な増加を防ぐ。ワーカーは1本で中心優先の投入順を保つ。完了回収も待機せず、未完了なら値なしを返す。要求投入が成功してから台帳を読込中へ進め、完了結果を受け取ってから準備完了へ進める。

ワーカーはglTFや画像を読まず、OW1の版付き実行時シーンだけを復元する。破損生成物は完了通知内の`実行時シーン読込エラー`になる。読込バイト数と所要時間は後続の固定経路計測で集計する。

## メモリ予算と縮退

RAMとVRAMはu64のバイト数で別々に上限と現在使用量を持つ。現在使用量は常駐中と解除待ちの既存資源を含み、候補一覧はこれから追加する新規読込だけを中心優先順で渡す。各候補には読込前の見積量を付け、先頭から両予算へ収まる範囲だけを収容する。途中の候補が収まらなければ、それ以降に小さい候補があっても飛び越さず外周側をすべて除外する。これにより穴のない近傍集合と決定的な退避順を維持する。

結果は全件収容、または最初の除外チャンクとRAM超過・VRAM超過を持つ型付き縮退である。加算オーバーフローも該当資源の超過として扱う。現在使用量が既に上限を超えている場合は入力状態のエラーとして縮退と区別する。収容一覧は見積量を保った候補のまま返す。収容した候補を台帳へ登録するときに見積量が必要であり、呼出し側が同じ見積を二度引くことを避けるためである。

### 上限を超えたフレームの退避

読込前の見積は実測より小さいため、見積で収容を決めた集合が読込完了後に上限を超えることがある。常駐前のチャンクはVRAMを数えないため、複数フレームにまたがって決めた収容の合計が常駐へ揃った時点でVRAM上限を超えることもある。どちらも予算にとっては「現在使用量が既に上限を超えている」入力であり、そのままエラーとして返すと以降のフレームでも同じ失敗を繰り返してストリーミングが止まる。そこで調停は、現在使用量が上限を超えているフレームでは予算を適用せず、退避へ倒す。

退避のフレームは新規収容を行わない。既に台帳にある座標だけを必要のまま反映し、反映が終わってから常駐チャンクを解除待ちへ進める。反映より先に退避すると、必要のまま残る座標が解除待ちから常駐へ復帰して退避が打ち消される。

退避する順は中心からのチェビシェフ距離の降順であり、同距離は座標の永続化番号の降順である。番号は座標ごとに一意であるため、走査順が不定な連想配列からでも同じ入力から同じ順を得る。距離0のチャンク、すなわちプレイヤーの所属チャンクは退避しない。足元の描画を消せないためである。

打ち切りは、退避した座標の解除が済んだとみなした見込み量で判定する。解除待ちの記録は解除が報告されるまでVRAMを数え続けるため、台帳の現在値では退避の効果が見えないからである。上限を超えている次元の使用量を減らせない記録は選ばない。常駐はRAMを数えないため、RAMだけが超過しているときは退避対象が無いまま超過が続く。これはエラーでなく、退避件数0と「退避後も超過」を持つ判定として報告する。

退避した座標は不要化による解除と同じ解除待ち一覧へ載せ、blitz_appは同じ後始末を行う。解除の経路を1本に保ち、呼出し側が不要化と退避を見分けずに済むようにするためである。

### RAM実測の記憶

退避したチャンクが再び収容されて同じ超過を繰り返さないよう、調停はチャンク座標ごとのRAM実測バイト数を覚える。予算候補の見積は、実測を覚えている座標では実測へ置き換える。覚えないと、解除した直後に見積で収まると判定して読み直し、実測でまた超過する往復が続く。

記憶は台帳から記録が消えても残す。再訪したときの見積精度がこの記憶の目的だからである。VRAMは実測を持たないため常に見積である。件数の上限は設けない。検証用世界は25チャンクであり、上限機構は必要になってから作る。

## 見積量とRAM・VRAMの区別

読込前の見積量はカタログの容量メタデータ、すなわち頂点数、インデックス数、展開済みテクスチャの合計バイト数から作る。1頂点と1インデックスのバイト長は実行時形式の版1が定める値をそのまま使い、見積側で同じ数字を複製しない。複製すると形式を変えたときに見積だけが古い数字のまま残るためである。件数と要素長の乗算、および各部の加算はオーバーフローを型付き失敗として返し、飽和や折り返しを行わない。

RAMは読込完了からGPU転送完了までCPU側がシーンデータを保持する量である。VRAMは常駐中のGPU資源、すなわち頂点バッファ・インデックスバッファ・テクスチャの量である。GPU転送が済んだCPUデータは破棄するため、同じ内容をRAMとVRAMで同時に数えることはない。現時点では両者の計算式が同じ値を返すが、1つの量へ統合しない。理由は2つある。ライフサイクルが違うため状態ごとの使用量が別々に変化することと、将来GPU側のアラインメント要件や圧縮テクスチャで値が分かれることである。

## 現在使用量の導出

台帳は見積量をチャンク記録に保持し、現在使用量を別フィールドとして持たない。状態から毎回導出する。保管を二重に持つと状態遷移のたびに両方を更新する義務が生まれ、片方だけ更新した状態を型が許してしまうためである。状態ごとの値は次のとおりである。

| 状態 | RAM | VRAM |
|---|---|---|
| 読込待ち | 0 | 0 |
| 読込中 | 見積 | 0 |
| 準備済み | 実測 | 0 |
| GPU転送中 | 実測 | 見積 |
| フレーム反映待ち | 0 | 見積 |
| 常駐 | 0 | 見積 |
| 解除待ち | 0 | 見積 |

予算へ渡す候補は読込前の見積を持ち、読込が完了した時点で読込器が返した読込バイト数がRAMの実測になる。置き換えは準備完了の反映1箇所だけで行い、以降の導出は実測を根拠にする。再要求で既存記録を必要へ戻すときに候補の見積で上書きしないのは、実測を失うためである。VRAMは常に見積であり、実測への置き換えは実GPU転送の接続と同時に行う。全チャンクの合算がu64を超える場合は型付き失敗として返す。
