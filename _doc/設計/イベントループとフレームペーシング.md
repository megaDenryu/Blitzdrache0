# イベントループとフレームペーシング

「1フレームを正確に16.6msにする」を誰がどうやって実現するか、およびwinit所有ループ（パターンA）から自前所有ループ（パターンB）への移行手順。

## 前提: 16.6msを作っているのは誰か

フレーム時間の制御に関わる層は3つある。上2つを混同しないことが重要。

```
OSイベントループ層   … winitが担当。マウス・キーボード・リサイズ等のOSイベントを配送する
フレームループ層     … 「1フレーム分の処理をいつ始めるか」を決める。所有権の論点はここ
GPU提示層           … Vulkanスワップチェーンの提示モード。実は16.6msの主たる供給源はここ
```

### 提示モード（present mode）がペーシングの主役

Vulkanでは `vkQueuePresentKHR` で完成した絵をスワップチェーンに提示する。
このとき提示モードによってブロック挙動が変わり、これがフレーム時間を実質的に決める。

| 提示モード | 挙動 | フレーム時間 |
|---|---|---|
| FIFO | ディスプレイのリフレッシュに同期して待つ（vsync）。全GPUで対応保証 | 60Hzモニタでは16.6msが基準。OS合成や提示期限超過で倍周期になり得る |
| MAILBOX | vsyncだが最新フレームだけ表示（低遅延、描き捨てあり） | リフレッシュ同期 |
| IMMEDIATE | 同期なしで即表示（ティアリング発生） | 無制限。ペーシングは自前責務になる |

**FIFOを使う限り、ループ側で時間制御を書かなくても提示待ちがフレームループの基準周期を作る。**
ただし、これはCPU側の全フレーム開始間隔が必ず16.6msに揃うという保証ではない。Windowsのデスクトップ合成、ドライバーのキュー制御、提示期限の超過により、次の更新まで待って約33msになる場合がある。
これが「ループ所有権を気にする場面は少ない」の正確な意味であり、逆に言えば以下の場面ではループ側の制御が必要になる。

- IMMEDIATEで動かしつつ自前フレームリミッタで任意のレート（例: 240fps上限）を作る
- 入力遅延の短縮（late-latch: フレーム開始を意図的に遅らせ、提示直前に入力を採取する）
- 固定タイムステップのシミュレーションを描画レートから分離する
- エンジンを別ホスト（エディタプロセス、テストハーネス）のループの1ステップとして駆動する
- ウィンドウなし実行（ウィンドウなしでシミュレーションのみ回す）

## パターンA: winit所有ループ（現行方針）

winitがループを所有し、こちらは `ApplicationHandler` トレイトの実装を渡す。
1フレームの心臓は `RedrawRequested` イベント。

```rust
impl ApplicationHandler for アプリ {
    fn resumed(&mut self, event_loop: &ActiveEventLoop) {
        // ウィンドウ生成とレンダラー初期化はここ（OSの準備完了後に呼ばれる）
    }

    fn window_event(&mut self, event_loop: &ActiveEventLoop, _: WindowId, event: WindowEvent) {
        match event {
            WindowEvent::RedrawRequested => self.一フレーム実行する(),
            WindowEvent::CloseRequested => event_loop.exit(),
            // 入力イベントはここで入力収集器に蓄積する
            _ => {}
        }
    }

    fn about_to_wait(&mut self, _: &ActiveEventLoop) {
        self.window.request_redraw();   // 毎周回、次フレームの描画を要求（ゲーム用の定石）
    }
}

fn main() {
    let event_loop = EventLoop::new().unwrap();
    event_loop.set_control_flow(ControlFlow::Poll);  // イベントが無くても回し続ける
    event_loop.run_app(&mut アプリ::生成する()).unwrap();
}
```

`一フレーム実行する()` の中身（入力確定→世界更新→描画内容抽出→描画）はコンポジションルートの明示的な逐次コードであり、winitは関与しない。

## パターンB: 自前所有ループ（pump_app_events）

最外周の `loop` を自分で書き、毎周回の先頭でwinitにイベント処理だけさせる。
`EventLoopExtPumpEvents` 拡張トレイト（デスクトップOSで利用可）を使う。

```rust
use winit::platform::pump_events::EventLoopExtPumpEvents;

fn main() {
    let mut event_loop = EventLoop::new().unwrap();
    let mut アプリ = アプリ::生成する();

    loop {
        // タイムアウト0 = 溜まっているOSイベントだけ処理して即返る
        let status = event_loop.pump_app_events(Some(Duration::ZERO), &mut アプリ);
        if let PumpStatus::Exit(_) = status { break; }

        アプリ.一フレーム実行する();

        アプリ.フレーム間ペーシング();  // ここが自前所有の意義。スリープ+スピンウェイト等を
                                        // 完全に自分の裁量で書ける
    }
}
```

## 移行手順（パターンA → B）

前提: blitz_engine のAPIは「更新・描画を外から呼ばれるだけ」のループモデル非依存であること（現行設計）。
この前提が守られている限り、**変更されるのは blitz_app の main.rs 周辺のみで、blitz_engine / blitz_render は1行も変わらない**。

1. `RedrawRequested` 内の1フレーム処理が `一フレーム実行する()` として独立メソッドに抽出されていることを確認する（パターンAの時点でそう書いておく）
2. `main()` の `event_loop.run_app(...)` を、パターンBの `loop { pump_app_events; ... }` に置換する
3. `ApplicationHandler` 実装は**そのまま残す**。pump_app_events も同じトレイト経由でイベントを配送するため、入力蓄積・リサイズ処理・終了要求の受け口は共通
4. `about_to_wait` の `request_redraw()` 呼び出しを削除し、`一フレーム実行する()` を自前ループから直接呼ぶ形に変える
5. `ControlFlow::Poll` 指定を削除し、周回末尾に自前のペーシング処理を追加する
6. 終了は `PumpStatus::Exit` の監視に変わる（`event_loop.exit()` の呼び出し側は不変）

移行規模の見積もり: main.rs の数十行。エンジン・レンダラーは無変更。

## 判断の記録

初期実装はパターンA + FIFO（vsync）で開始する。
FIFOが基準周期とティアリング防止を担う。提示時刻の厳密な安定性は実機計測で判定する。
IMMEDIATEでの自前リミッタ・late-latch・ホスト埋め込みのいずれかが実要求になった時点で、上記手順でパターンBへ移行する。

M11の2026-07-23計測では、GPU全パスが1ms未満でもCPU側p99が約34msになった。区間計測により遅延はフレームデータ準備や画像取得ではなく、2フレーム前のGPUキューに対するフェンス待機へ集中すると確認した。進行中フレーム数1・3への変更で再現性ある改善は得られなかったため2を維持する。

2026-07-25のOW2で、提示時刻を判定する計測入口を`VK_KHR_present_id`と`VK_KHR_present_wait`で実装した。各提示に単調増加のIDを付け、次フレームの先頭でそのIDの表示完了を待ち、観測時刻の間隔を実表示間隔として記録する。対応可否は物理デバイスの拡張一覧と機能フラグから判定し、非対応環境では拡張を有効化しない。この計測により、CPU側p99約34msが実表示の更新脱落を伴うと確定した。提示モードはFIFOのまま、進行中フレーム数も2のまま変更していない。

注意: この計測は描画ループを停止させる。NVIDIAドライバー596.21では`vkWaitForPresentKHR`がtimeout=0でも表示まで停止するため、毎フレーム約16ms止まる。常時有効にしてはならず、専用フラグ`--report-display-timing`を指定した実行だけで有効にする。指定が無いときは提示待機の2拡張を論理デバイスで有効化せず、素の条件の提示経路を保つ。詳細は `_doc/計測/OW2_2026-07-25.md` を参照する。
