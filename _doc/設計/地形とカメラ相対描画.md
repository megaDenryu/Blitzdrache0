# 地形とカメラ相対描画

この文書は、OW3で導入するカメラ相対描画の座標契約と、チャンク化した高さ地形のLOD描画の設計を管理する。実装と常に一致させて維持する。設計の経緯はjimbo札#143とAgentRoom「ゲームエンジン開発室」の壁打ち（2026-07-28、codex）にある。

## カメラ相対描画の契約

f64の大域ワールド位置からカメラ大域原点を引き、f32のカメラ相対座標だけをGPUへ渡す。GPUに大域の大きなf32値を持ち込んだ時点で精度は失われているため、引き算は必ずCPU側のf64で行う（`blitz_math` の `大域ワールド位置::カメラ相対へ変換する` が唯一の境界）。

**不変条件: 1フレームのGPU入力はすべて同じカメラ大域原点の相対フレームで表す。** シーンの頂点変換、シャドウのライトビュー射影、フレームUBOのカメラ位置と点光源位置は、同じ原点を引いた値を使う。方向光の方向は平行移動に依存しないため変換しない。ビュー射影はカメラ相対フレームで組み立て、対象側でも原点を引くため、ビューに大域平行移動を再び入れてはならない（二重減算の禁止）。

### 適用点: チャンク由来の描画アンカー

すべての描画対象は所有チャンクを持つ（OW0第4段。ストリーミング対象でないアセットは原点チャンクに属する）。この所有チャンクの大域原点（チャンク座標×一辺長のf64導出値）を**描画アンカー**とし、対象の配置を次の2つに分ける。

- **静的なローカルからアンカーへの変換**（f32）。scene形式の行列はこの意味であり、大きな平行移動を入れない。法線行列・マテリアル係数とともに対象別UBOへ生成時に一度だけ書き、以後変えない
- **f64の描画アンカー**。ファイルへ焼かず所有チャンクから導出する

毎フレーム、`アンカー大域原点 - カメラ大域原点` をf64で引いてf32へ狭めた**カメラ相対アンカー**を、シーンパスとシャドウパスの両方へ描画ごとの16バイトのプッシュ定数として渡す。頂点処理は「局所f32頂点 → 静的ローカルからアンカー(f32) → カメラ相対アンカーを加算 → 相対ビュー射影」の順である。プッシュ定数はフレームインフライトの多重化対象にならないため、対象別UBOの静的性が保たれる。

スキニングは従来どおり「ローカル→アニメ後ローカル」で完結させ、出力へ描画時のローカルからアンカーとカメラ相対アンカーを適用する。ジョイント行列へ大域平行移動を混ぜない。

布と粒子はGPU側で世界原点を基準に位置を計算するため、所有チャンクを原点チャンクとみなし、世界原点のカメラ相対値を同じプッシュ定数で受け取る。これらもフレームUBOのビュー射影を共有するため、対象側だけを相対化すると位置が壊れる。

影は同じ相対フレームで組み立てる。方向光の正射影領域は焼いた行列でなく再構築パラメータ（注視点の大域位置・光源距離・正射影寸法）で持ち、毎フレーム、カメラ大域原点を引いた相対位置からライトビュー射影を作る。点光源位置も大域位置で持ち、同じ原点で相対化する。シェーダーの `worldPosition`・`cameraWorldPosition` は意味がカメラ相対になるため、名前を相対であることが分かるものへ変える。

### 棄却した案

- **ビュー行列側だけで処理する案**: 対象の大きな平行移動が先にf32モデル行列へ丸められ、ビュー側参照する時点では失った桁を戻せない。照明・影が共有する `worldPosition` も分裂する。
- **対象別UBOのフレームスロット化（毎フレーム相対平行移動を書き込む案）**: 全対象×フレームインフライト数のバッファ複製と毎フレームの全対象書込みが要る。アンカー方式なら静的データは静的のままで、動くのは描画ごとの16バイトだけである。本文書の前版はプッシュ定数案を「チャンクに属さない対象で利得が消える」と棄却していたが、全描画対象が所有チャンクを持つため前提が誤っていた。
- **GPUへf64や高位・低位の2分割値を渡す案**: 既存の唯一境界（CPU側f64減算）とDoDに対して過剰である。

## 地形の表現

地形は高さ格子をアセットコンパイラの入力とし、実行時形式へは**LOD付きメッシュとして決定的に焼く**。実行時に高さ格子からメッシュ化する案は、生成時間と浮動小数結果が機材・並列順に依存してOW1のバイト決定性を後退させ、「実行時は版付き形式だけを読む」役割分離にも逆行するため棄却した。コンパイラは固定走査順・固定三角形対角・2^n+1格子・2倍刻みサンプル・固定の法線規則で生成し、隣接チャンクの境界高と法線はソースを共通の大域サンプル座標から切り出して一致させる。

実行時形式は**新種別を作らず、sceneの最新版で描画形状を判別共用体 `通常メッシュ | 地形LODメッシュ群` にする**。地形LODメッシュ群は段番号順の非空メッシュ列を持ち、各メッシュは既存の頂点形式・既存のPBR・既存の描画コマンドで描ける。旧scene_v1は版固有型で読み、全対象を通常メッシュとして最新版へ変換する（版ごとの型+最新への変換）。洞窟・張り出しは同じscene内の通常メッシュとして同居する。別の地形アセット種別はカタログ解決・読込器・完了キュー・描画束の二重化になるため棄却した。複数LODを通常描画対象として並べる案は、現行レンダラーが全対象を描くため選択の意味が失われ棄却した。

チャンクの大域配置はファイルへ焼かず、チャンク座標×一辺長からf64で導出する（描画アンカーと同じ導出。導出できるものを保存しない）。

### 高さ格子のソース形式

高さ格子とは、世界全体にひとつだけある大域サンプル格子から、チャンク1つ分の正方窓を切り出した高さの標本のことである。窓は隣接チャンクと重なる縁を持ち、重なり幅ぶんだけ格子添字が負の側へ伸びる。中央差分の法線が境界の格子点でもこの重なりの標本だけで閉じるため、隣接チャンクの境界の高さ・法線・接線は照合ではなく計算だけで一致する。

大域サンプル添字はチャンク座標×辺分割数＋格子添字で決まる整数である。実数の座標でなく整数で決めるのは、隣接する2つのチャンクが共有する標本を必ず同じ値で参照するためである。添字はi16の範囲に限る。標本の位置を実数へ変換するとき、i16からf32への変換だけが値を落とさないためである。範囲を超えた要求は無言で丸めず型付きエラーにする。

ファイル形式は固定識別値・形式版・辺分割数・重なり幅・チャンクの一辺メートルのヘッダーと、リトルエンディアンのf32を行優先（Zが外側、Xが内側）で並べた本体である。辺分割数は2の冪に限る。格子点数が2^n+1になり、1つおきに間引いた点がそのまま次に粗い段の格子点になるためである。

### スカートの深さ

スカートの深さはチャンクごとに1つ、コンパイル時に算出する。そのチャンクの四辺について、隣り合う2段の辺の最大偏差を全段対で取り、安全幅0.5メートルを足した値である。偏差とは、細かい段の格子点の高さと、その点を挟む2つの粗い段の格子点を結んだ直線の高さとの差のことである。隣接するチャンクの段差は最大1段へ緩和されるため、隣り合う段の対だけを見れば実際に開きうる隙間を必ず上回る。

深さを全段へ同じ値で適用するのは、段ごとに変えると同じ継ぎ目を挟む2段が違う深さで垂れ下がり、深い側の帯が浅い側からはみ出して見えるためである。安全幅を置くのは、標本の位置が完全に一致しても浮動小数の丸めで僅かに開くためである。

検証用地形世界の25チャンクでの実測は0.92メートルから1.14メートルであり、第2段が暫定で置いていた固定値12メートルの10分の1以下に収まった。

### LOD

- **チャンク単位LOD**。各地形チャンクは1つの描画束で、全LODを読込時にGPUへ載せる。距離判定は毎フレーム行い、選択したLODの頂点・インデックスだけを描画入力へ積む。**LOD切替はディスクI/O・束の解除再読込・GPU再確保を起こさない。** 段数は5段であり、辺分割数を64から4まで半減させる。全段の総量の理論値は最高詳細1段の約4/3であり、検証用地形世界での実測は1.379倍である(1チャンクあたり319,536バイトから440,688バイト)。理論値より大きいのは、外周スカートの頂点数が辺の分割数に比例して4分の1でなく2分の1でしか減らないことと、格子点数が分割数+1であることによる。全段分はカタログ見積とVRAM会計へ含める。
- 段の格子点は高さ格子を2の冪で間引いた部分集合であり、法線と接線は最詳細段と同じ中央差分の値を使う。段をまたいでも陰影が変わらず、粗い段の中央差分のために重なり幅を段の刻みまで広げる必要もない。
- 距離はカメラ大域位置とチャンクのf64大域包囲領域とのXZ最短距離で決め、切替閾値にはヒステリシスを入れる。基準距離は200メートル、ヒステリシス幅は前後10メートルであり、値はコンポジションルート(`crates/blitz_app/src/app/streaming/lod_sync.rs`)が持つ。距離をストリーミングの必要集合の中心でなくカメラの視点位置から測るのは、段が見え方で決まるためである。`--streaming-route`では2つが別の位置になる。
- **注意: 検証用地形世界の設定では段が0のままになる。** 先読み半径1と一辺100メートルでは、常駐する3×3の集合のうち視点から最も遠いチャンクでも最短距離は100×√2の141メートルであり、基準距離200メートルに届かない。距離選択そのものはユニットテストで境界値を検査しており、本番経路で段1以上が選ばれることは`--streaming-route`(視点が原点に留まり必要集合だけが移動する)で確認できる。段の分布は`--report-streaming-summary`の「最終フレームの地形詳細段」に出る。
- **隣接する常駐チャンクのLOD差は最大1段へ決定的に緩和する。** スカートの深さを「細かい辺と次に粗い辺の最大偏差+安全幅」からコンパイル時に算出するための前提であり、固定の巨大な深さより露出を抑えられる。隣接が常駐していないチャンクは単独で選択でき、選択のために未読込の隣接を要求しない。
- 境界の亀裂は**外周スカート**（各LODの四辺を複製して規定深さだけ下へ延ばした帯）で塞ぐ。粗い辺の頂点は細かい辺の部分集合に固定する。ジオモーフィングはOW3では入れない。

### 棄却した案

- **隣接LOD差の専用縫合**: 四辺の隣接状態に応じた最大16組のインデックス構成と、ロード・解除時の隣接再評価・角の組合せ検査が要り、既存束の独立性を失う。
- **ジオメトリクリップマップ**: カメラ中心のリングとトーラス状更新という別ライフサイクルが要り、100m目録・チャンク束の増分追加解除を迂回する並行インフラになる。全LOD同梱のVRAMか描画発行が実測予算を超えたときの再評価候補に留める。

### レンダラーの資源配置

この設計は `レンダラー` 直下の新しい資源フィールドを必要としない。LOD幾何は既存の「チャンク描画資源→描画対象資源」の内側に収まり、選択結果は既存の毎フレーム作業領域へ置ける。したがって札#139第12段「描画段階資源の器」を予測だけで起動しない。実装中に直下フィールドが実際に必要と判明した場合だけ、追加前に第9.5→10→11→12a〜c段を挿入する。

## DoDの検査設計

**大座標の画素判定は「原点移動に対する描画不変性」で測る。** 同じ局所シーンをA系列（原点近傍）とB系列（対象・カメラ・光源・影基準のすべてへ同じkm級のf64大域平行移動を加える）で描く。GPUへ届く相対値は同一になるため、ポスト処理なしの読み戻しはバイト一致を要求できる。さらにカメラを0.25m動かしたA'とB'を描き、A'=B'に加えて、A→A'とB→B'で高コントラスト標識の重心移動が非0であり両者の差が0.25画素以下であることを判定する。巨大座標で微小移動が丸めで消えて両画像が偶然静止する欠陥をこれで検出する。

**LOD亀裂は構造検査とGPU検査の2段で測る。** CPU側はコンパイラ出力の全LODについて、四辺の格子整合・粗辺頂点が細辺の部分集合であること・スカートの頂点とインデックス順・隣接差1の解決結果を検査する。GPU側は起伏のある2チャンクをLOD差のある組で接して斜めの固定視点から描き、地形を白・背景を判定専用色にして、共有辺の投影帯に背景色画素が0件であることを読み戻しで判定する。検査するのは四方向×段差0・1・最大4×細粗入替の24組と、四方向×片側の隣接が常駐しない場合の存在側段0・4の8組である。

判定領域を画面の広い区画でなく共有辺の投影帯に固定するのは、亀裂が共有辺の1画素幅にしか現れないためである。広い区画を数えると、地形が写っていない領域の背景画素と亀裂の背景画素を区別できず、逆に区画の内側さえ埋まっていれば合格になる。投影座標は`terrain_origin`の初期カメラと1280×720の画面から決め、ラスタライズが共有辺を所有する側の1画素帯へ寄せる。

**ストリーミング併用は既存の固定経路と目録・カタログ・読込・束の経路をそのまま使う。** 地形世界で100m境界とLOD閾値の両方を跨ぎ、読込・常駐・解除・LOD変更・選択段の描画・継ぎ目画素・RAM/VRAM会計を1回の自動終了実行で判定する。模擬ストリーマは作らない。

登録済み入口はリポジトリルートで実行する `cargo xtask ow3-dod` である。2026-07-29の実測では、A=BとA'=B'がバイト一致し、0.25メートルのカメラ移動に対する標識重心はA系列とB系列がともに27.6432画素移動し、移動ベクトル差は0.0000画素だった。移動量が2026-07-28の27.6417から動いたのは、OW5第5段のカスケードシャドウで標識に落ちる影の解像度配分が変わり、標識の重心がわずかにずれたためである。判定は系列間の一致であり、移動量の絶対値には依存しない。

GPU継ぎ目検査は32組すべてが合格し、共有辺の投影帯のROI合計11,744画素で番兵背景の露出が0画素だった。CPU構造検査は全段対の四辺部分集合、隣接四方向、非常駐隣接を含む。

半径2の統合経路は最初の120フレームを静止して25チャンクを先読みし、その後40フレームでX=50メートルから250メートルまで進んで100メートル境界とLOD閾値を横切る。実測はディスク読込25件・11,155,300バイト、GPU転送25件・11,274,000バイト、最大台帳25件、GPU資源解除10件、LOD変更2フレーム、LOD変更時の読込開始0件である。最大使用量はRAM 11,147,860バイト、VRAM 11,274,000バイトで、各16MiB上限内に収まった。最終描画選択は段0が12件、段1が3件であり、validationは0件である。

容量の値は2026-07-29のOW4第4段で地形チャンクへ植生の群を同居させたぶんだけ増えている。同居前はディスク読込11,022,050バイト、GPU転送11,017,200バイト、RAM最大11,018,170バイト、VRAM最大11,017,200バイトだった（参照: `_doc/設計/チャンクストリーミング.md`「検証用地形世界」）。件数・LOD変更・validationの判定に使う値は同居の前後で変わっていない。

## 段階導入

1. **カメラ相対の通常メッシュ縦切り**: 所有チャンクからのf64アンカー導出、カメラ相対アンカーの作業領域と両描画パスへの配線（プッシュ定数）、相対ビュー射影、点光源・方向光影の再構築パラメータ化とカメラ相対化、スキニングの契約維持を既存シーンで完成させる。本番呼出し元は既存のフレーム準備とシーン・シャドウ描画であり、原点移動不変性の最小の画素対検査もこの段に置く。
2. **単一メッシュ地形の縦切り**: コンパイラが高さ格子からLOD0と四辺スカートを既存sceneメッシュとして生成し、既存の目録・カタログ・読込・描画束で実際に常駐描画する。LOD0の生成ロジックは後段がそのまま使うため捨て実装にならない。実装済みであり、検証用地形世界の置き場と実行方法は `_doc/設計/チャンクストリーミング.md`「検証用地形世界」にある。
3. **複数LOD化**: sceneの最新版へ形状判別共用体と旧版変換を入れ、コンパイラが全LODとスカートを出し、エンジンの距離・ヒステリシス・隣接差1の解決を本番のストリーミング常駐集合へ接続し、既存作業領域が選択された幾何を両パスへ積む。全LOD分のRAM/VRAM見積を更新する。実装済みである。継ぎ目の画素判定は第4段で行う。検証用地形世界の既定の常駐集合では段が0のままになり、LOD差のある継ぎ目が画面に出ないためである(「LOD」節の注意を参照)。
4. **統合DoD計測**: 原点移動不変性のkm級2組・小移動列、全LOD境界の亀裂判定、固定経路の読込・LOD変更・解除・会計を1つの登録済みxtask入口へまとめる。実装済みであり、入口は`cargo xtask ow3-dod`である。片側の隣接が常駐しない継ぎ目と、判定領域の共有辺投影帯への固定は補正で加えた。
