# アーキテクチャ批判の要点（Claude へ伝える用）

2026-08-08 にユーザーが外部レビューから得た指摘の要点。
「エンジン先行は無意味だ」という主張ではない。問題は「作る順序」と「完了判定の正直さ」の2点に絞っている。

## 1. M11完了宣言の矛盾

- DoD（`_doc/計画/開発計画.md`）に「60fps（FIFO同期）で安定動作」がある
- しかしM11完了報告は「実表示時刻による60fps安定は未証明」と自認したまま完了扱いし、フェーズ2へ進んだ
- M11時点の実測: CPU側 p95 33.2550ms / GPU合計 0.7276ms（CPUがGPUの約47倍遅い）
- 影響: 完了判定の基準が信用できなくなる。以降のマイルストーンも同じ構造で「完了」が量産される恐れ

## 2. 投資順序の逆転

- ゲーム非依存で壊れている基盤（フレームペーシング・進行中フレームの同期）を後回しにした
- その一方で絵依存の機能（4距離区分CSM・SSAO・IBL焼き直しの間引き・自動露出・時間再構成）を先に全部積んだ
- 絵依存の機能は絵の様式・コンテンツが決まらないと最終形が決まらないため、企画が熟すまでは作り直しが効く
- 本来の順序:
  1. どのゲームでも絶対に要り、しかも今壊れている基盤（ペーシング）を直す
  2. 賭けの中核（ストリーミング・物量受け止め・アセットパイプライン）を詰める
  3. 絵依存の機能は企画の壁打ちが熟してから

## 補足: 接続契約は既に作ってある

- ScriptableObject相当（データ契約）: アセットコンパイラ + 版付き実行時形式 + カタログ
- MonoBehaviour相当（実行契約）: 入力インテント・介入モデル・フレーム段階
- つまり「接続機構を先に作るべき」は既に実行済みであり、新たな教訓ではない

## 残っている問い

- 60fpsのペーシング問題は「次フェーズのどこで・誰が・何を測って」直すのか?
- これが答えられないままなら、フェーズ2でも同じ構造で「完了」が量産される

## 関連する批判（今回は議論の対象外だったが、伝えておく価値があるもの）

- ゲームロジックをRustで書く決定: ゲームの変更はフル再コンパイル。ホットリロードはシェーダーだけ。MonoBehaviour的な機構を作っても、繋ぎ先がフルビルド待ちでは意味が薄い
- 日本語識別子 + 略語禁止: 外販・OSSを視野に入れるなら共有不可能。日本語が読めない人は1文字も読めない
- 100行分割ルール: ファイルの爆発を生み、読むコストを上げている

## コード面の裏付け（2026-08-08 検証）

「関連する批判」のうち、リポジトリを読み直して裏付けを取った結果を記す。4点中2点は修正・撤回が必要だった。

### 1. ファイル爆発は数値で裏付けられる（支持）

実測: `blitz_render` は .rs が1031ファイル（vulkan配下572、renderer配下119）、`blitz_app` は296ファイル。
具体例: `vulkan/lighting_query` が17ファイルで、1つの GPU レコード束（32バイトのヘッダ+方向光+局所光）を「内容型」「バイト列組み立て」「パック」「スロット資源」に分割し、検査も layout_tests / pack_tests / shader_struct_tests の3種に別れている。個々のファイルは17〜96行に収まっており、100行ルールは守られているが、読む側は1つのレコードを理解するのに複数ファイルを行き来する。

### 2. unwrap()禁止の機械的強制は迂回可能（一部支持）

`unwrap_used` / `expect_used` を deny しているが、`unwrap_or_else(|誤り| panic!(...))` は検出されない。この形が166ファイルに広がる（例: `auto_exposure/clamp.rs:38,52`、`adaptation_speed_pair.rs:43`、`positive_luminance.rs:27`、`middle_gray.rs:20`、`histogram_scale.rs:84`）。
ただし規約は「到達したらバグである状態にのみ panic! を使い、メッセージに破られた不変条件を書く」を許容しており、上記はすべてメッセージ付きなので趣旨には整合する。批判の射程は「機械的強制がこの形を通してしまう」の一点に限定される。

### 3. CPU↔シェーダーのバイト契約（当初主張を修正）

`shaders/lighting_query.slang:5-6` に「Rust 側はバイトを手書きで書くのでシェーダーから導出できない。片方変えたら必ずもう片方も変えること」とあり、二重管理であることは事実。
ただし `vulkan/lighting_query/shader_struct_tests.rs` が slang 原文を `include_str!` で読みパースし、CPU 側のバイト列と開始位置を突き合わせる機械検査を持ち、conform にも「CPU正本とslang写しで同じ値を持つべき定数の一致」がある。「型で閉じられておらず規約遵守で守っている」は不正確。正しくは「単一正本から導出するのでなく二重管理し、それをテストで担保している」。残る批判は、新しい構造体を足すたびに手書きと検査の2重コストがかかる点のみ。

### 4. FIXME 残置の指摘は撤回

初回調査で `view_bytes.rs` に FIXME が見えたと報告したが、grep の結果 `crates` 配下に FIXME は0件で、該当ファイルは22行で FIXME を含まない。読み取り出力の破損による誤認であり、この指摘は撤回する。
