# Codexのハーネス

この文書は、Codexの調査・実装・検証の工程を定める。ハーネスとは、AIが作業を進めるための指示・道具・検証の仕組みのことである。[AGENTS.md](../AGENTS.md) がこの文書の読了を要求する。

## 通常の工程

Codexは通常、単独で作業する。GPT-6 Astraは設計から検収まで自分で担当し、Lunaへ作業を渡さない。Codexは [CLAUDE.md](../CLAUDE.md) と共通規約を引き続き読むが、委譲を要求する工程を次のように置き換える。この置き換えは、ホームのCLAUDE.md、リポジトリ内の複製、それらが参照するスキル・役割定義にも適用する。

| Claude側の工程 | Codex自身が行う工程 |
| --- | --- |
| 副官へ反論と代案を求める | Codexは判断前に反例・規約との衝突・代案を検討する。 |
| 実装員へ担当を分ける | Codexは依存の順序に従って実装する。 |
| 命名・構造・文章などの検査員を起動する | Codexは変更範囲を各観点で自己レビューする。 |
| ビルド員を常駐させる | Codexは必要な検証を自分で直列に実行する。 |
| 待ち時間に全域の監査を派遣する | Codexは依頼された監査、または今回の変更に必要な範囲を自分で検査する。 |
| 外部AIへ検索・レビューを委譲する | Codexは提供された検索・読み取りの道具で調べ、根拠を確認する。 |

品質条件の維持は、別のエージェントの起動を意味しない。Codexは次の工程を自分で完了する。

1. Codexは入口が指定する規約、現在のブランチ、既存の差分を確認する。
2. Codexは目的・完了条件・変更範囲・変更リスクを定め、対象の設計正本、呼び出し元、型、状態の所有者、依存の向きを確認する。
3. Codexは反例と代案を検討し、決定した契約に従って実装する。Codexは他の作業の変更を取り消さない。
4. Codexは必要な検証を実行し、設計遵守・規約遵守・呼び出し側の接続・検証結果・差分全件を確認する。
5. Codexは変更内容、検証結果、未確認事項を報告する。引き継ぎが必要なら、Codexは目的・完了事項・残件・変更ファイル・判断の根拠を残す。

物理基盤の変更では、Codexは [物理基盤の工程](../.claude/skills/物理基盤の工程/SKILL.md) の契約・責務層・反証・一次計測・設計裁定・本実装の順序を維持する。Codexは副官への相談を自分の反例検討へ置き換えるが、必要なユーザーの設計裁定を自己判断で省略しない。

## 検証の場所と範囲

Codexはコード読解と静的検査を先に行い、変更に必要な単体・境界テストを選ぶ。コードの標準検証は `cargo xtask verify` とし、Codexは実行前に入口の現行実装と許可範囲を確認する。CodexはブラウザE2EやGUI自動操作を事前許可なしに実行しない。

ビルドを伴う検証では、Codexは専用チェックアウト `C:/devs/Blitzdrache0_build` をツールの作業ディレクトリに指定する。Codexは使用状況と既存の変更を確認してから検証対象を揃え、使用中のチェックアウトを切り替えず、他者の変更を消さない。Codexは作業ツリーごとにビルドの出力先を増やさない。Codexは対象のコミット・差分と検証ログが一致することを確認する。

文書だけの変更では、Codexは内容・参照先・索引・差分の空白エラーを確認する。設定を変更した場合、Codexは構文と手元のCLIによる読み込みも確認する。Codexはその確認のためにエンジン全体のビルドや子エージェントの実行を追加しない。

## Luna Maxによるオーケストレーション

オーケストレーションとは、親が子へ仕事を分けて結果を統合する運用のことである。利用者がこの運用を明示的に指定し、実際の親モデルが `gpt-5.6-luna`、推論設定が `max` の場合だけ、親は次の定義を使える。親がAstra・Sol・不明なモデルの場合、または利用者の明示指定がない場合、Codexは単独の工程を使う。AstraはLunaの親を子として起動してこの条件を迂回しない。

| 定義 | 担当 |
| --- | --- |
| [luna_max_worker](agents/luna_max_worker.toml) | 子は親が限定した範囲を調査・実装する。 |
| [luna_max_reviewer](agents/luna_max_reviewer.toml) | 子は読み取り専任で、対象の差分と根拠を検査する。 |

親は委譲先へ、利用者の運用指定、親のモデルと推論設定、目的、設計正本、編集可能な範囲、禁止する変更、完了条件を渡す。親は独立した仕事だけを分け、同じファイルを複数の子へ編集させない。子はさらに別の子を起動しない。親はビルドと最終検収を自分で行い、子の完了報告だけで合格にしない。

[config.toml](config.toml) は通常のサブエージェント機能を無効にする。Codexは `.codex/agents/` の独立した定義ファイルからLuna用の役割を読み込む。設定は親のモデルを変更しない。利用者がLuna Maxの運用を選ぶ場合、利用者は `C:/devs/Blitzdrache0` を作業ディレクトリとして次のコマンドで新しいCLIセッションを開始し、そのセッションへ具体的な作業を依頼する。

```powershell
codex -C C:/devs/Blitzdrache0 -m gpt-5.6-luna -c 'model_reasoning_effort="max"' -c 'agents.enabled=true' 'Luna Maxによるオーケストレーションを使用する。AGENTS.mdと.codex/README.mdに従う。'
```

このリポジトリは、2026-09-22に確認した `codex-cli 0.155.1` と現行の公式仕様に合わせ、`agents.enabled` と、`name`・`description`・`developer_instructions` を持つ独立したエージェント定義を使う。Codexは旧形式への切り替えや互換用の二重定義を行わない。設定を受理できない環境では、Codexは不一致を報告し、設定が適用されたものとして作業を進めない。

設定ファイル自体は親のモデルに応じた条件分岐を強制しない。通常の機能無効化と、入口・役割の利用条件を組み合わせて運用する。利用者による設定の上書きや、別の実行環境が機能無効化を適用しない場合でも、Codexは上記の利用条件に従う。既存セッションへの設定の自動反映は前提にしない。

## 参照文書と判断の根拠

Codexは共通規約をこの文書へ複製しない。[既存の規約入口](../.claude/commands/rule.md)、[文章規範](../.claude/skills/doc-writing/SKILL.md)、[READMEの設計・用語索引](../README.md#ドキュメント) が正本を案内する。CodexはClaudeの役割を起動するためだけの追加文書を読み込む必要はない。

2026-09-22時点の公式資料と、このリポジトリの運用判断を区別する。

- OpenAIは [Astra向けの指示の見直し](https://developers.openai.com/blog/rethinking-skills-and-prompts-for-gpt-6-astra) で、SolやLunaに有効な指示がAstraを過剰に制約する場合があると説明している。
- OpenAIの [Astraのガイド](https://developers.openai.com/api/docs/guides/latest-model) は、Astraのサブエージェントによる分担能力も説明している。この資料はサブエージェントの一律禁止を推奨していない。
- 今回確認した公式資料には、Astra単独とAstraからLuna Maxへ委譲する構成の品質を直接比較した結果は見つからなかった。Astra単独という選択は、品質低下が実証されたという主張ではなく、利用者が指定した運用方針である。
- OpenAIの [Lunaのモデル仕様](https://developers.openai.com/api/docs/models/gpt-5.6-luna) は `max` を含む推論設定を説明し、[サブエージェントの説明](https://learn.chatgpt.com/docs/agent-configuration/subagents) は専用の役割・モデル・指示の設定を説明している。手元のCLIへの適用形式は前節の確認結果に従う。
