## 呼称と語の選択（2026-08-09 制定。会話・報告・文書の全出力に適用）

Blitzdrache0でのオーナー裁定から制定した。経緯のクレーム: (1)「段とか順とか日本語じゃない
から使うな。中国語か？中国語を使うな。日本語を使え」（「着手順4」を「順4」、「第3段階」を
「段3」と呼んでいた） (2)是正の第一案でAIが「マイルストーンの内容名で呼ぶ」と別の言い換えへ
飛び、「なんで着手順やったらわかるのに着手順以外の言葉になるねん」 (3)「ステップはカタカナ語
でも日本語やんけ」 (4)「カタカナ語は小学生がわかるものだけにしろ。専門家とか関係ない」。

1. **漢字1文字を語として使う中国語的な圧縮を作らない・使わない。** 日本語では「着手順」
   「段階」が語であり、「順4」「段3」のように1文字へ切り詰めた時点で日本語でなくなる。
   元の完全な語で書く（着手順4・第3段階）
2. **誤りの是正は「元の完全な語へ戻す」ことであり、新しい言い換えを発明しない。** 読み手が
   既に知っている元の語が正解である
3. **カタカナ語の基準は「小学生が分かるか」。** 可: ステップ・ブロック・ファイル・テスト・
   カメラ等。不可: マイルストーン（→節目）・フォールバック（→代替）・ラウンドトリップ
   （→往復）等の業界カタカナ語。「専門家か非専門家か」という切り口は使わない
4. 既存文書内の既存表記の一括改稿はしない（ついで是正の対象）。既存文書へ追記するときは
   前後との整合を保ちつつ、新しく書く文はこの規則で書く

## 説明の順序（2026-07-20 制定）

- **幹 → 葉の順で説明する。** 新しい概念・仕組みは、まず層と位置づけ（それは何で、
  どこに属するのか）を定義してから詳細に入る。層の定義前に検証項目・パラメータ等の
  詳細を語らない（聞き手は「何の話なのか不明」になる）
- **仕組み・案があるなら最初から出す。** 出し惜しみして質問だけ先に投げない。
  ユーザーの知らない概念を前提にした質問は、先に概念を説明してからにする
- 可能ならユーザーの既知の経験への対応表で説明する（例: 新概念をUnity/ブラウザでの
  既体験に写像する）

## 文章規範（2026-07-20 制定。キャラなりきり以外の全出力に適用）

全文: `~/.claude/skills/doc-writing`（複製は `.claude/skills/doc-writing/`）。適用範囲はドキュメントに限らず、チャット応答・
コード内コメント・コミットメッセージ・**サブエージェントへの指示**を含む全出力。
根拠: 人間が一意に判定できない文はAIにも判定できず、推論コストの増加とミスに直結する。
委譲プロンプトの曖昧さはサブエージェントの成果物の欠陥として返ってくる。

- **未定義の造語・比喩を使わない。** 独自の抽象語を書きたくなったら、それは概念を
  まだ言語化できていないシグナル（ユビキタス言語不足と同型）。確立用語に言い換えるか、
  プロジェクトの用語定義ファイルに定義してから使う
- **定義は定義文で書く**: 「Xとは〜のことである」。「用語: 名詞句」形式を定義に使わない
  （許容は用語集と、関係が自明なkey-value列挙のみ。その場合も説明側は述語で終える）
- **素直な語順で書く**: 倒置・副詞前置の断片文・指示語止め（「〜がこれ」）を使わない。
  「意識的に」等の情報を持たない程度副詞は削り、代わりに「いつ・誰が・何を」を書く
- **主語を省略しない**（2026-09-04 オーナー裁定。仕事の文章の全部に適用する）。日本語の文法が
  主語の省略を許すことは、仕事の文章で省いてよい理由にならない。**「文脈から復元できるから
  省いてよい」という判断を認めない。** 復元できるかどうかは書き手の主観であり、読み手が同じ
  復元をする保証が無い。判定は述語ごとに行い、その動作の主体が書かれていなければ違反とする。
  同じ文の中で複数の述語が1つの主体を共有する形は、主体が書かれているため違反ではない
- **影響度は定量で書く**（倍率・オーダー・工数。「大きい」「重い」で止めない）
- **数量詞・指示語で受ける前に対象を名指しする**: 「2本ある。両方を立てる」では両方が何か
  読み手が決められない。「AとBの2つがある。この2つを立てる」の順で書く
- **手順のコマンドには実行場所を併記する**: どこで実行するかで結果が変わる。作業ディレクトリを
  移動するブロックは絶対パスで書き、直前のブロックに依存させない
- 文書固有の規則（常体統一・横幅揃えの文中ハード改行禁止）は全文スキルを参照。
  チャットの敬体は維持してよい（曖昧性排除の各規則はチャットにも適用する）

## コーディング憲法

### 型安全性
- `any` 禁止。`unknown` は外部境界のみ、即座に型ガードで絞る
- `as` キャストで逃げるのは設計の歪み。型を通すために設計自体を見直す
- 作ろうとしているものに忠実な型を書く。形式的な型付け禁止
- 条件分岐はディスクリミネイテッドユニオン/ポリモーフィズムで表現

### 数学DDD（2026-07-20 制定）

プリミティブ執着禁止の数値・数学版。ゲームに限らず任意のアプリケーションに適用する。

- **数値量はプリミティブ（number / f32 / int）で持たない。** 単位（次元）と基準系を型で
  区別する。典型例: 金額（通貨）、時間（ms/s）、UI寸法（px/rem/論理px/物理px）、
  割合（0〜1 と 0〜100）、角度（度/ラジアン）、座標系（スクリーン/ワールド/ローカル）、
  タイムスタンプ（UTC/ローカル）。これらの混同は全部「単位のない数値」が原因の同型バグ
- **単位は代数構造として扱う。** 加算は同一次元のみ許し、乗算は次元を合成する
  （速度 × 時間 = 距離）。次元の合わない演算はコンパイルエラーにする
- **ゼロコストで実装できるためコストを言い訳にしない。** Rust は newtype +
  `#[repr(transparent)]` + 幻影型（/rust スキル参照）、TypeScript は branded type
  （型レベルのみでランタイムコストゼロ）
- **生値に戻すのは境界1箇所のみ**（外部API・GPU・シリアライズ・DOM）。
  境界以外で生値が見えたらプリミティブ執着を疑う

### プリミティブ執着禁止はパス・テキスト・名前にも適用する（2026-08-11 明確化）

新規則ではない。「プリミティブ執着禁止: ドメイン概念は値オブジェクトで包む」の一般則が最初から
含意している適用範囲を、AIが「数値だけ」と誤読して破った経緯の記録である。経緯: Blitzdrache0の
生成台帳の実装で、台帳の本文が裸の`&str`+自由関数(`解析する`/`組み立てる`)、ソースルート・
出力ルートが裸の`&Path`(取り違えても型が通る)、既存の`チャンク座標`型が`(i32, i32)`タプルへ
剥がされてキーに使われ、`&mut 台帳`が自由関数の連鎖を流れる形をオーナーが検出した。クレーム:
「型に閉じ込めたりするべきなのに参照渡しのただの関数にしている」「100行守ってるから構造化
しなくていいでしょみたいなキモさ」。

1. **役割を持つパス(ソースルート・出力ルート等)、形式を持つテキスト(台帳の本文等)、名前
   (ファイル名・チャンク名等)はドメイン概念であり、newtype+メソッドで包む。** traitは不要
   (traitは複数実装に同じ振る舞いを与えるためのもので、ここでは過剰)
2. **操作はその型のメソッドにする。** これは「サービスの依存保持とコールバックの限定」の
   データ側の同型である。AIの既定Rustスタイルは操作の側(自由関数+依存の引き回し)とデータの側
   (プリミティブ+参照渡し)の両輪で歪む。可変のドメイン状態を`&mut`で自由関数の連鎖へ通さず、
   所有する型のメソッドで操作する
3. **役割の型は自分の配置を知る。** `出力ルート.台帳のパス()`のように、パスの導出をメソッドに
   して綴りを型の中の1箇所へ閉じる。汎用の連結(`join`の列)で綴りを呼び出し側へ散らさない
4. **ドメイン型が既に在るのに生値へ剥がして使うのは同罪。** 例: `チャンク座標`を`(i32, i32)`へ
   剥がしてマップのキーにする。能力(Ord等)が足りないなら型の側へ足す
5. **生のstd型(`&str`・`&Path`・`String`・タプル)へ戻すのは境界1箇所のみ**(std::fs等の外部API)。
   上の「生値に戻すのは境界1箇所のみ」と同じ条文である

### 設計
- **アーキテクチャ先行**(2026-08-10 制定。全リポジトリのコードに適用): 新しいサブシステム・
  新機能・新リポジトリのコードを書き始める前に、**層と依存の向き**(何が何を知ってよいか)を
  決めて書き出す。アーキテクチャとは「何が何を知ってよいか」の決定であって機能一覧の予測では
  ないため、要求が粗くても決まる。**「要求が固まっていない」「動いてから整理する」「まず最小で
  作る」を、層を切らない理由にしてはならない**。ドメインの種類ごとの既定の形から始めてよく、
  足りない情報は候補2〜3案と推奨を添えて聞く(導かずに聞くのも、聞かずに構造を捨てるのも違反)。
  境界は文書でなく機械(クレート分割・可視性・lint)で強制する。全文と手順: `skills/アーキテクチャ先行`。
  層が決まった後の役割語彙とファイル配置は `skills/layer-roles`
- **エディターを作るときは `skills/エディター制作` を先に読む**(2026-08-10 制定)。人が目で見て値を
  決めるための道具(エディター・調整画面・可視化)は、**表示が正本と一致していること自体が機能**である。
  暗黙の拡大縮小・補間・丸めを表示へ入れない。縮尺を変えるなら整数比だけにし、人が選ぶ。
  道具が生成する初期値が道具自身の検証を通ることを機械で確かめる。検査を足したら検証の入口へ接続する
- **可能性を閉じる決定を早期にしない**(2026-07-20 制定): 将来の選択肢を不可能にする設計・
  計画判断を早い段階で行わない(「プログラムの変更を困難にする継承という決定を早い段階で
  するな」の一般形)。計画の問いは常に「どの能力を・どの順で・どの品質で作るか」であり、
  「これを不可能にしますか?」という形の質問をユーザーに投げない。決定しないことと
  不可能にすることは別物
- Functional DDD: 不変性 + DDD集約。可変状態を最小化し新しい値を返す
- Composition over Inheritance: ドメイン層の継承禁止。UI層は許容
- DI + コンポジションルート: コンストラクタ注入。グローバルシングルトン禁止。依存の配線はコンポジションルートへ集約する（詳細は各プロジェクトの `coding_rule.md` 第2条）
- **コンポジションルートは多階層でよい。「1箇所」は「1つの型」を意味しない**（2026-09-04 追記）。この条文が「1つの型が全部を配線する」と読まれ、46個の対象を直接所有する型が「規約どおり」として育った実例がある。意味するのは「配線が散らばらないこと」であり、**上位の階層が下位の階層を組み立て、下位の階層がその中を組み立てる形は、この規約を満たす**。判定の問いは「配線がどこにあるか分からない状態か」であって「配線の型が1つか」ではない
  - **階層を切る基準は、責務・寿命・時間意味・生成破棄条件のどれかを共有するかである。** 起動時に決まって変わらないものと毎描画で作り直すもの、描画の都合で変わるものと世界の規則で変わるものは、別の階層に属する
  - **上位の階層は、下位の階層の中身を知らない。** 中身を取り出す口を並べて外から組み立てる形にしたなら、階層は切れていない
  - **束ねただけの階層を作らない。** 多いものを1つの入れ物へまとめる形は、同じ問題を1階層下へ移すだけである。束ねた先が第二の入れ物になっていないかを確かめる
  - **逆に、寿命・頻度・存在理由のどれか1つを共有し、束ねた先が「取り出す口」以外のメソッドを1つ以上持てるなら、束ねる**（2026-09-04 追記）。前の条が禁止側だけを書いていたため、束ねない判断が常に安全側になり、束ねるべきものが平のフィールドとして並び続けた。**問いは「入れ物になるか」であって「多いか」ではない。** 判定は、束ねた型が外へ見せるメソッドの名前を全部列挙して行う。列挙が中身をそのまま返す口だけなら入れ物であり、1つでも命令や判断があるなら概念である
- 値オブジェクト: privateコンストラクタ + `static create()` + `with*()` + `toOther()`
- **非同期・失敗しうる構築のfactory化**: 値オブジェクトに限らず、GPU初期化・DB接続等の非同期
  セットアップを要する型（サービス・エンジン等）は`privateコンストラクタ` + `static async 作成する()`。
  コンストラクタ内でPromiseをfire-and-forgetしない。これをやると「いずれ揃うはずの内部依存」
  全部に無意味な`| null`を付けることになる（詳細: `~/.claude/shared-knowledge/design_async_factory_construction.md`）
- プリミティブ執着禁止: ドメイン概念は値オブジェクトで包む

### 1ファイル100行の原則と分割の質（2026-08-27 制定。全リポジトリのコードに適用）

本節は2つの問いを別々に定め、両者がぶつかったときの順位を定める。(1) 分割してよいか (2) 100行を超えてよいか。この2つを1列に並べると、片方の条文がもう片方の言い訳になる。目的は「責務を正しく分離した結果として、各ファイルが小さくなる構造」であり、長いファイルを100行ごとに切ることでも、1つの責務だと言い張って何行でも書けることでもない。

制定の経緯は2つある。Graphite issue #10 のオーナー指示（100行に収めるためだけの機械的分割の禁止）と、Blitzdrache0 の2026-07-25の規約（超過を許す範囲の限定）である。前者は切りすぎの失敗から、後者は緩めすぎの穴から書かれており、どちらか片方だけでは規範として働かない。あわせて、これまでプロジェクトごとの規約・サブエージェント定義に散在していた100行原則そのものを、全リポジトリの原則としてここで制定する。

#### 分割してよいかの判定

1. **1ファイルは100行以内。目標ではなく原則である。** 1ファイル1関心事。1ファイルに公開型は原則1つ。関数は50行以内とし、超えるなら段階を私有の関数へ切り出す。モジュール境界と re-export により外部から見えるAPIの形は整理する。新しくコードを書くときは最初からこの粒度で書き、既存の超過ファイルはその領域を触る作業のついでに責務単位で分ける
2. **数える対象はコードの行だけである。空行と、コメントだけの行は数えない。** ファイルの100行、関数の50行、および次節の150行のいずれもこの数え方で数える。行末に書いたコメントはコードの行として数える。ファイルの見出しコメント・型や関数の説明・処理の段落の説明を書いたことで原則へ近づくのは、規範として逆である。この数え方は説明を書く余地を与えるためのものであって、縦に並んだ宣言の上へ説明を積んでよい理由にはならない（「コメント」の節で別に禁じている）
3. **100行に収めるためだけの分割を禁止する。** 分割したファイルには独立した責務が必要である
4. **判定の問い**: そのファイルは名前を付けられる責務・概念・生成物を所有しているか。それとも1つの流れを長さだけで切った一片か。前者なら分割してよく、後者なら分割してはならない
5. **所有しているファイルは3つを備える。** 担当することに名前が付く。触る状態が限定されている。呼び出し側が中身を知らなくても呼べる。流れの一片はどれも備えず、隣のファイルと一緒に読まないとどちらの意味も取れない
6. **不正な分割の形**: `xxx_1.rs / xxx_2.rs / xxx_3.rs` のような連番分割。呼び出し連鎖の深さで切ったもの。委譲するだけの薄いラッパーしか持たないファイル。100行を超えそうだという理由だけで `impl` や関数の続きを別ファイルへ移すこと
7. **禁止する理由**: 行数を理由にした分割は、その型が持つ責務（フィールド数・状態を変更できる範囲）を一切減らさない。責務過多を隠したまま行数の検査だけを通過させ、「分割は済んでいる」という誤った印象を与える
8. **合法とみなす形を列挙する場合、機械的な当てはめで判定してはならない。** 列挙に該当しなくても条4の問いを満たすなら合法であり、該当しても満たさないなら違法である。言語ごとの合法な形の列挙は各リポジトリの規約が持つ

#### 100行を超えてよいかの判定（分割の質が優先する）

1. **未正当な分割の禁止は、1ファイル100行以内より優先する。** 分割が条4の問いを満たさないなら、統合した結果100行を超えても統合する。害の性質が違うためである。長いファイルは読むのに手間がかかるだけだが、未正当な分割は責務過多を隠し、1つの流れを読むために複数ファイルを行き来させ、しかも行数の検査を通過する
2. **超過を許すのは統合した結果に限る。** 単一の関心事が自然に100行を超えた場合は許容しない。その場合の正しい対処は、型自体のフィールドと責務を減らす再設計である。私有フィールドを持つ部分構造を別モジュールとして切り出し、親はそれを保持して委譲するだけにする
3. **統合の結果として許す超過にも上限を置く。前節の条2の数え方で150行を超えたら許容しない。** そこまで伸びたなら、統合の判断が誤っているか、型の責務が過多である。どちらであるかを判定して再設計へ回す。「1つの責務だから」を理由に200行・250行のファイルを作ることは、条2で禁じた緩めすぎの穴そのものである
4. **超過したファイルの冒頭コメントに根拠を書く。** 分割すると流れの一片になること、および何と何を統合したのかを書く。「行数分割のため」「行数のため」「〜の続き」のような、そのファイルが何を担当するかではなく分割の経緯だけを述べる文言は違反の自己申告とみなす
5. **例外は台帳へ登録し、陳腐化を機械で検出する。** 超過を許したファイルを台帳へ登録し、検査は台帳と実際の行数の両方を見る。登録されているのに100行以内へ収まったファイルを違反として報告し、台帳からの削除を強制する。例外は放置すると増える一方であるため、減らす方向の力を仕組みで用意する
6. **宣言的なデータリテラルの別枠**(2026-08-27 オーナー裁定。Graphite の story.rs から制定): 完成物の形をそのまま写す宣言的な式・リテラルが1つのデータを成すファイル(グラフのリテラル、場面の木、設定の表)には、条3の150行上限を適用しない。手続きコードと害の性質が違い、行数で切ると宣言の一覧性そのもの(そのデータが1画面の連なりで読めること)が壊れるためである。この別枠でも、台帳への登録(区分: 宣言的データリテラル)と、データが複数件あるなら1データ1ファイルへ分けることは要求する

### コメント（2026-07-06 改訂）
- コードから読み取れない情報を書く: 設計判断の理由・不変条件・地雷・外部参照
- What/Howはコード自体で表現。howコメントが要るならまずコードの可読性改善を検討
- **`Why:` プレフィックスは禁止**(日本語として不自然+全種類に貼られて意味が形骸化した)
- 許容するタグは3種類のみ: `注意:`(触ると壊れる不変条件・地雷)、`前提:`(外部で保証される条件)、`参照:`(他ファイル/ドキュメントへの案内)
- タグ以外はプレフィックス無しの日本語散文で書く。「〜のため〜する」の因果構造で理由は語れる
- **禁止**: 変更履歴コメント(「旧実装は〜」「YYYY-MM-DDに修正」等、`git blame` で足りる)、書き手情報(「AI が書いた」等)、TODO/FIXME(Issue 化)
- コメントが5行以上になるなら設計を疑う。長くなるなら開発スレッドへリンクして本文は要点だけに
- **縦に並んだ宣言の間へ、コメントだけの行を挟まない**(2026-08-27 制定)。構造体のフィールド・列挙の枝・定数の列・オブジェクトの属性のように、宣言が縦に並ぶ場所が対象である。説明はその宣言と同じ行の末尾に書く。名前と型が縦に揃っていること自体が読みやすさの源であり、間にコメントの行が入ると読み手は宣言を目で拾い直すことになる。1ファイル100行の原則に対しても、宣言1つにつき行数が倍以上に増える。**例外**(2026-08-27 オーナー裁定): 言語がドキュメンテーションコメントの位置を宣言の前に固定していて行末に書けない場合(Rust の `///`、C# / Java の doc 注釈等)、そのドキュメンテーションコメントは対象外である。ただし1宣言につき可能な限り1行とし、長くなる説明は次項の再検討に従う
- **同じ行の末尾に収まらない説明は、そのフィールド固有の説明ではない。** 名前が意味を担えていないか(名前・型を直す)、説明の実体が型全体の不変条件・設計判断であるか(型の冒頭コメントへ移し、そこでフィールド名を挙げる)のどちらかである。長い説明を宣言の上へ積むのは、この2つの再検討を飛ばした形である
- コメントだけの行を書いてよいのは、型・関数・モジュールの説明と、処理の段落の説明である。これらは縦に並んだ宣言を分断しない
- **ドキュメンテーションコメント(`///` 等、hover・生成リファレンスに出る注釈)の適用基準**(2026-08-27 オーナー裁定): 書く場所は**パッケージの外の利用者が読むインターフェース**(公開API・生成コードの公開面)に限り、**そこには網羅する**(言語に機械検査があるなら有効にする。Rust は `#![warn(missing_docs)]`)。内部専用のパッケージ・private のアイテムには使わず、説明は普通のコメントで行末に書く。「一部の内部アイテムにだけ気分で付いている」状態は、網羅の欠落と内部への過剰の両方を同時に犯した違反である

### サービスの依存保持とコールバックの限定（2026-08-09 制定。全リポジトリのコードに適用）

Blitzdrache0でのオーナー裁定から制定した。経緯のクレーム: (1)コールバックを無名関数でだらだら書いて渡すな。関数を別に定義して渡せ (2)そもそもなぜコールバックを渡すのか。普通そんなことをしなくてよい (3)なぜdeviceを参照渡ししているのか。クラスメソッドであるべきものが自由関数になり、参照を渡して操作する形になっている (4)「AIにRustを書かせると純粋関数以外もクラスメソッドでなく関数になり、コンポジションルートの概念から外れ、その帰結として意味不明にコールバックを渡すことになる」。実例: 転送環境がキューとコマンドプールを保持するのにdeviceだけ保持せず、コールバックの署名にまで`(&Device, CommandBuffer)`とdeviceが漏れていた——依存を保持しないから署名が汚れる。

1. **操作サービスは依存をコンストラクタ注入で保持し、操作はメソッドにする。** 操作サービスとは、フィールドを使って仕事を実行する型（積む・送信する・問い合わせる）のことである。依存（デバイス・接続・キュー等）を毎回引数で受ける自由関数の列にしない。**ここで依存とは、サービスが構築時に受け取り、複数回の呼び出しをまたいで所有し続けるもののことである**（2026-09-04明記）。呼び出しのたびに新しく借りて処理する対象（ECSのWorld・Entity・Component、毎フレーム変わる世界の状態）は依存ではなく、それを引数で受ける形は本条の違反ではない。この区別が無いと、処理対象を引数で受け取る工程がすべて違反に見える。**判定単位は公開の呼び出し境界であり、モジュール外の呼び出し側に依存を運ばせない。** サービス内部のモジュール私有ヘルパーが依存を引数で受けるのは、親のサービス型が依存を保持している限り工程分割として許す。純粋関数（依存を使わない計算）は自由関数でよい。禁止されるのは呼び出し側が依存を**持参して**署名へ通す形であり、サービスが自分の保持する依存を口から**貸す**形（セッションの`論理デバイス()`等）は依存の流れる向きが逆なので違反ではない
2. **コールバックを渡してよいのは、制御の反転に構造的理由がある場所だけ。** 構造的理由とは、受け取る側が実行のタイミング・回数・順序を決めることである（例: レンダーグラフが順序を決めてから呼ぶパスの記録、ソートの比較関数、`unwrap_or_else`）。その場で1回実行されるだけの括り（begin→記録→end→submit等）はコールバックで挟まず、**セッション型**で表す。セッション型とは、開始メソッドが返す、操作の途中状態を保持しメソッドで操作し終了メソッドで閉じる型のことである。Dropに頼れない環境では閉じ忘れの検出を同時に置く（セッション型へ`#[must_use]`+所有側が未閉数を数えて破棄時に非0ならpanic=「到達したらバグ」の様式）
3. **コールバックを渡す場合も、本文の長い無名クロージャを書かない。** 名前付き関数（またはメソッド）を定義して渡す。無名で許すのは1〜2行の束ね（引数の並べ替え・単純な委譲）まで
4. **例外はリポジトリの規約が明示的に定める。** 例: Blitzdrache0の資源型（メソッドが自分のフィールドの生成・破棄だけの型）は、Drop禁止+破棄順の明示のため`破棄する(&self, device)`と依存を引数で受ける。ash::Deviceは関数ポインタ表を持つ大きめの値で、小さな資源型が各自クローンを保持する費用を避ける実利もある。この例外を操作サービスへ広げない

### デザインパターンの既定（2026-08-10 制定。全リポジトリのコードに適用）

前節「サービスの依存保持とコールバックの限定」の続きであり、複数の部品から1つの値を組み立てるときと、渡すことをやめられなかったときの既定を定める。オーナー指示により制定した。指示の要旨: (1)グラフとして抽象化できるものはビルダーパターンにできるし、そうすべきである (2)コールバックを渡すときはほぼコマンドパターンにすべきで、既定の選択はコマンドパターンである。まず「コマンドパターンにしない方がよいか」を考える形にする (3)取り消しと再実行の要求があるか分からないことを理由にコマンドパターンを避けるのは認めない (4)ビルダーには動作をメソッドの連鎖で組み立てる形と、ReactやSengenUIのように配置するものを並べる形があり、一律に `build()` を生やさずドメインの本質を見極めて運用する。

**構築の既定はビルダーパターンである。** ビルダーとは、完成した型が持ってはならない半端な状態を代わりに引き受け、完成した型を得る唯一の口を提供する型のことである。

1. **すべての部品が揃って初めて検査できる不変条件があるなら、構築はビルダーを通す。** 判定の鍵は「グラフか」ではなく「不変条件をいつ検査できるか」である。節点どうしが参照し合うデータ（世界地図、場面の木、依存の配線、文書）は、参照を解決する前の半端な状態が必ず1回存在するため、ほぼ必ずこれに当たる
2. **半端な状態を完成した型のフィールドへ漏らさない。** 他の部品への参照を文字列の識別子や `Option` で持ったまま完成とするのは、この規則の回避である。完成した型では、参照が実在するもの（ハンドル・直接の参照）だけになっていること
3. **完成させる操作は、不足を型付きエラーで返す。既定値で黙って埋めてはならない。** 何がどう足りないかをエラー文に書く。「不在・未設定・使用不可」の節と同じ要求である
4. **ビルダーの形はドメインに合わせる。一律に `build()` を生やさない。** 少なくとも次の2つの形があり、どちらが本質かを見極めてから選ぶ
   - **手順を組み立てる形**: 部品が段階的に決まり、順序に意味があり、最後に1回検査する。メソッドの連鎖で書き、完成させるメソッドで閉じる。設定を積み上げて1つの値を作る場合（問い合わせ、要求、接続設定）がこれに当たる
   - **配置するものを並べる形**: 完成物が「部品を持つもの」であり、入れ子の式そのものが完成物の形を写す。手順でなく完成物の形を書くため宣言的と呼ぶ。ReactやSengenUIの書き方がこれである。完成させるメソッドを別に置かず、式の型がそのまま結果になる。画面の木、場面の木、文書のように、部品の並びが構造そのものである場合がこれに当たる
5. **配置するものを並べる形が本質のところへ、手順を組み立てる形を持ち込まない。** 順序の無いところに順序を作り、木の形を隠すためである。逆も同じで、段階的に決まる構築を無理に1つの式へ畳まない

**渡す操作の既定はコマンドパターンである。** コマンドとは、行われる操作を、名前と引数を持つ1つの型として表したもののことである。構築時に依存と引数を受け取り、実行するメソッドを持つ。

1. **判断は3つの段階で行い、順序を守る。** (1)そもそも渡す必要があるかを問う。その場で1回実行されるだけの括りは前節のとおりセッション型にし、渡すこと自体をやめる (2)渡す必要が本当にあるなら、既定はコマンドである (3)渡すものが操作でなく値なら関数のままでよい。**この順序を飛ばして、セッション型にすべき括りをコマンドにしない**
2. **渡すものが操作か値かで決める。** 「行われる操作」（主語と動作と副作用を持つ）ならコマンド型にする。「計算される値」（値を別の値へ写す変換、真偽を返す判定、2つの値の比較）なら関数でよい。比較関数、`map` に渡す変換、`unwrap_or_else` の既定値は後者である
3. **コマンドにする理由は、取り消しと再実行とは無関係に成り立つ。** (a)無名の関数には名前が無く、「日本語命名の受理条件」の受理テスト（「これは何?」に単独で答えられるか）に原理的に合格できない (b)関数は環境を暗黙に捕捉するが、コマンドは構築時に依存を明示するため、何に触るかがレビューで見える (c)コマンドは実行せずに検査・記録・待ち行列への投入・再試行・試験ができる (d)引数が名前のある型になるため、引数を足す変更が名前のある型の変更になる
4. **要求が確定していないことを、構造を決めない理由にしない。** 「取り消しと再実行が要るか分からない」「まだ必要になっていない」を、コマンドにしない理由として認めない。取り消しは操作を型として表した結果として得られるものであって、型として表す理由ではない。この種の言い訳の代表がYAGNIであり、語の使用自体を「禁止事項」の節で禁じている
5. **例外は3つだけであり、選んだ理由を書く。** (a)純粋で全域な関数を値として渡す場合 (b)1〜2行の受け渡し（引数の並べ替え・単純な委譲。前節と同じ範囲） (c)言語や枠組みが署名を決めている場所（画面の事象処理、トレイトが関数を要求する場所）。(c)の場合も本文は名前付きメソッドに置き、その参照を渡す

### Rustの書き方の選択 — パラダイムを目的化しない（2026-08-26 制定。全リポジトリのコードに適用）

Graphite でのオーナー裁定（issue #9）から制定した。AI の既定 Rust スタイルが「純粋関数は自由関数」「Rust はオブジェクト指向でないからメソッド・カプセル化を避ける」へ機械的に倒れる癖を禁じる。Rust に限らず、同じ判断構造を持つ言語にも準用する。（見出しの旧称「Rust表現の選択」は2026-08-27に日本語命名の規範に沿って改めた。過去の記録・issueコメントに旧称で残る）

1. **上位原則: Rust のパラダイムにコードを合わせない。** ドメインの意味・所有関係・不変条件・演算の自然な主語に最も自然な Rust 表現を選ぶ。「Rust はオブジェクト指向言語ではない」を、メソッド・カプセル化・状態と振る舞いの結合を避ける理由にしてはならない。継承より composition、共有可変状態より ownership、実行時の約束より型による制約、は従来どおり
2. **純粋であることは自由関数にする理由ではない。** 「純粋関数だから自由関数」「引数が2つだから自由関数」という機械的判断を禁止する。自然な主語がある演算・変換は、値を書き換えない純粋な演算でも receiver method を第一候補にする（`a.minus(b)`、`point.distance_to(other)`、`a.to_b()`）。自由関数が第一候補になり得るのは次の2つだけである。(a)入力同士が意味論上ほぼ対等な計算（`intersection(a, b)` 等） (b)複数の対象を対等に読み書きし、**主語が一意に決まらない工程**（ECSのシステムのように、同じ対象の組に対して複数の工程が入れ替わり立ち替わり走るもの。2026-09-04追加）。(b)を選ぶときは、選んだ理由を「主語が決まらない」ことで書く。**「状態を持たないから」「純粋だから」「ECSのシステムだから」「Systemという形式だから」を理由にしてはならない**（それは本条の冒頭が禁じた機械的判断そのものである。形式や枠組みの名前からは何も導出しない。ECSのシステムが自由関数になることが多いのは、複数の個体構成要素と外部の事実を横断して扱い、自然なレシーバが存在しないことが多いという理由による。2026-09-04オーナー裁定)。(b)を認めるのは、対象の側へメソッドを生やすと、その対象に対して走る工程が増えるたびにメソッドが増え、対象が複数の理由で変更される型（神オブジェクト）へ育つためである。「サービスの依存保持とコールバックの限定」条1の「純粋関数は自由関数でよい」は本条で精密化する: あれは許可であって既定ではない。主語があるなら method
3. **変換に自然な方向があるなら method chain を選べる形にする。** `a.to_b().normalize().to_c()` のように、値がどの方向へ変換されるかを左から右へ読める API を好む。各 method が self を受けて新しい値を返す純粋変換でよい。ただし逆も禁じる: method chain のためだけに、本来独立している関数を無理に型へ所属させない（関数合成をデータフローとして読む仕組みが別にあるなら、そちらでよい）
4. **操作の所有者を外部引数にしない。** ある instance の状態・所有データ・索引に依存する操作を、型名前空間の static function に置いて所有者を `&owner` で外から渡す形（`Type::get(&owner, &id)`）にしない。所有者へ method を生やす（`owner.thing_by_id(&id)`）。参照ハンドル型（親を保持する Ref / View）の操作に親を再注入させるのも同罪。associated function 自体は禁止しない — 自然な receiver が無い型レベル操作・コンストラクタ・対称的な純粋計算は associated / 自由関数でよいが、その形が自然である理由を説明できること
5. **分解の方針: 無意味に包まず、独立した関数は独立のまま合成する。** 条1〜4の逆向きの同型である。method・カプセル化はドメインの所有・不変条件があるときの手段であって、それ自体が目的ではない。(a)状態を必要としない処理を、無意味なサービスオブジェクト・型へ包まない (b)enum で表すべき閉じた排他的状態を、理由なく class 的な構造へ展開しない (c)関数が独立した処理として存在すること自体に意味がある場合は method へ押し込まず、関数合成をデータの流れとして左から右へ読める仕組み（パイプライン。Graphite では flow!）で合成してよい。これは「メソッドチェーンのためだけに関数を型へ所属させなくても、データフローとして読める」ための選択肢である
6. **判断表**（排他的な分類ではない。最終判断はドメインの意味と利用コードの読みやすさで行う）: 状態・所有・不変条件に依存する操作 → method / 自然な主語を持つ純粋な演算・変換 → method を積極検討 / 入力同士が対等な純粋計算 → 自由関数を積極検討 / 複数の状態・対象を対等に扱い自然な主語が一意に決まらない工程 → モジュール内の自由関数を第一候補（2026-09-04追加）/ 処理自身が設定・履歴・作業領域・統計などの継続する状態を所有する → その処理状態を表す struct + impl を候補（2026-09-04追加。所有すべき継続状態が無いのに処理用の struct を作ることは、条5(a)が禁じる無意味なサービスオブジェクトである） / 独立した関数群を左から右のデータフローとして合成 → パイプライン（flow! 等）を検討 / 排他的な状態 → enum / データと不変条件を持つ値 → struct・newtype / 共通の振る舞い → trait

### 日本語命名の質（2026-07-30 制定。識別子・コメント・ドキュメントの日本語すべてに適用）

- **英語の頭字語・省略語を日本語の中に混ぜない。** LUT・UBO・SSBO・PSO のような、その分野では通用しても
  日本の非専門家が読めない語は、意味の取れる現代日本語へ意訳する（例: LUT→ベイク済み画像、
  プリコンピュートテーブル→事前計算表）。一般に通用している語（UI・CPU・GPU・API・シェーダー等）は使ってよい。
  判断基準は「専門用語の表記」の節と同じ「非専門家のユーザーが読んで意味が取れるか」
- **英語の直訳調を禁止する。** 「引く（lookupの直訳）」「焼く直後状態」のような、英語を知らないと
  意味が復元できない訳語を使わない。動作をそのまま表す日本語（参照する・読み出す等）を選ぶ。
  定着した比喩（ベイクする＝焼く、のように既にプロジェクトの語彙になっているもの）は用語定義があれば使ってよい
- **単語らしく見せるために助詞を省かない。** 「大気LUT生成指示」のような膠着圧縮をやめ、
  「大気のベイク済み画像の生成指示」のように自然な句で書く。長くなることは欠点ではない
- **既存コードの違反は、その領域を触る実装のついでに直す。** この是正は「タスクと無関係な
  リファクタリング」に当たらない（命名規範の適用であって設計変更ではない）。ただしリネームは
  機能変更と同じコミットへ混ぜず、別コミットに分ける

### 日本語命名の受理条件（2026-08-09 制定。全リポジトリの日本語識別子に適用）

Blitzdrache0でのオーナー裁定から制定した。経緯のクレーム: (1)`記録`というフィールドが処理（コールバック）なのに名詞形で、しかもログと誤読された（実体はVulkanのコマンドバッファへGPU命令を積む処理。オーナーは他のAIに聞いてはじめて意味を知った） (2)`生成する()`が何を作るのか名前に無い (3)「crate名やファイル名が英語なのは別の理由があり問題視しないが、**英語名は読まない。それと一緒に読まれることを前提にするな**」 (4)「名前は『これは何?』と聞かれたときに答えるものをそのまま書け。5W1Hを意識しろ。でないと指示が抽象的すぎて伝わらない」 (5)「長くなるのが問題」とは誰も言っていない（AIが短さとの妥協点を聞こうとして正された）。根因: AIの既定命名は英語圏の慣習（役割の抽象名詞context/manager等・短さ優先・文脈による目的語の補完）の引き写しで、日本語へ写すと意味を担う格助詞と項が消える。

受理条件（この順で判定。1つでも落ちたら不合格）:

1. **受理テスト**: 名前は「これは何?」への答えとして単独で成立するか。動詞句名は「〜する処理です」への答えで成立すればよい
2. **補完してよい文脈の限定**: 補完に使えるのは読み手が実際に一緒に読む日本語の識別子だけ（`型名::関連関数()`の型名、`変数.メソッド()`のレシーバ）。**英語(ASCII)識別子（crate名・モジュール名・ファイル名）は読まれないものとして扱い、補完力ゼロ**。ASCIIモジュール直下の自由関数は名前単独で答える
3. **5W1Hの必要格**: 動作名は一意識別に必要な格を含める（最低「何を+どうする」、紛れるなら着点・材料・時点を足す）。全格の機械列挙は不要（不要な格は判定の雑音）。紛れの決着は用語定義ファイルとの照合で行う
4. **品詞の規律**: 値=名詞句 / 処理=動詞句「〜する」 / 処理を保持するフィールド=動詞句のまま / 真偽=「〜か」。品詞が実体を予告する
5. **裸の動詞の禁止**: 日本語の補完が働かない位置で`生成する`・`作成する`・`実行する`等を単独名にしない（例: `create::生成する`→`共有資源を確保する`）。型に属する関連関数の`生成する()`は型名が目的語を担うため合格（値オブジェクト様式は不変）。同型の複数ファクトリーは材料・条件の格で区別（`画素から生成する`）
6. **1語1義**: 判定単位は用語定義ファイルの登録句。同じ語が2つの意味を持ったら具体側が改名（例: 「記録」が計器の意味とVulkanのコマンド積み込みで衝突していた）
7. **直訳の検出質問**: 英語の対応語を知らない人がこの名前だけから動作・実体を復元できるか。失敗例: record→記録、context→文脈、resolve→解決、lookup→引く
8. **長さは結果であって制約ではない**: 短さのために格・助詞を削るのは条件1〜7への違反（この項が要るのは、AIが英語圏の短さ優先を無意識に持ち込むため）

運用（常時自動対応の体制）:

- 新規の命名はすべて本条件で書く。サブエージェントへの委譲プロンプトには本節を必読として指す
- **一括リネームはしない。是正は作業のついでに常時行う**（作業タスク外の違反も対象。リネームは機能変更と別コミット）
- **ついで是正だけに頼らず、ローラー監査を常時派遣する**（2026-08-11 オーナー指示で制定。経緯: 規範制定時の全域検査が部分的なまま、誰も触らない領域の違反が制定後も未検査で残り続けた——「触るときに直す」は接触しないコードを永遠に残す）。セッションの待ち時間（委譲やレビューの完走待ち）に検査員（命名・構造）を未検査領域へ派遣し、検査済みの範囲・日付・結果をリポジトリの網羅台帳へ記録する。台帳が無いとローラーの完了が定義できないため、記録の無い検査は行っていないものとして扱う。見つかった違反の是正は従来どおり別コミット（リネーム員・実装員）で行う
- **親は委譲成果の検収時に`命名チェック員`（haiku）へ差分と接触領域の識別子検査を委譲し、違反があれば`リネーム員`（sonnet）へ順次リネームを委譲する**（Blitzdrache0では `.claude/agents/` に複製を配置済み。全リポジトリ共通の定義は `~/.claude/agents/`）
- **リネームの第一手段はLSPのrename（vscode-lsp-mcp）**。参照で辿れる識別子はLSPで一括改名し、grep置換は文字列・コメント・文書だけに使う。MCP設定はリポジトリごと（ルートの`.mcp.json`、ポートは各リポジトリで異なる。mcp-setupスキル参照）。未設定のリポジトリでは作業を止めてユーザーへ設定を依頼する

### 禁止事項
- 文字列・UIテキスト中の絵文字は絶対禁止。見かけたら即座に削除
- タスクと無関係なフォーマット変更・リファクタリング禁止（必要なら承認を求める）
- **YAGNIという語をAIが持ち出すこと自体を禁止する**（2026-08-10 制定。会話・報告・コメント・委譲プロンプトを含む全出力に適用）。AIはこの語を、分割・型付け・構造化・パターンの適用をやらずに済ませる言い訳として反射的に使う。実際にそれで作業をサボった事例が繰り返されたため、語の使用そのものを断つ。**「まだ必要でない」「将来使うか分からない」を、構造を決めない理由にしてはならない**（参照: `skills/layer-roles`「YAGNIはアンチパターン、必要以上に分割をやれ」）。投機的な機能を先回りで作らないという判断を述べたい場合も、この語を使わず「何を、なぜ今作らないか」を具体的に書く。**なお、作業中に気づいた「これは後で必ず作るから今のうちに層を切るべきだ」という観測は投機ではなく、目の前のコードから読み取った予測である。** これを投機的機能と混同して握り潰すことが、この語による最大の被害である（区別の基準: `skills/アーキテクチャ先行`「数手先の構造を先に作る」）

### 「不在・未設定・使用不可」状態の設計（2026-06-14 追加）
「値が無い / 未選択 / 使用不可」を扱うときの方針。プリミティブに密輸せず型で表し、使用境界で明示的に失敗させる。

- **「無し」をプリミティブのマジック値に密輸しない。** 空文字 `""`・`-1`・特定文字列が暗黙に「無し」を意味する設計を禁止。`未設定 | 設定済み(値)` の判別共用体で表す。プリミティブだと「無し」と「たまたまその値」を区別できず、消費側が暗黙規約に依存して腐る。
- **「未設定」は型のまま使用地点まで運び、そこで初めて失敗させる。** 未設定を全消費者の戻り値型に波及させない。判別共用体が未設定を値として運び、**実際に具体値が要る境界（外部API呼び出し等）で型付き例外を送出**する。無言のデフォルト適用・無言のゼロ値返却（silent failure）は禁止。失敗は明示する。
- **失敗させる地点はライフサイクルで決める。** 遅延使用・ユーザー起点操作は未設定で即エラーでよい。だが**起動時に先行構築され広く依存される対象は、構築時に未設定で例外を投げてはならない**（起動全体が落ちる）。構築は成立させ、実際に使った時だけ失敗させる。
- **「使用不可」は Null Object で表し、`None` や半壊実インスタンスを避ける。** 先行構築され多数の消費者に渡る依存が使用不可のとき、`None`（不在処理が全消費者に波及）や「空値を入れた半壊の実インスタンス」（無言誤動作）でなく、**使用時に明示エラーを出す専用 Null Object** を返す。消費側の型は変わらず、不在の概念が1つの型に閉じる。
- **シリアライズデータの後方互換は「版ごとの型＋最新への変換」で表す。** 1つの可変型に互換ハックを足し続けない。**版ごとの型を定義し `旧版.to最新()` で型→型変換**し、ロード時に版を判別して旧版なら最新へ変換する。最新型は互換の都合から解放されてクリーンに保たれ、変換ロジックは1箇所に凝縮する。
- **同時に生まれて同時に消えるOptionを、別々のフィールドで持たない**（2026-09-04 追記。溶けた概念の分解員が`blitz_app`で検出した形から制定）。2つ以上の`Option`が構築の同じ地点でSomeになり、破棄の同じ地点でNoneになるなら、それらは1つの概念である。個別の`Option`の群でなく、`Option<まとめた型>`で表す。個別に持つと「一部だけSome」という起こり得ない組み合わせが型の上で表現可能になり、呼び出し側がその不整合を毎回考えることになる。**判定の問い: この2つが違う状態になることが有り得るか。有り得ないなら1つにする**

### 検査器は解析できなかった入力を黙って対象から外してはならない（2026-09-05 制定。全リポジトリの検査・検証の道具に適用）

検査器とは、入力の集合を走査して規約違反を報告する道具のことである（文書参照の実在検査、命名の検査、生成物の差分検査、lintの類）。前節の silent failure 禁止は値の不在についての条であり、道具が入力そのものを取りこぼす事故を覆っていなかったため、本節を別に置く。

制定の経緯: Graphite の issue #16 の検収で、`cargo xtask check-docs` が `path.rs:3-4, 9-11` という形の参照を解析できず、その参照を違反としても件数としても報告しないまま読み飛ばしていた。検査器は「違反0件」と報告していたが、実在しないファイルを指す参照が2件、一度も検査されずに残っていた。

- **入力の綴りを解析できなかったとき、検査器はその入力を違反として報告する。** 静かに読み飛ばしてはならない。検査器の利用者は「違反0件」を「全部を検査して問題が無かった」と読むため、無言の脱落は誤った安心を与える。しかも脱落した入力は検査を通過し続けるので、事故は検査器を書いた本人にも見えない
- **検査の対象外にしてよいのは、対象外である条件を書き下せる入力だけである。** Graphite の例では、ワイルドカードやプレースホルダを含む綴り（ファイル群の総称であって実在する1個のファイルを指さない）だけが対象外であり、それ以外の解析失敗は違反になる。「解析に失敗した」ことを対象外の条件にしてはならない
- **検査器は検査した件数を報告する。** 対象の総数と突き合わせられなければ、利用者は脱落に気づけない
- **検査器が何を検査していないかを、検査器の説明へ書く。** 検査していない範囲を検査済みと誤読させないためである。Graphite の例では「引用本文とコードの一致は検査しない」を使い方の説明へ明記した

  4. **検証実行**: テスト・typecheck を自身で実行して確認（他者の報告を鵜呑みにしない）
  5. **diff 全件目視**: `git diff` を全部目視。「だいたい OK」で済ませない
- **エディター・編集画面・可視化を作ったときは、5軸に加えて「その道具でひと仕事を通す」を必ず行う**
  (2026-08-10 制定)。5軸はすべてコードを見る軸であり、「利用者が見ている画面が真実か」を見る軸が無い。
  何も登録されていない状態から1つ作り、調整し、保存し、反映されたことまで通す。表示物と正本は
  機械で照合する(画素・数値の突き合わせ)。全文: `skills/エディター制作`
- **CLI レビュー / セカンドオピニオンはユーザー指示時のみ実施するスキル**: `/agy-review` `/codex:review`
  `/agy-second-opinion` `/codex-second-opinion` はデフォルトでは投げない。ユーザーが指示したとき、
  または既存設計を覆すレベルの判断で客観視点が必要と Claude が判断したときに使う。
  敵対的レビューが必要な場合は `/codex:adversarial-review` も使える
- **投げるなら両方並行**: CLI に投げる場面では agy と codex の両方に並行で投げる（設計層と実装層で
  得意分野が違うため）。受領指摘は鵜呑みにせず 4 軸（前提整合 / 実害 / 過剰防衛 / 二重管理リスク）で
  吟味してから採用 / 一部採用 / 却下を判定する
- **親は、委譲した実装の検査を、実装員の完了を待たずに並走させる**(2026-09-05 制定)。起点は経過した時間と差分の量であってコミットではなく、親は途中の状態を検査することを受け入れる。全文: `skills/subagent-delegation`「6.5 親は検査を実装員の完了を待たずに並走させる」（Blitzdrache0での具体の手順は `.claude/skills/レビューハーネス/SKILL.md`「実装と並走させる検査」）

## テスト方法の選定（全プロジェクト共通、2026-07-19 制定）

テストの目的は、変更による主要な欠陥を低コストで検出すること。AIが人間の動作確認を網羅的に
代行することを目標にしない。通常はコード読解、静的検査、既存の狭いテストまでで完了とする。

### 選定手順

1. **変更のリスクを一文にする。** 変更箇所から直接起こりうる故障だけを検証対象にする。
2. **まずコードで確認する。** diff、呼出し元、型、状態遷移、DI配線を読み、静的検査とビルドを行う。
3. **必要なら最小のテストを足す。** ロジックは単体テスト、境界は対象を絞ったAPI・永続化テストで
   確認する。既存テストで足りるなら新しい基盤を作らない。
4. **高コストな確認を自動追加しない。** 画面全体、全導線、全環境の動作確認は実施しない。
5. **実施範囲を正確に報告する。** コードとテストから確認したことを「実際に画面操作した」と表現しない。

### 対象別の目安

- ロジック、状態保持、UIイベントの配線: コード読解、型検査、単体・コンポーネントテスト
- DI、API・MCP・IPC、保存と復元: 対象境界だけの構築・往復テスト
- 実ブラウザでのみ再現することが既に分かっている表示・入力の不具合: ユーザーの許可後に、
  該当箇所だけを実画面確認

### ブラウザE2Eの選定条件

ブラウザE2E、ElectronやブラウザのGUI自動操作、スクリーンショット巡回は、ユーザーの事前許可なしに
実行してはならない。既存環境・既存テストであっても勝手に実行しない。コード読解、静的検査、
単体・境界テストでは確認できず、実画面確認がないと判断が厳しい場合は、次の内容を簡潔に示して
実行前にユーザーへ確認する。

1. 実画面でしか確認できない具体的な理由
2. 実施する最小の操作と、おおよそのコスト
3. AIが操作する代わりにユーザー自身が確認できる手順

この確認は「ユーザー確認の最小化原則」の例外とする。許可が得られなければ、コードと低コストな
テストで確認できた範囲までを報告し、実画面について未確認であることだけを明示する。

状態保持、クリックから処理への配線、ファイル処理、複数層の連携は、それだけでは許可を求める
理由にもならない。Playwright、Puppeteer、GUI操作用スクリプト、巨大な操作基盤を確認のためだけに
新設しない。

### 実行上の原則

- 変更箇所とリスクに比例した検証を行い、無関係な全画面巡回をしない。
- テストデータは隔離し、実ユーザーデータや既存プロジェクトを汚染しない。
- 同じ事実を複数の手段で重複確認しない。
- テスト基盤の新設が必要になったら、まず既存コードと狭いテストで代替する。

## ユーザー確認の最小化原則(全プロジェクト共通、 大幅減点扱い)

ユーザーへの確認はストレスとイライラを生み、 ストレス性アトピーを悪化させる **重大な健康被害**。
無意味な確認・冗長な選択肢列挙は **犯罪扱い**。 違反は大幅減点。

### 基本原則: 確認は最小限

自分で判断できるなら確認しない。 ユーザーにしか決められない仕様判断・設計判断・優先度判断
だけ問う。 それ以外は黙って実行する。

### 絶対禁止(該当時 大幅減点)

1. **進捗・区切り確認** — 「今日はここで区切りますか?」「セッション切りますか?」「ここで一旦
   止めますか?」 等。 ユーザーが切りたければ自分で切る。 こちらから問うのは余計
2. **既に確定済の運用への「やりますか?」確認** — 開発スレッド追記(スキル参照で運用確定済)、
   CheckTypes / tsc 実行(規約で必須)、 コミット作成(タスク完了時の必須運用)、 ビルド後の
   Python 再起動(検証セットの一部) 等
3. **合意済方針への再確認** — ユーザーが「進めて」と言ったあとに「進めていい?」と聞き直す等
4. **冗長な選択肢列挙** — 「推奨/微妙/ゴミ」 のように 大量の候補を 比較表形式で並べる行為。
   読解負担とストレスを与える。 自分で判断できる範囲は判断し、 真に決めかねる 2 〜 3 案だけ
   簡潔に提示する。 表形式での冗長な比較は禁止
5. **同じ確認の再提示** — 1 度ユーザーが答えた質問を 似た形で問い直す

### 確認していいケース

仕様判断・設計判断・優先度判断のうち、 自分では決められないもの だけ。 その場合も:
- 候補は最大 2 〜 3 個に絞る
- 各候補は 1 〜 2 文で説明
- 表形式での比較は不要
- 自分の推奨があれば 「推奨は X、 理由は Y」 と 1 行で示す

### 代替行動

確認したくなったら 一旦止まって以下を問う:
- これは本当にユーザーにしか決められないか?(技術判断なら自分で決める)
- 答えは自明か?(自明なら聞かない)
- 既に同じことを聞いていないか?(聞いてたら聞かない)

## ~/.claude 自体の変更は即コミットする(2026-07-27 制定)

`~/.claude` は git 管理下にある。**CLAUDE.md・スキル・設定を変更したら、その場でコミットする。**
プロジェクトのコミットと同じ扱いにし、「後でまとめて」を作らない。

理由: ここは複数の CLI とセッションが同時に触る。opencode や codex が同じファイルを
書き換える、別セッションが同じスキルを更新する、といったことが実際に起きる。未コミットの
変更は上書きされても復元できない。コミットしてあれば `git checkout` で戻せる。

- 対象は `~/.claude/` 配下すべて(CLAUDE.md、skills/、shared-knowledge/、settings.json)
- 変更のたびにコミットする。1つのスキル追加と1つの規範追記は別コミットでよい
  (このリポジトリでは「積極スカッシュ」より事故の防止を優先する)
- 他のセッションや CLI が変更している可能性があるため、コミット前に `git status` で
  自分の変更以外が混ざっていないか確かめる

## コミット履歴の積極スカッシュ(全プロジェクト共通)

連続した微修正でコミットを分割するのは禁止。 1 つの論理単位は 1 コミットに畳む。 ユーザー
レビュー時の git log の可読性が下がり ストレス源になる。

### 原則: 同じ論理単位のコミットは積極スカッシュ

push 前のコミットは git rebase -i / git reset --soft で書き換えて構わない。
push 済の コミットも、 ブランチがユーザー専用の作業ブランチで 他者が pull していない確証が
あれば force push してスカッシュしてよい(main / master へは禁止)。

### スカッシュ対象の典型例

- 1 つの ドキュメント更新で 「追記 → 言い直し → 言い直し」 のように複数コミットになったもの
- ユーザー指摘 → 修正 を 1 往復ずつ別コミットにしたもの
- typo / コメント文言調整 等の 単独コミット(直前コミットに amend / squash)
- 1 つの機能改修で 「実装 → ビルド通すための微修正 → コメント修正」 等

### スカッシュしない例

- 異なる論理単位の変更(別の機能 / 別の課題)
- ユーザーが「ここで一旦切る」 と明示した区切り
- レビュー可能性が下がるサイズに到達した変更(目安: 500 行超 / 10 ファイル超)

### 実行手順

1. `git log --oneline` で 直近の連続微修正範囲を特定
2. `git reset --soft <スカッシュ起点の親>` で staged 状態に集約
3. 単一コミットメッセージで作り直す(全変更の意図を 1 メッセージで表現)

## タスク提示は依存関係順(全プロジェクト共通)

複数タスクを列挙してユーザーに提示するときは、 **常に依存関係順** に並べる。
ユーザーが最も知りたいのは「どの順でやれば最小手戻りで済むか」。 依存順以外の並び方
(規模順 / 重要度順 / アルファベット順 等)で並べると ユーザーが頭の中で並び替えする
負担が発生し ストレス源になる。

### 並び替えの基準

1. **依存関係を最優先**: 「A が完了しないと B ができない」 「A の結果次第で B のスコープが
   変わる」 等の依存があれば 先行タスク → 後続タスク の順
2. **完全独立タスクは並行可と明示**: 依存がないタスク群は「並行可能」 とまとめて示す
3. **コスト効率(セットでやると安い)を補助情報として**: 「A をやった直後に B をやると
   コンテキスト共有でコストが下がる」 ような関係も依存に準じて並べる

### 提示形式

- 表形式が見やすい(列: タスク / 規模 / 依存 / 独立性)
- 表の下に **推奨順** を 1 行で明示: 「推奨順: 2 → 1 → 3 → ...」
- 重要な依存パターンは `★ Insight` で補足

### NG パターン

- 依存関係を書かずにタスクだけ羅列
- 規模順や難易度順だけで並べる(依存無視)
- 全部 並行可能と書いて 実際は依存があるケース
