# 実装ハーネス

## これは何か

実装ハーネスとは、実装の作業を層ごとの専任実装員へ振り分け、ファイル境界で並列に走らせ、レビューハーネスの検収へ渡すまでの手順のことである。1体の汎用実装員へ丸ごと渡す形と違い、担当領域と必読ファイルが定義側に固定されているため、委譲プロンプトが短くなり、低コストのモデルでも規約に沿った実装が出る。

## 担当の選び方

触るパスから担当を選ぶ。

| 触るパス | 担当 | モデル |
| --- | --- | --- |
| `crates/editor_server/src/resource` `contract` | 型契約実装員 | sonnet medium |
| `crates/editor_server/src/routes` `storage` | サーバー実装員 | sonnet medium |
| `editor_web/src/ツール/*/編集モデル` | 編集モデル実装員 | sonnet medium |
| `editor_web/src/ツール/*/操作コマンド`、`editor_web/src/ヘッドレス` | 操作コマンド実装員 | sonnet medium |
| `editor_web/src/ツール/*/画面`、配線 | 画面実装員 | sonnet medium |
| `crates/blitz_sim` `crates/blitz_collision` | 物理実装員 | Opus medium |
| `_doc/` の生存型文書、`README.md` の索引 | 文書実装員 | sonnet medium |
| 移動・分割・整形の取り込み(判断が残っていない作業) | 機械的置換員 | sonnet low |
| 日本語識別子のリネーム | リネーム員 | sonnet medium |
| 上のどれにも収まらない、または複数層を1人で通す必要がある | 実装員 | Opus medium |
| 難易度が特に高い(設計と実装が絡む・前例が無い) | 実装員Fable版 | Fable low |

**Fable版は既定にしない。** Fableは強いが高価であり、Opus mediumで足りる作業に使うと費用だけが増える。Opusで一度出させて、質が足りないと分かってから切り替える。

## 並列化の切り方

- **ファイル境界で分担を切る。** 同じファイルを2体に触らせない。層で切ると境界が自然に分かれる
- 各体のプロンプトへ、相手の担当範囲を「触るな」として書く
- 型契約は先行させる。契約が確定してから、それを使う編集モデル・操作コマンド・画面を並列で走らせる(契約が動くと全員がやり直しになる)
- Opus 5とFable 5.1で動く実装員は同時4体までにする。それ以上を出すとレート制限で落ちる。実装員はビルドを走らせないため、体数がビルドの置き場を増やすことは無い
- 親は委譲中、同じファイル群を触らない

## 委譲プロンプトの必須要素

担当領域と規約は実装員の定義が持っているため、プロンプトには**そのタスク固有のもの**だけを書く。

1. **背景1段落**: 何を達成するか。どの設計正本の何番の判断に当たるか
2. **対象の設計正本の絶対パス**(あれば)
3. **触ってよい範囲と、触ってはいけない範囲**(並列時は他の担当の範囲を明示)
4. **完了条件**: 何が動けば完成か。試験で何を固定するか
5. **ビルド員の識別子**(実装員は `cargo` と `npm run` を走らせず、段階のコミットごとにビルド員へ依頼する。タスク固有に回す検査があればその名前も)
6. **コミットの可否と粒度**(刻んでから畳ませる。中断で成果が消えないため)。**作業の段階が成立したら即コミットする**と書く。目安は「1つの作業の段階につき1コミット」であり、段階の切り方は委譲プロンプトが示す着手の順序に合わせる
7. **走行中に届く指摘の扱い**: 親は、委譲プロンプトに、親が作業ツリーの差分を途中で検査しSendMessageで指摘を送ることがあると書く(レビューハーネス「実装と並走させる検査」)。実装員はいまの作業の段階を終えてから、次の段階へ移る前にその指摘を処理する(途中で割り込ませない)。指摘が後の段階で消える途中経過に対するものなら、実装員は「後の段階で消える」と返答してよい。実装員は、処理の結果を完了報告に「走行中に受けた指摘とその処理」の節として書く
8. **報告の形**: 変更ファイル・検証結果・設計判断・未完了の申告・走行中に受けた指摘とその処理

## 受領後にすること(省略禁止)

1. **ビルド員が返した最後の検証の結果を親が判定する。** 実装員の報告に引用された結果と、親へ届いた結果が一致するかを見る。届いていなければ親がビルド員へ依頼する
2. **`git diff` を全件目視する。** 「だいたいOK」で済ませない
3. **レビューハーネスを回す**(`.claude/skills/レビューハーネス/SKILL.md`)。走行中に並走させた検査があるなら、親はここで最後の差分で1回だけ起動し、保留の印が消えているかと走行中の指摘が処理されているかを見る
4. **合否を親が確定する。** チェック員の報告は材料であり、判定ではない
5. 実機での確認が要る種類の変更(エディターの見た目・操作)は、オーナーの試用へ回す。親が実画面を触るのは既定では行わない

## 検証はビルド員が回し、ビルドの置き場は本体の1つだけにする(2026-09-05制定)

**ビルドと検証は監督者である親の責務であり、実装員の責務は実装である**(2026-09-05のオーナー裁定「ロックになるならそれは監督者のあなたがやるべきです。実装員は実装が責務でしょ。ビルドは違う」)。制定の経緯: 親が実装員ごとに検証を走らせ、排他ロックを避けるために作業ツリーごとにビルドの置き場を切った結果、1本15〜20GBの置き場が5本でき、Cドライブの空きが62GBから29GBまで減った。同じ日にオーナーが「なんでtargetが4種類もあるの」と指摘した。

親はこの責務を、常駐の `ビルド員`(`.claude/agents/ビルド員.md`)1体へ預ける。サブエージェント同士は SendMessage で直接やり取りでき、送った相手は再開される(2026-09-05に親が2体で往復を実測した)。

- **親はセッションの最初にビルド員を1体起動して待機させ、委譲プロンプトにその識別子を書く。** 2体目を起動しない。1体しか居ないことが排他ロックの代わりである
- **実装員は `cargo`(`fmt` を除く)と `npm run` を走らせない。** 実装員は段階のコミットごとにビルド員へ SendMessage で検証を依頼し(作業ツリー・ブランチの先端・返信先)、返信を受けて直す。定義に書いてある
- **ビルド員は本体の `C:/devs/Blitzdrache0/target` を共有して回す**(`CARGO_TARGET_DIR=C:/devs/Blitzdrache0/target`)。依存クレートは1回しか組まれず、ブランチごとに組み直すのはワークスペース内のクレートだけになる。`target-<名前>` を作らない
- **記録を書くのは道具であり、ビルド員ではない。** `cargo xtask verify` 自身が各段の出力を1文字も落とさず `<出力の木>/verify-logs/` のファイルへ書き、その絶対パスを表示する([Issue #82](https://github.com/megaDenryu/Blitzdrache0/issues/82))。ビルド員は終了コードとそのパスだけを依頼者と親の両方へ返し、要約も引用もしない(2026-09-05のオーナー指摘「ビルドの結果は実装者が直接見れないと困る」)。実装員と親はそのログを自分で読む。親は判定だけを行う(既知の失敗との突き合わせ、閾値の書き換えの有無、報告との一致)。親が自分で検証を回すのは、ビルド員が居ない短い作業だけにする
- **作業ツリーは作業ごとに切ってよいが、PRがマージされたら親が `git worktree remove` で外す。** スレッド終了のときに親は `git worktree list` を見て、残っているものの理由を後記へ書くか外す。ビルド員も終了のときに親が止める

## 中断からの復旧

- 委譲先が無言で死んだら、タスクの出力ファイルの更新時刻と `git status` で作業の痕跡を確かめる
- 作業成果はワーキングツリーに残っているため、新しい体へ「`git status` と `git diff` で現状を把握してから続行せよ」と引き継がせる
- モデルを変えたい場合も同じ形で引き継ぐ(既存の体のモデルは変えられない)
