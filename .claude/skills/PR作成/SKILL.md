# PR作成

## これは何か

Pull Requestの本文の書き方と、更新の手順を定める。

**PRの本文はオーナーが読む文書である。** オーナーは差分を1行ずつ追わず、本文を読んで受理するかどうかを決める。したがって本文は「何が起きて、なぜそれをしたのか」が本文だけで分かる形でなければならない。差分を見ないと意味が取れない本文は、書いていないのと同じである。

## コミットを指すときは、日本語の名前を付けたリンクにする

**コミットハッシュを裸で書かない。** `991850b1` という文字列は読み手にとって意味を持たない。何のコミットなのか、そこを見るべきかどうかが判断できない。

書く形は次のとおりである。

```markdown
[粗マスへの改称](https://github.com/megaDenryu/Blitzdrache0/commit/991850b1)で75ファイルを改めた。
```

- **リンクの文字列は、そのコミットが何をしたかを日本語で書く。** コミットメッセージの見出しをそのまま使ってよい
- 複数のコミットをまとめて指すときは、範囲ではなく1つずつ書く。範囲の表記(`a1b2c3d..e4f5g6h`)は読み手が中身を知る手段を持たない
- コミットの一覧を節として並べるのはよい。その場合も各行を上の形にする

同じことがissueとPRにも当てはまる。`#56` は番号だけでは何の話か分からないため、初出では `issue #56(Rustコード規約の使い分けの明文化)` のように内容を添える。

## 投稿の前に文章チェック員へ回す

**PRの本文は文章規範の適用対象である。** 投稿・更新の前に文章チェック員へ検査させる。省略しない。

委譲するときは、読み手が誰で、何を知らないかを渡す。オーナーがその作業を自分で追っていないなら、そう書く。読者テストの観点(その読者が本文だけで理解できるか)は、規約の機械的な当てはめでは出てこない。

## 作業を足したら本文を追記する

既存のPRへコミットを足したら、本文もその場で更新する。

- **初回に書いた「次にやること」「別のPCでやること」の類は、完了したら現在地を書き換える。** 済んだ項目が未着手のまま残っていると、読み手が誤った前提でレビューする
- 追加した作業は節を分けて書く。日付を見出しへ入れる(`## 2026-09-04の追加分`)
- **PRの主題が途中で変わったなら、冒頭でそう述べる。** 主題の変化を書かないと、読み手は無関係なコミットが混ざっているように見える
- 検証の表は現在の値へ更新する。古い数字を残さない

## 本文に書くこと

1. **概要**: 何を作ったか。設計正本があるならその場所
2. **主題が変わったならその宣言**
3. **検証**: 検査の名前と結果の表。失敗しているものは、その理由と本PRとの関係を書く
4. **受理の状態**: 「機械検証済み(試用可能)」か「受理済み」か。この2つを混ぜない
5. **作業の内容**: 節ごとに「何が起きて、なぜそれをしたのか」。コミットは上の形のリンクで指す
6. **次にやること**: 依存順に並べる

## 違反のサイン

- 本文にハッシュが裸で並んでいる
- 「別のPCでやること」が全部完了しているのに初回のまま残っている
- 検証の表の数字が、いま走らせた結果と違う
- 文章チェック員を通していない
- 節の見出しが「変更点」「その他」のように、何が起きたかを言っていない
