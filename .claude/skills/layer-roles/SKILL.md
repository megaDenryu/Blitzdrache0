# レイヤー役割規約スキル

ファイルの肥大化(数百行の責務同居)を、行数制限の意志ではなく**役割語彙の構造**で防ぐ。理論の背景は `~/.claude/shared-knowledge/design_layer_role_vocabulary.md`。本スキルは自己完結しており、どのリポジトリでも単体で適用できる。

## 原理(要約)

1. **閉じた役割語彙**: レイヤーに存在してよいファイル種を有限個で列挙。「その他」枠なし。分類不能なコードは設計誤りのシグナル
2. **生成の隔離**: 生成コード(newの羅列、依存の組み立て)が一番かさばる。依存の束DTO+ファクトリを専用ファイルへ退去させる
3. **構築固定順**: 状態→資源→サービス→配線。後段は前段の構築済みインスタンスを直接参照でき、遅延評価やnullチェックの散在が消える
4. **昇格経路の事前指定**: 圧力→逃し先の表で分割の判断コストをゼロにする。判断コストゼロが、分割が実際に実行される条件
5. **契約の型化**: 必須プロパティ/網羅分岐でコンパイルエラー化+呼び忘れは実行時例外+違反サインの明文列挙+規範実装の指名

原則: **行数は従、役割純度が主**。分割単位は概念×役割の直積(ファイル名から両方読める)。

## 役割語彙の具体例(インスタンス化の見本)

対象リポジトリに役割規約文書があればそれが正本(下の場面1参照)。無い場合の出発点として、典型レイヤーの語彙例:

**Webサーバー層の例(8役割)**:

| 役割 | 中に書いてよいもの | 書いてはならないもの |
|---|---|---|
| 契約(DTO) | リクエスト/レスポンス型、直列化導出、単純検証 | ロジック、IO、フレームワーク依存 |
| ハンドラ | 抽出→検証→サービス委譲→応答変換の薄い層 | ビジネスロジック本体、IO直書き |
| サービス | ドメインロジック | HTTPの型、ルーター |
| ストレージ/境界 | fs・デバイス・外部プロセスとのIO | HTTPの関心事、無関係なドメイン判断 |
| ドメインモデル | 型と遷移(enum+網羅分岐) | IO、フレームワーク依存 |
| 機能束(ファクトリ) | 機能の依存一式struct+組み立て+局所ルーター | ロジック本体 |
| コンポジションルート | 設定読込、機能束の合成、起動 | ハンドラ、ロジック |
| テスト | テストのみ(本体と別ファイル) | — |

**UI層の例(4役割+束)**: プリミティブ部品 / ドメイン拡張部品 / 素部品(プリミティブのみの複合) / 部品集約(=配線係、ロジックはサービスへ抽出)。部品・状態・サービスは個別フィールドでN個持たず、束DTO+staticファクトリで一括構築する。

**機能束の形(言語不問の骨子)**: 1機能につき「依存一式を持つ構造体+`組み立てる()`+`配線する()/ルーター()`」を1ファイル。最上位のmainは各機能束の合成だけを書く。

## 場面1: 新規コードを書くとき

0. **層と依存の向きが決まっているかを先に確認する。** 決まっていなければ本スキルより前に `アーキテクチャ先行` スキルへ行く。本スキルは層の中の置き場所を決めるものであり、層が無い状態で適用すると「行数は整っているが依存の向きが無い」状態を作る
1. 対象リポジトリに役割規約文書があるか確認する(リポジトリのCLAUDE.mdのコード分割節から参照されているのが正しい配線)。あればその語彙でファイルを切ってから書き始める。無ければ上の見本から出発する
2. 1機能をいきなり1ファイルに書かない。契約/ハンドラ/サービス/IO境界/機能束を最初から別ファイルで始める。「あとで分割」はAI開発では起きない(YAGNIはアンチパターン、必要以上に分割をやれ)
3. **契約先行(DTOファースト)**: 実装より先に「入力DTO・出力DTO・関数シグネチャ」を決めてから中身を書く。引数が1個でもDTOまたは値オブジェクト/ドメイン型で受ける。裸のプリミティブ(string/int/bool)の引数・戻り値は外部境界(FFI・シリアライズ)のみ許容。裸プリミティブが内部に見えること自体をDDD違反のシグナルとして扱う。データ変換はDTOのメソッドに生やしてチェーンできる形にする

## 場面2: 肥大化したコードを分割するとき

1. まず対象ファイルの**同居している役割を列挙**する(読込/索引/検索/テスト、のように)。行数で切るのではなく役割で切る
2. リポジトリの役割語彙に各塊を割り当てる。語彙に無い役割が出てきたら語彙の拡張を検討し、規約文書側も更新する(規約と実装の乖離を作らない)
3. 生成コードは機能束/ファクトリへ隔離する。最上位(main等)は束の合成だけにする
4. 昇格経路表に従う。代表例:

| 圧力(サイン) | 逃し先 |
|---|---|
| 関数50行超 | 説明関数へ分解し、分解した関数は原則ファイルへ出す(関心事ごとに隣のファイル、言語の可視性宣言で不可視維持)。同一ファイルに残すのは10行未満の局所ヘルパのみ |
| 引数・戻り値に裸プリミティブ | DTO/値オブジェクト化(個数によらず。契約先行が原則で、ここに来るのは既存コードの是正時のみ) |
| impl/クラス150行超 | 責務ごとに型を分割 |
| 1ファイルに役割2つ以上 | 役割ごとにファイル分割 |
| 1概念のファイル3本以上 | ディレクトリ昇格(mod.rs/indexが集約点) |
| ハンドラにロジックが滲む | サービス抽出(ハンドラは抽出→検証→委譲→変換のみ) |
| 生成コードが消費側に散在 | 束DTO+ファクトリへ隔離 |
| 同型の分岐が複数箇所に拡散 | enum/型のメソッドへ集約、またはStrategyへ |

5. 触っていないファイルへのblanket refactorはしない。触る機会に適合化する

## 場面3: 新しいリポジトリ/レイヤーに規約を敷くとき

最初に次の3点を対象リポジトリ内の1文書にまとめる(これが無い規約は守られない):

1. **役割語彙表**: 役割名 / ファイル命名 / 中に書いてよいもの / 書いてはならないもの、の4列。有限個で閉じる
2. **昇格経路表**: そのレイヤー固有の肥大化圧力と逃し先
3. **規範実装の指名**: そのリポジトリ内で最も規約に適合した実装をファイル名+行数付きで指名し「まずこれを読め」と書く

文書化したら、リポジトリのCLAUDE.md(コード分割の節)から1行で参照させる。参照配線の無い規約文書は存在しないのと同じ。

## 検収時のチェック(親/レビュー側)

- 新規ファイルが役割語彙のどれかに分類できるか。できなければ差し戻しではなく語彙側の議論を起こす
- 行数が目安内でも役割混在なら指摘する(200行の「契約+ハンドラ+ストレージ」同居は違反)
- 網羅分岐・FFI定数表・テーブルデータの行数超過は役割が純なら許容
