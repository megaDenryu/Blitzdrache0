# インターフェース文書スキル

**インターフェースの文書とは、ある層を使う者(最終利用者・他の層・他の開発者)に対して、その層がどう振る舞うかの約束である。** 作り方を書く設計の文書とは向きが逆である。設計の文書はコードに追従して直すが、インターフェースの文書はコードより上の正本であり、食い違ったら誤っているのはコードの方である。

AI 駆動の開発では、オーナーの指示の多くはインターフェースに対するものである(「この操作でこうなってほしい」「この API はこれを返すべきだ」)。インターフェースの文書が無いと、実装員がコードを変えるたびに設計の文書がコードに合わせて書き換えられ、オーナーが決めた振る舞いが AI の都合で黙って変わる。制定の経緯: ClipViewer(2026-09-28)。画面.md に操作の約束が設計の判断と混ざって置かれ、実装員がコードに合わせて書き直し続けていた。利用者向けの説明書を今の実装から写したところ、写す過程でおかしな振る舞いが9件見つかった。

## 対象

- **最終利用者向けの説明書**: GUI・CLI で利用者が触る振る舞い(画面の文言・操作と結果・データが保存される条件と消える条件・キー・置き場所)。
- **各層の API の説明書**: 層の外から呼ばれる公開の型と関数が約束する振る舞い(受け付ける入力・返す結果・失敗の種類・副作用・順序の保証)。層の境界ごとに置く。内部の関数は対象外である。

## 手順

1. **まず今の実装をそのまま写す。** 理想の振る舞いを書かない。書く文は1つずつコードと画面の文言に突き合わせる。コードを読んでも分からない振る舞いは本文に書かず、分からないこととして報告する。
2. **写す過程で見つけたおかしな振る舞いは直さずに列挙する。** 文書には今の振る舞いを書き、おかしな点は「オーナーの判断事項」として別に挙げる。直すかどうかはオーナーが決める(振る舞いの変更だから)。
3. **冒頭に草案の印を置く**(`状態: 草案(オーナー未承認)`)。草案の間は、文書は今のコードの写しであり、食い違ったら文書を直す。
4. **正確さを検査員で確かめる。** 総合レビュー員に、記述を1つずつコードと突き合わせさせる(言い過ぎ・書き漏れた条件・データが消える条件を重く見る)。読み手が人間の利用者なら、文章チェック員も並べる。直した後、もう一度総合レビュー員にかける。
5. **オーナーの承認で正本にする。** 承認されたら草案の印を消す。その時点から、次の規則が効く。
6. **リポジトリの CLAUDE.md に規則を書く。**
   - その文書は振る舞いの正本である(承認の後)
   - AI はオーナーの決定なしに振る舞いの記述を変えない(表記の直しは、振る舞いを変えないことをコミットに書いて行ってよい)
   - コードと食い違ったらコードを直す
   - 振る舞いを変える依頼を受けたら、先に文書の変更案をオーナーに示し、決まってから実装する
   - 設計の文書は作り方を書き、インターフェースの文書と食い違ってはならない
   - 置き場所を README の文書の索引に登録する
7. **振る舞いを変えるときの順序**: オーナーの指示 → 文書の変更案を示す → オーナーの決定 → 文書を直す → 文書に合わせてコードを直す → 検査員で文書とコードの一致を確かめる。

## 委譲するときの注意

- 実装員に、インターフェースの文書をコードに合わせて書き換えさせない。実装員が文書との食い違いを見つけたら、報告させて親が判断する。
- 文書を書かせる委譲プロンプトには、読み手・正確さが最優先であること・推測で書かないこと・おかしな振る舞いは直さずに挙げることを書く。
- 文書に書く語は、オーナーが読んで分かる語にする(比喩や直訳の語を使わない。非推奨語の一覧に従う)。
