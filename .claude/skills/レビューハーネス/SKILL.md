# レビューハーネス

## これは何か

レビューハーネスとは、差分を観点ごとに分けて専任のチェック員へ並列で委譲し、その報告を親が統合して合否を決める手順のことである。1体の総合レビュアーへ丸ごと渡す形と違い、観点が固定されるため各チェック員のプロンプトが短くなり、低コストのモデルでも判定でき、同時に走らせられる。

**チェック員は指摘を出すだけであり、合否は決めない。** 合否は親が決める。技術裁定を委ねない(2026-08-09のオーナー裁定)。

## 観点の選び方

差分の性質から、走らせる観点を選ぶ。

| 観点(チェック員) | 走らせる条件 | モデル |
| --- | --- | --- |
| 命名チェック員 | **常時**(日本語識別子を1つでも足したか変えたら) | haiku |
| 構造チェック員 | **常時**(コードを足したか変えたら) | sonnet high |
| 行数と分割の質チェック員 | ファイルを新設・分割・統合したとき | sonnet medium |
| 契約整合チェック員 | `crates/editor_server/src/resource` `contract` か `editor_web/src/生成` を触ったとき | sonnet low |
| 孤立実装チェック員 | 公開の型・関数・コマンドの枝・検査を足したとき | sonnet low |
| テスト実効性チェック員 | テストを足したか変えたとき | sonnet high |
| 設計正本整合チェック員 | `_doc/設計/` に正本がある領域を触ったとき | sonnet high |
| 文章チェック員 | 文書・issue・PRの本文・コミットメッセージ・オーナーへ見せる文章を書いたとき。**`.claude/agents/` の定義と `.claude/skills/` のスキルを新しく書いたとき・書き換えたときも必ず含める** | sonnet medium |

**エージェント定義とスキルを検査の対象へ入れる理由**(2026-09-04制定): 文章規範の適用範囲は「サブエージェントへの指示」を含む。委譲プロンプトの曖昧さは、サブエージェントの成果物の欠陥として返ってくるためである。定義とスキルは委譲プロンプトの一部が固定されたものであり、検査を通さなければ同じ欠陥が全ての委譲へ効き続ける。実際に、`溶けた概念の分解員` の定義で「階層」を「段」と切り詰めた造語を使ったまま、オーナーの指摘を受けるまで検出できなかった(定義24体のうち違反はこの1件で、残りは検査で問題なしと判定された)。
| 検証再実行員 | 検証を親のコンテキストの外で回したいとき | sonnet low |
| レビュー員 | 上の観点で切り分けきれない差分、設計判断を含む差分、大規模な差分 | Opus medium |
| レビュー員Fable版 | 難易度が特に高い検収 | Fable low |

**迷ったら常時の2つ(命名・構造)に、差分が触った領域の観点を足す。** 全部を毎回走らせない。無関係な観点を走らせると、水増しの指摘が増えて親の判断が鈍る。

## このハーネスで捕まらないもの

上の表の観点はすべて**差分**を見る。したがって、**1回の変更としては正しいが、積み重なった結果として壊れる劣化を捕まえられない**(型が少しずつ責務を集め続ける、依存が少しずつ絡まり続ける等)。これは検査の厳しさの問題ではなく、見ている対象の問題である。

その劣化は `溶けた概念の分解員`(Opus 5・medium。難易度が特に高い領域は `溶けた概念の分解員Fable版`)が受け持つ。**この検査員をここで(差分の検収で)走らせてはならない。** 差分ではなく領域の現状を見る検査であり、走る契機が違う。

| | このハーネス(差分) | 溶けた概念の分解(現状) |
| --- | --- | --- |
| 見る対象 | `git diff` | 指定した領域の現状と変更履歴 |
| 走る契機 | 委譲成果の検収のたび | 待ち時間のローラー監査、節目の定点 |
| 記録 | 不要(検収の報告に含める) | `_doc/計画/検査の網羅台帳.md` の「まとまりとつながりの検査の網羅」へ1行 |

## 実装と並走させる検査(2026-09-05制定)

**検査の起点は実装員の完了通知ではなく、実装員が積むコミットである。** 完了通知の後に親が検査員5体を走らせ、指摘の是正の周を回し、再検査する形では、検査の待ち時間が実装の待ち時間へ足し算で乗り、親が次の実装に着手できない(2026-09-05のオーナー指摘)。実装員は作業の段階ごとにコミットする規律を既に持つ(実装ハーネス「委譲プロンプトの必須要素」の条6)ので、そのコミットを検査の単位にする。

**検査員に読ませるのは作業ツリーではなくコミットである。** 作業ツリーには書きかけのファイルが載っており、検査員がそれを読むと、完成品に含まれない変更まで検査員が検査してしまう。コミットは実装員が「この段階は成立した」と宣言した時点の静止した断面であり、書きかけを含まない。親は、検査員の委譲プロンプトに対象を `git show <ハッシュ>` か `git diff <前のハッシュ>..<ハッシュ>` の範囲で書き、「作業ツリーを読まず、指定したコミットの差分だけを読む」と明記する。

### 並走できる観点とできない観点

| 観点 | 走らせる時期 | 理由 |
| --- | --- | --- |
| 命名 / 構造 / 行数と分割の質 / 文章 | **コミットごと**(実装員の走行中) | 1コミットの差分だけで判定でき、後の段階に依存しない |
| 契約整合 / 孤立実装 | 最後のコミットの後 | 「配線されていない」は全部が揃うまで判定できない |
| テスト実効性 / 設計正本整合 | 最後のコミットの後 | 試験の全体像と正本の対応表が要る |
| 検証再実行 | 最後のコミットの後 | 実装員自身が回すものを親が再実行する |

命名と構造は「観点の選び方」の条件どおり常時である。行数と分割の質と文章は、「観点の選び方」の条件(ファイルの新設・分割・統合、または文書・issue・PRの本文・エージェント定義・スキルを書いたこと)に当たるコミットが出た時点で、そのコミットごとに走らせる。条件が外れて毎コミット必ず走るようになったのではない。

コミットごとに走らせる4つは、いまの検収で最も指摘の本数が多く、是正の周が増える原因でもある。これが前倒しされれば、完了時に残るのは後半の少数の検査だけになる。

### 親の手順

1. **親は、実装員を走らせたまま、実装員が作業しているGitのブランチへ積まれる新しいコミットを監視する。** `git -C <作業ツリー> log --oneline <起点>..HEAD` を数十秒おきに見る(Monitorで可)
2. **新しいコミットが出るたびに、そのコミットの差分を対象にコミットごとの観点の検査員を並列で起動する。** 1コミットに複数の段階が畳まれていても、そのまま1回の検査にする
3. **指摘は実装員がまだ走っているうちに SendMessage で送る。** 送る内容は、対象のコミット・箇所・違反の種類・書き直し案である。親の吟味(「指摘の吟味」の4軸)を通してから送る。検査員の報告をそのまま転送しない
4. **最後のコミットの後に、残りの観点の検査員を走らせる。** ここで出た指摘は従来どおり是正の周にする
5. 走行中に届いた指摘を実装員がどう処理したかは、完了報告に「走行中に受けた指摘とその処理」の節として書かせる

### 受け入れる費用

実装員が後の段階で同じ箇所を作り直し、先に走らせた検査が無駄になることはありうる。それは待ち時間と引き換えの費用であり、受け入れる。検査員の指摘が「後の段階で消える設計の途中経過」に対するものなら、実装員は「後の段階で消える」と返答してよく、親はそれを受理する。検査員は最終形を知らないためである。

## 手順

1. **差分を確定する。** `git diff --stat` と `git status` で、何を触ったかを一覧にする
2. **観点を選ぶ。** 上の表で条件に当たるものを列挙する
3. **並列で起動する。** チェック員はすべて読み取り専任であり、ファイルを書き換えないため、同時に走らせて競合しない。1つのメッセージで複数の Agent 呼び出しを出す
4. **委譲プロンプトに必ず書く。** 対象の差分の範囲(コミットの範囲かファイル一覧)、対象の設計正本のパス(あれば)、無視してよい既知の失敗(あれば)
5. **報告を統合する。** 同じ箇所への指摘が複数の観点から来たら1件へまとめる。観点どうしで判定が食い違ったら、親が現物を開いて決める
6. **親が最後に自分でやる**(省略禁止)
   - 検証の再実行(報告を鵜呑みにしない)
   - `git diff` の全件目視
   - 合否の確定

## 指摘の吟味

チェック員の指摘をそのまま採用しない。次の4軸で吟味してから採用・一部採用・却下を決める。

1. **前提整合**: その指摘は、このリポジトリの規約と設計正本の前提に合っているか
2. **実害**: 直さなかったとき、何が壊れるか。壊れないなら却下してよい
3. **過剰防衛**: 起きない事故に備える提案になっていないか
4. **二重管理リスク**: 直した結果、同じ規則の写しが増えないか

## 並列化の注意

- チェック員が `cargo` を同時に走らせると、ビルドの排他ロックで待ちが出る。検証の実行は検証再実行員1体へ集約し、他のチェック員には「検証は走らせず読み取りだけ」と指示すると速い
- 実機の検証(ブラウザ操作・スクリーンショット)は既定では行わない。オーナーの実操作へ回す(2026-08-22指示)
