# レビューハーネス

## これは何か

レビューハーネスとは、差分を観点ごとに分けて専任のチェック員へ並列で委譲し、その報告を親が統合して合否を決める手順のことである。1体の総合レビュアーへ丸ごと渡す形と違い、観点が固定されるため各チェック員のプロンプトが短くなり、低コストのモデルでも判定でき、同時に走らせられる。

**チェック員は指摘を出すだけであり、合否は決めない。** 合否は親が決める。技術裁定を委ねない(2026-08-09のオーナー裁定)。

## 観点の選び方

差分の性質から、走らせる観点を選ぶ。

| 観点(チェック員) | 走らせる条件 | モデル |
| --- | --- | --- |
| 命名チェック員 | **常時**(日本語識別子を1つでも足したか変えたら) | sonnet・medium(2026-09-12にhaikuから上げた) |
| 構造チェック員 | **常時**(コードを足したか変えたら) | sonnet high |
| 総合レビュー員 | **常時**(差分の検収のたび。観点ごとの検査員と並べて1体) | Opus 5.5・medium |
| 行数と分割の質チェック員 | ファイルを新設・分割・統合したとき | sonnet medium |
| 契約整合チェック員 | `crates/editor_server/src/resource` `contract` か `editor_web/src/生成` を触ったとき | sonnet low |
| 孤立実装チェック員 | 公開の型・関数・コマンドの枝・検査を足したとき | sonnet low |
| テスト実効性チェック員 | テストを足したか変えたとき | sonnet high |
| 設計正本整合チェック員 | `_doc/設計/` に正本がある領域を触ったとき | sonnet high |
| 文章チェック員 | 文書・issue・PRの本文・コミットメッセージ・オーナーへ見せる文章を書いたとき。**`.claude/agents/` の定義と `.claude/skills/` のスキルを新しく書いたとき・書き換えたときも必ず含める** | sonnet medium |

**エージェント定義とスキルを検査の対象へ入れる理由**(2026-09-04制定): 文章規範の適用範囲は「サブエージェントへの指示」を含む。委譲プロンプトの曖昧さは、サブエージェントの成果物の欠陥として返ってくるためである。定義とスキルは委譲プロンプトの一部が固定されたものであり、検査を通さなければ同じ欠陥が全ての委譲へ効き続ける。実際に、`溶けた概念の分解員` の定義で「階層」を「段」と切り詰めた造語を使ったまま、オーナーの指摘を受けるまで検出できなかった(定義24体のうち違反はこの1件で、残りは検査で問題なしと判定された)。
| ビルド員 | 常駐1体。実装員が段階のコミットごとに直接依頼し、親へも結果が届く | sonnet low |
| レビュー員 | 上の観点で切り分けきれない差分、設計判断を含む差分、大規模な差分、難易度が特に高い検収 | Opus medium |

**迷ったら常時の3つ(命名・構造・総合)に、差分が触った領域の観点を足す。** 全部を毎回走らせない。無関係な観点を走らせると、水増しの指摘が増えて親の判断が鈍る。

## このハーネスで捕まらないもの

上の表の観点はすべて**差分**を見る。したがって、**1回の変更としては正しいが、積み重なった結果として壊れる劣化を捕まえられない**(型が少しずつ責務を集め続ける、依存が少しずつ絡まり続ける等)。これは検査の厳しさの問題ではなく、見ている対象の問題である。

その劣化は `溶けた概念の分解員`(Opus 5.5・medium。難易度が特に高い領域も同じくOpus 5.5を使う)が受け持つ。**この検査員をここで(差分の検収で)走らせてはならない。** 差分ではなく領域の現状を見る検査であり、走る契機が違う。

| | このハーネス(差分) | 溶けた概念の分解(現状) |
| --- | --- | --- |
| 見る対象 | `git diff` | 指定した領域の現状と変更履歴 |
| 走る契機 | 委譲成果の検収のたび | 待ち時間のローラー監査、節目の定点 |
| 記録 | 不要(検収の報告に含める) | `_doc/計画/検査の網羅台帳.md` の「まとまりとつながりの検査の網羅」へ1行 |

## 実装と並走させる検査(2026-09-05制定)

**検査は実装員の完了通知を待たずに、実装員が走っているあいだに始める。** 完了通知の後に親が検査員5体を走らせ、指摘を是正させて再検査する周回を回す形では、検査の待ち時間が実装の待ち時間へ足し算で乗り、親が次の実装に着手できない(2026-09-05のオーナー指摘)。

**検査の起点は経過した時間と差分の量であり、コミットではない。** 親は、実装員を走らせたまま作業ツリーの差分を見張り、前回の検査から20分が経過したか、変更したファイルが10件に達したら、検査を1回起動する。実装員が積んだコミットは差分を切り取る機会の1つであって、コミットを待つ理由にはならない。

**親は、途中の状態を検査することを受け入れる**(2026-09-05のオーナー裁定。「完成品に含まれない変更を検査してしまうことは臨機応変にできるはずで、問題ではない」)。作業ツリーには書きかけが載っており、検査員の指摘のいくらかは後の作業で消える途中経過に対するものになる。それを避けるために、親は検査をコミットへ限定してはならない。二重に検査する費用より、検査を待つ時間のほうが高い。

### 差分の切り取り方

親は、起動の時点の作業ツリーの差分を1つのファイルへ書き出し(`git -C <作業ツリー> diff <起点> > <スクラッチパッド>/<名前>.patch`。未追跡のファイルは `git add -N` で差分に含める)、検査員にはそのファイルを読ませる。作業ツリーを直接読ませると、検査の途中で実装員が書き換えたファイルを検査員が読み、同じ1回の検査の中で前後が食い違う。切り取ったファイルは静止しているため、この食い違いが起きない。コミットが積まれていれば `git show <ハッシュ>` でもよい。

### 走らせる観点

**すべての観点を途中で走らせてよい。** 1つの差分で判定できる観点(命名・構造・行数と分割の質・文章)は、担当する検査員がそのまま判定する。全部が揃わないと判定できない観点(契約整合・孤立実装・テスト実効性・設計正本整合)は、途中で走らせると「まだ配線されていない」「まだ試験が無い」という指摘が出る。検査員には「実装は途中である。揃っていないことによる指摘は、断定せず『途中のため保留』と印を付けて別に列挙せよ」と指示する。親は保留の印が付いた指摘を次の回の検査で消えているかだけ見る。検証(`cargo xtask verify`)は実装員が走らせず、常駐のビルド員が回す(実装ハーネス「検証はビルド員が回し、ビルドの置き場は本体の1つだけにする」)。

観点を選ぶ条件は「観点の選び方」の表のとおりである。親は、命名・構造・総合は常時、行数と分割の質と文章はその条件に当たる差分が出た回に走らせる。

### 親の手順

1. **親は、実装員を走らせたまま、作業ツリーの差分の量を数十秒おきに見る**(`git -C <作業ツリー> diff --stat <起点>` をMonitorで見る)
2. **差分が目安の量に達するたびに、親は差分を切り取って検査員を並列で起動する。** 前の回の検査が終わっていなくても、親は次の回を起動してよい
3. **親は、指摘を「レビューを受け取る側の構え」の5軸で吟味してから、実装員がまだ走っているうちに SendMessage で送る。** 送る内容は、対象の箇所・違反の種類・書き直し案である。親は、検査員の報告をそのまま転送しない。親は、「途中のため保留」の印が付いた指摘を送らない
4. **実装員の完了通知の後、親は最後の差分でもう1回だけ検査を起動する。** 親は、この回で保留の印が消えているかと、走行中に送った指摘が処理されているかを見る。親は、ここで出た指摘だけを、次に実装員へ渡す是正の周回に含める。この回の後の手順は、下の「手順」の節のとおりである
5. 走行中に届いた指摘を実装員がどう処理したかは、完了報告に「走行中に受けた指摘とその処理」の節として実装員が書く

### 受け入れる費用

検査員の指摘が、実装員が後の段階で作り直す箇所や、まだ書きかけの箇所に対するものになることはありうる。それは待ち時間と引き換えの費用であり、親はそれを受け入れる。指摘が後の段階で消える途中経過に対するものなら、実装員は「後の段階で消える」と返答してよく、親はそれを受理する。検査員は最終形を知らないためである。

## 手順

1. **差分を確定する。** `git diff --stat` と `git status` で、何を触ったかを一覧にする
2. **観点を選ぶ。** 上の表で条件に当たるものを列挙する
3. **並列で起動する。** チェック員はすべて読み取り専任であり、ファイルを書き換えないため、同時に走らせて競合しない。1つのメッセージで複数の Agent 呼び出しを出す。親は、総合レビュー員が常時の対象であるため、観点ごとの検査員と同じメッセージで総合レビュー員も同時に起動する
4. **委譲プロンプトに必ず書く。** 対象の差分の範囲(コミットの範囲かファイル一覧)、対象の設計正本のパス(あれば)、無視してよい既知の失敗(あれば)
5. **報告を統合する。** 同じ箇所への指摘が複数の観点から来たら1件へまとめる。観点どうしで判定が食い違ったら、親が現物を開いて決める
6. **親が最後に自分でやる**(省略禁止)
   - 検証の再実行(報告を鵜呑みにしない)
   - `git diff` の全件目視
   - 合否の確定

## レビューを受け取る側の構え

受け取る側は、親と実装員である。対象は、すべてのレビューである。この対象は、観点ごとの検査員・総合レビュー員・レビュー員に限らず、外部のレビュー(Codexなど)とオーナー以外の人のレビューも含む。

**受け取る側は、レビューの指摘を正しいものとして扱わない。** 受け取る側は、指摘ごとに現物(コード・文書・検証の結果)を開いて、指摘が事実かを確かめてから採否を決める。受け取る側は、次の5軸で判定する。受け取る側は、1つ目の軸を、既存の4軸より先に確かめる。

1. **事実か**: 指摘が述べる状態は、現物で本当に起きているか
2. **前提整合**: その指摘は、このリポジトリの規約と設計正本の前提に合っているか
3. **実害**: 直さなかったとき、何が壊れるか。壊れないなら却下してよい
4. **過剰防衛**: 起きない事故に備える提案になっていないか
5. **二重管理リスク**: 直した結果、同じ規則の写しが増えないか

**受け取る側は、採用・一部採用・却下を、指摘ごとに理由を付けて記録する。** 受け取る側は、却下するとき、根拠を示して言い返す。受け取る側は、レビュアーに合わせるために、正しい実装を曲げない。

**受け取る側は、人間の開発者が自分の実装に意地を持ってレビュアーに反論するのと同じ構えを取る。** ただし、受け取る側は、意地を根拠で示す。この規約は、根拠の無い拒否も、盲目的な受け入れと同じく禁じる。

受け取る側とレビュアーの判断が割れたまま決まらないときは、親が現物で決める。設計の裁定が要るものは、親がオーナーへ上げる。

**この構えを定めた理由**: レビュアーは現物を部分的にしか見ておらず、誤った前提で指摘することがある。盲目的に受け入れると、正しいコードが壊れ、指摘の水増しが通る。PR #177 の期間には、外部のレビューが「抜け道がある」と指摘するたびに親が全部を塞ぎにいき、検査が約5,600行へ膨らんだ。その経緯は `_doc/開発スレッド/開発スレッド_2026-09-25_自己変更の禁止の検査の膨張とマーカーの思想.md` にある。

## 並列化の注意

- チェック員が `cargo` を同時に走らせると、ビルドの排他ロックで待ちが出る。検証の実行はビルド員1体へ集約し、他のチェック員には「検証は走らせず読み取りだけ」と指示すると速い
- 実機の検証(ブラウザ操作・スクリーンショット)は既定では行わない。オーナーの実操作へ回す(2026-08-22指示)
