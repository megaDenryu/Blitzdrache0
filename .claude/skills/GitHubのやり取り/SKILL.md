# GitHubのやり取り

issueとPull Requestは、オーナーが差分を1行ずつ追わずに判断するための文書である。差分を見ないと意味が取れない本文は、書いていないのと同じである。

## 長さ

AIは、手順・経緯・理由・検証の表を全部本文へ書き写し、見出しを規則の数だけ並べる。そうすると、オーナーは判断の前に本文そのものを読み解く作業を強いられる(2026-09-25、PR #186 の本文が約90行になり「レビューメッセージ自体のレビューからしないといけない」と指摘された)。

書き手は、読み手がいま判断するのに要ることだけを書く。経緯と理由の詳細はコミットのメッセージとissueにあるので、書き手はそれを本文へ写さない。書き手は、見出しや項目を足すたびに「オーナーの判断にこれが要るか」を問う。PRの本文とコメントは1画面(15行前後)を目安にする。

書き手は、本文にブランチのいまの状態だけを書く。作業の途中で犯して直した誤りと、判断の変遷(最初はこう考え、途中で変えた)は差分に残っていないため、書き手がそれを書くと、読み手は「これは直っているのか、まだあるのか」を1件ずつ判定させられる。書き手が書いてよいのは、その誤りが結果にまだ残っているとき(書き手は残っている制約として書く)と、レビュアーが確かめるべきことを変えるときだけである。経緯は、上のとおりコミットのメッセージとissueが残す。

書き手は、オーナーへのチャットの報告も同じく短くし、先頭の1行に状態を書く。状態は、全部終わって次の指示を待つ**完了**・誰かが動いていて親が待っている**作業中**・オーナーの判断が要って止まっている**要判断**の3つである。「〜しています」「〜を出しました」は完了と進行中のどちらにも読めるため、この1行が無いと読み手は全文を読んでから終わったかを推測することになる。

## いつ書くか

次のことが起きたら、親はその時点で自分から書く。書かないことは、やっていないことと同じである。

| 起きたこと | 書くこと |
| --- | --- |
| issueを読んで作業に入る | 吟味の結果をissueへコメントする |
| issueの作業が終わった | 完了条件ごとに、満たしたか・どこまで満たしたかを書く |
| PRへ push した | PRの本文の「何をしたか」と検証を現在地へ更新する |
| レビューを受けて対応した | そのPRへ返信する |
| 裁定が要る判断が出た | 推奨を1つ選び、理由を添えて裁定を求める |

## 吟味してから応答する

親は、issueの内容とレビューの指摘をそのまま受け入れない。親は、前提が現状と合っているか・実害があるか・過剰防衛でないか・二重管理を生まないかで吟味し、指摘ごとに採用・却下・修正して採用のどれかと、その理由を書く。親は、issueを読んだら実装の前に吟味の結果をコメントする(親が実装してから解釈を書くと、解釈が違ったときに親が作り直すことになる)。

## 書き方の決まり

- **書き手の明示**: Claudeは、自分が書くissue・PR・コメント・返信の先頭の1行を `> 書き手: Claude Code(親セッション)。オーナーの指示で書いた。セッション: <セッションのURL>` にする。オーナーと同じアカウントで投稿するため、この行が無いと読み手は読み分けられない。サブエージェントが書くときは「親セッション」を「<役名>(親: <親のセッションのURL>)」にする
- **リンク**: 親は、コミットを `[何をしたか](…/commit/<ハッシュ>)` の形で書き、ハッシュや範囲の表記(`a1b2..c3d4`)を裸で書かない。ファイルは `…/blob/<ブランチ>/<パス>`、ディレクトリは `tree`、issueの特定のコメントは `#issuecomment-<番号>` まで指す。日本語のパスはURLエンコードする。PRが閉じた後も読む文書では、ブランチでなくコミットのSHAで固定する。番号だけの参照は初出で内容を添える(`issue #56(Rustコード規約の使い分けの明文化)`)
- **投稿の前**: 親は、リンクにしたハッシュの実在を `git cat-file -t <ハッシュ>` で確かめ、本文を文章チェック員へ回す。投稿した後で誤りに気づいたら、親は新しいコメントを足さず `gh api -X PATCH repos/<所有者>/<リポジトリ>/issues/comments/<ID> -F body=@<ファイル>` で差し替える
- **状態を混ぜない**: 親が言えるのは「機械検証済み」までであり、「受理済み」を宣言するのはオーナーである。親は、完了条件を機械か現物で確かめたときだけ「満たした」と書く

## issueの管理体制

- **閉じ方**: 親がPRの本文に `Closes #N` を書くと、マージの時点でissueが閉じる。親は、issueの完了条件をすべて満たすPRにだけ `Closes` を書き、一部だけなら `Part of #N`、参照だけなら `Refs #N` にする。裁定で条件が外れたら、親はissueの本文の完了条件を先に書き換える。大きなissueは、親が子issueへ切り分けて親issueの本文のタスクリスト(`- [ ] #子番号`)に並べ、子のPRに `Closes` を書く
- **ラベル**: 親は、1つのissueに次の3軸から1つずつ付け、状態は作業の節目で付け替える(着手したら `着手可` を外し、PRを出したら `裁定待ち`、マージしたら閉じる)

| 軸 | ラベル |
| --- | --- |
| 種別 | `欠陥` / `機能` / `設計` / `規約と検査` / `計測` / `親issue` |
| 状態 | `着手可` / `依存待ち`(本文に何を待つかを書く) / `裁定待ち` / `保留`(理由を本文へ) |
| 領域 | `物理` / `描画` / `エディター` / `ECS` / `基盤`(xtask・資産・規約・文書) |

- **完了の報告**: 親は、完了条件の文言を1つずつ引用し、`- [x] 条件 — [反映のコミット](リンク)` / `- [ ] 条件 — 未着手` の形で現在地を書く。issueを閉じるかどうかはオーナーが決める
- **返信が来たら**: 親は、裁定・追加指示・却下を反映してから、反映したことを同じissueへ書く
- **棚卸し**: 親は、待ち時間に開いているissueを見て、ラベルが現状と違うもの・30日以上動かず `保留` でないもの・完了条件が無いものを直し、`_doc/計画/検査の網羅台帳.md` へ1行で記録する

## PR

- **出す時機**: 親は、ブランチを切って push したらその場でPRを出す。親は検証の完了を待たない(親は検証の節を結果が出てから更新する)。PRを出すことは提案であり、オーナーの許可は要らない。ただし、オーナーが指示したハーネス(`.claude/skills/`・`.claude/agents/`)の小さな修正について、親はPRを出さず `main` へ直接マージする
- **本文**: 既定の見出しは次の3つである。親は、受理の状態・主題が途中で変わったことの宣言・次にやることを、要るときだけ足す
  1. **何をしたか**: 箇条書きで数行。各行にコミットへの名前付きのリンクを添える
  2. **判断してほしいこと**: オーナーが決める事項と、受理に関わる未解決の事項(残る警告など)。無ければ見出しごと書かない
  3. **検証**: 通ったか、落ちたならその理由と本PRとの関係を数行で
- **レビューへの返信**: 親は、指摘ごとに採否とその理由を書き、是正したならそのコミットへのリンクを置く。親は、裁定が要るものについて推奨を1つ選ぶ。親は、指摘が正しかったなら、現物のどこで確かめたかを添えてそう書く。親は、対応中に別の欠陥を見つけたら、それも書く
- **受理の範囲**: オーナーが受理したのは、受理した時点のPRの先端である。受理の後に意味を変える変更を足したら、親はマージの前に再レビューを求める。親は、受理済みのPRへ別件を足さない(「PRの本数を増やしたくない」は理由にならない)。受理の後に足してよいのは、リベース・競合の解消・綴りの直しのような意味を変えない追随だけである
- **issueとの接続**: PRがissueの完了条件を満たしたら、親はPRとissueの両方へ書く。機能のPRから恒久的な体制の変更が大きく育ったら、親は別のPRへ切る(何を受理したのかが曖昧になるため)

## 違反のサイン

- PRの本文やコメントが1画面に収まらず、判断に要らない見出しを持つ
- 先頭に「書き手: Claude Code」の行が無い
- 本文に、途中で直した誤りや判断の変遷が書いてある
- オーナーへのチャットの報告の先頭に、状態の1行が無い
- コミットハッシュが裸で並んでいる、またはリンクが404を返す
- 完了条件を1つでも見送ったのに `Closes #N` を書いている
- レビューへ対応したのに返信していない、または指摘を全部採用している(吟味が働いていない)
- 受理の後に足した意味を変える変更が、再レビューを経ずにマージされている
