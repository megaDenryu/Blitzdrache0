# GitHubのやり取り

## これは何か

issueとPull Requestで、オーナーとやり取りする手順を定める。

**issueもPRも、オーナーが差分を1行ずつ追わずに判断するための文書である。** 差分を見ないと意味が取れない本文は、書いていないのと同じである。

## 5つの原則(issueとPRに共通)

### 1. 指示を待たない

次のことが起きたら、その時点で親が自分から書く。オーナーが「返信しろ」と言うのを待たない。

| 起きたこと | その場で行うこと |
| --- | --- |
| issueを読んで作業に入る | 吟味の結果をissueへコメントする(下の「吟味してから応答する」) |
| issueの作業が終わった | issueへ完了を報告する。完了条件を1つずつ引用して現在地を書く |
| PRへ push した | PRの本文の検証の表と次にやることを現在地へ更新する |
| レビューを受けて対応した | そのPRへ返信を投稿する |
| 裁定が要る判断が出た | 推奨を1つ選び、理由を添えて裁定を求める |

**書かないことは、やっていないことと同じである。** 読み手は、コミットの一覧からどの指摘がどう処理されたかを再構成できない。

### 2. 吟味してから応答する

**issueの内容とレビューの指摘を、そのまま受け入れない。** 4つの軸で吟味する。前提が現状と合っているか、実害があるか、過剰防衛でないか、二重管理を生まないか。

応答には、採用・却下・修正して採用のどれかを指摘ごとに書く。**却下するなら理由を書く。** 修正して採用するなら、原案のどこをなぜ変えたかを書く。

実例として、issue #56(Rustコード規約の使い分けの明文化)は4点を修正して採用した。原案の「状態を持たない処理は原則自由関数」をそのまま採ると、AIが何でも自由関数へ倒す癖を止めるために作った既存の条文と正面から衝突するためである。

### 3. 行き先を書けるものは全部リンクにする

| 参照 | 書く形 |
| --- | --- |
| コミット | `[粗マスへの改称](https://github.com/<所有者>/<リポジトリ>/commit/<ハッシュ>)` |
| ファイル | `[`_doc/設計/xxx.md`](https://github.com/<所有者>/<リポジトリ>/blob/<枝>/_doc/設計/xxx.md)` |
| ディレクトリ | 同じ形で `blob` を `tree` にする |
| issue・PR | `[#45](https://github.com/<所有者>/<リポジトリ>/issues/45)` |
| issueの中の特定のコメント | コメントの行き先まで指す(`#issuecomment-<番号>`)。長いissueで読み手に探させない |

- **コミットハッシュを裸で書かない。** `991850b1` という文字列は読み手にとって意味を持たない。何のコミットなのか、そこを見るべきかどうかが判断できない。リンクの文字列には、そのコミットが何をしたかを日本語で書く(コミットメッセージの見出しをそのまま使ってよい)
- 範囲の表記(`a1b2c3d..e4f5g6h`)も使わない。読み手が中身を知る手段を持たない
- 日本語のパスはURLエンコードする(`urllib.parse.quote`)
- 枝の名前でリンクすると、その枝を消したときに行き先が切れる。PRが閉じた後も読む文書なら、コミットのSHAで固定する
- **番号だけの参照は初出で内容を添える。** `#56` では何の話か分からないため、`issue #56(Rustコード規約の使い分けの明文化)` と書く

### 4. 投稿の前に2つ検証する

**コミットハッシュが実在することを `git cat-file -t <ハッシュ>` で確かめる。** 存在しないハッシュをリンクにすると、読み手は404のページへ飛ぶ。2026-09-04に実際に踏んだ(要約から書き起こしたハッシュが実在しなかった)。

**文章チェック員へ回す。** issueとPRの本文・返信・完了報告はすべて文章規範の適用対象である。委譲するときは、読み手が誰で何を知らないかを渡す。

投稿した後で誤りに気づいた場合は、`gh api -X PATCH repos/<所有者>/<リポジトリ>/issues/comments/<コメントID> -F body=@<ファイル>` で本文を差し替える。新しいコメントを足して訂正しない。

### 5. 状態を混ぜない

「機械検証済み(試用可能)」と「受理済み」は別である。**親が言えるのは前者までであり、後者を宣言するのはオーナーである。**

同じく、issueの完了条件を「満たした」と書けるのは、その条件を機械か現物で確かめたときだけである。

### 6. 書き手がClaudeであることを本文の先頭で明示する(2026-09-05制定)

この規則は、オーナーが自分で書いたものとClaudeが書いたものを、GitHub上で読み手が読み分けられるようにする(同じアカウントで投稿されるため、印が無いと読み手は区別できない)。**Claudeは、自分が書くissueの本文・PRの本文・コメント・レビューの返信の先頭の1行を、すべて次の形にする。**

```
> 書き手: Claude Code(親セッション)。オーナーの指示で書いた。セッション: <セッションのURL>
```

セッションのURLは、そのセッションのコミットの末尾に付ける `Claude-Session:` と同じものである。サブエージェントが投稿するときは、そのサブエージェントが「親セッション」の部分を「<役名>(親: <親のセッションのURL>)」にする。Claudeは、PRの本文の末尾に付ける `Generated with Claude Code` の行をこれとは別に維持し、末尾は読み飛ばされるため先頭にも置く。

## issueの管理体制(2026-09-05制定)

### issueの閉じ方はPRの本文の語で決まる

GitHubは、PRの本文に `Closes #N`・`Fixes #N`・`Resolves #N` があると、そのPRが既定の枝(`main`)へマージされた時点でissue #N を自動で閉じる。親は、この語を**issueの完了条件をすべて満たすPRにだけ**書く。

| PRとissueの関係 | 本文に書く語 | マージ時の動き |
| --- | --- | --- |
| PRがissueの完了条件をすべて満たす | `Closes #N` | issueが自動で閉じる |
| PRがissueの一部の条件だけ満たす | `Part of #N` | 閉じない。完了報告のコメントで未達の条件を列挙する |
| PRがissueを参照するだけ(原因の記録・関連) | `Refs #N` | 閉じない |

**親は、完了条件の引用によって判定を行う。** 親は「issueの作業が終わったとき」の手順で完了条件を1つずつ引用し、全部が「満たした」なら `Closes` を書き、1つでも「見送った」「裁定で外した」があれば `Part of` を書く。裁定で条件そのものが外れた場合、親はまずissueの本文の完了条件を書き換えてから `Closes` にする(条件を残したまま親が閉じると、後から読む人が満たしたと誤読する)。

複数のPRで進める大きなissue(例: Issue #40「剛体の接触」の5つの作業)は、**親が作業ごとに子issueへ切り分け、親issueの本文にタスクリスト(`- [ ] #子番号`)で並べる。** GitHubは親のタスクリストから子の進みを表示する。書き手は子issueのPRへ `Closes` を書き、親issueは、子issueが全部閉じた後にオーナーが閉じる(自動では閉じない)。

### ラベルは3軸で付け、1つのissueに各軸から1つずつ

| 軸 | ラベル | 意味 |
| --- | --- | --- |
| 種別 | `欠陥` / `機能` / `設計` / `規約と検査` / `計測` / `親issue` | 何を求めているか。`親issue` は子を束ねるだけで自分では閉じないもの |
| 状態 | `着手可` / `依存待ち` / `裁定待ち` / `保留` | いま誰が動けるか。`依存待ち` は本文に何を待つかを書く。`裁定待ち` はオーナーの判断を待つ。`保留` は着手しないと決めたもの(理由を本文へ) |
| 領域 | `物理` / `描画` / `エディター` / `ECS` / `基盤` | どのクレート群か。`基盤` は xtask・資産・規約・文書 |

状態のラベルは**作業の節目で親が付け替える**。親は、着手したら `着手可` を外し、PRを出したら `裁定待ち` にし、マージしたら閉じる。この規約は、ラベルを付け替えずに本文だけ更新することを違反とする(ラベルは一覧で読むための欄であり、本文は開かないと読めない)。

### 棚卸しは待ち時間に行う

親は、ローラー検査の待ち時間に、開いているissueを一覧で見て次を直す。(1) 状態のラベルが現状と合っていないもの (2) 30日以上動きが無く `保留` でないもの(理由を1行コメントし `保留` にするか、着手する) (3) 完了条件が無いissue(本文へ足す)。親は、棚卸しの結果を `_doc/計画/検査の網羅台帳.md` へ1行で記録する。

## issueのフロー

```
issueを読む
  → 吟味する(原則2)
  → 吟味の結果をコメントする ← ここを飛ばさない
  → オーナーの裁定を待つ(規約の改訂・設計判断の場合)
  → 実装する
  → 完了を報告する ← ここも飛ばさない
  → オーナーが閉じる
```

### issueを読んだとき

**そのまま実装に入らない。** 原則2の4軸で吟味し、結果をコメントする。特に規約と設計に関わるissueでは、原案のどこを採り、どこを修正し、なぜそうしたかを書く。

**吟味の結果をコメントしてから実装する。** 実装してから「こう解釈しました」と書くと、解釈が違ったときに作り直しになる。

### issueの作業が終わったとき

**完了条件を1つずつ引用して、現在地を書く。**

```markdown
## 完了条件の現在地

- [x] 上記方針をリポジトリの正式なRustコード規約へ反映する — [反映のコミット](リンク)
- [ ] 既存コードから代表例・反例を数件選び、規約との整合を確認する — 未着手
- [x] #44〜#55のECS実装Issueから参照できる — 本issueのコメントから参照可能
```

**満たしていない条件を「満たした」と書かない。** 部分的にしか満たしていないなら、どこまで満たしたかを書く。

**issueを親が閉じない。** 完了を報告し、閉じるかどうかはオーナーが決める。

### issueへ返信が来たとき

裁定・追加指示・却下のどれであっても、**反映してから、反映したことを同じissueへ書く。** 裁定を受け取ったまま黙って実装すると、オーナーは自分の裁定が届いたかどうかを知る手段を持たない。

## PRのフロー

```
PRを出す(本文を書く)
  → push する
  → 本文を現在地へ更新する ← push のたびに
  → レビューを受ける
  → 吟味して対応する(原則2)
  → 返信を投稿する ← ここを飛ばさない
  → オーナーが受理する
```

### 本文に書くこと(2026-09-13改訂)

**PRの本文は、いまこの枝に何が入っているかを書く場所である。親がどう辿り着いたかを書く場所ではない。** 読み手が決めるのは1つ、マージするかどうかである。その判断に要らない情報は全部ノイズであり、要る情報を薄める。

親は次の4つを、この順で書く。

1. **何が入っているか。** 枝の最終の状態を書く。変えた対象と、変えた後どうなっているかである。複数あるなら表にする
2. **なぜそれが正しいか。** レビュアーが検算する筋道を書く。設計の正本があるならその行き先を書く。判断が分かれうる箇所は、採った方と採らなかった方を1文ずつ書く
3. **検証。** 検査の名前と結果の表。失敗しているものは、その原因と本PRとの関係を書く
4. **どこを見てほしいか。** レビュアーに重点的に見てほしい箇所と、**結果に残っている制約**である。受理の状態(原則5)もここへ書く

### PRの本文に書いてはならないこと(2026-09-13制定)

**親は、作業の途中で犯して直した誤りを書かない。**

- 直した誤りは**差分に残っていない**。残っていないものを書くと、読み手は「これは直っているのか、まだあるのか」を1件ずつ判定させられる
- 親の判断の変遷(最初はこう考えた、途中でこう変えた)を書かない。読み手が要るのは最後の判断だけである
- 「私は〜と誤った」「〜を撤回した」という記述を書かない

**例外は2つだけである。**

- **その誤りが結果にまだ残っているとき。** それは誤りの告白ではなく、残っている制約の説明である(上の4)
- **その誤りが、レビュアーの確かめるべきことを変えるとき。** 例: ある検査を一度通らないまま進めたので、この箇所だけ重点的に見てほしい

**では作業の経緯はどこへ書くのか。** ログ型の文書(`_doc/開発スレッド/`)である。そこは追記だけを許し、判断の経緯と失敗を残すために在る。PRとissueは判断のための文書であり、経緯のための文書ではない。

**違反の見分け方。** 本文からその1文を消して、レビュアーのマージの判断が変わるか。変わらないなら消す。

### オーナーへの報告(チャット)の書き方(2026-09-13制定)

本文の規律はチャットの報告にも当てはまる。加えて、**報告の先頭の1行に状態を書く。**

| 状態 | 意味 |
| --- | --- |
| **完了** | 全部終わった。次の指示を待っている |
| **作業中** | 誰かが動いている。親は待っている |
| **要判断** | オーナーの判断が要る。止まっている |

この1行が無いと、読み手は報告の全文を読んでから「これは終わったのか、まだなのか」を推測することになる。「〜しています」「〜を出しました」という書き方は、完了と進行中のどちらにも読める。

報告の中身は、やったこと・次にやること(または待っているもの)・判断が要るならそれだけである。**経緯と、撤回した判断の列挙を書かない。**

### push したとき

**検証の表を、いま走らせた結果へ更新する。** 古い数字を残さない。

**初回に書いた「次にやること」「別のPCでやること」の類は、完了したら現在地を書き換える。** 済んだ項目が未着手のまま残っていると、読み手が誤った前提でレビューする。

### レビューを受けて対応したとき

返信に次を書く。

1. **指摘ごとに、採用したか却下したかを書く。** 却下するなら理由を書く
2. **是正したなら、そのコミットへのリンクを名前つきで置く**
3. **裁定が要るものは、推奨を1つ選んで理由を書く。** 選択肢を並べるだけにしない
4. **レビューが指摘していない欠陥を対応中に見つけたなら、それも書く。** レビューした側は、自分の指摘が何を掘り当てたかを知る
5. **指摘が正しかったなら、正しかったと書く。** 実在を確認した経緯(現物のどこを見たか)を添える

### 枝を切ったらPRを出す。検証の完了を待たない(2026-09-13制定)

**親は、枝を切って push したら、その場でPull Requestを出す。** 親は、ビルド員の検証が終わるのを待ってからPRを出す形を採らない。

理由を書く。PRは、オーナーが読んで判断するための場所である。**検証の結果はPRの本文の1つの節であって、PRを出す条件ではない。** 検証を待つあいだ、その作業はオーナーから見えない。見えないものは存在しないのと同じであり、この規約が「書かないことは、やっていないことと同じである」と定めたことと同型である。

- 親は、PRを出すときに検証の節を「ビルド員が回している。結果が出たらこの節を更新する」と書き、結果が出たら更新する
- 親は、PRを出すことにオーナーの許可を求めない。**PRを出すことは提案であって、変更を入れることではない。** 許可が要るのはマージである
- 枝を切ったまま push もPRもしない状態を作らない

### 受理の範囲は、受理した時点の先端だけである(2026-09-13制定)

**既存のレビューは、後から足した変更へ自動で広がらない。** オーナーが受理したのは、レビューを投稿した時点のPRの先端であって、そのPRという入れ物ではない。

- **受理の後に意味を変える変更を足したら、親は、マージの前に新しい先端への再レビューを求める。** 親は、PRの本文を更新したことをもって再受理とみなさない
- **親は、受理済みのPRへ別件を足さない。** 関連する話題であっても、受理の範囲と実際にマージされる範囲がずれる。**「別のPRを作る本数を増やしたくない」を理由にしてはならない**
- 受理の後に足してよいのは、意味を変えない追随だけである(依存するPRのマージへのリベース、競合の解消、綴りの直し)。この範囲なら再レビューは要らない

制定の経緯: 2026-09-13、PR #105(節参照実在検査のログ型の一覧へ検査報告の置き場を加える)がオーナーの受理を得た3時間後に、親が同じ枝へ別の是正(マークダウンの強調で嵩んだ指示語を節名と誤読する件)を足した。親はPRの題と本文を「誤検出を2件直す」へ更新して裁定も求めたが、**既に出ている受理は1件目だけを見たものであり、マージには2件目も入った。** 親の動機は「6本目のPRを作らずに済ませたい」であり、それは理由にならない。中身は別途受理されたが、運用としては誤りである。

## issueとPRの接続

**PRがissueの完了条件を満たしたなら、両方へ書く。** PRの本文に「issue #45の完了条件のうちAとBを満たす」と書き、issueにも「[PR #57](リンク)で満たした」と書く。片方だけだと、もう片方を読む人が現在地を知れない。

**機能のPRから、恒久的な体制の変更が大きく育ったら、別のPRへ切る。** 機能の受理判定と体制の受理判定が1本に重なると、何を受理したのかが曖昧になる。2026-09-04のPR #57はこの形になり、レビューで指摘された。

## 違反のサイン

- 本文の先頭に「書き手: Claude Code」の行が無い
- 完了条件を1つでも見送ったのに `Closes #N` を書いている
- issueにラベルが無い、または状態のラベルが現状と違う

- 受理を得た後に足した変更が、再レビューを経ずにマージされている
- 枝を切って push したのに、Pull Requestを出していない
- 本文に、作業の途中で犯して直した誤りが書いてある
- 本文に、親の判断の変遷が書いてある
- チャットの報告の先頭に、状態(完了・作業中・要判断)の1行が無い
- 本文や返信にコミットハッシュが裸で並んでいる
- レビューへ対応したのに、そのPRへ返信していない
- issueの作業が終わったのに、そのissueへ完了報告が無い
- 「別のPCでやること」が全部完了しているのに初回のまま残っている
- 検証の表の数字が、いま走らせた結果と違う
- 文章チェック員を通していない
- リンクが404を返す(ハッシュの実在を確かめていない)
- 指摘を全部採用している(吟味が働いていない)
- 節の見出しが「変更点」「その他」のように、何が起きたかを言っていない
