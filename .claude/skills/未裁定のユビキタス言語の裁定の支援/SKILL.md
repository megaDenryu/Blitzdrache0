# 未裁定のユビキタス言語の裁定の支援

ユビキタス言語の語は、基本的にそっくりそのまま型名や関数名になっているべきである(2026-09-30 オーナー指示)。ところが AI は、実装の都合で型名を語から少しずらしたり、語の登録だけ別の言い回しにしたりする。この食い違いは、裁定の場でしか人の目に触れにくい。

- 語を選んだら、その語と同じ名前の識別子(型・関数・モジュール)があるかを確かめ、一致しているか・どこが違うかをオーナーに伝える。一致していないものを見つけたら、裁定の中身と別に必ず言う。例外として、グラフのノードとエッジの型は、語の後ろに「ノード」「エッジ」を付けた型名にする(`設計概念` → `設計概念ノード`、`設計関係` → `設計関係エッジ`。2026-09-30 オーナー指示)。
- オーナーがそのセッションで「ファイルを開いて」と言ったら、そのセッションの間は、語を選ぶたびに定義のあるファイルを vscode-lsp-mcp の `vscode.open` で開く。言われていないセッションでは開かない。
- 語の説明は、定義文を読み上げるのでなく、コードの実物(型の中身・どこで何に使うか)で書く。定義文だけでは、オーナーは何の話か分からない。
- 次に出す語は、ほかの語の土台になっている語(その語の意味で別の語の意味が決まるもの)を先にする。土台を先に決めると、後の語をまとめて直せる。
- グラフの用語はカタカナ(ノード・エッジ)で書く。

裁定を受けた後の反映は、次の順で行う。

1. 採用なら `_doc/計画/ユビキタス言語.md` へ定義を書き(裁定の日付を添える)、改名なら語と識別子を改めて旧称を書く。
2. `_doc/計画/pending_ubiquitous_language.md` からその語の行を消す。
3. 短い版 `_doc/計画/裁定待ちの語の短い定義.md` を生成し直す(`cargo xtask gen-pending-short-definitions`。古いままだと `cargo xtask conform` が落ちる)。
4. 裁定の反映用のブランチへコミットする。
