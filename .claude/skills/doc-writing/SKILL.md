# 文章規範(全文)

適用範囲: キャラクターなりきりとユーザーによる文体指定を除く全出力。ドキュメントに限らず、コード内コメント・コミットメッセージ・サブエージェントへの指示・チャット応答に適用する。要点はグローバルCLAUDE.md「文章規範」節に常時掲載する(本スキルが全文、CLAUDE.mdが要約という分担)。

根拠: 人間が一意に判定できない文はAIにも判定できない。曖昧な文は読み手(人間・サブエージェント・将来のセッションの自分)の推論コストを増やし、解釈ミスを生む。特にサブエージェントへの委譲プロンプトの曖昧さは、成果物の欠陥としてそのまま返ってくる。

制定経緯: 2026-07-20、Blitzdrache0 の性能方針文書に対するユーザー指摘から制定。「片道ドア」「大技」「桁で効く」のような独自の比喩・造語が文書を埋め、外部レビュー(Gemini)からも「解読の負荷を読者に強いる」と指摘された。チャットでは通じる短縮表現が、文書に持ち込まれると未定義語になる。同日、適用範囲をドキュメントから全出力へ拡大した。2026-07-27、手順文書でコマンドの実行場所が書かれていない点と、対象を名指しする前に数量詞で受ける文についてユーザー指摘があり、「文体」へ1項目と「手順の書き方」の節を追加した。

## 原理: 未定義語の出現は概念の未言語化のシグナル

- 文書に自分が発明した抽象語・比喩を書きたくなったら、それは**その概念をまだ正確に言語化できていない**ということ。DDDでユビキタス言語に無い語を使い始めるのと同じ構造の欠陥として扱う。
- 対処は2択のみ: (1) 業界で確立された用語に言い換える。(2) プロジェクトのユビキタス言語(用語定義ファイル)に定義を追加してから使う。どちらもできない語は、概念自体が未整理なので文書に書かない。
- チャットと文書は言語域が別。会話ではユーザー自身も短縮・比喩を使うが、それに引っ張られない。文書の唯一の基準は「このプロジェクトを知らない技術者が読んで一義に意味が取れること」。

## 言い換えの規準

- 確立用語を優先する。例:
  - 「税金」→ 抽象化が増やす実行時コストと保守コスト
  - 「片道ドア」「扉」→ 不可逆な決定 / 可逆な決定。可逆性の実体は「変更した場合の影響範囲が現在の構造で局所化されているか」なので、そう書く
  - 「桁で効く」「桁のコスト」→ 定量で書く: 「10倍以上の性能差」「計算量オーダーの変化」「広範囲な書き直しを要する改修」
  - 「大技」→ 大規模な最適化手法
- 影響度・規模は可能な限り定量(倍率・オーダー・工数・行数)で書く。「大きい」「重い」で止めない。
- プロジェクト内で定義済みの語(ユビキタス言語・規約文書に登録済み)は使ってよいが、その文書だけ読む読者のために初出で参照(`参照:`)を張る。
- 外部レビュー(他LLM含む)の語彙置換案は鵜呑みにしない。「未定義語で読めない」という問題指摘は事実でも、提案された置換語が正確とは限らない。置換語自体を自分で検証する(例: one-way door はAmazonの意思決定用語として実在するが、それを知らない読者には「不可逆な決定」の方が一義)。

## 定義の書き方(数学的ライティングの最小限の導入)

- 用語を定義する文は、それが定義であることが文法から一意に読めるように書く: 「**X**とは、〜のことである」「Xを〜と定義する」。
- 「**用語**: 名詞句」形式(例: 「不可逆な決定: 広範囲な書き直しを要する選択」)を定義に使わない。この形式は見出し・定義・説明のどれなのかを読み手が判別できない。
- 「用語: 説明」形式の箇条書きを使ってよい場面は2つに限る: (1) ファイルや節の目的自体が用語集(定義の列挙)だと宣言されている場合。(2) 属性の列挙(「予算: 4.0ms」のようなkey-value)で、コロンが表す関係が自明な場合。どちらの場合も、説明側を完結した文(述語で終わる文)で書くことを優先する。
- 定義してから使う。用語をその定義より前の位置で使わない。前方の節で必要になる場合は参照を張る。

## 文体

- 常体(である調)で統一する。文書内で敬体(です・ます)を混ぜない。
- 語順は主語→目的語→述語の素直な順で書く。強調のための倒置や、副詞を前置した断片文(「今、意識的に決める」のような形)を書かない。「意識的に」「しっかり」のような程度・態度の副詞は情報を持たないので削り、代わりに「いつ・誰が・何を」を書く。
- 指示語で締める文(「〜がこれ」「〜がそれ」)を書かない。指す対象を主語にした通常の文に直す。
- **主語を省略しない**(2026-09-04 オーナー裁定)。日本語の文法が主語の省略を許すことは、仕事の文章で省いてよい理由にならない。「文脈から復元できるから省いてよい」という判断を認めない。復元できるかどうかは書き手の主観であり、読み手が同じ復元をする保証が無い。判定は述語ごとに行い、その動作の主体が書かれていなければ違反とする。同じ文の中で複数の述語が1つの主体を共有する形(「`アプリ`は資源を持ち、工程へ渡す」)は、主体が書かれているため違反ではない。文が変わったら、また書く。
- **数量詞・指示語で受ける前に、対象を名指しする。** 「起床源は2本ある。両方を同時に立てる」と書くと、両方が何を指すのか読み手が決められない。「A と B の2つがある。この2つを同時に立てる」の順で書く。数だけ示して先に進まない。
- 断片文・体言止めは表・箇条書きの項目内でのみ許容する。地の文は主語述語の揃った文で書く。
- 太字は1節に1箇所程度に抑える。強調の多用で文章構造の欠陥を補わない。

## 改行規則(Markdown・コード内コメント共通)

- **文の途中で横幅を揃えるためのハード改行をしない。** 表示幅の調整はエディタ・ビューアのソフトラップの仕事。1行にできる文は1行で書く。
- 改行は意味の境界のみ: 1文ごと、または段落ごとに改行する。箇条書きは1項目1行。
- コードブロック・表・見出しは各記法の要求どおり。
- 既存文書・既存コメントの改行スタイル修正は、内容を直すときに併せて行う(改行だけの一括整形コミットはしない)。
- 背景: 80桁ルール(行長制限)はパンチカード・80桁端末由来の歴史的規約であり、学習コーパスに多いため模倣しがちだが、このユーザー環境では採用しない。フォーマッタが行長制限を強制する場合は設定で緩める(rustfmt: max_width増、clang-format: ColumnLimit 0 + ReflowComments false、Prettier: printWidth増、black/ruff: line-length増)。

## 手順の書き方

- **コマンドを書くときは実行場所(作業ディレクトリ)を併記する。** `uv sync` や `npm run build` は、
  どこで実行するかで結果が変わる。コマンドだけを書いた手順は、書いた本人以外には再現できない。
- **文書の置き場所と実行場所が違う場合は明記する。** サブフォルダに置いた文書のコマンドが
  リポジトリのルート基準なら、その旨を冒頭で宣言する。読んだ場所が実行場所だと読み手は考える。
- **作業ディレクトリを移動するブロックは絶対パスで書く。** 相対パスの `cd` を含むブロックは、
  それ以降のブロックの前提を変える。上から順に実行した読み手が自分の居場所を見失う。
  各ブロックを、直前のブロックの状態に依存しない形にする。
- 手順は実行環境の変化で嘘になる。仮想環境の導入やリポジトリの移設でコマンドが変わったら、
  文書だけでなく**エラーメッセージ内のコマンド**も併せて直す。

## 執筆後のチェック

1. 初見の技術者として読み直し、一義に取れない文を書き直す。
2. 未定義語の検出: 文書内の名詞・動詞句のうち、業界標準でもプロジェクト定義済みでもないものを列挙し、上記2択(確立用語への言い換え / ユビキタス言語への定義追加)で処理する。
3. 冒頭の1文で「この文書は何を管理する何の文書か」が主語・述語の通った形で言えているか確認する。
4. 手順を含む文書なら、書いたコマンドを実際に実行して通ることを確かめる。通らない手順は書いていないのと同じである。
