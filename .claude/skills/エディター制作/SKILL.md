# エディター制作スキル

## エディターとは何か

**計算で決まる値なら、エディターは要らない。** 計算すればよいからである。エディターが存在するのは、
人の知覚が決定機関である場所だけである。したがってこの道具の出力は、最終的に人の判断である。

そこから本スキルの全体が導かれる。人の判断の入力は画面に映っているものであり、
道具はその入力を汚してはならない。

## 本スキルが解く失敗

エディターの検査は、放っておくとすべて「データとデータの照合」になる。保存したものが読み戻せるか、
要求と応答が合っているか、数値欄と保存内容が一致するか、テストが通るか。
これらを何本積んでも、**データではないものへ渡る最後の1本の辺**、すなわち画面から人の目へ渡る辺は
一度も検査されない。エディターの欠陥はそこに集まる。

制定の経緯: 2026-08-10、GameScriptingTheory の画像切り抜きツールで2件の欠陥をオーナーに指摘された。
1件目は、原画を0.497倍という非整数の倍率で縮小して表示しており、最近傍補間が画素をほぼ1行おきに
捨てて、1画素幅の輪郭線が消えていた。2件目は、道具が生成する初期値が道具自身の保存検証を必ず落ち、
新しい画像を登録すると保存できなかった。**どちらも、規約適合の検査・テスト・保存の往復・数値の一致を
すべて確かめたうえで見逃した。** 機構は全部調べ、道具としては一度も使っていなかった。

## 第1条: 表示は正本と一致していなければならない

人の判断の入力がそこだからである。表示の途中に入る変換は、見た目を汚すのではなく**判断の入力を汚染する**。
しかも人には他の情報経路が無いので、汚染されたことに気づけない。

1. **暗黙の変換を入れない。** 拡大縮小、補間、丸め、切り詰め、既定値の補完を、表示の途中で黙って行わない
2. **縮尺を変えるなら整数比だけにし、人が選ぶ。** 自動で決めない。非整数の倍率で標本化した画素は、
   元の画素と別物である。画素を判断の対象にする道具では、これは表示の問題ではなく値の破壊である
3. **人が決めることを機械が黙って決めない。** グローバルCLAUDE.mdの「無言のデフォルト適用・無言の
   ゼロ値返却は禁止」は値についての規則だが、**表示にも同じ規則が要る**。窓に収めるための自動調整は、
   判断の前提を機械が勝手に決める行為である
4. **試し表示は本番と同じ規則で描く。** 別の経路で描くと、人は嘘に対して調整する。
   本番の描画式と試し表示の式を並べて突き合わせ、一致していることを確かめてから受け入れる。
   補間の設定（最近傍か平滑か）も本番に合わせる
5. **判断の対象が「揃っているか」なら、揃えるべきものを同時に見せる。** 1つずつしか見えない画面では、
   不揃いは原理的に発見できない。見えないものは直せない

## 第2条: 生成する値と受け入れる値の定義を一致させる

エディターは「値を作る側」と「値を検める側」の両方を持つ。定義がずれると、
**自分が作ったものを自分で拒否する**という状態になる。

1. **境界の扱いを1箇所で決める。** 区間が閉じているか半開かのような規則を、生成側と検証側で別々に書かない
2. **初期値・既定値・自動補完の結果が、自分の検証を通ることを機械で確かめる。** これは目視では見つからない。
   生成した値を検証にかける自動検査を書く
3. **同じ規則を複数箇所へ書かざるを得ないときは、出どころを1箇所に固定して全箇所から参照する。**
   規則の写しが増えるほど、ずれは必ず起きる

## 第3条: 強制の仕組みは起動経路を持たなければ存在しないのと同じ

検査を書いただけで安心しない。**人が思い出して手で打つ必要のある検査は、走らない。**

1. 新しい検査を足したら、**その場で検証の入口へ接続する**。接続までが作成である
2. 接続したら、**わざと落として、検証の入口が本当に止まることを確かめる**。確かめていない接続は接続ではない
3. 検査の順序に注意する。前の段で止まる形の試験をすると、後ろの段の接続を確かめたことにならない
4. 文書へ「検証列に含める」と書いたなら、実装がそうなっているかを確かめる。書いただけで満たしたことにしない

## 第4条: 検収は、その道具で実際にひと仕事を通して行う

規約適合と機構の検査をいくら積んでも、道具として使えるかは分からない。

1. **利用者が最初にやることを、最初から最後まで通す。** 新しい対象を開き、値を作り、調整し、保存し、
   反映されたことを確かめる。途中で止めない
2. **すでに正しい値が入っている対象だけで試さない。** それは道具が値を作る経路を通っていない。
   何も無い状態から作る経路こそが壊れる
3. **表示物と正本を機械で照合する。** 画像なら画素を突き合わせる。数値なら表示と保存内容を突き合わせる。
   目視の「同じに見える」で済ませない
4. **一仕事は「作る部品の種類」ではなく「人が通せる仕事」で切る。** 表示・入力・設定画面のように
   作る側の都合で回を分けると、どの回も単独では一仕事にならず、全部が揃うまで誰も通せない
5. **エディターごとに正準の一仕事を1本、実装の前に決めて書き出す。** テストの手順ではなく、
   その道具の存在理由を短い物語にしたものである。開く・作る・確かめる・保存する・読み直して同じものが出る、
   までを1本に含める。この1本が丸ごと通らないうちは受理しない

## 第5条: 受理は機械検証で閉じない

制定の経緯: 2026-08-28、Blitzdrache0の楽曲エディターと建物エディターが、型検査・lint・単体試験258件・
ビルド・規約検査・Rust側の検証列のすべてが緑の状態で、オーナーの試用により「使い方が分からない」と
判定された。**緑のランプが6種類あって、道具が使えなかった。** 原因は、本スキルの第4条を作る側が
「機械検証と実読」に読み替え、道具として通す検収を最後まで実行しなかったことである。
規範が足りなかったのではなく、飛ばせる形で置いてあった。

1. **完了を二値にしない。** 次の4つの状態を区別する。

   ```
   実装中 → 機械検証済み → 試用可能 → 受理済み
   ```

   **`機械検証済み` を `完成` と呼ばない。** 作る側が報告してよいのは `試用可能` までであり、
   `受理済み` は人が実際に触ってしか付かない
2. **一仕事を通せる最初の縦切りができた時点で、人へ渡す。** 全部の機能が揃うまで待たない。
   「数音置ける＋鳴らせる＋保存できる」が初めて揃った時点が渡し時であって、
   パネルが全部完成した時点ではない
3. **人が触るまで分からないことを、機械で検出しようとしない。** 「この色だけの立方体を見て建物だと
   分かるか」「このボタンを押さないと視点を回せると気づけるか」は人の認知の問題である。
   自動化しようとすると、検収した気になる緑ランプが1つ増えるだけになる
4. **機械で確かめられるものは確かめる。** 押した操作で状態が本当に変わる・押せない操作が実行されない・
   保存と読み直しで結果が一致する・キーボードの操作が契約どおり届く・操作の対応表に未分類が残っていない、
   はいずれも機械で検査できる。「人が触るしかない」を口実に、これらを省かない
5. **「内部でコマンドが積まれた」を受理条件にしない。** 人が見て状態の遷移を認識できるところまでを
   1つの操作とみなす。積まれたが画面が何も変わらないなら、その操作は成立していない

## 第6条: 実装の前に、操作の対応表か操作契約を作る

作るものが決まっていても、**どう操作するかが決まっていないまま実装へ入ると、
作った側の都合で操作が決まる**。人はそれを「意味不明」と呼ぶ。

**試作・元になる道具がある場合は、操作の対応表を作る。** 機能の一覧ではなく、実際の操作の手順で対応させる。

| 元での行為 | 元で見える結果 | 新しい道具での行為 | 新しい道具で見える結果 | 方針 |

方針は `同じ` / `意図して変更` / `廃止` / `別の手段へ置換` のどれかを必ず付ける。見た目まで完全に写す
必要はない。**違えるなら違えることを事前に決める**のが目的である。これを作らないと
「数式は移植したが、鍵盤の空白で再生できなくなった」のような抜けが検出できない。

**試作が無い場合は、操作契約を先に正本化する。** いきなり画面を設計させない。最低限、次を書く。

- 何を一仕事とするか
- 主な操作は何か
- 視点・選択のような共通の操作はどうするか
- 操作したとき画面に何が返るか
- 最初にどこを触れば始められるか

## 第7条: 画面の区画は、置くものの性質で決まる

制定の経緯: 2026-08-28、Blitzdrache0の楽曲エディターと建物エディターについて、オーナーから
「1個1個の部品自体は問題ない。配置の問題」と判定された。設定の部品が中央へ縦一列に並び、
編集の対象そのものを押し出していた。**同じ失敗が2つのエディターで独立に起きたのは、
本スキルの第1条から第6条がすべて「正しさ」の規範であり、「置き場」の規範が1つも無かったためである。**
置き場が決まっていないと、作る側は「作った順に上から縦へ並べる」という最も安直な形へ倒れる。

### 5つの区画と、それぞれが持つもの

外殻の形(VSCode風の外殻を使う場合)に対して、区画の役割を次のとおり定める。

| 区画 | 役割 |
| --- | --- |
| アクティビティバー | 何の編集領域を使うか |
| 左サイドバー | 何を開くか |
| エディタ領域 | 何を編集するか |
| 右サイドバー | 選んだものをどう設定するか |
| 下パネル | 何を配置・利用するか / 時間の方向にどう変えるか(必要なエディターだけ) |

**判断の基準は「人が編集中ずっと見ているか」である。** ずっと見ているものがエディタ領域、
ときどき触るものが右サイドバーである。**設定をエディタ領域へ置くと、編集の対象が押し出される。**

**一覧には2種類あり、置き場が違う。** 「いま選んでいるものの中の要素の一覧」(楽曲のパターン、
建物の階)は右サイドバー、「これから使うものの棚」(建物の部品、世界の配置物とブラシ)は下パネルである。
この2つを同じ区画へ置くと、選ぶ対象と使う道具が混ざる。

**下パネルは常設ではない。** 横長の棚か時間軸を一時的に広げる必要があるときだけ開き、
該当しなければ閉じたままにする。

**外形を借りることと、用途まで借りることは別である。** VSCode風の外殻を使っても、
Console・Problems・Log のようなプログラミングの用途をそのまま持ち込む理由は無い。
左サイドバーについても同じで、ファイルの木を引き写すと「性質の違うものが1本の木へ並ぶ」形になる。

### 固定とスクロールの規律

エディタ領域の中でも、固定するものとスクロールするものを分ける。

1. **文脈は固定する。** いま何を編集しているか(名前)と、対象の全体に効く操作(再生・保存・表示の切替)は、
   スクロールしても消えてはならない。消えると「いま何をしているか」が分からなくなる
2. **スクロールするのは、数が増えうるものだけである。** したがって**「増えうるものの並び」は
   1つの部品として括る**。その部品の中だけがスクロールする
3. **縦の幅を、増えないものへ使わない。** 名前を出すためだけに1行取ると、増えうるものの
   見える範囲がそのぶん狭まる。名前は操作の帯と同じ行へ収める

### 操作の割り当ては、編集の種類ごとに1つに決める

**同じ種類の編集をする道具は、同じ操作で動かなければならない。** 道具ごとに操作が違うと、
人は毎回学び直すことになる。編集の種類ごとに割り当てを1つ決め、**個々の道具のものにしない**
(共通の置き場へ寄せる)。

三次元を持つ道具の例:

```
右ドラッグ = 視点の回転 / 中ドラッグ = 視点のパン / ホイール = 視点のズーム / 左 = 編集の操作
```

**視点の操作をモードのボタンで切り替えてはならない。** モードが切り替えてよいのは編集の操作だけである。
視点を動かすたびにモードを戻す必要がある形は、道具として成立していない。

### 編集対象の名前

- 名前はエディタ領域の上部に出す(いま何を編集しているかを示すものだから)
- **名前を変えたら、タブの見出しも追随する。** 追随しないと、開いているタブのどれが今のものか分からなくなる
- 保存済みのものを開いたときも、見出しは識別子ではなく名前になる

## 違反のサイン

1つでも当てはまれば、道具として成立していない疑いがある。

- 表示の寸法が、対象の寸法と一致しない
- 表示の倍率をコードが自動で決めている
- 試し表示と本番で、描画の式か補間の設定が違う
- 判断の対象が1つずつしか見えない
- 道具が作った初期値を、そのまま保存すると失敗する
- 書いた検査が、検証の入口から呼ばれていない
- 検収の記録に「テストが通った」「保存できた」しかなく、「実際に1つ作ってみた」が無い
- **機械の検証がすべて緑であることを根拠に「完了」と報告している**
- **回の分け方が「表示」「入力」「設定」のように作る側の都合になっており、どの回も単独では一仕事にならない**
- 押しても画面が何も変わらない操作がある
- 元になる道具があるのに、操作の対応表が無い
- 元になる道具が無いのに、操作契約を書かずに画面を設計している
- **設定の部品がエディタ領域へ縦に並び、編集の対象を押し出している**
- **数が増えないものが、増えうるものと一緒にスクロールして消える**
- **同じ種類の編集をする道具どうしで、操作の割り当てが違う**
- 名前を変えてもタブの見出しが追随しない

## 検収時のチェック

- 表示物と正本を機械で照合したか。その方法は何か
- 本番の描画式と試し表示の式を並べて突き合わせたか
- 何も登録されていない状態から、1つ作って保存まで通したか
- 足した検査は、検証の入口を落とすことを確かめたか
- 人が決めるべき値を、コードが黙って決めている箇所は無いか
- 正準の一仕事を1本書き出したか。それは丸ごと通るか
- いま報告しようとしている状態は `機械検証済み` か `試用可能` か。`完成` と書いていないか
- 押したときに画面が何も変わらない操作は無いか
- エディタ領域に、編集の対象そのもの以外が置かれていないか
- スクロールする範囲が、数が増えうるものだけに絞られているか
- 同じ種類の編集をする他の道具と、操作の割り当てが揃っているか
