# アーキテクチャ先行スキル

**アーキテクチャとは「何が何を知ってよいか」の決定であって、機能一覧の予測ではない。** 要求が粗くても、依存の向きは決まる。ゲームを作ると分かった時点で「規則は描画を知らない」は確定しており、どの機能が載るかとは無関係である。

## 本スキルが解く失敗

行数制限と役割語彙は「1つのファイルに何を書くか」を決めるが、「層が何で、何が何を知ってよいか」を決めない。その結果、全ファイルが100行以内で、フォルダにも分かれていて、しかし依存の向きが無い塊ができる。検査は通り、構造は無い。

`layer-roles` スキルは層が既にある前提で中身の置き場所を決める。本スキルはその手前、**層そのものを決める**段を受け持つ。順序は本スキル→`layer-roles` である。

## 禁止する言い訳

次を、層を切らない理由として認めない。

- 「要求がまだ固まっていない」「仕様が確定してから」
- 「動いてから整理する」「まず最小で作る」（最小とはスコープの話であり、依存の向きを未定にする理由ではない）
- 「小さいので層は要らない」（小さいものが大きくなるとき、層は後から入らない）
- YAGNI（語の使用自体をグローバルCLAUDE.mdの禁止事項で禁じている）

**「可能性を閉じる決定を早期にしない」との関係**: グローバルCLAUDE.mdのこの規則は本スキルと衝突しない。依存の向きを決めることは可能性を閉じない。むしろ変更の影響範囲を局所化し、後から差し替える力を作る。同規則が明記するとおり、決定しないことと不可能にすることは別物である。層を切らずに書いたコードのほうが、後で構造を入れられなくなるという意味で可能性を閉じる。

## 数手先の構造を先に作る（投機的機能と混同しない）

人間の開発者は、コードを書いている最中に「これは後で必ず作る。今のうちに抽象化して層を切るべきだ」と気づく。**この気づきは投機ではなく、目の前のコードとドメインから読み取った観測である。** YAGNIが禁じているのは、誰が要求しているか分からない機能を先回りで作ることであって、この観測を捨てることではない。AIはこの2つを区別できず、両方を同じものとして扱って作業を省く。これが本スキルが潰す失敗の実体である。

区別は次の3点で付く。

| | 投機的な機能（今は作らない） | 数手先の構造（今作る） |
|---|---|---|
| 予測の出所 | 想像した将来の利用者 | 目の前のコード、ドメインの性質、既存の計画や別リポジトリの決定 |
| 対象 | 機能 | 構造（層、抽象、拡張点、正本の位置） |
| 時間軸 | 不定 | 数手先。同じ作業の中か、数分から数時間後に確実に来る |

**ユーザーが説明していないことは、要求が無いことを意味しない。** ユーザーの頭の中には数手先があり、聞かれれば答えられる状態にある。実際には数分後に対処が要求される。人間の開発者が予測して対処するのと同じことを行う。

行動は次のとおり。

1. **目の前のコードから構造が導けるなら、今作る。聞かない。** 2つ目が現れた時点で3つ目が来ると考える。データが手で編集されているなら編集の道具が来ると考える。ドメインの性質から必ず来ると分かるものは、来たものとして扱う
2. **スコープの判断が要るとき（「Xも今作るか」）だけ、観測を1行で述べ、推奨を添えて聞く。** これはグローバルCLAUDE.mdの「ユーザー確認の最小化原則」に反しない。同原則が認める「自分では決められない仕様判断」そのものである
3. **気づきを言語化せずに捨てない。** 「後で要るかもしれない」と思った瞬間に、その思いつきを自分で握り潰して黙るのが最悪の行動である。観測は1行で述べれば、ユーザーは1行で肯定も否定もできる

## 手順

### 1. 既定の形から始める（決め打ちしてよい）

ドメインの種類が分かれば出発点は決まる。ここから始め、要らない層を削る形で進める。ゼロから毎回導出しない。

| ドメイン | 既定の層（矢印は「知ってよい」向き） |
|---|---|
| ゲーム | 規則（描画も入力も知らない） ← 内容データ ← 表示殻（エンジン依存はここだけに閉じる） |
| 編集ツール・開発環境 | 型契約 ← 操作コマンド ← 永続化境界 ← UI。**操作コマンド層を核にする**（Blitzdrache0 `_doc/設計/ゲーム制作アーキテクチャ.md` 判断8） |
| Webアプリ・サーバー | 契約 ← サービス ← ハンドラ、境界は別、配線はコンポジションルート1箇所（役割語彙は `layer-roles`） |
| CLI・タスクランナー | 引数の解釈 ← 手順 ← 外部プロセス境界 |
| ライブラリ | 公開型 ← 内部実装 ← 外部境界 |

同じ種類のものを別リポジトリで既に作っているなら、**その決定を先に読む**。リポジトリが違うことは、決定済みの形を無視してよい理由にならない。

### 2. 足りない情報だけ聞く。候補提示は必須

**黙って進むのも、全部聞くのも違反である。**

1. 自分で導けるものは導く。ドメインの種類、正本がどこにあるべきか、何が長生きすべきかは、たいてい要求から導ける
2. 聞くのは、**答えによってアーキテクチャの形が変わる問い**だけ。代表例は次の4つ
   - 何を将来差し替えるつもりか（エンジン、保存先、画面）
   - データの正本はどこか。誰が編集するか
   - 同じものを別の入口からも使うか（画面とCLIとAPI）
   - 壊れてはいけない不変条件は何か
3. 聞くときは**2〜3案を出し、それぞれ「後で何が難しくなるか」を1行で書き、推奨を明示する**。表形式の長大な比較はしない
4. 質問は最大3つ

これはグローバルCLAUDE.mdの「ユーザー確認の最小化原則」と矛盾しない。同原則は仕様判断・設計判断のうち自分で決められないものを聞くことを認めている。導かずに聞くのが違反であり、聞かずに構造を捨てるのも違反である。

### 3. 決めたことを1つの短い文書に書く

見本は Blitzdrache0 `_doc/設計/ゲーム制作アーキテクチャ.md`。次の4節で足りる。

1. **目的**: この系が何を成立させるか
2. **層の定義**: 層名 / 何を持つか / 何を知ってよいか。表1つ
3. **主要な設計判断**: 番号付き。見出しが一文で結論を述べる形にする（「判断3: 入力は2段構えにする」）
4. **この段階でやらないこと**: 何を、なぜ今作らないかを具体的に書く

生存型文書なので索引へ登録するまでが作成である（参照: グローバルCLAUDE.md「ツールとドキュメントの配置規約」）。

### 4. 機械強制の手段を同時に決める

**「文書に書いた」は強制ではない。** 境界を破ったときに何が落ちるかを決めて初めて境界が存在する。手段の例。

- クレート・パッケージの分割（依存を書かなければコンパイルできない。最も強い）
- モジュールの可視性
- import の向きを検査する規則
- lint の deny

強制の手段を選べない境界は、境界ではなく願望である。その場合は層の切り方が実態に合っていないことを疑う。

### 5. 層の中へ入る

層が決まったら `layer-roles` スキルで役割語彙とファイルの置き場所を決める。層の内側にも同じ規律を再帰的に適用する。

## 違反のサイン

1つでも当てはまれば、アーキテクチャが無い状態である。

- 同じ役割語（サービス・マネージャ・状態・ハンドラ・ユーティリティ）を持つファイルが3つ以上あり、互いの違いがどこにも書かれていない
- どのファイルがどの層に属するかを即答できない
- 境界を破るコードを書いても、何も落ちない
- フォルダは分かれているが、フォルダ間の依存の向きが決まっていない
- 全ファイルが100行以内なのに、1つの流れを追うのに5ファイルを行き来する
- 「とりあえず動く形」と「本来の形」が別にあると自分で思っている

## 検収時のチェック

- 各ファイルについて、属する層と、知ってよい相手を言えるか
- 依存の向きの違反を検出するものが実在するか。人の注意力でないか
- 層の定義の文書と実装が一致しているか。ずれたら実装に合わせて文書を直す
- 既定の形（手順1の表）から外れているなら、外れた理由が設計判断として書かれているか
