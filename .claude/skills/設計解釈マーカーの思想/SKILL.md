# 設計解釈マーカーの思想

設計解釈マーカーの意義は、Rust上の型が設計上何であるかを宣言し、その意味を語彙として固定することである。AIは、意味の拘束を無視した、意味の分からない語彙をどんどん増やしていく。設計解釈マーカーは、それを防ぐための意味論の基盤である。型が設計上何であるかをマーカーで宣言し、そのマーカーが守るべき性質を公理として置く。`M不変データ` の不変性は、その公理の1つである。

- マーカーの役目は、型を書く・直すAIに、その型が設計上何であり、どの法則を守らなければならないかを気づかせることである。`M不変データ` は、すべてのマーカーが持つこの役目を特に重視するマーカーである。「これは不変にしないといけない。そして今後もそれに固定されていないといけない」と、型を書く・直すAIが思うために `M不変データ` がある。
- AIが実際に犯す間違いは、不変性という観点を持たず、不変にすべきものを不変にしないことである。マーカーを実装したのに書き換える、という間違いは、いまのAIも人もしない。
- だから、マーカーの法則の違反を完全に機械で検知する仕組みは要らない。それを作ろうとすると、起きない間違いのために検査が膨れ上がる(PR #177 では約100ファイル・約5,600行に膨れた)。
- 現実に起きうるのは、マーカーを実装した型の `impl` を別のファイルに書き、マーカーを見ないまま書き換えることである。マーカーが目に入らない場所に実装を書かせるな。マーカーを実装した型の実装は、定義と同じファイルに置け。実際に違反が起きうるこの経路は、`cargo xtask conform` の警告が検出する。
- **マーカーに関わる機械の検査を足す前に、次の2つを問う。**
  1. **印を1つも付けないプログラムで、その検査は文句を言えるか。** 言えるなら作らない。「印 X が付いたものは性質 P を満たす」を確かめる検査(印が起点)は、印が無ければ調べるものが無く必ず合格する。これは許される(例: 存在理由の公理 A1〜A6、`M射影関数<状態, 状態>` の禁止)。「形 F を持つものには印 X が付いていなければならない」を確かめる検査(形が起点)は、印が無くても「この形なのに印が無い」と文句を言える。これは作らない。印は形から読み取れない書き手の意図を運ぶものであり、形から印の付け忘れを探すことは印の存在理由と食い違う。付け忘れは、書き手と検収が見れば気づける。実例として、2026-09-28 に Issue #175 で足した法則 A7(状態を受けて同じ状態を返す関数は遷移か規則によらない書き換えを宣言する)は形が起点の検査であり、検収の是正を11回回して抽出器を膨らませ、2026-09-30 のオーナー判断で外した
  2. **性質 P を判定するのに、印と宣言以外のコードまで全部読む必要があるか。** 要るなら原則作らない。起点が印でも、判定のために全ての関数の本体や署名を漏れなく読む検査は、読めない書き方が出るたびに読み方と例外を足すことになり、膨らみ続ける。印や宣言の型引数の中だけで判定できるなら問題ない(A1〜A6 はこちら)。実例として、Issue #175 の Phase 8(印の付いた型がアプリケーションから使われていることを、main とコンポジションルートの呼び出しを読んで確かめる)はこれに当たり、2026-09-30 のオーナー判断で取りやめた
  - 2つを満たしても、足す前に、見逃すと何が壊れるかを実際に起きた例で示し、コンパイラ・書き手・検収で捕まらないことを確かめる。例が無ければ足さない
- **AIは、この2つの問いで答えが決まる検査の是非や範囲(「〜も捕まえるよう広げるか」「〜の付け忘れを検出するか」)を、オーナーへ持ち込まない。** この種の問いを繰り返し諮ると、オーナーの手をふさぎ、プロジェクトの妨げになる(2026-09-30 オーナー指示)
- 新しい型を足すときは、それがどのマーカーの意味に当たるかを考えろ。どのマーカーにも当たらない型が増えるなら、その型が設計上何であるかを説明できていない。
- `M不変データ` を実装した型が守る書き方の規約(既存の値をその場で書き換えないこと・自己変更を行う API を持たないこと、および struct と enum それぞれの規約)は機械で検証しない。正本は `_doc/設計/設計オントロジー.md` 2.5.3 である。
