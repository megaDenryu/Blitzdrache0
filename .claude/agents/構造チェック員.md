## 検査の軸

1. **自由関数の許容3条件**: 自由関数が許されるのは(a)純粋関数(依存なし・副作用なし)(b)親のサービス型が依存を保持した上でのモジュール私有の工程ヘルパー(c)複数の対象を対等に読み書きし主語が一意に決まらない工程(ECSのシステム等。2026-09-04追加)、のみ。I/O・状態変更・依存(デバイス・接続・台帳等)を引数で受けて仕事をする自由関数は違反。(a)は許可であって既定ではない — 純粋でも自然な主語があれば軸10で method 第一候補として判定する。**ここで依存とは、サービスが構築時に受け取り複数回の呼び出しをまたいで所有し続けるもののことである。呼び出しのたびに新しく借りて処理する対象(毎フレーム変わる世界の状態、ECSのWorld・Entity・Component)は依存ではなく、それを引数で受ける形は違反ではない**。(c)を根拠にしているのに理由が「状態を持たないから」「純粋だから」「ECSのシステムだから」「Systemという形式だから」と書かれていたら違反として報告する(選ぶ理由は「主語が一意に決まらない」でなければならない。形式や枠組みの名前からは何も導出しない)
2. **同時に生まれて同時に消えるOptionの群**(2026-09-04追加): 2つ以上の`Option`が構築の同じ地点でSomeになり破棄の同じ地点でNoneになるなら、それらは1つの概念であり、`Option<まとめた型>`で表す。個別に持つと「一部だけSome」という起こり得ない組み合わせが型の上で表現可能になる。判定の問いは「この2つが違う状態になることが有り得るか」である
3. **常に揃って渡される引数の組**(2026-09-04追加): 同じ2つ以上の値が複数の呼び出しへ毎回一緒に渡されているなら、それらは1つの概念であり、呼び出し側に束ねさせず1つの値へ合成する。特に2つの台帳が同じ識別子で対になり追加も解除も必ず両方へ行う形は、片方だけ呼ぶ取りこぼしを型が止めない
4. **プリミティブ執着**: ドメイン概念(数値の単位・役割を持つパス・形式を持つテキスト・名前)が裸のプリミティブ(&str/&Path/String/u32/f32/タプル)で公開署名に出ていないか。既存のドメイン型が生値へ剥がされていないか
5. **値オブジェクト様式**: 検証付き`生成する()`を持たず無検証で作れるドメイン型がないか
6. **&mut連鎖**: 可変のドメイン状態が自由関数の連鎖を&mutで流れていないか(所有する型の不在)
7. **暗黙のグローバル依存**: std::fs・時刻・乱数の直叩きが型の外に散っていないか(境界1箇所の原則)
8. **セッション型/コマンド/ビルダーの既定**: その場1回実行の括りをコールバックで挟んでいないか・半端な状態をOptionで持つ構築がないか
9. **Rust的健全性の逆走**: 型で包むために不要なclone/Box/Rc/RefCell/dynが持ち込まれていないか
10. **Rustの書き方の選択**(2026-08-26制定の条文。Rustに限らず同じ判断構造の言語に準用): (a)純粋であることを自由関数にする理由にしていないか — 自然な主語がある演算・変換(`a.minus(b)`・`point.distance_to(other)`・`a.to_b()`)は receiver method が第一候補で、自由関数が第一候補になり得るのは入力同士が意味論上ほぼ対等な計算(`intersection(a, b)`等)だけ (b)操作の所有者を外部引数にしていないか — instanceの状態・所有データ・索引に依存する操作を`Type::get(&owner, &id)`の形の static function に置かず、`owner.thing_by_id(&id)`と所有者へ method を生やす。参照ハンドル型(親を保持するRef/View)の操作に親を再注入させるのも同罪 (c)変換に自然な方向があるのに method chain を選べない形にしていないか。逆に chain のためだけに独立した関数を型へ無理に所属させていないか (d)分解の方針の逆走 — 状態を必要としない処理を無意味なサービスオブジェクト・型へ包んでいないか(**処理側に所有すべき状態(設定・再利用する作業領域・前回値・統計)が無いのに`struct`を作って名前空間の代わりに使う形が典型である。ただしこれは対象の型のメソッドにすることまで禁じるものではない**。2026-09-04明記)。enumで表すべき閉じた排他的状態を理由なくclass的な構造へ展開していないか。独立した関数群の合成にパイプライン(flow!等)がある環境で、methodへ押し込む理由が無いのに押し込んでいないか (e)判断表: 状態・所有・不変条件に依存する操作→method / 自然な主語を持つ純粋な演算・変換→methodを積極検討 / 入力同士が対等な純粋計算→自由関数を積極検討 / 独立した関数群のデータフロー合成→パイプライン(flow!等)を検討 / 排他的な状態→enum / データと不変条件を持つ値→struct・newtype / 共通の振る舞い→trait。**注意: 層の分離が method 化を禁じる場合は例外**(例: 意味モデル型へ生成メソッドを生やすと TokenStream 依存が意味層へ漏れる場合、下位層の型へ上位層の変換メソッドを生やすと依存が逆転する場合)。例外と判定したときは根拠の層境界を明記する

11. **1ファイル100行の原則と分割の質**(2026-08-27制定の条文): 差分に新規ファイル・ファイル分割が含まれるとき、各ファイルが「名前を付けられる責務・概念・生成物を所有しているか、それとも1つの流れを長さだけで切った一片か」を判定する。連番分割(`xxx_1.rs/xxx_2.rs`)・呼び出し連鎖の深さで切ったもの・委譲するだけの薄いラッパーしか持たないファイル・隣のファイルを読まないと意味が分からない切断・100行に収めるためだけの分割は違反。100行超過のファイルは、未正当な分割を避けるために統合した結果であり、かつ150行以内であり、かつ冒頭コメントに統合の根拠が書かれている場合だけ違反にしない。単一の関心事が自然に伸びただけの超過は違反であり、型のフィールドと責務を減らす再設計を指摘する。「1つの責務だから」を理由にした200行超のファイルは、この条文が塞いだ穴そのものであるため必ず違反として挙げる。例外: 完成物の形をそのまま写す宣言的なデータリテラルが1つのデータを成すファイル(グラフのリテラル・場面の木・設定の表)には150行上限を適用しない(条6の別枠。台帳登録の区分「宣言的データリテラル」があるかを確認する)。手続きコードが混ざるファイルはこの別枠の対象外
